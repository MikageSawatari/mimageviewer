## 0. 要約

- 動画の音声を、**PC 内で動く音声認識モデル (whisper large-v3-turbo)** で時刻つきの文にし、mIV に保存する。音声は PC の外へ出ない。
- 用途は 3 つ。
  1. 動画のフルスクリーンの**左パネルに「文字起こし」タブ**を足し、時刻の順に並べる。行を押すとその時刻へ移る (2026-11-11 利用者の案)。
  2. **検索** (Ctrl+G / Ctrl+F) で、話された語から動画を探す。
  3. **MCP** で、文字起こしを AI アプリへ渡す (「この動画を要約して」「〜と言っている動画を探して」)。**最初の段階に入れる** (2026-11-11 利用者決定)。
- 推論は whisper.cpp (MIT) を組み込んだ**別プロセスの worker** (`mimageviewer-asr.exe`) で行う。本体とは匿名パイプでつなぎ、ネットワークで待ち受けない。
- 設定は評価で決めたものに固定する: **turbo (Q5_0)・前の文を渡さない (`-mc 0` 相当)・VAD を使わない・VAD を使わない後処理**。
  選ぶ画面は作らない。
- 始め方・ジョブ・保存・索引への反映・表示用キャッシュ・削除は、AI 説明文と同じ形にする。違うのは「長い・時刻つき」と「処理が長い」の 2 点。

## 1. 目的と範囲

### 含むもの (初回の版)

- お気に入りの中などにある**動画ファイル** (FS 上の実ファイル、`GridItem::Video`) の文字起こし。
- 利用者が明示的に始める作成ジョブ (選択した動画・現在のフォルダの直下の動画)。進捗表示と中止。
- 保存、動画フルスクリーンの左パネルでの表示とジャンプ、Ctrl+G / Ctrl+F の検索、MCP (項目情報・文字起こしの取得・検索)、
  メタ情報の書き出し / 取り込み、削除。

### 含まないもの (初回の版)

- 音声ファイル (`GridItem::Audio`)。音楽ビューの左パネルは別の部品 (ブックマークだけの一覧) なので、後段で扱う (U5)。
- ZIP の中の動画、Remote での表示、MCP から作成ジョブを始めること、何もしていない間の自動作成。
- 読み (かな) での照合。評価では効果があったが (題名の語の当たり 222 → 301)、使える部品の同梱に課題があり (§9.4)、
  ファイル名・説明文の検索にも効く別の機能として後段で扱う。
- 話者の区別、翻訳、字幕ファイル (SRT 等) の書き出し。
- 利用者が任意のモデル・言語・設定を選ぶこと。

### 内容に関与しない方針

AI 説明文 (§1 の同名の節) と同じ。出力の意味による選別・書き換えはしない。行うのは §6.4 の機械的な後処理
(繰り返し・ループ・決まり文句) だけ。公開文書では「音声を AI が文字にしたもの。聞き違いや抜けがある」と処理内容で説明する。

## 2. 評価で分かったこと (設計に効くもの)

数値は開発側で whisper.cpp v1.9.5 (Vulkan、RTX 4090) の CLI を回した結果 (製品バイナリではない)。
素材は正解つきの 5 本 (計 14.5 分) と利用者の動画 8 本 (計 475 分、A〜H)。

| 分かったこと | 設計への反映 |
| --- | --- |
| turbo は large-v3 より精度が良く約 2 倍速い。medium は turbo より遅い。日本語特化の Kotoba v2.0 は長尺で崩れた | モデルは turbo の 1 つに固定 (§3) |
| 既定の設定 (前の文を手がかりにする) は、長い配信で同じ文の繰り返しに崩れる (turbo・medium・large-v3 とも) | 前の文を渡さない (`n_max_text_ctx = 0`) |
| VAD は幻覚を消すが、高い声 (キャラクターのセリフ、F で利用者が確認) と BGM に重なった声を丸ごと落とす。しきい値を下げても直らない | VAD は使わない |
| VAD を使わない後処理 (決まり文句・ループ・繰り返し) で、崩れた 1 分の区切りが 32 → 1。正解つき素材では CER が全素材で最良、消えた正しい文は 0 | 後処理を移植する (§6.4) |
| 推論は音声の約 2.5% の時間 (8 本 475 分で 11.8 分)。初回だけシェーダの準備に約 11 s | 長い動画は 1 本で数分。進捗は動画の中の割合も出す (§6.1) |
| CPU だけ (8 スレッド) でも文字はほぼ同じで、音声の約 42% の時間 | CPU で動かすかは U2 |
| 2 本目の音声トラックの開始が動画より遅い動画では、先頭を再生時刻 0 から無音で埋めないと、時刻が約 3 s ずれる | 抽出は再生時刻にそろえる (§6.3) |
| VAD を使わないと、区間の始まりが直前の無音の分だけ早い (中央値 0〜3.2 s、最大 12.5 s) | ジャンプは少し前から始まる。遅れるより良いので初回はこのまま (§8.3) |
| whisper.cpp は区間の境目で 1 文字の UTF-8 を割ることがある (評価の G で JSON の読み込みが失敗した) | worker で区間の文字列を組み直す (§4) |

## 3. モデル

- **whisper large-v3-turbo の Q5_0 (約 574MB) に固定する**。重みは OpenAI が MIT で公開しているもの。
- 言語は**日本語に固定**して始める (whisper の `language = "ja"`)。評価は日本語だけで行った。U3。
- 復号は評価と同じ beam 5・best-of 5。
- 配布は AI 説明文と同じく追加ダウンロード (`<data_dir>/addons/asr/packs/<model_id>/`、GitHub Releases の固定タグ、sha256 で検証)。
  2GiB 未満なので分割は要らない。どこで量子化したものを配るかは U4。

## 4. 推論エンジンと worker の構成

- whisper.cpp を版固定 (評価と同じ v1.9.5) で組み込んだ C++ の worker exe を作る。形は VLM worker (`crates/vlm-worker`) と同じ:
  CMake、Vulkan 版、静的リンク、本体に内包して `<data_dir>/asr/workers/<sha256>/` へ取り出す (VLM の `vlm_worker_extract.rs` と同じ)。
  ポータブル版でも使える (VLM の U21 と同じ扱い)。
- **VLM worker とは別の exe にする**。llama.cpp (b12032) と whisper.cpp は別の版の ggml を同梱しており、1 つの exe に静的リンクすると
  シンボルが衝突する。whisper.cpp を llama.cpp と同じ ggml で build できれば 1 つにまとめて配布サイズを減らせるが、未確認 (§13)。
- ネットワークに触れないことを、リンクする範囲で保証する。whisper.cpp に HTTP の部品は無いが、VLM と同じく build の検査で
  worker exe の import に `ws2_32.dll`・`winhttp.dll`・`wininet.dll` が無いことを確かめる。
- **使う GPU は VLM と同じ判定関数で選ぶ** (専用メモリが最大のアダプタ、Vulkan の device LUID と DXGI の LUID で突き合わせる。
  VLM 計画 §4)。判定に使う VRAM の境目は T0 の計測で決める (§11)。
- worker の寿命: 作成ジョブの開始で起動 → モデル読み込み → 1 本ずつ処理 → ジョブの終了・中止・mIV の終了で終了。
  Job Object の kill-on-close で、本体が落ちても残らないようにする。常駐しない。
- **音声の入力は本体の FFmpeg で作る** (§6.3)。worker は FFmpeg を持たない。VLM が本体のデコーダで読んだ画像を渡すのと同じ分担。
- **区間の文字列は worker でトークンのバイト列から組み直し、UTF-8 として完結した形で返す**。区間の末尾で割れた文字のバイトは
  次の区間の先頭へ持ち越す。本体は受け取った文字列を UTF-8 として検証し、不正なら失敗として扱う (置き換え文字で黙って直さない)。

## 5. 長い音声の扱い

配信のアーカイブは数時間あり得る (利用者の動画にも 2 時間を超えるものがある)。16kHz の float で 1 時間 230MB なので、
whisper.cpp の CLI のように全体を 1 つの配列に読むと、長い動画で worker のメモリが数 GB になる。

- **本体は FFmpeg で頭から順に変換し、16kHz・モノラル・16bit の PCM を小さな枠 (1MiB 程度) でパイプへ流す**。一時ファイルは作らない。
- **worker は 30 分ずつの窓で推論する**。窓の終わりは、境目の前後 10 s のうち音の最も小さい 0.5 s の中央で切る
  (音の大きさだけで決める機械的な規則。VAD のモデルは使わない)。窓をまたいで渡す状態は持たない (前の文を渡さない設定のため)。
- **窓に分けると、全体を 1 回で処理した評価の結果とは変わり得る** (独立レビュー 1 回目 P2-6 で改めた)。whisper.cpp は呼び出しごとに
  入力全体の特徴量を計算し、その最大値で正規化する (評価に使った v1.9.5 の `whisper.cpp` の log-mel の処理)。末尾の処理や時刻による
  内部の窓の進み方も変わるので、差は境目の近くだけとは限らない。
- そのため T0 で確かめる。正解つき素材は合計 14.5 分で 30 分の境目を含まないので、**境目を含む正解つきの長い素材**
  (既存の素材を無音・BGM を挟んでつないだ 45 分以上のもの) を作り、合格条件を先に決めてから測る:
  全体の CER が 1 回処理と比べて悪化しないこと、境目の前後 30 s で発話の欠落・重複が無いこと、時刻のずれが 1 回処理と同程度であること。
  利用者の 8 本でも、1 回処理との食い違いを数える。満たさなければ、窓の大きさを変えるか、全体を 1 回で処理してメモリの上限で長さを割り切るかを決め直す。
- 本体側の変換は worker の推論と並行して進め、worker が窓を受け取りきれないときはパイプの書き込みが待つ (背圧)。
  変換の位置と推論の位置から進捗を出す。

## 6. 作成ジョブ

### 6.1 始め方と進捗

- 一覧の右クリックまたは「ツール → 文字起こしを作る」。対象は選んだ動画、何も選んでいなければ現在のフォルダの直下の動画。
  画像・本・音声などは対象外として件数を知らせる (AI 説明文の受入 C と同じ形)。既定のショートカットは割り当てない。
- 初めて使うときは、モデルの取得案内 (モーダル) を出す。書く内容: 何をするか (音声を PC 内で文字にする、PC の外へ出ない、
  聞き違い・抜けがある)、取得するもの (約 574MB、取得元、ライセンス)、[ダウンロード] [今はしない]。GPU が条件に満たないときは
  取得を勧めず理由だけを出す (U2)。取得の画面・キャンセル・`.partial` の再開は AI 説明文と同じ部品を使う。
- 進捗はモードレスの小窓: 本数 (処理済み / 全体)、今の動画の名前と割合 (音声の何分まで)、作成・既にあり・失敗の件数、中止。
  同時に動く文字起こしのジョブは 1 本。作成中に頼まれた分は後ろに足す。小窓を閉じてもジョブは続き、「ツール → 文字起こしの作成状況」で再表示する。
- **AI 説明文のジョブとは独立に動かし、互いを待たない** (§10 R2)。

### 6.2 1 本の流れ

1. 保存済みの行が「`status = ok`・同じ動画 (署名一致)・同じ音声トラック・同じモデル・同じ設定の版」なら飛ばす。失敗の行は飛ばさない。
2. 動画のパスと署名 (サイズ・更新日時) を覚え、§6.3 の抽出を始める。
3. worker が窓ごとに推論し、区間 (開始・終了・文) を返す。
4. 全体が終わったら、本体が §6.4 の後処理をかけ、§7 の規則で保存し、索引への反映を待たせる (§9)。

### 6.3 音声の抽出

- 音声トラックは、**その動画を開いたときに再生側が選ぶトラック**を使う。再生側は、利用者が前に選んで保存したトラックを、
  コンテナの既定のトラックより優先する (`video::audio_track_selection::resolve_initial_audio_track`。独立レビュー 1 回目 P3-2)。
  作成ジョブも同じ関数でトラックを決め、「どのトラックを聞くか」の判断を 2 か所に書かない。選んだトラックの番号を行に記録する。
- 後から利用者が別のトラックに切り替えても、行は 1 つのまま作り直さない (§12 R4)。左パネルと MCP の応答に、文字起こしに使ったトラックを示し、
  今再生しているトラックと違うときはタブの上に「別の音声トラック (2 本目) から作った文字起こしです」と 1 行出す。
  「古い」にはしない (動画は変わっていないため)。
- 時刻は**再生時刻にそろえる**: 音声の先頭が動画の開始より遅いときは、その分を無音で埋める (評価の `aresample first_pts=0` と同じ結果)。
  評価では、埋めた場合のずれは 3 ms だった。
- 音声トラックが無い動画は、何も保存せずに「音声なし」として件数に数える。

### 6.4 後処理 (評価の `postprocess.py` の `speech=None` を移植)

順に 3 つの規則をかける。定数は評価で決めた値に固定し、規則を変えたら設定の版 (`pp_version`) を上げる。

1. **決まり文句を除く**: 文全体が締めの決まり文句 (「ご視聴ありがとうございました」「チャンネル登録をお願いします」の類、正規表現は評価のまま) で、
   区間が 5 s 以上か 1 s 未満のものを除く。本当に言われた締めの言葉は 2〜3 s の区間だった。
2. **ループを縮める**: 1 区間の中で 1〜8 文字の同じ並びが 5 回以上続く所を 3 回分に縮める。
3. **繰り返しを除く**: 直前の 5 区間 (60 s 以内) と、正規化した文が同じ区間を除く。比べる履歴には除いた区間も含める。

- 除いた区間の数と規則ごとの内訳は行に記録する (表示はしない。不具合の調査用)。
- 評価で捨てた案: 「長い区間に文字が少ないものを除く」。正解つき素材では、密度の低い区間はむしろ本当の発話だった。
- 決まり文句の一覧と長さのしきい値は利用者の動画の出力を見て決めた。別の動画で一覧の外の幻覚が出る可能性は残る (§13)。

### 6.5 中止と失敗

- **中止は worker のプロセスを終わらせて行う** (既存の kill handle、`vlm_worker.rs` の `KillHandle` と同じ。独立レビュー 1 回目 P2-2 で改めた)。
  VLM worker は入力の読み取りと推論が 1 本の直列のループなので、推論中に中止の命令を読めない。whisper の中断の callback も、
  PCM の書き込み待ちや窓の受信中には効かない。中止すればそのジョブは終わるので、worker を残す理由が無い。
  - ジョブの持ち主 (App に 1 つ) が中止を受けたら、受付を閉じて `Running → Stopping` にし、本体側の FFmpeg の変換を同じジョブの
    取消の印で止め、worker を終わらせる (パイプの書き込み待ちは相手が終わることで解ける)。途中の結果は保存しない。
  - **中止の後に捨てるのは、まだ保存していない推論の結果と進捗の更新だけ** (独立レビュー 2 回目 P2-1)。保存役が DB の commit を済ませた
    「保存した」の知らせと、ジョブの「終了した」の知らせは、中止の後でも受け取って処理する (索引への知らせと表示キャッシュの消去を漏らさないため)。
    持ち主は「終了した」を受け取るまで `Stopping` のまま残る (AI 説明文の作成ジョブ `ui_dialogs/caption_job.rs` の完了の扱いと同じ)。
    中止のためにジョブの世代を新しく進める仕組みは足さない。
- 失敗 (読めない動画・音声の変換の失敗・UTF-8 の不正) は次へ進む。`ok` の行があれば上書きしない。無ければ `failed` の行を書く。
- worker の異常終了・モデルの読み込み失敗・VRAM 不足は、ジョブを止めて通知する。**まれな失敗は割り切り (ログ + 通知。やり直しは利用者がジョブを始め直す)**。

### 6.6 改名・削除と保存の順序

AI 説明文 §6.6 の方針をそのまま使う: **書く直前に `BEGIN IMMEDIATE` の中でファイルの署名を取り直し、作業を始めたときと違えば結果を捨てる**。
改名の移行 (`rename_key_migration`) は同じ DB を同じ lock で付け替えるので、順序はこれで正しくなる。
文字起こしは 1 本に数分かかるので、その間の改名で結果を捨てる場面は説明文より起きやすいが、作り直しは利用者の操作で足りる
(改名は普段あまりしない操作。捨てたときは件数を小窓に出す)。

### 6.7 削除

AI 説明文 §6.8 と同じ形の「文字起こしを削除」を一覧の右クリックに置く (件数を数える → 確認 → 1 トランザクションで削除、全 phase モーダル)。
作成ジョブがある間は押せない。

## 7. 保存

新しいストア `transcript.db` (SQLite。未リリースなので移行は不要)。**1 本 1 行**にし、区間の列は 1 つの列に入れる。
`STORES` には同じ path に複数行を持つもの (動画のブックマーク) も登録されているが、1 本 1 行にすると、汎用のコピー・復元 (unique なストア用)
をそのまま使える (§12 R3。独立レビュー 1 回目 P3-3 で根拠を正した)。

```text
transcripts(
  item_key      TEXT PRIMARY KEY,   -- 正規化 path (ai_caption.db と同じ規則)
  mtime         INTEGER, size INTEGER,  -- 作成時の動画の署名
  audio_stream  INTEGER,            -- 使った音声トラックの番号 (§6.3)
  model_id      TEXT,               -- 例: whisper-large-v3-turbo-q5_0@<sha256 の先頭>
  config_version INTEGER,           -- 復号の設定 (§3) と後処理 (§6.4) の版
  lang          TEXT,               -- 'ja'
  duration_ms   INTEGER,            -- 音声の長さ
  segments      TEXT,               -- 後処理済みの区間。JSON 配列 [[start_ms, end_ms, "文"], ...]
  removed_counts TEXT,              -- 後処理で除いた数 (規則ごと、JSON)
  status        TEXT,               -- ok / failed
  created_at    INTEGER,
  rev           INTEGER,            -- AI 説明文 §7 と同じ。DB 全体で使い回さない番号
  indexed       INTEGER             -- 0 = 索引への反映待ち
)
transcript_seq(n INTEGER)
transcript_removed(item_key TEXT, rev INTEGER, PRIMARY KEY (item_key, rev))
-- trigger は ai_caption.db の captions_ins / captions_upd / captions_del と同じ形
```

- 保存するのは後処理の後の区間だけ。後処理前の出力は保存しない (崩れた出力は同じ文の数百回の繰り返しで、残しても使い道が無い)。
  後処理の規則を変えたときは、利用者の作り直しで新しい規則になる (`config_version` の違いで「古い」と表示する)。
- 大きさの目安: 評価の 8 本では後処理後に 1 分あたり約 170 文字。2 時間の配信で約 2 万文字、JSON で 100KB 前後。
- `rename_key_migration::STORES` に登録し、mIV 内の改名・移動に追従させる。孤児整理の対象にもする。mIV の外での移動には追従しない。
- `metadata_transfer` (メタ情報の書き出し / 取り込み) に含めるかは U6。含める場合は AI 説明文と同じく「記載された空は消す」。
- 動画が変わった (署名不一致) 行は消さずに「古い」と表示し、検索には使い続ける (AI 説明文と同じ)。

## 8. 表示

### 8.1 左パネルの「文字起こし」タブ (2026-11-11 利用者の案)

動画フルスクリーンの左パネルは、今は上段の「ジャンプ / 画像補正」の 2 タブ (`NativeVideoLeftPanelTab`)。ここに **「文字起こし」タブ**を足す。

- 理由: 左パネルのジャンプ (ピン・ブックマーク・チャプター) と同じく「時刻の一覧から移る」操作で、利用者の手の位置も同じ。
  右パネル (メタデータ) は 1 枚の情報を読む場所で、数百行の一覧には向かない。
- ジャンプのタブに混ぜず、別のタブにする。2 時間の配信では数百〜千行になり、混ぜるとブックマークが埋もれる。
- 行は「時刻 + 文」。行を押すと既存の `NativeOverlayCommand::Seek { target_secs }` でその時刻へ移る (新しい命令は作らない)。
- 再生中の行を強調し、表示中は再生位置に合わせて自動で送る。利用者が一覧をスクロールしたら自動送りを止め、
  「再生位置へ戻る」の操作で再開する (自動送りの状態はタブを閉じたら捨てる presenter 内の一時状態)。
- 文字起こしが無い・作成中・失敗・古いときは、タブの中に 1 行の案内を出す (例: 「文字起こしはまだありません。一覧の右クリックで作れます」)。
  タブは常に出す (有無でタブが出たり消えたりすると、タブの位置が動いて押し間違えるため)。
- 動画↔音声モードの遷移・ファイル移動で閉じる扱いは、既存のジャンプのタブと同じ session 境界に従う (video-architecture の左パネルの節)。
- タブの中の語の絞り込み (パネル内検索) は初回の版では作らない。検索は Ctrl+G / Ctrl+F と §8.3 で行う。

### 8.2 データの流れ

- **文字起こしの表示用キャッシュは App に 1 つ持つ** (`TranscriptDisplayCache`、AI 説明文の `CaptionDisplayCache` と同じ形)。
  読み込みは小さな worker で行い、UI スレッドで DB を読まない。保存・削除・取り込み・`STORES` の汎用操作の後に消し、世代で古い読み込みを捨てる。
- **presenter へは、今の動画 1 本の「表示 snapshot」を 1 つの値で渡す** (独立レビュー 1 回目 P2-4 で改めた)。区間の列だけでは §8.1 の
  状態 (無い・読み込み中・作成中・失敗・古い・別トラック) を表せず、キャッシュを消しても presenter が持っている値は消えないため。
  - snapshot = `{ 対象の動画のキー, 状態, 区間の列 (Arc), 使ったトラック }`。App が今の動画とキャッシュから作り、今の
    `player.set_native_jump_entries` と同じ経路で再生器へ渡す。presenter は描くだけで、DB やファイルに触れない。
  - **作り直す時点を既存の経路にそろえる**: 動画を切り替えたとき (source swap で今の表示データを消している所)、読み込みが届いたとき
    (届いた結果のキーが今の動画と一致するときだけ採用)、キャッシュを消したとき (今の動画の分を読み直し、届くまでは「読み込み中」)、
    presenter を作り直したとき (F12 の配置変更。今のジャンプの一覧と同じく作り直しの後に渡し直す)、
    **作成ジョブの対象・状態が変わったとき** (今の動画が待ち行列に入った・処理中になった・終わった。DB は読み直さない)、
    **再生中の音声トラックが変わったとき** (独立レビュー 2 回目 P2-2)。
  - 「別の音声トラック」の判定は状態として持たず、行に記録したトラックと、**実際に再生しているトラック** (要求中の `desired` ではなく
    `applied`。既存の音声トラックの表示 `video/audio_track_ui.rs` と同じ区別) から snapshot を作るたびに導く。
  - 検証: A を読み込み中に B へ移る、表示中に削除・取り込み・作り直しが終わる、F12 の往復。
- detached viewer の動画も共通の presenter のパネル経路を使う (独立レビュー 1 回目で確認)。変えるのは「再生器へ渡すデータ」1 つで、
  detached の述語や viewport 経路は変えない。detached 専用の状態は足さない。実装で detached の経路に触れることになった場合は、
  detached-rework-plan §2 の手続きに従う。

### 8.3 時刻の精度

- VAD を使わないので、区間の始まりは実際の発話より早いことがある (評価で中央値 0〜3.2 s、最大 12.5 s)。行を押すと、言葉の少し前から再生が始まる。
- 遅れて始まる (言葉の頭が切れる) よりは良いので、初回の版はこのままにする。詰めるなら whisper のトークン単位の時刻を使う (後段)。

### 8.4 右パネル

右のメタデータパネルには、文字起こしの状態だけを 1 行で出す (「文字起こし: あり (2026-11-11、古い)」など)。本文は左パネルで読む。

## 9. 検索

### 9.1 Ctrl+G / Ctrl+F

- Tantivy に `transcript_text` (bigram + STORED) を足し、検索対象の種類に「文字起こし」(`SourceKind::Transcript`) を足す。
  「すべての対象」にも含める。
- ingest は、動画の文書を作るときに `transcript.db` を読み、`status = ok` の区間の文を空白区切りでつないで入れる。
- **schema が変わるので `INDEX_VERSION` を 11 → 12 に上げる**。v5.1.0 の利用者は、更新後の初回起動で索引を全件作り直す
  (作り直し中は Ctrl+G の結果が欠ける)。AI 説明文の版上げ (U3) と同じ扱いでよいかは U7。
- Ctrl+F は動画ごとに `transcript.db` を引いて比較対象に加える。
- 大きさの目安: 1,000 時間の動画で約 1,000 万文字。PDF の本文を対象外にした理由 (OCR の誤認識で偽ヒットが増える、search-architecture §4.7) は
  文字起こしにも一部当てはまるが、話された語で探すことがこの機能の目的なので入れる。

### 9.2 索引への反映

AI 説明文 §8 の「DB の反映待ちの印を管理役が拾う」仕組みを使う。

- 印 (`indexed = 0` / `transcript_removed`) は §7 の trigger が付ける。管理役は起動時・全件走査の後・知らせを受けたときに、
  自分の受け持つ範囲の反映待ちを読み、その動画を再 ingest し、commit の後に読んだ `(item_key, rev)` と一致するものだけを反映済みにする。
- **仕組みは 1 つにまとめる**。今の拾い直しと知らせは説明文専用になっている: 知らせは共通の `AtomicU64` (`IndexerManager::caption_epoch`、
  `notify_caption_changed` が進める) で、管理役ごとに見た値 (`seen`) を持って比べる (`indexer_supervisor.rs`)。
  「索引に入れる派生テキストのストア」の一覧 (説明文・文字起こし) を持つ 1 つの仕組みへ一般化し、同じ処理を写して 2 つ作らない。
  共通の番号と管理役ごとの `seen` の方式はそのまま使い、旗などの新しい知らせ方は足さない (独立レビュー 1 回目 P3-1)。
- **知らせと表示の失効を決める所まで一般化する** (独立レビュー 1 回目 P2-3)。今は `STORES` の汎用操作の結果 (`StoreMutationEffects`) が
  DB の名前を直接見て `ai_captions_changed` / `caption_display_stale` を立て (`rename_key_migration.rs` の `record_rows_changed`)、
  受け手 (`content_identity_detection.rs` の `apply_content_identity_store_mutations` ほか) がそれを見て知らせ・キャッシュの消去をしている。
  `STORES` に登録して知らせの名前を替えるだけでは、文字起こしだけが復元・削除されたときにこの印が立たず、表示も検索も更新されない。
  - ストアの記述 (`StoreDescriptor`) に「索引に入れる派生テキスト」「表示キャッシュの種類」を持たせ、`StoreMutationEffects` がそこから
    印を作る形にする。DB の名前を `matches!` で並べる判定を増やさない。
  - 取り込み (`metadata_transfer`) の変更の集計も同じ一覧を使う。知らせ・消去を行う時点 (今の完了の採用点) は変えない。

### 9.3 検索結果から時刻へ (段階 T3)

- Ctrl+G の結果のうち、文字起こしで当たった動画には、当たった区間の抜粋と時刻を出し、その時刻から開けるようにする。
- 抜粋と時刻は、結果を受け取った後に worker が `transcript.db` の区間へ同じ照合 (`search_query::matches_with_mode`) をかけて求める。
  索引には時刻を入れない。
- 開くときの時刻は、既存の「続きから再生」(`video_resume_positions`) とは別の、その 1 回だけの開始位置として渡す
  (続きから再生の記録は変えない)。渡し方は T3 の設計で決める。

### 9.4 読みでの照合 (後段)

評価では Sudachi (Apache-2.0、辞書 約 200MB) で効果があった (誤ヒットも 0 ではない)。pykakasi は GPL-3.0 で同梱できない。
辞書の大きさ・配り方・どの検索に効かせるかを別の計画で決める。

## 10. MCP (初回の版に入れる)

- **権限**: 「AI に見せる範囲」に 4 つ目のチェック **「文字起こし」** を足す (既定 OFF)。mcp-integration-plan §5.6 の表示と §15.2 の
  権限 snapshot に含め、変われば epoch を進める。AI 説明文のチェックとは別にする (内容の性質が違う。話した人の氏名や私的な会話を含み得る)。
- **`get_item_info`**: 動画に `transcript` 欄を足す。返すのは**状態の要約だけ** (有無・古いか・モデル・作成日・使った音声トラック・音声の長さ・区間数・文字数)。
  本文は返さない。1 回 50 件の応答に長い本文が入ると、項目の上限 (`MAX_ITEM_CHARS`) を超えて切り詰めだらけになるため。
- **新しい tool `get_transcript`**: 1 本の動画の区間を、時刻つきで返す。
  - 引数: 動画の指定 (`get_item_info` と同じ形)、開始時刻 (省略時 0)、続きの cursor。
  - 1 回の応答は文字数の上限まで。区間の途中では切らず、入りきらなかった分は cursor で続きを返す。
  - **cursor には許可の版に加えて、対象の動画のキーと行の `rev` を入れる** (独立レビュー 1 回目 P2-5)。続きの要求で行が作り直された・
    取り込まれた・消された (`rev` が違う・行が無い) ときは、最初から取り直すよう拒む。許可の版が違えば `PermissionChanged` で拒む。
    どちらも状態を持たない拒否で、行の snapshot は持たない (一覧の続きで変更を検出している `FolderCursor` と同じ考え方)。
- **認可は一覧の出し分けだけに頼らない** (独立レビュー 1 回目 P2-1)。tool の一覧 (`mcp-server` の `tool_names`。縮小画像のチェックで
  `get_thumbnail` を出し分けているのと同じ形) は見え方の制御で、取得の許可ではない。
  - `get_transcript` は、本体の受付で同じ権限 snapshot を見て、チェックが OFF なら拒む (縮小画像の受付での拒否と同じ)。
  - `get_item_info` の `transcript` 欄は、チェックが OFF なら DB を開く前に「許可なし」(AI 説明文の欄と同じ `NotPermitted`) にする。
  - 送信直前の許可の照合 (epoch) と、設定の書き出しから許可設定を外すことは、既存の仕組みをそのまま使う。
  - 許可の段は ReadOnly 以上。
- **`search_items`**: チェックが OFF なら `Transcript` を検索対象から外す (候補を集める段階と最終の照合の両方。AI 説明文と同じ)。
- **時刻を指定して開く** (`open_in_viewer` に開始時刻を足す) は、T3 の「その 1 回だけの開始位置」と同じ仕組みで足す。
- agent IPC の版を上げる (strict-equality)。MCP 担当と調整する。

## 11. GPU / VRAM・CPU

- whisper turbo (Q5_0) の VRAM は**未計測**。T0 で、推論中のプロセス単位の専用 GPU メモリのピークを測り、使える境目を決める。
- AI 補正・Remote の AI・AI 説明文のジョブとは**同時に動かし、止める仕組みは作らない** (VLM の U1 と同じ考え方)。
  VRAM を超えたときの遅さは割り切り、マニュアルで案内する。判断は設定と VRAM の総量だけで行い、空き VRAM で挙動を変えない。
- CPU だけの機種で使えるようにするかは U2。

## 12. 状態を減らす検討の記録

- R1: 設定はすべて固定 (モデル・言語・VAD なし・後処理)。選べるようにすると、同じ動画でも設定で結果が変わり、保存する記録と作り直しの判断が増える。
- R2: 文字起こしと AI 説明文のジョブを 1 つの待ち行列にまとめる案は採らない。どちらも GPU を使うが、同時に動かしても遅くなるだけで壊れない。
  まとめると、既に出荷した説明文のジョブの持ち主を作り直すことになり、得るものが少ない。
- R3: 1 本 1 行、区間は 1 列の JSON。汎用のコピー・復元 (unique なストア用) をそのまま使える。区間ごとの検索は §9.3 で行を読んでから行う。
- R4: 音声トラックは作成時に再生側と同じ関数で決めた 1 つ。トラックごとの複数行は持たず、後で切り替えても作り直さない (使ったトラックを示すだけ)。
- R9: 中止は worker を終わらせる。中止の命令を推論の途中で読む仕組み (読み取りと推論を別スレッドにする等) は作らない (§6.5)。
- R5: 後処理前の出力は保存しない。後処理の変更は作り直しで反映する (§7)。
- R6: 窓ごとの推論 (§5) は、メモリを抑えるためで、窓をまたぐ状態を持たない (前の文を渡さない設定のため)。
- R7: 左パネルのタブは常に出す。有無で出し分けない。
- R8: 改名・削除との順序は、保存直前の署名の確認だけで扱う (AI 説明文 U14 と同じ)。
- 不採用の単純化: 「作成中はモーダル」。数時間かかり得るので不便すぎる (AI 説明文と同じ)。

## 13. 未確認の事項 (T0 で確かめる)

- whisper turbo の VRAM のピークと、遅い GPU (サブ PC など) での速度。初回のシェーダ準備の時間。
- 30 分の窓と、音の小さい所で切る規則で、評価の CLI (全体を 1 回) と比べて結果が悪くならないか (§5 の合格条件)。
- whisper.cpp を llama.cpp b12032 の ggml で build して、1 つの worker exe にできるか (できれば配布サイズが減る)。worker exe の大きさ。
- 長い動画 (数時間) での worker のメモリと、本体の FFmpeg 変換の速さ。
- 決まり文句の一覧が、利用者の別の動画でも足りるか (評価に使っていない動画で、後処理後に残った繰り返しを数える)。

## 14. 段階

- **T0 — 計測 (製品の外、開発側)**: §13 のうち VRAM・速度・窓の切り方・ggml の共有。評価の環境 (`exp-asr-eval`) を使う。
- **T1 — 作る・見る・MCP**: worker、モデルの取得、作成ジョブと進捗、`transcript.db`、`STORES` 登録、削除、左パネルのタブとジャンプ、
  右パネルの 1 行、MCP の権限・`get_item_info` の要約・`get_transcript`、perf event (抽出・推論・保存)。
- **T2 — 検索**: `transcript_text`・`SourceKind::Transcript`・`INDEX_VERSION` 12・Ctrl+F・反映の仕組みの一般化 (§9.2)・MCP の `search_items`。
- **T3 — 検索結果から時刻へ**: 抜粋と時刻、その時刻から開く、MCP の `open_in_viewer` の開始時刻。

- 後段: 音声ファイル、読みでの照合、言語の拡大、トークン単位の時刻、Remote、自動作成、MCP からのジョブ開始。

## 15. 公開文書・安全性

- 新しく生じる通信は、モデルのダウンロード (利用者の操作時、GitHub Releases) だけ。
- 文字起こしは `transcript.db` と索引に保存する。MCP の「文字起こし」チェックが ON のときだけ AI アプリへ渡る。
  話された氏名・私的な会話もそのまま文字になるので、チェックの説明と公開文書に書く。
- 更新する公開文書: `privacy.html` (日英) の「ネットワーク通信」「端末内に保存されるデータ」、製品ページの「安心して使えます」、
  マニュアル (動画のページ・検索のページ・AI 連携のページ)、ライセンス表示 (whisper.cpp・ggml・whisper の重み、いずれも MIT)。
- 設計文書: video-architecture (左パネル)、search-architecture (§4.8 の「音声文字起こしは対象外」を改める、§4.11 の版の履歴)、
  async-architecture (worker 一覧)、architecture-overview、mcp-integration-plan、keymap-spec (キーは割り当てないが、メニュー項目の記録)。
