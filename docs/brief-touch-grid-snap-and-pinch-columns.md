## 1. 指を離したときに逆方向へ戻る

### 1.1 症状

実機報告 (2026-08-07):

> 指を離したとき、**反対側に戻ってスナップする**ことがあるのが気になる。
> 逆向きには進まずスナップするほうが良さそう。少しだけ戻るなら良いが、
> 現状では**セルの高さ半分くらい戻る**ことがあるように見える。

### 1.2 現状

`settle_grid_touch_scroll` ([src/ui_main.rs:337](../src/ui_main.rs)) は
**最寄り行へのスナップ**で、進行方向を見ていない:

```rust
if remainder_y.is_finite() && remainder_y >= row_h * 0.5 && row < max_row {
    row += 1.0;
}
```

→ どちら向きでも**最大 0.5 行ぶん逆走**する。報告の「半分くらい戻る」と一致する。

### 1.3 ⚠ しきい値を一律に下げてはいけない

`remainder_y` は常に `[0, row_h)` の**正の値**なので、同じしきい値が上下で逆の意味になる。

描画位置 = `anchor_y + remainder_y`。位置が増える = 下方向へスクロール。

| 離した時点の進行方向 | 前進 (逆走しない) 側 | 逆走側 |
| --- | --- | --- |
| 下方向 (位置が増加中) | `anchor + row_h` へ進む | `anchor` へ戻る (`remainder_y` ぶん) |
| 上方向 (位置が減少中) | `anchor` に留まる | `anchor + row_h` へ進む (`row_h - remainder_y` ぶん) |

しきい値を 0.5 → 0.2 に下げると、**下方向は改善するが上方向は最大 0.8 行の逆走になり悪化する**。

### 1.4 直し方 — 進行方向でスナップする

**最後の移動方向を覚えて、その方向へスナップする。** ただし「ほんの少ししか進んでいない」
ときだけ逆方向への確定を許す (でないと 1px 動かしただけで 1 行進んでしまう)。

```
tol = row_h * 0.15   (定数として 1 か所に置き、根拠を doc comment に書く)

進行方向が下: remainder_y > tol            → anchor + row_h へ    それ以外 → anchor へ
進行方向が上: remainder_y < row_h - tol    → anchor へ            それ以外 → anchor + row_h へ
```

→ **どちら向きでも逆走は最大 `tol` (= 15%)** に収まる。

- **進行方向を一時状態として持つ**こと。`remainder_y` と同じ場所 (viewport の `ctx.data_temp`) に置く
- **方向が不明なとき** (ドラッグしていない / 端数が動いていない) は
  **従来どおり最寄り行**へフォールバックする
- 上下端のクランプは従来どおり。**行き過ぎ / 跳ねを起こさないこと**
- `tol` は実機で調整しうるので、**1 か所の定数**にすること

### 1.5 テスト

`settle_grid_touch_scroll` 相当の**純関数**として:

- 下方向・端数 0.1 → 戻る (最大 `tol`)
- 下方向・端数 0.2 / 0.4 / 0.9 → **すべて前進**する
- 上方向・端数 0.9 → 留まる (前進しない)
- 上方向・端数 0.8 / 0.5 / 0.2 → **すべて留まる**
- 上方向・端数 `row_h - tol` 以上 → 進む
- 方向不明のときは最寄り行
- **どのケースでも逆走量が `tol` を超えないこと**を表明する (今回の本命)
- **結果の `anchor_y` が常に `row_h` の整数倍**であること (既存の不変条件)
- 上下端でクランプすること

## 2. 一覧のピンチで列数を変える

### 2.1 要望

> ピンチ操作では**列数が変わる**とよいですね。

### 2.2 前ステップの指示を反転する (意図的な変更)

`266948f4` のブリーフでは「一覧では 2 本目が来ても `Pinch` へ昇格させない」と指示した。
**これを取り消す。** 一覧でもピンチを受け付け、**意味を「列数変更」にする**。

- 認識器は従来どおり `Zoom { factor, pivot }` を出す。
  **認識器に「列数」の概念を持ち込まないこと** (認識器は操作を報告し、意味付けは surface が決める)
- **一覧の呼び出し側が `Zoom` を列数の増減へ変換する**
- 一覧のピンチ中は **`Pan` を無視する** (列数変更とスクロールが同時に起きると操作が読めない)
- ピンチ中は `GridScroll` が走らないこと (所有権が `Pinch` に確定するので自然に満たされるはず)

### 2.3 列数の増減

既存経路と同じ場所へ合流させる ([src/app.rs:33546](../src/app.rs) 付近の Ctrl+ホイール分岐):

- `settings.grid_cols` を `MIN_GRID_COLS` 〜 `MAX_GRID_COLS` でクランプ
- `bump_input_seq("grid_cols", None)` を呼ぶ
- **ピンチを広げる (factor > 1) → 列数を減らす** (セルが大きくなる)。
  縮める → 列数を増やす。写真アプリの慣習に合わせる

**ヒステリシスを入れること。** ピンチは 1 フレームに小さな factor を多数出すので、
そのまま列数へ渡すと激しく往復する。

- ジェスチャ開始 (または直前の列数変更) からの**累積倍率**を持つ
- 累積が一定比 (例: 1.25 倍 / 0.8 倍) を越えたら **1 列だけ**動かし、累積をリセットする
- 比は **1 か所の定数**にして、doc comment に根拠を書く

### 2.4 ⚠ 設定の保存はジェスチャ終了時に 1 回だけ

Ctrl+ホイール経路は列数を変えるたびに `self.settings.save()` を呼んでいる。
**ピンチで同じことをすると、1 ジェスチャ中に設定 DB へ何度も書き込む。**

→ **ピンチ中は保存せず、ジェスチャ終了時 (`PinchEnd` 相当) に 1 回だけ保存する**こと。
列数の適用自体は即座に行う (見た目は追従する)。

### 2.5 テスト

- 累積倍率が閾値を越えるまで列数が変わらないこと
- 越えたら 1 列だけ動き、累積がリセットされること
- 広げる → 列数が減り、縮める → 増えること
- `MIN_GRID_COLS` / `MAX_GRID_COLS` でクランプされ、それ以上動かないこと
- **1 ジェスチャ中に `settings.save()` が複数回呼ばれないこと** (可能な形で検証する。
  難しければ「保存を呼ぶ箇所がジェスチャ終了経路だけである」ことをテストで固定する)
- ピンチ中に `GridScroll` が発火しないこと
