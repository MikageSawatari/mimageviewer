# mImageViewer v1.0.0 Stability Review (Opus 4.8 multi-agent)

- **実施日**: 2026-05-29
- **手法**: churn / unsafe hotspot を 8 観点に分割し Opus 4.8 でマルチエージェント並列レビュー
  → 各指摘を独立した敵対的検証エージェントが反証 (refute) → 生き残った指摘のみ採録。
- **規模**: 24 エージェント / tool 利用 551 回 / 約 11 分。
- **結果**: 生 15 件 → 敵対的検証通過 **10 件** (P2×1, P3×9、**P1 なし**)。
- **観点**: erase / conceal / video-engine / video-decoder / video-presenter / 並行処理 / クラッシュ監査 / app.rs 非同期適用。

各指摘の `verify_reasoning` (検証エージェントがコードを読んで確認した根拠) は省略している。
原データは `%APPDATA%` 配下のタスク出力 (`tasks/wp6zj20ms.output`) を参照。

## 統合レポート (synthesis agent)

### P1 — crash / data-loss / wrong-result on common paths

**該当なし。** 共通経路で crash / データ損失 / 誤結果に至る指摘は敵対的検証を通過しなかった。
最もユーザーに見えやすい ZIP 固着バグも、破損/読込不能エントリが前提なので P2 とした。

### P2 — 起きにくい経路、または緩和策ありの実バグ

#### P2-1. ZIP byte 読み失敗で全画面ローダが `Failed` を送らず「読込中…」永久固着
**File:** `src/app.rs:15256-15277` (worker); 影響は `app.rs:20018-20034` (poll_prefetch) と `src/ui_fullscreen.rs:2543`

`start_fs_load` worker の ZIP エントリ経路は `zip_loader::read_entry_bytes` でバイトを読むが、
`Err` 時に log + perf event だけ出して `tx.send(FsLoadResult::Failed)` を**呼ばずに** `return` する。
`tx` が drop されチャネルが切断されると、`poll_prefetch` は `TryRecvError::Disconnected` を
「`fs_pending` から idx 削除」としか扱わず `FsCacheEntry::Failed` を入れない。
`is_loading = !is_video && !is_separator && !fs_load_failed && !fs_cache.contains_key(&fs_idx)`
(`ui_fullscreen.rs:2543`) なので、idx がどのマップにも無く failed でもない状態になり、
ユーザーが移動するまでスピナーが永久に出続ける。PDF 経路 (`app.rs:15247`) と静止画経路
(`app.rs:15506`、「UI が『読込中…』のまま固まらないよう失敗を明示通知する」というコメント付き)
は両方 `Failed` を送っており、**この ZIP 経路だけが送信を欠いている**。

**Fix:** `zip_read_fail` の Err arm (~`app.rs:15260-15273`) で `emit_exit("zip_read_fail"); return;` の
直前に `let _ = tx.send(FsLoadResult::Failed);` を追加 (兄弟 arm と同じ)。これで `poll_prefetch` が
`FsCacheEntry::Failed` を入れ `is_loading` が解ける。

### P3 — 軽微 / エッジケース

#### P3-1. shutdown event 作成失敗時に activation listener が busy-spin → 終了 join ハング
**File:** `src/single_instance.rs:278-338` (分岐 309/330/335)、Drop join は `361-377`

起動時に `CreateEventW(shutdown)` が失敗 (`handles.shutdown == 0`) し activate event は成功した場合、
コードは `shutdown = stop` と別名化し `wait_handles = [activate, stop, stop]` になる。
`WaitForMultipleObjects(bWaitAll=false)` は**最小の**signaled index を返すので、Drop が
(manual-reset の) stop event を立てると wait は index **1** を返す。index-1 分岐は
`&& handles.shutdown != 0` (この時 false) で skip され、index-2 分岐には到達せず、
`else { continue }` に落ちて再 arm → 立ったままの stop で再び 1 → 100% CPU busy-spin。
`ActivationListener::drop` が `th.join()` で永久ブロックし終了経路が固まる。希少だが実ハング。

**Fix:** `stop` を shutdown スロットに別名化しない。最善は `wait_handles` を動的に組む
(`handles.shutdown != 0` の時だけ push) こと。最小修正は stop 分岐で両 index を受ける:
`} else if r.0 == WAIT_OBJECT_0.0 + 2 || (handles.shutdown == 0 && r.0 == WAIT_OBJECT_0.0 + 1) { break; }`。

#### P3-2. decoder の info 送信後 panic でエラーが UI に出ず動画が無言フリーズ
**File:** `src/video/decoder.rs:1618-1631`; actor は `src/video/engine/actor.rs:568-575`; UI 経路は `src/video/mod.rs:5256-5260`

`run_decoder` が `info` 送信**後**に panic すると、`catch_unwind` の復旧は `DecoderEvent::Failed` を
出すが `clock.set_decode_failed(true)` を呼ばない。actor の `Failed` ハンドラは `Idle` 遷移のみで
エラーを記録しない。UI の唯一の in-flight 失敗経路 `if self.clock.decode_failed()` (`mod.rs:5257`) は
true にならず、in-thread の first-frame watchdog (`decoder.rs:3083-3101`) は別 sub-thread にあり
demux thread が既に unwind したので発火できない。結果、動画は `Idle` で無言フリーズ
(「再生に失敗しました」も出ず、復旧もなし)。trigger は demux 本体での稀な算術/index/state panic。

**Fix:** `catch_unwind` の err 分岐 (`decoder.rs:1618`) で `Failed` 送信に加えて
`clock.set_decode_failed(true)` を呼ぶ (既存 UI 経路が発火する)。

#### P3-3. `FastDownmixToStereo` が setup 時の ch 数/format で読む → 途中変化で native OOB read
**File:** `src/video/decoder.rs:5751-5826` (run/mix_packed/mix_planar); 構築は `1968-1969`; `AudioSetup` `5860-5874` に保持

`FastDownmixToStereo` は audio decoder setup 時に `dec.ch_layout()`/`dec.format()` から一度だけ構築され
再構築されない。`mix_packed` は raw pointer に対し `base[i*self.channels + entry.plane]` を読むが、
配信フレームが今も `self.channels`/`self.format` を持つか毎フレーム検証しない。途中で ch 数が
減るフレーム (adaptive/broadcast/連結 AAC/AC-3/E-AC-3 の layout 切替) が来ると `data[0]` buffer を
超えて OOB read → native crash (panic hook では捕捉不可、無言で落ちる)。format 変化
(I16 を F32 と誤解釈) でも over-read。発生は低確率だが最大の unsafe 面での実メモリ安全性ギャップ。

**Fix:** `FastDownmixToStereo::run()` で dispatch 前にライブフレームを検証し不一致なら安全な
resampler 経路へ抜ける: `if frame.ch_layout().channels() as usize != self.channels || frame.format() != self.format { return None; }`
(呼び出し側は既に `None` を `5185` で処理)。一度きりの logger 警告 + `debug_assert!` で可観測化。

#### P3-4. `compose_mosaic` の per-tile `u32` 和が巨大タイルで overflow → 色化け
**File:** `src/conceal_compose.rs:67-98`; tile size は `src/conceal.rs:185-193` で上限なし

per-tile アキュムレータが `u32` (`tile_stats` at `conceal_compose.rs:67`)。各チャネルが
`p.r() as u32` をタイル内全画素で加算する。タイルが ~16.84M 画素超 (辺 > ~4104px) で 1 チャネル和が
`u32` を wrap する。`compute_tile_size` の `LongEdgeRatio` は上限クランプなし (multiplier 5.0 =
`TILE_RATIO_MAX` で `tile ≈ long_edge/20`) なので、長辺 ~82,000px で tile ≈ 4105 となり wrap、
そのタイルの平均色が誤る (`avg_r = sr / tc` が wrap した和を読む)。release では `u32` wrap で
無言の誤結果 (crash ではない)。極端な trigger (その画像は先に OOM するレベル) のため P3。

**Fix:** `tile_stats` のチャネル和を `u64` 化 (最安、overflow を完全排除)。任意で
`compute_tile_size` 側も実効 tile を `min(tile, 4096)` にクランプ。

#### P3-5. `compose_blur` InsideOnly が縦パスでマスク外色を漏らす
**File:** `src/conceal_compose.rs:500-537`

InsideOnly はマスク外画素を一切サンプリングしない契約 (隣接色のにじみ防止)。横パスは
`mask_for_sampling` で守るが、横方向にマスク内隣接が無いと `acc_w==0` の fallback で**元のマスク外色**を
`tmp` に書く。縦パスの bbox 内分岐 (`531-536`) は `tmp[bsi]` を**マスク判定なしで**読む
(コメントが「全 bbox 内画素を重み 1 の寄与として扱う」と明言)。よってその元マスク外色が近傍の
マスク内画素の縦 blur に寄与する。bbox 外分岐は既にマスク再判定 (`517-521`) しており、内分岐だけ
無防備。斜め/不規則境界 (InsideOnly の現実的用途) で品質劣化。既存テストは左右分割
(列が一様なマスク) なので縦漏れを捕えられない。

**Fix:** Pass 2 で `mask_for_sampling` が `Some` のとき、対応画素 `(bbox.x0+bx, sy)` がマスク外の
`tmp` 寄与を skip (bbox 外分岐と同じ)。または Pass 1 から per-`tmp` 妥当性重みを持ち回り Pass 2 で
再利用する (重み 1 固定をやめる)。

#### P3-6. `present_with_surface_swap` のエラー早期 return で waitable HANDLE リーク
**File:** `src/video/native_presenter/mod.rs:1914-1977`

`create_video_swap_chain` は素の kernel `HANDLE` (windows-rs `HANDLE` は `Copy`・`Drop` なし) を
local `new_waitable` (`1914`) に返す。これが RAII 所有者 (`RetiredVideoSurface`、`Drop` で `CloseHandle`)
に移るのは `1977`。その間の 6 つの `?` 早期 return (`1915`/`1919`/`1926`/`1959`/`1962`/`1965`) では
`new_swap_chain` は COM Drop で Release されるが `new_waitable` は忘れられ kernel handle リーク。
コードはこの handle を所有扱いしている (`RetiredVideoSurface::drop` `262`、`NativeVideoPresenter::drop`
`7672` が両方 `CloseHandle`)。trigger はアダプタメモリ圧迫下の一時 Present/Commit 失敗
(まさに fast-swap 経路が想定する状況)。繰り返すとプロセス寿命の間 handle が蓄積。

**Fix:** `create_video_swap_chain` 返却直後に `new_waitable` を小さな scopeguard で包み
(disarm されなければ CloseHandle)、`1977` で `RetiredVideoSurface` に移った時に disarm。
または `create_video_swap_chain` が「所有権取得まで Drop で waitable を閉じる」型を返す。

#### P3-7. 消費済み GPU frame 再 present で keyed-mutex key=0 → モード切替で黒フレ + 10ms stall
**File:** `src/video/native_presenter/mod.rs:3206-3235`; prime 経路 `src/video/mod.rs:2396-2407`

`acquire_source_keyed_mutex` は常に `AcquireSync(1, 10)`、`KeyedMutexReadGuard::drop` (`859-867`) は
常に `ReleaseSync(0)` なので、一度 present した frame は key=0 で残る。window/fullscreen 切替の
prime 経路は `present_retire.back()` (通常空でない=共通分岐) を再 present するが、これは消費済みで
key=0。prime 経路は source mutex を key=1 に戻さないので `AcquireSync(1, 10)` が 10ms 待って `Err`、
`present()` 失敗、`primed=false`。結果、新ウィンドウが一瞬黒/古フレ + presenter thread が切替毎に
10ms stall。graceful に処理・ログ済み、次のライブ frame (producer の key=1) で ~1 フレで回復。

**Fix:** prime を `present_retire.back()` でなく `source.queue.front()` (未消費 frame) から行う。
または prime 経路で keyed-mutex acquire を skip (producer copy は既に fence 完了)。
または `released_to_reader==false` での `AcquireSync(1)` timeout を「読取可能」と見なし 0-timeout で best-effort。

#### P3-8. MI-GAN 補完がマスク画素を alpha=255 固定 (diffusion fallback と非一貫)
**File:** `src/ui_erase.rs:3186` (合成), `3168` (init)

`inpaint_migan` は `pixels[src_idx] = Color32::from_rgb(r, g, b)` で合成し、マスク画素の alpha を
255 固定にする (非マスク画素は元のまま)。diffusion fallback (`inpaint_diffuse`, `3253-3355`) は
平均し `from_rgba_unmultiplied` で出力するので alpha を保つ。よって透過 PNG で 2 バックエンドが
同入力に異なる alpha を出し、保存/エクスポート画像 (`save_with_metadata` は unmultiplied alpha を
尊重) で MI-GAN のマスク域が透明でなく不透明になる。影響小: マスクが透過画素に接する時のみ顕在化。

**Fix:** 元の alpha を保つ: `pixels[src_idx] = Color32::from_rgba_unmultiplied(r, g, b, original.pixels[src_idx].a())`。
または erase を RGB-only と明記し両バックエンドで一貫して flatten。

#### P3-9. erase-inpaint worker spawn が `.expect()` → spawn 失敗でプロセス crash
**File:** `src/ui_erase.rs:2741-2760`

`run_inpaint_and_cache` は worker を `std::thread::Builder::...spawn(...).expect("spawn erase-inpaint worker")`
で起動する。これは UI thread から到達する (E キー / Esc / 目アイコンプレビュー / F7/F8 slot apply /
auto-apply-saved-mask)。thread 生成が失敗 (handle/アドレス空間枯渇) すると `.expect()` が panic し
編集中にプロセス crash (graceful に劣化しない)。panic hook でログは残るが hard crash。なおこの
`.expect()`-on-spawn は他にも多数 (`delete_worker.rs:72`, `capture.rs:124/155`,
`dwm_iconic_thumbnail.rs:237`) あり、この 1 箇所だけが特別危険ではない。job は self-bounded
(同 idx/kind の前 job を cancel)。

**Fix:** spawn の `Result` を match し、`Err` 時は log + feedback toast (`[補完失敗]` 等) + `tx`/`rx`
drop + pending entry 挿入 skip にする (`.expect()` をやめる)。

---

## 回帰テストで最も費用対効果が高い 5 領域

1. **全画面ローダのエラー arm 対称性** (`start_fs_load` → `poll_prefetch` → `is_loading`)。
   各失敗種 (ZIP read fail / PDF render fail / decode fail / channel disconnect) を注入し、
   idx が最終的に `FsCacheEntry::Failed` になる (永久スピナーにならない) ことを表駆動で検証。
   P2-1 を直接捕え、今後追加されるエラー arm も守る。
2. **`single_instance` の劣化起動下の activation listener**。`handles.shutdown == 0` を強制し、
   listener thread が stop event を観測して `Drop`/`join` が有界時間で返ることを検証 (P3-1 + 将来の
   `WaitForMultipleObjects` index 別名化退行を捕捉)。
3. **`conceal_compose` の数値とマスク境界の正しさ**。(a) `u32` overflow するサイズのタイルで平均色が
   正しい (P3-4)、(b) InsideOnly の縦漏れを左右分割でなく斜め/不規則境界マスクで (P3-5)。純関数なので安価・高価値。
4. **video decoder の失敗通知契約**。info 送信後 decoder panic を擬似注入し `clock.decode_failed()` が
   true になり UI がユーザー可視のエラー状態に至ることを検証 (P3-2)。「無言フリーズ」ギャップを閉じ
   decoder→actor→UI のエラー契約を固定。
5. **`FastDownmixToStereo` の per-frame パラメータ検証**。`run()` に setup と異なる
   `ch_layout().channels()`/`format()` のフレームを与え `None` を返す (OOB read しない) ことを検証 (P3-3)。
   最大 unsafe 面に対する ch/format 組合せの fuzz と相性が良い。
