## 1. 何を作るのか

X や Instagram には、縦長の画像を 2〜4 枚投稿して、カルーセルでめくると全体が 1 枚の絵に
見える投稿の作り方がある。これを mIV から直接作れるようにする。

- フルスクリーンで表示中の 1 枚に、**N 個の枠を同時に**出す
- 枠は**グループ全体で**ドラッグ・リサイズする (個別には動かさない)
- 枠と枠の間の帯は**出力に含めない**。SNS が画像の間に入れる隙間の裏に隠れる部分なので、
  あらかじめ捨てておくと継ぎ目が繋がって見える
- N 枚を連番で書き出す

**一度きりの操作**として作る。既存の「切り取り」(`export_crop`) のようにページへ永続化しない。

## 2. 実測した SNS 側の仕様

2026-09-01 に実測 (X)。測定手段は §2.3。

### 2.1 X — 2026 年 7 月からカルーセル表示

複数画像の表示が、4 枚を田の字に並べるグリッドから**横スワイプのカルーセル**へ変わった
(iOS 先行、ブラウザ展開済み、Android 順次)。**旧来の 2x2 の 4 分割アートは X では成立しない。**
1 画面に映るのは 1 枚目の全体と 2 枚目の 3/4 ほど。

隙間の実測:

| 環境 | 画像幅 | 隙間 | 幅に対する比 |
| --- | --- | --- | --- |
| PC ブラウザ (innerWidth 1229) | 335.5 CSS px | 5.33 CSS px | 1.588 % |
| モバイル Web (viewport 375) | 201.0 CSS px | 5.33 CSS px | 2.652 % |
| iOS アプリ (440pt / dpr 3) | 214.0 CSS px (642 device px) | 4.00 CSS px (12 device px) | 1.869 % |

**隙間の絶対値は環境ごとに違う** (Web 5.33 / アプリ 4.00 CSS px)。「X の隙間は何 px」という
単一の正解は存在しないので、**枠幅に対する比**で持つ。

比 `r` を決めたときの各環境の誤差は `|r x 画像幅 - 隙間|` (画面 CSS px)。

| r | PC ブラウザ | iOS アプリ | モバイル Web |
| --- | --- | --- | --- |
| **1.7 %** | **0.37 px** | **0.36 px** | 1.91 px |
| 2.0 % | 1.38 px | 0.28 px | 1.31 px |

閲覧の主戦場である PC ブラウザと iOS アプリの両方が 0.4 px 以内に収まる **1.7 % を採用**する
(利用者判断 2026-09-01)。P8 以降は X へ切り替えたときの既定とし、なし / 任意も選べる。

**実投稿で検証済み (2026-09-01)**。1792x2304 の絵を 3 枚へ分割して実際に投稿し、書き出した
3 ファイルを元画像へ位置合わせ (FFT 相互相関) して確認した。3 枚とも 2098x2798 で寸法が
完全に一致し、元画像の x=0 / 600 / 1200 に等間隔で並び、捨てられた帯は枠幅 591px に対して
9px (測定の刻みは 4px、設計値は 10.05px = 1.7%)。投稿画面でも継ぎ目は繋がって見えた。

**アスペクト比**: **X は枠の比率を制限しない。**配信メタデータ (`sizes.large` /
`medium` / `small`) はいずれも `resize: "fit"` で、切り取るのは 150x150 のサムネイルだけ。

> **2026-09-01 の訂正。**ここには当初「iOS で 0.75〜1.18、ブラウザで 0.75〜1.33。3:4 が
> 切られずに出せる最も縦長な比率」と書いていたが、**下限は誤り**だった。測ったのが 3:4 の
> テスト画像だけで、それより縦長を一度も試していないのに範囲の端と読んだ。実際の公開投稿を
> 測ると 3:4 よりはるかに縦長の枠が普通に使われ、切り取られていない。

実測 (2026-09-01、公開 API `cdn.syndication.twimg.com/tweet-result` の `original_info` =
アップロード実寸と、iOS アプリのスクリーンショットの画素):

| 投稿 | 枚数 | 1 枚の実寸 | 枠の横/縦 | 合計 |
| --- | --- | --- | --- | --- |
| 3 分割 | 3 | 277 / 278 / 277 x 1216 | **0.228** | 832x1216 |
| 4 分割 (2 件) | 4 | 304x832 | **0.365** | 1216x832 |
| 分割なし (同じ作者) | 1 | 832x1216 | 0.684 | — |

3 分割の投稿は iOS アプリで **359x1576 = 0.2278** で表示されており、アップロード実寸
277/1216 = 0.2278 と一致する。**切り取られていない。**

**さらに重要な発見: 実際に行われているのは「絵全体を N 等分する」であって、
「一定比率の枠を N 個並べる」ではない。** 3 枚の合計 277+278+277 = 832 は、同じ作者が
分割せずに投稿した絵の 832x1216 と同じキャンバス。4 枚も 304x4 = 1216 ちょうど。
**継ぎ目の帯を 1px も捨てていない。**枠の比率は「絵の比率 ÷ 枚数」として結果的に決まる。

捨てないと継ぎ目は隙間のぶんだけ不連続になるが、背景が緩い絵では気付かれない。
捨てるかどうかは**利用者に選ばせる** (§4.1)。

**未確認**: タイムラインのカルーセルで極端に細い枠がどう出るか。X は未ログインで
タイムラインを描かず、ブラウザ拡張のタブは非表示のままなので測れなかった。上の表は
投稿詳細と配信メタデータに基づく。

**出力解像度**: X はタイムライン用に `name=small` (実測 510x680) へ変換し直して配信する。
タイムラインの見え方に出力解像度は効かない。ただしタップ拡大時は別の変換が使われるので、
SNS 分割の既定は**長辺 2048px 以下**とし、元が小さければ拡大しない。大きいまま必要なら
エクスポートダイアログで「そのまま」を選べる。

### 2.2 Instagram — 隙間なし、ただし比率に硬い上下限がある

「パノラマ投稿」「シームレスカルーセル」として X より歴史が長く、専用アプリも複数ある。
1 コマが画面幅いっぱいに出るため、**捨てる帯は無い (隙間 0 %)**。

**X と決定的に違うのは、Instagram には比率の制限があること** (2026-09-01 調査):

- フィードが表示できるのは **1.91:1 (横長) 〜 3:4 (0.75、縦長)** の範囲。外れると切り取られる
- **カルーセル全体が 1 枚目の比率に固定され**、違う比率のコマは中央で切られるか余白が付く

つまり **X 用に作った細い枠をそのまま Instagram へ出すと壊れる**。投稿先を選ばせる理由は
隙間だけでなく、この比率チェックにある (§4.1)。

> **未実測**。§2.1 と違い、Instagram は実機計測をしていない。上の 2 点は複数の公開解説が
> 一致している内容で、Instagram 自身のヘルプページは取得できなかった。**X の 3:4 という
> 前提が実測で覆った直後なので、この数値も同じ疑いを持って扱うこと。**継ぎ目がずれる /
> 切られるという報告が出たら §2.3 と同じ手順で測り直す。

### 2.3 測定手段 (再現用)

**道具は [tools/x_carousel_probe/](../tools/x_carousel_probe/) に置いてある** (スクリプトと手順書)。
X がまたレイアウトを変えたら、そこの手順で測り直して `SnsTarget::seam_ratio_parts()` を更新する。

内訳は次の 3 つ。

1. **DevTools スニペット** — 投稿ページのコンソールに貼ると、記事ごと・行ごとに画像の表示矩形、
   隙間、`naturalWidth/Height`、配信サイズ (`name=`) を表にする。**自分で投稿しなくても
   他人の公開投稿で測れる。**
2. **座標を色に埋め込んだテスト画像** — 合成キャンバス上の x 座標を
   `R = 255x/(W-1)` (粗) / `G = x mod 256` (密) / `B = 96` (固定) で埋め込んだ 1536x2048 の
   画像を N 枚。スクリーンショットの任意の画素から元画像の x を 1px 精度で復元できる。
   50 % 縮小 + JPEG q75 でも中央値 0px / p90 1px。
3. **`decode_x.py`** — スクリーンショットの 1 行を走査し、倍率と隙間を「元画像の px」で出す。

アプリ (iOS/Android) は DevTools が使えないので、スクリーンショットの画素を直接数える
(§2.1 の iOS 行はこの方法)。**ブラウザとは違う値が出たので、アプリを Web で代用しないこと。**

### 2.4 非対象の SNS

Bluesky のようにグリッドで並べる SNS では、X で使えなくなった 2x2 の 4 分割が今も成立する。
**2x2 は本機能では扱わない** (§5)。要望が出たら配置軸を足す形で拡張する。

## 4. 仕様

### 4.1 データモデル

新規モジュール 2 本。

- `src/sns_split.rs` — 純ロジック (幾何と投稿先プリセット)。ユニットテストはここ
- `src/ui_sns_split.rs` — App グルー (モード出入り、キャンバス描画、パネル、書き出し起動)

```rust
pub enum SnsTarget { X, Instagram }

pub struct SnsSplitLayout {
    pub target: SnsTarget,
    pub count: u8,        // 2..=4
    pub seam_permille: u16, // 0..=100 (枠幅に対する千分率)
    pub group: CropRect,  // source image coordinate
}

pub enum SnsFrameRatio { Free, Ratio3x4, Ratio4x5, Ratio1x1 }
```

`SnsTarget` は投稿先を切り替えたときの**継ぎ目の既定値** (X = 17 permille /
1.7 %、Instagram = 0 / なし) と、Instagram だけに行う書き出し時の比率検査を決める。
枠の比率は投稿先の持ち物ではなく、`SnsFrameRatio` で
**自由 (既定) / 3:4 / 4:5 / 1:1** から独立に選ぶ。`SnsSplitLayout` は選択結果の
`group` を持つので、比率プリセットそのものは持たない。

`CropRect` は既存 [`export_crop::CropRect`](../src/export_crop.rs:17) を**型として**再利用する
(source image coordinate の矩形という意味は同じ)。`CropSettings` / `CropDb` / サイドカーには
一切触らない。

**`SnsSplitLayout` は永続化しない。** `App` が `Option<SnsSplitLayout>` で持ち、モードを
抜けたら破棄する。`Settings` へ残すのは次の 4 つだけで、いずれもページに紐づかない。

- `sns_split_target: Option<String>` (`"x"` / `"instagram"`、既定 `"x"`)
- `sns_split_count: u8` (2..=4、既定 2)
- `sns_split_seam_permille: u16` (0..=100、既定 17)
- `sns_split_frame_ratio: Option<String>`
  (`"free"` / `"3:4"` / `"4:5"` / `"1:1"`、既定 `"free"`)

読み込み時は枚数と継ぎ目を範囲内へ clamp し、不明な投稿先は X、不明な比率キーは自由へ
戻す。投稿先・枚数・継ぎ目・枠比率は次回の操作へ引き継ぐが、ページ上の配置は保存しない。

### 4.2 幾何 — グループ矩形は比率自由、枠は累積境界で分ける

**自由を選んだときの**枠の比率は入力ではなく、選んだグループ矩形から得られる結果である。
枚数を `N`、継ぎ目を `p = seam_permille`、整数化したグループの幅と高さを
`Wg` / `Hg` とすると、横方向を次の単位で分ける。

```
total_units  = N * 1000 + (N - 1) * p
frame_units  = 1000
seam_units   = p
frame_height = Hg
```

枠 `k` (0 始まり) の左右端は、グループ左端からの累積単位をそれぞれ整数ピクセルへ
丸めて決める。

```
start_units = k * (1000 + p)
end_units   = start_units + 1000
x_k_min = Xg + round(Wg * start_units / total_units)
x_k_max = Xg + round(Wg * end_units   / total_units)
y       = Yg .. Yg + Hg
```

`sns_split.rs` はこの導出と、以下の不変条件をユニットテストで押さえる。

- 枠は N 個で高さは共通。割り切れない横幅は累積境界の丸めで配るため、**枠幅同士・
  継ぎ目幅同士はそれぞれ最大 1px 違い得る**
- 枠と継ぎ目を合わせた総幅はグループ幅に厳密に一致し、丸めによる欠落や重複を作らない
- `p = 0` のとき枠が隙間なく連続する
- 832x1216 を継ぎ目なしで 3 分割すると **277 / 278 / 277 x 1216** となり、元画像の
  全幅・全高をちょうど使う
- **枠の幅・高さは必ず 1px 以上**。グループをいくら小さくしても退化しない
- グループ矩形は `frames_extent()` へスナップする。すなわち **`group == frames_extent()`** が
  構成で保証され、「暗転マスクの見た目」と「実際の出力」が食い違わない

**収容規則 (`clamped` / `fits`)**: `clamped` はグループの横と縦を独立に画像へ
収める。画像幅が枚数より小さく、幅 1px の枠を N 枚並べることさえできない場合も枠を退化
させず最小配置を返し、`fits()` が false を返す。UI はこれを理由付きで書き出し不可にする。

比率プリセットが自由以外のときだけ、1 枠の比率 `a` と現在の継ぎ目から
`a * (N + (N-1)*p/1000)` をグループの理論比率として既存の比率固定リサイズへ渡す。
累積境界を整数化した後は、先頭枠の実幅に対してプリセット比率へ最も近く、かつ 3:4 を
下回らない整数の高さへ揃える。これにより、3:4 自身や極小の 4:5 が 1px の丸めだけで
Instagram の 0.75 下限を外れない。

**1536px 幅の枠に対して、継ぎ目 1.7 % で捨てる帯は 26.1px (片側 13.1px)** になる。

### 4.3 操作

- **移動・リサイズはグループ全体**。8 ハンドル + 本体ドラッグ。個別枠は動かせない
  (連結が壊れるため。§5)
- 枠比率が**自由**なら、辺・角の各ハンドルで横と縦を独立に変える。比率プリセット中だけ
  理論グループ比率を固定し、辺では反対辺、角では反対角を固定する P6 の契約を使う
- 投稿先を切り替えると継ぎ目を投稿先の既定 (X = 17、Instagram = 0) へ戻す。自由なら
  グループ矩形を保つ。自由から固定へ切り替えるときは中心と幅を起点に合わせる
- 枚数・継ぎ目の変更も、自由ならグループ矩形を保つ。固定プリセット中は同じ比率へ
  合わせ直す。固定比率間の遷移は、同じ整数ピクセルの中心セルで画像内に置ける最大矩形に
  対する現在の占有率を引き継ぐ。異なる整数格子への初回の丸め後も反復往復で寸法を累積変化
  させず、高さで制限される画像でも単調に縮ませない
- **「画像全体に合わせる」**は、自由なら画像全域そのもの、固定プリセット中なら比率を
  保って画像内に収まる最大の中央矩形にする。モード開始時も保存済みの 4 設定で同じ配置を行う
- パネルには `1 枚 277 x 1216 (0.23)` の形式で、出力サイズを適用する前の
  元画像上の先頭枠寸法と横/縦を表示する。後続枠の幅は累積丸めにより最大 1px 違い得る
- Escape でモード終了 (破棄)。既存の切り取りモードと同じ

### 4.4 描画

`ui_crop` の描画をベースにする。

- グループ外側は暗転 (既存の切り取りと同じ)
- **枠は実線**、枠と枠の間の帯は**暗転**して「ここは出力されない」と分かるようにする
- 枠の中に **1 / 2 / 3 / 4 の番号** (= 投稿順) を出す
- ハンドルはグループの 8 箇所のみ。枠の境界にはハンドルを出さない

### 4.5 投稿後プレビュー

パネル内に、N 枚を現在選択中の継ぎ目比で横並びに描くミニプレビューを置く。
これは校正用ではなく**構図の確認用**。継ぎ目が顔や重要な線の上に落ちていないかは、
並べて見ないと分からない。

### 4.6 書き出し

既存のエクスポートダイアログを経由する。出力先・形式・倍率・連番・メタデータの扱いを
そのまま使うため。

- `ExportEntry` に `crop: Option<CropRect>` を足し、**あるときは `ExportPagePixels.crop` より
  優先**する。`render_export_page_pixels` の適用箇所 1 つの分岐で済む
- entries は N 個。`suffix` = 1..N、`label` = `"1 / 4"` 形式
- Instagram では `frames()[0]` の実際の整数ピクセル寸法を正として横/縦を調べ、
  **0.75 未満または 1.91 超**なら書き出しを止める (境界値は許可)。X には比率制限を
  適用しない。画像が小さすぎる理由を優先し、パネル警告・ボタンの無効理由・実行直前確認は
  同じ判定と「Instagram はこの比率を切り取ります。枠の比率を 3:4 〜 1.91:1 に収めるか、
  投稿先を X にしてください」を使う
- **SNS 分割中は隠蔽プリセットの一括書き出しを無効にする** (現在の設定 1 種に固定)。
  N x 5 = 最大 20 ファイルの出力は意図と合わない。ダイアログでは理由付きで無効表示にする
- 倍率は既存の選択肢のままだが、**既定は `LongEdge(2048)`** (2026-09-01 の実投稿を受けて変更)。
  当初は等倍にしていたが、表示 pixels には AI 拡大が焼き込まれることがあり、実測で 1 枚 5.6MB と
  X の PNG 上限 (5MB) 際まで膨らんだ。`LongEdge` は**元が小さければ何もしない**ので、AI 拡大を
  使っていない画像は等倍のまま出る。§2.1 のとおり X はタイムライン用に `name=small` へ変換し直す
  ため、縮小してもタイムラインの見え方は変わらない。**通常書き出しの既定
  (`Settings::export_default_scale`) は書き換えない**

### 4.7 起動導線

- **編集ツール行の 7 つ目のボタン**として、**エクスポートの右**に置く
  ([ui_adjustment_panel.rs:13953](../src/ui_adjustment_panel.rs:13953) 付近)。
  現在は右から エクスポート / テキスト / 切り取り / 隠蔽 / 補正レイヤー / 消しゴム の順に
  `header_rect.max.x` からの相対で並んでいるので、アンカーを 1 つずらす。
  **エクスポートが右端でなくなる**点は利用者了承済み (2026-09-01)
- **アイコンは「SNS」の文字にしない。**ボタンは 28x28 px で 1 文字 7px になり読めない。
  既存 6 つは全てベクター描画のピクトグラムなので、**縦長の枠が 3 つ並び、間に隙間がある**
  絵を `draw_icons.rs` に `draw_sns_split_icon` として足す
- 有効条件は既存の編集ツールと同じ (`can_overlay_edit` = `Image` / `ZipImage` / `PdfPage`、
  `image_edit_tools_disabled_reason`、連結読み中は無効)
- 見開き表示中は `plan_page_edit_pivot` で Single へ pivot し、退場時に復元する

### 4.8 キー割り当て

[keymap-spec.md](keymap-spec.md) の規約どおり `KeyAction` へ足す。

| Action | 文脈 | 既定 |
| --- | --- | --- |
| `FsSnsSplitMode` | フルスクリーン | **既定割り当て無し** (ボタンが入口) |
| `SnsSplitExecute` | `KeyContext::SnsSplit` (新設) | **既定割り当て無し** |

**書き出しの入口はパネルの「分割して書き出す」ボタン** (2026-09-01 の実機確認による変更)。
当初は `CropExecute` に揃えて <kbd>Ctrl+E</kbd> を既定にしていたが、
**パネルにボタンが無いとキーに気付けない**という指摘を受けた。<kbd>Ctrl+E</kbd> は通常の
エクスポートのものなので混ぜず、モード中に押されたら既存のガードがパネルのボタンを案内する。
アクション自体は残すので「操作カスタマイズ」から割り当てられる。`ini_name()` / `context()` / `trigger()` /
`default_chords()` / `ALL_ACTIONS` / 呼び出し側 helper / [keymap.ini.default](keymap.ini.default)
を揃えること。Escape での退場は既存の切り取りと同じ扱い (keymap 対象外)。

## 5. 非対象

| やらないこと | 理由 |
| --- | --- |
| **2x2 グリッド配置** | X では成立しない (§2.1)。Bluesky 等でしか使えない配置のために軸を増やさない |
| **縦並び (N x 1)** | X にも Instagram にも無い |

| **既存の切り取りへの複数矩形対応** | §3.1 |
| **投稿機能そのもの** | mIV は画像を作るところまで |

## 7. 決定済み / 未決

### 決定済み (2026-09-01、利用者判断)

1. **本体内に直接実装する。**同梱の別 exe にはしない。署名対象 PE の追加・launcher 内包・
   ポータブル同梱・AV 誤検知面が恒久的に増える一方、この操作の瞬間には画像が既に
   フルスクリーンで合成済みなので、一時ファイル経由の利点が無い
2. **通常の切り取りとは別の一度きりの操作**にする。`CropSettings` には触らない (§3.1)
3. **横一列の連結バンド**。選んだ継ぎ目が 0 でなければその帯を捨てる。グループ全体で
   ドラッグ・リサイズし、個別枠は動かさない
4. **配置は 1 x N の横並びのみ**
5. **継ぎ目は なし / 1.7 % / 任意**から選ぶ。任意値は 0.0〜10.0 %、0.1 % 刻み
6. **投稿先は X / Instagram の 2 つ**。投稿先は継ぎ目の既定 (X = 1.7 %、
   Instagram = なし) と Instagram の比率検査だけを決め、枠比率は独立したプリセットにする
7. **ボタンはエクスポートの右**、アイコンは縦 3 枠のピクトグラム
8. **書き出しはパネルのボタンから。**<kbd>Ctrl+E</kbd> は通常のエクスポート専用のままにし、
   `SnsSplitExecute` は既定割り当てを持たない (2026-09-01、実機確認)
9. **固定プリセット時の比率固定リサイズは共有コード側を使う。**掴んだ辺・角の反対側を
   固定して足りない軸を比率から求める。既存の切り取りの比率プリセットにも同じ不具合があったため
   (2026-09-01、実機確認)

### 未決

無し。実装に着手できる状態。実装中に判断が要るものが出たらここへ追記する。

## 8. 利用者向け文書を書くときの注意

- **「これで必ず繋がる」と書かない。**§2.1 のとおり隙間は環境ごとに違い、1.7 % は
  PC ブラウザと iOS アプリに合わせた値。モバイル Web では 1.9px ほどずれる
- **バージョン番号を本文に書かない** (CLAUDE.md「マニュアル・製品ページの記述方針」)
- 内部用語 (CropRect / ExportEntry / パイプライン最終段) を出さない
- Instagram の 0 % が未実測である旨は docs 側 (本書 §2.2) にだけ残す。利用者向けには書かない
