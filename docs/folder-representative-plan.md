# Folder representative thumbnails (§1.275 / §1.276)

Accepted design for v4.1.0 (2026-09-25). This document records the selection and cache contract for automatic physical-folder representatives.

## Candidate order

The requested folder's manual pin wins. Otherwise, at each directory reached within the configured depth, choose the first direct image under `folder_thumb_sort`. If there is no direct image and depth remains, merge physical child directories and ZIP/CBZ/PDF files into one list under that sort. At a child directory's position, honor its own pin, then recurse. A non-image child pin and an archive candidate may use only an already-created, valid, exact catalog thumbnail; never open or render an archive merely to choose a parent representative. An active archive pin requires its exact `#pin:` row; an old unpinned row cannot substitute. Depth zero accepts direct images only. A direct image now beats a child pin, and a cached archive may beat a later-sorted child directory.

## Keys and typed provenance

`FolderThumbProvenance::AutoSelected` means that a folder resolver produced the pixels, including a manual pin that resolves to a folder and then auto-selects inside it. Its key uses `folderthumb:auto-v3:{sort}:d{depth}:{identity}` plus any pin suffix. `Seeded` means a leaf pin or seeded video frame directly supplies the pixels and keeps the released key form, with the existing `auto-v2` base where applicable. Request construction, video seeding, child-pin lookup, cleanup, Remote, and the benchmark must agree. A released row lacking a provenance/proof is usable only for a typed Seeded request. The v3 bump causes one-time regeneration of automatic folder rows; ZIP/PDF keys are unchanged. Cleanup removes obsolete folder keys exactly; synthetic-view catalogs skip `delete_missing`, leaving old rows inert.

## Catalog revision and proof

Each physical-directory catalog owns a random instance ID and an integer archive-row revision in an additive table. SQLite `AFTER INSERT/UPDATE/DELETE` triggers bump the revision for `zipthumb:`, `pdfthumb:`, and pinned `folderthumb:...#pin:` rows, in the row mutation's transaction. The revision table exists before trigger installation and before any cleanup or migration that can mutate thumbnails. A completion marker becomes valid only after all triggers exist; interrupted setup is retried and remains unverifiable until repaired. Deleting and recreating a catalog yields a new instance ID. Older applications ignore this table.

The resolver captures a proof comprising every directory catalog where it examined archive candidates or child-pin rows, in visit order, including misses and directories reached through a child Folder pin. For each directory it records a consistent read snapshot of candidate stamps and `(instance ID, revision)`, or a typed `Absent` when the catalog does not exist. Other I/O failures are `Unverifiable`. The proof also records the winning source path, mtime and size, and the selected catalog-row identity when applicable. The proof is saved atomically with the folder WebP. An explicit empty proof means no archive/pin-row dependency; missing or malformed proof on an AutoSelected row is invalid.

The separate folder-pin store owns a store-wide random instance ID and revision. The revision row and its `AFTER INSERT/UPDATE/DELETE` triggers are installed in one schema transaction. Those triggers advance the revision in the same transaction as every pin row mutation, including cleanup and rename paths. Each resolver pin lookup reads the row and revision in one SQLite snapshot. The proof has a required typed pin-store field: `NotConsulted` or `Observed(state)`. A proof written before this field existed fails deserialization and is reselected. The proof records the revision once any candidate's pin state is consulted; if later lookups observe a different revision, it becomes `Unverifiable`. A direct-image winner found before any pin lookup has no pin dependency. Missing pin-store access or an I/O error is `Unverifiable`, never an assertion that no pins exist. Validation compares the current pin-store pair, so changing a child image pin or adding an archive pin invalidates an automatic parent even when no thumbnail catalog row changes.

Startup emits `db_open_folder_thumb_pins` with elapsed milliseconds and `migration_ran`, measuring the additive schema work on first open. `bench_scroll` uses a persistent empty pin store beside its cache catalogs, so its automatic proofs can validate on warm benchmark runs without using the user's manual pins.

On an AutoSelected cache hit, the heavy-I/O worker checks the proof's catalog and pin-store identities/revisions with short-lived read-only handles and checks the winning source with one metadata call. A mismatch, `Unverifiable`, or missing proof triggers reselection. It never enumerates directories or opens archives during validation. The in-memory cache entry carries the same proof and takes the same validation path. Seeded rows are never proof-validated; a Seeded miss must not run the automatic resolver or replace pinned content. Legacy catalogs without the revision table are initialized once on the worker by a row-preserving writable open. A failed initialization is memoized by catalog path and the main DB plus WAL identity/stamp for the process lifetime; validation remains `Unverifiable` without retrying the writable open until the catalog changes. Candidates can still use released rows, but the next request reselects.

## Timing and limits

The resolver checks cancellation during enumeration, between candidates and directories. It reuses one catalog handle per visited directory, queries candidate stamps incrementally with the revision in a short read snapshot, and stops at the first winner. It reads stamps without BLOBs and only loads/decodes a promising WebP. It runs on the thumbnail heavy-I/O worker. A proof-validation perf event records proof length, elapsed milliseconds and outcome.

The proof is captured before the folder row is saved. A later catalog mutation advances its revision, so the next load rejects that row. Returning to a parent reloads and validates it. Already-visible textures remain until the list is next loaded, as with existing child-image changes. The guarantee covers catalog-row mutations and the winning source's deletion/rename/change. Other deep filesystem changes that mIV did not make retain the existing folder-mtime behavior.
