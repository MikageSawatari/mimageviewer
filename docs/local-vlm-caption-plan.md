## 0. 要約

- 画像の内容を、**PC 内で動く画像対応の AI モデル (VLM)** に短い説明文と検索語にさせ、mIV の索引へ保存する。
  画像は PC の外へ出ない。
- 用途は 2 つ。(1) mIV の検索 (Ctrl+G / Ctrl+F) で「海」「誕生日」「猫」のように内容で探せる。
  (2) MCP で、画像の代わりに説明文を AI アプリ (Claude / ChatGPT) へ渡せる (画像を送らずに整理を頼める)。
- **使うのは通常の (検閲を外していない) モデル**。mIV は**出力の内容に関与しない** (選別・書き換え・言い換えをしない)。
- 推論は llama.cpp (MIT) を組み込んだ**別プロセスの worker** (`mimageviewer-vlm.exe`) で行い、
  本体とは匿名パイプで通信する。**ネットワークで待ち受けない** (MCP と同じ方針、§4)。
- モデルは追加ダウンロード。**Qwen3.5-4B (Apache 2.0) の 1 モデルに固定する** (2026-11-02 利用者決定、V0 の比較で
  9B と品質の差が見えなかったため。§3.3・§18.6)。モデルを選ぶ画面や機種ごとの段は作らない。
- 段階: V0 = 製品外でのモデル比較 → V1 = worker・ダウンロード・作成ジョブ・保存・表示 → V2 = 検索 →
  V3 = MCP の返却列。

## 1. 目的と範囲

### 含むもの

- お気に入り配下などの**画像ファイル** (FS 上の静止画) の説明文と検索語の作成。
- **本** (ZIP・PDF・EPUB・RAR などの書庫・フォルダ) の**表紙**の説明文と検索語の作成 (§6.7、U16)。
- 利用者が明示的に始める作成ジョブ (選択した項目・現在のフォルダ)。進捗表示と中止。
- 説明文の保存、メタデータパネルでの表示、検索への反映、MCP での返却。

### 含まないもの (v5 の初回)

- ZIP 内画像・PDF ページを 1 枚ずつ扱うこと、ZIP の中のフォルダとして見える本 (`ZipDir`)、動画・音声 (後段、§14)。本は表紙だけを扱う (§6.7)。
- 何もしていない間の自動作成 (後段。2026-11-02 利用者決定 U5)。
- GPU (Vulkan) が使えない機種。「GPU が必要です」と表示して機能を使えなくする (U7)。
- 説明文から mIV タグ (`tags.db`) を自動で付けること。検索語は**タグとは別系統**の検索用テキストにする
  (サイドカー §4.10 と同じ扱い)。タグ化したいときは、利用者か MCP 経由の AI アプリが提案・適用する。
- mIV 内のチャット・エージェント (2026-11-02 の検討で後回しにした)。
- 利用者が任意の GGUF を指定すること。v5 は mIV が用意した一覧のモデルだけ (§12 R3)。
- 検閲を外したモデル (2026-11-02 利用者決定)。

### 内容に関与しない方針 (2026-11-02 利用者決定)

- モデルの出力は長さの上限 (§6.4) で切ることと、検索語の全く同じ語の重複を除くこと (§21.7.3) 以外、そのまま保存・表示・返却する。
- 語の選別・置き換え・伏せ字、内容による保存拒否、「断ったかどうか」の判定はしない。
  モデルが説明を断った文や曖昧な文を返したら、それもそのまま保存する。
- 公開文書では「画像の内容を AI が文章にしたもの。正確とは限らない」と処理内容で説明し、
  「検閲」「安全」などの評価語や、特定の用途に向けた宣伝はしない。

## 3. モデル

### 3.1 候補 (2026-11-02 時点、出どころは §17)

数値は 4bit (Q4_K_M) の**重みだけ**のサイズ (出どころ: vdf.ai の比較記事、2026-10-06)。
画像トークン用の作業メモリと mIV 自身の VRAM は含まない。

| 段 | 候補 | 重みの目安 | ライセンス |
| --- | --- | --- | --- |
| 軽量 (8GB) | Qwen3.5-4B / Qwen3.5-9B、Gemma 4 E4B | 9B 約 5.9GB、E4B 約 4.9GB、4B は未確認 | Apache 2.0 |
| 標準 (12〜16GB) | Qwen3.5-9B (8bit で約 9.7GB)、Gemma 4 12B | 12B は未確認 | Apache 2.0 |
| 高品質 (24GB、**候補から外した**、§3.2) | Qwen3.5-27B、Gemma 4 31B、Qwen3.5-35B-A3B (MoE) | 約 17.0 / 19.1 / 22.0GB | Apache 2.0 |

- Gemma 4 は画像のトークン数を 70〜1120 から選べる (モデルカード)。説明文には少なめが向くとされる。
- Gemma 4 のモデルカードは「140 以上の言語」とだけ書き、日本語を名指ししていない。日本語の質は V0 で確かめる。
- 予備: GLM-4.6V-Flash 9B (MIT)、Ministral 3 (Apache 2.0)、MiniCPM-V 4.6 1.3B (Apache 2.0)。
- 採らない: Llama 4 (EU の企業への制限があり、大きすぎる)、LFM2.5-VL (年商による商用制限)。
- Qwen3.6-27B (2026-04、Apache 2.0) は画像対応かどうか未確認。

### 3.2 候補の絞り込み (2026-11-02 利用者決定)

- **v5 の候補は 4B 級と 9B 級だけにする。** 27B 級以上は、VRAM にぎりぎり収まっても他の機能との併用が厳しく、
  使える機種が RTX 5090 など一部に限られるため外す (§11.1 の見積もりとも一致)。
- 比べる候補: Qwen3.5-4B / Qwen3.5-9B、Gemma 4 E4B (と、必要なら予備の GLM-4.6V-Flash 9B)。
- 注意: Gemma 4 E4B は実効 4.5B だが、埋め込み込みでは 8B あり、4bit の重みは約 4.9GB で
  Qwen3.5-9B (約 5.9GB) に近い (§3.1)。VRAM の点では「4B 級」と見なせない可能性があり、V0 の実測で確かめる。
  Qwen3.5-4B は Hugging Face 上で約 5B パラメータ、9B は約 10B と表示されている。

### 3.3 決め方

- V0 (§14) で 4B 級と 9B 級を比べる。系統は 1 つにそろえる (プロンプトと出力の調整を 1 系統で済ませるため)。
- **4B 級と 9B 級で品質に大きな差がなければ、4B 級の 1 モデルに固定する** (利用者が挙げた選択肢)。
  固定すると、モデル選択の画面・複数モデルのダウンロードと削除・機種ごとの段の判定 (§11.2 (d)) が要らなくなり、
  8GB 機にも載せやすい。
- 差がある場合は、4B 級と 9B 級の 2 段を利用者が選ぶ。GPU の VRAM 総量から「推奨」を表示するだけで、自動では選ばない
  (実行時の状態で挙動を変えない方針)。
- 「大きな差」の判断は利用者が評価用セットの結果を見て行う。
- **決定 (2026-11-02 利用者): Qwen3.5-4B に固定する。** V0 の目隠し比較で 4B と 9B に差が見えず (§18.6)、
  Gemma 4 E4B は出力が安定しなかった (§18.3)。取得するのは Q4_K_M の本体 (2.74GB) と画像用部品 mmproj-F16 (0.67GB) の 2 ファイル。
  9B 以上を選べるようにするのは、利用者から要望が出てからの後段とする。

## 4. 推論エンジンと worker の構成

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A | llama.cpp の `llama-server` を子プロセスで起動し、127.0.0.1 の HTTP で呼ぶ | 不採用。PC 内の他プロセスやブラウザから届く口ができ、「mIV はネットワークで待ち受けない」が崩れる。鍵と Origin 検査を足す管理も増える |
| **B** | **llama.cpp (libllama + libmtmd) を組み込んだ自前の worker exe。本体とは匿名パイプ (長さ付きの枠、§21.3)** | **推奨**。待ち受ける口が無い。既存の TRT worker・PDFium worker と同じ形で、落ちても本体を巻き込まない |
| C | 同梱済みの ONNX Runtime (DirectML) + onnxruntime-genai | 不採用。VLM の ONNX 版がほぼ無く、今の `ort` (api-24) との組み合わせの制約も増える |

- GPU は **Vulkan 版**を既定にする (NVIDIA / AMD / Intel で 1 本の build が動き、CUDA 版より配布が小さい)。
  速度差は V0 で測る。CUDA 版を足すかは V0 の結果で決める。
- **worker がネットワークに触れないことを、リンクする範囲で保証する** (独立レビュー 1 回目 P2-7 で改めた)。
  llama.cpp は版を固定する (V0 は b12032)。この版では `LLAMA_CURL` は廃止済みで指定しても効かず、代わりに HTTPS 用の
  `LLAMA_OPENSSL` が既定 ON になっている (`CMakeLists.txt`、§17)。そのため「curl を無効にした」ことは保証にならない。
  - worker にリンクするのは `ggml`・`libllama`・`libmtmd` だけにする。モデルの取得・HTTP・RPC を持つ `common`・`tools`
    (server / downloader)・`ggml-rpc` はリンクしない。`LLAMA_OPENSSL=OFF`、`LLAMA_BUILD_SERVER` / `TOOLS` / `EXAMPLES` / `TESTS` = OFF、`GGML_RPC=OFF`。
  - build の検査で、worker exe と同梱 DLL の import に `ws2_32.dll`・`winhttp.dll`・`wininet.dll` が無いことを確かめる (CI でも回す)。
  - chat template と grammar (JSON schema からの文法変換) が `common` 側にある場合は、必要な部分だけを worker 側に持つ。
    どこまで `common` に頼らずに済むかは V1 の最初に確かめる (§16)。
- **推論する GPU と、8GB の判定に使う GPU を同じものにする** (同 P2-5)。今の `gpu_info` は DXGI で最初に見つかった
  専用メモリ付きのアダプタを返すだけで、Vulkan の device とは結び付いていない (`src/gpu_info.rs`)。
  VLM 用に 1 つの判定関数を作り、「使う Vulkan device」と「その device の VRAM 総量」を一緒に返す。device は専用メモリが最大の
  アダプタとし、Vulkan の device LUID (`VkPhysicalDeviceIDProperties`) と DXGI の adapter LUID で突き合わせる。
  worker にはその device を指定して起動する。判定は総量だけで、空き VRAM は使わない (U1)。
- **画像ごとに推論の状態を独立させる** (同 P2-8)。重み (モデルと mmproj) はジョブの間使い回し、会話・KV キャッシュ
  (memory)・sequence と位置・grammar 付きの sampler は 1 件ごとに作り直す (またはクリアする)。前の画像の内容が混ざらないこと、
  連続処理で文脈を使い切らないことを、V1 の最初の確認で「A の後に B を処理した結果」と「B だけを処理した結果」が一致することで確かめる (温度 0)。
- Rust からの組み込み方 (`llama-cpp-2` crate か、C API の自前 binding か) と、libmtmd を Rust から使えるかは未確認 (§16)。
- worker の寿命: 作成ジョブの開始で起動 → モデルを読み込む → 1 件ずつ処理 → ジョブの終了・中止・mIV の終了で終了。
  Job Object の kill-on-close (`src/epub_convert.rs` の EPUB worker に実例がある) で、本体が落ちても
  VRAM を持ったまま残らないようにする。常駐はさせない。
- 入力画像は**本体側の既存デコーダ** (WIC / TurboJPEG / LibRaw ほか) で読み、縮小した RGB をパイプで渡す (共有メモリは使わない、§21.3)。
  対応形式が本体と完全に一致し、worker にデコーダを持たせずに済む。

## 5. モデルの配布

- **2026-11-03 改め (U20)**: 配布元は mIV 側で量子化したモデル (GitHub Releases、分割) にした。下の Hugging Face から直接取る案は採らない。詳細は §21.7.1。
- 保存先: `<data_dir>/addons/vlm/packs/<model_id>/`。`INSTALL_OK` と `active.json` で導入済みを判定する。
- 取得元: mIV の固定 GitHub Releases `vlm-model-v1`。公式の重みから mIV 側で量子化した本体と mmproj、LICENSE、NOTICE を配る (§21.7.1)。
  本体は 2GiB 未満の部分に分割する。index の schema、ファイル・部分のサイズと SHA-256 を検証し、全体の検証後だけ有効にする。
- 取得: 既存と同じく `.partial` への Range 再開・再試行・sha256 の照合。取得は利用者の明示操作でだけ始める。
- ライセンス: モデルの Apache 2.0 の本文と NOTICE、llama.cpp / ggml の MIT をライセンス表示に加える。
- 削除: 設定画面からモデルを削除できる (1 モデルなので項目は 1 つ)。説明文はモデルを消しても残る。

## 6. 説明文の作成ジョブ

### 6.1 始め方

- 一覧の右クリック「AI 説明文を作る」(選択項目、何も選んでいなければ現在のフォルダの直下)。
  既定のショートカットは割り当てない。足すときは `KeyAction` 経由にする。
- 進捗を表示するモードレスの小窓 (件数・現在の項目・中止)。同時に動くジョブは 1 本。
  作成中にもう一度始めた分は、今のジョブの後ろに足す (§12 R1)。
- **初めて使うとき (モデルが未取得のとき) は、モデルの取得案内を出す** (2026-11-02 利用者決定)。編集用追加パック
  (editing-add-on-download-spec §1・§4) や TensorRT pack と同じく、本体には同梱せず追加ダウンロードにする。
  起動時や通常の閲覧中には案内しない。「AI 説明文を作る」を選んだときだけ出す。
  - 確認画面 (モーダル) に、取得と合わせて次を書く。注意はこの画面とマニュアルで伝え、初回設定には ON/OFF を置かない
    (作成は手動なので止める動きが無く、スイッチを置いても「メニューに出すか」だけになり、取得状態との組み合わせが増えるため)。
    - 何をするか: 画像の内容と画像内の文字を、PC 内の AI が文章と検索語にする。画像は PC の外へ出ない。正確とは限らない。
    - 取得するもの: モデル (Qwen3.5-4B、約 3.4GB) と取得元、ライセンス。
    - **VRAM の総量が 8GB 級で、AI 補正が「高品質」のとき**: 「AI 補正と同時に使うと遅くなることがあります。
      快適に使うには AI 補正を『軽量』にして、mIV を再起動してください」と 1 行出す。文言は表示した時点の VRAM 総量と設定だけで決め、状態は持たない。
      再起動まで含めるのは、mIV が一度読み込んだ AI 補正のモデルをモードを変えても降ろさないため
      (`apply_ai_feature_mode_change` は結果のキャッシュを消すだけで、`AiRuntime` の `sessions` は残る。§18.4、独立レビュー 1 回目 P2-6)。
      降ろす仕組みは足さない (U1 は同時に動かす前提で、状態を増やさない)。
    - ボタン: [ダウンロード] [今はしない]。
  - **VRAM の総量が 8GB 未満のとき**は、取得を勧めず「この PC の GPU では使えません (VRAM 8GB 以上が必要)」とだけ出す (U1)。
    Vulkan が使えないときも同様 (U7)。
  - 取得中は進捗の画面 (modeless、キャンセル可。§21.7.2 で改定) を出す。取得と検証は worker で行い、UI スレッドは止めない。
    キャンセルと失敗の扱いは編集用追加パックと同じ (`.partial` を残して次回に再開、失敗はログ + 通知)。
  - 取得が終わったら、選んでいた項目で作成ジョブを始める。対象はクリックした時点のパスを持ち、取得中に一覧を動かしても変えない。
    ただし取得は数分かかり得るので、この間に画面外 (エクスプローラーなど) で対象が消えた場合は、ジョブ側の「対象のファイルがもう無い」(§6.5) で扱う。

### 6.2 1 件の流れ

1. 保存済みの説明文が「`status = ok`・同じ画像 (署名一致)・同じモデル・同じプロンプト版」なら飛ばす。失敗の行は飛ばさない (§6.5)。
2. 本体の worker スレッドで画像を読み、**長辺 1024px** まで縮小する (拡大はしない。2026-11-02 利用者決定 U9、§18.7)。
   利用者が選ぶ設定にはしない (V0 では速度と VRAM が同じで、精度は 1024px が劣らなかったため、選ぶ理由のある取捨が無い。
   選べるようにすると、同じ画像でも設定で説明文が変わり、保存する記録と作り直しの判断が増える)。
   RTX 4090 より遅い GPU での速度は未計測。V1 で遅い GPU で測り、1024px が目に見えて遅い場合だけ考え直す。
3. worker へ渡して推論する。出力は JSON schema (文法) で `{"caption": "...", "text": "...", "keywords": ["..."]}` の形と
   上限に固定する (§6.3・§6.4)。
4. 結果を保存し (§7)、その 1 件の索引を更新する (§8)。

### 6.3 プロンプト

- 固定のプロンプトを mIV が持ち、`prompt_version` で管理する。利用者による編集は v5 では出さない。
- 説明文と検索語は日本語だけにする (U4)。英語 UI の利用者向けは後段で検討する。
- 内容の観点を限定する指示 (例: 「人物の年齢を推定しない」) は入れない。内容に関与しない方針 (§1) のため。
  入れるのは形式の指示 (長さ・文体・検索語の個数) だけにする。
- **出力は 3 欄**: 説明文 (`caption`)・**画像内の文字** (`text`)・検索語 (`keywords`)。画像内の文字は、表紙の題名・作者名、
  看板、ラベルなどを書かれているとおりに書き写す欄で、無ければ空にする。目的は Ctrl+G / Ctrl+F で当たるようにすること。
  題名と作者名を別の欄に分けることはしない (2026-11-02 利用者判断: 検索で当たれば足り、作品名と作者名の区別はモデルにも難しい)。
  V0 で使ったプロンプト (v0-3、§18.7):

  ```text
  この画像に写っているものを日本語で説明してください。
  caption: 1〜3 文、200 文字以内。写っていないことは書かない。
  text: 画像の中で読み取れる文字 (題名・作者名・看板・ラベルなど) を、書かれているとおりに書き写す (200 文字以内)。無ければ空文字。推測で補わない。
  keywords: 画像を検索するときに使える日本語の語を 5〜15 個。
  ```

- 出力は JSON schema で形を固定し、**§6.4 の上限も schema に書く** (`maxLength` / `maxItems`)。llama.cpp は schema を文法に
  変えて生成を縛るので、上限を超える出力が作られない。V0 で、上限を書かない schema では検索語の列が同じ語の繰り返しで
  止まらなくなった例が 26 枚中 1 枚あり、上限を書くと 26 枚すべて正しく終わった (§18.7)。

### 6.4 上限

- 説明文は 400 文字、画像内の文字は 400 文字、検索語は 20 個・1 語 32 文字。schema に書いて生成の段階で守らせ (§6.3)、
  生成のトークン数にも上限を置く (V0 では 800。表紙の奥付のような文字の多いページで約 360 トークン使った)。

### 6.5 中止と失敗

- 中止は処理中の 1 件の推論が終わった時点で止める (途中の結果は保存しない)。
- **成功の条件** (独立レビュー 1 回目 P2-9): 生成が終了トークンで止まり (出力上限で止まっていない)、JSON として完全で、
  3 欄の型と §6.4 の上限を本体側でも検証して通ったものだけを `ok` として保存する。grammar は出力上限までに JSON が
  閉じることまでは保証しないため、この検証を省かない。
- 失敗 (読めない画像・JSON の不成立・出力上限で止まった) は次へ進み、ジョブ全体は止めない。
  その項目に `ok` の行が既にあれば、それを残して上書きしない。`ok` の行が無ければ `failed` の行を書く (パネルで「失敗」と出すため)。
  失敗の行は次のジョブで飛ばさずにやり直す (§6.2)。自動の再試行はしない。
- 対象のファイルがもう無い (ジョブの途中で mIV の外から消された) ときは、何も保存せずに次へ進む。
- worker の異常終了・モデルの読み込み失敗・VRAM 不足は、ジョブを止めて通知する。
  **まれな失敗は割り切り (ログ + 通知。やり直しは利用者がジョブを始め直す)**。自動の再試行や再起動はしない。

### 6.6 ジョブの持ち主と、改名・削除・取り込みとの順序

VLM の結果は推論の後に届く。何もしないと、A を推論している間に A→B と改名した場合に、DB の付け替えの後で A の行を書いてしまう。
削除の後の保存も同じ形になる (独立レビュー 1 回目 P1-1)。

**方針 (2026-11-02 利用者の案、U14): 書く直前に、ファイルが作業を始めたときと同じ状態かを確かめ、違えば結果を捨てる。**
改名・移動・削除は普段あまりしない操作なので、重なった項目は作り直しを利用者に任せ、順序を合わせる仕組みは作らない。

- **ジョブの持ち主は App に 1 つ** (`CaptionJobOwner`)。ウィンドウ (viewport) ごとには持たない。detached viewer を閉じてもジョブは続き、
  mIV の終了でジョブは中止される (worker は Job Object で終わる)。
- **DB に書くのは持ち主の保存役だけ**。worker は DB を書かず、結果を持ち主へ返す。
- **画像を読むときに、その時点のパスと署名 (サイズ・更新日時) を覚える**。結果はこの 3 つと組で持つ。
- **保存は 1 つのトランザクションの中で、確かめてから書く**:
  1. `ai_caption.db` に `BEGIN IMMEDIATE` (書き込みの lock を取る)。
  2. そのパスのファイルの署名を取り直し、覚えた署名と比べる。
  3. ファイルが無い・署名が違う → 書かずに終える (結果を捨てる。ログに件数だけ残す)。同じ → 書く。
  4. `COMMIT`。
- この順序で、改名・削除とどう重なっても正しくなる。既存の改名の移行と孤児整理は、ファイル操作が終わった**後に**、同じ DB を
  `BEGIN IMMEDIATE` のトランザクションで付け替え・削除する (`rename_key_migration::migrate_store`)。そのため:
  - 確かめる前にファイル操作が済んでいれば、2 で「無い」と分かって捨てる。
  - 確かめた後にファイル操作が起きても、DB の付け替えは保存の `COMMIT` の後になるので、書いた行は新しいキーへ正しく運ばれる。
  - 「確かめてから書くまでの間に、付け替えが先に済む」ことは、lock があるので起きない。
- 待ち行列にある項目が改名・削除されていた場合は、読み込みで「ファイルが無い」になり、何も保存せずに次へ進む (§6.5)。
  改名後の項目は、利用者がもう一度「AI 説明文を作る」を選ぶと作られる。
- 画像がその場で書き換えられた (同じパスで署名が変わった) 場合も、同じく捨てる。古い画像の説明文を新しい画像に付けない。
- **割り切る場合 (2026-11-02 利用者決定 U15、独立レビュー 4 回目 P1)**: 名前を入れ替える操作 (本のページの並べ替えなど) は、
  ファイル名の入れ替えを済ませてから DB の行を付け替える (`books.rs` の並べ替え → `rename_key_migration` の一時キー経由の付け替え)。
  この 2 段の間にジョブがそのページを読むと、名前を変えても署名 (サイズ・更新日時) は変わらないので確認を通り、正しい説明文が
  一度保存される。その直後の付け替えが、その行を「元のページの説明文」として別の名前へ運ぶため、1 ページ分の説明文が別のページに付く。
  付いた先でファイルの署名 (サイズ・更新日時) が違えば「古い」と表示され、作り直せる。ただし、別の画像でもサイズと更新日時が
  同じ場合 (同時に展開した同じ大きさの無圧縮画像など) は、誤って付いたことを見分けられず「古い」にもならない。§6.2 の飛ばす条件にも
  当たるので、通常の作り直しでも直らない (独立レビュー 5 回目 P2)。また、署名が同じ画像どうしの入れ替えなら、入れ替えの前に読んで
  付け替えの後に保存した場合も確認を通る。上書きで失われるのは機械の出力だけ。
  起きるのは、作成ジョブ中に同じ本のページを並べ替えた場合だけなので、仕組みは足さない。
- **メタ情報の書き出し・取り込みは、作成ジョブ中も止めない**。書き出しは DB の読み取りなので、ジョブの書き込みと重なっても
  どちらかの時点の内容になるだけ。取り込みとジョブの保存が同じ項目に重なったときは、後から書いた方が残る。どちらも今のファイルに
  対する機械の出力で、利用者が作ったデータではないので、後勝ちでよい。
- 改名の移行の待ち対象 (`rename_migration_writers_busy`) には加えない。保存の lock と署名の確認で足りるため。
- **同じ項目をもう一度頼まれた**ら、待ち行列にあれば足さない。推論中の 1 件なら、その結果の保存の後に (§6.2 の飛ばす条件で) 飛ばされる。
- **モデルの削除は、作成ジョブの実行中はできない** (設定画面のボタンを無効にする)。
- 経緯: 独立レビュー 2 回目までの案は「改名・削除の間は保存の受付を閉じ、成功した付け替えに合わせて待ち行列と結果の名前を直す。
  ジョブ中はメタ情報の書き出し・取り込みを止める」だった。2026-11-02、利用者の案 (確かめて違えば捨てる) に置き換え、
  受付の開け閉め・名前の付け直し・取り込みの停止をすべて外した。

### 6.7 本の表紙 (2026-11-02 利用者決定 U16)

本 (ZIP・PDF・EPUB・RAR などの書庫・フォルダ) は、表紙の画像から説明文を作る。用途は、表紙の題名・作者名を読み取り、MCP で AI アプリに
本の整理を頼むこと (例: 題名・作者ごとに分ける、タグを提案させる)。本を開く必要は無い。

- **保存の場所は新しく作らない**。タグと★はすでに、一覧の本のセル (`GridItem::ZipFile` / `PdfFile` (EPUB を含む) / `ConvertibleArchive` /
  `Folder`) に、本のパスをキーにして付けられる (`tag_ops.rs` の `tag_target_for_item`、`rating_path_key`)。説明文も同じく本のパスを
  `item_key` にして `ai_caption.db` に 1 行持つ。改名・移動への追従は §7 の `STORES` の仕組みがそのまま効く。
- **対象**: 一覧の本のセルのうち、実際のパスを持つもの。ZIP の中のフォルダとして見える本 (`GridItem::ZipDir`) はキーが合成なので v5 では
  対象外とする。フォルダは、**利用者が選んだときだけ**本として扱う (選んでいないときの「現在のフォルダの直下」には、直下の画像と
  ZIP・PDF などの本を含め、サブフォルダは含めない)。普通のフォルダを選んだ場合も、その表紙 (下の規則) の説明文になる。
- **始め方**: 画像と同じ右クリックの「AI 説明文を作る」。選んだセルが本なら表紙を、画像ならその画像を処理する。ダブルクリック (本を開く) は使わない。
- **表紙は一覧のサムネイルと同じもの**にする: 利用者が固定した表紙 (`folder_thumb_pins.db`) → ZIP・RAR は最初の画像 → PDF・EPUB は
  1 ページ目 → フォルダは並び順で最初の画像。見えている表紙と AI が読む表紙を一致させるため。
- **表紙の解決を 1 つにまとめる** (独立レビュー 6 回目 P2-3・P2-4 で改めた)。今、表紙を決める処理は、固定表紙の適用と変換済み書庫の選択が
  `App` 側 (`app.rs` の固定表紙・変換済み書庫の処理)、読み込みが `thumb_loader` 側に分かれ、PDF のパスワードもサムネイルの経路から渡されている。
  固定表紙はフォルダ内の画像だけでなく、子の ZIP の中の画像・子の PDF のページ・子のコンテナの固定表紙のたどり (`FolderPinSource::ZipEntry` /
  `ZipDir` / `PdfPage`) も指せる。そこで、**本のキーを受け取り、「実際に読むもの (ファイル / 書庫の中のエントリ / PDF のページ)・その場所・
  署名」をまとめて返す 1 つの解決** (`resolve_book_cover`) を既存の経路から切り出し、一覧のサムネイルと説明文の両方がそれを使う。
  PDF の保存済みパスワードも、この解決の中で既存のサムネイルと同じく渡す (`render_page_anonymous` はパスワードを渡せないので使わない)。
  切り出しはサムネイルの挙動を変えない形で行う。
- **署名と `cover_ref`**: 解決の結果をそのまま記録する。`cover_ref` は「実際に読んだもの」を区別できる形 (読んだファイルの本からの相対パス +
  書庫の中のエントリ名 / PDF のページ番号) にする。署名は**保存先のキーが指すもの**で取る (独立レビュー 7 回目 P2 で改めた):
  - ファイル 1 つの本 (ZIP・PDF・EPUB・RAR・7z・LZH): **本そのもののファイル**のサイズ・更新日時。RAR・7z などは変換済みの別の ZIP を
    読むことがあるが (`archive_cache`)、読んだ変換済み ZIP の署名は使わない。変換済み ZIP が残ったまま元の本が改名・削除されても、
    保存の確認 (§6.6) で元の本が無い・違うと分かって捨てられる。解決は「元の本」と「実際に読んだもの」の対応も返し、変換済み ZIP が元の本に
    対応しているかは既存の確かめ方 (`archive_cache` の元ファイルと cache の両方の確認) で見る。
  - フォルダの本: キーのフォルダにはサイズ・更新日時の意味が無いので、**実際に読んだファイル** (フォルダの中の画像・子の書庫・子の PDF) の
    サイズ・更新日時。フォルダが改名・削除されれば、そのファイルも無くなるので捨てられる。
  - **EPUB は、実際に読んだ変換済みの世代の元ファイルの署名を使う** (独立レビュー 6 回目 P2-2)。保持済みの変換世代があると、今の EPUB を
    確かめる前にその世代を返すため (`pdf_loader::resolve_epub_at`)、今のパスから取り直した署名を古い世代の表紙に付けない。読んだ世代の
    元ファイルの署名 (`ReadTarget` の `display_source_state`) を記録し、保存の確認 (§6.6) では今の元ファイルの署名と照合する。
- **「古い」の判定も、作り直しを飛ばす判定も、同じ照合で行う**: 今の表紙の解決の `cover_ref` と署名が、行と一致するか。表示 (§9) と MCP (§10) の
  「古い」もこの照合で決める (独立レビュー 7 回目 P2。固定表紙は本とは別の DB にあり、ZIP の固定表紙を別のページに変えても ZIP の署名は
  変わらないため、署名だけでは「古い」にならない)。表紙の解決はファイルを読むので、表示用の共有キャッシュ (§9) の読み込み worker で行い、
  UI スレッドでは行わない。
  **照合し直すきっかけ**: 固定表紙の変更・解除と、表紙の選び方を変える既存の操作 (一覧のサムネイルの読み直しを起こすもの) でも、共有キャッシュを
  全部消して世代を進める (独立レビュー 8 回目 P2)。固定表紙の変更は説明文の行を変えないので、§9 の書き手からの無効化だけでは照合し直されない。
  つなぐ場所は、固定表紙の変更がサムネイルの読み直しを要求している既存の経路 (`app.rs` の固定表紙の変更・解除の処理) と同じにする。
- **作り直しを飛ばす条件 (§6.2) にも、今の表紙の解決を使う** (独立レビュー 6 回目 P2-1)。本では「`status = ok`・今の解決の `cover_ref` と署名が
  行と一致・同じモデル・同じプロンプト版」のときだけ飛ばす。固定表紙を変えれば、本体のファイルが変わらなくても作り直される。
- **未変換のファイルは飛ばす** (2026-11-02 利用者決定 U18、独立レビュー 6 回目 P2-5)。対象は、PDF へ変換していない EPUB と、変換が要るのに
  有効な変換済みの ZIP が無い書庫 (7z・LZH と、solid・入れ子・暗号化の RAR)。変換が要るかどうかは、一覧と同じ既存の判定
  (`rar_loader` の直接読み取りの可否と、`App` の `ConvertedArchiveSourceState` = Direct / CachedZip / Unavailable) で決め、Unavailable を飛ばす。
  直接読める RAR は処理する (独立レビュー 8 回目 P2 で、RAR を一律に対象外とした誤りを直した)。何も保存せず (`failed` の行も書かない)、次へ進む。ジョブの終わりに「未変換のため飛ばした件数」を出し、
  「一度開いて変換すると作れます」と添える。
  理由: 表紙を読むには変換が要るが、変換は確認・中止のあるモーダルの受付 (`ui_dialogs/epub_convert.rs` ほか) で行う。作成ジョブからその受付を
  呼ぶと、ジョブの途中にモーダルの変換と中止が挟まり、組み合わせが増える。
- **プロンプトは画像と同じ** (§6.3)。V0 の比較用画像にも本の表紙・奥付が 6 枚あり、題名・作者名・レーベル名を書き写せていた (§18.7)。
- **表示**: 情報パネルは本を開いて見ているときだけ出る (`draw_metadata_panel` は fullscreen 側からだけ呼ばれる)。パネルには今も
  「この本」のタグ・★の欄 (`current_metadata_panel_container_rating`、`tag_target_note_for_item`) があるので、その並びに本の説明文を出す。
  一覧で本を選んだだけのときの表示は v5 では作らない。
- **MCP**: `get_item_info` は今も本を 1 項目として返す (種類 Archive / Pdf / Folder、★とタグ付き、`item_info.rs`)。ここに §10 の
  `ai_caption` 列を本でも返す。ページ・エントリを指定した要求では、本の説明文を `container_ai_caption` として返す (`container_tags` と同じ形)。
  ページ・エントリの指定に今対応しているのは PDF と ZIP 系だけで (`item_info.rs`。EPUB・RAR などは拒否される)、`container_ai_caption` は
  この既存の対応範囲に足すだけにする。対応範囲は広げない (独立レビュー 6 回目 P3)。
- **検索**:
  - Ctrl+F は今いる一覧の各項目をその場で照合し、本のセルも対象 (今は名前) なので、本の説明文も照合に加える。
  - Ctrl+G の索引に本として載っているのは PDF・EPUB だけで (`ingest_worker.rs`、`IndexKind::Pdf`)、ZIP・RAR・フォルダの本は載っていない
    (search-container-item-redesign §3.2 の「ZIP は Ctrl+S だけ」の設計)。PDF・EPUB の本は、その文書に説明文を入れる (§8 のまま)。
  - **説明文がある本に限り、ZIP・RAR・フォルダの本も Ctrl+G の索引 (アイテム索引) に載せる** (2026-11-02 利用者の案、U17)。
    説明文の無い ZIP などは今どおり Ctrl+S (コンテナ索引) だけ。ZIP をアイテム索引から外したのは、名前だけの文書が Ctrl+S の名前検索と
    重なっていたためで (search-container-item-redesign §3.2 案 B1)、表紙の内容を持つ文書はこの重なりに当たらない。PDF・EPUB が
    すでに「Ctrl+S ではコンテナ、Ctrl+G では文書情報を持つアイテム」の両方に載っているのと同じ扱いになる。
    - **載せる条件は 1 つの判定にまとめ、索引に文書を作る・消す 3 つの経路すべてで使う** (独立レビュー 6 回目 P2-6)。条件は
      「その本のパスに `status = ok` の行が `ai_caption.db` にある」(`failed` の行は数えない)。今は、全件走査の候補作り (`search_walker`)、
      反映待ちの拾い直しからの再 ingest (§8)、ファイルの変更通知 (`indexer_supervisor` の watcher。今は ZIP とフォルダの候補を拒否し、
      候補を作れなければ文書を消す) が別々に候補を作るので、そのままだと次が起きる:
      説明文を消すと再 ingest が名前だけの文書を残す / 説明文の反映の後に ZIP の変更通知が来ると文書が消え、反映待ちの印も戻らない /
      失敗の行だけの本が索引に入る。3 つの経路は、**今回足す ZIP・RAR・7z・LZH・フォルダの本**についてだけ、この判定で「載せる (文書を作る)」か
      「載せない (文書と `fts_meta` の行を消す)」かを決める。判定は DB の今の状態を読むだけで、別の状態を持たない。
      **PDF・EPUB は今どおり説明文の有無によらず載せる** (今の走査・ingest の対象。独立レビュー 7 回目 P3)。説明文が消えたら、文書は残して説明文だけを外す。
    - 全件走査では、お気に入りの受け持ち範囲 (`OwnedRange`) の中の `status = ok` の本の行を 1 回の問い合わせで読み、その本だけを候補に入れる。
      「ZIP を候補に入れない」(案 B1) への例外はこの 1 か所。古い (署名が合わない) `ok` の行も検索に残す方針 (§7) はそのまま。
    - 説明文の変更は §8 の反映待ちの印で拾い、その本を再 ingest する。文書の中身は名前・説明文・画像内の文字・検索語。
    - 種類は本 (書庫は `IndexKind::Zip`、フォルダは `IndexKind::Folder`)。Ctrl+G の種別の絞り込みに「本」を足すか、既存の分け方に
      入れるかは V2 で決める。結果を開くと本が開く (PDF と同じ)。MCP の `search_items` も本 (Archive / Folder) として返す。
    - **索引に載せるだけでは、結果に本として出ない** (独立レビュー 6 回目 P2-7)。今の検索の結果 (`GlobalHit`) は種類を持たず、Flat 表示は
      ZIP を明示的に捨て (`global_search_ui.rs`)、結果の項目化では RAR やフォルダが画像として扱われる。MCP の分類も RAR・7z・LZH を
      Archive にしない (`agent_ipc/mod.rs`)。V2 で、結果に索引の種類を持たせ、Flat・Drill の項目化と MCP の分類を本に対応させる。
      種類は索引から渡し、フォルダかどうかを UI スレッドでファイルを調べて決めない (同期 I/O を足さない)。

## 7. 保存

- 新しいストア `ai_caption.db` (SQLite、未リリースなので移行は不要)。

```text
captions(
  item_key      TEXT PRIMARY KEY,   -- 正規化 path (tags.db の item_key、rating.db の path と同じ規則)
  mtime         INTEGER, size INTEGER,  -- 作成時の署名 (画像・書庫は本体のファイル、フォルダの本は表紙の画像。§6.7)
  model_id      TEXT,               -- 例: qwen3.5-4b-q4_k_m@<commit>
  prompt_version INTEGER,
  lang          TEXT,
  caption       TEXT,
  visible_text  TEXT,               -- 画像内の文字の書き写し (無ければ空)
  cover_ref     TEXT,               -- 本の表紙の場所 (書庫内のエントリ名・PDF のページ番号・フォルダ内の相対パス)。画像は空 (§6.7)
  keywords      TEXT,               -- JSON 配列
  status        TEXT,               -- ok / failed
  created_at    INTEGER,
  rev           INTEGER,            -- DB 全体で使い回さない番号。内容かキーが変わるたびに新しく振る (§8)
  indexed       INTEGER             -- 0 = 索引への反映待ち、1 = 反映済み (§8)
)
caption_seq(n INTEGER)              -- 1 行だけ。rev の発行元 (増える一方)
caption_removed(                    -- 消した行の、索引から消すための反映待ち (§8)
  item_key TEXT, rev INTEGER, PRIMARY KEY (item_key, rev)
)
-- 書き手が誰でも (ジョブの保存・取り込み・STORES の汎用の付け替え・コピー・復元・孤児整理)、
-- 次の trigger が反映待ちの印と新しい rev を付ける。書き手のコードに印の扱いを持たせない。
CREATE TRIGGER captions_ins AFTER INSERT ON captions BEGIN
  UPDATE caption_seq SET n = n + 1;
  UPDATE captions SET rev = (SELECT n FROM caption_seq), indexed = 0 WHERE item_key = NEW.item_key;
END;
CREATE TRIGGER captions_upd AFTER UPDATE OF item_key, mtime, size, model_id, prompt_version, caption,
    visible_text, cover_ref, keywords, status ON captions BEGIN
  UPDATE caption_seq SET n = n + 1;
  UPDATE captions SET rev = (SELECT n FROM caption_seq), indexed = 0 WHERE item_key = NEW.item_key;
  -- キーが変わったときは、旧キーの索引からも消す
  INSERT OR IGNORE INTO caption_removed SELECT OLD.item_key, n FROM caption_seq WHERE OLD.item_key <> NEW.item_key;
END;
CREATE TRIGGER captions_del AFTER DELETE ON captions BEGIN
  UPDATE caption_seq SET n = n + 1;
  INSERT OR IGNORE INTO caption_removed SELECT OLD.item_key, n FROM caption_seq;
END;
```

- `rev` を「行と一緒に動く番号 (`rev + 1`)」にしない (独立レビュー 3 回目 P2)。本の入れ替えは一時キーを経由してキーを 2 回付け替える
  (`rename_key_migration.rs` の book migration) ので、行ごとの番号だと、別の画像の行が同じ `(item_key, rev)` になり、
  古い反映済みの知らせが新しい行の印を消してしまう。DB 全体で増える一方の番号なら、同じ組は二度と現れない。
- trigger の対象の列に `rev` と `indexed` は含めない (管理役が印を消す UPDATE で trigger が動かないように)。

- 1 項目 1 行 (最後に作ったものだけを残す)。作り直しで成功したら上書きする。失敗で `ok` の行を上書きしない (§6.5)。
- 書き手は、ジョブの持ち主の保存役、メタ情報の取り込み、`STORES` の汎用操作 (改名・移動・本の構造操作の付け替え、
  コピー `copy_stores`、内容に基づくメタ情報の復元 `content_identity::restore`、孤児整理)。保存役と他の書き手の順序は §6.6。
  汎用のコピーはキー以外の全列をコピーする (`copy_exact`) が、コピー先は INSERT になるので、trigger で新しい `rev` と反映待ちに直る
  (独立レビュー 3 回目 P2)。
- 取り込みで説明文が「空」と記載された項目は行を消す (既存のメタ情報と同じ「記載された空は消す」)。消した行は
  `caption_removed` に反映待ちとして残るので、索引から古い説明文が消える (独立レビュー 3 回目 P2)。
- 画像が変わった (署名不一致) 説明文は消さずに「古い」と表示し、検索には使い続ける。本では表紙の場所 (`cover_ref`) の不一致も「古い」にする (§6.7)。作り直しは利用者の操作で行う。
- `rename_key_migration::STORES` に登録し、mIV 内の改名・移動・本の構造操作に追従させる。孤児整理の対象にもなる。
- mIV の外での移動には追従しない (タグなどの既存ストアと同じ)。
- 説明文は `metadata_transfer` (メタ情報のエクスポート / インポート) に含める (U6)。既存の他のメタ情報と同じく、
  記載された項目ごとに上書きする。取り込み先で画像の署名が一致しなければ「古い」と表示する (上の規則のまま)。
  取り込みはモデルの有無と関係なく行える (説明文の表示・検索にモデルは要らない)。

## 8. 検索への反映

- Tantivy に `ai_caption_text` (説明文 + 画像内の文字 + 検索語) を足し、検索対象の種類に「AI 説明」(`SourceKind::AiCaption`) を足す。
- ingest は、画像の文書を作るときに `ai_caption.db` を読んで入れる。全件の走査・作り直しもこの経路なので、DB の内容がそのまま入る。
- **DB を書いた後の索引の更新は、「反映待ち」の印を DB に持たせて管理役が拾う** (独立レビュー 1 回目 P2-3、2 回目 P2 で改めた)。
  - 理由: サイドカーはファイルの変更通知から再 ingest になるが、`ai_caption.db` を書いても画像のファイルは変わらないので通知は来ない。
    通常の走査も画像とサイドカーの署名が同じなら「変化なし」にする (`search_walker.rs` の差分判定)。起動時の走査を省く経路もある
    (`can_skip_initial_scan`)。管理役への命令の通り道は容量 4 で、あふれた分は捨てられる (`try_send`)。そのため、命令だけで
    知らせると、止まっている間・あふれたときの更新が、再起動や通常の走査でも戻らない。
  - 仕組み: 反映待ちの印は §7 の trigger が付ける (行の INSERT・内容やキーの UPDATE で `indexed = 0` と新しい `rev`、
    行の DELETE とキーの付け替えの旧キーで `caption_removed` に 1 行)。書き手のコードは印を扱わない。
    **反映待ちの一覧の持ち主は DB そのもの**で、メモリ上の待ち行列は作らない。
  - 管理役 (お気に入りごと) は、(1) 起動したとき (走査を省く場合も)、(2) 全件走査の後、(3) 「説明文が変わった」の知らせを受けたとき に、
    自分が受け持つ範囲の反映待ち (`captions` の `indexed = 0` と `caption_removed`) を `(item_key, rev)` で読み、その項目を再 ingest する。
    **受け持つ範囲は既存のメタ情報の所有範囲そのもの**: `effective_metadata` が有効な owner の `OwnedRange` (子のお気に入りと共通の除外を
    除いた範囲、`metadata_ownership.rs`)。metadata が無効の管理役 (類似検索だけのもの) は拾わない。範囲の外の項目は読まず、反映済みにもしない
    (親が子の範囲を拾って印を消すと、子の更新が失われるため。独立レビュー 4 回目 P2)。新しい所有の規則は作らない。
    再 ingest は ingest の時点の DB を読む。行が無ければ、画像・PDF・EPUB は説明文なしの文書になり (文書は残る)、§6.7 で足す
    ZIP・RAR・フォルダなどの本は文書と `fts_meta` の行が消える (§6.7 の共通の判定)。
  - 索引の commit の後、**読んだ `(item_key, rev)` と一致するものだけ**を反映済みにする (`captions` は `indexed = 1`、`caption_removed` は行を消す)。
    `rev` は使い回されないので、読んだ後にまた書かれた・付け替えられた行の印は残り、次に拾われる。
  - 知らせは**管理役ごとの旗** (`AtomicBool` と各管理役の既存の起床の仕組み) にし、容量のある通り道は使わない。何度知らせても 1 回の拾い直しになる。
    送り手は、動いている管理役すべての旗を立てる。配るのは管理役の一覧を持つ `metadata_reconfiguration` で、全件確認を全管理役へ配る既存の `dispatch_full_check` (`view.controls`) と同じ形にする。共有の旗 1 つにすると、ある管理役が
    自分の範囲を拾った時点で旗を消し、別の管理役が知らせを受け取れなくなる (独立レビュー 4 回目 P2)。
  - 送り手 (§7 の書き手すべて) は DB の commit の後に旗を立てるだけ。旗を立て忘れても、次の起動時・全件走査の後に拾われる。VLM 側で索引の文書 (`IndexDoc`) を
    作って直接入れることはしない (文書を作るのは管理役だけ)。
  - お気に入りの外の項目は索引に入らないので、`captions` の印は残ったままでよい (拾われないだけで害はない)。
    `caption_removed` のうち、どのお気に入りの root にも属さないもの (本の入れ替えの一時キーなど) は、起動時に捨てる
    (残すと拾われないまま溜まる)。
  - §7 の trigger の動きは、2026-11-02 に設計担当がメモリ上の SQLite で確かめた: 本の入れ替え (一時キーを経由した 2 回の付け替え) の後、
    入れ替え前に読んだ `(item_key, rev)` での反映済みの更新は 0 行に当たった。`indexed = 1` のままのコピーは、コピー先が新しい `rev` と
    反映待ちになった。削除は `caption_removed` に残った。
- **schema が変わるので `INDEX_VERSION` を 10 → 11 に上げる**。既存の作り直しの仕組み (共通 owner) で、
  v5 へ更新した後の初回起動時に Tantivy を全件作り直す。作り直し中は Ctrl+G の結果が欠ける
  (2026-11-02 利用者が受け入れ、U3。作り直し中の表示は既存の仕組みに従う)。
  v5 で索引を変えるほかの変更があれば、同じ版上げにまとめる。
- Ctrl+F は画像ごとに `ai_caption.db` を引いて比較対象に加える (その場でのファイル読み込みは不要)。
- **MCP の検索では、「AI 説明文」チェックが OFF のとき `AiCaption` を検索対象から外す** (独立レビュー 1 回目 P1-2、§10)。
  MCP の `search_items` は検索対象を既定 (`SearchTarget::All` = `SourceKind::ALL`) で組み立てているので、何もしないと
  `AiCaption` を足しただけで MCP の検索にも入り、列を隠しても説明文や画像内の文字 (氏名・メールアドレスなど) で
  画像の場所を探せてしまう。利用者自身の Ctrl+G / Ctrl+F は従来どおり全種類を対象にする。

## 9. 表示

- メタデータパネルに「AI 説明」欄 (説明文・画像内の文字・検索語・モデル名・作成日・古いかどうか)。DB は UI スレッドから読まない。
  本の説明文は、本を開いているときのパネルの「この本」の欄に出す (§6.7)。
  読み込みと保持は下の共有キャッシュで行い、既存の読み込み worker (`start_metadata_load` → `run_metadata_load`) には足さない。
- **保存の後に表示を新しくする** (独立レビュー 1 回目 P2-4、2 回目 P2 で改めた)。今の読み込みは、キーごとのキャッシュが全欄そろっていれば読み直さず、
  届いた結果をそのまま採用する。メタデータのキャッシュと読み込み中の印はウィンドウ (viewer context) ごとに持たれている
  (`viewer_context_registry.rs` の `metadata_cache` ほか)。そのため、ある窓で「説明文なし」を読んだ後に作成すると、その窓と休眠中の窓に古い表示が残る。
  - **説明文の表示用キャッシュは、既存の context ごとのメタデータキャッシュに入れず、App に 1 つの共有キャッシュとして持つ**
    (`CaptionDisplayCache`、キー → 読み込み済みの行と `rev`、または読み込み中)。どの窓のパネルもこれを読む。消すのも 1 か所で済み、
    休眠中の窓が古い値を持つことが無い。既存のメタデータ読み込み worker には足さず、説明文だけの小さな読み込み worker を使う。
  - ジョブの保存役が書いたら、そのキーの共有キャッシュを消す。
  - 取り込みと `STORES` の汎用操作 (付け替え・コピー・復元・孤児整理) が終わったら、**共有キャッシュを全部消す** (独立レビュー 3 回目 P2)。
    説明文の表示用キャッシュは小さく、消しても表示中の項目を読み直すだけなので、どのキーが変わったかを書き手ごとに数え上げない。
  - 読み込みは開始時の「キャッシュの世代」(キーごとに、消すたびに増やす番号) を持ち、届いたときに世代が違えば採用せず読み直す
    (保存より前に始まった読み込みが後から届く場合のため)。
  - context ごとの既存キャッシュには触れないので、detached viewer の経路と述語は変えない。
- detached viewer の経路と述語には触れない。パネルが共通部品で detached にも表示が出る場合は、
  detached-rework-plan §2 の手続きに従う。

## 10. MCP との関係

- `get_item_info` に `ai_caption` 列 (説明文・画像内の文字・検索語・モデル名・古いかどうか) を足す。本 (Archive / Pdf / Folder) でも返し、
  ページを指定した要求では本の説明文を `container_ai_caption` として返す (§6.7)。
- 「AI に見せる範囲」に、縮小画像・撮影位置と並ぶ 3 つ目のチェック **「AI 説明文」** を足す
  (mcp-integration-plan §5.6 の 3 欄表示と §15.2 の権限 snapshot に含め、変われば epoch を進める)。**既定は OFF** (U2)。
- MCP で説明文を使いたい場面は多いと見込むので (2026-11-02 利用者、U13)、チェックの説明に「ON にすると AI アプリが説明文と
  画像内の文字で検索でき、内容も受け取る」と書く。
- このチェックは列だけでなく**検索にも効かせる** (§8、独立レビュー 1 回目 P1-2)。`search_items` の検索対象を同じ snapshot から作り、
  OFF なら候補を集める段階と最終の照合の両方で `AiCaption` を外す。
- **ページ送りの続き (cursor) に、許可の版 (permission epoch) を入れる** (独立レビュー 2 回目 P2)。今の cursor が持つのは
  版・tool・引数の digest・返した件数だけで、既存の epoch 検査は 1 つの要求の受付から応答までの変化しか見ない
  (`src/agent_ipc/mod.rs` の `Cursor` と `Reply::wire`)。そのため、1 ページ目の後にチェックを変えると、検索対象が変わった結果に
  古い件数を当てて続きを返してしまう。cursor を作るときの許可の版を cursor に入れ、続きの要求で今の版と違えば
  `PermissionChanged` で拒む (AI アプリには最初から検索し直してもらう)。他の補助チェックの変更にも同じく効く。
  `agent_ipc` は MCP 担当の範囲なので、V3 で実装するときに MCP 担当と調整する。
- MCP から作成ジョブを始める tool は v5 では出さない (GPU を長時間使う処理を AI アプリ側から起こさない)。後段で検討する。
- Remote IPC は変えない (Remote での表示は後段)。

## 11. GPU / VRAM と他の AI 処理

### 11.1 VRAM の見積もり (2026-11-02、**すべて推定・未計測**)

> 2026-11-02 に V0 で実測した。VLM は §18.1、AI 補正は §18.4、併用の見込みは §18.5。以下は計測前の推定として残す。

AI 補正の VRAM 使用量は実測の記録が無い。ONNX Runtime の確保分は mIV の VRAM 会計
(`src/app/vram_accounting.rs`) に入らない設計のため、perf ログからも読めない (web-remote-ai-plan §10)。
以下はコードの設定値とモデルのサイズからの推定。

| 使い手 | 根拠 (コード・文書) | 推定 |
| --- | --- | --- |
| mIV の表示用テクスチャ | 共有 pool = 検出 VRAM × `gpu_memory_percent` (既定 **50%**、`default_gpu_memory_percent`)。上限であり常に使い切るわけではない | 8GB 機で最大 4GB、24GB 機で最大 12GB |
| AI 補正 (1 モデル) | 重み 5〜72MB (`vendor/models/*.onnx` の 4.9MB〜71.6MB)。タイル 192px (DirectML) / 256px (TensorRT) / 512px (軽量モデル) (`src/ai/upscale.rs` `model_tile_size`)。TensorRT の検討では複数モデルの warmup 込みで計 1GiB を想定 (archive/ai/tensorrt-batching-feasibility.md) | 数百 MB〜1GB 台 |
| VLM 軽量 (4B 級) | 重み (4B は未確認、2.5〜3GB 程度と推定) + 画像エンコーダ + 文脈 + 計算用 buffer | 約 4GB |
| VLM 標準 (9B 級) | 重み 5.9GB (§3.1) + 同上 | 約 7〜8GB |
| VLM 高品質 (27B 級) | 重み 17.0GB (§3.1) + 同上 | 約 19〜20GB |

- **VLM は AI 補正の 5〜20 倍程度**を見込む。両者は同じくらいではない。
- テクスチャの pool を上限まで使った最悪の場合の合計:
  - 8GB 機: 4 + 1 + 4 (軽量) = 約 9GB で、すでに超える。
  - 12GB 機: 6 + 1 + 4 (軽量) = 約 11GB。9B 級は載らない。
  - 16GB 機: 8 + 1 + 7.5 (9B) = 約 16.5GB で境目。
  - 24GB 機: 12 + 1 + 7.5 (9B) = 約 20.5GB で収まる。27B 級は載らない。
- VRAM を超えたとき、Windows (WDDM) は一般に確保の一部を共有システムメモリへ退避させるため、
  即座の失敗より「全体が遅くなる・カクつく」形で現れると考えられる (一般的な OS の挙動。mIV では、
  VRAM 6GB の利用者環境の不具合で同じ見立てを立てたが、因果は未確認のまま: video-strip-resolved-report-20260912.md)。
  ONNX Runtime / llama.cpp 側の確保が失敗する場合もあり得る (未確認)。

### 11.2 選択肢 (U1、判断は V0 の計測後)

- (a) 作成ジョブの実行中は、AI 補正 (アップスケール・デノイズ) と Remote の AI を使わない。
  確実だが、「ジョブ中かどうか」で AI 補正の経路が分かれ、表示・キャッシュ・Remote の各所に分岐が入る。
- (b) 前面の AI 要求が来たら worker を止めてモデルを降ろし、後で再開する。中断・再開・中止の競合で状態が最も多い。
- (c) 制限なしに同時に動かし、VRAM 不足は割り切る。8GB 機では実用にならない恐れ。
- **(d) 同時に動かす前提で、機種に合わせてモデルの段を選ばせる (環境を選ぶ設計)。** 2026-11-02 に利用者が挙げた案。
  各段に「必要な VRAM」を決め、検出した VRAM で選べる段を限る (または推奨と警告を出す)。
  AI 補正の経路には手を入れず、ジョブ中の分岐も作らない。状態は増えない。
  代わりに、8GB 機は軽量の段だけ (または対象外)、24GB 機でも 27B 級は選べない、という制約が付く。
- 設計担当の現時点の見立て: 状態を増やさない (d) が有力。AI 補正の推定が 1GB 程度なら、止めても空くのは
  VLM の 1/5〜1/20 で、排他の仕組みに見合う効果は小さい (2026-11-02 利用者も同じ見立て)。
  ただし推定は未計測なので、V0 で実測してから決める (§14)。27B 級は候補から外した (§3.2)。
  4B 級に固定した場合 (§3.3)、(d) は「VRAM が足りない機種では使えない」の 1 判定だけになる。
  → 2026-11-02 に 4B 固定が決まったので、(d) は段の選択ではなくこの 1 判定になる。境目は §18.5 (8GB 機は AI 補正「軽量」となら収まる見込み)。
  8GB 機をどう扱うかは U1 として残る。
  → **決定 (2026-11-02 利用者、U1)**: (d) を採る。AI 補正・Remote の AI と同時に動かし、止める仕組みは作らない。
  VRAM 総量 (アダプタの専用メモリ) が 8GB 以上なら使え、未満なら「VRAM が足りません」と表示して機能を使えなくする。
  8GB 製品が報告する値はわずかに 8GiB を下回ることがあるため、境目の値は実装時に実機の報告値で決める (例: 7.5GiB)。
  8GB 機で AI 補正「高品質」と併用した場合の遅さは割り切り、マニュアルで AI 補正を「軽量」にするよう案内する。
- いずれの案でも、判断は設定と検出した VRAM の総量だけで決め、空き VRAM による適応はしない。

## 12. 状態を減らす検討の記録

- R1: ジョブは同時 1 本。追加分は後ろに足す。複数ジョブの並行・優先度は作らない。
- R2: worker は常駐させない。「読み込み済みで待機中」の状態を作らず、ジョブと寿命をそろえる。
- R3: 任意の GGUF を使わせない。モデルの組み合わせ・プロンプトの形式差・ライセンス表示の分岐をなくす。
- R4: 1 項目 1 行。履歴やモデル別の複数保存をしない。
- R5: 自動作成 (何もしていない間) は v5 で作らない。前面の操作との取り合いを最初から作らない。
- R6: AI 補正との関係は、割り込み・再開の状態を持たない案 ((a) か (d)) から選ぶ。(b) は採らない (§11.2)。
- R7: 改名・削除と保存の順序は、保存の直前にファイルの署名を確かめて違えば捨てることで扱う (§6.6、U14)。受付の開け閉め・
  名前の付け直し・メタ情報の取り込みの停止を作らない。重なった項目は作り直しを利用者に任せる。
- R8: AI 補正のモデルを降ろす仕組みは足さない。8GB 機の案内は「軽量にして再起動」で済ませる (§6.1)。
- R9: 索引への反映待ちはメモリの
  待ち行列ではなく DB の印 1 つにする (§8)。説明文の表示用キャッシュは窓ごとではなく App に 1 つにする (§9)。
  いずれも、状態の持ち主を 1 つにして、止まっている間・窓が休眠している間の取りこぼしを無くすため。
- 不採用にした単純化: 「作成中はモーダル」。ジョブは数時間かかり得るので、その間 mIV を使えなくするのは不便すぎる。

## 13. 安全性・プライバシー・公開文書

- 推論は PC 内で完結する。新しく生じる通信は**モデルのダウンロード (利用者の操作時、GitHub Releases)** だけ。
- 説明文はローカルの `ai_caption.db` と索引に保存する。MCP のチェックが ON のときだけ AI アプリへ渡る。
- 説明文は画像の内容を表す文字列で、ファイルの場所と合わせると敏感な情報になり得る。
  §5.6 の「AI に見せるもの」に明記する。
- 画像内の文字の欄は、画像に写っている氏名・メールアドレス・SNS のアカウント名などもそのまま書き写す
  (V0 で、同人誌の奥付ページからメールアドレスとアカウント名を書き写した例がある)。内容に関与しない方針 (§1) のとおり選別はしないので、
  MCP の「AI 説明文」チェックの説明と公開文書で「写っている文字も含む」ことを明記する。
- ダウンロードしたモデルは sha256 で固定し、一覧に無いファイルは読み込まない (GGUF の解析不具合への備え)。
- 更新する公開文書: `privacy.html` (日英) の「ネットワーク通信」と「端末内に保存されるデータ」、
  製品ページの「安心して使えます」、マニュアル (AI 連携のページと検索のページ、AI 説明の新しい節)、ライセンス表示。
  「mIV は外部と通信しない」系の記述が偽にならないかを確かめる。
- 設計文書: search-architecture (§3・§4)、async-architecture (worker 一覧)、ui-responsiveness、architecture-overview、mcp-integration-plan。

### 21.3 V1-1 の設計

**通信は長さ付きの枠をパイプに流すだけにし、共有メモリは使わない。** 1 件の入力は長辺 1024px の RGB で最大約 3MB、出力は数 KB なので、
PDFium worker と同じくパイプにそのまま流して足りる。共有メモリの名前・寿命・読み書きの順序の約束を持たずに済む (状態を減らす)。

- **worker の起動**: EPUB worker と同じく `CreateProcessW` (suspended・`CREATE_NO_WINDOW`) → Job Object (kill-on-close) に入れる → resume。
  stdin・stdout は匿名パイプ (親側は継承させない)、stderr はログへ流す。EPUB と同じ処理を 2 か所に書かず、Job Object 付きの起動を
  1 つの helper にまとめて両方が使う (EPUB の挙動は変えない)。親が落ちれば Job Object で worker も終わる。
  - **子に渡すハンドルを、その子の標準入出力の端だけに限る** (独立レビュー 10 回目 P2-1)。今の EPUB は継承可能なパイプを作り、
    `CreateProcessW` に `bInheritHandles = true` を渡している (`epub_convert.rs`)。この形のままだと、EPUB 変換と VLM の worker が同時に起動したとき、
    互いの子側の端も継承し、片方の worker を止めても別の子が書き込み側を握っていて EOF が届かない。helper は
    `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (`STARTUPINFOEX`) でその子の端だけを渡し、起動後は親に残った子側の端を閉じる。EPUB にも同じ helper を使う。
- **枠** (独立レビュー 10 回目 P2-2 で中身の形を決めた): 外側は u32 little-endian の全体の長さ + 中身 (`pdf_loader` の `write_msg` / `read_msg` と同じ。
  共通にできるなら同じ関数を使う)。中身は「u32 の JSON の長さ + UTF-8 の JSON + 残りのバイト列」。`caption` の残りのバイト列は、行を詰めた RGB8
  (幅 × 高さ × 3 バイト、行の間に余白なし) で、長さが幅 × 高さ × 3 と一致しなければ不正。16MiB の上限は外側の全体の長さに当てる。
  不正な枠 (長さの上限超え・JSON の不正・RGB の長さの不一致・知らない種類) は、受け取った側がその worker を終わらせる扱いにする (やりとりを続けない)。
- **worker の標準入出力はバイトで扱う**: `--serve` では stdin・stdout を CRT の文字モードで扱わず、Win32 の `ReadFile` / `WriteFile` で読み書きする
  (または `_setmode(_O_BINARY)`)。文字モードでは改行が変換され、RGB や長さが壊れる。stdout はやりとり専用にし、ログは stderr だけに出す
  (llama.cpp・ggml のログの出力先も stderr に向ける)。
- **やりとり** (どれも 1 往復、同時に 1 つだけ):
  - `hello` → 版 (`protocol_version`) と worker の source identity を返す。版が違えば使わない (VST3 と同じ)。
  - `load` (モデル・mmproj のパス、device の LUID、CPU スレッド数) → 読み込みにかかった時間と使った device。
  - `caption` (要求の番号、幅・高さ、RGB) → 要求の番号、結果 (`ok` / `image_failure` / `fatal`)、3 欄、検証 (§6.5)、生成トークン数、時間。
    `image_failure` は 1 件の失敗 (次へ進む)、`fatal` は続けても意味がない失敗 (VRAM 不足など。ジョブを止める)。V1-0 の分け方をそのまま使う。
  - `shutdown` → 終わる。返事を待たずに Job Object で終わらせてもよい (TRT と同じく、片付けを待たない)。
- **worker 側 (C++)**: `--serve` を足す。1 件の処理は V1-0 の確認用モードと同じ関数を使う (処理を 2 つに分けない)。画像は本体から RGB で受け取り、
  worker はデコードしない (§4)。確認用モード (`--selftest`) は PNG を読んでこの関数に渡す形に揃え、残す (回帰の確認に使う)。
- **Rust 側の client** (`VlmWorkerClient`): 起動・`hello`・`load`・`caption`・終了を持つ。呼ぶのはジョブの worker スレッドだけで、UI スレッドからは
  呼ばない。時間の上限: `hello` 30 秒、`load` 120 秒、最初の `caption` 120 秒 (Vulkan の初回準備、§20)、2 件目以降 60 秒。上限を超えた・パイプが
  切れた・`fatal` が来たら、worker を終わらせて client は使えなくなる (再起動や再試行はしない。まれな失敗は割り切り)。
- **待ちを解く仕組みと止め方** (独立レビュー 10 回目 P2-3)。パイプの読み書きは同期 I/O で期限を持たないので、次のようにする。
  - パイプの読み書きは、client が持つ**書き手のスレッドと読み手のスレッド**だけが行う (TRT worker の reader と同じ形)。ジョブのスレッドは
    要求を書き手へ渡し、応答を読み手からの channel で `recv_timeout` で待つ。ジョブのスレッドがパイプで止まることは無い。
  - worker を終わらせる手段は **kill handle** (Job Object の handle を共有したもの) 1 つ。client と App の持ち主の両方が持ち、どちらからでも
    `TerminateJobObject` できる。期限切れ・不正な枠・`fatal` のときは client が、mIV の終了のときは App が呼ぶ。worker が終わればパイプが切れ、
    書き手・読み手のスレッドは誤りで抜け、ジョブのスレッドは channel の切断で抜ける。**止めるのが先、スレッドの回収はその後**で、
    UI スレッドは回収を待たない (回収は既存の reaper と同じく別スレッドで行うか、切り離す)。
  - **通常の中止** (利用者がジョブを止める) は、今の 1 件の推論が終わるのを待ってから `shutdown` を送り、kill handle で終わらせる (§6.5)。
    **mIV の終了** は待たずにすぐ kill handle で終わらせる。この 2 つを分ける。
- **GPU の判定**: worker の `--list-devices` (V1-0 で作った、DXGI の LUID と Vulkan の device の対応と VRAM 総量) を、モデルを読まずに起動して使う。
  結果は「使う device (専用メモリが最大のアダプタ) と、その VRAM 総量、Vulkan の有無」の 1 つ。判定は mIV の起動ごとに 1 回、必要になったときに
  worker スレッドで行い、その起動の間は結果を使い回す (実行時の空きでは変えない)。`gpu_info` (DXGI の最初のアダプタ) は使わない。
- **worker の場所**: 1 つの関数で解決する。V1-1 では、環境変数 `MIV_VLM_WORKER` → `vendor/vlm-worker/mimageviewer-vlm.exe` (開発用) の順。
  本体への内包・展開 (VST3 と同じ content-addressed)・portable での置き方・source identity の照合・署名は V1-3 でこの関数に足す。
- **確認**: Rust の統合テスト (既定では走らない。モデルのパスを環境変数で渡したときだけ) で、`--serve` 経由の 26 枚の出力が V1-0 の確認用モードの出力と
  26/26 一致することを確かめる。通信の枠・時間の上限・`image_failure` と `fatal` の分け方・パイプが切れたときは、偽の worker (テスト用の小さな exe か
  Rust のテスト用 binary) で確かめる。
- **まれな失敗**は割り切り (ログ + 通知。ジョブを止め、利用者がやり直す)。

**既存の作り (2026-11-02、コードで確認)**

- path をキーにするストアは `*_db.rs` が `open` (無ければ作成・schema の確認) / `open_at` / `open_existing_for_write` / `db_path()`
  (`data_dir::get().join(...)`) を持つ (`rating_db.rs`)。改名・移動・本の構造操作・孤児整理・削除の hard purge・内容同一性の復元は
  `rename_key_migration::STORES` の記述子を走査し、DB ごとに自分で接続を開く。ファイルが無い DB は飛ばす。
- メタ情報の取り込みは、関係する DB を全部 1 つの接続に `ATTACH` し、**1 つのトランザクションで全 DB を更新する**
  (`metadata_transfer.rs` の import)。複数 DB をまたいで原子的にするため、参加する DB はすべて rollback journal (WAL 不可) で、
  取り込みの前に各 DB を `open_at` で開いて schema を作っておく。書き出し (`export`) は各 DB を読み取りで開き、走査範囲の表と join して読む。
- 形式の版は `FORMAT_VERSION = 11` で、v4.11.0 で出荷済み。欄ごとの有無は `ManifestSections` の bool。新しい欄は版を上げ、
  古い版の取り込みではその欄を無効にする (`composition` の前例: `version < FORMAT_VERSION` なら `sections.composition = false`)。
  欄の選択 UI は無い (書き出しは常に全欄)。
- `copies_with_book_page` は、本の構造操作でページを別の本へ写すときに行も写すかで、今は編集・★・タグの 8 種だけが `true`。

**作るもの**

1. **`src/ai_caption_db.rs`** (`CaptionDb`、他の `*_db.rs` と同じ形)。
   - schema は §7 のまま (表 `captions`・`caption_seq`・`caption_removed` と trigger 3 つ)。列の名前は `mtime_ms` / `size` にし、
     更新日時はミリ秒 (`metadata_transfer` の `FileFingerprint` と同じ単位・同じ求め方)。`PRAGMA user_version = 1`。未リリースなので移行は無い。
   - **journal は rollback (既定の DELETE) のまま**にし、WAL にしない (取り込みの原子的な更新に参加するため)。busy timeout は保存で 5 秒。
   - 読み取り: `get(item_key)` (飛ばす判定 §6.2 と表示用)。キーは `StoreKeyNormalization::KeepDrive` (タグ・★と同じ) で、正規化は呼び出し側でなく
     記述子の `normalize_path` を使う。
2. **保存役** `CaptionDb::save(&SaveRequest) -> Result<SaveOutcome>` (ジョブの worker スレッドから呼ぶ。UI スレッドからは呼ばない)。
   - `SaveRequest`: 項目のパス、**署名を取り直すパス** (画像はその画像、ファイル 1 つの本は本のファイル、フォルダの本は実際に読んだファイル、
     EPUB は元の EPUB。§6.7)、読んだときの署名 (size + mtime_ms)、`cover_ref`、model_id、prompt_version、lang、結果 (`Ok{caption, text, keywords}` /
     `Failed`)。どの値を入れるかは V1-3 (画像) と V1-4 (本) が決める。保存役は「渡されたパスを取り直して比べる」だけで、本の種類を知らない。
   - 手順 (§6.6): `BEGIN IMMEDIATE` → 署名を取るパスの `metadata` を取り直す → 無い・読めない・size か mtime_ms が違う (更新日時が取れない場合も含む)
     → `ROLLBACK` して `Discarded` → 同じなら書く → `COMMIT`。ファイルの読み取りは `metadata` 1 回だけ (lock を持つ時間を短くする)。
   - 書き方: `Ok` は無条件に upsert。`Failed` は、行が無いか `failed` の行のときだけ upsert し、`ok` の行があれば何もしない (`KeptExistingOk`。§6.5)。
     upsert は `INSERT ... ON CONFLICT(item_key) DO UPDATE` にする (`INSERT OR REPLACE` は削除 + 挿入で、削除の trigger が既定では動かず
     `caption_removed` が狂うため使わない)。
   - 戻り値 `SaveOutcome`: `Written` / `KeptExistingOk` / `Discarded`。`Written` のときだけ、呼び出し側 (V1-3) が表示の無効化 (V1-4) と索引の旗 (V2) を立てる。
   - lock が取れない (5 秒の busy) などの DB の失敗は、まれな失敗として割り切る (エラーを返し、V1-3 がジョブを止めて通知する)。
3. **`STORES` への登録**: `store("ai_caption.db", "captions", "item_key", unique = true, KeepDrive, BookStorePolicy::Follow, copies_with_book_page = false)`。
   - `Follow` にするのは、本の構造操作 (改名・ページの並べ替え) で、タグ・★と同じく本の worker が運ぶため (U15 の割り切りはこの動きが前提)。
   - `copies_with_book_page = false`: ページを別の本へ写すとファイルは新しくなり (更新日時が変わる)、写した説明文はすぐ「古い」になるだけなので写さない。
     写さないストアもコピー先は初期化される (既存の規則) ので、コピー先に前の説明文が残ることは無い。
   - **本へのページ追加にも説明文の初期化をつなぐ** (独立レビュー 12 回目 P2-2)。ページ追加は汎用の構造操作ではなく専用の
     `AppendMetadataWriter` (`book_append_undo.rs`、対象は既存の 8 種) で追加先のキーを初期化する。末尾のページを mIV の外で消してから
     別の画像を追加すると、番号と名前が再利用され、前の画像の説明文がその名前に残る。`AppendMetadataStores` に説明文を足し、
     `prepare_destination` (ファイルを作る前) で追加先のキーの行を消すだけにする (写さない。`copies_with_book_page = false` と同じ扱い)。
   - **内容同一性の復元の限界** (独立レビュー 12 回目 P2-3): `STORES` に載せると復元の写し先には入るが、復元元の台帳 (`content_identity.rs` の
     記録) は編集・タグ・★のある項目でしか作られない。説明文だけを持つ画像を mIV の外で改名した場合は、台帳が無いので説明文は運ばれない。
     説明文は作り直せる機械の出力なので、説明文のために台帳の記録 (ファイル内容のハッシュ) を足すことはしない。既に台帳にある項目
     (編集・タグ・★もある画像) の説明文が一緒に運ばれるだけ、とする。
   - `caption_removed` と `caption_seq` は登録しない (キーで運ぶと、旧キーを索引から消す印が新しいキーへ移ってしまう)。
   - これで改名・移動・本の構造操作・孤児整理・削除の hard purge・内容同一性の復元 (`copy_stores_at`) が説明文にも効く。どの経路でも §7 の trigger が
     `rev`・`indexed`・`caption_removed` を付けるので、書き手のコードに印の扱いを足さない。STORES の件数を数えているテストは足した分だけ直す。
4. **`metadata_transfer`** (U6):
   - `FORMAT_VERSION` を 12 に上げ、`ManifestSections` に `ai_captions` (serde の既定は false) を足す。12 より古い版の取り込みでは
     `ai_captions = false` にする。v4 の mIV は v12 の書き出しを読めない (版を上げるたびの既存の扱いと同じ)。
   - **版の境界を欄ごとの固定の定数に分ける** (独立レビュー 12 回目 P2-1)。今は受け入れる版の一覧が 11 を `FORMAT_VERSION` で表し、
     構成情報を無効にする条件も `version < FORMAT_VERSION` なので (`metadata_transfer.rs` の `validate_bundle_manifest` と manifest の読み込み)、
     定数を 12 にするだけでは v11 を拒み、受け入れても v11 の本の構成情報を捨ててしまう。構成情報の導入版 (`COMPOSITION_FORMAT_VERSION = 11`) と
     説明文の導入版 (`AI_CAPTION_FORMAT_VERSION = 12`) を別の定数にし、受け入れる版の一覧に 11 を明示する。
   - `PortableEntry` に `ai_caption: Option<PortableAiCaption>` (無ければ書かない)。中身は model_id・prompt_version・lang・caption・visible_text・
     keywords・cover_ref・作成時の署名 (size + mtime_ms)・created_at。**書き出すのは `status = ok` の行だけ** (`failed` は「作れなかった」印で、
     他の PC へ運ぶ意味が無い)。`ZIP` 内のページなど仮想の項目 (`virtual_items`) には足さない (v5 は対象外、§1)。
   - 取り込み (欄が有効なとき): 記載された項目に説明文があれば upsert (`status = ok`、署名は書き出し元の値のまま。取り込み先のファイルと合わなければ「古い」になる §7)。
     記載された項目に説明文が無ければ、その項目の行を消す (既存の欄と同じ「記載された空は消す」)。記載の無い項目には触れない。
     upsert は保存役と同じく `ON CONFLICT DO UPDATE`。取り込みは署名の確認をしない (後勝ち、§6.6)。
   - 取り込み前の schema の用意 (`open_at`) と `ATTACH`・journal の確認の一覧に `ai_caption.db` を足す。
   - `ImportChangedSections` に `ai_captions` を足し、変えた件数を数える (V1-4 で表示の共有キャッシュを消し、V2 で索引の旗を立てるきっかけ)。
     書き出し・取り込みの件数の表示は、既存の欄と同じ並びに足す。値の検証 (文字数・個数の上限 §6.4、keywords が文字列の配列) は既存の欄の検証と同じ場所で行う。
5. **テスト**
   - schema と trigger: INSERT / 内容の UPDATE / キーの UPDATE / DELETE で `rev` が全体で増え、`indexed = 0`、旧キーと削除が `caption_removed` に入る。
     `rev`・`indexed` だけの UPDATE では trigger が動かない。本の入れ替え (一時キーを経由した 2 回の付け替え) の後に古い `(item_key, rev)` で
     反映済みにしても 0 行 (§8 で確かめた筋書きを実装で確かめ直す)。
   - 保存役: 署名一致で書く / ファイルが無い・size 違い・mtime 違いで捨てる / `Failed` が `ok` を上書きしない・`failed` は上書きする / `Ok` は両方を上書きする /
     別の接続が書き込みの lock を持っている間は待ち、その commit の後に確認する (改名の付け替えが先に済んだら「無い」で捨てる筋書き)。
   - `STORES`: 改名・移動・孤児整理・hard purge・内容同一性の復元・本の構造操作で行が運ばれる・消える。
   - 本へのページ追加: 説明文の付いた末尾のページを mIV の外で消し、別の画像を追加して同じ番号になったとき、追加先に説明文が残らない。
   - `metadata_transfer`: v12 の往復 / `failed` を書き出さない / 説明文の無い記載で消す / v11 の取り込みで説明文に触れず、v11 の本の構成情報は
     今までどおり取り込まれる / 不正な値を拒む /
     取り込み後の `ImportChangedSections.ai_captions`。
   - 既存の metadata_transfer・rename_key_migration・content_identity・delete_worker・metadata_cleanup のテストが通ること。

#### 21.7.1 V1-3a: モデルの用意と配り方 (U20)

  `quantize.imatrix.*`)。mIV では、調整用の文章を **mIV 自身の日本語マニュアル** (`htdocs/mimageviewer/manual/*.html` の本文、
  `scripts/vlm-eval/make_calibration.py`) から作る (第三者の文章のライセンスを持ち込まない)。`llama-imatrix` を 512 トークン × 128 区切りで回した。
- **結果 (2026-11-03、V0 と同じ 26 枚)**:

#### 21.7.2 V1-3b: worker の内包・モデルの導入・GPU の判定・案内

- **worker の内包** (U19・U21):
  - build: `crates/vlm-worker` を CMake で build し、成果物は今と同じ `vendor/vlm-worker/mimageviewer-vlm.exe`。`build.rs` の vendor 検査に足す

  - インストール版・単体exe版: core に `include_bytes!` で埋め込み、`<data_dir>/vlm/workers/<内容の SHA256>/mimageviewer-vlm.exe` に展開する。

  - 署名: `build-release.ps1 -Sign` で、埋め込む前に署名する (VST3 と同じ順序)。**ポータブル版は別の入口** (`build-portable.ps1`) で、自分で build・
    コピーし、包む先の PE の一覧 (`$portablePe`) を署名する (独立レビュー 14 回目 P2-4)。この一覧にも worker を足す。順序は
    source identity の検査 → 署名 → 署名の検証 → zip 化。
  - `worker_executable()` は「環境変数 `MIV_VLM_WORKER` (debug build だけ) → ポータブル版なら exe の隣 → 埋め込みの展開」にする。
  - 実行時の確認は `hello` の protocol の版 (V1-1) と、`hello` に足す `prompt_version` (プロンプトは worker が持つため。protocol の版を 2 に上げる)。
    source identity は build 時の検査に任せ、実行時には比べない (VST3 と同じ)。
  - 古い版の展開先は消さない (VST3 と同じ。1 つ約 46MB)。
  - **同梱する exe の source identity を、起動せずに確かめる関門を作る** (独立レビュー 14 回目 P2-3)。`tools/source-identity.ps1` はソースの hash を
    計算するだけで、vendor の exe とは比べない。VST3 の `scripts/vst3-host-identity.ps1` と同じく、exe の中に焼き込まれた `MIV_VLM_SOURCE_SHA256` の印が
    1 つだけあり、今のソースの hash と一致することを検査するスクリプトを足す。つなぐ場所は `build.rs` の release の関門、`build-release.ps1` (内包の前)、
    `build-portable.ps1` (置く前)。`-SkipBuild` で build を飛ばす経路でも検査は飛ばさない。ソースを直して exe を作り直し忘れると、ここで止まる。

  - 置き場所は §5 のとおり `<data_dir>/addons/vlm/`。`packs/<model_id>/` にファイル、`INSTALL_OK`、`active.json` (編集用追加パックと同じ形)。

    VLM の導入だけが使う (既存の 2 系統は今回は移さない)。編集用追加パックの検証の境目をそのまま引き継ぐ (独立レビュー 14 回目 P3-5):
    取得先は固定 (release の build では環境変数による上書きを無視する)、`model_id` と各ファイル・部分の名前は安全な名前か検査する

  - **取得・中止・削除は 1 つの持ち主の「実行中の処理」として持つ** (独立レビュー 14 回目 P2-1)。編集用追加パックは、削除で `active.json` を消した後に

#### 21.7.3 V1-3c: 作成ジョブ

- **持ち主**: App に `caption_job: Option<CaptionJob>` を 1 つ (§6.6)。同時に 1 本。
- **待ち行列とジョブの終わりは App が 1 か所で決める** (独立レビュー 14 回目 P2-2)。worker が「待ち行列が空」を見て自分で終わると、App が同じ時に
  対象を足した場合に、受け付けた対象が消える。そこで:
  - 待ち行列 (パスの一覧) は App が持つ。worker スレッドには 1 件ずつ渡す (channel で `Item(path)` か `Finish`)。worker は 1 件を終えるたびに
    結果を返して次を待つ (VLM worker は読み込んだまま待つ。返すときに `request_repaint` する)。
  - App は結果を受け取ったフレームで、待ち行列が空でなければ次の 1 件を、空なら `Finish` を送る。対象の追加も同じ App の上で行うので、
    「追加」と「終わりの判断」が同じ持ち主の上で順に起きる。
  - 実行中に足された対象は待ち行列の後ろへ (同じパスが待ち行列にあれば足さない、§6.6)。
  - **受付を閉じる時点と `Finish` を送る時点を分ける** (独立レビュー 15 回目・16 回目 P2)。ジョブの状態は `Running` と `Stopping` の 2 つ。
    - `Stopping` に入る (= 受付を閉じる) のは、(a) 待ち行列が空で最後の結果を受け取ったとき (正常の終わり) と、(b) **中止を押したとき** (押した時点で。
      推論中の 1 件の結果を待たない。動画アップスケールのキューも中止を押した時点で中止中にする)。
    - `Finish` を送るのは、`Stopping` で、推論中の 1 件が無いとき (a ではその場で、b では今の 1 件の結果を受け取ったとき。その結果は保存しない、§6.5)。
    - `Stopping` の間の「AI 説明文を作る」は対象を足さず、「前のジョブを終えています。終わってから選び直してください」と知らせる (取得中の扱いと同じ。
      次のジョブのための待ち行列は持たない)。worker スレッドの完了の知らせで `caption_job` を `None` にし、その後の要求は新しいジョブになる。
  - 回帰テスト: 1 件の結果が返る前後の追加・最後の結果を受け取って `Finish` を送った後、完了の知らせの前の要求・中止を押してから今の 1 件の結果が返るまでの要求。
  - ほかに持つもの: `Arc` の進捗、cancel の `AtomicBool`、worker の kill handle (mIV の終了で使う)、結果の `mpsc`。
- **対象の集め方** (§6.1):
  - 右クリックの対象は、一覧の既存の選択の規則をそのまま使う (`selection_target_indices(ActionSurface::MainWindow)`。チェックが今の選択を含むときは
    チェックの全件、含まないときは選択の 1 件。独自の規則を足さない。独立レビュー 14 回目 P3-6)。何も選んでいない・空白部分の右クリックなら、
    今のフォルダの直下 (画像と本。サブフォルダは含めない)。
  - 実際のパスを持つ画像 (`GridItem::Image`) だけを対象にする。ZIP 内の画像・PDF のページ・動画・音声は対象外 (§1)。本は V1-4 まで「対象外」として数える。
  - 一覧の項目は UI スレッドでパスに直して渡す (ファイルは読まない)。以後はパスだけを使う。
- **メニュー**: `MenuCommand::CreateAiCaptions`「AI 説明文を作る」を足し、`ContextMenuItemId` (表示・順序の設定) にも登録する。既定のショートカットは割り当てず、
  `KeyAction` は足さない (メニューだけの操作。keymap-spec の「メニュー専用」の扱い)。
- **1 件の流れ** (§6.2): worker スレッドで
  1. ファイルの `metadata` から署名を取る。無ければ「無い」で次へ (保存しない)。
  2. 保存済みの行が `ok`・署名一致・同じ `model_id`・同じ `prompt_version` なら飛ばす。
  3. `decode_canonical_image` (先頭のフレームだけ、RAW は現像) で読み、mIV の非破壊回転を当て (`rotation.db` を worker で読む)、長辺 1024px に縮小 (拡大しない、Lanczos3)、RGB8 にする。
     見えている向きと AI が読む向きを合わせるため、回転も当てる。回転を変えても説明文は「古い」にしない (署名はファイルのもの)。
  4. `VlmWorkerClient::caption` → `ImageFailure` なら `Failed` を保存、`Ok` なら保存 (`CaptionDb::save`、V1-2)。`Discarded` は数えるだけ。
     保存の前に、**検索語の全く同じ語の重複を除く** (前後の空白を除いて同じ文字列なら、最初の 1 つを残し、順番は変えない。2026-11-03 利用者の指摘)。
     モデルの出力を受け取るのはこのジョブだけなので、除くのはここ 1 か所。片方がもう片方を含む語 (「海」と「海辺」) は別の語として残す
     (どちらを残すかの判断は内容への関与になる、§1)。全角・半角の違いをそろえる正規化はしない (26 枚では差が無かった)。
  5. `fatal`・worker の切断・時間切れ・DB の失敗はジョブを止めて通知する (まれな失敗は割り切り)。
- **worker の寿命**: ジョブの開始で起動 (§4)、`start_at` → kill handle を App に渡す → `hello` → `load` → 1 件ずつ。待ち行列が空になったら `shutdown`。
- **中止**: 窓の [中止] で cancel を立て、今の 1 件の推論が終わったら止める (結果は保存しない、§6.5)。mIV の終了では kill handle で即座に止め、join しない。
- **進捗の小窓**: modeless、メイン窓だけに描く (動画アップスケールのキューと同じ)。件数 (済み / 全体)・今の項目の名前・飛ばした数 (作成済み・対象外・ファイルが無い)・
  失敗の数・[中止]。終わったら結果を 1 行で知らせる (`show_feedback_result`)。detached viewer を閉じてもジョブは続く (App の持ち主なので)。
- **Remote**: リモート操作中でもジョブは止めない (動画アップスケールのキューはリモート操作中に新しいタスクを始めないが、VLM は `AiRuntime` を使わず、
  ジョブは利用者がローカルで始めたもの)。
- **保存の後の知らせ**: `Written` のとき、V1-4 の表示の共有キャッシュと V2 の索引の旗へ知らせる場所を 1 つの関数にしておく (V1-3c では中身は空)。
- **perf**: 読み込み・推論・保存に `perf::event` を入れる (§14)。

**状態を減らす検討**

- 取得中の 2 度目の要求は対象を足さず、選び直してもらう (取得と待ち行列の組み合わせを作らない)。
- worker は常駐させず、ジョブと寿命をそろえる (R2)。再起動・再試行はしない。
- ジョブ中のモデルの削除は押せなくする (削除とジョブの組み合わせを作らない)。
- 本 (V1-4) は V1-3c では対象外として数えるだけにし、表紙の解決を V1-3c に入れない。
- まれな失敗 (ディスクフル・展開の失敗・DB の失敗) は割り切り (ログ + 通知)。

#### 21.11.2 V1-4a: 画像の説明文の表示

コードで確かめた前提 (2026-11-03):

- 情報パネル (`ui_metadata_panel.rs` `draw_metadata_panel` → `draw_metadata_panel_inner`) を呼ぶのは fullscreen の描画 (`ui_fullscreen.rs`
  `render_fullscreen_viewport_with_root_input`) だけ。detached viewer も同じ関数を、その context を `App` に載せた状態で呼ぶ
  (`App::update_active_viewer_context`)。パネルは常に `&mut App` で動く。
- context ごとのメタデータキャッシュは `ViewerContextBundle` (`viewer_context_registry.rs`) が持ち、載せ替えで `App` の field と入れ替わる。
  `sidecar_display_cache` と `folder_thumb_pin_dirty` は bundle に入っておらず、すでに全 context で共有している。共有キャッシュはこの前例に倣う。
- 画像の説明文のキーは、`GridItem::Image` の `metadata_cache_key(idx)` と同じ文字列になる (`CaptionDb::normalize_path` は STORES の記述子の
  KeepDrive 正規化 = `adjustment_db::normalize_path`)。ZIP 内の画像・PDF のページのキー (`::` 付き) は説明文の対象ではない。
- `CaptionDb::open_at` はスキーマを作る (書く)。読み取り専用で開く関数は無い。rollback journal なので、長く開いた読み取りの transaction は
  書き手の COMMIT を待たせる (V1-3c の `CommitBusyGuard`)。
- 一覧の `image_metas` の更新日時は秒で、説明文の署名 (ミリ秒) とは厳密に比べられない。

設計:

1. **持ち主**: `App` に `caption_display: CaptionDisplayCache` を 1 つ (bundle に入れない)。
   - 中身: キー → `Loading { gen }` / `Loaded { row: Option<CaptionRow>, current: Option<FileSignature>, gen }`。`epoch` (全部消すたびに増やす) と
     キーごとの `gen` (そのキーを消すたびに増やす) を持つ。
   - 大きさの上限は 512 件。超えたら全部消す (表示中の項目は次のフレームで読み直す。LRU は持たない)。
2. **読み込み worker**: 説明文だけの小さな worker を 1 本、初めて要るときに起動し、mIV が終わるまで要求を待つ (channel で `(key, path, epoch, gen)`)。
   - 1 件ごとに、`ai_caption.db` を **読み取り専用で開く関数** (`CaptionDb::open_read_only`、新設。ファイルが無ければ `None` を返し、作らない) で
     1 回の SELECT を行い、`std::fs::metadata` で今の署名を取る。読み取りの transaction を持ち越さない (接続は持っていてよいが、文と文の間で
     transaction を開いたままにしない)。DB が無いときは、作成ジョブが作るまで「行なし」。
   - 結果は `mpsc` で返し、`request_repaint` する。`App::ui` の先頭 (`poll_caption_job` の隣) で受け取る。届いた結果の `epoch`・`gen` が今と違えば
     採用しない (保存や取り込みより前に始まった読み込みが後から届く場合)。読み直しは、次にパネルがそのキーを描くときに起きる。
   - mIV の終了では channel を閉じるだけで join しない。DB の失敗は「行なし」として扱いログに出す (まれな失敗は割り切り)。
3. **要求のきっかけ**: パネルが `GridItem::Image` を描くとき、キーがキャッシュに無ければ要求を送る (UI スレッドは channel に送るだけで I/O をしない)。
   同じキーを描き続けている間は、`Loading` 中も送り直さない。ほかの種類 (ZIP 内の画像・PDF のページ・動画・音声・本) では要求しない (本は V1-4b)。
   - **今の署名は、表示を始めるたびに取り直す** (独立レビュー 18 回目 P2-1)。キャッシュにある `current` は、その読み込みの時点の署名でしかない。
     画像は外部で上書きされても説明文の DB は変わらないので、DB の無効化だけでは「古い」にならない。そこで、パネルが描くキーが前のフレームと
     変わったとき (開く・前後の移動・開き直し) は、キャッシュにあっても読み直しを送る。届くまでは今の値を出し (ちらつかせない)、届いたら入れ替える。
     1 回の表示につき SELECT と stat が 1 回で、毎フレームは送らない。一覧の読み直し (今の context のメタデータキャッシュを消す経路、`app.rs` の
     一覧の再読み込み) でも共有キャッシュを全部消す。
   - **読み込み中の再入場 (2026-11-03 設計担当の判断)**: 表示を始めたときは `Loading` 中でもそのキーの `gen` を進めて再送する。
     先の結果は世代不一致で捨て、新しい stat は再入場後に取る。「Loading 中は送り直さない」は同じキーを描き続ける毎フレームだけの規則。
     再入場の印や後続 read 待ち状態は足さず、Loading / Loaded の2状態を保つ。Loaded の再読込中は以前の値を残す。
4. **パネルの欄「AI 説明」**: ★・タグ・パレットの後、ツイート・生成情報・EXIF の前に置く (内容の説明なので、生成情報より上)。
   - `ok` の行: 説明文・画像内の文字 (空なら出さない)・検索語 (読点でつなぐ) を、既存の `draw_text_section` (Copy ボタン付き) で出す。
     下に「作成日」を 1 行。モデルの `model_id` はその行の hover に出す (UI に内部名を常に出さない)。
   - `failed` の行: 「この画像の説明文を作れませんでした」と作成日だけ。
   - **古い**: 行の署名と今の署名が違えば「画像が変わっています。右クリックの『AI 説明文を作る』で作り直せます」を添える (説明文は消さずに出す、§7)。
     ファイルが無ければ (今の署名が `None`) 古いとは出さず、説明文をそのまま出す (独立レビュー 18 回目 P3-4)。閲覧中は一覧の更新が先送りされ、
     消えた項目が残ることがある (`app.rs` の閲覧中の一覧更新の先送り)。説明文は「そのパスに作ったもの」で、ファイルが無いことは一覧の側の状態なので、
     この欄では扱わない。
   - 行が無い・読み込み中は欄を出さない (読み込みの間に「無し」がちらつかないように)。「表示するものが無い」の判定 (`draw_no_metadata`) に

#### 21.13.1 表紙の解決 `resolve_book_cover`

1. **解決の切り出し**: `thumb_loader::process_load_request` の中の「どこを読むか」を決める部分 (EPUB の世代の解決・フォルダの代表の選択・
   ZipDir の代表・ZIP/RAR の最初の画像の決定) を、2 つの関数に切り出す (下の 2 段)。
   切り出しの前後でサムネイルの結果を変えない。
   - **2 つの段に分けて切り出す** (独立レビュー 20 回目 P2-1)。今の `process_load_request` は、EPUB の世代と署名の確定を cache の参照の前に行い、
     フォルダ・ZIP の代表の選択を cache に無かった後に行う。`CacheOnly` は元のファイルを開かずに終わる。この順序と、取り消し・終わりの位置を変えない:
     - 前段 `prepare_load_request_stamp` (cache の参照の前): EPUB の世代の確定と署名 (今の `stamp_resolved_pdf_request` の部分)。
     - 後段 `resolve_read_after_cache_miss` (cache に無かった後): フォルダの代表・ZipDir の代表・ZIP/RAR の最初の画像の決定。
     サムネイルは「前段 → cache の参照 → (無ければ) 後段 → 読み込み」の今の順で呼ぶ。本のための解決は cache を見ずに前段と後段を続けて呼ぶ。
   - **後段の結果型** `ResolvedRead` (独立レビュー 20 回目 P2-2): 読む位置 `ReadLocation` (`File(path)` / `ArchiveEntry { archive, entry }` /
     `PdfPage { pdf, page }` / `ChildCached { .. }` / 読めない (理由付き)) に加えて、今の後段が読み込み・保存の段へ渡しているものをそのまま運ぶ:
     フォルダの選定証明 (`FolderSelectionProof`)、取得済みの bytes・画像・寸法 (ZIP の最初の画像を読んだ bytes など)、子の保存済みサムネイルの WebP と寸法、
     有効な署名。サムネイルの読み込み・保存の段は、これを受け取って今と同じ処理をする (選定証明を保存し、取得済みの bytes を読み直さない)。
     EPUB の `ReadTarget` (lease) は前段で得たものを、署名の確定から描画の終わりまで同じものを持つ。
   - 切り出しは挙動を変えない移動に限る。サムネイルの既存のテストに加え、各種類 (画像・ZIP・RAR の直接と変換済み・PDF・EPUB・フォルダの直下の画像・
     子の本の代表・固定表紙の各種) で、切り出しの前と同じ読み込み先になることをテストで押さえる。
2. **本のための解決** `resolve_book_cover(book_path, kind, &BookCoverEnv) -> BookCover` (worker で呼ぶ。UI スレッドでは呼ばない):
   1. 一覧と同じ計画を作る: `make_load_request_with_visibility` 相当の計画と `apply_folder_thumb_pin` を **worker で**行う
      (`app/color_filter.rs` の `run_color_scan_worker` が worker で `apply_folder_thumb_pin` を呼ぶ前例に倣う)。固定表紙の DB は `Arc<FolderThumbPinDb>` を渡す。
   2. 変換が要る書庫は、App の map ではなく worker で同じ判定 (`resolve_converted_archive_candidate`、`pub(crate)` にする) を行う。`Unavailable` は
      「未変換」として返す (§6.7・U18)。
   3. 前段と後段を呼ぶ。`ChildCached` (フォルダの代表が子の本の保存済みサムネイル) のときは、**選定の結果に残した「固定表紙の持ち主のコンテナ」と
      「解決済みの位置」** から読む (独立レビュー 20 回目 P2-3)。子フォルダ B の表紙を `B/book.pdf` の 3 ページ目に固定し、親 A がその WebP を採った場合、
      今の `winner.path` は PDF を指すが、固定の指定は B の行にあるので、PDF の葉のパスから選び直すと 1 ページ目になってしまう。そこで、子の
      選定 (`resolve_folder_thumb_image_inner` の子の固定表紙の解決) が固定表紙を使ったときは、その持ち主と `ResolvedPinTarget` を選定の結果に
      残し、本の解決はそれを読む。固定表紙を使っていない子だけ、子の本の規則 (子の固定表紙の確認を含む) で 1 から解決する。
      深さは `folder_thumb_depth` まで、同じ本に戻ったら止める (既存の固定表紙のたどりの循環検出と同じ考え方)。サムネイルの側は、残した情報を使わず
      今どおり WebP を使う (選定の結果に field が増えるだけで、選び方は変えない)。
   4. 返すもの: 読む位置 (`ReadLocation` のうち `File`/`ArchiveEntry`/`PdfPage`)、`cover_ref`、署名とその元のパス、読めない理由 (未変換・
      固定表紙のエントリやページが無い・本が無い)、**動画のフレームの表紙** (下の 6)。
   6. **動画のフレームを表紙に固定した本** (独立レビュー 20 回目 P2-4): 一覧は `video_pins.db` の WebP (固定したフレームの縮小画像) を表紙にする。
      v5 では**対象外**にする (§1 で動画は対象外。フレームを 1024px で取り出し直すには動画のデコードが要り、ジョブに動画の処理が入る)。解決は
      「動画のフレームの表紙」として `cover_ref` (`<動画の相対パス>#frame=<固定のフレームの位置>`) と動画ファイルの署名を返し、ジョブは
      「対象外 (動画の表紙)」に数えて何も保存しない。表示では、行の `cover_ref` と違うので「古い」になる (画像の表紙で作った後に動画のフレームへ
      固定し直した場合)。動画の固定表紙の DB (`VideoPinDb`) は `BookCoverEnv` に入れる。
3. **`cover_ref` の形**: `<本からの相対パス>` に `#entry=<書庫の中のエントリ名>` か `#page=<0 始まりのページ番号>` を付ける (相対パスは区切りを `/` に揃える。
   本そのものなら相対パスは空)。例: ZIP の最初の画像 `#entry=001.jpg`、フォルダの直下の画像 `cover.png`、フォルダの子 PDF の 3 ページ目 `sub/b.pdf#page=2`。
   変換済み ZIP を読んだときは、**変換済み ZIP の中の実際のエントリ名**を記録する (独立レビュー 20 回目 P3-6。変換は名前の正規化・重複名への連番・
   入れ子の展開の prefix を行うので、元の書庫の名前とは違うことがある。元の名前への逆変換はしない)。
4. **署名** (§6.7 のまま): ファイル 1 つの本は本そのもの、フォルダの本は実際に読んだファイル、EPUB は読んだ世代の元ファイルの `display_source_state`。
   EPUB の 100ns 単位はミリ秒に直す (`FileSignature::from_metadata` と同じ切り捨てで、変わっていないファイルでは同じ値になることをテストで押さえる)。
5. **`BookCoverEnv`** (worker へ渡す、UI スレッドで作る。I/O をしない): `folder_thumb_sort`・`folder_thumb_depth`・一覧の表示の種類の設定
   (`listing_file_type_visibility`)・`Arc<FolderThumbPinDb>`・動画の固定表紙の DB・archive cache の DB・PDF のパスワードの材料 (下の 21.13.2 の 4)。

#### 21.13.2 本の作成ジョブ (V1-3c のジョブを広げる)

1. **対象**: 選んだセルが `ZipFile` / `PdfFile` (EPUB を含む) / `ConvertibleArchive` / `Folder` なら本として足す。`ZipDir` は対象外 (§6.7)。
   選択なし・空白の右クリックの「今のフォルダの直下」には、直下の画像と ZIP・PDF などの本を含め、サブフォルダは含めない (§6.7。フォルダは選んだときだけ本)。
   待ち行列の 1 件は `CaptionTarget::{Image(path), Book { path, kind }}`。同じパスは足さない (§6.6)。
2. **1 件の流れ (本)**: `resolve_book_cover` → 飛ばす判定 (`status = ok`・`cover_ref` と署名が行と一致・同じ `model_id`・同じ `prompt_version`) →
   読む位置から 1 枚を読む (書庫のエントリ・PDF のページは長辺 1024px 相当で、ファイルは画像と同じ流れ) → 画像と同じ縮小・RGB8 → 推論 →
   検索語の重複除去 → 保存 (`SaveRequest { item_path: 本のパス, signature_path, signature, cover_ref }`)。mIV の非破壊回転は、読む位置が
   ふつうの画像ファイルのときだけ画像と同じく当てる (書庫の中・PDF のページはサムネイルも回転の DB を見ていないなら当てない。実装の始めに確かめる)。
3. **飛ばす・数える**: 未変換 (§6.7・U18) は何も保存せず「未変換のため飛ばした」に数え、終わりに「一度開いて変換すると作れます」を添える。
   動画のフレームを表紙にした本は「対象外」に数える (21.13.1 の 2 の 6)。
   固定表紙のエントリ・ページが無い本は「読めなかった」に数え、行は書かない (§21.11.3 の 8)。
4. **PDF のパスワード**: 開くときの規則 (`pdf_open_password`) を、App の状態に依らない関数 (保存済みの store・今のその場の PDF とパスワードを引数に取る) に
   切り出し、App と worker の両方から呼ぶ (優先順を複製しない)。ジョブの開始時に store の複製と、今のその場の PDF のパスとパスワードを worker へ渡す
   (store を worker へ複製する前例がある)。パスワードが無い・違う PDF は「パスワードが必要」に数えて飛ばす。ジョブの途中でパスワードを尋ねない
   (モーダルの割り込みを作らない)。
5. 進捗の小窓に「未変換」「パスワードが必要」の数を足す。それ以外 (中止・終了・受付の締め切り) は V1-3c のまま。

#### 21.13.3 本の説明文の表示

1. 情報パネルの「この本」の欄 (本を開いて見ているとき、★・タグの並び) に、本の説明文を画像と同じ形で出す。見出しは「この本の AI 説明」。
   本のキーは、パネルの「この本」の★が使う `physical_container_rating_key` (変換済みの書庫は元の書庫のパス) と同じ。
2. 共有キャッシュ (V1-4a) をそのまま使い、要求に「本」の種類と `BookCoverEnv` を足す。読み込み worker は、行を読んだ後に `resolve_book_cover` で
   今の `cover_ref` と署名を取り、行と比べて「古い」を決める (§6.7。固定表紙を変えると「古い」になる)。表紙の解決は表示を始めるときに 1 回。
   解決が読めない (本が無い・未変換) ときは「古い」と出さない (画像のファイルが無いときと同じ扱い)。
3. 古いの文言: 「表紙が変わっています。右クリックの『AI 説明文を作る』で作り直せます」。
4. 無効化に足すもの: **固定表紙の変更・解除で全部消す** (§6.7、独立レビュー 8 回目)。つなぐ場所は `set_folder_thumb_pin` と `remove_folder_thumb_pin` そのもの
   (ZIP の中では呼び出し側が「読み直しの印」を取り除くので、印の消費の側ではなく、DB を変える 2 つの関数につなぐ)。動画の固定表紙の変更・解除も同じ。
   **固定表紙の DB を取り込み・STORES が変える場合も全部消す** (独立レビュー 20 回目 P2-5): 取り込みの全部消しの条件に `ImportChangedSections.thumbnail_pins`
   (と動画の固定表紙) を足し、`StoreMutationEffects` の `captions_changed` を「`ai_caption.db`・`folder_thumb_pins.db`・`video_pins.db` のいずれかの行が変わった」に広げる
   (名前は `caption_display_stale` などに改める)。固定先の子の画像を改名して親の固定表紙だけが書き換わる場合も、これで拾う。

#### 21.13.4 状態を減らす検討

- 一覧の経路 (計画を UI スレッドで作る・固定表紙のたどりを UI スレッドで行う) は今回動かさない。本のための解決は worker で同じ部品を呼ぶだけにする。
  一覧の経路を worker へ移すのは別の課題 (UI スレッドの同期 I/O の削減) として残す。
- 本のジョブはパスワードを尋ねない・変換をしない (モーダルの割り込みを作らない)。
- 表示の古いの判定は表示を始めるときに 1 回だけ解決する (固定表紙の変更は全部消しで拾う)。
- まれな失敗 (書庫が壊れている・PDFium の失敗) は「読めなかった」に数えるだけ。

#### 21.13.5 テスト

- 切り出しの前後でサムネイルの読み込み先が同じこと (上の各種類)。
- `resolve_book_cover`: 各種類の `cover_ref` と署名、子の本の代表の解決し直し (子の固定表紙を含む)、循環と深さ、未変換、固定表紙の先が無い。
- EPUB の署名のミリ秒換算が `from_metadata` と一致すること。
- 本のジョブ: 対象の集め方 (選択・空白・スタック・`ZipDir`)、飛ばす判定 (固定表紙を変えると作り直す)、未変換・パスワードの数え方、保存の中身。
- 表示: 「この本」の欄、固定表紙の変更で全部消えて「古い」になること、`physical_container_rating_key` と保存のキーが一致すること (変換済みの書庫を含む)。
