## 1. 見開き切り替えが表示に届かない (継続中)

`367f3816` でコンテナ更新に単一の owner を与えたが、**まだ直っていない。**

### 1.1 実機で確定している事実

- 単ページへ切り替えると `/api/container` は `single` / 26 groups で 200 を返す
  (サーバ側は正しい)
- **その後 64 秒間、`page_display` イベントが 1 件も出ない。** 画面は見開きのまま
- 切り替え直後に**英字のトーストが一瞬出る**。利用者は読めなかった

英字ということは、`LatestOnlyTaskQueue.pump()` の catch が JS 例外の `error.message` を
そのまま `showBoundaryMessage` に渡している。**その中身がどこにも記録されていないので、
原因が特定できない。**

### 1.2 まずやること: 失敗を観測可能にする

**これを最優先で入れる。原因の推測より先に、事実を残せるようにする。**

- 更新の失敗を `recordClientError` で telemetry へ送る (category は
  `spread_refresh_error` 等)。**stack を含める**
- 利用者へ出すのは日本語の一文にする。生の JS 例外メッセージを画面に出さない
- **早期 return の理由を型で残す。** 現在 `performContainerSpreadRefresh` は複数の条件で
  `VIEWER_GROUP_LOAD_SUPERSEDED` を返すが、どれで抜けたか分からない。理由を
  telemetry に記録する (viewer 不一致 / container 不一致 / load 失敗 / abort など)
- `updateViewerImage` が `loadGroup` に到達せず早期 return した場合も、その理由が
  分かるようにする。**`page_display` が 1 件も出ないことが今回の唯一の手掛かりだった**

そのうえで原因を特定して直す。**症状パッチを当てない。** 分からなければ、観測を入れた
状態で報告してよい (利用者に再現してもらう)。

### 1.3 分かっている手掛かり

- コンテナ更新は 8 秒差で 2 回走っている (どちらも `single` 26 groups)
- `performContainerSpreadRefresh` は `state.pageGroupIndex` を更新してから
  `updateViewerImage` を呼ぶ。`page_display` が出ないので `loadGroup` へ到達していない
- 直後の別操作 (rtl への切り替え) では表示が更新されている

## 2. ドットが HUD の枠からはみ出す

## 3. ドットの前後が逆になる

1 ページ目で `●●●●｜` (後方に 4 個、前方に 0 個) になる。

**原因**: 表示の分割を `pagePrefetchHudPlan` の ahead / behind バケツで決めているが、
このバケツは `pagePrefetchPlan` の `direction` (= `state.pageDirection`、最後に動いた向き)
に従う。**戻る操作の直後は前後が入れ替わる。** 1 ページ目で `direction = -1` だと、
ページ 1〜4 が「後方」として計画され、区切りの左に並ぶ。

**直し方**: 表示の分割を**現在ページとの位置関係**で決める。現在の表示グループより前の
ページは左、後のページは右。先読み計画そのものが進行方向を優先するのは正しいので、
**計画は変えず、表示の分け方だけを変える**。

RTL のときに「これから読む側」を右に置く既存の意図は維持する。

## 4. 予算が一杯のとき、近いページより遠いキャッシュが優先されてしまう

利用者の実機報告: `●●●●｜●●●○●●●●●●●●` のような状態で止まる。すぐ隣が未取得なのに、
遠くのページは取得済みで、そこから進まない。

**原因**: 現在の admission は「保持量が予算以上なら新しい取得を始めない」だけで、
保護集合 (表示中 + 計画の先頭 K) の中に**距離の優先順位が無い**。遠いページが予算を
埋めていると、近いページを取りに行けない。

**直し方** (利用者の提案どおり):

- 予算が一杯でも、**これから取りに行くページより「遠い」キャッシュがあれば、それを捨てて
  枠を作る**
- **自分より近いキャッシュは絶対に捨てない。** 捨てると取得と破棄が往復する
  (§14.6 でこの往復を構造的に無くしたので、戻さないこと)
- 「遠い / 近い」は現在の表示グループからの距離で決める。計画の並び順
  (`pagePrefetchPlan` は近い順に返す) を使ってよい
- 捨てられるものが無ければ、これまでどおり開始を止めて超過を受け入れる

これにより、予算が小さくても**近いページから順に埋まる**ようになる。

## 5. テスト

`node --test --experimental-test-isolation=none crates/remote-web/web/*.test.mjs`

- 更新の失敗が telemetry に記録され、利用者へは日本語が出る
- 早期 return の理由が区別できる
- ドットの分割が現在ページとの位置関係で決まる (進行方向を変えても入れ替わらない)
- 1 ページ目で後方のドットが 0 個になる

- 捨てられるものが無ければ開始を止める
