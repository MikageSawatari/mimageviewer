# リモート閲覧: 一覧に出るものは開ける (登録済み項目を起点に加える)

作業ツリー: `C:\home\mimageviewer-web` (branch `web-remote`)。
実装 = Codex、レビュー・テスト・統合 = ClaudeCode、実機確認 = 利用者。

直前の改名 (commit `69bf7d33`、`favorite_id` → `root_id`) の続き。

## 1. 直す問題

今のリモートは **お気に入りの中しか開けない**。一覧を作る段階で、お気に入りの外にある項目を
**黙って落としている** (`to_remote_entries` の `map_existing_to_favorite` が `None` を返す)。

そのため:

- タグやレーティングを付けた項目が、お気に入りの外にあると**一覧から消える**
- 本棚フォルダがお気に入りの外にあると、**本棚が丸ごと空に見える**
- 閲覧履歴・ブックマーク・スマートフォルダでも同じことが起きる
- **利用者は外出先で初めてそれに気づく**。家では見えていたので予測できない

利用者判断: **「mIV が一覧に出すものは、リモートからも開ける」**。
これを規則そのものにする。どの一覧からも項目が黙って消えない状態にする。

## 2. 構造の決め

### 2.1 起点 (root) は 2 種類になる

| 種類 | ID | 開ける範囲 |
| --- | --- | --- |
| お気に入り | 既存の favorite UUID | 従来どおり root 配下すべて |
| 登録済み項目 | パスから決まる UUID (下記 2.3) | 2.4 の粒度 |

**解決するのは 1 か所だけ。** 呼び出し側は「どちらの種類だったか」を知らない。
`root_id` の doc comment (改名時に入れた) の約束をここで守る。

### 2.2 起点の出どころ = 一覧が返せるもの

**「その一覧が返せるパスの集合」がそのまま起点の集合**になる。別の基準を作らない
(基準が 2 つあると必ずずれる)。

| 一覧 | 起点になるパス |
| --- | --- |
| タグビュー | tags.db の全 item_key |
| レーティング一覧 | rating.db で ★1〜5 が付いている行 |
| ブックマーク | 本のブックマーク / 動画・音声のブックマークが指すパス |
| 閲覧履歴 | 履歴 DB を**一覧と同じ上限** (`settings.reading_history_limit`) で読んだ結果 |
| 本棚 | `settings.books_root_path()` の 1 フォルダ |
| スマートフォルダ | 各ルールの `source` フォルダ |

- スマートフォルダは `include_descendants` の値によらず **`source` 配下を開ける**ようにする。
  利用者が指定したフォルダそのものであり、お気に入りと同じ扱いでよい
- **コンテナ検索 (Ctrl+S 相当) はこの拡張の対象外**。索引が `favorite_root` で引かれており、
  定義上お気に入りの中しか返さない

### 2.3 ID はパスから決まる値にする

- 正規化パス (`adjustment_db::normalize_path` と同じ規則) から **UUID v5** を作る。
  namespace は固定値を 1 つ定義する
- **UUID の形であることが必須**。HTTP 入口の `root_and_path`
  ([crates/remote-web/src/http.rs](../crates/remote-web/src/http.rs)) が
  `root` を `Uuid` として parse する。形が違うと入口で弾かれ、原因が分かりにくい失敗になる
- パスから決まるので**再起動しても同じ ID** になる。保存したリンクが翌日切れない
- ID は逆算できないが、**逆算されても意味が無い**設計にする。解決時に「その ID の指す
  パスが**今も登録されているか**」を確かめるので、登録の無いパスの ID は解決しない

### 2.4 登録済み項目の粒度

| 登録されたもの | 開けるもの |
| --- | --- |
| ファイル (画像 / 動画 / 音声 / ZIP / PDF / アーカイブ) | **それ自身だけ**。`relative_path` は空のみ有効 |
| フォルダ | **配下すべて** (お気に入りと同じ) |

- **ファイル起点でも subresource は許す。** ZIP のエントリや PDF のページは
  `relative_path` が空のまま subresource で指すので、これを塞ぐとタグを付けた ZIP を
  開けなくなる
- **親も兄弟も開けるようにならない。** `D:\private\` の中の 1 枚に星を付けても
  `D:\private\` は開けない。これが登録の粒度を項目単位にしている理由

### 2.5 登録を外したら開けなくなる

各 DB の変更を検知して起点を読み直す。お気に入りが settings.db の `data_version` を見て
読み直しているのと同じ仕掛け (`RemoteFavoriteRoots` /
[crates/remote-web/src/store.rs](../crates/remote-web/src/store.rs) の `ObservedDatabase`)。

タグを外した項目は次の解決から通らなくなること。**これはテストで固定する。**

### 2.6 お気に入りが優先

あるパスがお気に入りの中にも入っていて、かつ登録もされている場合は、**お気に入りを使う**。

- 一覧に出す住所は従来どおりお気に入り相対になり、既存の挙動が 1 つも変わらない
- この変更は**純粋な追加**になる。お気に入りの中の項目の住所・親移動・パンくずは不変

### 2.7 規則の持ち主は 1 つ

「何が登録済みか」は**本体と remote-web の両方が独立に判定する** (二重検査は維持する)。
しかし規則が 2 か所にあると、片方だけ直したときに穴が開く。

**新しい共有クレートを 1 つ作り、両プロセスがそれを使う。** 中身は:

- ID の導出 (2.3)
- 各 DB からの起点の列挙 (2.2)
- 変更検知 (2.5)
- 粒度の判定 (2.4)

本体の `adjustment_db::normalize_path` は、この共有クレートの正規化へ委譲して
**正規化規則も 1 つに保つ** (2 つあると ID がずれて解決できなくなる)。

お気に入り側の読み取りは今のまま 2 実装で構わない (この増分では触らない)。

### 2.8 上限

登録済み項目は数万件になり得る。**上限を 1 つ決めて超えたら記録に残す** (無言で打ち切らない)。
上限に達した状態でも、お気に入りの中は今までどおり全部開けること。

## 3. 影響範囲

- `src/remote_ipc/path_guard.rs` — 解決器。`resolve_existing` / `map_existing_to_*`
- `src/remote_ipc/collections.rs` — 全一覧の写像 (`to_remote_entries*`)。
  **落とすのではなく登録済み起点へ写す**
- `src/remote_ipc/container.rs` — フォルダ / コンテナ列挙、サムネイル、ページ
- `crates/remote-web/src/store.rs` — 二重検査 (`retain_allowed_remote_entries` /
  `retain_allowed_folder_list_entries` / `validate_remote_address*`)
- `crates/remote-web/web/app.js` — 親移動の扱い (下記 4)
- `PROTOCOL_VERSION` を 1 つ上げる。`docs/web-remote-plan.md` §13.5 も更新

## 4. ブラウザ側

- **起点の外へ出る移動を作らない。** 登録済み項目の画面で「親フォルダへ」を押しても
  起点の外の住所を組み立てない。**元の一覧へ戻る** (`gridReturnHash` の既存経路)
- パンくずの先頭は、お気に入り名の代わりに**その項目の名前**にする
- クライアントは**起点の種類を判定しない**。「親があるか」は住所から決まる
  (`relative_path` が空かどうか) ので、種類で分岐しない
- タグタブの「件数は mIV 全体の数です」の注記は、**範囲が広がって数と中身が一致する
  ようになったら外す**。残す必要があるかを判断して、不要なら消す

## 5. ドキュメント

`docs/web-remote-plan.md` §3.1 は今こう書いてある:

> **お気に入りに登録されていない場所は、いかなる方法でも読めないこと**

これは**この増分で変わる**。新しい不変条件を、次の 3 点が読み取れる形に書き直す:

1. 読めるのは「お気に入りの中」または「mIV に明示的に登録された項目」に限る
2. 登録された項目は、その項目自身 (フォルダなら配下) だけ。親も兄弟も開けない
3. 登録が外れたら読めなくなる

絶対パスを URL に出さない規則は**変わらない**ので、そのまま残す。

## 6. やってはいけないこと

- 登録の有無を確かめずに、ID から得たパスをそのまま開くこと
- 登録済み項目の**親フォルダ**を起点にすること
- クライアントに起点の種類を渡し、種類で分岐させること
- ID の導出規則や列挙規則を本体と remote-web で別々に書くこと (2.7)
- 絶対パスを応答・URL・ログに出すこと
- 二重検査 (remote-web 側の検証) を省くこと
- お気に入りの中の項目の住所・親移動・パンくずを変えること (2.6)
- タグ・レーティング・履歴の DB へ書き込むこと。**読み取り専用で開く**

## 7. テスト

- お気に入りの外にある**タグ付き項目**が一覧に出て、開けること
- 同じ項目の**タグを外すと**開けなくなること (2.5)
- お気に入りの外の**レーティング項目 / ブックマーク / 閲覧履歴 / 本棚 / スマートフォルダ**が
  それぞれ一覧に出て開けること
- 登録された**ファイル**の起点で、`relative_path` が空でない住所が**拒否される**こと
- 登録された**ファイル**の起点で、ZIP エントリ / PDF ページの subresource が**通る**こと
- 登録された**フォルダ**の起点で、配下が開けること
- 登録も何もされていないパスの ID が**解決しないこと**
- 登録済み項目の**親フォルダ**の ID が解決しないこと
- junction で起点の外へ出るパスが拒否されること (既存の脱出テストと同じ形)
- お気に入りの中にも登録にも該当するパスが、**お気に入り側の住所で返る**こと (2.6)
- 応答 JSON に絶対パスが含まれないこと
- remote-web の二重検査が、登録済み起点を**受け入れ**、未登録を**落とす**こと
- 上限に達したときの挙動 (2.8)
- 既存の web テスト 245 件を維持すること
