## 1. なぜ要るか

連続シークで再生が止まった件 (別ブリーフ) を調べたとき、
**「セグメント取得が止まった」ことは分かったが、その瞬間のバッファ状態が分からなかった。**

- バッファが枯渇していた → 取得側の問題
- バッファは十分あったのに止まった → 再生側 (append / seek 処理) の問題

**この区別が付けば原因の範囲が半分になる。** 現状はどちらとも言えない。

利用者からの要望:

> 10 秒に 1 回、この動画の情報をテレメトリで送っておくことはできないか。
> それができれば、止まったときに 10 秒ほど待ってから診断を依頼すれば、
> **止まった時の状況と、その前にどういったバッファ状況だったか**調査可能になる。

## 3. やってほしいこと

### (a) HUD に動画の健全度を出す

既存の HUD (右下の小窓) に、動画再生中だけ表示する。少なくとも:

- **先読みバッファ秒数** (`video.buffered` と `currentTime` の差)
- `video.readyState`
- **フレーム落ち** (`getVideoPlaybackQuality()` の `droppedVideoFrames` / `totalVideoFrames`)
- 帯域推定 (hls.js の `bandwidthEstimate`)
- 直近のセグメント取得所要時間 (`FRAG_LOADED` から)

`navigator.connection` が使える環境なら回線種別・RTT も。**無い環境で壊れないこと。**

**何を出すかは判断してよい。** 上は「これがあると今回の切り分けができる」という下限。
画面が狭いので、詰め込みすぎない方がよければそう判断してほしい。

### (b) 定期的に telemetry へ送る

**動画再生中だけ、10 秒に 1 回**。停止時に遡って読めるようにする。

**再生位置 (`currentTime`) を必ず含めること。** バッファ秒数と並べると、
サンプル間で時刻が進んだかどうかが直接見え、止まっているかの判定になる。

**重要: 再生が進んでいなくても送り続けること。** 止まっているときこそ要る。
`timeupdate` のような再生進行に依存する契機に載せない。

**送らない条件も判断してほしい。** 動画を開いていないときに送る意味は無い。
電池と通信を無駄にしない範囲で。

### (c) 節目では即時に送る

停止を検知した瞬間 (「通信待ちが N 秒続いています」を出すとき) は、10 秒周期を
待たずにその場のサンプルを送ってほしい。**止まった瞬間の値が一番効く。**

## 4. 記録の 2 段階化 (利用者の要望)

> ファイルパス等も含めた方が調査には良い。一方でリリース後もある程度の情報は
> 取っておいた方がトラブル調査に役立つ。**ログを 2 段階にして、開発中に
> デバッグログ機能を ON にした場合のみ、ファイルパスやセッション ID など
> 少し幅広く収集する形にできないか。**

これを実装してほしい。**既定 = 通常段。明示的に ON にしたときだけ詳細段。**

| | 通常段 (出荷時、既定) | 詳細段 (デバッグ ON) |
| --- | --- | --- |
| 数値・固定の列挙値 | 入れる | 入れる |
| ファイルパス / アドレス | **入れない** | 入れる |
| サーバのメッセージ | 入れない | 入れる |
| 端末 ID | 入れない | 入れる |

**前例がある。** 本体の性能記録 (`--perf-log`) は既にファイルパスを出しており、
開発中は基本 ON で運用されている。**詳細段がパスを持つこと自体は本体の運用と揃っている。**
新しい方針を作るのではなく、この段の切り方に合わせてよい。

**設計してほしい点:**

- ON / OFF をどこで持つか (端末側の設定か、本体側か)。
  **既定 OFF で、ON のままになっていることが分かる形**にすること
- 通常段に何を残すか。「リリース後もトラブル調査に役立つ」ことが目的なので、
  空にしない。判断して報告してほしい

### 段によらず必ず守ること

- **PIN と Bearer token はどの段でも記録しない。** 既存の
  `permanent_log_secrets` + `redact_serialized_secret`
  ([diagnostics.rs](../../crates/remote-web/src/diagnostics.rs)) を迂回しない
- **session ID は生値を書かない。詳細段でも相関用のハッシュ (または短い派生値) にする。**
  session ID は capability であり、あなた自身が「URL へ出さない」と判断したもの。
  **ログは調査のために外へ渡される**ので、生値を書くと渡した相手に操作権を
  渡すことになる。相関だけできれば調査には足りる

**この線引きが妥当か、判断して報告してほしい。** ハッシュで調査に足りるか、
他に生値が要る場面があるかを含めて。

## 5. その他守ること

- 量を増やしすぎない。10 秒に 1 回なら現状の telemetry 量から見て無視できるはずだが、
  **1 サンプルの大きさは抑えること**
- 既存の HUD 表示 (画像・グリッド) を退行させない

## 6. 受け入れ条件

- 動画再生中、HUD にバッファ秒数・`readyState`・フレーム落ちが出る
- 動画を開いていないときは従来どおりの HUD
- 再生中は 10 秒ごとに telemetry へ健全度が届く
- **再生が止まっている間も届き続ける**
- 停止検知の瞬間にも 1 件届く
- **通常段では** file path・アドレス・端末 ID・サーバメッセージが telemetry に出ない
- **詳細段 (デバッグ ON) では**それらが出て、調査に足りる
- **どちらの段でも** PIN / Bearer token は出ない。session ID は生値で出ない
- `navigator.connection` や `getVideoPlaybackQuality` が無い環境で壊れない
- **回帰テスト**を付ける。サンプルの組み立ては純関数で固定できるはず
- web テストが緑
