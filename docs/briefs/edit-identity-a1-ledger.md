## 2. なぜ A1 を先に出すのか

台帳は使われ始めるまで空で、**遡っての一括スキャンはしない** (§3.3)。
早く入れるほど実データが溜まり、A3 の実機確認が現実的なデータでできる。
開発機の実データでは編集を持つ物理ファイルが **921 件** ある。

## 3. 実装

### 3.1 台帳

- スキーマは正本 §3.2 のまま。列を足さない・減らさない。
- 置き場は他の DB と同じ `crate::data_dir` 配下。
- **`busy_timeout` を明示する** (rusqlite の既定は 5 秒だが、`journal_mode` を
  変えるだけでは効かない。既存 DB モジュールの作り方に合わせる)。
- **これは新規ストアなのでマイグレーション不要** (CLAUDE.md「永続データ・スキーマ変更時の
  判断」)。その旨をコミットメッセージに 1 行残すこと。

### 3.2 ハッシュ

- `sha2` は既に依存にある (`Cargo.toml`)。新しいクレートを足さない。
- 段 1 = **先頭 64KB + size** の SHA-256。段 2 = **ファイル全体** の SHA-256。
- **段 2 は打ち切らない** (§3.1)。巨大ファイルでも全体を読む。
- 段 1 / 段 2 の計算は **純関数として切り出す** (`&[u8]` と size を受ける形、
  またはファイル全体を読まずに済む `Read` を受ける形)。テストでファイル無しに検証できること。

### 3.3 記録

- 記録の起点は **編集の確定点**。少なくとも次を通ること:
  - [app.rs:53515](../../src/app.rs:53515) `save_mask_with_sidecar`
  - [app.rs:53621](../../src/app.rs:53621) `save_conceal_with_sidecar`
  - [app.rs:58168](../../src/app.rs:58168) `save_comic_objects`
  - [app.rs:60192](../../src/app.rs:60192) `set_page_params_for_target`
  - [app.rs:60266](../../src/app.rs:60266) `set_page_params`
  - **ローカル調整・出力範囲・★・タグの確定点も同様に探して通す。**
    正本 §2 の「復元する範囲」が対象なので、そこに挙がっているものは全部拾う。
    **見つけた確定点の一覧を報告に書くこと** (漏れの検査はこちらでする)。
- 記録するのは **物理ファイル 1 件**。ページ単位ではない。
  - 画像 → その画像ファイル
  - ZIP / PDF のページ → **容器ファイル**
  - 変換アーカイブ (RAR / 7z / LZH / 入れ子入り ZIP) → **元のアーカイブファイル**
  - `kind` 列は `image` / `zip` / `pdf` / `convertible`
- **UI スレッドから I/O しない** (CLAUDE.md「UI スレッドでの同期 I/O は即 worker 化する」)。
  確定点は「worker へ 1 件投げる」だけにする。
- **`(file_key, size, hashed_mtime)` が一致する限り再計算しない** (§3.3)。
  この判定も純関数に切り出してテストする。
- `last_edit_at` は確定のたびに更新してよい (A3 が候補の既定選択に使う)。

### 3.4 `STORES` への登録

**A1 の時点で登録する** (§3.2 の注記、§10.1「段をまたいで守ること」)。
[rename_key_migration.rs:288](../../src/rename_key_migration.rs:288) の `STORES` へ
`content_identity.db` / `edit_origin` / `file_key` を足す。

- `unique` = true (`file_key` は PRIMARY KEY)。
- `normalization` は **`KeepDrive`** (`file_key` は `path_key::normalize_keep_drive` した
  物理ファイルパス、§3.2)。**自前で正規化方式を選ばず、記述子に従って書くこと。**
- この表は削除 worker の hard purge も走査するので、登録すればリネームと削除の両方に追随する。
- `restore_declined` は path キーではない (`full_hash` + `target_key`) ので、
  `target_key` の扱いを A3 で決める。**A1 では `STORES` に足さない。**

## 4. 制約

- **backfill の一括スキャンをしない** (§3.3)。台帳は使われながら埋まる。
- **時間窓・sleep・retry で吸収しない。**
- **記録は将来の設定 OFF でも止めない** (§7)。A1 に設定は無いので、
  「設定を見て止める」分岐を先回りして作らない。
- 既存の編集保存経路の**挙動を変えない**。記録の失敗が編集の保存を失敗させてはならない
  (ただし**黙って捨てず、ログに理由を残す**)。

## 5. テスト

- 段 1 / 段 2 のハッシュが期待値になること (既知バイト列の固定値で)。
- `(file_key, size, hashed_mtime)` 一致で **再計算しない**こと
  (I/O 呼び出し回数か、ハッシュ関数の呼び出し回数を数える)。
- size または mtime が変わったら**再計算する**こと。
- `kind` が画像 / ZIP / PDF / 変換アーカイブで正しく決まること。
- ZIP / PDF のページを編集したとき、記録されるのが**容器ファイル**であること。
- `STORES` にリネームが効くこと — 既存の
  `migrates_exact_file_keys_across_stores` 系のテストは `STORES` を走査しているので、
  記述子を足せば自動で対象になるはず。**なっていなければ理由を報告する。**
- 記録の失敗が編集保存を壊さないこと。
