## 1. 症状 (利用者報告、実機。私が API で裏を取った)

**(a)** 本体で自動トリムを設定しても、端末では**トリム前の絵が出続ける**。

**(b)** そのとき、**見開きの片方だけが古い**状態が起こる。トリム済み (背が低い) と
未トリム (背が高い) が並ぶのでレイアウトが破綻し、**中央に黒い隙間**が出た。
**60 秒ほど待って再読込すると直る。**

利用者の手順: ブラウザで見る → 本体で自動トリムを設定 → ブラウザで開き直す。

## 2. 原因 (特定済み。ここは再確認しなくてよい)

ページ画像は 2 段でキャッシュされ、**どちらもトリム変更で無効化されない**:

| | 鍵 | 無効化 |
| --- | --- | --- |
| 端末内 `PageResourceCache` | `infoCacheKey + targetPx + pageRenderRevision + renderContext` ([app.js:3426](../../crates/remote-web/web/app.js)) | されない |
| HTTP キャッシュ | 同じ要素を含む URL / `private, max-age=60` ([http.rs](../../crates/remote-web/src/http.rs) の api_page) | 60 秒で自然に切れるだけ |

`pageRenderRevision` が上がるのは **端末側で画像補正を保存した 1 箇所だけ**
([app.js:5426](../../crates/remote-web/web/app.js))。**本体側の変更では上がらない。**

60 秒の `max-age` が**ページごとに独立して切れる**ので、(b) の「片方だけ新しい」が起きる。

## 4. 守ってほしい不変条件

**見開きの 2 ページは、必ず同じ版のレンダリング結果であること。**

今回壊れたのはここ。鮮度の取り方が何であれ、**片方だけ古い組み合わせが表示に到達しては
いけない。** 版が変わったら、そのグループは両方まとめて取り直すこと。

`max-age` を短くするだけの対応はしないこと。ずれる窓が狭くなるだけで、なくならない。

## 5. もう 1 件 — 見開きの相手が無いとページごと 400 になる

`remote_view_trim_plan` ([container.rs:2894](../../src/remote_ipc/container.rs)) は、
Auto かつ見開きスロットで `spread_partner` が無いと `BadRequest` を返す。

実機の API で確認した:

```
HTTP 400 {"error":"miv_media_error","message":"見開き Auto の相手ページが指定されていません"}
```

**上下をそろえるのは表示の仕上げであって、それが決められないからといってページ自体を
出さないのは強すぎる。** 相手が無ければ単ページ扱い (`AutoSingle`) に落として表示すること。

現在のクライアントは常に相手を送っているように読めるが、**送れない経路が将来できたときに
ページが真っ白になる**のは割に合わない。§4 の不変条件を満たしたうえで、ここは落として通す。

## 6. 受け入れ条件
