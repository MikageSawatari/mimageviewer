## 3. 3 つの課題

### (a) 原寸表示で操作 UI の位置が変わる / 見切れる

**これは診断不要。** 利用者の指摘どおり、表示倍率を変えても操作 UI は動くべきでない。
前後移動ボタンが見切れると、その状態から抜けられなくなる。

**直してほしい。** 画像の表示倍率と、操作 UI の配置を独立させる。

### (b) 原寸から戻らないことがある

記録上はトグルできているので、**戻れない条件がある**。

**私の仮説** (確定ではない): 原寸では画像がビューポートより大きくなり、パンが有効になる。
その状態ではジェスチャー判定がパンを優先し、**2 回目のダブルタップが成立していない**
のではないか。

**検証して報告してほしい。** 別の原因ならそちらを教えてほしい。
**再現条件が分かるまで、成立しやすくする方向の調整 (閾値を緩める等) を入れないこと。**

### (c) 「微妙なズーム」が何か分かっていない

原寸切り替えとは別物だと利用者が言っている。候補は複数ある。

- ブラウザのダブルタップズーム (= visual viewport の拡大)
- こちらの原寸切り替えだが、元画像が小さくて拡大幅が小さい場合
- 別のジェスチャー (ピンチの誤判定など)

**判別できる材料が記録に無い。** そこで:

**`window.visualViewport.scale` を記録に加えてほしい。**
1 より大きければ**ブラウザが拡大している**ことが確定する。こちらの原寸切り替えは
visual viewport を変えないので、これだけで 2 つを区別できる。

- 既存の `image` / `command` telemetry に載せるか、独立させるかは判断してよい
- **通常段でよい** (数値であり、秘密ではない)
- 量を増やしすぎないこと。毎フレーム送るような形にしない

### (d) ブラウザの拡大を止めるべきか

`.viewer-stage` と `.image-viewer` は `touch-action: none` なので、そこでは起きない。
だが**バー・ボタン・余白・body など、宣言の無い場所では起こり得る。**

このアプリは全画面で使うので、**ブラウザのダブルタップズームはどこにも要らない**と
私は考えている。既定として `touch-action: manipulation` を広く効かせ、
個別に `none` / `pan-y` を宣言している要素はそのまま優先させる形が素直に見える。

**この判断が妥当か検証して報告してほしい。** 既存のピンチ操作や独自ジェスチャーと
競合するなら、やらずに報告してよい。**ピンチズームは残すこと。**
viewport meta で `user-scalable=no` / `maximum-scale=1` は使わないこと
(弱視の利用者に有害で、iOS Safari は無視する)。

- ピンチズームが残っている
- **回帰テスト**を付ける。トグルの状態遷移は純関数で固定できるはず
