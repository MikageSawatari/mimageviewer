# PDF を 1 ページ描くたびに文書を開き直すのをやめる

着手前に [docs/async-architecture.md](../async-architecture.md) と、バックログ §2.13 / §2.14 を読むこと。

## 1. 現状

`core_render_with_count` ([pdf_loader.rs](../../src/pdf_loader.rs)) は**要求ごとに**
`load_pdf_from_file` を呼ぶ。`core_analyze_page` / `core_get_info` / `core_enumerate` も同じ。
子ワーカーは `Pdfium` インスタンスは持ち越すが ([run_worker_process](../../src/pdf_loader.rs:1000))、
**開いた文書は持ち越さない**。

## 2. 実測 (2026-08-20、既存 perf ログ 443MB から集計)

`pdf/pool_recv` の `worker_render_ms` (= `core_render_with_count` 全体) を集計した。

| 出力の長辺 | 件数 | 中央値 |
| --- | ---: | ---: |
| 0–499 px | 35 | 112 ms |
| 500–999 px | 235 | 107 ms |
| 1000–1499 px | 58 | 124 ms |
| 1500–1999 px | 13 | 131 ms |

**画素数が 16 倍になっても 17% しか増えない。** 1 回あたり **約 100ms が出力サイズと無関係な
固定費**である。

| | 件数 | 中央値 |
| --- | ---: | ---: |
| ある文書の**初回**描画 | 61 | 320 ms |
| **2 回目以降** | 280 | 109 ms |

OS のファイルキャッシュが温まっても固定費は残る。

**要求は同じ本に固まる**: ログ中の 1 冊は 88 回、次が 61 回描画されており、上位 10 文書で
全体の 74.8% を占める。88 回 = **同じ本を 88 回開いている**。固定費だけで約 8.8 秒。

## 3. まだ分かっていないこと

`worker_render_ms` は **開く + ページ取り出し + 描く** を全部含む。約 100ms の固定費が

- **(a) 文書を開く** (xref 解析) → **文書キャッシュで消える**
- **(b) ページを取り出す** (`doc.pages().get()`) → **ページごとなのでキャッシュでは消えない**

のどちらかは、現在の計測では分離できない。**計装で分ける。**

## 4. やること

### 4.1 計装 (先に入れる)

`core_render_with_count` の内側を 3 つに分けて `WorkerRenderMetrics` へ載せる:

- `open_us` — `load_pdf_from_file`
- `page_us` — `doc.pages().get()` + `analyze_page_content` + 寸法取得
- `render_us` — `render_with_config` (現在の `render_us` はこの 3 つ全部なので**意味が変わる**)

親側の `pdf/pool_recv` イベントへ `worker_open_ms` / `worker_page_ms` / `worker_render_ms` として
出す。**IPC のメトリクス形式は親子が常に同一ビルドなので、後方互換は不要。**

`core_analyze_page` / `core_get_info` / `core_enumerate` にも同じ計装を入れる価値はあるが、
**まず render だけでよい** (件数が桁違いに多く、固定費の正体はここで分かる)。

### 4.2 直前 1 冊のキャッシュ

**ワーカープロセスごとに、直前に開いた 1 冊だけを保持する。** 全文キャッシュではなく直近 1 件で
足りるのは、§2 のとおり要求が同じ本に固まるため。

**キーは (path, パスワード, mtime, サイズ)。要求ごとに stat して確認する。**

- path だけでは足りない。**削除・差し替え後もワーカーは古い文書を握り続ける** ので、
  同じパスに別のファイルが来ると古い中身を返す (ABA)。
- stat のコストは開き直しに比べて無視できる。
- mtime / file_size は `core_enumerate` が既に取っており ([pdf_loader.rs:400](../../src/pdf_loader.rs:400) 付近)、
  enumerate の応答が運んでいる。**mIV 内の PDF 同一性判定として一貫する。**
- **判定は純関数に切り出す** (前回のキー × 今回のキー → 再利用 / 開き直し)。PDFium 無しでテストできる。
- **時間窓は使わない。** 「一定時間で閉じる」は入れない (§5 参照)。

`doc_reused: bool` をメトリクスへ載せ、**キャッシュが効いていることを perf ログで確認できるようにする**。

`ipc_render` / `ipc_analyze_page` / `ipc_get_info` / `ipc_enumerate` が `&Pdfium` ではなく
キャッシュを受け取る形にする。`run_worker_process` のループに `pdfium` と並べて置けば
生存期間は素直に通る (`pdfium` はループの外)。

### 4.3 実装上の引っかかり

pdfium-render の `load_pdf_from_file<'a>(&'a self, .., password: Option<&'a str>)` は
**パスワードの寿命が `Pdfium` の借用と同じ**。文書を長く持つとパスワード文字列も同じだけ
生かす必要がある (PDFium 自身はコピーするので API 側の過剰制約)。

パスワード付き PDF のために回避が要る。**やり方は任せるが、無制限に leak しないこと**
(異なるパスワードの数だけに抑える等)。**この点で詰まったら実装せずに報告すること。**

## 5. ファイルハンドルについて (調査済み)

`load_pdf_from_file` は `File::open` したハンドルを文書の生存期間ずっと持つ。
ただし **2026-08-20 に実測した結果、掴んだままでも `rename` / `remove_file` / シェル経由の
ゴミ箱移動はすべて成功する** (Rust の `File::open` は `FILE_SHARE_DELETE` を含めて開くため)。

**したがって「掴むこと」を理由にした解放タイマーは要らない。** 危険なのは §4.2 の ABA であって、
ロックではない。

アイドル時のメモリ (見終わった本を各ワーカーが抱え続ける) が問題になるかは**別途実測する**。
効くと分かったら、時計ではなく既存の決定的な信号 (`bump_render_context_epoch`) に載せて解放する。
**今回はタイマーも epoch 解放も入れない。**

## 6. テスト

- キャッシュ判定の純関数: 同一キーで再利用 / path 違い / mtime 違い / サイズ違い /
  パスワード違い でそれぞれ開き直すこと
- stat に失敗する (削除された) 場合に再利用しないこと
- メトリクスに `open_us` / `page_us` / `render_us` / `doc_reused` が載ること

子プロセスを起動するテストは書けないので、**判定と計測の切り出しでテストする**。

## 7. やらないこと

- `render_page_async` (in-process 再レンダリング) の変更。§2.14 は別件で、実測後に判断する
- 解放タイマー / epoch による解放 (§5)
- 複数文書のキャッシュ (直近 1 件で足りることは §2 の実測で示されている)
