# 追補: セッションを版の正本にする / 切断されたら明示的に再接続するまで止まる

[codex-remote-session-epoch-and-seek-drag-brief.md](codex-remote-session-epoch-and-seek-drag-brief.md)
の §2 を、利用者との相談で**この形に差し替える**。§3 (シークバー) は変更なし。

## 0. 立場

**本体が正本。独自の規則を発明しない。**
以下は私が読んで確認した内容だが、**実際と違っていたら実際の方を報告してほしい。**
私の要約に合わせて実装しないこと。

## 1. 利用者の提案 (原文の要旨)

> 最初に接続したとき、操作開始のコマンドで明示的にセッション ID を取得し、以降の全
> リクエストはその ID を付与。本体側では、有効なセッションでなければエラーを返す。
> スマホ側がセッションエラーになったら、セッション開始処理をやり直し、キャッシュも破棄する。
>
> この形であれば、スマホとタブレットの両方からそれっぽく使えてしまう、といった中途半端な
> 動きも防げ、確実に利用中の端末を特定できる。

> 本体側で切断したら、ping タイミングで切られたことを通知し、それ以上操作できない方が
> 自然。切られたら、明示的に再接続ボタンを押さない限り再開できない方がよい。
> **現状だとアプリを切り替えて触ってしまうと、意図せず本体側の操作が奪われてしまう。**

## 2. 私が確認した現状

- `client_id` は **端末の識別子**。`localStorage` に永続し、再接続しても同じ
  ([app.js の `loadRemoteClientId`](../../crates/remote-web/web/app.js))。
  **取得ごとに変わる ID は存在しない**ので、これを版には使えない
- `SessionResponse` は `{status, message}` だけ。**トークンを返していない**
  ([lib.rs:963](../../crates/remote-ipc/src/lib.rs))
- 全リクエストは `X-mIV-Remote-Client: <端末ID>` を付けており、サーバは
  `NotAcquired`/`Expired` → 428、`LocalInUse`/`Superseded` → 409 を返す
- **`/api/session/ping` が 30 秒ごとに飛んでいる** ([app.js:91](../../crates/remote-web/web/app.js))
- **自動で取り直す箇所が 3 つある**:
  - [app.js:453](../../crates/remote-web/web/app.js) `visibility_resume` — **画面に戻っただけ**
  - [app.js:1087](../../crates/remote-web/web/app.js) `command` — 何か操作しただけ
  - [app.js:427](../../crates/remote-web/web/app.js) ブラウザの戻る/進む

最後の 3 つが、利用者の言う「アプリを切り替えて触ると本体の操作が奪われる」の正体。

## 3. やってほしいこと

### (a) 取得ごとに変わるセッション ID を発行し、版の正本にする

- `/api/session/acquire` が**取得ごとに変わる ID** を返す
- 端末は以降の全リクエストにそれを付ける。サーバは無効なら弾く
- **この ID を端末キャッシュの版として使う**。ID が変われば古い項目に到達しない
- 端末 ID (`client_id`) は端末の識別として残す。**役割を混ぜないこと**

これで「どの端末が使用中か」が一意になる。取られた端末は全リクエストが弾かれる。

### (a-2) 取得は 1 回にする — いまはコマンドのたびに往復している

pre-flight を外した後も、**ページ送りは毎回 `/api/session/acquire` の往復を払っている**。

`dispatchCommand` は全コマンドで `acquireRemoteSession("command")` を await してから
コマンドを再実行する ([app.js:1075](../../crates/remote-web/web/app.js))。
`acquireRemoteSession` は**既に active でも早期 return せず毎回 POST する**
([app.js:512](../../crates/remote-web/web/app.js))。

つまり現状のページ送りは **取得の往復 → コマンド → 画像取得** の直列。

**利用者の提案はここを直接消す。** 取得は最初の 1 回だけにして、以降は発行された
セッション ID を付けるだけにすれば、この往復は消える。サーバは ID を検証するだけでよい。

**取得を 1 回に絞ったとき、所有権の移動 (別端末が取る / 本体が切断する) を
取りこぼさないかを確認して報告してほしい。** そこは (c) の扱いと繋がる。

### (b) 版の通知を ping に載せる。事前問い合わせを廃止する

`/api/session/ping` は**既に 30 秒ごとに払っている往復**。ここに現在の版を載せれば、
**ページ送りの往復をゼロにしたまま**本体側の変更が届く。

`updateViewerImage` 冒頭の `await refreshRemoteStateGeneration(...)` は**やめる**。

放置中は最大 30 秒ぶん古い版を持ち得るが、ページをめくればリクエストがサーバへ届いて
既存の 409 経路で直る。利用者はこれを承知している。

**ping 間隔は変えないこと** (電池を食う)。

### (c) 切断されたら、明示的に再接続するまで動かない

**切れた理由で扱いを変える。** 理由は既に 4 つに分かれている。

| 理由 | 扱い |
| --- | --- |
| `LocalInUse` (本体が明示的に切断) | **自動で取り直さない。再接続ボタンのみ** |
| `Superseded` (別端末が取った) | **同上** (自動だと 2 台で奪い合いになる) |
| `Expired` (放置によるタイムアウト) | 自動で取り直してよい |
| `NotAcquired` (初回) | 自動取得 |

`Superseded` を含めたのは、利用者の言う「両方からそれっぽく使えてしまう」への対処。
自動で取り直すと 2 台が交互に奪い合う。**取られた側は止まるのが正しい。**

さらに、**ping で切断を検知したら能動的に知らせる**こと。今は端末が何か操作するまで
気づかない。切断中は操作できないこと、再接続の手段があることが画面から分かるようにする。

**この分け方が妥当か判断して報告してほしい。** `Expired` を自動にしてよいか、
`Superseded` を止める判断で問題ないかも含めて。

## 4. 変えないこと

- **お気に入りの照合は live のまま** (毎 request、`data_version` 2 µs)。
  セキュリティ境界なので緩めない
- **見開きの 2 ページが版違いで混ざらない**こと
- PIN 認証・fail-closed guard を弱めない

## 5. 受け入れ条件

- ページ送りで `/api/remote-state` の往復が発生しない
- 本体で切断 → 端末は **30 秒以内に**切断を知り、操作できなくなる
- 切断後、**画面に戻る / 操作する / 履歴移動しても勝手に取り直さない**
- 再接続ボタンを押したときだけ再開し、そのときキャッシュを破棄する
- 2 台目が接続したら 1 台目は止まり、勝手に奪い返さない
- 放置によるタイムアウトからは、これまでどおり自動で復帰する
- 消したお気に入りが端末から開けない (退行させないこと)
- **回帰テスト**を付ける。理由ごとの再取得可否は純関数で固定できるはず
- `cargo test -p mimageviewer --lib` / remote / ipc / web が緑
