### コレクションを読書順にした (2026-08-13)

**症状**: サブ展開スマートフォルダ (フォルダ 77 + 画像 66,934) で、本体のシークバーは 66,934。
リモートは一覧のスクロールバーこそ 67,011 で正しいが、**画像をタップすると 1,163** になる。

**原因** (追跡済み): コレクションの項目 (`RemoteEntry`) は `address` を持たないため、
`openGridEntry` が旧 `{kind:"image"}` 経路へ落ち → `navigate(#image/<path>)` →
route 解決が **`loadContainer(親フォルダ)`** を呼び → `applyContainerData` が
`state.collection = null` にして読書順を実フォルダのものへ差し替えていた。
設計としてそうなっていた (`rootOpenReturnHash` が戻り先にコレクションを保持) が、
サブ展開はフォルダをまたいで読むための機能なので本体に合わせた。

- ✅ `bb8c62b9` **catalog の寸法だけを引く問い合わせ** (`load_source_dims`)。
  横長判定のために `load_all` が thumbnail の blob まで運んでいた。
  **実測 (利用者の実カタログ 4,628 枚): 157.4 MiB / 316 ms → 0.429 MiB / 100 ms。367 分の 1。**
  全行が寸法列を持っていたので blob は一度も答えになっていなかった。
  「キーが無い」= 行が無い / 「キーはあるが空」= 寸法列より前の古い行、を区別し、後者だけ
  `load_one` で復元する。**これが下のコレクション見開きの前提** (77 フォルダ分を旧 query で
  開くと 12 GB になる)
- ✅ `8a922591` **本体側**: `CollectionPayload` に address ベースの `page_groups` +
  spread mode / reading direction / gap。ペア判定は**本体と同じ `build_remote_spread_page_groups`**
  を通す (2 つ目の実装を作らない)。横長フラグは**親フォルダごとに 1 回**カタログを開き、
  処理し終えたら drop。protocol v49
- ✅ `fdb6b1cb` **クライアント側**: コレクションから画像を開いても実フォルダへ移らない。
  URL は `#collection/<kind>[/<id>]/image/<encoded>`。**`/image/` で先に分割**しないと
  `image` が rating 値や smart id として食われる。検索結果とタグ一覧は `state.collection` を
  使うが `/api/collection` ではないので従来どおり親コンテナを開く

**やらなかったこと**: コレクションの「続きから」位置 (保存位置の鍵が無い)、
コレクションごとの見開き状態の永続化 (`spread_db` のコンテナキーに相当する安定した鍵が無く、
鍵の設計を混ぜたくない)。セッション中の切り替えはクライアントが現在値を要求に載せるので効く。
既定は本体と同じ `NON_BOOK` = 単ページ。

**本体の見開きペア決定について** (調査結果): 本体は**毎フレーム** nav 配列の先頭から表示ユニットを
組み直す (`ui_fullscreen.rs:10266` のコメント)。横長画像はペアの切れ目を変えるだけで**ループは短くならない**。
判定材料は全てメモリ上なので 1 件あたりは安い。リモートは同じ関数を応答ごとに 1 回呼ぶだけ。

### RR-04: 1000 件上限は何を守っているのか (2026-08-13 実測)

**結論: 上限が守っているものは「無圧縮の転送量」だけで、他に壁は無い。**

| 層 | 件数に対する費用 | 出所 |
|---|---|---|
| クライアント DOM | **なし** — `VirtualGrid` が可視セルだけ materialize する | `app.js` の `VirtualGrid` |
| サムネイル | **なし** — セルが materialize された時だけ 1 枚要求する | `bindThumbnail` (`app.js:6745`) |
| コンテナ列挙 (フォルダ / ZIP / PDF) | **ほぼなし** — 本体が一覧用にどのみち作る listing から `.take(1000)` するだけ。PDF はページ番号から住所を組むだけ | `container.rs:3297`, `:3404`, `:3495` |
| コレクション列挙 (検索 / タグ / レーティング / 履歴) | **1 件ごとに `canonicalize`**。実測 warm 30〜40 µs、cold 125 µs (この PC、6757 件と 4963 件で測定) | `collections.rs:894` |
| wire JSON | **250 B/件** (実測) | 下表 |
| HTTP 圧縮 | **無い** (`Content-Encoding` の実装が remote-web に存在しない) | — |
| named pipe | 1.36 GB/s なので無視できる | 既存計測 |

転送量の実測 (実フォルダの listing 形状で生成):

| 件数 | 無圧縮 | gzip | 比 |
|---:|---:|---:|---:|
| 1,000 | 245 KiB | 16 KiB | 15.6x |
| 5,000 | 1.24 MiB | 68 KiB | 18.6x |
| 6,757 | 1.70 MiB | 94 KiB | 18.2x |

パスは前方一致が多いので 15〜20 倍縮む。**gzip を入れれば 1 万件でも 140 KiB 程度**になる。
`flate2` は `zip` 経由で既に `Cargo.lock` にあるので依存は増えない。

**上限の実害は「一覧が切れる」だけではない**: `page_groups` も同じ 1000 件から作られるので
(`container.rs:3313`)、**1000 ページを超える PDF / 画像フォルダはリモートで 1001 ページ目以降を
開く手段が無い**。ビューアは `state.pageGroups` を辿ってページを送るため。

なお本体自身の上限は検索 5000 (`SEARCH_RESULT_LIMIT`)、タグ 10000 (`TAG_VIEW_RESULT_LIMIT`) で、
**リモートの 1000 は本体より厳しい**側に振られている。

推奨: ① JSON 応答に gzip → ② 上限を本体に揃える (検索 5000 / タグ 10000、コンテナ 10000 程度)。
gzip 後は転送側にプログレス表示は要らない。必要になるとすればコレクション側の canonicalize
(1 万件で最大 1.2 秒) の方。

**① は `5e65e23e`、② は `238e1a7e` で実装済み (10 万件)。**
100 万件を採らなかった理由: `MAX_RESPONSE_FRAME_BYTES` (64 MiB) を確実に超える。
なお frame 上限超過は接続を壊さない — `reader_loop` が broken にして張り直す
(`crates/remote-web/src/ipc_client.rs:1853`)。ただし**その一覧は何度やっても失敗する**ので、
producer 側で予算を守るのが正しい。

読書履歴だけは本体設定由来の上限 (最大 1000) が別にあるので、10 万件にはならない。

## 保存済みトリムの基準について (2026-08-12、本体側と合意)

- 本体が基準サイズを保存するようになったら、**リモートもそれを読む形へ移す**。
  ページ固有の正準寸法を推定する必要がなくなり、vector ページも同じ規則で扱える

- 基準サイズを持たない**既存の保存値をどう解釈するか**は本体の決定に従う。
  リモートが独自に決めない

## ページ供給の律速 (2026-08-12 実測、高画質 8192)

デコード先読み (`eaa7038d`) で**端末側の待ちは消えた**。先読みが間に合ったページは
`tap_to_display_ms` 中央値 **6ms** (2〜33)、`decode_ms` は **0**、19 グループすべてが
スピナーのしきい値 225ms を下回った (修正前は中央値 287ms で 17/17 が超過)。

残る待ちは**供給が追いつかないとき**だけになった。1 ページ (46.6 MP) の内訳:

| 区間 | 中央値 | 割合 |
|---|---|---|
| 本体のレンダリング + JPEG エンコード (`ipc_ms`) | **2281ms** | 71% |
| リモートサービス側 (枠待ち + 応答書き出し) | 536ms | 17% |
| 端末への転送 (約 5 MiB) | 約 370ms | 11% |
| 端末から見た合計 (`fetch_ms`) | 3240ms | |

**転送は 1 割強しかない。**待ちを作っているのは本体側の生成である。標準画質 (4096) は
11.6 MP なのでここが素直に縮む。「標準だと軽い」のはブラウザだけでなく本体側も
4 分の 1 になっていたため。

**並列数を上げても供給は増えない** (2026-08-12、3 層すべてを 3 にして実測)。46 MP の
ページで `ipc_ms` 中央値は同時 2 本で 2016ms、**同時 3 本で 2952ms**。供給に直すと
**0.99 → 1.02 ページ毎秒で、+2% しかない**。この機械は **2 本の時点で既に飽和**しており、
3 本目は増えた分をちょうど食い潰す。

> ⚠ **一度、間違った結論を出している。**同じ日の先行測定で「3 本なら 1.26 ページ毎秒
> (+27%)」と読んだが、その標本の「同時 3 本」は**先読み 2 本 + 表示要求 1 本**が偶然
> 重なったもので、先読みが 3 本競合している状態ではなかった。**優先度で分けて数えること。**

**上限は 3 段が直列に並んでいて、1 つ動かしても効かない。**最初に remote-web の
`MAX_CONCURRENT_PAGE_PREFETCH` だけ上げて commit したが実効は変わらず、戻した
(`aa145071`)。その後 3 層まとめて 3 にした (`daf58505`)。

| 層 | 定数 |
|---|---|
| 端末 | `PAGE_PREFETCH_CONCURRENCY` ([app.js](../../crates/remote-web/web/app.js)) |
| リモートサービス | `MAX_CONCURRENT_PAGE_PREFETCH` ([http.rs](../../crates/remote-web/src/http.rs)) |
| 本体 | `worker_count - 1` ([heavy_queue.rs](../../src/remote_ipc/heavy_queue.rs))、`remote_heavy_worker_count` ([pipe.rs](../../src/remote_ipc/pipe.rs)) |

本体側にあった「リモートは設定の半分・最大 3 本」という remote 専用の割引は**撤去した**。
理由は速度ではなく**保守**で、session が排他である以上 (plan §2.2、リモートが操作権を
持つ間は本体の通常入力がロックされる)、割引が守ろうとしていたローカル表示 worker は
そもそも動いていない。設定値と実際の並列数が一致するほうが後で嘘をつかない。

**結論: 供給は 8192 で約 1 ページ/秒が上限で、並列数では動かない。仕事を前倒しする
以外に打つ手がない** (= 本体側の投機的準備)。

### 1 ページ 1784ms の全内訳 (2026-08-13、46.5 MP、同一ログ)

| 部分 | ms | 割合 | 判定 |
|---|---|---|---|
| PDFium の描画 | 507 | 28% | **画素数に固有**。減らすには解像度を下げるしかない |
| **受け取り後、`source` 段の中** | **458** | **26%** | **未解明。コピー 2〜3 回分に相当** |
| compose | 284 | 16% | **未解明**。注釈も補正も無いページで何をしているのか |
| JPEG エンコード | 155 | 9% | 妥当 |
| ワーカーの RGBA 組立 | 100 | 6% | 妥当 |
| パイプ転送 (書き + 読み) | 138 | 8% | **問題なし** (186 MB / 1.36 GB/s、syscall 往復 4 回) |
| 縮小 | 64 | 4% | 妥当 |

**測って否定できたもの** (どれも「遅そうに見えた」だけ):

| 疑ったもの | 実測 | |
|---|---|---|
| PDFium が並列化していない | 同時 4 本で劣化なし (880 / 926 / 833ms) | 無実 |
| メモリ帯域の飽和 | JPEG・縮小は同時本数で完全に平ら | 無実 |
| `LineWriter` が改行ごとに flush | 書き込み 2 回 / flush 1 回 | 無実 |
| JSON に画像を入れる費用 | 5.34 → 19.07 MiB (3.6 倍)、encode 30 + decode 32ms | 62ms のみ |
| 「説明できない 530ms」 | **別セッション同士を比べた誤り**。同一セッションでは
`ipc_ms` 1861ms と計装合計 1869ms が一致 | 存在しない |

> ⚠ **異なるセッションの数字を並べて差を論じない。**この一連で 2 回踏んだ。
> 比較は必ず同一ログ・同一区間で行う。

**PDF サムネイルが温まらない** (同一文書を 32 枚連続で描いても p50 147ms のまま)。
描画時間は **約 160ms の固定費 + 7.9 ms/MP** で、0.1 MP のサムネイルはほぼ全部が固定費。
原因の候補が 2 つあり**打ち手が正反対**なので、確定するまで直さない:

1. `load_pdf_from_file` を要求ごとに呼んでいる ([pdf_loader.rs](../../src/pdf_loader.rs)) →
   文書をキャッシュすれば消える
2. スキャン PDF の埋め込み画像を毎回展開している → **文書キャッシュでは消えない**

**他の IPC 経路の棚卸し** (2026-08-13): Susie 32bit worker は PDF と同じ作り
(生 BGRA を stdin/stdout の `[4B len][payload]`) なので、**転送側に手を入れるなら共通の候補**。
VST3 bridge は**既に共有メモリ** (272B ヘッダ + f32 リング) で正しい形。本体 ↔ remote-web は
named pipe の `[4B len][JSON]` で、画像バイトも JSON 内 (3.6 倍に膨らむが実測 62ms)。
動画は圧縮済みセグメントなので優先度低。

### 利用者から出た設計案 (未着手)

**本体側のレンダリングと、端末への転送を別の資源として扱う。**遅い回線では同時転送を
減らして近いページを先に届けたい、本体側は増やしたい、と要求が逆を向いているのに、
今は 1 つの上限で束ねている。

- 符号化済みバイトの置き場を**リモートサービス側**に持つ (本体はパイプで渡し切る。
  ローカルなので速く、本体に新しいキャッシュの寿命管理を足さずに済む)
- 上限を「本体に同時に描かせる数」と「端末へ同時に流す数」に分ける
- クライアントが「用意して」と「送って」を分けて伝える

**部品は既にある**: `PagePriority::Foreground / Prefetch`、`PageDemand` の
`promote` / `release`、世代・補正・セッションを含んだキャッシュキー。新規は在庫と
上限 1 つとクライアントの言い分け。**書き直しではなく中くらいの増分。**

**効かない場面**: 飛んだ直後の 1 ページ目は何も用意されていないので変わらない。
読む速度が本体の生成速度を超えれば、やはり追いつかない。

## 直近で学んだこと

- **カタログの `source_*` を編集座標の基準に使わない。** master が PDF で意味を変え
  (raster px → 1/1000 ポイント)、青一色になった。基準は**ページ固有で要求解像度に依存しない
  値**でなければならない。不変条件「保存済みトリムは要求解像度が変わっても同じ割合を切り出す」
  をテストに置いた
- **本体の挙動を先に確認してから合わせる。** vector PDF を描画失敗にしたが、本体は失敗しない
  (ズーム依存のラスタへ適用する) ので、リモートだけ読めなくなるところだった
- `fetch_ms` は `waitForDisplay` の待ち時間で、体感は `tap_to_display_ms`。取り違えて
  「取得済みなのに待たされている」と誤読した
- **高画質のページ送りが待たされる原因はデコードだけである** (2026-08-12 の端末ログ、
  8192 で先読みが間に合った 17 表示グループ)。`tap_to_display_ms` 中央値 287ms に対し
  `decode_ms` 中央値 271ms で、**差は 16〜30ms**。17/17 がスピナーのしきい値 225ms を
  超えていた。先読み外しは 2464〜3814ms、標準 4096 の `decode_ms` は 94ms。
  **先読み自体は効いている**ので、残りはデコードを前倒しできるかどうかに尽きる

## 作業の進め方 (この一連で確立したもの)

## 段階 3 に持ち越した宿題 (段階 2 で判明)

- **1 worker の環境で実行不能な先読みに誰が応答するか。** 予約が `workers - 1` なので
  worker 1 本では先読みが pop されない。今は入口が即 503 を返すが、入口を外すと client の
  timeout まで queue に残る
- **prefetch の `start` に display request ID が無い。** 段階 1 の coordinator は計画由来の
  start に `requestId` を載せない。registry は必須にしているので、wire に載せる identity を
  段階 3 で決める
- 昇格した `Work` は `PageRequest.priority` が Prefetch のまま。pop 時に registry の実効優先度で
  解決するか、render 前に書き換える
- 剪定・拒否・shutdown で捨てる `Work` には typed な応答を返す (`SessionOperation` を drop
  しても client には返らない)
- registry の cancel token と `SessionOperation::cancel_flag()` は別物。render から見える
  取消源を 1 つにするか、明示的な合成点を作る
- `QueueMetrics` と新 queue の二重計上を避けつつ、既存ログの `queued` / `active` /
  `queue=heavy` を保つ

実機確認済み: 見開き切替、× で閉じる、拡大しない、連打でタップが抜けない、ドラッグ誤爆なし。
