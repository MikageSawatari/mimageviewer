## ページ供給の律速 (2026-08-12 実測、高画質 8192)

デコード先読み (`eaa7038d`) で**端末側の待ちは消えた**。先読みが間に合ったページは
`tap_to_display_ms` 中央値 **6ms** (2〜33)、`decode_ms` は **0**、19 グループすべてが
スピナーのしきい値 225ms を下回った (修正前は中央値 287ms で 17/17 が超過)。

残る待ちは**供給が追いつかないとき**だけになった。1 ページ (46.6 MP) の内訳:

| 区間 | 中央値 | 割合 |
|---|---|---|
| 本体のレンダリング + JPEG エンコード (`ipc_ms`) | **2281ms** | 71% |
| リモートサービス側 (枠待ち + 応答書き出し) | 536ms | 17% |
| 端末への転送 (約 5 MiB) | 約 370ms | 11% |
| 端末から見た合計 (`fetch_ms`) | 3240ms | |

**転送は 1 割強しかない。**待ちを作っているのは本体側の生成である。標準画質 (4096) は
11.6 MP なのでここが素直に縮む。「標準だと軽い」のはブラウザだけでなく本体側も
4 分の 1 になっていたため。

**並列数を上げても供給は増えない** (2026-08-12、3 層すべてを 3 にして実測)。46 MP の
ページで `ipc_ms` 中央値は同時 2 本で 2016ms、**同時 3 本で 2952ms**。供給に直すと
**0.99 → 1.02 ページ毎秒で、+2% しかない**。この機械は **2 本の時点で既に飽和**しており、
3 本目は増えた分をちょうど食い潰す。

> ⚠ **一度、間違った結論を出している。**同じ日の先行測定で「3 本なら 1.26 ページ毎秒
> (+27%)」と読んだが、その標本の「同時 3 本」は**先読み 2 本 + 表示要求 1 本**が偶然
> 重なったもので、先読みが 3 本競合している状態ではなかった。**優先度で分けて数えること。**

**上限は 3 段が直列に並んでいて、1 つ動かしても効かない。**最初に remote-web の
`MAX_CONCURRENT_PAGE_PREFETCH` だけ上げて commit したが実効は変わらず、戻した
(`aa145071`)。その後 3 層まとめて 3 にした (`daf58505`)。

| 層 | 定数 |
|---|---|
| 端末 | `PAGE_PREFETCH_CONCURRENCY` ([app.js](../../crates/remote-web/web/app.js)) |
| リモートサービス | `MAX_CONCURRENT_PAGE_PREFETCH` ([http.rs](../../crates/remote-web/src/http.rs)) |
| 本体 | `worker_count - 1` ([heavy_queue.rs](../../src/remote_ipc/heavy_queue.rs))、`remote_heavy_worker_count` ([pipe.rs](../../src/remote_ipc/pipe.rs)) |

本体側にあった「リモートは設定の半分・最大 3 本」という remote 専用の割引は**撤去した**。
理由は速度ではなく**保守**で、session が排他である以上 (plan §2.2、リモートが操作権を
持つ間は本体の通常入力がロックされる)、割引が守ろうとしていたローカル表示 worker は
そもそも動いていない。設定値と実際の並列数が一致するほうが後で嘘をつかない。

**結論: 供給は 8192 で約 1 ページ/秒が上限で、並列数では動かない。仕事を前倒しする
以外に打つ手がない** (= 本体側の投機的準備)。

| 疑ったもの | 実測 | |

| 「説明できない 530ms」 | **別セッション同士を比べた誤り**。同一セッションでは
`ipc_ms` 1861ms と計装合計 1869ms が一致 | 存在しない |

> ⚠ **異なるセッションの数字を並べて差を論じない。**この一連で 2 回踏んだ。
> 比較は必ず同一ログ・同一区間で行う。

**PDF サムネイルが温まらない** (同一文書を 32 枚連続で描いても p50 147ms のまま)。
描画時間は **約 160ms の固定費 + 7.9 ms/MP** で、0.1 MP のサムネイルはほぼ全部が固定費。
原因の候補が 2 つあり**打ち手が正反対**なので、確定するまで直さない:

1. `load_pdf_from_file` を要求ごとに呼んでいる ([pdf_loader.rs](../../src/pdf_loader.rs)) →
   文書をキャッシュすれば消える
2. スキャン PDF の埋め込み画像を毎回展開している → **文書キャッシュでは消えない**

**他の IPC 経路の棚卸し** (2026-08-13): Susie 32bit worker は PDF と同じ作り
(生 BGRA を stdin/stdout の `[4B len][payload]`) なので、**転送側に手を入れるなら共通の候補**。
VST3 bridge は**既に共有メモリ** (272B ヘッダ + f32 リング) で正しい形。本体 ↔ remote-web は
named pipe の `[4B len][JSON]` で、画像バイトも JSON 内 (3.6 倍に膨らむが実測 62ms)。
動画は圧縮済みセグメントなので優先度低。

### 利用者から出た設計案 (未着手)

**本体側のレンダリングと、端末への転送を別の資源として扱う。**遅い回線では同時転送を
減らして近いページを先に届けたい、本体側は増やしたい、と要求が逆を向いているのに、
今は 1 つの上限で束ねている。

- 符号化済みバイトの置き場を**リモートサービス側**に持つ (本体はパイプで渡し切る。
  ローカルなので速く、本体に新しいキャッシュの寿命管理を足さずに済む)
- 上限を「本体に同時に描かせる数」と「端末へ同時に流す数」に分ける
- クライアントが「用意して」と「送って」を分けて伝える

**部品は既にある**: `PagePriority::Foreground / Prefetch`、`PageDemand` の
`promote` / `release`、世代・補正・セッションを含んだキャッシュキー。新規は在庫と
上限 1 つとクライアントの言い分け。**書き直しではなく中くらいの増分。**

**効かない場面**: 飛んだ直後の 1 ページ目は何も用意されていないので変わらない。
読む速度が本体の生成速度を超えれば、やはり追いつかない。

## 直近で学んだこと

- **カタログの `source_*` を編集座標の基準に使わない。** master が PDF で意味を変え
  (raster px → 1/1000 ポイント)、青一色になった。基準は**ページ固有で要求解像度に依存しない
  値**でなければならない。不変条件「保存済みトリムは要求解像度が変わっても同じ割合を切り出す」
  をテストに置いた
- **本体の挙動を先に確認してから合わせる。** vector PDF を描画失敗にしたが、本体は失敗しない
  (ズーム依存のラスタへ適用する) ので、リモートだけ読めなくなるところだった
- `fetch_ms` は `waitForDisplay` の待ち時間で、体感は `tap_to_display_ms`。取り違えて
  「取得済みなのに待たされている」と誤読した
- **高画質のページ送りが待たされる原因はデコードだけである** (2026-08-12 の端末ログ、
  8192 で先読みが間に合った 17 表示グループ)。`tap_to_display_ms` 中央値 287ms に対し
  `decode_ms` 中央値 271ms で、**差は 16〜30ms**。17/17 がスピナーのしきい値 225ms を
  超えていた。先読み外しは 2464〜3814ms、標準 4096 の `decode_ms` は 94ms。
  **先読み自体は効いている**ので、残りはデコードを前倒しできるかどうかに尽きる

## 段階 3 に持ち越した宿題 (段階 2 で判明)

- **1 worker の環境で実行不能な先読みに誰が応答するか。** 予約が `workers - 1` なので
  worker 1 本では先読みが pop されない。今は入口が即 503 を返すが、入口を外すと client の
  timeout まで queue に残る
- **prefetch の `start` に display request ID が無い。** 段階 1 の coordinator は計画由来の
  start に `requestId` を載せない。registry は必須にしているので、wire に載せる identity を
  段階 3 で決める
- 昇格した `Work` は `PageRequest.priority` が Prefetch のまま。pop 時に registry の実効優先度で
  解決するか、render 前に書き換える
- 剪定・拒否・shutdown で捨てる `Work` には typed な応答を返す (`SessionOperation` を drop
  しても client には返らない)
- registry の cancel token と `SessionOperation::cancel_flag()` は別物。render から見える
  取消源を 1 つにするか、明示的な合成点を作る
- `QueueMetrics` と新 queue の二重計上を避けつつ、既存ログの `queued` / `active` /
  `queue=heavy` を保つ

実機確認済み: 見開き切替、× で閉じる、拡大しない、連打でタップが抜けない、ドラッグ誤爆なし。
