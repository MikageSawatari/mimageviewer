## 1. なぜ必要か

段 3b で AI アップスケールがスマホから使えるようになったが、**利用者が実機で
「解像度の差がほとんど分からない」**と報告した。原因は知覚ではなく構造:

- スマホは `cssWidth × devicePixelRatio` (実測 ≒1200px) でページを要求する
  ([command-core.mjs:436](../../crates/remote-web/web/command-core.mjs) `requestWidth`)
- AI は原寸に走るので 2048px → 8192px になるが、**送る前に 1200px へ縮小**される
- ピンチ拡大は届いた 1200px の CSS 変形だけで、高解像度を要求し直さない

本体は AI 後のテクスチャを高解像度のまま持つので拡大すると細部が出る。
**ここが PC とスマホの差**であり、段 3 の価値がここで決まる。

これは段 3b が壊したものではなく、元からの viewer の解像度方針。AI で顕在化した。

## 2. 確認済みの数字

| | 値 | 出所 |
| --- | --- | --- |
| ズーム上限 | **6×** | `reduceViewerTransform` の `Math.min(6, ...)` |
| AI 適用の入力上限 (既定) | 2048 | `default_ai_upscale_skip_px()` |
| AI 出力上限 | **8192** | 4 倍 → `MAX_TEXTURE_DIM` |
| ページ描画上限 | **8192** | `PDF_RENDER_MAX_LONG_PX` |

6× に必要な 1200 × 6 = 7200px は 8192 の内側に収まる。

転送量の実測 (WebP q=90 = `PAGE_WEBP_QUALITY`、細部のある実写):
1200px = 0.12 MB / 4800px = 1.67 MB / 8192px = **4.73 MB**。
縦長のページ状素材の 8192px は 1.5 MB。Wi-Fi なら 1 秒未満。

**再推論は走らない見込み。** `RemoteAiNativeCacheKey` ([container.rs:105](../../src/remote_ipc/container.rs))
に `target_px` が無いので、同じページの別サイズは原寸 AI 結果の縮小と encode だけになる。
**これが本当にそうかを確認してほしい。** 前提が崩れると設計が変わる。

## 3. 設計判断 (決定済み)

### 3.1 段階は粗く

利用者の希望。細かく刻むと再取得が増え、サーバ側の縮小 + encode も毎回走る。

**2 段を既定とする**: `fit` (現状) と `zoomed` (取れる上限)。
上限まで取っても数 MB で済む実測があるので、中間段を置く利点が小さい。

3 段以上が要ると判断したら、**理由と一緒に提案してほしい** (例: 実測で 8192 の
縮小 + encode が無視できない時間を食う場合)。

### 3.2 上限は「実際にある画素」でクランプ

要求長辺 = min(8192, `fit幅 × 6`, **その画像で実際に得られる画素数**)。

3 つ目が重要。原寸 1500px の画像に 8192px を要求しても、無い情報は増えない。
`encode_thumb_webp` は `resize_dynamic_fit` を通るので、**source より大きい box を
渡したときに拡大するのか、それとも source 止まりなのかを確認してほしい。**
拡大するなら、無駄な bytes を送らないよう client 側で必ずクランプする。

client が「実際に得られる画素数」を知る方法も調べて報告してほしい。
page 応答が持つ `width` / `height` で足りるのか、AI 後の寸法を別途返す必要があるか。

### 3.3 取得のタイミング

- **ピンチ中は要求しない。** 現在の画像を引き伸ばして即応する
- **ズームが落ち着いてから**要求する
- 等倍へ戻したときに小さい方へ**戻さない**。持っている高解像度を捨てない

### 3.4 AI 版を取ること ⚠

高解像度で欲しいのは **AI 適用後**の絵であり、`/api/page` の非 AI 版ではない。

現在の作りでは AI 結果は job が持つ。`remoteAiGroupHash` は `target_px` を含むので、
別 target の要求は新しい group 扱いになり、旧 job は `Superseded`、新 job は
native cache に当たって finalize だけ走る — という理解でいる。

**この理解が正しいかを確認してほしい。** 違うなら、job を作り直すのか
result GET に寸法を持たせるのかを、既存の 10 分保持と terminal identity を
壊さない形で判断し、根拠と一緒に提案してほしい。

`/api/page` の非 AI 版も同じ高解像度で先に出すかは、§2.1 の
「AI を待たずに出して原子的に差し替える」規則との整合で判断してほしい。

### 3.5 AI 無しでも効く

この変更は AI を使っていないページにも効く (細かい原稿を拡大したときにぼやけない)。
**AI 有効時だけの分岐にしない。**
