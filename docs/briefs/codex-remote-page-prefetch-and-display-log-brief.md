## 0. 前提 — 画像を小さくしない

**ページの要求解像度を下げる方向は採らない。** 漫画はよくズームするため、画面ぴったりの
解像度にすると拡大時に品質が落ちる。利用者の明示の判断 (2026-08-09)。

`imageQualityPreset` の値、`PAGE_JPEG_QUALITY`、`viewerImageLayout` の要求幅の決め方は
**変更しないこと**。改善は先読みを実効化する側で行う。

## 1. 観測された症状

利用者報告 (実機 iPad):

1. ページを捲ると中央にインジケータが出て待たされることが多い
2. 1 ページから 2, 3 ページへ移動したのに、画面が 1 ページ目のまま変わらなかった。
   **シークバーのページ数は更新されていた**。再現せず

## 2. 調査済みの事実 (再調査不要)

### 2.1 キャッシュの予算が実測と合っていない

[app.js](../../crates/remote-web/web/app.js) の定数と、その上のコメント:

    // 標準画質の実測約 1.2 MiB/ページなら、進行方向 3 ページで従来と同じ約 3.6 MiB。
    const PAGE_PREFETCH_AHEAD = 3;
    const PAGE_PREFETCH_BEHIND = 1;
    const PAGE_RESOURCE_CACHE_LIMIT = 12;
    const PAGE_RESOURCE_CACHE_MAX_BYTES = 32 * 1024 * 1024;

予算は **1.2 MiB/ページ**を前提に決まっている。実測は p50 1.5 MB、p95 7.9 MB。
先読み窓は現在 + 前 1 + 先 3 = **5 ページ**なので、p95 では約 39 MB 必要になり
**32 MB の予算に入らない**。つまり先読みしたページを、使う前に自分で捨てている。

同じ形の不具合が過去にある (`docs/final-composite-budget-thrash-plan.md` の
予算超過 → evict → 再計算ループ)。**予算が作業集合より小さいと、先読みは逆効果になる。**

### 2.2 先読みは直列で、サーバの枠も 1

- クライアント側: 先読みは 1 件ずつ直列。foreground が来ると `abort` する
- サーバ側: `ipc_prefetch_limit: 1`

1 ページ 0.6〜2.4 秒なので、3 ページ先まで埋めるのに **2〜7 秒**かかる。
利用者がそれより速く捲ると、先読みは永久に追いつかない。

### 2.3 503 が 1 回来ると先読み計画が全部消える

    .catch((error) => {
      if (error?.status === 503) this.pending = [];
    })

直近ログで **350 件**の `admission_busy` 503 が出ている。1 件でも来ると pending 全消去で、
次にページを捲るまで先読みが再開しない。**待たされる主因はここの可能性が高い。**

### 2.4 表示結果がログに残っていない

`command` テレメトリは `next_page` が発火した記録は残すが、**その結果どのページが
表示されたかを持たない** (`outcome` が空)。症状 2 はログから追跡できない。

`HTTP 428` も調べたが、全て `/api/thumb` のセッション取得前で無関係だった。

## 3. やること

### 3.1 先読みを実効化する (症状 1)

順に効果を確かめられるよう、**独立した変更として入れること**。

- **予算を実測に合わせる。** `PAGE_RESOURCE_CACHE_MAX_BYTES` が先読み窓
  (現在 + `BEHIND` + `AHEAD`) を保持できない状態を作らない。固定値を大きくするのか、
  実測サイズから窓を決めるのか、窓を保持できる下限を予算に課すのかは選んでよいが、
  **「予算 < 作業集合」が起き得ない構造にすること**。コメントの前提値も実測へ更新する
- **503 で pending を全消去しない。** admission_busy は一時的な混雑であって、計画が
  無効になったわけではない。既存の再試行判定 (`thumbnailRetryDecision` が
  `ipc_busy` を予算消費なしで再試行する) と同じ考え方に揃える
- **先読みの同時実行数を見直す。** クライアントの直列制約とサーバの
  `ipc_prefetch_limit: 1` は対で効いている。片方だけ上げても意味が無い。上げる場合は、
  foreground のページ要求が先読みに待たされないことを担保すること (現在は abort で
  担保している。この保証を壊さない)

### 3.2 表示履歴を記録する (症状 2)

利用者提案: シークバーのページ数表示と、画面上の画像表示を時刻付きで記録し、履歴を
サーバへ送る。

**症状 2 は「シークバーは進んだが画像が変わらなかった」ので、入力でも取得でもなく
表示側の問題と分かっている。** その境界を跨ぐ記録にすること。

- ページ送りの結果として、**要求したページ番号・シークバーに出したページ番号・実際に
  画面へ適用した画像の識別子**を、時刻とともに残す
- 適用しなかった場合は**その理由**を残す (世代不一致 / revision 不一致 / セッション不一致 /
  キャッシュミス / abort など、既存の判定名をそのまま使う)
- 既存のテレメトリ送信に載せる。新しい送信経路を作らない
- **秘密情報を載せない** (PIN / Bearer / セッション ID の生値)。既存の相関ハッシュを使う
- パスを載せない (既存方針。ログにはページ番号と識別子だけ)

**この増分では症状 2 を直さない。** 原因が特定できていないので、guard / retry / 追加
repaint を入れない。観測できるようにするところまで。

## 4. やってはいけないこと

- ページの要求解像度・画質プリセット・JPEG 品質を下げること (§0)
- 予算超過を「先読み窓を狭める」だけで回避すること (症状が変わるだけで、待ち時間は減らない)
- 症状 2 に対して原因不明のまま guard / retry / 追加 repaint を入れること
- foreground のページ要求が先読みに待たされる構造にすること
- テレメトリに秘密情報・パスを載せること

## 5. テスト

- 先読み窓が予算に収まらない設定を作れないこと (予算と窓の関係を純関数で固定する)
- 503 を受けても pending が残ること
- foreground 要求が先読みより優先されること
- 表示履歴が、適用した場合と適用しなかった場合の両方を理由付きで残すこと
- 履歴に秘密情報とパスが含まれないこと (既存の redaction テストと同じ形で)
