### なぜ共有が間に合わないか

**組の 2 つの要求が同時に来ていない。**同時受け付け数の都合で、`#3` と `#4` は別々の

だから自分で描く。そして `j239` が描き終えた raster を、後から来た `j240` が
受け取っている — **順番が逆**になっている。

同時に届いた組 (`#1`,`#2`) では共有が効いて両方安い。つまり**機構は正しく、
起動の順番だけが問題**。

## 決定: 相手の解決を、自分のページのデコードと同時に始める

`page_inner` ([container.rs](../../src/remote_ipc/container.rs) の 3327 行付近) では、
`view_trim_plan` が **`load_image_timed` を呼ぶ前に**確定している。相手ページは
その時点で分かっている。

- **plan が `AutoSpread` なら、そこで相手の bbox 解決を開始する** (待たない)。
- 続けて今までどおり自分のページを `load_image_timed` でデコードする。
- `Trim` 段で相手の結果を回収する。**自分の source が終わる頃には相手も終わっている**ので、
  `trim` 段はほぼ 0 になる。

相手の要求が後から届いても、single-flight が join / 受け渡しで拾うので**デコード回数は
増えない**。組で 2 回のまま、2 回が並列に走るようになるだけ。

期待値: 要求した側 2330ms → **約 1400ms**。

### 実装の形

**`std::thread::scope` を使うこと。** `&self` をそのまま借りられるので
`Arc<ContainerEngine>` を `page_inner` まで通す配管が要らない。scope の終わりで必ず
join されるので、スレッドが取り残されない。

```
scope の中で:
  1. plan が AutoSpread かつ相手の bbox が未キャッシュなら、相手解決を spawn
  2. 自分のページを load_image_timed (今までどおり)
  3. Trim 段で spawn した結果を join して harmonize
```

**先に相手のキャッシュを見て、当たっていれば spawn しない。**温まった状態
(実測では 2 周目以降) で無駄なスレッドを作らない。

### キャンセル

- spawn した側には**専用の participant token** を渡す。ジョブ本体の token をそのまま
  渡さない。
- **自分のページが早期に失敗した場合は、その専用 token を立ててから scope を抜ける。**
  立てないと、要らなくなった相手の解決を join で待つことになる。
- 専用 token を立てても、**相手自身の要求が参加者として残っていれば共有デコードは続く**
  (`a58d410d` の参加者数の仕組みがそのまま効く)。ここは新しく作らない。

## テスト

1. **`AutoSpread` では、自分のページの source が終わる前に相手の解決が始まっている**
   (開始順序を観測できる形にする)。
2. **`AutoSingle` / `Stored` では相手の解決を始めない**。
3. **相手の bbox が既にキャッシュにあれば、スレッドもデコードも起こさない**。
4. **自分のページが失敗しても scope を抜けられる** (相手の解決を待ち続けない)。
5. **専用 token を立てても、相手自身の要求が参加者として残っていればデコードは完走する**。
6. **調停後の bbox が今までと同一**。同じ入力で `a58d410d` と同じ矩形を返す
   (見た目が変わらないことの根拠)。

1・4・6 は今回の肝なので、**実装を潰したときに落ちることを自分で確かめてから**報告すること
(例: 相手の解決を今までどおり Trim 段まで遅らせる / 失敗時に token を立てない /
harmonize の左右を入れ替える)。

`page_inner` を丸ごと呼ぶテストにしない。**開始順序と回収を判定できる最小の形に切り出して**
テストする。
