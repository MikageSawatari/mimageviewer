# リモートのページ生成が、どの段で時間を使っているかを測れるようにする

作業ツリー: `C:\home\mimageviewer-web` (branch `web-remote`)。`29b3b632` の続き。
**これは計測を入れる作業で、速度を変える修正ではない。**

## 0. 前提 — 先に読むもの

- `src/remote_ipc/container.rs` — `page_inner` (2091 行付近)、`load_image` (3435 行付近)。
  **この経路には `perf::event` が 1 つも無い** (grep で 0 件)
- `src/pdf_loader.rs` — `pool_send` / `pool_recv` / `pool_dispatch` の既存イベント。
  **書き方の手本はここにある** (`rtt_ms`、`busy`、`total`、`wait_ms` の持たせ方)
- `src/perf.rs` — `perf::event` の API
- `scripts/analyze_perf.py` — 既存の集計スクリプト
- [`docs/ui-responsiveness.md`](../ui-responsiveness.md) — 計装の方針

## 1. 実測で分かっていること (再調査不要)

高画質 8192、46.6 MP のページ 1 枚:

| 区間 | 中央値 | 出どころ |
|---|---|---|
| リモートから見た本体の処理 (`ipc_ms`) | **2398ms** | remote-web の診断ログ |
| うち PDFium のレンダリング (`rtt_ms`) | **881ms** | perf log の `pool_send` / `pool_recv` |
| ワーカーの空き待ち | 0.1ms (中央値) | `pool_dispatch` の `wait_ms` |
| **残り = 本体内の後処理** | **約 1517ms (63%)** | **計測が無い** |

**PDFium は並列で劣化していない。**他が 0 / 1 / 2 本走っている時の `rtt_ms` は
880 / 926 / 833ms で、同時 4 本の場面も 129 回あった。プールは正しく並列に動いている。

一方**リモート全体は並列にすると劣化する**。先読みを同時 2 本から 3 本にしたとき、
1 本あたり 2016 → 2952ms に伸び、供給は 0.99 → 1.02 ページ毎秒 (+2%) しか増えなかった。
**24 コアの機械で、である。**

つまり **PDFium から返った後の 1517ms のどこかが、並列に効いていない。**
46 MP のラスタは RGBA で **186 MB** あり、3 本同時なら 560 MB の生バッファを何度も
舐めることになる。**lock による直列化なのか、メモリ帯域の飽和なのかを、まだ区別できない。**

## 2. 決定

**`ipc_ms` の内訳を段ごとに出す。**速度を変える修正はこの増分では行わない。

区別したいのは次の 2 つである。**これが分かる形で計測すること。**

- **待たされている** (lock を取れずに開始が遅れる) → 直列化。外せる可能性がある
- **走ってはいるが遅い** (開始は早いが処理自体が伸びる) → 帯域か CPU の飽和。
  並列度では解決しない

## 3. 変更内容

### 3.1 段ごとの時間

`page_inner` から応答を返すまでを段に分けて `perf::event` を出す。少なくとも次を分ける
(実際の経路に合わせて増減してよいが、**理由を報告すること**)。

- 解決・DB 参照 (`resolve`、view trim plan、spread / rotation / 補正の読み出し)
- **元画像の取得** (PDF なら pool 経由、画像なら decode)。ここは既存の `rtt_ms` と
  突き合わせられる値にする
- 合成 (コミック注釈・補正・トリム)
- 縮小
- **JPEG エンコード**
- 合計

各イベントに **画素数**と**扱っているバイト数**を持たせる。段の重さを画素あたりで
比較できるようにするため。

### 3.2 その段に何本入っていたか

各段について、**その時点で同じ段に入っている他のリモートページ生成の本数**を記録する。
`pool_send` の `busy` / `total` と同じ考え方である。

これが §2 の区別に必要な情報である。段の所要時間が本数に比例して伸びるなら競合、
本数によらず一定なら競合していない。

### 3.3 待ち時間を分けて出す

lock を取る箇所があるなら、**取得までの待ち時間**を所要時間と別に出す。
`pool_dispatch` の `wait_ms` と同じ形。**待ちが 0 に近いのに遅いのか、待たされているのかで
結論が変わる。**

### 3.4 集計

`scripts/analyze_perf.py` に、この経路を読むサブコマンドを足す。出すもの:

- 段ごとの所要時間 (中央値 / p90)、画素あたりの時間
- **同時本数ごとの段の所要時間** (§3.2 の値で層別)
- 待ち時間 (§3.3)

## 4. 触らないもの

- **速度を変える修正はこの増分では入れない。**遅い段が見つかっても直さない。
  測ってから決める
- PDF pool、`rtt_ms` などの既存イベント (**手本として読むだけ**)
- 並列数の 3 つの上限、画質プリセット、デコード先読み、表示所有権
- protocol、remote-web (`crates/`)。**本体の `src/` だけで完結させる**
