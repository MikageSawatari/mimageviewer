## 1. 件 A: 再読込後に再生が始まらない = 自動再生の拒否

**前回足してもらった計装が原因を一撃で特定した。ありがとう。**

利用者の報告:

> リモートの画面内で再読み込みをしても、動画の再生が始まりませんでした。
> iOS で 1 回終了させたところ、動いてそうです。

記録:

| 時刻 | attempt | reject | 理由 | success | 状態 |
| --- | --- | --- | --- | --- | --- |
| 00:52:29 | 3 | **3** | **NotAllowedError** | 0 | paused / 位置 0 / rs 4 |
| 00:53:17 以降 | 5 | 0 | — | 5 | 再生中 (1.2 → 11.2 → 21.2 → 31.2) |

**ブラウザの自動再生ポリシー。** 再読込後は user activation が無いので `play()` が拒否される。
アプリを再起動して利用者がタップしたら成功した。データは届いていた (rs=4 / 先読み 24 秒)。

### 問題は、拒否のあとに出る表示

同じ記録で、この状態のまま停止監視が動いていた:

```
00:52:41  waiting_threshold   paused=true  t=0  rs=4   → 「通信待ちが 3 秒続いています」
00:52:53  stall_terminal      paused=true  t=0  rs=4   → 「再生が停止しました。現在位置から再接続できます。」
```

**どちらも状況に合っていない。** 通信は正常で、再接続しても直らない。
必要なのは**利用者のタップ**だけ。

`cd925dba` で 3 秒警告は判定を通るようにしたが、`playRequested` は true のままなので
`cancel` にはならない。**自動再生拒否は「再生する意図はあるが、ブラウザが許していない」**
という第 3 の状態で、停止でも通常再生でもない。

### やってほしいこと

`play()` が `NotAllowedError` で拒否されたとき、**待機・停止の表示ではなく、
タップで再生できることを示す表示にする。**

- 文言・見た目は判断してよい。既存の通知機構に載せるか別 UI にするかも含めて
- **タップ 1 回で再生が始まること**が要件。案内を読んでから別の場所を探させない
- `NotAllowedError` 以外の拒否 (`AbortError` 等) を同じ扱いにしないこと。
  中身を確認して、拒否理由ごとに妥当な扱いを判断してほしい
- 自動で `play()` を繰り返さない。ポリシー上通らないので無駄で、記録も汚す

**停止監視は、自動再生が拒否されている間は動かすべきではない**と私は考えるが、
そこが正しい境界かは判断してほしい。

## 2. 件 B: 一時停止が「再生状態を変更できませんでした」で失敗する

利用者の報告:

> タップして一時停止しようとしたら、**再生状態を変更できませんでした**のエラーが出ました。
> **次の動画に移動して同じことをすると、今度はちゃんと一時停止し**、通知も出ませんでした。

### 記録 (サーバ側)

```
00:54:00〜00:54:19  /stream/9/1/*.m4s  /api/video/state  すべて 200
00:54:09.493  422  POST /api/video/control
00:54:11.773  422  POST /api/video/control
```

**制御だけが 422。ストリーム配信は前後とも正常に続いている。**

### 私がソースで追ったところ

- 422 は `VideoStreamErrorCode::Failed`
  ([http.rs:1674](../../crates/remote-web/src/http.rs))
- Pause で `Failed` になる経路は 1 つだけ:
  `streaming.session.set_playing(false)` が false を返し
  `"remote session ownership was lost"` になる
  ([ui.rs:1260](../../src/remote_ipc/ui.rs))
- その false は `set_streaming_playing` から来る。false になる条件は
  ①`active` が無い ②**session generation 不一致** ③`streaming` が None
  ④**registration_id 不一致** のいずれか
  ([session.rs:425](../../src/remote_ipc/session.rs))
- `session` id 自体は一致している。**不一致なら `SessionMismatch` (409) になるはずで、
  観測は 422 だった** ([ui.rs:1246](../../src/remote_ipc/ui.rs))

**私の仮説は 1 つ潰した。** 「古いストリームの解除が新しい登録を消す」と考えたが、
`unregister_streaming` は `streaming.id == registration_id` で守られており、
古い id の解除は新しい登録を消さない ([session.rs:463](../../src/remote_ipc/session.rs))。
**この仮説は成立しない。**

**どの条件で false になったのかは特定できていない。調べて報告してほしい。**

### もう 1 つ、分類そのものを見てほしい

仮に本当に ownership が失われていたのなら、**それはセッションの問題**であって
機能の失敗ではない。今は `Failed` → 422 → 「再生状態を変更できませんでした」という
**一時的な機能エラー**として出ており、その間も再生は続いている。

- 本当に ownership を失ったなら、既存の切断・再接続の経路へ行くべきではないか
- そうでないなら、`Failed` (= 422) という分類自体が間違っているのではないか

**どちらなのか判断して報告してほしい。** 分類が違うだけなら直し、
本当に失っているなら、なぜ配信は続いているのかも含めて説明してほしい。

**再現条件も分かれば書いてほしい。** 利用者は「次の動画では直った」と言っている。
新しいストリームを開始した直後だけ起きるように見える。
