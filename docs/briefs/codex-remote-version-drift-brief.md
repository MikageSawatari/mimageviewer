## 1. なぜ要るか

## 3. 利用者の指摘で設計が変わった

> 配信中に配り直すことは、通常利用ではありえないケースではないでしょうか。
> mIV 本体を更新したら、本体は必ず終了し、次に接続したときに、
> リモートから本体への接続処理が再度実行されることになると思います。

**その通りだった。** 本体を更新するには本体を終了する必要があり、終了すればサービスも死ぬ。
**通常利用でセッション中にアセットが変わることはあり得ない。**
上のコメントが守っている「視聴中に画面が飛ぶ」は、**開発時にしか起きない**
(私がサービスを動かしたままファイルを編集する、まさに今の状況)。

そしてもっと強い論拠が出る。**版が変わった = 本体が再起動した = ストリームもセッションも
全部死んでいる。** 接続時点で保持すべきものが無いので、**リロードの代償がゼロ**。
画面位置もハッシュルーティングなので戻る。

**この推論が間違っていたら指摘してほしい。** 特に「版が変わったのに前のセッション状態が
生きている」経路があるなら、それは知りたい。

## 4. やってほしいこと

### (a) 版をテレメトリに載せる

**通常段。** 版番号は秘密ではなく、リリース後の調査でこそ効く。

端末が**自分の走っている版**を送る。サーバ側が**今なら配る版**と突き合わせられること。
食い違い自体が診断結果になる。

**どう持たせるかは判断してよい。** 全 event に付けると量が増えるので、
セッション単位で 1 度でよければそうしてほしい。**1 サンプルの大きさは抑えること。**

### (b) 接続時、版が古ければ自分で読み直す

セッションを取得した時点で照合し、走っている版が古ければ**そのままリロードする**。
バナーで選ばせない。§3 のとおり、この時点で失うものが無い。

**無限ループを防ぐこと。** リロードしても版が変わらなかった場合に繰り返してはならない。
「どの版のためにリロードしたか」を覚えて、**リロード後も古いままなら二度目は踏まず
バナーへ落とす**。アセットは `no-cache` なので通常は起きないが、経路上の中継が
古い応答を返す可能性は消せない。**スマホで無限リロードは実害が大きい。**

**バナー自体は残す。** 開発中は実際にアセットが動的に変わるので、そこでは意味がある。

判定は純関数に置いてほしい。既存の `appUpdateNotice()` を拡張するのか別に作るのかは
判断してよい。**呼び出し側に分岐を散らさないこと。**

## 5. 受け入れ条件

- 記録から「その端末がどの版で動いていたか」が分かる
- 走っている版と配信されている版の食い違いが記録から分かる
- 接続時に版が古ければ自動でリロードされ、**利用者の操作を要さない**
- **リロード後も古い場合、二度目のリロードをしない**。バナーへ落ちる
- 視聴中に配り直された場合 (開発時) は従来どおりバナー
- **通常段**に版が入る。PIN / Bearer token / 生の session ID はどの段にも出ない
- **回帰テスト**を付ける。ループ防止は純関数で固定できるはず
- web テストが緑。Rust を触るなら `cargo test -p mimageviewer --lib` も
