## 2. 実測 (私が測った。**実装前に本体の encoder で追試してほしい**)

同一素材、8192×4096 出力:

| 方式 | 時間 | サイズ |
| --- | --- | --- |
| WebP q90 method=4 (**現状**) | 3314 ms | 4.73 MB |
| WebP q90 method=0 | 892 ms | 6.38 MB |
| **JPEG q85** | **67 ms** | **4.62 MB** |
| JPEG q90 | 75 ms | 5.93 MB |

4096×2048 では WebP q90 method=4 が 844 ms / 1.23 MB、JPEG q85 が **15 ms / 1.21 MB**。

**JPEG q85 は現状 WebP と同じサイズを 1/50 の時間で出す。**
WebP が有利なのは小さい画像で、大きいページでは差が消える。
現状は「サムネイル向けの選択を大きいページへ流用していた」状態。

私の計測は PIL (libjpeg-turbo + libwebp)。**本体の `webp` クレートと `turbojpeg` で
追試し、q85 が現状 WebP q90 と同等サイズかを確認してほしい。**
違えば実測に合わせて quality を決め、根拠を報告してほしい。

## 3. やること

### 3.1 リモートのページ転送を JPEG へ

- **対象はリモートのページと AI 結果**。`/api/page` と
  `/api/ai/jobs/{id}/result` の両方
- **サムネイルは WebP のまま**。小さい画像では WebP が有利で、
  `catalog` のキャッシュ形式でもある
- encoder は `turbojpeg` (libjpeg-turbo、SIMD)。既にデコードで依存済み
- 透過は現状でも `encode_thumb_webp` の `to_rgb8()` で落としているので後退しない
- `Content-Type` が変わる。**全 consumer を洗ってほしい** (header、client の
  decode、cache、telemetry、テスト)

### 3.2 画質モード 4 段

動画の品質モードと同じ形にする。**既存の形に合わせること。**

| モード | 長辺 |
| --- | --- |
| 高品質 | 8192 |
| **標準 (既定)** | **4096** |
| 軽量 | 2048 |
| 最軽量 | 1024 |

**既定は標準。** 回線が遅いときの体感を優先し、標準でも拡大しなければ十分なため。

- `target_px` = min(モードの長辺, その画像で実際に得られる画素)。
  `resize_dynamic_fit` は拡大しないので、上限指定として渡すだけでよい
- 実行時の空き帯域や回線速度で**自動的に変えない**。設定だけで挙動が決まる
- 保存場所は動画品質モードに合わせる。**client 側 (端末ごと) か server 側かを
  既存実装から判断し、根拠と一緒に報告してほしい**
