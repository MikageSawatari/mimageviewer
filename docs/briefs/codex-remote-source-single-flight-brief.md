## 何が起きているか (実測、perf log から)

見開き + 自動トリムでページを開くと、**1 組につき片方のページが 2 回デコードされる**。
組の 2 つの要求がどう並ぶかで、2 通りの形で現れる。

```
組 (#1,#2) 同時開始:
  j165 #1  source 31.336→32.271 (935ms)   trim 32.419→33.640 (1221ms)
  j166 #2  source 31.334→32.413 (1079ms)  trim 32.643→32.674 (  31ms)

  j165 が #2 の bbox を要求したのは 32.419。j166 がそれを公開したのは約 32.45。
  30ms 早かっただけで、j165 は #2 を丸ごと描き直した (1221ms)。

組 (#3,#4) 逐次:
  j167 #3  source 31.334→32.426 (1092ms)  trim 32.670→33.731 (1061ms)
  j168 #4  source 33.919→34.998 (1079ms)  trim 35.126→35.164 (  38ms)

  j167 が #4 を丸ごと描き (1061ms)、bbox だけ取ってラスタを捨てた。
  その 200ms 後に j168 が同じ #4 を描き直した (1079ms)。
```

どちらも 2 ページに対して **3 回デコード**している。合計は 2378ms / 2480ms で、
組の相方 (1441ms / 1446ms) の 1.7 倍。104 ジョブ中 12 件がこの形。

## 本体にこれが無い理由

本体は見開きをペアでデコードしているのではなく、**両ページが `fs_cache` に載っていて
`cached_margin_bbox(idx)` がそれを読むだけ**
([ui_fullscreen.rs](../../src/ui_fullscreen.rs))。載っていなければ `None` を返して何もしない。
ペアなのは調停の計算だけで、要求でもデコードでもない。

**リモートに欠けているのは「ペアの要求」ではなく、デコード済みラスタの共有**。
リモートには補正後の `page_composite_cache` と bbox キャッシュはあるが、
**生ラスタを受け渡す場所が無い**ので、相手のラスタが手元に無いたびに描き直している。

## 決定: 生ラスタの single-flight + 1 件の受け渡しスロット

`load_image_timed` の `Source` 段 ([container.rs](../../src/remote_ipc/container.rs) の
`process_load_request` から channel drain までで `(color_image, decoded_source_dims)` を作る区間)
を、**デコード identity で共有する 1 つの機構**の後ろに置く。

- **entry はデコード開始時に作る** (状態 = 進行中)。同じ identity を要求した別ジョブは
  **待つ**。デコードは 1 回だけ走る。
- **完了したら、待っていた全員に `Arc<ColorImage>` を配る**。
- **配ったあと、ラスタを 1 件だけスロットに残す**。次に同じ identity を要求した者は
  デコードせずに受け取る。スロットは 1 件。別の identity が来たら置き換わる。

これで上の 2 パターンが両方消える。同時開始 (#1,#2) は進行中 entry への相乗りで、
逐次 (#3,#4) は受け渡しスロットで。

### identity に入れるもの

`crate::thumb_loader::LoadRequest` の組み立てに実際に効く値をすべて含める
(path / mtime / file_size / pdf_page / zip_entry / zip_dir_prefix / cache_key_override) に加えて:

- **`target_px`** — 解像度が違えば別のラスタ。共有してはいけない。
- **`full_page`** — `Thumbnail` は `skip_cache` も `cache_decision` も違う。共有してはいけない。

`AutoTrimReference` と `CompositedPageWithAutoTrim` は `full_page()` が同じ true で、
`request` の組み立てが完全に一致する (違うのは後段の合成有無だけ) ことを確認済み。
**この 2 つが共有できることが、この修正の全体**。

**identity を構成する値を取りこぼすと、別物のラスタを配ることになる。**
`LoadRequest` の各フィールドを 1 つずつ確認し、identity に含めないものは
「なぜ結果に影響しないか」をコード中のコメントに残すこと。

### 受け渡しスロットの大きさ

**1 件**。上限バイト数は設けない。

これはキャッシュではなく、**組の相方に渡すための受け渡し**なので、必要な件数は 1。
最高画質のページは 1 枚で 190MB 程度になるため、件数を増やすと素直に効いてくる。
1 件だけ、次の identity が来たら解放、で足りる。

### copy-on-write を許容する

スロットが強参照を持つ間、`execute_remote_edits` / `execute_remote_composite` が
`Arc` を一意に持てず、1 回コピーする可能性がある (190MB で 40ms 程度)。
**1000ms の描き直しを消すための取引として許容する。**

ただし**見えるようにする**こと: 実際にコピーが起きた場合が分かるよう、compose 段に
phase を足す (下の「計測」参照)。後で不要と分かれば外せる。

## キャンセルと所有権 (ここだけが新しい機構)

共有デコードは 1 つの cancel token で走る。参加者ごとの token をそのまま使うと、
先に諦めた参加者が、まだ待っている参加者のデコードを殺す。

- **共有 token は、参加者が全員いなくなったときだけ立てる**。参加者は entry に対する
  guard を持ち、guard の Drop で参加者数を減らし、0 になったら共有 token を立てる。
- **各参加者は自分の cancel token も見る**。自分が cancel されたら guard を落として
  `Busy` を返す。他の参加者が残っていればデコードは続く。
- **owner が失敗 / キャンセルで終わったら、entry を「壊れた」状態にする**。待っていた側は
  待ち続けず、**自分でデコードし直す**。タイムアウトで誤魔化さない。

### デッドロックしないことの根拠 (不変条件)

ジョブ A が「B のラスタ」を待ち、同時に B が「A のラスタ」を待つと循環する。
これは**起こり得ない**。理由:

**どのジョブも、自分のページのデコードを終えてからでないと、相手のページを要求しない。**
段の順序が `Source` → `Compose` → `Trim` で、相手ページの解決は `Trim` にある。
つまり待つ側は、その時点で進行中の entry を 1 つも所有していない。
待ちの辺は必ず「実際にデコード中の owner」へ向かい、owner は待たない。循環しない。

**この不変条件をコードで守ること**: 進行中 entry を所有したまま別の entry を待とうとしたら
`debug_assert!` で落とす。将来 `Trim` を `Source` より前へ動かす変更が入ったときに、
静かにデッドロックへ入らないようにする。理由をコメントに残す。

次の perf log でこの修正の効果と副作用が見えるようにする。

- `Source` 段の outcome に、デコードしたのか / 進行中に相乗りしたのか / スロットから
  受け取ったのかを入れる (例: `decoded` / `joined` / `handoff`)。
- 相乗りした場合の待ち時間を phase (`singleflight_wait_ms`) で残す。
- `Compose` 段に、raster のコピーが実際に起きた場合の phase を残す。

## やらないこと

- **トリムの検出解像度を変えない**。基準解像度を導入する案は取り下げた。トリム結果が
  本体と変わり、リモートだけ余白の残り方が違う状態を作るため。**bbox は今までどおり実ラスタから
  検出する。この修正で見た目は 1 px も変わらない。**
- `AutoTrimReference` 経路を消さない。相手ページが処理中でもスロットにも無い場合
  (末尾ページ、相手の要求がキャンセルされた場合) の正しい退路として残す。
  この修正で稀になるだけ。
- `RemoteAutoTrimCacheKey` から `target_px` を外さない。bbox は解像度ごとのラスタから
  出るので、キーに入っているのが正しい。
- HTTP の要求形式を変えない。`/api/page` は 1 要求 = 1 ページのまま。
  ブラウザ側は一切触らない。
- `page_composite_cache` の大きさや方針を変えない。

## テスト

1. **同じ identity への同時要求で、デコードが 1 回しか走らない** (2 つ目は相乗りして
   同じ `Arc` を受け取る)。
2. **スロットに残っているラスタは再デコードされない** (逐次パターン)。
3. **`target_px` が違えば共有しない** (別々にデコードされる)。
4. **`Thumbnail` と full page は共有しない**。
5. **owner が失敗したら、待っていた側は自分でデコードして成功する** (壊れた entry からの退路)。
6. **参加者が全員 cancel されたら共有デコードが cancel される**。
7. **一部の参加者だけ cancel されても、残った参加者のデコードは完走する**。
8. **不変条件**: 進行中 entry を所有したまま別の entry を待つと `debug_assert!` で落ちる。

1・5・8 は今回の肝なので、**実装を潰したときに落ちることを自分で確かめてから**報告すること
(例: single-flight をやめて常にデコードする / 壊れた entry で待ち続ける /
所有チェックを外す)。

デコード自体を差し替えられる形になっていないなら、**共有機構を `process_load_request` から
切り離した純粋な形 (「identity → 結果を作る関数」を受け取る) にしてテストする**。
本物の PDF デコードを回すテストにはしない。
