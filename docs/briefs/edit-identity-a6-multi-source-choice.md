# A6: 複数のコピー元がある行を、利用者が選べるようにする

**正本は [docs/edit-content-identity-plan.md](../edit-content-identity-plan.md) §5 / §6.1。**
A1 / A2 / A3a / A3b / A4 は実装済み。復元ウィンドウは
[src/ui_dialogs/content_restore.rs](../../src/ui_dialogs/content_restore.rs)。

## 1. 観測された失敗

利用者報告 (2026-08-22)。復元したのに**テキスト注釈が来なかった**。

ログ:

```
detection ready folder=...\y targets=1 sources=3
  candidate target=y\ChatGPT ... (2).png source=.../chatgpt image ... (2) - コピー.png
  candidate target=y\ChatGPT ... (2).png source=.../chatgpt image ... (2).png
  candidate target=y\ChatGPT ... (2).png source=.../🌷/chatgpt image ... (2).png
```

実機の `comic.db` を読むと、**注釈を持つのは 3 つのうち 1 つだけ**
(`testimage/chatgpt image ... (2).png`)。残り 2 つは持っていない。

そして台帳では **3 件とも `last_edit_at = 0`**。§5 の「複数候補は `last_edit_at` が
新しいものを既定に」は**同点で機能しない**。A4 の backfill で載る行は編集時刻が不明なので
必ず 0 であり、**backfill が救う母集団ではこの既定順が最初から死んでいる**。
結果、注釈を持たない側が既定に選ばれた。

さらに `🌷/...` は**それ自体が直前に復元されたコピー**で、注釈を持たないまま原本と同列に
並んでいる (復元先が復元元へ昇格する §8.2-4 の副作用)。

## 2. 採らない方針 (利用者判断、2026-08-22)

**「編集データ量が多い候補を既定にする」は採らない。**
量が多いことと、利用者が期待するコピー元であることは一致しない。
**自動で決めず、選べるようにする。**

## 3. やること

### 3.1 複数コピー元があることを、まず気付かせる

ウィンドウの**上部**に、複数コピー元を持つ行が 1 つでもあるときだけ出す:

```
3 件、複数のコピー元があります。コピー元を選択してください。
```

- 件数は**複数コピー元を持つ行の数** (候補元の総数ではない)。
- 0 件のときは**出さない** (通常ケースの見た目を変えない)。
- 実装語を出さない (CLAUDE.md「マニュアル・製品ページの記述方針」)。

### 3.2 行ごとに、どれから複製するかを選べるようにする

現状 ([content_restore.rs](../../src/ui_dialogs/content_restore.rs) の
`render_restore_rows`) は、複数あるとき `ComboBox` の見出しが
**「他 1 件の候補」** になっていて、**今どれが選ばれているのかが分からない**。
選択中のパスは行のラベル側にあり、選択 UI と分離している。

- **選択中のコピー元が、選択 UI 自体に見えること。**
- **その行に選択肢があることが、ひと目で分かること。**
- 候補の並びは**決定的**にする (`last_edit_at` 降順 → `file_key` 昇順)。
  同点でも並びが揺れないこと。**内容量では並べない。**
- 移動 / コピーの別 (`コピー元は残っています` / `移動`) は候補ごとに出す。
  同じ行の候補でも、消えている元と残っている元が混ざり得る。

**単一候補の行の見た目は変えない。** 大多数はそちらなので、そこに UI を足さない。

## 4. やらないこと

- **内容量 (編集行数) による自動選択・自動並べ替え**。§2 のとおり採らない。
- 候補ごとの中身の内訳表示 (「補正・注釈・★」等) は**今回入れない**。
  必要かどうかは、まず選べるようにしてから実機で判断する。
- `last_edit_at` を編集ストアの時刻から推定する案は採らない
  (時刻を持つストアと持たないストアがあり、中途半端になる)。
- 復元先が復元元へ昇格する挙動 (§8.2-4) は変えない。

## 5. 制約

- 既存の A1〜A5 の挙動を変えない。UI と候補の並び順だけ。
- `[閉じる]` / チェックを外して `[復元する]` / `次から確認しない` の
  3 つの意味 (§6.2) を変えない。
- glyph lint を通す。

## 6. テスト

- 複数コピー元を持つ行が無いとき、上部の注意文が**出ない**こと。
- 1 行だけ複数のとき「1 件、…」、3 行が複数のとき「3 件、…」になること
  (候補元の総数ではないこと)。
- 候補の並びが `last_edit_at` 降順 → `file_key` 昇順で決定的なこと。
  **全部 0 でも並びが安定すること** (今回の実データがこれ)。
- 行ごとに選び直すと、その行の復元元が実際に変わること。
- 単一候補の行の描画が変わっていないこと。
- UI スナップショット: **複数コピー元の行を含む状態**で 1 枚
  ([docs/ui-snapshot-policy.md](../ui-snapshot-policy.md))。
