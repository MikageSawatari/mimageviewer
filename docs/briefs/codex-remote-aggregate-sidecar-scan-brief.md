## 1. 指摘

`RemoteThumbnailSources::for_remote_entries` ([src/remote_ipc/mod.rs](../../src/remote_ipc/mod.rs))
は、集約系一覧に含まれる動画の**親フォルダごとに 1 回** `scan_directory_with_settings` を
呼ぶ。ブリーフの「一覧の件数だけ `read_dir` しないこと」は満たしている。

ただし **上限が無い**。`MAX_REMOTE_COLLECTION_ENTRIES = 1000` なので、動画が別々の
フォルダに散っている一覧では最大 1000 回の `read_dir` が 1 リクエスト内で同期的に走る。
タグビュー・レーティング一覧・閲覧履歴・本棚は「フォルダを跨いだ結果集合」なので、
これは想定外の入力ではなく**普通に起こり得る形**。

加えて:

- 結果は保持されないので、並べ替え・再訪のたびに同じ走査を繰り返す
- この経路は増分前は走査ゼロだった。新しく足された費用である

## 2. なぜ上限で足りるか

§3.3 で **sidecar が無い動画も Windows Shell からサムネイルを得る**ようになった。
つまり sidecar は「画質・本体との一致」のための優先指定であって、サムネイルが出るか
出ないかを決めるものではなくなっている。走査を打ち切った親の動画は Shell 経路へ落ちる
だけで、タイルは従来どおり絵が出る。

## 3. やること

- `for_remote_entries` が走査する**異なる親フォルダの数に上限**を設ける (64 を提案。
  値の根拠を短くコメントに残すこと)
- 上限で打ち切った親の数を `crate::logger::log` に出す。**黙って切り詰めない**
- 打ち切られた親の動画は `thumbnail_address` を持たないまま返す (= Shell 経路へ落ちる)
- 上限に達した場合と達しない場合のテストを足す

## 4. やらないこと

- 走査結果のキャッシュを新設しないこと。まず上限だけで様子を見る
- 上限を設定項目にしないこと
- 走査を別スレッドへ逃がさないこと (応答の形が変わる)

## 5. 補足: 将来の選択肢 (今回はやらない)

上限が実機で見えるようなら、次の増分で**遅延導出**へ変える手がある。集約系では
`thumbnail_address` を埋めず、`generate_video_resolved` が `source_address` 不在時に
自分で同 stem 画像を導出する。表示されたタイルの分だけ働く形になる。ただし同じ
フォルダに動画が大量にある一覧では同じ `read_dir` を繰り返すので、その場合は親単位の
メモ化が要る。今回の上限で足りるなら、この複雑さは持ち込まない。
