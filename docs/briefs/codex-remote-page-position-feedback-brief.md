## 0. この brief の位置づけ

直前の `3aaa345d` で「シークバーのページ数だけ進んで画像が変わらない」を直したが、
**直し方の向きが逆だった**。位置を画像に追従させた結果、タップしても何も動かず、
しばらくしてから一気にページが飛ぶ状態になった。ドラッグでも、指を離した瞬間に
バーが元位置へ戻り、少し経ってから離した位置へ移動する。

`3aaa345d` を revert するのではなく、**足りなかった状態を足して構造を完成させる**。

## 1. 事実 (調査済み。再調査不要)

### 1.1 ページ構成は既にクライアントが全部持っている

利用者は「ページのペアリング判断のため、本全体のページ構成を最初に取得する必要が
あるかもしれない」と書いているが、**すでに取得済み**である。追加の取得は要らない。

- `setContainerPageGroups()` [app.js:2462] が、コンテナを開いた時点で
  サーバから受け取った group 一覧から `state.pageGroups` / `state.seekPageGroups` を
  本全体ぶん構築する。
- `viewerSeekSnapshot(groupIndex)` [app.js:2521] は `state.seekPageGroups` /
  `state.images.length` / 読み方向だけから決まる純関数で、**任意の group index の
  ラベルをサーバに聞かずに出せる**。見開きのペアリングもこの中に入っている。
- ペアリングが変わるのは見開きモード変更・向き変更時の `refreshContainerSpread()`
  だけで、ページ送りでは変わらない。

したがって「要求した位置のページ番号を先に出す」ことに新しい通信は不要。
**新しい API・新しい先読み取得を追加しないこと。**

### 1.2 いま無反応になる理由 (2 つの経路が同時に黙っている)

- **位置**: `changeImageTo()` [app.js:3859 付近] から `setSeekState` の呼び出しが
  `3aaa345d` で外れた。要求しても位置表示は動かない。
- **処理中表示**: `beginLoadingIndicator()` [app.js:8421] は
  `loadMeasuredImage` / `loadMeasuredSpread` の**中**、つまり
  `LatestPageLoadQueue` が実際にそのジョブを走らせ始めてから呼ばれる。
  `pending` で待たされている要求は**表示が一切出ない**。
  さらに `PAGE_LOADING_INDICATOR_DELAY_MS` の遅延が上に乗る。

「1 件実行中 + 1 件待機」の要求削減 (`2c78a591`) 自体は正しい。
待たされている間が無表示なのが問題。

### 1.3 ドラッグで戻る理由

`commitSeekGroup()` [app.js:3696] が、`acquireRemoteSession` を待つ**前に**
無条件で `viewer?.restoreDisplayedSeekState()` を呼んでいる。
これが「離した瞬間に元位置へ戻る」の正体。

## 2. 直す (件 1・件 3 は同じ 1 つの構造)

### 2.1 位置は 2 つある。両方を持ち、両方を見せる

いま 1 つの値に 2 つの意味を載せているのが原因。以下を**別々の状態として持つ**。

| 状態 | 意味 | 所有者 |
| --- | --- | --- |
| 要求位置 | 利用者が最後に要求したページ | 既存の `state.pageGroupIndex` がそれ |
| 描画位置 | いま画面に出ている画像のページ | `ImageViewer.displayedSeekState` (既存) |

UI の導出規則を 1 か所に決める:

- **シークバーの値・ページ数ラベル・上部タイトルは、常に要求位置に従う。**
  タップでも、ドラッグの指離しでも、要求した瞬間に動く。
- **要求位置 ≠ 描画位置 の間は処理中表示を出す。**
- 画像が出たら描画位置が要求位置に追いつき、処理中表示が消える。
- **要求が破棄された場合に限り**要求位置を描画位置へ戻す。これが唯一の巻き戻し。

「新しい要求が来たので古い要求を捨てる」は破棄ではない (より新しい要求位置が
そのまま生きる)。巻き戻すのは、**もう何も届かないと確定したとき**だけ。

### 2.2 処理中表示は「ジョブ単位」ではなく「キューの稼働区間」で出す

`LatestPageLoadQueue` が busy (= `active` か `pending` のどちらかがある) の
区間に対して 1 本の表示を出す。

- idle → busy になった時点で遅延タイマーを開始する (要求を積んだ瞬間。
  ジョブが走り始めた時点ではない)。
- busy のまま待機要求が差し替わっても**タイマーを再スタートしない**。
  再スタートすると、速いタップを繰り返す間ずっと無表示のままになる。
- busy → idle で消す。

`PAGE_LOADING_INDICATOR_DELAY_MS` の遅延そのものは残してよい (速い読み込みでの
点滅を防ぐため)。開始の起点だけを変える。

処理中表示の見た目・位置は現状の `.viewer-loading-indicator` [styles.css:958] を
そのまま使う。加えて、要求位置 ≠ 描画位置 の間はページ数ラベル
(`.viewer-counter`) を暫定表示と分かる程度に弱める (不透明度を落とす等)。
**数字を「?」等に置き換えない** — 要求したページ番号が読めることが今回の要件。

### 2.3 ドラッグの指離し

`commitSeekGroup()` の先頭にある無条件の `restoreDisplayedSeekState()` を外す。
離した位置に留め、そのまま処理中表示へ入る。
巻き戻しは、既に revert している以下の失敗経路だけに残す:

- `acquireRemoteSession` が false / reject
- `changeImageTo` が false (境界で動けなかった)

### 2.4 やってはいけないこと

- キューの削減 (`2c78a591`) を戻して要求を全部投げ直す。無反応の原因は要求数ではない。
- 待ち時間を隠すためのタイマー延長・スロットリング・遅延投入の追加。
- ページ構成やページ番号のためのサーバ問い合わせ追加 (§1.1)。
- 描画位置と要求位置を、bool や「片方が null なら…」で表現すること。
  2 つの値と、そこから導く 1 つの導出規則にする。

## 3. 件 4: AI 処理中の帯を控えめにする

`.viewer-ai-status` [styles.css:986] は `left:12px / right:12px / max-width:680px /
min-height:42px` で、下部バーのすぐ上に横いっぱいに出る。スマートフォンでは画像を
覆う。PC 本体版は同種の表示が画面左下にあり、多くの場合黒帯の上なので気にならない。
リモートでは画像の上に出るため邪魔になる。

### 3.1 変更内容

- 通常の進捗表示 (`準備しています` / `接続を確認しています` /
  `remoteAiProgressText()` の内容 / `表示を整えています` / `取り消しています`) は、
  **左下の小さいインジケータ**にする。横いっぱいに広げない。
- インジケータをタップすると、現在の詳細文言と `取り消す` を出す。
  **取り消し手段を消さないこと。**
- **失敗表示は従来どおり読める形で出す。** エラーは読ませる必要があるので
  縮めない。`showRequestError` / `state === "failed"` の経路が該当。
- 完了表示 (`hideAfterMs: 2400`) は縮小形のままでよい。

安全域 (`env(safe-area-inset-*)`) と下部バーの高さを踏まえ、下部バーや
`.viewer-boundary-message` と重ならない位置にする。

### 3.2 触らないもの

- `.viewer-boundary-message` (「最後のページです」等) は今回の対象外。
- AI ジョブの開始・取り消し・ポーリングのロジック。表示形態だけを変える。

## 4. テスト

- 位置の導出規則を純関数として切り出し、単体テストを付ける。最低限:
  - 要求 → 未着の間は要求位置が出て、処理中である
  - 画像到着で描画位置が追いつき、処理中が解ける
  - 待機要求の差し替えでは巻き戻らない
  - 破棄 (session 取得失敗 / 境界) では描画位置へ戻る
- キュー稼働区間の判定 (idle→busy で開始、差し替えで再スタートしない、
  busy→idle で終了) の単体テスト。
- 既存の web テスト 209 件を維持すること。
