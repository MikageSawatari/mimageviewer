## 2. 確定した 3 件 (すべてログと source inspection で裏取り済み)

直前の増分で入れた `page_display` テレメトリが各回の理由を記録している。

### 2.1 Web: 先読み計画が、前景の待っている通信を打ち切る (修正済み `143fc596`)

`PageResourceCache.loadForeground` は進行中の先読みに相乗りする。`schedule` は
「新しい計画に無い進行中」を打ち切る。先読み窓は現在のグループを含まないので、捲った先の
ページは計画から外れた瞬間に打ち切られる。前景が待っていた当のもの。

修正: active に前景待機者数を持たせ、待機者がいる間は計画から打ち切らない。

### 2.2 本体: 前景描画の開始が、自分で使う先読みを打ち切る (修正済み `eed5ff93`)

`ContainerEngine::begin_page_render` は、前景が始まると登録済みの先読みを全部打ち切って
いた。優先度は URL の `prefetch=1` の有無で決まる。見開きは 1 ページずつ要求されるので、
片方が先読み中・もう片方が未取得だと、後者の前景要求が前者を殺す。

修正: 先読み登録に対象 `RemoteAddress` を持たせ、自ページと `spread_partner` は残す。

### 2.3 Web: 見開きの片方が、もう片方を打ち切る (未修正、今回の観測)

`loadForeground` の中の、他の active を打ち切るループ:

    const joined = this.active.get(request.cacheKey);
    if (joined) joined.foregroundWaiters += 1;
    for (const active of this.active.values()) {
      if (active.key !== request.cacheKey && active.foregroundWaiters === 0) {
        active.controller.abort();
      }
    }

`loadMeasuredSpread` は `Promise.all(pages.map(async ...))` で 1 ページずつ
`loadForeground` を呼ぶ。map のコールバックは同期的に順次起動されるので、**4 ページ目の
同期部分 (join + 打ち切りループ) が、5 ページ目の `loadForeground` より先に走る**。
その時点で 5 ページ目の先読みは待機者ゼロなので打ち切られる。直後に 5 ページ目が
中止済みの通信へ相乗りして `AbortError` になり、`Promise.all` ごと失敗する。

実ログ (1 → 2/3 → 4/5 の 4/5 で失敗):

    82526ms  applied      dom_committed  [2,3]  適用済み
    83339ms  command      next_page
    83345ms  not_applied  abort          [4,5]  候補=[] 適用=[]

## 3. 3 件に共通する形

**打ち切りの判断はページ単位でされているのに、「必要か」は表示グループ単位で決まる。**

3 箇所とも、「この仕事はもう要らない」を、**今の表示が何を必要としているかを知らないまま**
決めている。2.1 と 2.2 は事後に個別の条件 (待機者数 / アドレス一致) を足して塞いだが、
判断の入口は増えたままで、次の入口でまた同じことが起きた。それが 2.3。

## 4. 見てほしいこと

### 4.1 まず全体の流れを把握する

リモートで 1 ページ表示されるまでに、どこがどの責務を持っているかを追ってほしい。

- Web: 表示グループの決定 → 各ページの要求生成 → キャッシュ / 先読み / 相乗り →
  取得 → デコード → DOM 適用
- HTTP: admission (`IpcClass`)、優先度の判定 (`prefetch=1`)
- 本体: ページ描画、編集結果の合成、先読みの登録と打ち切り、worker 枠

そのうえで**責務の置き場所が妥当かを評価**してほしい。特に:

- **表示単位は見開き (最大 2 ページ) なのに、要求・キャッシュ・打ち切りは 1 ページ単位。**
  この不一致は必要か。グループを単位にすると何が良くなり、何を失うか
- **前景が進行中の先読みに相乗りする設計は妥当か。** 相乗りするから「他人に打ち切られる」
  余地が生まれている。相乗りしない (別に取る) 場合の費用は実際どれくらいか
- **打ち切りは何のために要るのか。** 枠を空けるためなら、直前の増分で本体は前景用に
  1 枠を予約済み (`min(heavy_workers - 1, 2)`)。Web 側の打ち切りは何を守っているのか
- **優先度が URL の `prefetch=1` で決まる設計は妥当か。** 相乗りすると「前景が待っている
  のに本体からは先読みに見える」状態が生まれる。2.2 はこれが原因

### 4.2 打ち切りの入口を全部挙げる

進行中の仕事を打ち切る / 捨てる / 無効化する箇所を、Web と本体の両方で列挙する。
少なくとも次を含むが、これで全部だとは思わないこと。

- `PageResourceCache` の `schedule` / `loadForeground` / `pump` / eviction
- `AbortController` を作る・`abort()` する箇所 (viewer の `fetchController`、
  `invalidatePendingLoad`、`destroy`、`cleanupScreen`、`loadContainer` / `loadFolder`)
- 本体の `begin_page_render` / `finish_page_render` / `page_prefetches`
- IPC admission の拒否と、その拒否の呼び出し側での扱い
- セッション取得 / 失効 / owner 交代に伴う無効化
- ページ以外 (サムネイル、AI ジョブ、アーカイブ変換) で同じ形になっている箇所

各入口について、**何を根拠に「もう要らない」と判断しているか**を書くこと。

### 4.3 直し方を設計する

個別の条件を各入口に足す形にはしないこと。**2.1 と 2.2 の修正も、より良い構造に
置き換わるなら置き換えてよい。**

満たしてほしいこと:

- 打ち切りの入口が増えても、同じ誤りが起きない
- 「本当に不要な仕事を打ち切る」能力は失わない (性能のために必要)
- 表示に失敗したときの状態が、シークバーと画面で食い違ったまま残らない
  (現在は残る。`loadGroup` の戻り値が終端の失敗と追い越しを区別できないため未修正)
