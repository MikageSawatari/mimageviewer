## 1. 実測で分かっていること (再調査不要)

高画質 8192 のページ (46.5 MP) 1 枚あたり:

| 区間 | 中央値 | 割合 |
|---|---|---|
| 本体のレンダリング + JPEG エンコード | **2281ms** | 71% |
| リモートサービス側 | 536ms | 17% |
| 端末への転送 (約 5.4 MiB) | 約 370ms | 11% |

**並列数では供給が増えない。**3 層すべてを 3 にして実測したが、1 本あたりが 2016 →
2952ms に伸び、供給は 0.99 → 1.02 ページ毎秒 (+2%) だった。**2 本の時点で機械は
飽和している。**したがって**仕事を前倒しする以外に打つ手がない**。

画質別の 1 ページあたりの費用 (実測):

| 長辺 | 画素 | 生成 | 符号化後 |
|---|---|---|---|
| 8192 | 46.5 MP | 1969ms | 5.37 MiB |
| 6144 | 26.1 MP | 約 1150ms | 約 3.5 MiB |
| 4096 | 11.6 MP | 608ms | 1.89 MiB |
| 3072 | 6.5 MP | 約 384ms | 約 1.2 MiB |
| 2048 | 2.9 MP | 289ms | 0.64 MiB |

**符号化済みで保持するので容量は小さい。**デコード済み画素なら 1 枚 186 MB だが、
JPEG なら 5.37 MiB で **約 35 分の 1**。60 枚でも 322 MiB に収まる。

## 2. 決定 (2026-08-12、利用者判断)

**本体が、端末に要求される前にページを用意して符号化済みバイトで持っておく。**

- 窓は**後方 12 / 前方 48**。**本体の環境設定**に置く (端末側の先読み枚数とは**別の設定**)。
  費用を負担する側が決める: 端末側は端末のメモリと回線、本体側は PC の CPU とメモリ
- 既定値は本体の `prefetch_back` / `prefetch_forward` (4 / 12) ではなく **12 / 48**。
  符号化済みは容量が桁違いに小さく、深い窓が現実的なため
- **在庫はリモートサービス側ではなく本体側に持つ**。本体が生成したものをそのまま
  保持する。パイプ転送は端末が要求した時点で行う

**捨てる規則は枚数で決める。**容量の上限で挙動が変わる形にしない (利用者方針:
「見えない上限値で動作が制限されると、なぜ先読みされないのかユーザにはわからなくなる」)。

## 3. 変更内容

### 3.1 用意する

- 端末からの `Page` 要求を受けたら、**その位置を中心に窓を張り直す**。窓に入っていて
  まだ無いページを、**近い順に**生成して保持する
- **近い順に確定させること。**48 枚を均等に進めると、すぐ先のページが最後まで揃わず、
  連続めくりに効かない
- 生成は既存の heavy queue の **prefetch lane** を使う (表示要求より後回しになる既存の
  規則をそのまま使う。専用の経路を作らない)
- **キーは端末が使うものと同じ**にする。`target_px` / 世代 / セッション epoch / 補正 /
  render context を含む既存のキー体系に合わせ、**要求時にそのまま当たる**こと。
  ここがずれると、用意したのに一度も使われない (デコード先読みで実際に確認した観点)

### 3.2 捨てる

- **窓から外れたら捨てる。**別の場所へ移ったら、古い窓の生成は中止し、保持も解放する
- **session owner が変わったら全部捨てる。**在庫は session が持ち主である。
  排他 (plan §2.2) により owner は常に 1 つなので、**窓が複数並ぶことはない**
- 画質・補正・世代が変われば**キーが変わるので自然に外れる**。別途の無効化を足さない

### 3.3 ダイアログに出す

いまリモート接続ダイアログは「処理中 N 件 / 待機 N 件」を**合計でしか出せない**。
`OperationState` ([session.rs](../../src/remote_ipc/session.rs) 140 行付近) が種別を
持っていないためである。

- `OperationState` に**種別**を持たせ、`SessionSnapshot` を経てダイアログまで運ぶ。
  種別は `describe_message` が既に `page_foreground` / `page_prefetch` として算出済み
- ダイアログに**準備の状況**を出す:
  - 準備済み **N 枚** (窓の枚数のうち)
  - 準備中 **N 件** / 待機 **N 件**
- 既存の「処理中 / 待機」の合計表示は残し、その内訳が分かる形にする

**表示のためだけに新しい計数を持たない。**heavy queue は lane ごとの `queued` /
`active` を既に持っているので、それを読む。

**状態遷移として検証すること** (CLAUDE.md「バグ修正の一般原則」)。

- 要求された位置から窓が張り直され、**近い順に**生成されること
- **窓から外れた分が中止・解放される**こと。飛んだ後に古い窓の生成が続かないこと
- **session owner が変わったら全部捨てる**こと
- 保持は**枚数で**決まり、容量では決まらないこと
- **用意したページが、端末の要求で実際に当たる**こと (キーの一致。ここが本命)
- 種別つきの計数がスナップショットまで運ばれ、prefetch と foreground が分かれること
