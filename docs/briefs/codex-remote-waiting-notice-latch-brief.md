## 2. 私が読んだ機構 (検証してほしい)

`e813f8bb` で `playbackStallWatch` を停止処理の単一所有者にしたが、
**その watch の終わり方に「再生が戻ったから解消」が無い**ように見える。

- `notePlaybackProgress()` は watch を **延長する** (`lastProgressAt` を更新して
  terminal timer を差し直す)。**終了させない**
- `videoPlaybackStallDecision()` の戻り値は `cancel` / `defer` / `waiting` / `stalled` の
  4 つで、**「進行しているので解消」に当たる結果が無い**
- 実際に watch を落とすのは `clearWaiting()` で、再生中の経路からは `onPlaying` だけ。
  `playing` は「止まっていた → 再生した」遷移でしか発火しないので、
  **要素が実際には止まらなかった場合 (spurious な `waiting` / `stalled`) は二度と来ない**

結果として、時刻が進むたびにタイマーが差し直され、`waiting` が永久に続く。

**再生位置が進んでいることは「止まっていない」ことの定義そのもの**なので、
進行は watch を延ばす根拠ではなく、終わらせる根拠のはず。

### 直し方について

**判定は純関数に置いてほしい。** 現状 `videoPlaybackStallDecision` が
`elapsedSinceProgressMs` しか見ておらず、進行そのものを表現していない。
ここに「解消」を持たせればテストで固定できる。

呼び出し側で「進んでいたら `clearWaiting()` を呼ぶ」を足すだけの形にしないこと。
それだと所有者が 2 箇所になり、次に同じ取りこぼしが起きる。

**具体的な述語は判断してよい。** 一瞬進んで再び止まる吃音を「解消」と扱わない下限を
どこに置くかも含めて。

## 3. もう 1 つの症状 (同じ所か、別か判断してほしい)

> 最初動画再生しようとしたときにも出て**再生が始まりませんでした**。
> 1 回シークすると再生が始まりました。

記録:

```
video_stream_media_stalled:
  current_time_secs: 0,  ready_state: 4,  buffered_ahead_secs: 3.958,
  paused: true,          network_state: 2
video_stream_playback_waiting (3 秒後):
  current_time_secs: 0,  ready_state: 4,  buffered_ahead_secs: 23.958,
  paused: true,          waiting_trigger: "stalled"
```

**24 秒分バッファされ `readyState` は 4 なのに、要素は `paused: true` で位置 0。**
データはあり、再生が始まっていないだけ。

私が気づいた点 2 つ:

1. `onStalled` は `paused` も `playRequested` も見ずに `beginWaiting("stalled")` する。
   HTML の `stalled` は取得が滞っただけでも発火し、**一時停止中でも出る**
2. `beginWaiting` の **3 秒警告タイマーには判定が一切入っていない**。
   `videoPlaybackStallDecision` は `!playRequested` なら `cancel` を返すが、
   その判定は 15 秒の terminal 側でしか呼ばれない。**通知だけ先に出る**

ただし「なぜ再生が始まらなかったか」は分かっていない。`playIfRequested()` が
呼ばれなかったのか、`play()` が拒否されたのか、記録からは読めない。
**ここは調べて報告してほしい。** 原因が分からないまま自動 `play()` 再試行を足さないこと。

判別の材料が足りないなら、**足りない記録を足すだけで止めてもよい**
(`play()` の rejection を残す等)。次の再現で分かる形になっていれば十分。
