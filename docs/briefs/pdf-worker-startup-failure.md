# PDF ワーカーの起動失敗を、縮退ではなく失敗として扱う

着手前に [CLAUDE.md](../../CLAUDE.md) の「バグ修正の一般原則」と
[docs/async-architecture.md](../async-architecture.md) を読むこと。

## 1. 現状 — 3 つの状態があり、真ん中が誰にも見えない

`PdfWorkerPool` は `POOL_SIZE`(=5) 個の子プロセス起動を試み、**失敗はログ 1 行で流す**
([pdf_loader.rs:1710](../../src/pdf_loader.rs:1710) 付近)。

```rust
Err(e) => {
    crate::logger::log(format!("pdf-pool: worker {i} startup failed stage=spawn_or_readiness error={e}"));
}
```

| 実際に起動できた数 | 現在の挙動 |
| --- | --- |
| 5 | 正常。**唯一テストされている構成** |
| **1〜4** | **黙って縮退動作。利用者には何も見えない** |
| 0 | in-process フォールバック (メインプロセスで PDFium を直接動かす) |

**リトライは無い。**

## 2. なぜ直すのか (利用者判断 2026-08-20)

- **テストできない分岐を残さない。**1〜4 個の構成は実機でもテストでも通せない。
  何が起きるか想定できない状態で利用者が使い続けることになる。
- **in-process フォールバックは 5 対の分岐を生んでいる** (`worker_count > 0` の if / else が
  [3056](../../src/pdf_loader.rs:3056), [3090](../../src/pdf_loader.rs:3090),
  [3136](../../src/pdf_loader.rs:3136), [3318](../../src/pdf_loader.rs:3318),
  [3579](../../src/pdf_loader.rs:3579))。**その else 側を通るテストは 1 本も無い。**
- 多機能は目指すが、**処理の分岐を必要以上に増やさない**。

## 3. やること

### 3.1 リトライ

ワーカー起動失敗は AV スキャンや一時的な資源枯渇など、再試行で通る類が多い。
**回数を区切って再試行する。** 時間で粘らない (回数で決める)。

### 3.2 3 未満は失敗として扱う

**最低 3。** 各レーン (Critical 予約 / Normal / HighNormal) が 1 を割らない最小値であり、
ワーカー数設定の下限として決めた値と同じ ([pdf-fullscreen-lane-capacity.md](pdf-fullscreen-lane-capacity.md)
で入れた `non_critical_lane_caps` は 1〜2 でも clamp で安全だが、**そこへ到達させない**)。

リトライしても 3 未満なら「縮退成功」ではなく **PDF サブシステムの失敗**。

### 3.3 失敗の見せ方

- **明示的なエラーを出す。**原因 (最後の spawn エラー) とログの場所を添える。
- **PDF を無効化する。**PDF を開こうとしたら「利用できません」と明示する。
  中途半端に遅い / おかしい状態で使わせない。
- **アプリは終了しない。**mIV は画像ビューアで PDF は形式の 1 つ。画像・動画・アーカイブの
  閲覧は無関係に正常なので、それを巻き添えにしない。起動時に落とすと利用者から見て
  「アプリが起動しない」だけになり、**原因がいちばん分かりにくい失敗の形**になる。

### 3.4 in-process フォールバックを削除する

`worker_count > 0` の 5 対の分岐を **IPC 経路のみ**にする。`PdfWorker` / `get_worker()` と
その周辺 (`WorkerRequest` の in-process 用経路) が不要になるなら**まとめて削除する**。
0 ワーカーは §3.2 の失敗に含まれるので、フォールバック先は要らない。

**削除でテストが赤くなる場合は止めて報告する** (in-process 経路に依存したテストがあるなら、
それは設計判断が必要)。調査時点では、pdf_loader のテストは純関数側 (`render_page_canonical_raster_with`)
だけでワーカー経路に触れていないことを確認済み。

## 4. 制約

- **時間窓で粘らない。**リトライは回数で区切る。
- **silent fallback を新しく作らない。**失敗は必ず利用者に見える形にする。
- 起動失敗時に**他の機能を巻き添えにしない**。
- ワーカー数はまだ `POOL_SIZE` 定数のまま (設定化は次の作業)。**今回は定数のままで良い。**

## 5. テスト

- 起動失敗をシミュレートして、**リトライが指定回数走る**こと。
- 3 未満で確定したとき、**PDF が無効化され、エラーが利用者に見える**こと。
- そのとき**画像 / 動画 / アーカイブの経路が影響を受けない**こと。
- `worker_count > 0` の分岐が消え、in-process 経路が到達不能になっていること
  (削除するので、コンパイルが通ること自体が保証になる)。
