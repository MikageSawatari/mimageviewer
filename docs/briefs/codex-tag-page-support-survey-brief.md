# 調査ブリーフ: タグをページ単位で付けられるようにする前の影響調査

## 背景

[docs/item-kind-capability-matrix.md](../item-kind-capability-matrix.md) §6 の 1 / 2 / 3 / 4 / 9 / 10 は
すべて「タグとページの関係」に集約される。現状、同じ ZIP / PDF ページに対してタグは
入口ごとに三通りの答えを返す。

| 入口 | 現状 |
| --- | --- |
| グリッドの通常メニュー / `T` | 拒否 (無効化・トースト) |
| ビューアの右パネル | **コンテナへ寄せる** (黙って親 ZIP / PDF に付く) |
| グリッドのピン留めクイック | 無反応 (silent return) |

一番悪いのは 2 番目。利用者はページにタグを付けたつもりで、実際は本全体に付いている。

**方針は決まっている**: ★ と同じく「ページ」と「コンテナ」を別の対象として扱い、
メタデータパネルには 2 行出す ([ui_metadata_panel.rs:328-341](../../src/ui_metadata_panel.rs:328) が
★ の実装)。**黙った付け替えを無くすのが目的**であって、タグをどこにでも付けられる
ようにするのが目的ではない。

## このタスクは調査のみ

**コードを変更しない。** 実装方針を決めるために必要な事実を集める。
成果物は `docs/tag-page-support-survey.md` の新規作成のみ。

## 既に確認済みの事実 (裏取りは不要、前提として使ってよい)

- `item_tags` は `item_key TEXT` のみで **種別カラムを持たない**
  ([tags_db.rs:111](../../src/tags_db.rs:111))
- ページのキー形式は既に存在する ([edit_source.rs](../../src/edit_source.rs) `page_key_for_grid_item`)
  - 実ファイル: `normalize_path(path)` (`::` を含まない)
  - ZIP ページ: `<zip>::<entry 小文字>`
  - PDF ページ: `<pdf>::page_<n>`
- ★ は同じキー体系を使い、さらに `RatingItemKind` を**明示カラムで**持つ
  ([rating_db.rs:22](../../src/rating_db.rs:22))
- `tags.db` は **リリース済み**。スキーマを変えるなら後方互換の移行が要る
- タグのサイドカーミラーは実ファイル限定で、ページには最初から作られない
  ([tag_write_worker.rs:21](../../src/tag_write_worker.rs:21))

## 答えてほしい問い

各問いに `file.rs:line` の根拠を付ける。**推測は「未確定」と明記**して分ける。

### Q1. `item_key` を実パスとして扱っている場所はどこか

`item_tags.item_key` から `PathBuf` を作る、`Path::exists` を呼ぶ、親フォルダを取る、
拡張子で分類する、といった処理を**全部**挙げる。`::` を含むキーが流れ込んだときに
何が起きるかを 1 件ずつ書く (無害 / 誤動作 / パニック)。

最低限この範囲は見る。漏れがあれば足す。

- `tag_view.rs` (`run_tag_view_search` / `TagViewItemKind` / `TagViewEntry.path`)
- `tag_prewarm.rs`
- `tag_write_worker.rs`
- `tag_ops.rs`
- `rename_key_migration.rs` (改名・移動でタグキーをどう書き換えているか)
- `delete_worker.rs` (削除時の purge)
- タグ facet / 検索へタグを供給している経路
- メタデータ転送 (`metadata transfer`) がタグを扱う経路
- リモート (`remote_ipc`) がタグを返す経路

### Q2. タグ横断一覧はページを復元できるか

`TagViewItemKind` に `Folder / Image / Video / Audio / ZipFile / PdfFile / Archive` しか無い。
★ の横断一覧は `rating_view.rs:174-225` で `ZipImage` / `PdfPage` / `ZipDir` を
**元の variant として復元**している。タグ側で同じことをするには何が要るか。

- `item_kind` カラムを足す案と、`item_key` の `::` を解析する案の、それぞれの必要作業と壊れ方
- 特に **ZIP 内エントリ名に `::` や `page_3` が含まれる場合**、解析案が誤分類しないか
  (実際に起こり得るかも判断する)

### Q3. 改名・移動でページタグは追随できるか

`rename_key_migration.rs` が実パスのタグキーをどう書き換えているかを読み、
**コンテナ (ZIP / PDF) を改名したときに、その中のページのキーも書き換わるか**を
確かめる。★ は同じ問題を持つはずなので、**★ が既にどう解いているかを調べて、
タグはそれに倣えるかを書く** (★ が解けていないなら、そう書く)。

### Q4. タグ facet と検索への影響

ページにタグが付いたとき、ファセットバーの件数・タグ検索の結果に何が起きるか。
ページが結果に出る場合、それを開く経路 (materialize) はあるか。

### Q5. 実装の分割案

上を踏まえ、**段階に分けた実装順**を提案する。各段は単独でリリースできる形にする。
「ここで止めても壊れていない」境界がどこかを明記する。**規模の見積り (触るファイル数と
おおよその行数) も付ける。**
