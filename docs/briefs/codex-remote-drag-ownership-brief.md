# リモート閲覧: はみ出しを持っている側に 1 本指ドラッグを渡す

作業ツリー: `C:\home\mimageviewer-web` (branch `web-remote`)。
実装 = Codex、レビュー・テスト・統合 = ClaudeCode、実機確認 = 利用者。

## 1. 観測された失敗

- **原寸で 1 本指ドラッグしても何も動かない。** メニュー経由で原寸にしても同じ。
- **幅フィットで下端まで進むと、左パネルのメニューが出てしまう。** スクロールの続きの
  つもりのドラッグが、ナビゲーションのスワイプとして扱われている。

## 2. 調査済みの事実 (再調査不要)

- `.viewer-stage` は既定で `overflow: hidden` だが、
  **`[data-fit-mode="width"]` と `[data-fit-mode="original"]` では `overflow: auto`**。
  つまりこの 2 つでは**ステージ自身がスクロールする**。[styles.css](../crates/remote-web/web/styles.css)
- `.viewer-stage` は `touch-action: none`。**ブラウザ既定のスクロールは効かない**ので、
  アプリが動かさない限り何も動かない。
- 1 本指ドラッグの分岐は 2 つしかない。
  - 変換でパンする分岐 (もとは `this.scale > 1.01` で判定していた)
  - `fitMode === WIDTH` のとき `stage.scrollTop` を動かす分岐 (**縦のみ**)
  - **原寸に対応する分岐が無い**。これが「何も動かない」の直接の原因。
- 直前の修正 (`65fcf70f`) で、パンの判定を「内容が表示領域からはみ出しているか」に
  変えた。**これは誤り**。原寸のはみ出しを持っているのはステージのスクロールであって
  変換ではない。変換でパンしてもスクロールコンテナと食い違う。**この判定は置き換える。**
- スワイプ判定には `contentScrolled` が渡っている。これは**実際にスクロール量が動いたか**で
  立つフラグ。すでに端に達していると動かないので立たず、スワイプとして扱われる。

## 3. 構造の決め

**はみ出しを持っている側が、そのドラッグを所有する。**

| 状態 | はみ出しの持ち主 | 1 本指ドラッグ |
| --- | --- | --- |
| ピンチで拡大中 | 変換 (`scale > 1`) | 変換をパンする |
| 原寸 | ステージのスクロール | ステージを**縦横**スクロールする |
| 幅フィット | ステージのスクロール | ステージを縦スクロールする (現行どおり) |
| 全体表示 | 誰も持たない | 従来どおり (タップ / スワイプ) |

- 判定を 1 か所に集約する。分岐ごとに別の条件を書かない。
- 原寸で横にもはみ出しているときは横も動かせること。
- ピンチ拡大とステージスクロールが同時に成り立つ場合の優先順位を決め、根拠をコメントに残す。

## 4. スワイプに渡さない条件

**スクロールする面で始まったドラッグは、離すまでそのドラッグの持ち主であり続ける。**

- 端に達して以降も、そのドラッグはスクロールの一部として扱う。ナビゲーションのスワイプに
  変わらない。
- 判定は「実際に動いたか」ではなく「**その面がその向きのスクロールを担っているか**」で行う。
  現行の `contentScrolled` は前者なので、端では成立しない。
- 利用者から「短時間のときだけスワイプにする」という案が出ているが、**時間はこの問題の
  本質ではない**ので、時間の閾値では解かない。ゆっくりスワイプしたい場面と、端で
  スクロールを続けたい場面を時間で分けられない。所有権で分ける。
- 全体表示のようにスクロールを担う面が無い場合のスワイプは、現行どおり残す。

## 5. やってはいけないこと

- 原寸のパンを変換 (`panX` / `panY`) で実装すること。ステージが `overflow: auto` の間は
  スクロールが正本。
- `touch-action` を緩めてブラウザ既定のスクロールに戻すこと。ジェスチャの所有が壊れる。
- スワイプへ渡さないための時間閾値・移動量閾値の追加 (§4)。
- ドラッグ中に毎フレーム `getBoundingClientRect` を呼ぶこと。ジェスチャ開始時に決めて
  持ち回る。
