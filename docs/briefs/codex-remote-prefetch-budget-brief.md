# 先読みを予算方式にし、処理時間を可視化する

作業ツリー: `C:\home\mimageviewer-web` (branch `web-remote`)。

## 0. 前提 — 先に読むもの

- [`docs/web-remote-plan.md`](../web-remote-plan.md) §14 / §14.5 / §14.5.1 (直前の段階 A)
- **これは所有権の cutover とは別の増分**。`PageResourceCache` の
  `foregroundWaiters` / `prefetchPlanned` / `loadForeground` の打ち切り走査、
  `abortUnownedActive`、本体の `begin_page_render` には**触らない**。cutover で置き換える

## 1. なぜ変えるか (実測)

利用者の iPad で「ページを捲ると中央にインジケータが出て待たされる」。直近 3.5 分の
`remote-web-log.jsonl` から:

| 項目 | 実測 |
|---|---|
| ページ要求 | 64 件 (200: 51 / 503: 11 / 409: 2) |
| 応答時間 | p50 2.08s / p95 2.67s |
| うち本体の生成 (`ipc_ms`) | 1.84s |
| ページサイズ | p50 4.9MB / p95 6.6MB |
| 出力 | 5628 × 8191 (`target_px` 8192 = 画質「高品質」) |

- 転送は 6.6MB を約 0.24 秒。**ボトルネックは本体のレンダリング**
- 503 はすべて `admission_busy` (`prefetch_in_flight: 2/2`)
- 現在の窓は**前方 3 ページ / 後方 1 ページ**。見開きだと前方 1.5 タップ分しかない

先読み窓が固定ページ数なので、1 ページのコストが画質や content で 4 倍変わっても
追随しない。**窓の深さをバイト予算から決める**ように変える。

## 2. 予算方式 (利用者の提案が起点)

現在の `PageResourceCache.remember` は、`limit` (12 件) と `byteLimit` を超えると
**保持中のものを古い順に捨てる**。捨てた先が今まさに必要なページだと、取得 → 破棄 →
再取得のループになる (本体側で同種の失敗をした記録が
[`docs/final-composite-budget-thrash-plan.md`](../final-composite-budget-thrash-plan.md))。

**変更する規則:**

1. **予算は「新しい取得を始める門」にする。** `pump()` は保持バイト数が予算以上なら
   新しい先読みを**開始しない**。既に取得済みのものは予算を超えていても保持して使う
2. **破棄は「保護集合の外」だけ。** 保護集合 = 表示中のページ + 現在の先読み計画の先頭
   K 件 (`pagePrefetchPlan` は近い順に返す)。保護集合しか残っていないなら、**破棄せずに
   超過を受け入れる**
3. **窓の深さは上限として持つだけにする。** `PAGE_PREFETCH_AHEAD` / `BEHIND` を本体と
   同じ **12 / 4** へ上げ、実際の深さは予算が決める。標準画質 (1 ページ 1.5〜2MB) なら
   全部入り、高品質 (5〜7MB) なら自動的に浅くなる
4. `pageResourceCacheBudget` の `minimumBytes` 下限 (= ページ数 × 8MiB) は**撤去**する。
   これがあると窓を深くしただけで予算が膨らみ、予算方式の意味が消える
5. 保持バイト数は**走る合計として持つ** (今は `remember` のたびに全件を舐めている)

**予算の値**: 端末のメモリ量を知る手段は Safari には無い (`deviceMemory` /
`performance.memory` は使えない)。**検出を発明しないこと。** 保守的な固定値
**64 MiB** から始める。これが唯一メモリを縛る数値になる。

**保持しているのは圧縮 JPEG (Blob) であって展開後のビットマップではない** (展開は表示中の
2 ページだけで、古い object URL は revoke 済み)。この前提を壊さないこと。

**再開の保証**: 予算超過で先読みを止めた後、ページが進んで保護集合が変われば
`schedule()` → `pump()` で再開する。破棄できるものが無い状態で止まり続けるのは正しい
挙動なので、タイマーで無理に回さない。

## 3. 処理時間の可視化

利用者が画質を選ぶとき、いま体感でしか判断できない。**画質設定の各プリセットに
「直近 10 ページの平均」を出す。**

### 3.1 本体の生成時間をヘッダで返す

`/api/page` の 200 応答に **`X-mIV-Page-Render-Ms`** を足す (値 = 既に記録している
`ipc_ms`)。クライアントは合計しか測れないので、これが無いと生成と転送を分離できない。
秘密情報ではないので露出して問題ない。既存ヘッダは `crates/remote-web/src/http.rs` の
`X-mIV-Image-Width` 付近。

### 3.2 直近 10 件を画質プリセットごとに保持する

前景ページの表示が成功したときだけ、次の 3 つを記録する。

- **生成** = `X-mIV-Page-Render-Ms`
- **転送** = 合計 fetch 時間 − 生成 (0 未満は 0 に丸める)
- **展開** = 既存の `decode_ms`

プリセット ID ごとにリングバッファ 10 件。`localStorage` に保存する
(`local-settings.mjs` の隣。タイミング値だけなので秘密は含まない)。

### 3.3 表示

画質選択 UI (`app.js` の `IMAGE_QUALITY_PRESETS` を描画している箇所) で、**標本のある
プリセットにだけ**次の形で出す。

    直近 10 ページの平均 — 生成 1.8 秒 / 転送 0.2 秒 / 展開 0.3 秒

**標本の無いプリセットには何も出さない。推測値を作らないこと。**

**ラベルの注意**: この数値は**プリセットの性質ではなく、いま読んでいる本の性質**である。
大きな PDF と小さな JPEG では桁が違う。「高品質 = 1.8 秒」と読める出し方にしないこと。
「直近 10 ページの平均」と明示する。

## 4. 触らないもの

- 取消・lease の所有権 (段階 B+C+D0 の cutover)
- 要求解像度と JPEG 品質そのもの (利用者の判断で変えない)
- `page_display` テレメトリ
- 本体側の admission (`try_acquire_prefetch` / `remote_heavy_worker_count`)。
  同時実行数の引き上げは別途検討する

## 5. テスト

`node --test --experimental-test-isolation=none crates/remote-web/web/*.test.mjs`

**純関数**

- 予算超過時に新規開始を許可しない / 予算内なら許可する
- 保護集合は破棄されない。保護集合しか無いときは超過を受け入れる
- 保護集合の外から古い順に破棄される
- 平均の計算。標本 0 件、1 件、10 件超 (古いものから落ちる)
- 転送時間が負にならない (生成 > 合計 のとき 0)

**キャッシュ**

- 深い窓 (12/4) でも、予算を超えたところで開始が止まる
- 表示中のページが破棄されない
- ページが進んで保護集合が変わると先読みが再開する
- 取得 → 破棄 → 同じキーの再取得が起きない

**Rust**

- `/api/page` の 200 に `X-mIV-Page-Render-Ms` が付く

## 6. ドキュメント

`docs/web-remote-plan.md` に節を追加し、次を記録する。

- 予算を「破棄の引き金」ではなく「開始の門」にした理由と、保護集合の定義
- 窓の深さが予算で決まるようになったこと (固定ページ数をやめた)
- 端末メモリの検出手段が無いので固定 64 MiB から始めること
- 処理時間表示が content 依存であること

`htdocs/mimageviewer/manual/tut-remote.html` に画質設定の説明があれば、処理時間表示に
触れる。無ければ追加は不要。
