# 重複画像の検出と整理 — 設計計画

> ステータス: **設計 v0 (2026-09-03)。未実装・未レビュー。** §11 に要確認事項がある。
> 調査の前段は [similar-image-search-research.md](similar-image-search-research.md)。

## 0. この機能が狙うもの (確定)

ユーザー判断 (2026-09-03) により、狙いは調査メモ §1 の **B = 近重複** に確定。

> ダウンロードした画像の重複を見つけ、**高画質な方を残す判断**をして、
> 重複を消す。漫画も対象。「似た絵」ではなく、**ほぼ同じ画像だが解像度が違う /
> 少し修正が入っている**ものを見つけたい。

**やらないこと (確定)**:
- C (同じキャラ / 別衣装 / 同 seed 別サンプラー) と D (意味的類似) は狙わない。
  AI 生成画像の「似た絵」はフォルダ分けとプロンプト検索でカバーする。
- したがって **埋め込み (CLIP / WD14) は使わない**。ONNX モデルもワーカーも増やさない。

この確定により、**閾値は締める方向**に倒す。誤検出 (無関係な画像がペアになる) は、
取りこぼしより有害である — 削除判断の UI に無関係なペアが混ざると信用を失うため。

## 1. 検出できるもの / できないもの

**検出できる (狙う)**

| 差分 | 例 |
| --- | --- |
| 解像度違い | 同じ絵の 1200px 版と 2400px 版 |
| 再エンコード | JPEG 品質違い、PNG↔JPEG、WebP 変換 |
| 軽微な修正 | 手直し版、色調整、小さなロゴ除去 |
| メタデータのみ違う | 画素は同一、EXIF/タグだけ違う |

**検出できない (v1 では非対象。誤解を招かないよう UI にも書く)**

| 差分 | なぜ |
| --- | --- |
| **切り抜き / 余白追加 / 帯付き** | perceptual hash は位置合わせをしないので構図がずれると別物になる |
| **左右反転** | 同上。必要なら反転版のハッシュも持つ拡張が要る (§10 将来) |
| **大きな回転** | 同上 |
| **特徴の乏しい画像同士** | 真っ白ページ等は原理的に 64bit では区別できない (§5) |

## 2. データモデル

### 2.1 保存先: 独立した `similar.db`

`catalog.db` (サムネイルキャッシュ) には**載せられない**。`thumbnails.thumb_data` が
`NOT NULL` で、キャッシュ設定 Off / Auto では行自体が作られないため
(カラー検索で一度踏んだ罠。[color-search-plan.md](color-search-plan.md) の変遷を参照)。

`fts_meta.db` への相乗りも見送る。FTS の `INDEX_VERSION` を bump したときに
**重複ハッシュまで道連れで消える**のは損が大きすぎる (再生成は数時間かかる)。

```
%APPDATA%/mimageviewer/similar.db

image_hash(
  item_key      TEXT PRIMARY KEY,  -- search_norm::normalize_path と同じ正規化
  mtime         INTEGER NOT NULL,
  file_size     INTEGER NOT NULL,
  hash_version  INTEGER NOT NULL,  -- §3.3
  phash64       INTEGER NOT NULL,  -- 候補生成・単体クエリ用 (8B)
  phash256      BLOB    NOT NULL,  -- 検証・スコア表示用 (32B)
  confidence    INTEGER NOT NULL,  -- 0..255。低いと featureless (§5)
  width         INTEGER NOT NULL,
  height        INTEGER NOT NULL,
  format        INTEGER NOT NULL,  -- JPEG/PNG/WebP/... 「どちらを残すか」判定用
  jpeg_quality  INTEGER            -- 量子化テーブル由来の推定値。取れないとき NULL
)
```

- 1 件あたり署名部は 8 + 32 + 数バイト ≈ **48 バイト**。100 万件で 48 MB。
  実際の DB サイズはパス文字列が支配的で、**合計 150〜250 MB 程度**の見込み。
- 起動時に全行を読むのではなく、**重複機能を初めて使うときに一括ロード**する
  (100 万行の読み出しは数秒かかるため、通常の閲覧を遅くしない)。
  在メモリ表現は `Vec<(phash64, phash256, u32 /*行 id*/)>` = 約 44 MB。

### 2.2 ハッシュ 2 本立てにする理由

- `phash64` — 単体クエリと全件スイープの**線形走査**に使う。狭いほど速い (§4)。
- `phash256` — 64bit で当たった候補を**検証**し、ユーザーに見せる「一致度」を出す。
  64bit だけだと無関係な画像の偶発一致が残るが、256bit まで一致する確率は無視できる。

段階を分けることで、**閾値を締めても取りこぼさない**構造にできる:
64bit 側は少し緩め (候補を広めに拾う) → 256bit 側で厳しく落とす。

## 3. ハッシュ生成

### 3.1 正準パイプライン (ここがずれると全部壊れる)

**同じ画像から常に同じハッシュが出ること**が唯一絶対の不変条件。
入力経路 (元画像 / サムネイル / ZIP 内 / PDF ページ) によってハッシュが変わってはならない。

したがって:

- **サムネイルキャッシュからハッシュを作らない**。サムネイルは設定で解像度が変わり、
  縮小フィルタの経路も違うため、同じ画像でも元画像から作ったハッシュと 1〜3bit ずれる。
  距離 0〜2 で判定する機能では、この 1bit が致命傷になる。
- 常に **元画像をデコード → 固定サイズのグレースケール → DCT** の 1 経路に通す。
- JPEG は既存の `thumb_loader::pick_dct_scale_num(src_max_edge, target_px)` で
  **1/8〜1/1 の縮小デコード**が使えるので、4000px の JPEG でも十分速い。
  ただし *スケール係数の選び方自体が結果を変える*ので、
  「target_px を固定値にし、常に同じ規則で選ぶ」ことをテストで固定する。

### 3.2 手順 (案)

1. 元画像を、長辺が 128px 以上になる最小のスケールでデコード
2. 128×128 のグレースケールへ縮小 (フィルタを 1 つに固定する)
3. 2D DCT → 低周波 16×16 を取り出す
4. 16×16 の 255 個の AC 係数を中央値で 2 値化 → **`phash256`**
5. 同じ係数群の左上 8×8 を別途中央値で 2 値化 → **`phash64`**
6. AC 係数の絶対値の中央値から **`confidence`** を算出 (§5)

### 3.3 `hash_version`

上記の手順を 1 箇所でも変えたら (縮小フィルタ、DCT サイズ、2 値化の基準、
グレースケール変換の係数)、既存のハッシュと互換性が無くなる。
**`hash_version` を上げ、古い行を無効化して再生成する**。
「なんとなく動いているハッシュ」を混在させない。

### 3.4 いつ生成するか

FTS インデクサ ([search-architecture.md](search-architecture.md) §4) と同型の
**明示的なバックグラウンド索引ジョブ**にする。進捗表示・キャンセル・中断再開・
mtime/size による差分更新が要る点も同じ。

**サムネイル生成の副産物にはしない**。理由は 2 つ:
- §3.1 のとおりサムネイルからは作れない (別途デコードが要るので副産物にならない)
- 閲覧したフォルダしか埋まらないと、スキャン結果が「何を見たか」に依存して
  再現しなくなる。重複検出は**スコープ内を全部見た**という保証が要る

コストの目安: 100 万枚のデコードが主。JPEG は縮小デコードが効くので、
並列で **1 時間前後**を見込む (要実測)。**初回は明示的に開始させる**。

## 4. 検索 — 索引は作らない

### 4.1 実測 (本機、単スレッド、`rustc -O -C target-cpu=native`)

| 操作 | 100 万件 |
| --- | --- |
| **単体クエリ** (1 枚 vs 全件、64bit 線形走査) | **0.33 ms** |
| 同上、256bit | 1.6 ms |
| **全件スイープ** (総当たり N²/2、64bit) | **61 秒** (単スレッド) / **5 秒前後** (16 並列) |

### 4.2 したがって VP-tree / BK-tree / MIH / HNSW は作らない

hydrus が VP-tree を持つのは全件ペア列挙のためだが、**総当たりでも 16 並列 5 秒**なので
索引を持つ理由がない。索引を持たなければ:

- 追加は `Vec::push`、削除はエントリ無効化だけ
- 再構築・世代整合・キャンセル中の一貫性という**複雑さが丸ごと発生しない**
- 索引と DB の乖離というバグの種類が存在しない

多段索引 (MIH) も試作して 0.6 秒まで縮んだが、**5 秒を 0.6 秒にするために
ハッシュテーブル 3 本の保守を背負う価値はない**と判断する。

## 5. 特徴の乏しい画像 (白ページ問題) — 最重要

### 5.1 これは「誤検出が少し出る」問題ではない

真っ白 / ほぼ白のページは DCT 低周波がほぼ 0 になり、2 値化した bit は実質ノイズになる。
その結果、**無関係な白ページ同士が距離 0〜2 で当たる**。漫画を含むと大量に発生する。

100 万件のうち 10 万件が「200 種類の白ページの ±1bit ゆらぎ」だと仮定した実測:

| 条件 | 走査時間 | 検出ペア数 |
| --- | --- | --- |
| 均一 (理想) | 0.59 s | **0** |
| 白ページ 10% / 200 種 | 14.70 s | **24,998,937** |
| 白ページ 10% / 200 種 + 退化ハッシュを除外 | 0.70 s | 43,756 |

**2,500 万ペア**が出る。レビュー UI が成立しないどころか、走査自体が 25 倍遅くなる。
対策なしでは漫画を含むライブラリでこの機能は動かない。

### 5.2 対策 = ハッシュ生成時に `confidence` を測って除外する

検索側で「バケットが大きすぎたら捨てる」という後付けの足切りはしない
(閾値でデータを捨てる対症療法で、なぜ捨てたかがテストできない)。
**ハッシュを作った時点で、その 64bit が画像を識別できるだけの根拠を持つかを測る。**

- `confidence` = 2 値化に使った AC 係数の絶対値の中央値を 0..255 に正規化した値
- 閾値未満なら **`featureless`** とし、**候補生成の対象から外す**
- 「この画像の重複を探す」を featureless な画像に対して実行した場合は、
  結果 0 件ではなく **「この画像は特徴が少ないため重複判定できません」と明示する**
  (無言で 0 件を返さない)

閾値は §9 の較正ツールで**実データから決める**。決め打ちしない。

### 5.3 それでも漫画のページ単位重複は薦めない

`featureless` で走査は成立するようになるが、そもそも
**「漫画の 1 ページだけを削除したい」という用途は今回の狙いではない**
(それは Komga の広告ページ掃除の用途)。§6 のとおり本単位にする。

なお `confidence` は「白ページか」だけを見る。**クレジットページのように
特徴はあるが多数の本に共通するページ**は別の問題で、§6.2 で扱う。

## 6. 漫画 (ZIP / PDF / 画像フォルダ) は「本単位」で判定する (決定済み)

判定単位は**ページではなく本**。削除の単位がユーザーの判断単位と一致するため。

### 6.0 扱う関係は「同一」だけではない (2026-09-03 改訂の要点)

初版の草案は「2 冊の一致度 = 対応が取れたページの割合」という **対称な 1 つの指標**
だったが、これでは次の実在ケースを検出できない。

| ケース | 例 | 対称な一致率だと |
| --- | --- | --- |
| **分割 / 統合** | 前後編に分かれた 2 冊 (各 100p) と、統合版 1 冊 (200p) | 100/200 = **50%** → 重複と判定されない |
| **共通ページ追加** | 同じ本に、クレジットページが 1 枚足された版 | 100/101 = 99% → 一応通るが、位置合わせに依存すると崩れる |
| **短い本の偽陽性** | クレジットページしか無い 2 冊 | 100% → **無関係な本が「完全一致」になる** |

さらに草案の候補絞り込み「**ページ数が近い**本だけ比較する」は、
分割/統合ケース (100p と 200p) を**構造的に検出不能にする**。この条件は削除する。

したがって本単位の判定は、以下の 4 点を満たす形にする。

### 6.1 ページの対応付けは「集合」で取る。位置で合わせない

本の署名は「ページ順に並べた列」ではなく **ページハッシュの多重集合**として扱い、
2 冊の対応付けは距離 ≤ r の最大マッチングで取る。

- 先頭にクレジットページが 1 枚挿入されただけで全ページが 1 つずれる、という
  位置合わせ由来の破綻が起きない
- ページ順は**判定には使わず**、結果表示 (どのページが欠けているか) にだけ使う

### 6.2 ページの「識別力」を測る — クレジットページ問題

同人誌のクレジットページ、サークルの宣伝ページ、スキャン団体のロゴページは
**多数の本に共通して現れる**。これを一致に数えると、無関係な本同士が繋がる。

そこで、ページを次の 3 種に分ける。

| 種別 | 定義 | 一致計算での扱い |
| --- | --- | --- |
| **featureless** | §5 の `confidence` が閾値未満 (白ページ等) | 分子・分母の**両方から外す** |
| **ありふれたページ** | 同じページが K 冊を超える本に現れる (クレジット/広告) | 分子・分母の**両方から外す** |
| **識別力のあるページ** | 上記以外 | これだけで一致率を計算する |

**「分子から外すが分母には残す」ことはしない。** 分母に残すと、クレジットページが
1 枚増えただけの版が一致率を落として重複と判定されなくなる (=ケース 2 が壊れる)。
両方から外せば、**クレジットページの有無は一致率にそもそも影響しない**。

「ありふれたページ」の判定は、ページ全件走査 (§4) の結果から作る。
距離 ≤ r で繋がったページのクラスタが何冊にまたがるかを数え、K 冊超なら
ありふれたページとする。**このクラスタリングは単連結 (single linkage) なので、
連鎖でクラスタが際限なく育つ危険がある**。クラスタの直径に上限を設けるか、
代表ハッシュからの距離で判定するかは、§10 の較正で実データを見て決める。

### 6.3 カバー率は両方向で持ち、関係を分類する

`matched` = 識別力のあるページのうち、距離 ≤ r で対応が取れた枚数。

```
coverage_A = matched / (A の識別力のあるページ数)
coverage_B = matched / (B の識別力のあるページ数)
```

| 判定 | 条件 | 意味 |
| --- | --- | --- |
| **同一** | 両方 ≥ 閾値 | 同じ本。解像度・再エンコード・クレジット差のみ |
| **包含** | 片方のみ ≥ 閾値 | 片方がもう片方の一部。**分割/統合はここに出る** |
| 無関係 | 両方 < 閾値 | |

**分割/統合はこの「包含」から自然に出る。** 統合版 C に対して、前編 A と後編 B が
それぞれ `coverage_A→C = 100%` / `coverage_B→C = 100%` になるので、
結果 UI は **「C に含まれる本: A, B」** という形で 1 グループにまとめられる。
「A と B の和が C を覆い切るか」の検証 (union coverage) は仕上げの精度向上であって、
**グループを見せるだけなら不要**。初版では包含の一覧までを出す。

### 6.4 候補生成 — ページ数は使わない

候補本ペアは **「距離 ≤ r で一致する識別力のあるページを 1 枚以上共有する本」**。
ページ全件走査 (§4、100 万ページで 16 並列 5 秒前後) が出すページペアを
本 ID に畳むだけで得られる。ページ数の近さは条件に入れない (§6.0)。

本ペアの総当たり (3.3 万冊 → 5.4 億ペア) はやらない。走査はページ単位のまま 1 回。

### 6.5 判定できない本は「判定不能」と言う

識別力のあるページが **0 枚** の本 (白ページだけ、クレジットページだけ) は、
一致率の分母が 0 になる。**0% でも 100% でもなく「判定不能」を返す。**
§5.2 の featureless 画像と同じ原則で、無言で 0 件や誤った 100% を返さない。

### 6.6 検出できない (v1 では非対象)

- **別々にスキャンされた同じ本** — トリミング位置・レベル補正・傾き補正が違うと
  ページの pHash が離れる。§1 の「切り抜きは検出できない」と同じ理由
- **ページの並べ替えのみが違う版** — 集合で見るので「同一」と判定される。
  これは仕様 (並び順の違いは重複として扱ってよい)

### 6.7 実装コスト上の注意

**ZIP 内ページのハッシュ生成は別パイプラインになる** (ZIP を開いて全ページをデコードする)。
`fts_meta.db` は ZIP を 1 行として持つだけでページ行を持たないため、ここは新規に要る。
`similar.db` にも本↔ページの対応表 (`book_page(book_key, page_index, item_key)`) が要る。

## 7. 「どちらを残すか」の判定

**自動削除はしない。** 推奨を出して理由を書き、決めるのはユーザー。

推奨スコア (上から順に見て、決まった時点で確定。決まらなければ次へ):

1. **画素数 (幅×高さ) が大きい方**
2. **可逆形式** (PNG / 可逆 WebP) > 非可逆 (JPEG / 非可逆 WebP)
3. **JPEG 品質推定が高い方** (量子化テーブルから推定。取れないときはスキップ)
4. **ファイルサイズが大きい方**
5. **mtime が古い方** (オリジナルの可能性が高い)

さらに UI に出す注意 (自動判定には使わないが、判断材料として表示する):

- **AI プロンプト等のメタデータを持っている方**は元ファイルであることが多い
  (mIV は既に PNG tEXt / EXIF を読める)
- **mIV の AI アップスケールで作った派生物**は「高解像度だが元ではない」。
  画素数だけで決めると派生物を残してしまう。**推奨理由を必ず文字で見せる**のはこのため

推奨は必ず「なぜそれを推したか」を 1 行で表示する (「2400×3200 (相手は 1200×1600)」等)。
理由を出さない推奨は入れない。

## 8. 削除 — 既存経路をそのまま使う

mIV には既に **「ゴミ箱へ移動 (タグ・評価も整理)」** がある
(`context_menu_model.rs` の `MenuCommand::MoveToRecycleBin`、
バックグラウンドのゴミ箱移動ワーカー、削除確認ダイアログはドライブ種別と
ゴミ箱設定で文言が変わる)。**重複整理専用の削除経路を新設しない。**

- 復元可能 (ゴミ箱) であることが、この機能の安全性の土台
- タグ・レーティングの後始末が既に組まれている
- 削除確認ダイアログも既存のものを通す

## 9. UI

### 9.1 入口 A: 「この画像の重複を探す」 (単体クエリ)

- 右クリックメニュー / フルスクリーンのメタデータパネルから起動
- 0.33 ms で返るので**同期で出してよい**
- 結果は**場所をまたいだフラット一覧**に出す。
  `TopLevelGridSurface` に `Duplicates` を追加する
  (`ReadingHistory` / `Rating` / `Bookmarks` と同じ形。既存の合成パス機構に乗る)
- そこから既存の「この場所を開く」で類似先フォルダへジャンプできる

### 9.2 入口 B: 「重複をまとめて探す」 (全件スイープ、初版に入れる)

- 明示的に開始。スコープはお気に入り配下 (= Ctrl+G と同じ範囲)。任意フォルダ指定は初版では作らない
- 結果はグループ一覧 (1 グループ = 同一と判定された画像の集合)
- 各グループで推奨 1 枚に印、残りにチェック → 「チェックをゴミ箱へ」

### 9.3 検証は既存の比較表示をそのまま使う

mIV には既に比較機能がある — グリッドから `X` でピン留め (`GridComparePin`)、
フルスクリーンで `FsCompareToggle` / `Cycle` / **`Wipe`** / **`Diff`**。
**この `Diff` こそが「本当に同じ画像か / どこが違うか」を人間が確かめる道具**なので、
重複レビュー UI から既存の比較表示へ渡すだけでよい。**新しい比較 UI を作らない。**

### 9.4 閾値の見せ方

生のハミング距離は見せない。「厳密 / 標準 / ゆるめ」の 3 段にする。
各段が実際にどの距離かは §10 の較正で決め、ドキュメントには数値を書く。

## 10. 閾値の較正 — 数値を推測で決めない

hydrus の「距離 4 = 髪型や衣装の違い」といった数値は 64bit pHash の話であり、
本設計の 256bit + 独自の縮小経路にそのまま当てはまらない。
**ユーザーの実データで測ってから決める。**

`--features dev-tools` の bin (`bench_dupe`、`bench_thumbs` と同じ扱い) を用意し、
指定フォルダに対して:

1. 各画像から、**既知の重複**を合成する (50%/75% 縮小、JPEG q=95/85/70 再圧縮、
   PNG→JPEG 変換、右下に小さなロゴを合成)
2. 「同一画像とその派生」の距離分布と、「無関係な画像同士」の距離分布を出す
3. 2 つの分布が分離する点を閾値にする。**分離しないなら設計を見直す**
4. `confidence` の分布も同時に出し、featureless の閾値を決める

この較正結果を本ドキュメントに追記してから実装を確定する。

## 12. テスト方針 (骨子)

- **正準性**: 同じ画像を別経路 (元画像 / ZIP 内 / PDF ページ) から通しても
  ハッシュが完全一致すること。これが崩れたら機能全体が無意味になるので最優先。
- **`hash_version`**: 版が違う行を再利用しないこと。
- **featureless**: 合成した near-blank 画像 2 枚が候補ペアに**ならない**こと。
  featureless な画像への単体クエリが 0 件ではなく「判定不能」を返すこと。
- **本単位の関係判定** (§6): 合成した本の集合で、以下がテーブル駆動で確定すること。
  ここは純ロジックなので、実画像を使わずページハッシュ列だけで書ける。
  - 前編 (100p) + 後編 (100p) と統合版 (200p) → **包含** 2 件。
    「ページ数が近い本だけ比較」に退行したらこのテストが落ちる
  - クレジットページを 1 枚足した版 → **同一** (一致率が下がらないこと)
  - クレジットページを**先頭に**挿入した版 → **同一**
    (位置合わせに退行したらここで落ちる)
  - 同じクレジットページしか共有しない無関係な 2 冊 → **無関係**
  - 識別力のあるページが 0 枚の本 → **判定不能** (0% でも 100% でもない)
  - ページを並べ替えただけの版 → **同一** (仕様として固定する)
- **推奨判定**: §7 の順序が同点処理も含めて決定的であること (テーブル駆動テスト)。
- **削除**: 既存のゴミ箱経路を通ること (専用経路を作っていないことの回帰テスト)。
- **性能**: 合成 100 万件で単体クエリが 1 ms 未満、スイープが所定時間内。
