# 重複画像の検出と整理 — 設計計画

> ステータス: **設計 v0。Codex Sol レビュー済み (2026-09-03) → 実装保留。**
> §13 に指摘と対応方針。**§2〜§7 の記述は保留中であり、そのまま実装しないこと。**
> 調査の前段は [similar-image-search-research.md](similar-image-search-research.md)。

## 0. この機能が狙うもの (確定)

ユーザー判断 (2026-09-03) により、狙いは調査メモ §1 の **B = 近重複** に確定。

> ダウンロードした画像の重複を見つけ、**高画質な方を残す判断**をして、
> 重複を消す。漫画も対象。「似た絵」ではなく、**ほぼ同じ画像だが解像度が違う /
> 少し修正が入っている**ものを見つけたい。

**やらないこと (確定)**:
- C (同じキャラ / 別衣装 / 同 seed 別サンプラー) と D (意味的類似) は狙わない。
  AI 生成画像の「似た絵」はフォルダ分けとプロンプト検索でカバーする。
- したがって **埋め込み (CLIP / WD14) は使わない**。ONNX モデルもワーカーも増やさない。

この確定により、**閾値は締める方向**に倒す。誤検出 (無関係な画像がペアになる) は、
取りこぼしより有害である — 削除判断の UI に無関係なペアが混ざると信用を失うため。

## 1. 検出できるもの / できないもの

**検出できる (狙う)**

| 差分 | 例 |
| --- | --- |
| 解像度違い | 同じ絵の 1200px 版と 2400px 版 |
| 再エンコード | JPEG 品質違い、PNG↔JPEG、WebP 変換 |
| 軽微な修正 | 手直し版、色調整、小さなロゴ除去 |
| メタデータのみ違う | 画素は同一、EXIF/タグだけ違う |

**検出できない (v1 では非対象。誤解を招かないよう UI にも書く)**

| 差分 | なぜ |
| --- | --- |
| **切り抜き / 余白追加 / 帯付き** | perceptual hash は位置合わせをしないので構図がずれると別物になる |
| **左右反転** | 同上。必要なら反転版のハッシュも持つ拡張が要る (§10 将来) |
| **大きな回転** | 同上 |
| **特徴の乏しい画像同士** | 真っ白ページ等は原理的に 64bit では区別できない (§5) |

## 2. データモデル

### 2.1 保存先: 独立した `similar.db`

`catalog.db` (サムネイルキャッシュ) には**載せられない**。`thumbnails.thumb_data` が
`NOT NULL` で、キャッシュ設定 Off / Auto では行自体が作られないため
(カラー検索で一度踏んだ罠。[color-search-plan.md](color-search-plan.md) の変遷を参照)。

`fts_meta.db` への相乗りも見送る。FTS の `INDEX_VERSION` を bump したときに
**重複ハッシュまで道連れで消える**のは損が大きすぎる (再生成は数時間かかる)。

```
%APPDATA%/mimageviewer/similar.db

image_hash(
  item_key      TEXT PRIMARY KEY,  -- search_norm::normalize_path と同じ正規化
  mtime         INTEGER NOT NULL,
  file_size     INTEGER NOT NULL,
  hash_version  INTEGER NOT NULL,  -- §3.3
  phash64       INTEGER NOT NULL,  -- 候補生成・単体クエリ用 (8B)
  phash256      BLOB    NOT NULL,  -- 検証・スコア表示用 (32B)
  confidence    INTEGER NOT NULL,  -- 0..255。低いと featureless (§5)
  width         INTEGER NOT NULL,
  height        INTEGER NOT NULL,
  format        INTEGER NOT NULL,  -- JPEG/PNG/WebP/... 「どちらを残すか」判定用
  jpeg_quality  INTEGER            -- 量子化テーブル由来の推定値。取れないとき NULL
)
```

- 1 件あたり署名部は 8 + 32 + 数バイト ≈ **48 バイト**。100 万件で 48 MB。
  実際の DB サイズはパス文字列が支配的で、**合計 150〜250 MB 程度**の見込み。
- 起動時に全行を読むのではなく、**重複機能を初めて使うときに一括ロード**する
  (100 万行の読み出しは数秒かかるため、通常の閲覧を遅くしない)。
  在メモリ表現は `Vec<(phash64, phash256, u32 /*行 id*/)>` = 約 44 MB。

### 2.2 ハッシュ 2 本立てにする理由

- `phash64` — 単体クエリと全件スイープの**線形走査**に使う。狭いほど速い (§4)。
- `phash256` — 64bit で当たった候補を**検証**し、ユーザーに見せる「一致度」を出す。
  64bit だけだと無関係な画像の偶発一致が残るが、256bit まで一致する確率は無視できる。

段階を分けることで、**閾値を締めても取りこぼさない**構造にできる:
64bit 側は少し緩め (候補を広めに拾う) → 256bit 側で厳しく落とす。

## 3. ハッシュ生成

### 3.1 正準パイプライン (ここがずれると全部壊れる)

**同じ画像から常に同じハッシュが出ること**が唯一絶対の不変条件。
入力経路 (元画像 / サムネイル / ZIP 内 / PDF ページ) によってハッシュが変わってはならない。

したがって:

- **サムネイルキャッシュからハッシュを作らない**。サムネイルは設定で解像度が変わり、
  縮小フィルタの経路も違うため、同じ画像でも元画像から作ったハッシュと 1〜3bit ずれる。
  距離 0〜2 で判定する機能では、この 1bit が致命傷になる。
- 常に **元画像をデコード → 固定サイズのグレースケール → DCT** の 1 経路に通す。
- JPEG は既存の `thumb_loader::pick_dct_scale_num(src_max_edge, target_px)` で
  **1/8〜1/1 の縮小デコード**が使えるので、4000px の JPEG でも十分速い。
  ただし *スケール係数の選び方自体が結果を変える*ので、
  「target_px を固定値にし、常に同じ規則で選ぶ」ことをテストで固定する。

### 3.2 手順 (案)

1. 元画像を、長辺が 128px 以上になる最小のスケールでデコード
2. 128×128 のグレースケールへ縮小 (フィルタを 1 つに固定する)
3. 2D DCT → 低周波 16×16 を取り出す
4. 16×16 の 255 個の AC 係数を中央値で 2 値化 → **`phash256`**
5. 同じ係数群の左上 8×8 を別途中央値で 2 値化 → **`phash64`**
6. AC 係数の絶対値の中央値から **`confidence`** を算出 (§5)

### 3.3 `hash_version`

上記の手順を 1 箇所でも変えたら (縮小フィルタ、DCT サイズ、2 値化の基準、
グレースケール変換の係数)、既存のハッシュと互換性が無くなる。
**`hash_version` を上げ、古い行を無効化して再生成する**。
「なんとなく動いているハッシュ」を混在させない。

### 3.4 いつ生成するか

FTS インデクサ ([search-architecture.md](search-architecture.md) §4) と同型の
**明示的なバックグラウンド索引ジョブ**にする。進捗表示・キャンセル・中断再開・
mtime/size による差分更新が要る点も同じ。

**サムネイル生成の副産物にはしない**。理由は 2 つ:
- §3.1 のとおりサムネイルからは作れない (別途デコードが要るので副産物にならない)
- 閲覧したフォルダしか埋まらないと、スキャン結果が「何を見たか」に依存して
  再現しなくなる。重複検出は**スコープ内を全部見た**という保証が要る

コストの目安: 100 万枚のデコードが主。JPEG は縮小デコードが効くので、
並列で **1 時間前後**を見込む (要実測)。**初回は明示的に開始させる**。

## 4. 検索 — 索引は作らない

> §13-L: この節の数値のうち「16 並列 5 秒」は**未計測の外挿**。
> 全件スイープを v1 に入れると決めた以上、スイープ時だけ張る一時的な多段索引は再評価対象。

### 4.1 実測 (本機、単スレッド、`rustc -O -C target-cpu=native`)

| 操作 | 100 万件 |
| --- | --- |
| **単体クエリ** (1 枚 vs 全件、64bit 線形走査) | **0.33 ms** |
| 同上、256bit | 1.6 ms |
| **全件スイープ** (総当たり N²/2、64bit) | **61 秒** (単スレッド) / 16 並列は**未計測** |

### 4.2 したがって VP-tree / BK-tree / MIH / HNSW は作らない

hydrus が VP-tree を持つのは全件ペア列挙のためだが、**総当たりでも 16 並列 5 秒**なので
索引を持つ理由がない。索引を持たなければ:

- 追加は `Vec::push`、削除はエントリ無効化だけ
- 再構築・世代整合・キャンセル中の一貫性という**複雑さが丸ごと発生しない**
- 索引と DB の乖離というバグの種類が存在しない

多段索引 (MIH) も試作して 0.6 秒まで縮んだが、**5 秒を 0.6 秒にするために
ハッシュテーブル 3 本の保守を背負う価値はない**と判断する。

## 5. 特徴の乏しい画像 (白ページ問題) — 最重要

### 5.1 これは「誤検出が少し出る」問題ではない

真っ白 / ほぼ白のページは DCT 低周波がほぼ 0 になり、2 値化した bit は実質ノイズになる。
その結果、**無関係な白ページ同士が距離 0〜2 で当たる**。漫画を含むと大量に発生する。

100 万件のうち 10 万件が「200 種類の白ページの ±1bit ゆらぎ」だと仮定した実測:

| 条件 (いずれも**多段索引 (MIH) 版**の走査。§4.1 の総当たり 61 秒とは別アルゴリズム) | 走査時間 | 検出ペア数 |
| --- | --- | --- |
| 均一 (理想) | 0.59 s | **0** |
| 白ページ 10% / 200 種 | 14.70 s | **24,998,937** |
| 白ページ 10% / 200 種 + 退化ハッシュを除外 | 0.70 s | 43,756 |

**2,500 万ペア**が出る。レビュー UI が成立しないどころか、走査自体が 25 倍遅くなる。
対策なしでは漫画を含むライブラリでこの機能は動かない。

### 5.2 対策 = ハッシュ生成時に `confidence` を測って除外する

検索側で「バケットが大きすぎたら捨てる」という後付けの足切りはしない
(閾値でデータを捨てる対症療法で、なぜ捨てたかがテストできない)。
**ハッシュを作った時点で、その 64bit が画像を識別できるだけの根拠を持つかを測る。**

- `confidence` = 2 値化に使った AC 係数の絶対値の中央値を 0..255 に正規化した値
- 閾値未満なら **`featureless`** とし、**候補生成の対象から外す**
- 「この画像の重複を探す」を featureless な画像に対して実行した場合は、
  結果 0 件ではなく **「この画像は特徴が少ないため重複判定できません」と明示する**
  (無言で 0 件を返さない)

閾値は §9 の較正ツールで**実データから決める**。決め打ちしない。

### 5.3 それでも漫画のページ単位重複は薦めない

`featureless` で走査は成立するようになるが、そもそも
**「漫画の 1 ページだけを削除したい」という用途は今回の狙いではない**
(それは Komga の広告ページ掃除の用途)。§6 のとおり本単位にする。

なお `confidence` は「白ページか」だけを見る。**クレジットページのように
特徴はあるが多数の本に共通するページ**は別の問題で、§6.2 で扱う。

## 6. 漫画 (ZIP / PDF / 画像フォルダ) は「本単位」で判定する (決定済み)

判定単位は**ページではなく本**。削除の単位がユーザーの判断単位と一致するため。

### 6.0 扱う関係は「同一」だけではない (2026-09-03 改訂の要点)

初版の草案は「2 冊の一致度 = 対応が取れたページの割合」という **対称な 1 つの指標**
だったが、これでは次の実在ケースを検出できない。

| ケース | 例 | 対称な一致率だと |
| --- | --- | --- |
| **分割 / 統合** | 前後編に分かれた 2 冊 (各 100p) と、統合版 1 冊 (200p) | 100/200 = **50%** → 重複と判定されない |
| **共通ページ追加** | 同じ本に、クレジットページが 1 枚足された版 | 100/101 = 99% → 一応通るが、位置合わせに依存すると崩れる |
| **短い本の偽陽性** | クレジットページしか無い 2 冊 | 100% → **無関係な本が「完全一致」になる** |

さらに草案の候補絞り込み「**ページ数が近い**本だけ比較する」は、
分割/統合ケース (100p と 200p) を**構造的に検出不能にする**。この条件は削除する。

したがって本単位の判定は、以下の 4 点を満たす形にする。

### 6.1 ページの対応付けは「集合」で取る。位置で合わせない

本の署名は「ページ順に並べた列」ではなく **ページハッシュの多重集合**として扱い、
2 冊の対応付けは距離 ≤ r の最大マッチングで取る。

- 先頭にクレジットページが 1 枚挿入されただけで全ページが 1 つずれる、という
  位置合わせ由来の破綻が起きない
- ページ順は**判定には使わず**、結果表示 (どのページが欠けているか) にだけ使う

### 6.2 ページの「識別力」を測る — クレジットページ問題

同人誌のクレジットページ、サークルの宣伝ページ、スキャン団体のロゴページは
**多数の本に共通して現れる**。これを一致に数えると、無関係な本同士が繋がる。

そこで、ページを次の 3 種に分ける。

| 種別 | 定義 | 一致計算での扱い |
| --- | --- | --- |
| **featureless** | §5 の `confidence` が閾値未満 (白ページ等) | 分子・分母の**両方から外す** |
| **ありふれたページ** | 同じページが K 冊を超える本に現れる (クレジット/広告) | 分子・分母の**両方から外す** |
| **識別力のあるページ** | 上記以外 | これだけで一致率を計算する |

**「分子から外すが分母には残す」ことはしない。** 分母に残すと、クレジットページが
1 枚増えただけの版が一致率を落として重複と判定されなくなる (=ケース 2 が壊れる)。
両方から外せば、**クレジットページの有無は一致率にそもそも影響しない**。

「ありふれたページ」の判定は、ページ全件走査 (§4) の結果から作る。
距離 ≤ r で繋がったページのクラスタが何冊にまたがるかを数え、K 冊超なら
ありふれたページとする。**このクラスタリングは単連結 (single linkage) なので、
連鎖でクラスタが際限なく育つ危険がある**。クラスタの直径に上限を設けるか、
代表ハッシュからの距離で判定するかは、§10 の較正で実データを見て決める。

### 6.3 カバー率は両方向で持ち、関係を分類する

`matched` = 識別力のあるページのうち、距離 ≤ r で対応が取れた枚数。

```
coverage_A = matched / (A の識別力のあるページ数)
coverage_B = matched / (B の識別力のあるページ数)
```

| 判定 | 条件 | 意味 |
| --- | --- | --- |
| **同一** | 両方 ≥ 閾値 | 同じ本。解像度・再エンコード・クレジット差のみ |
| **包含** | 片方のみ ≥ 閾値 | 片方がもう片方の一部。**分割/統合はここに出る** |
| 無関係 | 両方 < 閾値 | |

**分割/統合はこの「包含」から自然に出る。** 統合版 C に対して、前編 A と後編 B が
それぞれ `coverage_A→C = 100%` / `coverage_B→C = 100%` になるので、
結果 UI は **「C に含まれる本: A, B」** という形で 1 グループにまとめられる。
「A と B の和が C を覆い切るか」の検証 (union coverage) は仕上げの精度向上であって、
**グループを見せるだけなら不要**。初版では包含の一覧までを出す。

### 6.4 候補生成 — ページ数は使わない

候補本ペアは **「距離 ≤ r で一致する識別力のあるページを 1 枚以上共有する本」**。
ページ全件走査 (§4、100 万ページで 16 並列 5 秒前後) が出すページペアを
本 ID に畳むだけで得られる。ページ数の近さは条件に入れない (§6.0)。

本ペアの総当たり (3.3 万冊 → 5.4 億ペア) はやらない。走査はページ単位のまま 1 回。

### 6.5 判定できない本は「判定不能」と言う

識別力のあるページが **0 枚** の本 (白ページだけ、クレジットページだけ) は、
一致率の分母が 0 になる。**0% でも 100% でもなく「判定不能」を返す。**
§5.2 の featureless 画像と同じ原則で、無言で 0 件や誤った 100% を返さない。

### 6.6 検出できない (v1 では非対象)

- **別々にスキャンされた同じ本** — トリミング位置・レベル補正・傾き補正が違うと
  ページの pHash が離れる。§1 の「切り抜きは検出できない」と同じ理由
- **ページの並べ替えのみが違う版** — 集合で見るので「同一」と判定される。
  これは仕様 (並び順の違いは重複として扱ってよい)

### 6.7 実装コスト上の注意

**ZIP 内ページのハッシュ生成は別パイプラインになる** (ZIP を開いて全ページをデコードする)。
`fts_meta.db` は ZIP を 1 行として持つだけでページ行を持たないため、ここは新規に要る。
`similar.db` にも本↔ページの対応表 (`book_page(book_key, page_index, item_key)`) が要る。

## 7. 「どちらを残すか」の判定

**自動削除はしない。** 推奨を出して理由を書き、決めるのはユーザー。

推奨スコア (上から順に見て、決まった時点で確定。決まらなければ次へ):

1. **画素数 (幅×高さ) が大きい方**
2. **可逆形式** (PNG / 可逆 WebP) > 非可逆 (JPEG / 非可逆 WebP)
3. **JPEG 品質推定が高い方** (量子化テーブルから推定。取れないときはスキップ)
4. **ファイルサイズが大きい方**
5. **mtime が古い方** (オリジナルの可能性が高い)

さらに UI に出す注意 (自動判定には使わないが、判断材料として表示する):

- **AI プロンプト等のメタデータを持っている方**は元ファイルであることが多い
  (mIV は既に PNG tEXt / EXIF を読める)
- **mIV の AI アップスケールで作った派生物**は「高解像度だが元ではない」。
  画素数だけで決めると派生物を残してしまう。**推奨理由を必ず文字で見せる**のはこのため

推奨は必ず「なぜそれを推したか」を 1 行で表示する (「2400×3200 (相手は 1200×1600)」等)。
理由を出さない推奨は入れない。

## 8. 削除 — 既存経路をそのまま使う

mIV には既に **「ゴミ箱へ移動 (タグ・評価も整理)」** がある
(`context_menu_model.rs` の `MenuCommand::MoveToRecycleBin`、
バックグラウンドのゴミ箱移動ワーカー、削除確認ダイアログはドライブ種別と
ゴミ箱設定で文言が変わる)。**重複整理専用の削除経路を新設しない。**

- 復元可能 (ゴミ箱) であることが、この機能の安全性の土台
- タグ・レーティングの後始末が既に組まれている
- 削除確認ダイアログも既存のものを通す

## 12. テスト方針 (骨子)

- **正準性**: 同じ画像を別経路 (元画像 / ZIP 内 / PDF ページ) から通しても
  ハッシュが完全一致すること。これが崩れたら機能全体が無意味になるので最優先。
- **`hash_version`**: 版が違う行を再利用しないこと。
- **featureless**: 合成した near-blank 画像 2 枚が候補ペアに**ならない**こと。
  featureless な画像への単体クエリが 0 件ではなく「判定不能」を返すこと。
- **本単位の関係判定** (§6): 合成した本の集合で、以下がテーブル駆動で確定すること。
  ここは純ロジックなので、実画像を使わずページハッシュ列だけで書ける。
  - 前編 (100p) + 後編 (100p) と統合版 (200p) → **包含** 2 件。
    「ページ数が近い本だけ比較」に退行したらこのテストが落ちる
  - クレジットページを 1 枚足した版 → **同一** (一致率が下がらないこと)
  - クレジットページを**先頭に**挿入した版 → **同一**
    (位置合わせに退行したらここで落ちる)
  - 同じクレジットページしか共有しない無関係な 2 冊 → **無関係**
  - 識別力のあるページが 0 枚の本 → **判定不能** (0% でも 100% でもない)
  - ページを並べ替えただけの版 → **同一** (仕様として固定する)
- **推奨判定**: §7 の順序が同点処理も含めて決定的であること (テーブル駆動テスト)。
- **削除**: 既存のゴミ箱経路を通ること (専用経路を作っていないことの回帰テスト)。
- **性能**: 合成 100 万件で単体クエリが 1 ms 未満、スイープが所定時間内。

## 13. Codex Sol レビュー結果 (2026-09-03) — 実装保留

`codex exec -c model="gpt-5.6-sol" --sandbox read-only` で設計レビューを実施。
総合判定は **「方向性は採用。アルゴリズムと本判定は再設計。実装着手は保留」**。
以下、ClaudeCode 側で裏取りした結果を付けて記録する。

### 13.1 検証して「指摘が正しい」と確認したもの (実装前に解決必須)

- **A. §3.2 の 256bit の作り方が算術的に不可能。**
  16×16 = 256 係数から DC を除くと **255**。255 個の AC から 256bit は作れない。
  8×8 も DC を除けば 63bit。PDQ は 64×64 グレースケールから **DC を避けた
  16×16 の周波数スロット**を使って 256bit にしている。ここを踏襲する。

- **B. 「64bit で候補 → 256bit で検証」は安全な二段階ではない。**
  同じ DCT 係数を別々の中央値で 2 値化すると強く相関するため、64bit 段で落ちた
  真の重複を 256bit 段は救えない。§2.2 の「緩く→厳しくすれば取りこぼさない」は
  **根拠がない**。
  修正案 (数学的に正しいことを確認): 前段を **256bit の実ビット部分集合**にする。
  `d256 <= R` ならその部分集合の距離も必ず `<= R` なので、同じ R で前段を切れば
  recall が構造的に保証される。

- **C. §6.2 の「K 冊超えを common として除外」は破綻する。**
  同じ本のコピーを K+1 冊持っていると**本文全ページが common 扱いになり、
  最も明白な重複本が判定不能になる**。再版・人気作の複数保存でも同じ。
  → 完全除外をやめ、**文書頻度による重み付け** (`log((全冊数+1)/(近傍を含む冊数+1))`)
  にする。クレジット追加は低い重みなので coverage をほぼ落とさず、
  固有の追加ページは高い重みで残る。featureless だけ重み 0 でよい。

- **D. §1 と §5/§9 が矛盾している。**
  §1 は「小さなロゴ除去」を検出対象に挙げているが、小さな透かしの追加は
  64bit pHash で中央値 8bit 程度という報告がある。**距離 0〜2 前提とは両立しない。**
  どちらかを直す (検出対象から外す / 閾値を上げる) 必要がある。

- **E. ペアからグループを作る方法が未設計。** 近重複関係は推移的ではない
  (A≒B、B≒C でも A≒C とは限らない)。単連結でグループ化すると修正の連鎖で
  別物が同じ削除グループに入る。medoid 半径・complete-link 相当・代表との再検証など、
  **グループ化規則を明示的に決める**。

- **F. 本の索引に原子性がない。** 200 ページ中 100 ページでキャンセル/失敗/差し替えが
  起きると、不完全な本から誤った coverage が出る。
  `book_scan_state = Building | Complete | Failed` + container generation を持ち、
  **Complete 世代だけを検索対象にする**。

- **G. 片方向 coverage 100% は「重複」ではない。** 短い試し読み本やサンプルが、
  長い本やアンソロジーの一部と一致する。最低一致ページ数だけでなく
  **最低情報量・連続一致長・順序整合**が要る。

- **H. アンソロジーに一作品が丸ごと入っている場合、包含だが削除候補ではない。**
  「同一冊」「版違い」「部分収録」「分割/統合」を別分類にし、
  **包含には削除推奨を出さない**。

- **I. §6.1 でページ順を完全に捨てたのは行き過ぎ。** クレジット 1 枚の挿入は、
  挿入・削除を許す**順序アラインメント** (ページ候補辺の重み付き最長単調列) で
  普通に扱える。順序を捨てると証拠を 1 つ失う。

- **J. §5 の `confidence` は「ハッシュの信頼性」を測っていない。**
  AC 係数絶対値の中央値は主にコントラスト/テクスチャ量。bit の安定性は
  **2 値化閾値からどれだけ離れているか**で決まる。また「コーパス内での識別力」は
  単一画像だけでは分からない。少なくとも
  `content_energy` / `hash_stability` / `corpus_density` の 3 つに分ける。
  → **PDQ は同じ目的の quality 指標を既に持っており** (視覚的に一様すぎる画像を弾く)、
  自作するより PDQ のものを較正して使う方が根拠がある。

- **K. §3.1 の「bit 完全一致が唯一絶対の不変条件」は言い過ぎ。**
  必要な不変条件は「支持する全経路で、**判定が変わらない範囲に距離が収まる**こと」。
  PDF ラスタと元画像、別 decoder、既存 WebP サムネイルに bit 完全一致を要求するのは
  非現実的。「1〜3bit しかずれない」も**根拠のない数値**だった。

- **L. 「16 並列で 5 秒」は未計測の外挿。** 5,000 億比較はメモリ帯域律速なので
  単スレッド値を 16 で割れない。§4 に注記済み。

- **M. 実装前に決めるべきで計画に無かったもの**:
  削除直前の再検証 (レビュー後に対象パスの中身が差し替わっている可能性)、
  **削除側にしか無いタグ・評価・注釈の統合方針**、
  「別物」と判定した組を再スキャンのたびに再表示しない ignore の永続化、
  ICC/gamma/alpha/EXIF orientation/PDF レンダ DPI などの正準化仕様、
  「本」の境界 (ネストフォルダ、ZIP 内の章、アンソロジー内ディレクトリ)。

- **N. §7 の画質推奨を辞書順で単一の勝者にするのは危うい。**
  高解像度は単なるアップスケールかもしれず、PNG は JPEG 画素の再保存かもしれず、
  JPEG quality 値は encoder 間で共通尺度ではなく、古い mtime がオリジナルとも限らない。
  **参考信号として並べ、単一の勝者を自動確定しない**。

### 13.2 ClaudeCode 側で留保・反論した点

- **サムネイル再利用の利得は「未知」であって「大きい」ではない。**
  Codex は「支配的コスト (100 万枚のデコード) が消える」としているが、それが成立するのは
  `catalog.db` のサムネイル被覆率が高い場合だけ。キャッシュ設定 Off / Auto では
  行自体が無い (§2.1)。**まず被覆率を測る**。測る前に per-source 閾値と遅延再検証の
  複雑さを設計へ入れるのは順序が逆。ただし K のとおり §3.1 の書き方は言い過ぎなので、
  「bit 完全一致」ではなく「判定が変わらない範囲」に書き換えるのは受け入れる。

- **§5.1 の 0.59s と §4.1 の 61 秒は矛盾ではない** (前者は MIH、後者は総当たり)。
  ただしドキュメントがアルゴリズム名を書いていなかったのは事実なので注記した。

- **PDQ も平坦ページ問題そのものは解かない** (Codex も認めている)。
  PDQ を採る利点は ①標準実装と較正済みの quality 指標がある ②距離分布が研究されている
  ③自作ハッシュの「根拠がない」状態を回避できる、の 3 点。
  漫画特有の問題は**連続値検証の側**で解く。

- **Rust の PDQ 実装は古い。** `pdqhash` 0.1.1 (Apache-2.0、2022-07、`image` 0.23 依存)
  は mIV の `image` と重複依存になる。どうせ自前のグレースケールバッファを食わせるので、
  **仕様に沿って自前実装/移植する**のが現実的。Codex はこの実装コストに触れていない。

- **連続値検証の保存コストを Codex は定量していない。**
  32×32 グレースケールを全件持つと 1 KB/件 = 100 万件で 1 GB。
  **候補ペアだけ再デコードすれば保存は不要**。まずこちらを検討する。

### 13.3 これを受けた次の一手 (§10 を差し替える)

較正だけでは足りず、**アルゴリズムの bake-off** が要る。順序:

1. **実データの正解集合を作る。** 合成リサイズだけでは不十分。実際の再ダウンロード、
   別解像度、JPEG 再圧縮、軽微な修正、漫画、再版、アンソロジー、分割/統合を
   手作業でラベル付けし、**閾値調整用と最終評価用を分ける**。
2. **受入基準を先に決める。** pair/group precision、既知重複の recall、
   1 回の全件走査で人間に確認させる誤候補の上限、判定不能率。
   5,000 億組では極小の偽陽性率でも大量の誤候補になるため、平均距離分布では足りない。
3. **bake-off**: PDQ-256 / 現行 pHash 案 / blockhash / 16×16・32×32 の連続値輝度 /
   勾配距離を、**同じ実データ・同じ hard negatives** で比較する。
   連続値側は L2 一本ではなく、輝度 L1・gain/offset 補正後の L1・勾配 L1・
   **大差画素の面積率** (小ロゴや局所修正を「小面積差」として扱う)・アスペクト比を別々に持つ。
4. **その結果が出てから** `similar.db` のスキーマを確定する。

**ユーザーへの依頼事項**: 1 の正解集合には実データが要る。
「同じ画像の別解像度版」「再版」「分割/統合の実例」「アンソロジー」を含む
フォルダを指定してもらう必要がある。

## 14. 追加検討 (2026-09-03、ユーザー指摘 3 件)

### 14.1 「画像のみのフォルダを本として扱う」設定との関係

対象の設定は `Settings.auto_fullscreen_image_folders`
(UI: 「画像のみのフォルダは、PDF/ZIP のように本として扱う」、`auto_fullscreen_zip_pdf` に従属)。
本扱いかの判定は既存の正本 `folder_scan::is_image_only_book_contents(has_container, all_media)`
が持つ。**重複検出はこの述語を再実装せず、必ずこれを呼ぶ。**
この述語の境界は「サブフォルダ・ZIP/PDF・有効な変換アーカイブが 1 件でもあれば本ではない」
「メディアが全て画像」なので、入れ子フォルダの曖昧さは既に排除されている。

**問題**: この設定はいつでも切り替えられる。素直に追従すると、同じフォルダが
「N 枚の画像」と「1 冊の本」の間を行き来し、**索引の意味が設定で変わる**。
さらに OFF のとき、同じ 200 ページの漫画フォルダを 2 つ持っていると
**画像ペアが約 200 件出る** — まさに避けたいレビューキューの氾濫が起きる。

**方針: ハッシュは常に画像単位で保存し、本は導出する。**

- `similar.db` が持つのは**アイテム単位のハッシュだけ**。
  ZIP/PDF のページは container entry key、画像フォルダのページは通常のファイル。
  **設定を切り替えてもハッシュは 1 件も無効化されない** (再生成が発生しない)。
- 本としての関係 (§6) は、**一致したページペアを所属コンテナへ畳む**ことで導出する。
  この畳み込みは「結果の集約」であって「ライブラリのモデル」ではないので、
  **設定の ON/OFF に関わらず常に行う**。これで OFF 時の氾濫が起きない。
- 設定が影響するのは**呼び方と既定の見せ方だけ**にする。
  ON なら「本」、OFF なら「フォルダごとにまとめた結果」。検出内容は同じ。
- ページ順は既存の本のページ順規則 (名前順固定、
  [book-page-order-plan.md](book-page-order-plan.md)) を使う。§14.2 の順序整合が要るため。

**この方針の副次的な利点**: サブフォルダを持つため `is_image_only_book_contents` では
本にならないフォルダ (例: 巻ごとのサブフォルダを持つ作品フォルダ) でも、
ページペアの畳み込みは働くので「このフォルダ全体が別のフォルダと重複している」を出せる。

### 14.2 部分一致の見せ方 — ページ帯 (ユーザー提案、採用)

アンソロジー・総集編・単話と合本のように、**一方がほぼ丸ごと他方に含まれる**ケースでは、
「似ている本」を出すだけでは削除判断ができない。ユーザー提案は
**1 冊分のページを箱の列として並べ、一致度で色分けして一望させる**というもの。これを採る。

**これは表示の工夫ではなく、判定の証拠そのものである。**

- §13.1-I で順序アラインメントを入れると、対応の取れたページは
  **連続した区間**として並ぶ。帯を見れば
  「この単話は合本の 34〜77 ページに連続して入っている」と
  「たまたま散発的に数ページ一致しているだけ」が**一目で区別できる**。
  散発一致は偶然、連続区間は本当の収録関係、というのが判定規則そのものになる。
- §13.1-H (アンソロジーの包含に削除推奨を出さない) も、帯で
  「A は B の一部を占めるが、B には A に無いページが 200 ページある」が見えれば、
  ユーザーが即座に判断できる。
- 再版 (版違い) では、**どのページが増えた / 変わったか**が帯に出る。
  これは「旧版を消してよいか」の決め手になる情報で、集約スコアからは絶対に出てこない。

**データモデルへの影響**: 本ペアの結果は集約スコアだけでなく
**ページ単位の対応付けを保持する**必要がある。§6.3 の coverage だけでは足りない。

**帯の色分け (最低 4 状態)**:

| 状態 | 意味 |
| --- | --- |
| 強一致 | 検証まで通った対応ページ |
| 弱一致 | 候補には出たが検証が閾値近辺 |
| 不一致 | 相手に対応ページが無い |
| 採点対象外 | featureless / 文書頻度が高いページ (§13.1-C の重み付けで実質 0 になったもの) |

「採点対象外」を明示するのは Codex 指摘 (除外ページ数を隠さない) への対応でもある。

**UI 上の注意**: 200〜600 ページの本を 1 行に収めるので、箱は数 px 幅になる。
ミニマップ相当の圧縮表示が要る。箱のクリックでそのページ対を
**既存の比較表示 (wipe / diff)** に渡す。ここも新規に比較 UI を作らない。

### 14.3 正解集合の作り方 — 「まず広く計算して、出たものを手で判断する」

ユーザー提案: 既知の重複を狙って探すのは現実的でないので、
**まず広範囲に計算し、部分一致したものを拾い、それを手作業で判断する**。
**この方針を採る。**ただし 1 点だけ補正が要る。

**正しい点**: 手で探す方式は破綻する。100 万件から「同じ画像の別解像度版」を
人手で見つけるのは不可能で、見つかったとしても偏った標本になる。
検出器に候補を出させる方が、実データの分布をそのまま反映できる。

**補正が要る点**: 検出器の出力だけをラベル付けすると、
**precision (出したもののうち何割が本物か) は測れるが、recall (見逃したもの) は原理的に測れない。**
そのまま閾値を調整すると「今のアルゴリズムが見つけるもの」に収束し、
**§13.3 のアルゴリズム比較が、候補を出した側に有利に歪む**。

**対策 (これだけ守れば提案どおりで良い)**:

1. **候補プールは、比較対象アルゴリズム全部の和集合を、意図的に緩い閾値で作る。**
   PDQ / 現行 pHash 案 / blockhash / 連続値輝度 のどれか 1 つで候補を出さない。
   プールが全アルゴリズムの上位集合になっていれば、
   **プール内での相対 recall は測れる**し、比較が公平になる。
2. **絶対 recall は合成ペアで下から押さえる。** ユーザー自身の画像から
   縮小・再圧縮・ロゴ合成した既知ペアを作れば、
   「その変換に対して各アルゴリズムが取りこぼす率」は絶対値で測れる。
   実データのラベルは precision と相対 recall、合成は絶対 recall、と役割を分ける。
3. **ラベル付けは捨て仕事にならない。** ここが重要で、
   - 「別物」と判断した組 = **§13.1-M で必要な ignore リストそのもの**
   - 「重複」と判断した組 = 正例
   つまり**較正のためのラベル付け作業が、そのまま製品機能のデータになる**。
   逆に言うと、**ignore の永続化を先に作れば、較正用のラベリング UI を別途作らずに済む**。

**順序への影響**: この方式を採ると「まず測ってから作る」ではなく
**「パイプラインを作らないと測れない」**になる。したがって Phase 1 は次になる。

```
Phase 1 (較正兼用):
  ハッシュ生成 (アルゴリズムは差し替え可能な interface の裏に置く)
  → similar.db (署名列は algo_id 付きの opaque BLOB。スキーマを早期に固定しない)
  → 全件スイープ (緩い閾値・全アルゴリズムの和集合)
  → 最小のレビュー / ラベリング UI (= ignore の永続化を兼ねる)
  → 既存の比較表示 (wipe/diff) へ受け渡し
Phase 2:
  ラベルが溜まったらアルゴリズムを確定し、閾値・重み・受入基準を決める
  → 署名列を確定してスキーマを固定 → 本判定 (§6, §14.2) を仕上げる
```

**この段階でも削除機能は出さない。** Phase 1 は「候補を出して、人が別物/重複を記録する」
までに留める。削除は受入基準 (§13.3-2) を満たしてから解禁する。
