## 1. 調べたい症状

実機報告 (2026-08-07):

> ピンチ昇格の修正で改善したが、**何度か操作していると、ピンチが 2 回に 1 回、
> 交互にしか効かないようになった気がする**。

「交互」は、**あるジェスチャが残した状態が次を潰し、その失敗自体で状態が晴れる**という形が典型。

## 2. 今のプローブでは足りない理由

`src/touch_debug.rs` は egui の**生イベント列**しか記録していない。
今回知りたいのは**こちらの相関層が何を判断したか**で、それが一切見えない。

とくに `src/touch_correlation.rs` の `process_event` には、
**タッチと対応づかない primary イベントが 1 つでもあればフレームのコマンドを全部捨てる**
fail-closed 経路がある:

```rust
Event::PointerButton { button: PointerButton::Primary, .. } => {
    frame.ambiguous = true;
    self.cancel_stream(geometry, now_ms);
}
```

`pending` の不一致でも同じことが起きる。**同じ症状を出しうる経路が複数あり、
どれが発火しているかログでしか分からない。**

## 3. 入れるもの

**診断ログだけ。挙動は 1 ミリも変えないこと。** 既存の `MIV_TOUCH_DEBUG` gate に相乗りする
(新しい環境変数を増やさない)。

`Event::Touch` を含むフレーム、**または `ambiguous` が立ったフレーム**について、1 行出す。
含める情報:

| 項目 | 理由 |
| --- | --- |
| surface / app frame / egui pass 番号 | 「1 フレーム 1 回」の効き方を確認する |
| **この drive がコマンドを返す回か、replay か** | `04f71c12` の分離が効いているかの確認 |
| **`ambiguous` が立ったか。立った場合は原因** (`pending` 不一致 / 非対応 primary のどちらか、および該当イベント) | **本命** |
| **`cancel_stream` が呼ばれたか** | 状態が消えるタイミングの特定 |
| 処理前後の `pending` (`PendingSignature` の variant 名) | 次フレームへ持ち越された状態を見る |
| 処理前後の `pointer_touch` の有無 | egui-winit の `pointer_touch_id` ミラーがずれていないか |
| 処理前後の `TouchOwner` | ピンチに入れたのか、入れなかったのか |
| 発行した `TouchCommand` の種類と個数 | 実際に何が出たか |
| その時点の接点数 | 2 本目が認識されているか |

**1 行にまとめること** (複数行に分けると、フレームの対応づけが読みにくい)。
`Zoom` の factor など数値は出さなくてよい (種類と個数で足りる)。

## 4. 制約

- **`MIV_TOUCH_DEBUG` 未設定では 1 行も実行されないこと。** 既存の `OnceLock` gate に相乗りする
- **相関の判断ロジックを変えないこと。** 観測点を足すだけ。
  ログのために評価順序や早期 return を変えない
- **既存テストの期待値を変えないこと。** 変えないと通らないなら、それは挙動を変えている
- 文字列整形は gate の内側で行う (未設定時に `format!` を走らせない)
- `App` にフィールドを足さない
- **範囲を広げないこと。** 疑わしい箇所を「ついでに直す」のは禁止。
  **原因が確定してから別ステップで直す**
