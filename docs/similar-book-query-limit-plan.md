## 1. 原因

### 1.1 終わらない照会

`similar_book_engine::query_snapshot` は次の順で動く。

1. origin の各署名について `resolve_signature_neighborhood` (半径 32 の近傍検索 + 近傍の所属本の解決)。
2. 3 ページ以上つながった本を候補に残す (`BOOK_MIN_MATCHED_PAGES`)。
3. **候補の本ごとに全ページを読み、origin の memo に無い署名すべてに同じ近傍検索をかける**
   (候補側ページの common 判定のため)。その後に対の分類とページ帯を作る。

近傍検索の回数は「origin の異なる署名数 + 候補の本すべての (origin に無い) 異なる署名数」になる。
時間を決めるのは origin のページ数ではなく候補側の総ページ数で、0.5 の表 (980 ページで 13 秒、
10,000 ページ・8 冊で 178 秒) と一致する。報告のフォルダは雑多な画像の詰め合わせで、無関係な
CG 集や画像フォルダと数枚ずつ偶然一致して候補が 618 冊に膨らんだ。

完了しても 618 冊の一覧は利用者の役に立たない。性能だけでなく結果の意味の面でも、この規模は
機能の対象外とするのが妥当。

### 1.2 ちらつき (推定。利用者の観測は 0.1 のとおり曖昧)

`ui_metadata_panel.rs` の `draw_similar_panel` は、`results_are_stale` が真のあいだ
「索引を更新中です。変更は更新完了後に結果へ反映されます」の 1 行と 8 px の余白を、
「この本と重なる本」の**上**に描く。`SimilarIndexManager::query_results_are_stale` は索引 worker が
`Running / AwaitingWatch / AwaitingArray` のあいだ真になる。

0.3 のとおり 1 回目の照会中は 60〜90 ms の差分更新が約 1.7 秒おきに走っていた。そのたびに
この行が数フレームだけ出て消え、下の「調べています」が上下に動いたと考えると、0.1 の印象と
「差分更新が 0 件の今は再現しない」の両方に合う。個別画像の見出し横の「(更新中)」も同じ契機で
点滅する (こちらは横に出るだけで位置は動かない)。

本の照会側には、実行中に「調べています」自体が消える経路は見つからなかった。このセッションでは
完了した照会が 1 つも無く、`BookQueryPoll` は常に `Preparing` だったため。

## 2. 決定事項 (利用者合意、2026-09-19)

1. 「索引を更新中です…」の行と、見出し横の「(更新中)」は**削除する**。索引が更新されたことを
   画面へ知らせる必要は無く、照会結果に更新が反映されるかどうかの厳密さも求めない。
   索引を初めて作っている最中の「準備中」表示は別物で、残す。
2. 一定ページ数を超える本は、**調べる側としても相手としても**本の重なり検索の対象外にする
   (対称のページ数上限)。超えた本を開いたときは、待たせずに理由を表示する。
3. ページ数上限だけでは「上限未満の詰め合わせ + 相手が数百冊」を止められないので、候補が
   出そろった時点の総ページ数で打ち切る**仕事量の予算**を安全弁として足す。
4. 上限と予算は定数で決め、空きメモリや経過時間など実行時の状態では変えない
   (同じ索引・同じ本なら必ず同じ結果になること)。
5. しきい値 (0.6 の実測を見て利用者が選択、2026-09-19): **ページ数上限 3,000、候補の総ページ数の
   予算 10,000**。目安は「最悪でも約 30 秒」。
   - 根拠: 近傍検索は 1 回約 2.3 ms。origin 段は最大 3,000 回で約 7 秒、候補段は最大 10,000 回で
     約 23 秒。候補段の検索回数は候補のページ数を超えない (実測 0.60〜0.95 倍)。
   - この値での既知ケース: 980 ページの CG 集 (候補 6,288 ページ、14 秒) は従来どおり結果が出る。
     5,225 ページのゲーム CG の ZIP はページ数上限で対象外になる (従来は 30 秒で結果が出ていた)。
     これは利用者が承知のうえで選んだ。1 万枚の画像フォルダと報告のフォルダは対象外。
   - 測定時の索引でページ数上限を超える本は 27 冊 (約 34,900 冊中)。
   - 比較した他の案: 6,000 / 20,000 (最悪約 60 秒、5,225 ページの ZIP も通る)、
     1,500 / 5,000 (最悪約 15 秒、980 ページの CG 集が打ち切られる)。
6. 照会の並列化は本計画の対象外 (§6)。

### 作業 B: 照会の内訳を計装する (Small、挙動不変)

今回、キャンセルされた 2 回の照会 (91 秒 / 197 秒) について「どこまで進んでいたか」がログから
分からなかった。ベンチも内訳を出さないので、上限を決める材料が無い。

- engine が照会 1 回の統計を返す。最低限: origin のページ数と異なる署名数、候補の本の数
  (3 ページ未満で落とす前 / 後)、候補の総ページ数、近傍検索の回数 (origin 側 / 候補側)、
  段階ごとの所要 (origin 側の探索 / 候補側の判定と分類)。
- **キャンセル・失敗で終わった場合も、そこまでの値を返す**。成功時だけ出す形にしない。
- 製品経路: perf の `similar_book` / `end` イベントへ上記を足す。perf 無効時に新しい計測コストを
  持ち込まない (カウンタの加算は可、時刻取得は既存の `perf::is_enabled()` の規律に合わせる)。
- ベンチ: `BenchQuerySummary` (または同じレコード) に同じ値を出す。出力形式を変えるなら
  ベンチ側の `SCHEMA_VERSION` を上げる。`result_sha256` の対象に統計を混ぜない
  (結果の同一性と計測値は別物)。
- 結果そのもの (`BookQuery` の中身) は 1 ビットも変えない。既存のオラクル比較・ベンチの
  `result_sha256` がそのまま通ること。

### 作業 D: 上限の実装 (Medium)

値は §2 の 5 (ページ数上限 3,000、候補の総ページ数の予算 10,000)。

- **D-1 origin のページ数上限**: origin のページを読んだ直後、近傍検索を 1 回も行う前に判定する。
  超えていたら専用の終端結果 (例: `BookQuery::TooLarge`) を返す。
- **D-2 候補のページ数上限**: 上限を超える本は候補から外す。**ページの common 判定
  (`BOOK_MAX_BOOKS_PER_PAGE`) には手を入れない** — 上限超の本も「そのページを含む本」として
  従来どおり数える。変えるのは「相手として一覧に出すか、相手の全ページに近傍検索をかけるか」だけ。
- **D-3 仕事量の予算**: 候補が確定した時点 (D-2 の除外後) で候補の総ページ数を求め、予算を
  超えていたら、**候補側の近傍検索を 1 回も行わずに**専用の終端結果
  (例: `BookQuery::TooManyCandidates`) を返す。一部だけ調べて部分的な一覧を出すことはしない。
- **D-3 の早期打ち切り**: origin 段の途中でも、「すでに 3 ページ以上つながった、上限以下の候補」の
  ページ数の合計は単調に増えるだけで、最終的な合計の下界になる。この下界が予算を超えた時点で
  origin 段を打ち切って同じ終端結果を返してよい。最後まで走らせても結論は同じなので決定性は
  保たれる。報告のフォルダは origin 段だけで 20 秒かかるので (0.6)、これが無いと「対象外」と
  伝えるまでに最大 7 秒待たせる。候補のページ数は、その候補が初めて 3 ページに達したときに
  1 回だけ求める (数え方は次の項のとおり 1 つに揃える。行を読み込まず同じ条件で件数だけ数えても
  よい)。打ち切り時点の origin 側検索回数が全件より少ないことを
  統計で検証できる。
- ページ数の数え方は D-1 / D-2 / D-3 で 1 つに揃える (engine が実際に読む、現行 hash version の
  ページ行)。`container.page_count` と行数を場面ごとに使い分けない。
- 上限と予算は、既存の `dupe::book::Params` と同じ流儀で engine へ渡す値にする。テストが
  3,001 ページの fixture を作らずに小さい値で境界を検証できるようにするため。製品の値は
  `similar_index.rs` の `BOOK_*` 定数群に置き、`similar_book_query_verify` など同じ定数を
  複写している箇所も揃える。
- 終端結果は executor から見て通常の完了と同じ (`BookQueryTerminal::Ready`)。キャッシュされ、
  毎フレームの再実行や repaint 要求を生まない。
- UI (`draw_book_relations`): 見出しは出し、spinner は出さない。文言は
  「ページ数が多いため、重なる本の検索はできません」/
  「重なる候補が多いため、検索を打ち切りました」。固定の灰色を足さず既存の `DIM_COLOR` の
  流儀に合わせる。`python scripts/check_ui_glyphs.py` を通す。
- 旧経路 `similar_index.rs` の `query_book_ready*` はテスト・計測用のオラクルで、製品からは
  呼ばれない。上限は製品経路 (`similar_book_engine`) にだけ入れ、オラクル比較テストは
  上限以下のケースで従来どおり一致すること。
- 文書: `htdocs/mimageviewer/manual/fullscreen.html` の類似の節 (状態の列挙) に、ページ数の
  とても多い本・フォルダは対象外である旨を足す (版番号・内部用語なし)。`docs/spec.md` の
  該当箇所、[duplicate-detection-plan.md](duplicate-detection-plan.md) §19.4 の確定値も更新する。

## 4. 不変条件

1. 上限以下の本どうしの判定 (relation / 一致ページ数 / coverage / ページ帯の上書き) は、
   この変更の前後で同じ。変わってよいのは「上限超の本が相手から消える」ことだけ。
2. 同じ索引・同じ origin に対する結果は決定的。時間切れ・空きメモリ・負荷で結果を変えない。
3. 上限・予算で止まる照会は、近傍検索の重い段に入る前に終わる (D-1 は 0 回、D-3 は候補側 0 回)。
4. UI スレッドに新しい同期 I/O・DB 参照を足さない。判定は既存の照会 worker の中で行う
   ([ui-responsiveness.md](ui-responsiveness.md) §4)。
5. 照会 executor の所有関係 (client ごとの要求、FIFO、soft refresh / hard invalidate) は変えない。
6. detached viewer の述語・viewport 経路には触れない。触れる必要が出たら実装を止めて報告する
   (`CLAUDE.md` の凍結ルール)。
7. `similar.db` / `similar.base` へ書き込まない。

## 5. 受け入れ条件

- A: 索引 worker の状態で類似パネルの配置が変わらないテストが、削除前のコードで失敗し、
  削除後に通る。未使用になった API・テストが残っていない。
- B: `similar_book` / `end` に内訳が出る。**キャンセルされた照会でも出る**ことをテストで確認する。
  結果のハッシュが B の前後で一致する。
- D: 予算の早期打ち切りと、origin 段を最後まで走らせた場合とで、同じ終端結果になること
  (打ち切りは速さだけを変え、結論を変えない)。予算ちょうど = 対象、予算 + 1 ページ = 打ち切り。
- D: 境界 (ちょうど上限 = 対象、上限 + 1 = 対象外) を origin / 候補の両方で検証する。上限超の本が
  存在しても、上限以下の相手との判定が不変条件 1 のとおり変わらないことを、同じ fixture の
  「上限超の本あり / なし」で比べる。D-1 / D-3 で止まったとき、統計上の近傍検索回数が
  不変条件 3 のとおりであること。UI は文言が出て spinner が無く、repaint を要求しないこと。
- 実機確認 (利用者): 報告のフォルダで類似タブを開くと、待たずに理由が表示される。普通の本では
  従来どおり結果が出る。ダウンロード中など索引が頻繁に更新される状況でパネルが上下に動かない。

## 6. 対象外

- 予算超過時の部分的な結果。打ち切ると、丸ごとの写しが別の場所にある、という関係も表示されない
  (0.7 の 1,255 ページ / 972 ページのフォルダがこれに当たる)。一致の多い候補から順に予算の範囲だけ
  調べる形は考えられるが、「一部だけの一覧」をどう見せるかの設計が要るので今回は入れない。
- 照会の並列化。1 スレッドなので効果は見込めるが、ページ送りなど前面の処理と CPU を取り合うため、
  優先度と並列度の設計が要る。上限を入れた後に、13〜27 秒かかる中規模ケースの扱いとして別途検討する。
- 候補側の全ページに近傍検索をかける設計そのものの見直し (common 判定の省略・近似)。判定結果が
  変わるため、[duplicate-detection-plan.md](duplicate-detection-plan.md) の検証をやり直す規模になる。
- 画像が 1 枚増えるたびに、その画像フォルダの本全体を書き直して差分更新が 2 回走る挙動 (0.3)。
  1 回 60〜90 ms で実害は小さい。必要なら
  [similar-index-incremental-reconcile-plan.md](similar-index-incremental-reconcile-plan.md) 側で扱う。

## 7. 再測定の手順

`target-bench/` (gitignore 済み) にビルドと索引コピーを置く。実行中の本体や通常の `target/` に触れない。

1. ビルド: `cargo build --release --features dev-tools,portable --bin similar_book_query_bench --target-dir target-bench`
   (`portable` が無いと起動時に拒否される。`CARGO_INCREMENTAL=0` を付ける)。
2. 索引のコピー: `similar.base` をコピーし、`similar.db` は SQLite のオンラインバックアップで
   整合コピーを取る (本体が動いたままでよい。読み取りロックだけ)。コピー中に `similar.base` が
   書き換わっていないことを確かめる。
3. **コピーした DB だけ** `PRAGMA journal_mode=DELETE` にする。ベンチは WAL ヘッダのままの DB を
   拒否する。元の DB には触れない。
4. `--root` には、お気に入りのうち別バージョン索引が有効なものを、小文字・スラッシュ区切りで
   すべて渡す。`--origin` も同じ形式の container key。
5. 重いケースは 10 分かかる。`--warmup 0 --samples 1` で十分。
6. 0.5 の各ケースの具体的な container key は公開文書に書かない。測定機の
   `target-bench/results/*.jsonl` の `config` レコードに残っている。
