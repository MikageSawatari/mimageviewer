## 1. 今のツールの棚卸し (v5.1.0)

### 1.1 18 個のツール

許可の段は 4 つ (`disabled` / `read_only` / `read_and_open` / `organize`。計画書 §7 の「移動・名前変更」「ごみ箱」の 2 段は未実装で、
`AgentLevel` に無い)。別に「縮小画像」「撮影位置 (GPS)」「AI 説明文」の 3 つの切り替えがある (すべて既定 OFF)。

全ツールの説明に入れている、ページ送りは cursor。

### 1.2 できないこと (棚卸し)

1. **サブフォルダをまたぐ取り出し**: `list_folder` は直下だけ。`list_library` の rated はライブラリ全体で、フォルダの範囲を指定できない。
2. **件数だけ知る手段**: ★ごと・種類ごとの件数も、全行を取って AI が数える。
3. **画像の細部を見る手段**: 縮小画像は長辺 512 まで。小さな文字・ピント・細部の比較は難しい。
4. **一覧の絞り込み・並び**: 名前・拡張子・タグ有無・寸法で絞れず、並びは保存済み (利用者の画面の設定) のまま。
5. **複数タグの条件**: `items_by_tag` は 1 タグだけ。タグを含む全文検索もできない (§31.1、mIV タグは全文索引に入らない)。
6. **タグの付け替えの一括**: 表記ゆれの統一などは、全件を取って `add_tags` + `remove_tags`。
7. **コレクションの並べ替え・削除**: 段階 2 で「提供しない」と決めている (計画書 §7)。
8. **ファイルの移動・名前変更・ごみ箱**: 段階 2b、未実装。AI アプリ自身のシェルで動かすと mIV のタグ・★が新しい path へ引き継がれない (§31.1)。
9. **似た画像・同じ絵の検索**: 別バージョン索引は AI 連携に出していない。候補のフォルダが分かっていて枚数が少なければ縮小画像の見比べで
   できた (観測者: サブ PC 担当、計画書 §32 の U12)。
10. **動画・書庫・フォルダの代表画像**: `get_thumbnail` は動画・書庫の代表・フォルダを `unsupported` にする。
11. **開く操作の幅**: 本のページ・ZIP 内の項目を指定して開けない。コレクションや検索結果を開けない。
12. **検索が効かない場所の判別**: 索引の対象外のフォルダで 0 件になっても、AI には「無い」のか「索引が無い」のか分からない。

### 1.3 比較材料 (backlog §1.740 の記述)

Claude Code (ファイルを読める権限あり) は★をファイルから直接調べ、縮小画像と大きな画像も見て選んでいた (利用者の観測、v5.0.0 の試験)。
MCP 経由では長辺 512 までで、細部の比較が難しい。★の取り出しの遠回りは v5.1.0 (§1.735) で解消済み
(観測者: サブ PC 担当、計画書 §42 J。Codex で「★2 の画像から 3 枚選んで★4 に」が `list_folder` 1 回 + `set_rating` 1 回)。
**Claude Desktop・ChatGPT アプリの画面からは未確認。**

## 2. 依頼の例と、今のツールで足りるか

利用者の使い方 (AI 生成画像の整理・選定、本・漫画の管理、タグ付け、コレクション作り) から、AI アプリに頼まれそうな依頼を 20 個挙げる。
判定は設計書とコードからの見立てで、実機では未確認 (確認済みのものは出どころを書く)。候補の番号 (M1〜) は §3。

依頼 3・11・15・17 の遠回りの解消は、AI アプリがツールを選べるかにも依存する。計画書 §32.2・§33.2・§34 のとおり、AI アプリが mIV のツールより
先に自分の画面操作を試す観測 (観測者: サブ PC 担当) があるので、**ツールを増やしても選ばれるとは限らない**。

## 3. 候補ごとの評価

規模の目安: 小 = 引数・出力の追加で既存の経路を使える、中 = 新しい読み取りの経路や 1 つのツール、大 = 本体の別機能の公開・表示状態に触れる・独立レビューが要る。
「説明文の文字数」は tools/list へ足す文字数の**見積り** (§5)。

### M1 サブフォルダを含む一覧・絞り込み

- 内容: `list_folder` に `recursive` (と深さの上限) を足す。★・種類・名前の絞り込みを下のフォルダまで適用する。
  別案: `list_library` の rated に path の範囲を足す (rating DB を直接引くので速いが、未評価 (★0) は取れない)。
- 効果: 依頼 1・8。§1.735 の続きとして、利用者の★で選ぶ作業に最も近い。
- 規模: **中〜大**。
  - 物理フォルダだけを下りる。**ZIP・PDF は行として返し、中へは下りない** (中は `list_folder` で ZIP を指定して読む)。こうすると、backlog が
    懸念した「rating DB のキー (ZIP 内・合成の本) と path の接頭辞の照合」が要らなくなる。組み合わせを減らす案 (CLAUDE.md の簡素化方針) として採る。
  - 1 回の走査に 20 秒の期限と取消がある。本体の `folder_scan` の 10 万件性能テストが単独で 74 秒だった記録 (計画書 §42 J。テストでの値で、
    実際の使い方での時間ではない) があり、**件数・深さの上限と、時間切れのときの返し方 (これまでの行 + cursor)** の設計が要る。
  - cursor は再帰の走査位置を持たせる (走査の途中で一覧が変わったら取り直す、既存の契約)。
- 権限・プライバシー: 新しい許可は不要 (今も任意のフォルダの直下を読める)。ただし 1 回で渡る path・名前・タグの量が増える。上限で抑える。
- 説明文の文字数: 引数 `recursive` / `max_depth` + 説明で **+150〜250 文字**。

### M2 フォルダの要約 (件数だけを返す)

- 内容: ★ごと (0〜5)・種類ごとの件数、直下のサブフォルダの一覧と件数を、全行を返さずに返す。`list_folder` の `summary` 引数にするか、新しいツール
  `summarize_folder` にする。M1 と組み合わせるとサブフォルダ込みの件数になる。
- 効果: 依頼 2・19 (EXIF の集計は別)。大きなフォルダで見通しを立てるのに全件を取らずに済む。
- 規模: **小〜中** (`list_folder` の基本一覧の作り方と★の解決関数 `RatingKey` を再利用できる。集計は返す行がないので応答は小さい)。
- 権限・プライバシー: 新しい許可は不要。渡る情報は件数と子フォルダ名で、全行より少ない。
- 説明文の文字数: 引数にする場合 **+200〜300 文字** (出力 schema が別の形になる)。新ツールなら **+800〜1,100 文字**。

### M3 確認用の大きめの画像

- 内容: `get_thumbnail` の `long_side` の上限を 512 → 1024〜1568 程度に広げる。大きい長辺のときは 1 回の枚数 (20 → 数枚)・1 枚と合計のバイト数の上限を別に決める。
- 効果: 依頼 3・4・5。利用者の比較材料 (大きな画像を見て選ぶ) に直接対応する。
- 規模: **小〜中**。上限定数 (`MAX_THUMBNAIL_SIDE`・`MAX_THUMBNAIL_IMAGE_BYTES`・`MAX_THUMBNAIL_TOTAL_BYTES`・`MAX_THUMBNAIL_ITEMS`) と `get_thumbnail` の縮小経路
  (`encode_thumb_webp`、毎回 decode する経路) の範囲で、新しい経路は要らない。大きい画像は 1 枚あたりの WebP が大きくなるので、
  agent IPC の frame (4 MiB)・MCP の画像 block (base64 で約 1.33 倍)・AI アプリ側の受け取れる大きさ (未確認) を設計時に確かめる。
- 権限・プライバシー: **縮小画像の許可の下**に置くが、渡る情報の質が変わる (小さな文字も読める解像度になり、AI の提供元へ渡る)。
  設定画面の「AI に見せるもの」の文言、マニュアル・`privacy.html` の縮小画像の説明を更新する。別の切り替えにするかは利用者の判断 (§7)。
  「隠す編集のある画像は返さない」の検査は今と同じに通す。AI アプリ側のトークン消費は大きい画像ほど増える。
- 説明文の文字数: schema の最大値の変更は文字数ゼロ。説明の「Above 512 clamped」と枚数の条件の書き換えで **+50〜150 文字**。

### M4 タグの改名・統合

- 内容: タグ名の付け替えを 1 回で行う `merge_tags` (複数の元のタグ → 1 つのタグ)。mIV の UI の改名・統合と同じ経路を使う。
- 効果: 依頼 6。AI 生成画像のタグ付けで出やすい表記ゆれの整理。今は全件を `items_by_tag` で取って 500 件ずつ付け替える。
- 規模: **中**。計画書 §21 で「タグは差分で書き、改名・統合とは双方向に排他する」と決めてあるので、その排他の整合を取る必要がある。
  UI 側の改名・統合の経路 (複数 viewer context のタグ表示の更新を含む) を使う。
- 権限・プライバシー: 整理の段。**1 回の操作で何千件のタグが変わり、元に戻す機能は作らない (U11)**。「1 回の変更は 500 件まで」(§5.5) の方針と
  衝突するので、上限の例外 (または件数の事前確認) を利用者に決めてもらう。渡る情報は増えない。
- 説明文の文字数: 新ツールで **+450〜650 文字**。

### M5 複数タグの条件

- 内容: `items_by_tag` に `tags` (複数 AND)・`exclude_tags`・`min_stars`・`kind` を足す。
- 効果: 依頼 7・8。タグはファイル単位で、全文索引に入らない (§31.1) ので、今は AND の手段が無い。
- 規模: **小〜中** (タグ表示の問い合わせ `CollectionEngine` の `TagItems` が複数タグに対応できるかは設計時に確認。できなければ `TagsDb` を直接読む)。
- 権限・プライバシー: 新しい許可は不要。
- 説明文の文字数: **+150〜250 文字**。

### M6 `list_folder` の絞り込み・並び・寸法の追加

- 内容: `name_contains`・`extensions`・`tagged` (有/無)・`order` (名前・更新日・大きさ・★・寸法)。行に寸法 (幅・高さ) を付けるかは別に判断する。
- 効果: 依頼 8・9・10。
- 規模: `name_contains`・`extensions`・`tagged` は **小** (基本一覧を作った後の絞り込みで、§1.735 と同じ位置)。`order` は **中** (保存済みの並びとの関係、
  cursor の `listing_digest` との整合。★順のときの既存の「一覧が変わると取り直し」の契約と同じ扱いになる)。寸法は画像ごとに header の読み取りが要り、
  「読み取りの費用を測ってから決める」(backlog) のとおり **大きなフォルダで時間が掛かる恐れ**がある。この候補の中で最後に回す。
- 権限・プライバシー: 新しい許可は不要。
- 説明文の文字数: 引数の追加で **+250〜400 文字** (`order` の enum を含む)。

### M7 索引の対象の案内

- 内容: `search_items` の応答 (または `miv_status`) に、検索が効く場所 (索引を ON にしたお気に入りの場所) を返す。AI が「この path は索引の対象か」を判断できるようにする。
- 効果: 依頼 11・20。索引外で 0 件のときに、AI が「無い」と答えず `list_folder` へ切り替えられる。
- 規模: **小** (索引の設定は本体が持っている。読み取りの追加)。
- 権限・プライバシー: **新しい情報が渡る**: 利用者がどのフォルダを索引化しているか。path は既に読めるが、設定の内容を見せることになる。
  設定画面の「AI に見せるもの」に 1 行足す。
- 説明文の文字数: **+100〜200 文字** (出力の schema と説明)。

### M8 コレクションの並べ替え・削除

- 内容: `reorder_collection` / `delete_collection` (元のファイルは触らない。登録だけの操作)。
- 効果: 依頼 12。
- 規模: **小〜中** (collection actor の既存の操作。並べ替えは一覧画面の並び設定との関係を設計時に確認)。
- 権限・プライバシー: 整理の段。**削除は段階 2 で「提供しない」と決定済み** (計画書 §7) なので、再決定が要る。登録の削除は元に戻せない (U11)。

### M9 移動・名前変更・ごみ箱への削除 (段階 2b)

- 規模: **大**。表示中の一覧・viewer に影響するので App の UI 側で受け付ける。表示状態と複数 viewer context に触れるので独立レビュー必須。
  detached リワーク中の規則 (CLAUDE.md) の確認も要る。許可の段を 2 つ足す (設定画面・案内・公開文書)。
- 権限・プライバシー: **最も大きい**。ファイルそのものを動かす・消す。ごみ箱へ移すと**戻しても mIV のタグ・★等は戻らない** (計画書 §5.2)。上書きはしない。
  プロンプトインジェクションで誤操作される危険が高まる (許可の範囲の中の操作は確認なしで実行される、U9)。

## 5. ツール説明の文字数

### 5.1 現状

- tools/list の最大 (整理まで・全切り替え ON) は **39,464 文字** で、上限 40,000 から必要な余裕 512 を引くと**余裕は 536 文字**
  (観測者: 設計担当、計画書 §42 J。v5.1.0 のコード)。検査は `crates/mcp-server/src/tests.rs` の
  `stage2_complete_tool_discovery_fits_final_envelope_budget` で、`chars + 512 <= MAX_MCP_RESPONSE_CHARS`。
- **この 40,000 は mIV が自分で置いた予算** (`MAX_MCP_RESPONSE_CHARS`、応答全体に共通) で、AI アプリ側の上限としては未確認。
  実際に効くのは、各 tool の説明と schema が **AI アプリの文脈を消費する**こと (計画書 §15.3「ツールを増やしすぎない」)。
  約 39,000 文字は英語・JSON で見て 1 万トークン前後と見積もれる (推定)。
- 現在の 1 ツールの平均は約 2,200 文字。`outputSchema` が大半を占めると見られる (`schema.rs` の構成から。実測ではない)。
  例えば全ツールに同じ形の `failure` (`error` の `code` enum 10 個) が付き、1 ツール 300 文字前後 × 18 で **約 5,000 文字**、
  ページ形式の行ごとの `too_long` の分岐が約 8 ツール分、各 object の `required` と `additionalProperties: false` の繰り返しがある。

### 5.2 縮める方法 (候補の前に先にやる)

最初の作業は**ツールごと・要素ごとの実測** (どの tool が何文字か)。見積りで終わらせず、数字を出してから下の方法を選ぶ。

1. `failure` の `code` を enum でなく文字列にする、または共通の短い形にする (見積り −2,000〜−2,500)。クライアントに実益の少ない厳密さ。
   ただし、tools の `outputSchema` の契約を変えるので、握手・テストの更新と、AI アプリが `outputSchema` の検証をしているかの確認 (未確認) が要る。
2. 出力の object の `additionalProperties: false` と重複する `required` の整理 (見積り −1,000〜−2,000)。
   厳密さを緩めると、列を足したときの扱いが変わる (§1.735 は `additionalProperties: false` のために版を上げた)。メリット・デメリットを設計時に整理する。
3. `$defs` でまとめられる同一 schema を増やす (`get_item_info` と書き込み系では済み。ページ形式の `too_long` の分岐、★の範囲など)。見積り −500〜−1,000。
4. 説明文の短縮 (権限・制限の要点は残す)。見積り −500〜−1,000。計画書 §34 のとおり、冒頭に「mImageViewer (mIV)」を入れる決まりは守る。
5. ツールの統合 (`add_tags` と `remove_tags` を `edit_tags` に、`add_to_collection` と `remove_from_collection` を 1 つに、など)。
   ツール数が減り文字数も大きく減る (見積り −1,500〜−2,500) が、AI がツールを選ぶ観測 (§32・§34) への影響と、`destructiveHint` の付け方 (削除系だけ true) が
   変わるので、**採るかは利用者と相談**。この洗い出しでは推さない。
6. (最後の手段) 上限を上げる。AI アプリ側の上限と文脈の消費を確かめてから。

目標: 次の版で M1〜M7 を入れるなら、軽量化で **約 2,000〜3,000 文字**の余裕を先に作る (候補の合計 +1,000〜1,800 文字と、512 の余裕の確保のため)。見積りなので、実測で調整する。

## 6. おすすめの範囲

優先の考え方: (a) 利用者の実際の使い方に直結する、(b) 読み取りだけで済み権限の議論を増やさない、(c) 説明文の文字数に収まる、(d) 次の版に入れられる規模。

### 案 A (推奨): 読み取りの拡充 — 「★・件数・画像で選ぶ」を完成させる

M15 (軽量化) + **M1 (サブフォルダ込み)** + **M2 (フォルダの要約)** + **M3 (確認用の大きめの画像)** + **M7 (索引の対象の案内)** + M6 の小さい部分 (`name_contains`・`extensions`・`tagged`)。

- 理由: §1.735 で入れた★の取り出しの続きで、利用者の観測した不便 (サブフォルダの★、細部を見て選ぶ) に直接答える。
  全部が読み取りで、**新しい許可の段は要らない** (M3 だけ縮小画像の許可の下で渡る情報の質が上がるので文言を更新)。
- 規模: **中〜大** (M1 が最大。M1 を `list_folder` の再帰に限り、ZIP の中へは下りない設計で小さくする)。
- 文字数: 合計 +750〜1,300 見積り。M15 で先に余裕を作る前提。
- 公開文書: マニュアル「AI アプリとの連携」の頼み方の例 (サブフォルダ込みの★・件数・細部を見て選ぶ)、縮小画像の説明 (`privacy.html` を含む) を更新。
- 外すもの: M5・M4 (整理の効率化は案 B)、M9・M10・M11・M12 (大きい別設計)。

### 案 B (拡大案): 案 A + 整理の効率化

案 A + **M5 (複数タグの条件)** + **M4 (タグの改名・統合)**。

- 理由: タグ付けの作業 (AI 生成画像の表記ゆれの整理、複数タグの条件) の遠回りを減らす。M4 は 1 回の操作で多数に影響し、元に戻す機能が無い
  (U11) ので、**上限の例外の決定が要る**。
- 規模: 案 A + 中。文字数: 案 A + 600〜900 見積り (軽量化の目標を 3,000 文字側にする)。
- 外すもの: 案 A と同じ + 移動・類似 (別の版)。

### 次の版では入れず、別に設計するもの

- **M9 (移動・名前変更・ごみ箱)**: 最も効果が大きいが、規模・権限・元に戻せない点で別の版にする。許可の段の設計と独立レビューが先。
- **M10 (似た画像)**・**M11 (動画・書庫の代表画像)**・**M12 (開く操作の拡張)**・**M8 (コレクションの削除)**: それぞれ別の設計 (別バージョン索引の公開、動画の経路、表示状態の所有、削除の再決定)。
- **M13・M14**: 効果が限定的。要望が出てから。
