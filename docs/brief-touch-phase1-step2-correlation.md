## 0. これは何か

**plan §5.2 の設計の核心。** 「設定なし・マウス無影響・タッチのときだけ別動作」が成立するかは、
**入力源を確実に判定できるか**にかかっている。ここを作る。

やること:

1. egui の raw イベント列から `TouchSample` を取り出し、surface ごとの `TouchRecognizer` を駆動する
2. **どの primary pointer イベントがそのタッチ由来か**を、イベント列シグネチャで相関する
3. 相関結果と Step 1 のコマンドを、Step 3 が問い合わせられる形で公開する

---

## 1. 絶対制約 — このステップも挙動ゼロ変更

**Step 2 では抑止を「計算」するだけで「適用」しない。** 実際に egui の click を抑止するのは
Step 3 で、**抑止されたクリックを置き換えるコマンドの配線と同時**に行う。

理由: ここで抑止だけ先に効かせると、コマンドがまだ繋がっていないので
**「タッチしても何も起きない」という退行**になる。抑止と代替動作は必ず同じステップで入れる。

したがって Step 2 完了時点で、**マウスでもタッチでも現在とまったく同じ挙動**であること。
差分は「内部で分類できるようになった」だけ。

## 2. 実機ログで分かった、設計を左右する事実

Step 0 の実機ログ (タッチディスプレイ PC、2026-08-06) から。**推測ではなく観測結果**なので、
これに合わない実装は間違い。

### 2.1 シグネチャは実機で確認済み

`Touch(Start)` 55 回 / `Touch(End)` 55 回が完全一致し、並びは plan §5.2 のとおりだった:

```
開始: Touch(Start) -> PointerMoved            -> PointerButton(Primary, pressed=true)
移動: Touch(Move)  -> PointerMoved
終了: Touch(End)   -> PointerButton(Primary, pressed=false) -> PointerGone
```

### 2.2 ⚠ 1 フレームに複数の完結したタッチが入る

**実機では 1 フレームに 10 個の完結したタッチ列 (id=48〜57) が入っていた。**
アプリが再描画していない間にイベントが溜まるため。

→ **「1 フレーム = 1 タッチ」を前提にしないこと。** フレーム内のイベント列を**順序どおり**
走査し、複数の Start/End の組を扱えること。コマンドも複数返りうる。

### 2.3 ⚠ タッチ列はフレーム境界をまたぐ

実機のあるフレームは **`PointerGone` から始まっていた** (前フレームのタッチの続き)。

→ **相関の状態はフレームを越えて保持すること。** 「フレーム単位で完結する」前提にしない。
フレーム途中で切れた列を、次フレームの先頭から継続できること。

### 2.4 接点 id は単調増加し再利用されない

id の等価比較で追跡してよい (Step 1 と同じ前提)。

### 2.5 `Cancel` は一度も観測されなかった

**未検証のまま**。防御的に実装し、`Cancel` で相関状態も所有権も破棄すること。

## 3. 作るもの

### 3.1 surface の識別

タッチ状態は **`ViewportId` + surface** をキーに持つ (plan §5.1-5)。

**実機ではフルスクリーンが embedded モード** (メイン ctx と同居) で動いていた。
つまり `ViewportId` だけでは一覧グリッドと静止画フルスクリーンを区別できない。surface が要る。

```rust
pub(crate) enum TouchSurface { MainGrid, StillFullscreen }
```

Step 2 で使うのはこの 2 つ。native 動画 / 音楽は Step 4 以降で足す。

**同じ viewport の同じフレームで 2 つ以上の surface が駆動されないこと**を保証する
(embedded フルスクリーン中にグリッドも駆動すると、同じイベントを二重に食う)。
どちらが駆動するかの判定条件を doc comment に書くこと。

### 3.2 状態の置き場所

- **`App` にフィールドを足さない。** `ctx.data_temp` に `(ViewportId, TouchSurface)` をキーとして持つ
  (plan §5.1-5)。**detached リワークの凍結ルールに抵触しないため**で、ここは譲れない
- `TouchRecognizer` に `Clone` を derive する必要がある (`data_temp` の要求)
- **「最後の入力デバイスはタッチ」のようなグローバル状態を作らない** (plan §5.2)

### 3.3 相関 (fail-closed) — 中核

`ctx.input(|i| &i.events)` の**順序どおりの走査**で、次を満たす primary pointer イベント
**だけ**を「このタッチの合成 pointer」と判定する:

- 直前に対応する `Event::Touch` があり、§2.1 の並びと**完全一致**している
- 位置が一致している

**肯定証拠だけで新経路へ入る (fail-closed)**。具体的に:

- 一致しない primary イベントは**すべて従来のマウス入力として扱う**
- 相関が曖昧なら従来の pointer 経路へ戻す
- **同一フレームに相関付けられない primary mouse event があれば、タッチ側の action を中止する**
- `zoom_delta()` 単独では入力源を判定しない (`multi_touch()` と active ownership を条件にする)

> ⚠ **「同じフレームに Touch があったから、そのフレームのクリックは全部 touch」は不可。**
> マウス併用時に誤判定する (plan §5.2)。

### 3.4 ⚠ `should_suppress_primary()` の扱い — Step 1 レビューで見つかった罠

`TouchRecognizer::should_suppress_primary()` は、**タッチ終了後も次の `Start` まで true のまま残る**
(最終 `End` の後にアダプタが問い合わせられるようにするための意図的な設計)。

**これを primary イベントごとに無条件で問い合わせてはならない。**
タッチ直後のマウスクリックが食われ、plan §5.15 の
「タッチを行っていない mouse-only の入力列については挙動を一切変更しない」保証が壊れる。

正しい順序:

```
① §3.3 の相関でその primary イベントがタッチ由来だと確定させる
② 確定したものに対してだけ should_suppress_primary() を適用する
```

**この順序を回帰テストで固定すること** (§5 のテスト項目)。

### 3.5 診断用の強制無効 (plan §5.14-6)

環境変数 `MIV_DISABLE_TOUCH_GESTURES` が設定されていたら、この層は
**コマンドを 1 つも返さず、抑止も一切しない** (= 完全に現行挙動)。
`OnceLock` でキャッシュする (`src/touch_debug.rs` の `touch_debug_enabled` と同じ形)。

`src/touch_input.rs` は純ロジックなので**そちらに環境変数を持ち込まないこと**。
gate はこの新しい層に置く。

### 3.6 公開する API

Step 3 が使う形にする。最低限:

- そのフレームで確定した `Vec<TouchCommand>` を取得できる
- ある `Response` / primary イベントについて「タッチ由来なので既存 click を抑止すべきか」を
  問い合わせられる (§3.4 の順序を守った形で)

## 5. テスト

**plan §5.15 の保証に直結するので、ここは厚くすること。**

必須:

1. **mouse-only のイベント列で、タッチ分類も抑止も一切発生しないこと** (最重要)
2. **タッチ完了後の次フレームでマウスクリックした場合に抑止されないこと** (§3.4 の罠)
3. §2.1 のシグネチャと完全一致する列が正しく相関されること
4. **順序が違う列 / 位置が違う列は相関されないこと** (fail-closed の確認)
5. **1 フレームに複数の完結したタッチ列**が入っても全部処理されること (§2.2)
6. **フレーム境界をまたぐ列** (フレーム先頭が `PointerGone` 等) が継続処理されること (§2.3)
7. マウスとタッチが同一フレームに混在したとき、タッチ側 action が中止されること (§3.3)
8. `MIV_DISABLE_TOUCH_GESTURES` 有効時に何も起きないこと
9. `Cancel` で相関状態と所有権の両方が破棄されること

### 5.1 依存更新の番人 (plan §5.2 が明示的に要求)

§2.1 のシグネチャは **egui の一般契約ではなく egui-winit 0.33.3 の実装契約**である。
依存を上げたときに黙って壊れないよう、**シグネチャそのものを固定する回帰テスト**を置くこと。

- 期待する並びを**テスト内に明示的に書く**
- そのテストの doc comment に、根拠となる
  `egui-winit-0.33.3/src/lib.rs:676-738` と、**この前提が壊れたら何が起きるか**を書く
- egui-winit を実際に動かす必要はない。「この並びを受理し、崩れた並びを拒否する」ことを
  固定できればよい

## 7. 制約

- **アプリを起動しないこと。** 検証ビルドは ClaudeCode が用意する
- ブランチ操作・コミットは不要。master の作業ツリーで作業する
- **`App` にフィールドを足さない** (§3.2)
- **detached-rework 凍結ルールは有効。** detached 述語 / viewport 経路の判定を変えないこと。
  触れる必要が出たら、**触らずに報告すること**
- **範囲を広げないこと。** 「ついでに Step 3 も」は不可。§1 の理由で、抑止と代替動作は
  同じステップに入れる必要があるが、それは Step 3 側でまとめて行う
