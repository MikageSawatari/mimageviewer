## 0. 利用者決定の要約 (backlog §1.911 から)

1. 順番は mIV の DB に保存する。フォルダへファイルを書かない。
2. mIV 上の改名だけ追従する。外部で改名・追加されたファイルは未知として末尾。消えたファイルは飛ばす。
3. 手動順のとき、一覧でのドラッグは並べ替え。その間、一覧からのドラッグでのコピー・移動はできなくてよい。
   手動順以外では従来どおりのドラッグ。
4. 手動順に切り替えたときの初期の並びは直前の並び順。
5. 一度も並べ替えていない手動順は記録しない。最初の並べ替えが成功した時点で記録する。
6. 記録したフォルダで別の並び順へ切り替えてから手動順に戻すと記録した順に戻る。記録は消さない。
7. 記録を捨てて直前の並び順からやり直す操作 (リセット) が要る。

範囲外 (V1): ZIP / PDF / EPUB などの仮想フォルダ、本として開いたページ順、検索結果・スマートフォルダ・
コレクション・本棚・サブフォルダ展開・評価/タグ/しおりビュー、Remote からの並べ替え操作。

## 1. 今のコードの事実 (設計の前提)

- 並び順 `SortOrder` (src/settings.rs) は**全体共通**の 1 つ (`settings_kv` の `sort_order`)。フォルダごとの記憶は無い。
  例外はお気に入りごとの表示状態 (`FavoriteViewState`、`remember_favorite_view_state`、既定 OFF)。
- フォルダ一覧の並びは `materialize_local_folder_listing_with_order_and_metadata` (src/app/book_materialization.rs) が
  唯一の合流点。PC 本体・Remote (`remote_ipc/container.rs` の `recompute_folder_listing_with_rating_read`)・
  Agent IPC が同じ関数を使う。`GridDisplayOrder` で 4 段 (実フォルダ / アーカイブ類 / 画像 / 動画・音声) に分け、
  同じ段の中を `SortOrder` で並べる。
- 通常の open は scan を worker で行い、並べ替えは UI スレッドの `prepare_scanned_folder_listing_with_cache_keys`。
  watcher の再走査 (`start_external_rescan_with_cause`) は worker で並べ替えまで行い、全置換で反映する。
  並び順の変更は `apply_sort_change_reload` で再走査。
- 前/次・スライドショーは `App.items` + `current_reader_order()` に従う。独立した順は無い。
- ファイル名スタック (`filename_stack.rs`) は自分で並べ直す。スタックの ON/OFF は transient (フォルダを出ると解除)。
- 一覧のドラッグは `dispatch_grid_cell_input` (src/ui_main.rs) で `drag_started` を判定し、`pending_native_drag` を立てて
  描画後に `SHDoDragDrop` (モーダル) へ入る。左ドラッグの範囲選択は無い。右ドラッグはリング/ジェスチャ。
  Explorer からのドロップは別経路 (OLE target) で、現在フォルダへのコピー。
- 並べ替えのドラッグは「本のページの並べ替え」窓と「コレクションの並べ替え」窓にほぼ同じ実装がある
  (挿入位置 = セルの左右半分、縦棒の挿入線、端での自動スクロール、選択グループの移動)。共通部品は無い。
- 改名追従は `rename_key_migration.rs` の `STORES` (1 行 = 1 つの path キー列)。mIV 上の改名 (F2 / 右クリック) だけが
  移行を呼ぶ。mIV 上の移動・コピー・貼り付け・D&D は移行しない (既存の方針)。削除時は同じ表で purge する。
  孤児整理ダイアログも同じ表を走査する。content-identity の復元 (`copy_stores_impl`) は unique store の行を
  新しい path へ複写する。
- 本棚の本の順 ([book-order-plan.md](book-order-plan.md)) は棚の中の JSON ファイル。今回は決定 1 によりフォルダへ
  書かないので、形式は流用せず「未知は末尾・名前順」「読むだけでは書かない」の規則だけ揃える。

## 2. 「手動順を選んでいる」状態の持ち方 — 推奨: フォルダごと (利用者確認 Q1)

並び順は全体共通なので、手動順を全体の並び順の 1 つにする案 (A) と、フォルダごとの状態にする案 (B) がある。

| | A: 全体の並び順の 1 つ (`SortOrder::Manual`) | B: フォルダごと (推奨) |
| --- | --- | --- |
| 手動順を選んだ後に別のフォルダを開く | そのフォルダも手動順。記録が無ければ直前の並び順で表示し、ドラッグは並べ替え (最初のドラッグで記録) | 全体の並び順で表示。ドラッグは従来どおり |
| ドラッグが並べ替えになる範囲 | 手動順を選んでいる間の**全フォルダ** | 手動順を選んだフォルダ / 記録が有効なフォルダ**だけ** |
| 「直前の並び順」 | 手動順を選ぶ直前の全体の並び順を別に保存する | そのとき表示していた全体の並び順 |
| 他への波及 | `SortOrder` の全 match、お気に入りの表示状態、Remote の並び順変更、ツールバーの並び順ボタン、旧版が新しい値を読めない (評価順追加時と同じ非互換) | 既存の並び順の設定には触れない。フォルダの記録に「有効」の印を持つ |

B を推奨する理由: 決定 3 のオプトイン (ドラッグがコピー・移動でなくなる) を、利用者が手動順を選んだフォルダに
閉じ込められる。A では手動順を選んだまま別のフォルダでファイルを Explorer へドラッグしようとすると、
並べ替えになってしかもそのフォルダの記録が始まる。状態の組み合わせも B のほうが少ない (全体の並び順・お気に入り・
Remote の並び順変更と独立)。

B の規則:

- フォルダの状態は 3 つ: **通常** (全体の並び順) / **手動・未記録** (切り替えただけ。メモリだけ) /
  **手動・記録あり** (DB に順と「有効」の印)。記録があって「有効」が外れているものは表示上 **通常**。
- 通常 → 手動: 記録があれば記録した順 (決定 6)、無ければ今表示している並び (決定 4) で手動・未記録へ。DB に書かない (決定 5)。
- 手動・未記録で別のフォルダへ移ると、その選択は消える (決定 5 の「記録しない」の帰結。セッション内でも覚えない)。
- 手動 → 別の並び順を選ぶ: 全体の並び順をそれに変え、このフォルダを通常に戻す。記録があれば「有効」の印だけ外す (決定 6)。
- 手動・記録ありのフォルダは、開き直しても・再起動しても手動順で開く。
- お気に入りの表示状態が並び順を覚えている場合も、手動のフォルダでは手動順が勝つ。

## 3. 保存先とキー

新しい DB ファイル `folder_order.db` (data_dir、`folder_thumb_pins.db` と同じく機能ごとの DB)。

```sql
CREATE TABLE folder_order_items (
  item_key TEXT PRIMARY KEY,   -- 子の完全 path、normalize_keep_drive (tags.db と同じ)
  position INTEGER NOT NULL
);
CREATE TABLE folder_order_folders (
  folder_key TEXT PRIMARY KEY, -- フォルダの完全 path、normalize_keep_drive
  active INTEGER NOT NULL,     -- 1 = 手動順が有効 (決定 6 の印)
  revision INTEGER NOT NULL
);
PRAGMA user_version = 1;
```

- フォルダの列を items に持たない。`STORES` は 1 行 1 列なので、2 つの path 列を持つ表はフォルダ改名で片方が古く残る。
  フォルダの子は `item_key` の範囲 (`folder_key + '/'` から上限まで、既存の `prefix_upper_bound` と同じ考え方) を引き、
  直下の子だけを Rust 側で残す。
- `STORES` に 2 行足す: `folder_order.db / folder_order_items / item_key` と `folder_order.db / folder_order_folders / folder_key`
  (KeepDrive、unique、book_policy = Follow)。これで mIV 上のファイル改名・フォルダ改名 (子の prefix 書き換え)・削除の purge・
  孤児整理に既存の表で乗る。
- **content-identity の復元と metadata_transfer / image_folder_zip_metadata の複写からは外す**。位置は元のフォルダの中の値なので、
  別のフォルダへ複写すると移動先の順に混ざる。移動したファイルは移動先で未知 = 末尾 (backlog の案どおり)。
  descriptor に「複写しない」印を足すか既存の分類で外すかは実装時にコードで決める。
- 保存は**そのフォルダの直下の行を全部消して今の全順を 0..n で書き直す** (1 transaction)。古い名前の孤児 (外部で改名・
  移動されたもの) は次の保存で自然に消える。
- キーは小文字化されるので、大文字小文字だけの改名は移行が何もしないが、キーが同じなので位置は保たれる。

## 4. 並びの決め方 (resolver)

`materialize_local_folder_listing_with_order_and_metadata` に、手動順の記録を受け取る入口を足す
(`ListingOrderRequest` に手動の形を足す。名前は実装で決める)。PC 本体・Remote・Agent IPC が同じ結果になる。

1. まず従来どおり基準の並び (全体の並び順、お気に入りの表示状態が効くならそれ) で並べる。
2. 手動のときは、**段 (`GridDisplayOrder`) の中で**、記録にある子を記録の位置順に先に出し、記録に無い子
   (未知) を後ろへ**名前順**で並べる (本棚順 §4 と同じ)。記録にあって実在しない子は飛ばす。
   段をまたいだ並べ替えはしない (利用者確認 Q2)。
3. 手動・未記録のときは 1 の結果のまま (= 直前の並び順)。
4. 読むだけでは書かない。未知の子は、次にそのフォルダで並べ替えたときに記録へ入る。

記録を読む場所 (UI スレッドで DB を開かない、[ui-responsiveness.md](ui-responsiveness.md) §4):

- フォルダを開く scan の worker (`start_folder_open_scan`) が記録を読み、scan の結果に載せる。
- App は今のフォルダの記録を**メモリに 1 つだけ持つ** (所有者はフォルダ一覧の状態)。watcher の再走査・並び順の変更による
  再走査には、DB を読み直さずこのメモリの記録を渡す。mIV 上の改名の完了時にはメモリの記録のキーも書き換える。
  これで「改名の移行が DB に届く前に再走査が走り、改名したファイルが末尾へ行く」競合が起きない。
- Remote は自分のプロセスで `folder_order.db` を読む (今の listing の再計算と同じ thread)。
- 読めない記録 (DB の異常) は既定の割り切り: ログ + 通知、基準の並びで表示し、そのフォルダの手動順の書き込みを止める。

## 5. 一覧での並べ替えのドラッグ

- 対象: 手動 (未記録・記録あり) のフォルダの**サムネイル一覧**。詳細表示は手動順で表示するが、ドラッグは従来どおり
  (利用者確認 Q4)。
- `dispatch_grid_cell_input` の `drag_started` で、手動のときは `pending_native_drag` を立てず、並べ替えのドラッグを始める。
  手動以外では今のコードをそのまま通る (決定 3 の「戻る」ことをテストで確かめる)。
- 掴んだセルが選択 (`checked`) に含まれれば選択全体を、含まれなければ掴んだ 1 件を動かす (コレクションの窓と同じ)。
  選択内の相対順は保つ。
- 挿入位置はセルの左右半分で前/後ろ。挿入線は既存の窓と同じ縦棒。段の外・別の段の上では挿入線を出さず、離しても動かない。
- 端での自動スクロールは一覧の外部スクロール所有者を通し、オフセットは `cell_size` の整数倍を守る
  (coding-conventions の一覧スクロール規則)。
- フィルタ (ファセット・絞り込み) で隠れている子がある場合、見えている子の並べ替えを全体の順へ合成する
  (`collection_visible_order::merge_visible_order` と同じ考え方)。隠れている子の相対位置は保つ。
- 離した位置が元と同じなら何もしない (記録も始めない)。動いたときだけ、App のメモリの記録と `App.items` を
  その場で並べ替え (再走査しない)、保存を worker の latest-value writer へ送る。最初の成功で手動・記録ありになる (決定 5)。
- 並べ替えのドラッグ中はカーソル形状を変えてよい (決定 3 のオプトイン)。Esc での取り消しは既存の窓に無いので足さない
  (一覧の外で離せば何もしない)。
- 共通化: 本・コレクションの窓の挿入位置・自動スクロール・グループ移動の重複関数を、今回の一覧と 3 か所で使う
  共通 helper へまとめるかは実装の最初の段で判断する (まとめるなら挙動不変のリファクタとして別コミット)。

## 6. 切り替えとリセットの UI

- 「ソート順」メニューと並び順のドロップダウン (ツールバー / ファセットバー共通の `draw_grid_sort_dropdown`) に
  「手動順 (このフォルダ)」を足す。手動のときはこれが選択状態、ほかの並び順は非選択に見せる。
- 「手動順をリセット…」を同じ場所に足す。記録があるフォルダでだけ有効。**確認あり** (利用者が作った順が消えるため)。
  実行すると記録 (items と folders の行) を消し、そのフォルダは手動・未記録として**今の全体の並び順から**やり直す (決定 7)。
- 使えない場所 (§0 の範囲外、本としてページ順が固定のフォルダ = `GridSortLockReason::PageOrderFixed`) では
  「手動順」を無効表示にする。判定は `listing_sort_capabilities` に乗せる。
- ファイル名スタックの表示中は手動順を使えない (利用者確認 Q3)。スタックを ON にしたら手動の表示を外し (記録は残す)、
  手動を選ぶとスタックを OFF にする。どちらも transient の状態なので DB には書かない。
- キー操作: `KeyAction` に「手動順に切り替え」を既定キー無しで足す (keymap の 6 点を揃える)。並べ替え自体のキー操作
  (選択を前へ/後ろへ) は V1 では足さない (本棚順・コレクションの窓と同じく、固定入力の扱いも不要)。
- Remote: 手動のフォルダは同じ resolver で同じ順に見える。Remote からの並び順変更は手動のフォルダでは拒否し、
  理由を表示する (`physical_page_order_locked` と同じ拒否の経路)。Remote からの並べ替え・手動の切り替えは V1 では無い。

## 7. 手動順のフォルダで今の使い方から変わること (利用者確認 Q5)

手動を選んだフォルダ (と、記録があって有効なフォルダ) のサムネイル一覧でだけ、次が変わる。
手動を選んでいないフォルダ、詳細表示、ほかのビューは今のまま。

1. サムネイルのドラッグで、Explorer・他のアプリへのファイルのドラッグ (コピー) ができない。
2. サムネイルを一覧の中のフォルダのセルやフォルダツリーへドラッグして移動・コピーすることができない。
3. ファイル名スタック表示と同時に使えない。
4. Remote から、そのフォルダの並び順を変えられない。

1・2 が要るときは、詳細表示に切り替えるか、別の並び順に戻せばよい (記録は残る)。

## 8. 段の分け方 (実装の段)

1. ストアと resolver: `folder_order.db` (schema・読み書き・STORES 2 行と複写の除外)、listing の手動入口、
   scan worker / 再走査 / Remote の受け渡し、App のメモリの記録と改名時の書き換え。UI 無しでテストできる範囲。
2. 切り替え・リセットの UI、`listing_sort_capabilities`、スタックとの排他、KeyAction、Remote の拒否。
3. 一覧の並べ替えドラッグ (共通 helper の判断を含む)、保存 writer、フィルタ中の合成、自動スクロール。
4. マニュアル・製品ページ・設計文書 (architecture-overview・display-pipeline・keymap-spec・virtual-folders の範囲外の記述・
   filename-stack-plan) の更新。

## 9. テスト

- resolver: 記録順・未知は末尾で名前順・消えた子を飛ばす・段の中だけ・未記録は基準の並び・大文字小文字違い。
- 状態遷移: 通常→手動 (記録無し/有り)→並べ替え→別の並び順→手動に戻す→記録した順、リセット後は今の並び順から、
  手動・未記録で別フォルダへ移ると消える、DB に書くのは最初の成功した並べ替えからだけ。
- 改名: mIV 上のファイル改名・フォルダ改名で位置が保たれる、削除で purge、孤児整理の対象になる、
  content-identity の復元で他フォルダへ位置が複写されない。改名直後の再走査で末尾へ行かない (メモリの記録)。
- 入力 routing (handler-level): 手動のときだけ drag が並べ替えになり `pending_native_drag` が立たない。手動以外・詳細表示では今のまま。
  選択グループの移動、段をまたぐ離しは無効、同じ位置は無変更。
- Remote と PC が同じ順を返す。Remote の並び順変更が手動のフォルダで拒否される。
- UI スレッドで `folder_order.db` を開かない (open / 再走査 / 並べ替えの各経路)。

## 10. 簡素化の検討 (CLAUDE.md「状態の組み合わせを減らす」)

- 採用: 手動をフォルダごとにして全体の並び順・お気に入り・Remote の並び順変更と独立させた (§2)。
- 採用: 未記録の手動はメモリだけ・フォルダを出たら消す。「切り替えたが未記録」を DB と同期する状態を作らない。
- 採用: 保存はフォルダの全順の書き直しだけ (差分更新・位置の詰め直しの別処理を持たない)。孤児も同じ書き直しで消える。
- 採用: 今のフォルダの記録の所有者を 1 つ (App のメモリ) にし、再走査は DB を読み直さない。改名との競合を構造で消す。
- 採用: スタック表示と排他にした (スタックの中の並びと手動順の組み合わせを扱わない)。
- 採用: Remote は読むだけ。Remote からの並べ替え・切り替えは扱わない。
- 不採用: 本棚順と同じフォルダ内 JSON (決定 1 でフォルダへ書かない)。
