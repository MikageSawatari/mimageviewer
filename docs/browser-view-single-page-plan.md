# §1.870 ブラウザから開いた画像が保存先の別の画像と見開きになる件の設計

2026-11-23。設計担当 ClaudeCode。ブランチ `browser-870-single-page` (master `30c5a0e32` から)。実装は未着手。
独立設計レビュー 1 回目 (GPT-6.1 Sol / xhigh、`8d8d6c841`) は REVISE。指摘 4 件 (P1 1・P2 3) を、この版で直した (§8)。

## 1. 観測と、コードで確かめた原因

- **観測** (利用者、2026-11-23): メイン PC の v5.6.0 と拡張 0.2.0 で、手引きの 1-4「mIV が起動しているときに続けて開く」を行ったときのこと。ブラウザから開いた画像と、保存先のそれ以外の画像の 2 枚が見開きになることがあった。<kbd>1</kbd> で単ページにすれば問題ない。
  - 利用者の設定の値と、保存先の月のフォルダの保存行は未確認。§6 の質問 0。
- **原因** (コード):
  - ブラウザから開く窓 (`DetachedWindowPurpose::BrowserView`) は、保存先の月のフォルダ (例 `…\mimageviewer\browser\2026-11`) をふつうの物理フォルダとして読み込み、その中の受け取った画像を開く。
  - 単ページ / 見開きの形は、ほかのフォルダと同じ決まりで決まる。BrowserView 用の扱いは無い。
  - 読み込みの既定値は `SpreadRestoreDefaults::for_physical_folder` (`src/app.rs:13752`) が決める。入力の `book_locked` は `physical_page_order_locked` (`src/app.rs:13712`) で、次のどれかなら真になる。
    - (1a) 本棚の製本フォルダ (`is_direct_book_folder`)
    - (1b) コンテナとして開く指定のフォルダ (`is_open_as_container`)
    - (1c) **画像だけのフォルダを本として扱う設定** (`auto_fullscreen_image_folders_enabled()`) が有効で、一覧がすべて画像
      - この設定 (`settings.rs:9799`) は、環境設定の「本の表示モード」が「開いたとき、ページを表示」(`auto_fullscreen_zip_pdf`、または複数ウィンドウのモード) で、かつ「画像のみのフォルダは、PDF/ZIP のように本として扱う」(`auto_fullscreen_image_folders`、既定 OFF) が ON のときに有効になる。
      - ブラウザの保存先の月のフォルダは画像だけなので、この設定が有効なら必ず本扱いになる。
  - 判定の順番:
    1. `book_locked` が真: 全体の既定 `default_spread_mode`。
    2. 「通常フォルダにも既定のページ構成を使う」(`apply_default_spread_to_plain_folders`、既定 OFF) が ON の実フォルダ: `default_spread_mode`。
    3. それ以外: 単ページ (`NON_BOOK`)。
  - そのフォルダに保存行 (`spread.db` の `spreads`、キーはフォルダのパス) があれば、それが既定値に勝つ (`src/app.rs:29365`、`src/spread_db.rs:94`)。
  - したがって、受け取った画像が別の画像と組になるのは次のどれかのときで、ここで尽きる。いずれのときも、全体の既定が見開きであることが前提。
    - (1c) の設定が有効。
    - 「通常フォルダにも既定のページ構成を使う」が ON。
    - その月のフォルダで、以前に見開きを選んで保存した。
    - 利用者がその月のフォルダを製本 (1a)、またはコンテナ指定 (1b) にした。
  - 月のフォルダには、前に受け取った関係のない画像が並ぶ。そのため隣の画像と組になる。
- **<kbd>1</kbd> の意味** (`src/ui_fullscreen.rs:47409` `apply_fullscreen_spread_mode`):
  - 表示中のフォルダの保存行を Single に書き換える (`persist_spread_presentation`) 操作で、一時的な切り替えではない。
  - 利用者の回避は、その月のフォルダについては残る。次の月の新しいフォルダでは、また既定に戻る。

## 2. 守ること

- 受け取った 1 枚は、単ページで見えること。関係のない保存済みの画像と組にならないこと。
- 利用者が保存した見開きの設定 (全体の既定、ほかのフォルダの保存行) を変えない。勝手に書き込まない。
- 利用者が保存先のフォルダで明示的に選んだ形は、覚えて従う (読み込み・保存・再計算の 3 つで同じ既定を使う)。
- 決まりは設定とデータから決まり、開いた順番・窓の状態・起動直後の準備の進み具合で変わらない (決定性)。
- UI スレッドで同期 I/O をしない。
- 別ウィンドウ (detached) の述語・viewport・窓の寿命には触れない (凍結の決まり)。

## 3. 案

### 案 A (推奨): ブラウザ閲覧の保存先のフォルダは、ページ構成の既定を単ページにする

- **決まり:** 「ブラウザ閲覧の保存先」の根とその下のフォルダは、ページ構成の既定を単ページ (`NON_BOOK`) にする。読み込み・保存・メタデータの再計算・Remote の 4 つで、同じ既定を使う。
- **優先順位 (判定の順番):**
  1. 明示の本 (1a・1b): 全体の既定。製本やコンテナ指定は利用者の明示の操作なので、今までどおり。
  2. **保存先の根の下: 単ページ。** (1c) の自動の本扱いと、「通常フォルダにも既定」の ON より先に判定する。
  3. 自動の本扱い (1c): 全体の既定。
  4. 「通常フォルダにも既定」が ON の実フォルダ: 全体の既定。
  5. それ以外: 単ページ。
  - どの順位でも、保存行があれば保存行が勝つ (今までどおり)。
- **範囲:** 変えるのはページ構成 (見開き・読む方向・連結) の**既定値だけ**。
  - (1c) のほかの効果 (ページ順の固定、画像フォルダを全画面で開く、など) は変えない。
  - そのため、`physical_page_order_locked` の bool はそのまま残す。ページ構成の既定のためだけに、本扱いの種類 (明示 / 自動 / なし) を返す関数を足し、`physical_page_order_locked` はその結果から bool を作る (判定の綴りを 1 か所にする)。
- **触れる場所:**
  - (a) 既定の計算:
    - `SpreadRestoreDefaults` に、物理フォルダの既定を決める関数を 1 つ置く。入力は、本扱いの種類・保存先の根の下か・実フォルダか・設定。
    - 呼び出し元 3 か所 (`install_loading_items_inner` `src/app.rs:44826`、メタデータの取り込み完了 `src/app.rs:51073`、Remote `src/remote_ipc/container.rs:6884`) が、すべてこれを使う。
  - (b) 保存時の既定の一致の判定 (P2、§4):
    - `persist_spread_presentation` (`src/ui_fullscreen.rs:46953`) と Remote の保存 (`src/remote_ipc/ui.rs:3130`) は、今は全体の既定と比べ、一致すると保存行を消す。
    - これを、(a) と同じそのフォルダの既定と比べる形にする。
  - (c) メタデータの再計算 (P2): 今は「通常フォルダにも既定」が ON のときだけ (a) の計算を使い、OFF では旧経路で全体の既定に戻り得る (`src/app.rs:51078`・`51112`)。保存先の根の下では、ON / OFF に関係なく (a) の既定を使う。根の外は、今の計算をそのまま保つ。
- **窓の経路への影響:** 無い。
  - フル機能のモード (linked 窓) では、メインの App が月のフォルダを読み込む。そのときの値が単ページになるだけ。
  - 複数ウィンドウのモードでも、fork はその値を写すだけ (`viewer_context_registry.rs:5186`)。
  - 窓を閉じたときの復元、次の画像が届いたときの掛け直し、保存の漏れ止め、どれも要らない。BrowserView の述語を新しく読まない。
- **メインウィンドウとの一貫性:** 場所▼の「ブラウザ閲覧」から月のフォルダを開いて全画面にしても、同じく単ページ。窓とメインの一覧で形が食い違わない。
- **前後の画像への移動:** 今までどおり移れる。移っても単ページのまま。新しい制限は足さない。

### 案 B: BrowserView の窓だけ、表示を常に単ページにする (保存行も無視)

- 窓の用途 (`BrowserView`) を見て、表示の形だけ単ページにする。設定値と表示値を分ける。
- **退けた理由** (状態の組み合わせが大きく増える。CLAUDE.md「設計の簡素化」):
  - フル機能のモードでは、BrowserView の窓がメインの App と `spread_mode` を共有している。一時的に Single を入れると、次の処理がすべて要る。
    - 窓を閉じた・置き換えた・F11 / park したときに戻す。
    - フォルダの読み直し (`src/app.rs:45065`、`51073`) の後に掛け直す。
  - 保存の漏れが 4 経路ある (`ui_fullscreen.rs:47834`・`47892`・`30778`、お気に入り表示中の既定の書き換え `settings.rs:9718`)。
  - 「設定値と表示値を分ける」形にすると、`spread_mode` を読む全画面の処理すべてに、窓の用途の判定が入る。detached の述語を表示の主経路へ持ち込むことになる。
  - 利用者が保存先で明示的に選んだ見開きも上書きしてしまう。

### 案 C: 受け取った 1 枚だけを見せ、前後へ移れなくする

- 退けた。窓に新しい制限を足すことになり、今できる「保存済みの画像を見返す」がなくなる (リリース済みの挙動の退行)。

## 4. 案 A の細部

- **保存先の根:**
  - 環境設定の「ブラウザ閲覧の保存先」(`settings.browser_view_output_dir`) が指定されていればそれ。無ければ既定 (ピクチャ\mimageviewer\browser)。
  - 根自身とその下を対象にする。比べ方は既存のパス比較 (`folder_tree::path_eq` と同じ、大小無視の component 比較)。
- **既定の根の求め方 (P2、初期化の境界):**
  - 既定の根は、ピクチャの既知フォルダに `mimageviewer\browser` を足して作る。`SHGetKnownFolderPath(FOLDERID_Pictures, KF_FLAG_DONT_VERIFY)` を使う。`KF_FLAG_DONT_VERIFY` は存在の確認をしない旗で、今の `KF_FLAG_DEFAULT` は存在の確認が残る。
  - **UI が動き出す前に 1 回だけ求めて保持し、判定は保持した値だけを読む。** 置き場所は、App を作る前の起動処理 (`main` から eframe の起動の前)。
    - 判定の側からは照会しない。照会の完了を待つ経路も作らない。
    - 照会に失敗したとき (ピクチャを解決できない) は、既定の根なしとして保持する。そのときは、明示の保存先だけが対象。
  - 登録の側 (`browser_integration::backend::Environment::capture`) の既定の保存先も、同じ関数から作る (綴りを 1 か所にする)。登録の側は今までどおり worker で呼ぶ。
    - 登録の側の `pictures_dir()` は、ピクチャのフォルダが無いと `USERPROFILE\Pictures` に代える。この代替とだけは食い違い得る。
    - まれな環境なので割り切る。そのときはふつうのフォルダの決まりに従うだけで、データは変わらない。
- **連携が OFF のとき:** 判定は連携の ON / OFF に関係なく、保存先の根で行う。OFF にした後も、以前に受け取った画像のフォルダは同じ形で見える。
- **保存先を変えたとき:** 新しい根が、次の通常の読み込みから対象になる。前の根は対象から外れ、前の保存先に残った画像のフォルダは、ふつうのフォルダの決まりに戻る。保存行は書かないので、何も失われない。
- **保存行の扱い (P2):**
  - 読み込みの既定値は `spread.db` に書かない。既存のテスト `plain_folder_spread_install_uses_scan_and_does_not_persist_defaults` と同じ契約。
  - 保存時の「既定と同じなら行を消す」判定は、そのフォルダの既定 (§3 (a)) と比べる。
    - 例: 全体の既定が Ltr のとき、保存先の月のフォルダで <kbd>2</kbd> (Ltr) を選ぶと、フォルダの既定 (Single) と違うので行を残す。再読み込みしても Ltr。
    - 例: その後 <kbd>1</kbd> で Single に戻すと、フォルダの既定と同じなので行を消す。
  - **ほかのフォルダへの波及:** 同じ不整合が、今の通常フォルダにもある。「通常フォルダにも既定」が OFF で全体の既定が Ltr のとき、ふつうのフォルダで Ltr を選ぶと、全体の既定と一致して行が消え、再読み込みで単ページに戻る (コードからの推測、実機では未確認)。
    - (b) をそのフォルダの既定と比べる形にすると、この不整合も同時に直る。
    - これはリリース済みの挙動の修正で、不便になる変更ではない。ただ、見える挙動が変わるので、§6 の質問 4 で利用者に確かめる。
  - 保存の入口のうち、本・ZIP・抽出の経路 (`snapshot_ops.rs:4325`、`global_search_ui.rs:6240`、`image_folder_zip_job.rs:1309`) は、キーが物理フォルダではないか、既定が全体の既定と同じなので、変えない。実装の前に、キーが物理フォルダになり得ないことを確かめる。
- **Remote:** Remote も同じ既定の関数を使う (`container.rs:6884`)。保存先の根を live な `reading_settings` に含める。内部の snapshot に足すだけなので、IPC の wire は変わらない (独立レビューの確認)。保存側 (`remote_ipc/ui.rs:3130`) も (b) と同じ形にする。
- **公開文書:**
  - マニュアルの「ブラウザ連携」の「保存先と『ブラウザ閲覧』」に 1 文足す。「保存先のフォルダは、ページ構成の既定の設定にかかわらず単ページで開きます。見開きにしたい場合は、そのフォルダで見開きを選ぶと覚えます。」の形。
  - 設定リファレンスの「通常フォルダにも既定のページ構成を使う」と「画像のみのフォルダは、PDF/ZIP のように本として扱う」に、例外として 1 文ずつ足す。

## 5. テスト (実装時)

- 既定の関数の表の単体テスト:
  - 入力: 本扱いの種類 (明示 / 自動 / なし) × 保存先の根の下か × 「通常フォルダにも既定」ON / OFF × 実フォルダか。
  - 根の外は、今までどおりの結果になること。
- インストールの状態遷移テスト:
  - 全体の既定が見開きで、(1c) が有効、または「通常フォルダにも既定」が ON のとき、保存先の月のフォルダを読み込むと `spread_mode == Single`。
  - `spread.db` に行が書かれない。
  - 保存行 (見開き) があれば見開き。
  - 明示の本 (1a・1b) なら全体の既定。
- 保存と再読み込みの回帰: 全体の既定が Ltr のとき、保存先の月のフォルダで Ltr を選ぶ → 再読み込みで Ltr。Single に戻す → 行が消える。ふつうのフォルダ (根の外、「通常フォルダにも既定」OFF) でも同じ (§6 の質問 4 で直すと決めた場合)。
- メタデータの取り込みの後の再計算: 保存先の根の下で、「通常フォルダにも既定」の ON / OFF の両方で Single を保つ。根の外は今までどおり。
- 既存の browser818 のテスト (フル機能 / 複数ウィンドウの両経路) で、受け取った画像が単ページで開くこと。窓の経路のコードは変えない。
- 環境設定の保存先を変えたとき、次の読み込みから新しい根で判定されること。
- 既定の根: 保持した値だけを読むこと (判定の関数が照会を呼ばないこと)。照会に失敗したときは、明示の保存先だけで判定すること。
- Remote: 月のフォルダの既定が Single、Remote からの保存と再読み込みも同じ規則であること。
- 実機確認 (利用者): 全体の既定が見開きで、(1c) が有効、または「通常フォルダにも既定」が ON の状態で、手引きの 1-3〜1-4 と同じ操作をする。毎回単ページで開くこと。

## 6. 利用者に決めてもらうこと (推奨を先頭に)

0. (確認) 観測した時点の設定の値。
   - 「本の表示モード」が「開いたとき、ページを表示」(または複数ウィンドウのモード) で、「画像のみのフォルダは、PDF/ZIP のように本として扱う」(1c) が ON だったか。
   - 「通常フォルダにも既定のページ構成を使う」が ON だったか。
   - 全体の既定は見開きだったか。
   - 月のフォルダに保存行があったか。
   - どれも案 A で直る (保存行のときは、利用者の明示の選択として残る)。統括が利用者の `settings.db` と `spread.db` を読み取りだけで確かめられるなら、質問は不要。
1. 直し方:
   - **(推奨) 案 A**: 保存先のフォルダは既定を単ページにする。そこで見開きを選んだら、それを覚えて従う。
   - 案 B: ブラウザから開いた窓だけ、常に単ページ (そのフォルダで選んだ見開きも無視する)。窓を閉じたときの戻し方や保存の漏れ止めが要り、手間と不具合の余地が大きい。
2. 前後の画像への移動:
   - **(推奨) 今までどおり移れる**。移っても単ページ。
   - 受け取った 1 枚だけを見せ、移れなくする。今できる「見返す」が無くなる。
3. 保存先のフォルダで見開きを選んだ場合:
   - **(推奨) 覚えて従う** (案 A のまま)。
   - 保存先のフォルダでは見開きを選んでも覚えない。
4. 保存時の既定の一致の判定を、ふつうのフォルダにも揃えるか:
   - **(推奨) 揃える**。ふつうのフォルダで全体の既定と同じ見開きを選んだとき、再読み込みで単ページに戻る今の不整合 (コードからの推測、未確認) も直る。
   - 保存先のフォルダだけに限る。ふつうのフォルダの挙動は今のまま。

## 7. 凍結の決まりとの照合

- 案 A は、別ウィンドウの述語 (`DetachedWindowPurpose`・linked / independent)・viewport・窓の寿命・placement に触れない。変えるのは、フォルダのページ構成の既定値の決定と、保存時のその既定との比較だけ。
- 窓の種類で分岐する処理を足さない。症状を消す guard / delay / retry / 一括 reset / silent fallback ではない。
- 原因 (関係のない画像が並ぶフォルダに、本と同じ見開きの既定を当てていた) に対応する。
- 独立レビュー 1 回目の言葉:「ブラウザ保存先を共通のフォルダ既定で扱う方針は、detached の述語・viewport 経路に触れず、原因となる既定値の決定境界を修正するものであり、症状パッチではない。」
- 実装の後にも独立レビューを受け、結果を [detached-rework-plan.md](detached-rework-plan.md) §11 に記録する。

## 8. 独立設計レビューの記録

- **1 回目 (2026-11-23、GPT-6.1 Sol / xhigh、read-only、`8d8d6c841`): REVISE。** 凍結の決まりの点の構造方針には合意 (§7)。
