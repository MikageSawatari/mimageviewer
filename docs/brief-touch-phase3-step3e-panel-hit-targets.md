## 1. この Step の範囲

Step 3b で左右パネルは指で**開ける**ようになった。しかし plan §5.7-3 の実測どおり、
**パネルの中身が 100% では押せない / 押し間違える**。

Step 3c が上バーで作った resolver を、**パネル内の名指しされたコントロール**へ広げる。

**入れるもの** (すべて静止画フルスクリーンの左右パネル):

| 対象 | 現状 (100%) | 解決方式 |
| --- | --- | --- |
| **★ 行** | 1 個 ≒ 20×20、最小値指定なし | **行全体を 5 等分**して最寄りの ★ |
| **タグ ON/OFF** | 通常 Button、最低高 18 | 行内の最寄りボタン |
| **AI モデル行** | radio / checkbox 本体のみ | **行全体**をタップ対象に |
| **カラー化スロット** | 22×22 | 隣接スロットの中点まで |
| **ブックマーク追加** | 24×20 | 周囲へ拡張 |

**入れないもの**:

- **slider の縦方向 hit**。plan §5.7-3 の訂正どおり **実 hit target は track 全体
  (幅 100 × 高さ最低 18)** で、handle が小さくても track のどこを押しても操作できる。
  しかも slider は tap ではなく **press-drag-release の連続ストリーム**なので、
  「最寄り id を解決する」という本 Step の機構とは別物になる。
  **実機で押しにくいと分かってから、別の Step で扱う。**
- **native 動画パネル** (ジャンプ / ブックマーク / 補正 / ★ / タグ)。別レンダラなので後続 Step
- **HUD ボタンのターゲットサイズ**。後続 Step
- **音楽ビューの初回ヘルプ**。後続 Step

⚠ ただし **範囲は「面」ではなく「機構」で切ること**。★ 行やタグボタンの描画コードが
静止画と音楽ビューで**共有されている**なら、両方に効くのが自然である。
**範囲を狭めるために共有コードを分岐させないこと。**

## 2. 既存の機構をそのまま広げる

**新しい仕組みを作らないこと。** Step 3c が
[src/ui_fullscreen/draw_icons.rs](../src/ui_fullscreen/draw_icons.rs) に持っている形をそのまま使う:

1. 描画時に各ボタンが **自分の rect と `egui::Id`** を viewport ごとの `ctx.data_temp` へ記録する
2. 次フレームの入力処理で、**相関済み touch tap の release 位置**を
   **前フレームに記録した矩形群**へ解決する (`resolve_bar_touch_target`)
3. 解決された id を、**既存の `Response::clicked()` 相当の分岐へ合流**させる
4. 幾何が変わったフレーム (bar_rect 変化) では、**古い矩形へ解決せず 1 フレーム待つ**

### 2.1 上バーとの違い — 群 (group) の概念が要る

上バーは「1 つの矩形の中に横一列」なので 1 次元 Voronoi で済んだ。
パネルは **★ 行 / タグの折り返し行 / AI モデルの縦リスト / カラー化スロット** が同居する。

したがって **「コンテナ矩形 + 主軸」を持つ群**へ一般化する:

- **★ 行**: 行矩形の中で**横**に 5 等分
- **タグ**: 折り返すので**行ごとに群**を作り、行の中で横に最寄り
- **AI モデル行 / カラー化スロット**: 縦リストなら**縦**に最寄り (= 行全体が当たり判定)
- 群の**コンテナ矩形の外**に落ちた tap は**未割当のまま**にする
  (上バーの左端より左を未割当にしているのと同じ考え方)

### 2.2 ⚠ パネルはスクロールする — 前フレームの矩形が動く

上バーは固定なので `bar_rect` の一致だけで無効化できた。
**パネルは `ScrollArea` の中なのでスクロールすると矩形が動く。**

- 記録時のスクロールオフセットを一緒に持ち、**解決時に一致しなければ解決しない**こと
- 指ドラッグでスクロールした直後のフレームで、**古い位置のボタンへ解決してはならない**。
  これは「スクロールしたつもりが★が付いた」という実害になる
- 1 フレーム待って解決しないほうが、間違ったボタンを押すよりはるかに良い

## 3. ⚠ 見た目とレイアウトを変えないこと

plan §5.7-3 の注意をそのまま守る:

> タッチを検出したフレームだけ widget 自体を大きくすると**レイアウトが跳ねる**。
> **見た目の rect は固定したまま、raw touch 位置から action を解決する**方式にすること。

- egui の widget rect、paint rect、mouse の hover / click 判定を**一切変えない**
- 解決した id を既存の分岐へ流すだけにする
- **スナップショットが変わったら、それは見た目を変えてしまった合図**である

## 4. ⚠ 先に読むこと — plan §5.10「実機で 3 回踏んだ同型バグ」

この機構は「前フレームに記録した値」を次フレームで使う **cross-frame state** である。
着手前に §5.10 を読むこと。特に:

- egui は同じアプリフレームを**複数 pass** 走らせる。既存実装が `prepared_pass` /
  `cumulative_pass_nr()` でこれを扱っているので、**同じ扱いに揃える**こと
- 解決結果を replay して**同じタップで 2 回発火させない**こと
  (★ が 2 回設定される、タグが ON→OFF に戻る、といった形で出る)
- 新しい bool を足したくなったら設計を疑う

## 5. マウス無影響 (§5.15)

- **マウスのみの入力列で挙動が一切変わらないこと。** hover、click、ドラッグ、
  ツールチップ、フォーカスすべて不変
- resolver が動くのは**相関済みタッチ tap のときだけ**
- `MIV_DISABLE_TOUCH_GESTURES=1` で現行挙動へ戻ること

## 6. テスト

- ★ 行が 5 等分され、各区画が正しい星に解決すること (境界を含む)
- ★ 行の**外**をタップしても解決されないこと
- タグが折り返して複数行になったとき、**別の行のボタンに解決しないこと**
- AI モデル行 / カラー化スロットが行全体 / 中点まででタップできること
- **スクロールオフセットが変わったフレームでは解決しないこと** (§2.2 の回帰テスト)
- 同一タップが複数 pass で**2 回発火しないこと**
- マウスのみの列で従来どおりであること
- 既存のスナップショットが**変わらないこと** (§3)
