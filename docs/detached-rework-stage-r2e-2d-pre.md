## 1. なぜこの段を足したか (設計は②-d を分けないと書いている)

設計 §7 は②-d を「**ここだけは分けられない**」としている。**保管の移行はそのとおり**で、
2 つの保管が 2 つの問いに答えているのが病因なのだから、移行中に 3 つ目を作るのは悪化でしかない。
**保管は 1 コミットで切り替える。この段はそれを変えない。**

分けるのは保管ではなく**読み方**である。実測 (`ab777ed0` 時点、非テスト):

| | 箇所 |
| --- | --- |
| `.active_detached_viewer_context` のフィールドアクセス | 84 |
| └ うち `.is_some()` / `.is_none()` | **47** |
| └ うち `as_ref` / `as_mut` / `take` / 代入 | 23 |
| `.paused_bundle` のフィールドアクセス | 42 |
| └ うち `.is_some()` / `.is_none()` | **4** |
| └ うち `as_ref` / `as_deref` / `as_mut` / `take` / 代入 | 33 |

**存在検査 51 箇所が、この rework の病因そのものである。**
設計 §1 の診断は「**1 つの保管が 2 つの問いに答えている — `None` は『ここに無い』であって
決して『別の場所にある』ではない**」。`.is_some()` はその 2 つを混ぜたまま書ける形で、
**どの問いを訊いているのかがコードに書かれていない**。

保管を差し替える段で同時に問いを決めると、**命名の誤りが保管のバグに見える**。
先に名前を付けておけば、②-d は「名前の付いた問いを registry へ向け直す」だけになる。

## 2. やること

### 2.1 判断に使っている存在検査に名前を付ける (23 箇所)

`,` で終わる (= `format!` / ログの実引数) ものを除いた**判断サイト**は次の 23 箇所。

```
src/app/gamepad_input.rs:564, 5797
src/app/startup_ops.rs:516
src/app.rs:34870, 36451, 36576, 37671, 37710, 37866, 38150, 39317, 39425,
          39483, 39911, 39938, 40006, 40355, 40939, 41160, 41293, 41324,
          42542, 42772
```

**1 箇所ずつ読んで、何を訊いているのかを決めて、その名前のメソッドにする。**
機械的に一括置換しない。**同じ形でも違う問いのことがある。**

問いの語彙は設計 §3.5 の `ContextResidence` に寄せる (②-d でそのまま registry へ向けられる)。
たとえば次のような区別がある — **これは分類の例であって、当てはめる先の一覧ではない**:

- 「detached の context が**在る**か」(= 所有の有無)
- 「今のセッションが detached か」(= セッションの状態。context の有無とは別)
- 「main が投影を**所有している**か」(= `is_none()` を裏返して使っている箇所)

⚠ **`is_none()` を「〜でない」と読んで否定形の名前にしない。**
何を意味しているのかを書くこと。[app.rs:41160](../src/app.rs:41160) と
[:42772](../src/app.rs:42772) は設計 §6.5 が**暫定回避策**と名指ししている箇所で、
`is_none()` が「main がセッションを持っている」の代用になっている。
**この段では撤去しない** (撤去は②-d) が、**名前でそう言うこと**。

⚠ **§1.1 の 4 コピーは 1 本にする。** 4 箇所とも同一であることを確認してから畳む。
差があれば畳まずに報告する。

### 2.2 ログ・診断の存在検査は 1 つの入口に通す (28 箇所)

`format!` の実引数になっている残り 28 箇所は判断ではない。
**1 つの診断用メソッドに通す**だけでよい (例: `active_detached_context_debug_state()`)。
②-d でここを `residence()` に差し替えるとき、直す場所が 1 箇所で済む。

⚠ **表示される文字列を変えないこと。** ログの形式が変わると、既存の調査手順や
`analyze_perf.py` 系の読み方が壊れる。`bool` を出しているなら `bool` のまま出す。

### 2.3 `paused_bundle` の存在検査 4 箇所も同様に

数が少ないので同じ扱いでよい。②-pre が holder 側に残した**前置きフィルタ 2 つ**
(vst3 の pending 判定 / rename 述語、設計 §7 ②-d の ⚠) がここに含まれるはずなので、
**含まれていたら報告する** (②-d で `ContextRef` 述語へ移す対象)。

## 3. やらないこと

- **保管を変えない。** `active_detached_viewer_context` / `paused_bundle` はそのまま。
- **`as_ref` / `as_mut` / `take` / 代入は触らない** (23 + 33 箇所)。
  これらは所有の操作であって、②-d が transaction に置き換える。
- **§6.5 の暫定回避策を撤去しない。** ②-d。名前を付けるだけ。
- **`residence()` / `ViewerContextId` / registry を作らない。** ②-d。
- **述語を「あると便利だから」で増やさない。** 実際に呼ばれるものだけ。
- **テストを増やさない。** 挙動不変で、既存 6251 件が回帰の番人。
  §1.1 の 4 コピーを畳んだ結果だけは、既存テストが覆っていなければ 1 本足してよい。

## 4. 完了条件

1. 非テストコードに `.active_detached_viewer_context.is_some()` /
   `.is_none()` / `.paused_bundle.is_some()` / `.is_none()` が
   **新しい述語の実装の中以外に 1 つも無い**こと。

   ```
   rg -n "\.active_detached_viewer_context\.is_(some|none)\(\)|\.paused_bundle\.is_(some|none)\(\)" src/ -g "!tests.rs"
   ```

   出力を貼る。残るのは新しい述語の中だけ。
2. `cargo test -p mimageviewer --lib` が緑。**件数 6251 のまま** (§3 の例外を使った場合は 6252)。
3. `cargo fmt --check` が無出力。
4. `cargo run -p viewer_context_audit` が exit 0 (既知の指摘 1 件のまま。
   **新しい違反を出さないこと**)。
5. `git diff --numstat HEAD` を貼る。`src/app/tests.rs` の変更は**述語名の追随のみ**で、
   assertion の中身を変えていないこと。
