## 1. 測定済みの事実 (再測定不要)

`C:\tmp\miv-speed-test` (5600×3500 JPEG 12 枚) で `--perf-log` 取得済み。

- キーリピート間隔 **34ms** に対し、実際に表示できたページ間隔 (ready→ready) は **84ms**
- UI スレッドの内訳: **アップロード 21.3ms** + **`final_composite_build` 21.0ms** ≒ **42ms/枚**。
  34ms 間隔の入力に構造的に追いつかない
- デコード自体は 103ms だがワーカー並列なので律速ではない
- 連結読みが滑らかなのは、スクロール中は**実体化済みのページを見せるだけ**で、この
  42ms がキーごとに出ないから
- 当初疑った「current 待ちで他の pending を全キャンセルする経路」は**発生していない**
  (`fs/cancel_check` 132 件すべて `cancelled=false`)

## 2. やること

**次のページ送り入力がまだ残っている間は、通過するページを実体化しない。**

- 通過ページは**アップロード済みのカタログサムネイルで 1 フレーム描く**
- **ページ表示自体は飛ばさない** (利用者要件: 一瞬でも見える形にする)。
  押しっぱなし中も各ページが最低 1 回は描かれること
- 通過ページの画質が落ちるのは**許容**する (利用者判断 2026-08-09:
  「画質を落としてもページ送りを素早くする方をとりたい」)
- サムネイルが無いページは従来どおりデコード待ちでよい

## 3. 設計上の制約 (ここが本題)

### 3.1 「通過ページか」は **保留中の入力**から決めること。時間で決めない

「直前のページ送りから N ms 以内なら通過扱い」のような**経過時間ガードを入れない**。
見えない時間状態で意味が変わる作りは、この repo で繰り返し問題になっている
([docs/touch-support-plan.md](touch-support-plan.md) §5.10)。

**そのフレームの入力キューに次のページ送りがまだ残っているか**という、その場で確定する
事実から決めること。残っていれば通過ページ、残っていなければ停止先として実体化する。

現在の入力処理がページ送りをどう消費しているか (1 フレーム 1 回か、まとめて処理か) を
先に確認し、**1 フレーム 1 ページ進む現在の挙動は変えない**こと (まとめて N ページ進めると
通過ページが表示されなくなり、利用者要件に反する)。

### 3.2 実体化を「止める」のであって「後で捨てる」のではない

通過ページに対して、アップロードと `final_composite_build` を**始めない**。
始めてから結果を捨てる形にすると UI スレッドの 42ms が残る。

### 3.3 停止した瞬間に完全な画質へ寄せること

キーを離した (= 保留入力が無くなった) フレームで、そのページは通常どおり実体化する。
サムネイルのまま残らないこと。

### 3.4 他の入力経路を壊さないこと

ホイール、クリック、シークバードラッグ、ゲームパッド、スライドショー、連結読みの
既存挙動を変えない。連結読みは元から速いので**触らない**。

## 4. 計測 (対策 2 の判断に使うので必須)

再測定して比較できるよう、perf event を残すこと。

`scripts/analyze_perf.py` で読める形にすること (既存の event 命名に合わせる)。
