## 3. 出荷前に直すべき新規指摘

### RE-1 (P1) バックアップの成否が GUI ではどこにも残らない

- 根拠: `src/collection_store/db.rs:104, 128, 135` が `eprintln!`。本体は `windows_subsystem = "windows"` なので
  標準エラーは捨てられる。tags.db は `logger::log`、settings.db は診断ログへ出している。
- 影響: `docs/spec.md` と `manual/collections.html:161` の「失敗はログに記録して機能を維持」が公開時点で偽。
  バックアップが一度も作られていない状態を利用者もサポートも検出できない。
- 修正方向: tags.db と同じく `crate::logger::log` へ流す。成功時も世代数と所要時間を 1 行残すと RE-3 (計装) も兼ねられる。

### RB-1 (P1) 壊れた journal による削除・名前変更の恒久拒否

- 根拠: §1 の表のとおり。`JournalLoadError` は `Read` と `Parse` を型で区別している (`src/rename_key_migration.rs:234-267`) のに、
  admission は両方を同じ `RecoveryFailed` に入れる。`start_delete_files` は全削除の単一入口なので影響はアプリ全体。
  journal の temp ファイルは fsync されない (元 M-7) ため、切断された JSON は起こり得る。
- 経緯: 利用者は 2026-09-20 に「読み取り失敗時に限り物理変更前に停止し理由を表示する」方針を承認している。
  ただしその承認は一過性の読み取り失敗を想定した記述で、**決定的に読めないファイルで永久に止まる**場合の
  出口は設計記録 (`docs/collection-migration-journal-recovery.md`) に無い。修正前は壊れた journal をログ 1 行で
  破棄していたので、M-2 は「旧 bytes の保護」と「操作不能」を交換した形になっている。
- 修正方向 (利用者判断が要る): `Read` (一過性。ロック・I/O) は現行どおり停止して再試行。`Parse` (決定的) は
  settings.db の quarantine と同じく **別名へ退避** (bytes は保持) して空として続行し、退避した旨とファイル名を
  日本語で 1 回通知する。あわせて表示文言から serde の英語を外す (RB-8)。

## 5. キー操作 (A-4) について

- 利用者の指摘どおり、コミット済みの状態ではお気に入りに `GridOpenFavorite1`〜`20` があるのに、コレクションには
  「コレクション N を開く」に当たる操作が無かった。**原因の一部は初回レビュー側にある**。元指摘 A-4 は
  「追加 / 開く / 管理の入口が無い」と書いたのに、Fable が書いた実装計画 §23.9 は追加の 3 操作しか列挙しなかった。
- **追補 (2026-09-21)**: Codex の再調査により、未コミットの §23.12 で本とコレクションの 1〜20 番・前後移動・
  追加先を開く・3 種の管理画面を開く操作と、リングの「追加先のコレクションに追加」が実装された。
  追加レビューの結果は §10.1。

## 6. 利用者の判断が要る点

| 論点 | 選択肢と推奨 |
| --- | --- |
| RB-1 壊れた journal | **推奨**: `Parse` は別名退避して空として続行 + 日本語で 1 回通知、`Read` は現行どおり停止。代案: 現行維持のうえ、表示に対処 (ファイルの場所と退避方法) を書く |

| RD-5 DB 側の全件読み | **推奨**: v4.0.0 は計装済みの `actor_rtt` で 10,000 件時の実測を取り、許容なら v4.0.x で revision だけ返す軽量コマンドを足す |

### 10.2 サイドカー確認の再訪時再利用 — P1=0 / P2=4 / P3=8。**v4.0.x 送りを推奨**

初回レビュー・再レビューの指摘対応ではなく、スマートフォルダ / コレクションの Ctrl+↑↓ で毎回かかる約 150 ms の
確認を条件付きで省く性能改善 (`docs/sidecar-confirmation-reuse-plan.md`、状態は「実装・検証中」)。

- **中核の安全性は成立している**。同期判定の入力 (pending / failed writer、全 bytes SHA-256、両 family の marker、
  最後の source revalidation) は毎回すべて取り直され、再利用されるのは byte 同一入力に対する決定的な解析結果だけ。
  復旧データを誤って読み飛ばす経路は見つからなかった。
- P2:
  - **S2-1** 解析結果をナビゲーションをまたいで保持する。計測記録では実データ 1 フォルダで約 148 MB、上限 256 MiB。
    既存コードが長時間稼働時のメモリ対策として明示的に捨てている物を復活させる方向で、設定で切れず解放点も無い。
  - **S2-2** perf イベントが無く、hit / miss の理由が記録されない。出荷後に効いているか判定できない (計画 §3.1 が未達)。
  - **S2-3** 再利用の一致判定は正規化したパスで行うのに、返すサイドカーは証明作成時の元の綴りを持ち回り、それが
    `App.sidecars` (完全一致 key) の key になる。別の綴りで同じフォルダへ到達すると同一ファイルの owner が 2 つでき、
    後勝ちの flush で編集が消える余地がある。Fable 確定 (`src/sidecar_import/probe_reuse.rs:45-49, 90`、
    `src/sidecar.rs:688-700`)。strict probe 経路では要求された綴りが入るので、この差分で初めて生じる。
  - **S2-4** 計画 §4 が自ら挙げた回帰 (pending / failed writer、dirty write-disabled owner、検証失敗、予算超過) が未テスト。
- 効果は未観測。計画 §6 も実 UI の体感は利用者の検証で確認するとしており、この差分の改善を実機で見た人はまだいない。
- S2 は代替案として、解析結果を保持せず数百バイトの検証証明書だけを持つ形 (メモリ保持ゼロで節約の約 75%) を
  v4.0.x の比較候補として記録している (S2-12)。
