# 本のサムネイルは表紙だけ保存する設定 (§1.452)

- 状態: 設計 (2026-11-08)。v5.1.0 向け。設計 = ClaudeCode、実装 = Codex Sol / high、独立レビュー = Sol / xhigh。
- 発端: 5ch >>623・627。Leeyes の「先頭の画像のみ保存する」に当たる設定。
  目的は、少ない容量でなるべく多くの本の表紙サムネイルを残すこと。
- 関連: [サムネイルカタログ設計](catalog-design.md)、[仮想フォルダ](virtual-folders.md) §3.1・§3.1.1・§3.4、
  [サムネイル要求のライフサイクル](thumbnail-request-lifecycle-plan.md)。

## 1. 仕様

環境設定 → キャッシュに、チェックボックスを 1 つ足す。**既定 OFF** (今の動きのまま)。

- ON のとき、**本の中のページ一覧のサムネイル** (ZIP・CBZ・直読み RAR・変換書庫・入れ子書庫の中の
  画像、PDF・EPUB のページ) を、サムネイルキャッシュに**新しく保存しない**。
- **本棚に並ぶ表紙** (親フォルダの一覧に出る本のタイル) は今までどおり保存する。表紙は本の先頭ページ、
  または利用者が代表に固定した画像で、これが「先頭ページと代表画像だけを残す」に当たる。
- 保存しないページも、表示に必要なときは今までどおり作ってメモリに持つ。ページ一覧・
  フルスクリーンのシーク用サムネイル・ページ概観・先読みは今のまま使える。
- 保存済みのキャッシュは今までどおり読む。設定を変えただけでは、保存済みのキャッシュも
  代表の固定も消さない。
- 代償: 本の中のページは、一度メモリから外れたあと・開き直したとき・再起動後に作り直すので、
  ページ一覧の表示が遅くなることがある。これを設定画面とマニュアルに書く。

### 1.1 「先頭」と「代表」の扱い

表紙の行は、親フォルダの catalog に本ごとに 1 行ある (`zipthumb:` / `pdfthumb:` / `archivethumb:`、
固定があれば `#pin:` 付き)。この行の画像は、固定が無ければ本の自動表紙 (ZIP は書庫内の格納順で最初の
画像、PDF は 1 ページ目)、固定があれば代表の画像そのものである。**したがって「先頭ページと代表画像だけ
保存する」は、表紙の行だけ保存して本の中のページの行を保存しないことで満たせる。**

本の中の一覧で「先頭のページ」「代表のページ」を見分けて、その行だけ保存する案は採らない
(§5 の比較)。中の一覧の先頭行は、既存の「親の表紙 → 本の catalog への seed」(`src/app.rs` の
親表紙 seed。PDF は 1 ページ目、ZIP は一覧の最初の `ZipImage`) が今までどおり 1 行だけ写すので、
本を開いたときに最初のページはすぐ出る。この seed は表紙の画像をそのまま写すだけで生成を伴わず、
今回変えない。

### 1.2 代表を変えたとき

代表を付け替えると、親の表紙タイルのキーが `#pin:{新しい source_id}` に変わる。親の一覧で新しい
キーの要求が出て、表紙として普通に保存される。古い代表の行は既存の `delete_missing` が今までどおり
整理する。新しい仕組みは要らない。本の中で代表に固定したページ自身の行 (エントリ名・ページキー) は、
ON のとき保存しない。親の表紙行が代表の画像を持っているので、本棚の表示には影響しない。

### 1.3 既存の保存設定との優先関係

保存の判定は次の 1 式にまとめる。

```text
保存する = 行の種類が保存を許す (ON のとき、本の中のページの行は許さない)
        && 保存先が使える
        && (force_cache || CachePolicy の判定)
```

- **Off**: もともと新しく保存しないので、この設定は効果が無い (チェックは押せるままにし、説明で触れない)。
- **Auto**: 「PDF ページは常に」「ZIP 内画像は常に」は、表紙には今までどおり効き、本の中のページには
  効かない (ON が絞る)。
- **Always**: 表紙は保存し、本の中のページは保存しない。
- **force_cache**: ドライブ直下の固定代表など、表紙タイル側の要求だけが使う。本の中のページの要求には
  付かないので、式の順序で差は出ないが、行の種類の判定を先に置いて意味を固定する。
- **一括キャッシュ作成**の「ZIP ファイルの中身もキャッシュ」「PDF ファイルの中身もキャッシュ」は、
  その場で利用者が明示して選ぶ操作なので、**一括作成の選択を優先する** (中身も保存する)。一括作成の
  ダイアログで、ON のときに「この設定より、ここでの選択が優先されます」と一行添える。
  一括作成の保存経路 (`src/app/cache_ops.rs`) は変えない。
- 別物で変えないもの: ZIP / PDF 変換キャッシュ、EPUB 変換キャッシュ、編集プレビューキャッシュ、
  フルサイズ・AI の先読み、`pdf_meta` / `container_page_meta` (ページ数)、動画・音声のサムネイル。

### 1.4 対象範囲

| 対象 | ON のとき |
| --- | --- |
| ZIP / CBZ / 直読み RAR / 変換書庫 (RAR・7z・LZH → ZIP) の中の画像 (`ZipImage`) | 保存しない |
| 入れ子書庫・書庫内フォルダの中の画像 (外側書庫の catalog にエントリ名で入る行) | 保存しない |
| 書庫内フォルダ・入れ子書庫のタイル (`ZipDir`、`zipdir:`) | 保存する (その中の本の表紙) |
| PDF / EPUB のページ (`PdfPage`) | 保存しない |
| 親一覧の本タイル (`ZipFile` / `PdfFile` / `ConvertibleArchive`)、固定代表 | 保存する |
| 検索・コレクション等の合成一覧の本タイル (代表の override 付き) | 保存する |
| 検索・コレクション等の合成一覧に出る本のページ (`ZipImage` / `PdfPage`) | 保存しない |
| フォルダの代表 (`folderthumb:`)、通常の画像ファイル | 変わらない |
| 本として扱う画像フォルダの中の画像 | **対象外 (変わらない)** |

本として扱う画像フォルダは対象にしない。中の画像は通常の画像ファイル (`GridItem::Image`) で、
保存先もそのフォルダ自身の catalog であり、通常のフォルダと区別する材料が要求に無い。Auto では
速く読める画像はもともと保存されないことが多く、容量の問題は書庫・PDF より小さい。対象にするには
本扱いの判定を要求生成側へ持ち込む必要があり、状態が増えるので見送る。マニュアルには
「ZIP・PDF などの書庫と文書が対象」と書く。

## 2. 判定の置き場所

**worker の保存直前の 1 か所** (`thumb_loader::load_one_cached` の保存判定と、PDF の取消時回収の
判定) に置く。設定は `CacheDecision` に持たせる。

- `CacheDecision` に `book_cover_only: bool` を足し、`from_settings` で `Settings` から写す。
  `without_thumbnail()` では false。
- 行の種類は、`load_one_cached` が catalog のキーを決める規則と同じ入力で決める。
  `cache_key_override` が無く、`pdf_page` か `zip_entry` がある要求は、キーがページキー
  (`pdf_page_cache_key`) かエントリ名になる「本の中のページの行」である。override がある要求
  (表紙・代表・`zipdir:`・検索の代表) は対象外。この分類を 1 つの関数にまとめ、キーの導出と
  保存判定の両方から呼ぶ (同じ意味を 2 か所に書かない)。
- 保存判定: `save_target.open_if(force_cache, policy_should_save)` の前に行の種類を見て、
  許さない行なら保存先を開かない。
- PDF の取消時回収 (`HarvestOnCancel`): 保存しない行なら回収の意味が無いので `AbortOnCancel` にする
  (既存の「保存しないなら回収しない」と同じ考え)。

この置き場所なら、本体の通常一覧・idle 高画質化 (`SourceOnly`)・RAW の非同期現像の続き・
シーク用サムネイル・ページ概観・mIV Remote (`remote_ipc/container.rs` の preloaded 直呼びを含む)
が、全部同じ判定を通る。要求を作る側 (`make_load_request`、Remote の要求生成) は変えない。

### 2.1 設定の反映の時点

- 本体: thumbnail worker は一覧を読み込むたびに `spawn_thumbnail_workers` で作り直され、そのとき
  `CacheDecision::from_settings` を取る。新しい設定は、OK の後に次に開いた一覧から効く。
  Off / Auto / Always の変更と同じ時点で、専用の作り直し処理は足さない。
- mIV Remote: Remote の thumbnail / container engine が持つ設定 snapshot から `CacheDecision` を作る。
  既存のキャッシュ設定と同じ時点で反映する (実装時に snapshot の更新時点をコードで確認し、
  既存の `cache_policy` と同じであることを確かめる。違えば設計担当へ返す)。

## 3. 影響と代償

- **本体の見開き・横長判定**: メモリ上のサムネイルとフルサイズの寸法を使う (`ui_fullscreen.rs` の
  `known_page_dims`)。保存しなくても、表示したページの寸法は今までどおり分かる。
- **mIV Remote の横長判定**: Remote はページの寸法を catalog の行から読み、行が無い ZIP のページは
  ヘッダだけ読む補完 (`remote_ipc/container.rs`)、PDF は worker への問い合わせで補う。入れ子書庫と
  RAR のページは補完が無く寸法不明になり得る。これは「ZIP 内画像は常にキャッシュ」を外した場合と
  同じ既存の制約で、ON の利用者だけに起こる。マニュアルに一言書く。
- **再生成**: 同じ一覧を見ている間は、表示中のページは Loaded のまま保たれ、保存しないことを理由に
  作り直す経路は無い (通常の再要求は Pending / Evicted のとき、idle 高画質化は origin と解像度で判断)。
  メモリから外れたページへ戻る、開き直す、再起動する場合は作り直しが増える。これは要望どおりの交換。
- **既存の行**: 本の catalog の `delete_missing` は、今の一覧ではなく本に存在する全エントリ・全ページの
  キーを存続集合にする。保存を絞ってもキーの体系は変えないので、保存済みのページの行は消えない。
  ON の間に元のページが更新された場合、古い行は上書きされず残る (mtime / サイズが合わないので
  読まれない)。本を消す・キャッシュ管理で消すときに今までどおり整理される。
- **親表紙からの seed と、本 → 親への書き戻し**: seed は表紙の行を中の先頭行へ写すだけなので残す。
  書き戻しは本の catalog の cache_map に行があるときだけ動き、ON で中のページを保存しなければ
  何もしない (親の表紙は通常どおり親の一覧で作られる)。
- **通常の使い方の変化**: 既定 OFF なので無い。

## 4. 変える場所

1. `Settings`: `cache_book_cover_only: bool` (`#[serde(default)]`、既定 false)。
   `overwrite_non_preferences_from` には足さない (環境設定で編集する項目のため)。
   `settings_transfer.rs` の分類で、既存のキャッシュ設定と同じ「移行しない」群に入れる。
2. `CacheDecision`: フィールド、`from_settings`、`without_thumbnail`、直接リテラル (テスト・
   `bench_scroll`) の追従。
3. `thumb_loader`: 行の種類の関数、`load_one_cached` の保存判定、`HarvestOnCancel` の判定。
4. 環境設定 → キャッシュ (`ui_dialogs/preferences/pages.rs` の `page_cache`): モードの直後、Auto の
   しきい値群の外に置く。環境設定の検索 (`search_index.rs`) に項目を足す。
   - 文言 (案): 「本 (ZIP・PDF など) は表紙のサムネイルだけ保存する」
   - 説明 (案): 「本棚に並ぶ表紙 (先頭ページ、または代表に固定した画像) だけを保存し、本の中のページの
     サムネイルは保存しません。容量を抑えられますが、本を開き直したときにページ一覧の表示が遅く
     なることがあります。保存済みのキャッシュは消えません。」
5. 一括キャッシュ作成のダイアログ (`ui_dialogs/cache_creator.rs`): ON のとき、中身のチェックの下に
   「ここでの選択が優先されます」の一行。
6. マニュアル `htdocs/mimageviewer/manual/settings.html` の「キャッシュ生成設定」の表に 1 行。
   必要なら `tut-cache.html` にも短く。製品ページは変えない (通信・保存先・権限は変わらない)。
7. `docs/catalog-design.md` §9 と `docs/virtual-folders.md` §3.1 に、この判定を 1 段落ずつ。

## 5. 採らなかった案

- **本の中の先頭ページ・代表ページの行も保存する**: 先頭の定義が二つある (自動表紙は書庫内の格納順、
  中の一覧は読書順・本の構成の後)。同期 I/O 無しで一致させるには、列挙 worker で表紙の identity を
  確定して結果に持たせ、要求に型付きの保存指示を載せる必要がある。さらに、ZIP の中で代表を付け替えても
  一覧は作り直されず、表示済みのページは再要求されないので、新しい代表を保存させる専用の受付が要る。
  得られるのは、親の表紙行と同じ画像の複製 1〜2 行だけである。状態と経路が増える割に利点が小さいので
  採らない。最初のページの即時表示は既存の seed で足りる。
- **設定で一括作成の「中身も」を抑える**: 利用者がその場で明示した選択を、離れた場所の設定で
  黙って無効にすることになる。一括作成の選択を優先し、ダイアログに一行添える。
- **要求を作る側 (UI) で保存可否を決めて要求に載せる**: Remote・合成一覧・派生要求のすべての作り手が
  漏れなく載せる必要があり、漏れると黙って効かない。worker の保存直前なら作り手を問わない。

## 6. テスト

設定の追加は、編集 → OK → 効果まで通しで確かめる。

1. `CacheDecision` / 行の種類の関数: (override 有無) × (`zip_entry` / `pdf_page` / なし) × ON / OFF の表。
2. worker (`load_one_cached` / `process_load_request`、偽の PDF レンダを使う既存の型に倣う):
   ON で `ZipImage`・`PdfPage` の行が作られず、表示 (SourcePixels → Finalized) は届く。`ZipFile`・
   `PdfFile`・`ConvertibleArchive`・`ZipDir`・固定代表 (`#pin:`) の行は作られる。OFF では今までどおり
   ページの行も作られる (Always と Auto + 常にキャッシュ)。ON でも保存済みのページの行は読まれる
   (cache hit)。idle 高画質化 (`SourceOnly`) と RAW の続きでも ON が効く。PDF の取消時回収が
   ページでは選ばれない。
3. Remote: container の ZIP エントリ・PDF ページの要求 (preloaded 直呼びを含む) で ON が効き、
   本の表紙要求は保存される。
4. 本体の通し: 環境設定のダイアログで ON にして OK → 設定が保存される → 本を開く (worker が作り直される)
   → 本の catalog にページの行が増えず、親の catalog に表紙の行がある。既存の
   `make_load_request` → worker → catalog の検査 (`src/app/tests.rs` 52226 行付近) に倣う。
5. 既存の行を消さない: ページの行がある本を ON で開き直しても、`delete_missing` の後に行が残る。
6. 代表の変更: ON で本に代表を固定し直すと、親の表紙の新しい `#pin:` 行が保存される。
7. 設定: serde の既定 false、旧設定からの読み込み、環境移行の分類テスト、環境設定の検索項目。

## 7. 簡素化の検討 (CLAUDE.md「状態の組み合わせを減らす」)

- 採用: 判定を worker の保存直前 1 か所に置き、作り手ごとの印を作らない。
- 採用: 「先頭・代表」を表紙の行そのものと見なし、中の一覧での先頭・代表の識別と、代表変更時の
  保存受付をなくした (§5)。
- 採用: 反映の時点を既存のキャッシュ設定と同じ (次に開いた一覧から) にし、表示中の一覧を追従させる
  処理を足さない。
- まれな失敗は割り切り (ログ + 通知 [+ 作り直し])。この設定は保存を減らすだけで、新しい失敗の経路を作らない。
