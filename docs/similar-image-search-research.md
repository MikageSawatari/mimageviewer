# 類似画像検索 / 重複検出 — 調査メモ

> ステータス: **調査のみ (2026-09-03)**。実装計画ではない。
> **→ この調査を受けて狙いは §1 の B (近重複) に確定した。設計は
> [duplicate-detection-plan.md](duplicate-detection-plan.md) が正本。**
> 対象要件 (ユーザー提示):
> - 100 万アイテム程度まで実用速度で動くこと
> - **ある画像を見ているときに「これに似た画像」を一覧表示し、類似先のフォルダへジャンプできる**こと
> - 「ライブラリ全体を総当たりして重複を整理する」機能は無くてもよい

---

## 0. 先に結論

1. **「1 枚に対する類似検索」なら、索引 (VP-tree / BK-tree / HNSW) は要らない。**
   本機での実測で、100 万件の 64bit ハッシュを **線形走査して 0.33 ms** (単スレッド)。
   256bit で 1.6 ms、1024bit の 2 値化埋め込みでも 7.0 ms。索引の保守コスト (追加/削除/再構築/
   世代整合) を丸ごと避けられるので、**Vec への線形走査が構造的に一番安い**。
2. **本当のコストは検索ではなく「全画像のハッシュを作ること」**。100 万枚のデコードが要る。
   ここは既存のサムネイル生成 / FTS インデクサに相乗りさせる話になる。
3. **ハッシュの永続化は必須**。カラー検索でやった「オンデマンドで現在表示分だけスキャン」は
   ここでは成立しない (類似先は今表示していないフォルダにあるのが前提のため)。
   ただし `catalog.db` には載せられない (§4.1)。
4. **マンガ (線画・白背景) は古典的 perceptual hash が最も苦手な領域**。ここは要注意 (§3.4)。

## 1. 「類似」は 4 つの別物 — まずここを分ける

他ツールの機能を並べると、同じ「Find Similar」の名前で**目的の違う 4 つ**が混ざっている。
mIV でどれを作るかを最初に決めないと、閾値も UI も決まらない。

| # | 何を見つけたいか | 典型例 | 必要な技術 |
| --- | --- | --- | --- |
| A | **完全重複** | 同じファイルを 2 回落とした | SHA-256 (画素ではなくバイト) |
| B | **近重複** | リサイズ / 再エンコード / 軽い色調整 / ロゴ入り | perceptual hash (距離 0〜2) |
| C | **別バージョン (alternates)** | 同じ絵の差分・別衣装・同 seed の別サンプラー・修正版 | perceptual hash (距離 4〜8) では取りこぼす。埋め込みの方が強い |
| D | **意味的に似ている** | 同じキャラ / 同じ構図 / 同じ画風 | CNN / CLIP / タガー埋め込み |

ユーザーの要望「ある画像を見て似た画像を一覧」は、文脈次第で **B・C・D のどれにもなり得る**。
AI 生成画像コレクションなら実質 C/D、スキャン漫画やダウンロード画像なら B が中心。

**hydrus はこの区別を UI に持ち込んだ数少ない例**で、ペア判定を
「duplicate (どちらが上位か)」「alternates (別物だが関連)」「false positive」に分ける。
mIV が C を狙うなら、この「重複ではなく別バージョン」という語彙は借りる価値がある。

## 2. 他ツールの実装と用途

### 2.1 hydrus network — 収集家向け、最も設計が近い

- **64bit pHash + VP-tree** で相互ハミング距離を検索。
- 検索距離の意味づけをドキュメントで明示している:
  - `0` = ほぼ確実に同一画像 (リサイズ / JPEG 再圧縮違い)
  - `4` = 髪型や衣装の違い程度まで拾う
  - `8+` = 効果が薄れる。`10〜12` に上げると誤検出でキューが溢れるので非推奨
- UI は **duplicate filter**: 2 枚を左右に並べ、ズーム/位置を同期。
  左クリック「こちらが良い、他方を削除」、右クリック「alternates」、中クリック「取り消し」。
- 性能注記: 「1 枚あたりのペア探索は速いが、数十万件になると総 CPU 時間が効いてくる。
  特に検索距離を上げると顕著」。← **これは全件ペア列挙 (mIV では作らない機能) のコスト**。
- 用途: 収集した画像から同じ絵の低画質版を捨て、最高画質を残す。

### 2.2 digiKam — 「1 枚に似た画像」がちゃんと独立機能になっている

- **Haar ウェーブレット指紋** (Jacobs et al. Fast Multiresolution Image Querying) を
  全画像について DB に事前計算して保持。
- その 1 つの指紋で **3 つの機能**を回している:
  1. Find Duplicates (全件)
  2. **Find Similar Image (1 枚を投げて似た画像を出す)** ← ユーザー要望と同じ形
  3. **Find by Sketch (手描きスケッチで検索)**
- 類似度は % レンジで指定、表示件数も 1〜50 で指定。
- **示唆**: 指紋を持ってさえいれば「1 枚→類似一覧」「スケッチ検索」まで同じ土台で伸ばせる。
  Haar 系は色分布 + 粗い構図を持つので、線画・イラストで DCT pHash より素直に効くことが多い
  (イラスト向け画像検索サービスにも同じ論文系統の実装が使われていると言われる。未検証)。

### 2.3 XnView MP — 汎用ビューワの最小構成

- `Tools > Find Similar`。比較軸を **名前 / サイズ / 日付 / バイナリ / 視覚的内容**から選ぶ。
  視覚的内容にすると再圧縮版・リサイズ版も拾う。
- `View > Compare` で 2〜4 枚をパン/ズーム同期で並べる (判断用)。
- 用途: 「消していいか」を人間が目で決めるための道具。**検出より比較 UI に価値がある**という設計。

### 2.4 Eagle — 整理アプリらしい割り切り

- 「完全に同一のファイル」スキャンと「似ている画像」スキャンを**別機能に分けている**。
  前者は形式やサイズが違うと拾わないと明記。
- 似ている画像側は解像度 / 形式 / `_final` `_v2` のようなバージョン表記でグルーピングし、
  「一番良い 1 枚」を選びやすくする。定期スキャン / 取り込み時スキャンあり、一括削除あり。
- 用途: 素材収集で「同じ素材の別解像度・別形式」を畳む。

### 2.5 Komga — **漫画特有の使い方 (mIV に一番効くかもしれない)**

- ライブラリに **page hashing** を有効化すると、**本をまたいで重複しているページ**を検出する。
- 並べ替えが「重複数」「画像サイズ」「削除で浮く合計サイズ」。
  Matches ボタンでそのページを含む全書籍を確認 → 無視 / 手動削除 / 自動削除。
- 用途: 広告ページ・奥付・スキャン団体のクレジットページが何十冊にも入っているのを一括で掃除する。
- **mIV への示唆**: mIV は ZIP 内エントリまで検索キーを持っている (§4.2) ので、
  「この 1 冊と同じページを含む本」や「このページは他に 37 冊に入っている」は同じ土台で出せる。
  これは XnView / digiKam にはない、コミックビューワ側の差別化要素。

### 2.6 Immich — 埋め込み方式の実例と、その限界

- CLIP 埋め込みを pgvector に入れ、cosine 距離で重複候補を出す。閾値 0.001〜0.1。
- **重複の種類という概念が無く、全部「意味的類似」**。そのため
  「閾値を締めると再圧縮された本物の重複を取り逃す / 緩めると連写や加筆違いまで重複扱いになる」
  というトレードオフが公に指摘されている。
- **示唆**: 埋め込み *だけ* にすると B (近重複) の精度が落ちる。B は perceptual hash、
  C/D は埋め込み、と**役割を分ける**のが素直。

### 2.7 czkawka (Rust)

- perceptual hash + マルチスレッド。ハッシュアルゴリズムとハッシュサイズを設定で選べる。
- Rust の `image_hasher` クレート (`img_hash` のフォーク) は同じ作者の系譜。実装参照先として有力。

## 3. アルゴリズム

### 3.1 古典的 perceptual hash

| 方式 | 中身 | 特徴 |
| --- | --- | --- |
| aHash (Mean) | 8x8 平均輝度で 2 値化 | 最速・最弱 |
| dHash (Gradient) | 隣接画素の大小関係 | 速度と精度のバランスが良い |
| pHash (DCT) | 32x32 グレースケール → 2D DCT → 低周波 8x8 を中央値で 2 値化 → 64bit | 事実上の標準。hydrus もこれ |
| wHash | Haar ウェーブレット係数を 2 値化 | |
| blockhash | ブロック平均の中央値比較 | 実装が単純、仕様公開 |
| **PDQ** (Meta, 2019) | pHash 系を拡張した **256bit** | 古典系では**頑健性が最も高い**という評価。計算は dHash より重い |

Rust では **`image_hasher`** (Mean / Gradient / DCT / Blockhash、ハッシュサイズ可変) が
`image` クレートのバッファをそのまま食えるので接続しやすい。

### 3.2 Haar ウェーブレット指紋 (digiKam 系)

64bit に潰さず、**ウェーブレット係数の上位 N 個 (符号付き) + 平均色**を持つ方式。
- 部分一致・スケッチ検索に強い。イラスト/線画で pHash より素直に効くことが多い。
- ただし比較が「係数集合の重なり」なのでハミング距離ではなく、
  **係数 → 画像 ID の転置索引**が要る (単純な線形走査にはならない)。
- 100 万件でも索引自体は現実的だが、**pHash より実装量が多い**。

### 3.3 埋め込み (C/D 用)

- 汎用: CLIP / DINOv2 (ONNX 化済みモデルが多数ある)。
- **イラスト特化: WD14 タガー系が 1024 次元の埋め込みを出せる**。
  Danbooru 系データで学習されているので、キャラ・画風・構図の「似ている」が
  汎用 CLIP より人間の感覚に近いと期待できる。実際に danbooru 埋め込みでの類似画像検索デモが存在する。
- **mIV は既に `ort` (ONNX Runtime) + DirectML を積んでいる**ので、
  ランタイム側の追加コストはモデルファイル分だけ。ここは他の汎用ビューワに対する明確な優位。
- **2 値化 (binary quantization)**: float32 を符号で 1bit にすると 32 分の 1 になり、
  ハミング距離で検索できる。再ランク付きで検索性能を ~96% 保てるという報告がある。
  1024 次元 → 128 バイト/枚 → **100 万枚で 122 MB**、線形走査 7.0 ms (実測、§3.5)。
  つまり **埋め込みを入れても索引は要らないまま**。

### 3.4 苦手な入力 — mIV の中身に直撃する

- **クロップ・回転・反転に不変ではない**。切り抜き版や左右反転は pHash では拾えない
  (左右反転版も欲しいなら「反転画像のハッシュ」も併せて持つのが定石)。
- **低分散画像で退化する**。真っ白背景の線画・文字だけのページは DCT 低周波がほぼ同じになり、
  **無関係なページ同士が距離 0〜2 で当たる**。pHash の誤検出は
  「大域的な色分布と粗い空間配置が似ているだけで意味的に無関係」なときに起きる、という指摘どおり。
  → 漫画ページに素で適用すると使い物にならない可能性が高い。対策候補:
  - ハッシュサイズを上げる (16x16 → 256bit)
  - 係数の分散/エントロピーが閾値未満のページは「特徴なし」として類似候補から除外する
  - アスペクト比・ページ寸法・平均色などの安価な補助条件で足切りする
  - Komga 的な「ページ重複」用途では、むしろ**低分散ページの一致こそが正解** (広告・奥付) なので、
    用途によって扱いを逆にする必要がある

### 3.5 実測 (本機、単スレッド、`rustc -O -C target-cpu=native`)

100 万件のハッシュ配列を線形走査して最小ハミング距離を求める時間:

| ハッシュ幅 | 想定 | 100 万件 | 500 万件 | 100 万件のメモリ |
| --- | --- | --- | --- | --- |
| 64bit | pHash / dHash | **0.33 ms** | 2.9 ms | 7 MB |
| 256bit | PDQ / 16x16 hash | **1.6 ms** | 10.6 ms | 30 MB |
| 1024bit | 2 値化埋め込み (1024 次元) | **7.0 ms** | 35.8 ms | 122 MB |

(計測コード: `count_ones()` による XOR+popcount のベタなループ。SIMD 手書きなし、並列化なし。)

**結論: 100 万件は索引不要。** VP-tree / BK-tree / HNSW を入れる理由が無い
(hydrus が VP-tree を使うのは「全件ペア列挙」をやるため。mIV はそれを作らない前提)。
線形走査なら追加は `Vec::push` だけ、削除はエントリの無効化だけで済み、
**世代整合・再構築・キャンセルの複雑さが丸ごと消える**。

### 3.6 本当のボトルネック = ハッシュ生成

- ハッシュ計算そのもの (32x32 縮小 + DCT) はデコード時間に埋もれる程度で無視できる。
- したがってコストは実質「100 万枚をデコードする時間」。
  既にサムネイルが `catalog.db` にある画像なら、その WebP を decode するだけで済むので桁違いに安い。
- ここは Ctrl+G 用の FTS インデクサと同じ性質の**バックグラウンド長時間ジョブ**になる
  (進捗表示・キャンセル・中断再開・世代管理)。設計は [search-architecture.md](search-architecture.md) §4 の
  インデクサパイプラインをそのまま踏襲するのが自然。

## 4. mIV に載せるとしたら (未確定・要判断)

### 4.1 保存先 — `catalog.db` は使えない

カラー検索の設計で一度踏んだ罠 ([color-search-plan.md](color-search-plan.md) の変遷を参照):
`thumbnails.thumb_data` が `NOT NULL` で、キャッシュ設定 Off / Auto では行自体が作られない。
**サムネイルキャッシュの有無に依存する保存先は破綻する**。

候補:
- **(a) `fts_meta.db` の `files` テーブルに列を足す** — path PK / mtime / size / generation / status を
  既に持っており、**お気に入り配下の全アイテムを走査する仕組みも既にある**。相乗りが最も安い。
  ただし FTS の `INDEX_VERSION` と寿命が結合する (再構築時に一緒に消える) 点は要判断。
- **(b) 独立した `similar.db`** — 寿命を分離できる。テーブルは実質
  `(item_key PK, mtime, file_size, hash BLOB, flags)` の 1 枚。
  起動時に全行を `Vec` に読み込む (100 万行 × 数十バイト = 数十 MB、読み込みは 1 回)。

現時点では **(b) を推す**。FTS 索引の再構築で類似ハッシュまで消えるのは損が大きい。

### 4.2 スコープ

- 索引対象は **お気に入り (favorites)** = Ctrl+G と同じ範囲にすると、
  ユーザーの心的モデルが既存機能と揃う。
- パスキーは既存の `normalize_path` (小文字化 + `/` 区切り + ZIP は `<zip>\u{1F}<entry>`) を流用。
  → **ZIP 内ページも最初から対象にできる** = Komga 的なページ重複が同じ土台で出せる。

### 4.3 UI (要望「類似先のフォルダにジャンプ」への当てはめ)

- 起動点: フルスクリーンのメタデータパネル or 右クリックメニューの「この画像に似た画像」。
- 結果の見せ方: **v2.1.0 のレーティング横断一覧ビュー / 読書履歴ビューがそのまま雛形**。
  場所をまたいだフラット一覧 + そこから「この場所を開く」で既存のジャンプ経路に乗る。
  → **新しいビュー基盤を作らずに済む**のがこの案の一番の利点。
- 距離指定: hydrus 流に生のハミング距離を見せるか、「厳密 / 普通 / ゆるい」の 3 段にするか要判断。
  要望が「見ている画像の類似を出す」なので、**既定 1 つ + 「もっと広く探す」1 ボタン**で足りるかもしれない。
- XnView の `Compare` 相当 (類似ペアをパン/ズーム同期で並べる) は mIV に既に比較表示があるので繋げられる。

### 4.4 段階案 (規模感の目安。実装計画ではない)

- **Phase 1**: 64bit dHash + pHash の 2 本を持ち、1 枚に対する類似検索のみ。
  索引なし・全件ペア列挙なし。バックグラウンド生成 + `similar.db`。
- **Phase 2**: 線画対策 (256bit 化 / 低分散ページ除外 / アスペクト補助条件)、
  左右反転ハッシュ、ZIP ページ重複ビュー (Komga 相当)。
- **Phase 3 (差別化)**: WD14 系タガー埋め込み → 2 値化 128 バイト → 「同じキャラ / 同じ絵柄」検索。
  ort + DirectML が既にあるので追加は主にモデルとワーカー。ここは XnView / digiKam / Eagle に無い。

## 5. まだ決まっていないこと

1. **狙う類似は B / C / D のどれか** (§1)。ここで全部が決まる。
2. **対象コレクションの実態** — AI 生成画像中心か、スキャン漫画中心か、写真中心かで
   最適なハッシュも、線画対策の要否も変わる。
3. **動画・音声をどうするか** — 代表フレームのハッシュで妥協するか、対象外にするか。
4. **索引生成をいつ回すか** — サムネイル生成の副産物にするか、FTS と同じ明示的な索引ジョブにするか。
5. **`similar.db` を持つコスト** — 100 万件で数十 MB。永続ストア追加の是非。
