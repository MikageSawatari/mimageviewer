# v0.9.2 Task: native HUD overlay flicker after right-panel click

## Status

- Target: v0.9.2
- Priority: P3 unless the flicker becomes more visible or starts affecting input.
- Scope: investigation completed; implementation intentionally deferred.
- Code changes at time of this note: none.

## User-visible symptom

In fullscreen video playback, saving the current video frame with `Ctrl+S`
can cause a very brief flicker. The user described it as if another window or a
different-sized layer flashes for one frame, sometimes with a different image on
the left side.

The flicker is not always reproducible. It became reproducible with the
condition below.

## Reproduction

1. Open a video in fullscreen native presenter mode.
2. Move the cursor to show the right metadata panel.
3. Click inside the right panel.
4. Move the cursor away so the right panel disappears.
5. Press `Ctrl+S` to save the current video frame.

Expected:

- The save-start / saved toast appears without any video/background flicker.

Actual:

- A one-frame flicker can occur when `Ctrl+S` is pressed.

Important negative check:

- With `MIV_HUD_OVERLAY=0`, the user reported that the flicker probably stops.
  This strongly points at the independent HUD overlay HWND path rather than the
  frame capture worker or video decode path.

## Current conclusion

The likely cause is a visible transition in the independent HUD overlay HWND
path:

```text
right panel visible
-> HUD overlay HWND region includes the right panel rect
-> click inside the panel
-> HUD HWND receives mouse down and calls claim_foreground(focus_hwnd)
-> cursor moves away
-> right panel disappears
-> overlay becomes hidden, egui overlay DComp visual is detached, HUD region is
   reduced/emptied
-> Ctrl+S
-> save-start toast is queued
-> overlay becomes visible again
-> egui overlay surface is rendered, DComp visual is attached, HUD region is
   updated to the toast rect
-> DWM/DComp can show a transient stale/incorrect composition frame
```

The frame extraction itself is not the likely cause. `Ctrl+S` calls
`save_video_frame_to_file`, which spawns `video-frame-save` and captures through
a separate FFmpeg decode path. That path does not resize or mutate the native
presenter HWND/DComp tree.

## Details that make this condition-specific

- The right panel is rendered by the HUD overlay HWND path, so its visible rect
  becomes part of the HUD window region.
- Clicking the panel makes the HUD HWND receive mouse input and run the
  presenter foreground handoff path.
- Moving the cursor away makes the right panel disappear. If no other overlay
  element is visible, `render_once` reaches the hidden-overlay path and detaches
  the egui DComp visual.
- `Ctrl+S` then creates a toast, which makes the overlay visible again.
- The current flow renders/presents the egui overlay and attaches the DComp
  visual before `tick_overlay_video_state` publishes the final HUD regions for
  that outcome. That hidden->visible transition is the main suspect.

## Fix direction to try first

Prefer a narrow fix in the HUD overlay HWND path only.

Candidate:

- During hidden -> visible transitions for HUD HWND mode, publish/apply the new
  HUD region before attaching the egui overlay visual, or otherwise avoid a
  compositor frame where the visual is attached while the HWND region/z-order is
  still in the previous hidden or stale state.
- Keep the `MIV_HUD_OVERLAY=0` presenter fallback behavior unchanged.
- Preserve the current click-through model: when no HUD UI is visible, the HUD
  HWND region must be empty so the presenter/VST windows below receive input.

Avoid as the first fix:

- Keeping the egui overlay visual permanently attached. Older notes mention a
  production setup where an empty/transparent overlay surface could appear as an
  opaque black visual, so permanent attach risks reintroducing that class of
  bug.
- Broad changes to video frame capture, decoder state, or the fullscreen keymap.
  The reproduction and `MIV_HUD_OVERLAY=0` result do not point there.

## Risk assessment

Risk is low-to-medium if the patch is limited to the HUD HWND hidden->visible
transition. It is not a pure UI-only area: this code involves Win32 HWND
regions, DComp visual attach/detach, z-order, VST GUI interop, mouse
click-through, and focus handoff.

Main regressions to watch for:

- HUD appears behind VST GUI.
- Invisible HUD region steals clicks from VST/presenter.
- Right panel or left jump panel stops receiving clicks.
- Bottom seek HUD drag/click becomes unreliable.
- Toast is clipped, missing, or appears at the wrong place.
- Empty overlay appears as black/opaque on affected GPU/driver setups.
- Keyboard focus/IME behavior regresses after clicking HUD controls.

## Validation checklist

Manual checks:

- Reproduce the exact right-panel sequence above and verify no flicker.
- Run the same sequence with `MIV_HUD_OVERLAY=0` and confirm fallback behavior is
  unchanged.
- Show right metadata panel, click inside it, scroll/click links if available.
- Show left jump panel and click entries/bookmark/pin actions.
- Use bottom HUD seek, volume, mute, loop, speed, normalize, screenshot/copy.
- Move the cursor away and confirm video/presenter clicks are not stolen by an
  invisible HUD region.
- Open a VST3 GUI in fullscreen video mode and verify HUD can still appear above
  it when appropriate.
- Confirm toasts for save-start and save-complete are visible and not clipped.

Useful diagnostics:

- `MIV_HUD_DEBUG=1`: region changes should show the right panel rect, then an
  empty/no-panel state, then a toast rect. Any unexpected full-screen region
  around `Ctrl+S` is suspicious.
- Perf/log events to compare around the flicker:
  - `egui_overlay_visual attached=false`
  - `egui_overlay_visual attached=true`
  - `egui_overlay_present`
  - `[HUD-DEBUG] regions changed ...`
  - native foreground handoff logs from the HUD click path
