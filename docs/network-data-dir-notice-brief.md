# 実装ブリーフ: データの保存先がネットワーク上にあることを知らせる

対象: v3.1.0。利用者報告 (5ch 専用スレ #234 / #235、2026-08-16)。

## 1. 何が起きているか

ポータブル版を **NAS の画像フォルダに置いて**使っている利用者から、次の 3 つが報告された。

1. 起動が重い
2. 書庫の画像表示が重い
3. **一度終了して再起動すると、遅いか、起動しなくなる。プロセスを強制終了しても凍ったまま**

同じ使い方をしていた別のビューア (データベースを持たない実装) では差が出なかった、とのこと。
別の利用者からも「重い」との反応があった。

## 2. 分かっている構造 (調査済み)

- mIV は **7 つのデータベースで `PRAGMA journal_mode=WAL`** を使う
  (`catalog` / `settings_db` / `search_index_db` / `fts_meta` / `archive_cache` /
  `edit_preview_cache` / `auto_aspect_cache`)。
- **WAL はネットワーク共有では成立しない。** WAL は `-shm` 共有メモリファイルを介して
  プロセス間の状態を持つ設計で、SMB 越しではこれが機能しない。SQLite 自身が
  「WAL を使う全プロセスは同じホスト上にあること」を要件として明記している。
- ポータブル版の既定 data_dir は **`<exe_dir>/data`** (`src/data_dir.rs` の `flavor_default`)。
  exe を NAS に置くと、サムネイルカタログ・全文索引・レーティング・タグ・変換アーカイブ・
  編集キャッシュが**すべて SMB 越し**になる。
- 報告 3 (強制終了もできない) は、SMB の中断不可能な I/O 待ちに特有の症状で、
  アプリ側のデッドロックでは通常こうならない。

**ただし「これが原因だ」と断定はできない。** 画像読み込み自体が SMB 越しである影響も
同時に効いているため。切り分けは §5 の手順を利用者に実施してもらう。

## 3. やること — 検出して 1 回知らせる

**この版で行うのは検出と案内だけ。** journal_mode の変更は行わない
(どのモードが速いかは NAS 実機で実測しないと決められないため。別途扱う)。

### 3.1 検出

解決済みの data_dir がネットワーク上かを判定する。**build flavor で分岐しない**
(インストール版でも `--data-dir` にネットワークパスを渡せる)。

- **UNC パス** (`\\server\share`、`\\?\UNC\server\share`) — 純粋な文字列判定。
  cfg なしで書けるので**ここを純関数に切り出してテストする**。
- **割り当てドライブ** — `GetDriveTypeW` が `DRIVE_REMOTE` (= 4) を返す場合。
  `src/ui_dialogs/context_menu.rs:408` に既存の呼び出し方があるので倣う。
  Windows 専用なので `#[cfg(windows)]`。**非 Windows でもビルドが通ること**
  (CI の ubuntu `cargo check` が番人)。

判定は **settings 読み込みの後**に行う。抑止フラグを読む必要があるうえ、その時点なら
共有が到達可能であることが確認済みで、`GetDriveTypeW` が切断ドライブで待たされる心配もない。

### 3.2 知らせ方

起動時に 1 回だけダイアログを出す。`src/ui_dialogs/whats_new.rs` が同種の
「起動時に一度出す」ダイアログの雛形になる。

内容に入れるもの:

- 検出した事実 — データの保存先がネットワーク上にあること。**保存先のパスも示す**
- 起こり得ること — 起動や表示が遅くなる、終了後の再起動で応答しなくなることがある
- 対処 — データだけをローカルに置く方法 (`--data-dir` の実例をそのまま示す)
- 詳しい確認手順への誘導 (§5 のマニュアル節)

**書き方の注意:**

- **「これが原因です」と断定しない。** 「原因になることがあります」に留める。実際に
  画像読み込み側が主因の可能性が残っている。
- 利用者はそこへ置くことを選んでいる。**責めたり、使い方を否定したりしない。**
- 実装語 (WAL / SQLite / SMB / shm) を出さない。「データベース」も避け、
  「mIV が使うデータ (サムネイルや検索用の索引など)」のように書く。

### 3.3 抑止

**同じ保存先に対しては 2 回目以降出さない。** 毎回出すと、その場所で使うと決めた利用者に
とってただの邪魔になる。

- 抑止した保存先のパスを設定に記録する (例: `network_data_dir_notice_dismissed_for`)。
- **保存先が変わったら再び出す** (別の場所へ移したときは、その場所について改めて知らせる)。
- ダイアログには「閉じる」と、抑止するための明示的な操作を置く。

## 4. テスト

- **純関数のテスト**: UNC の各形、ドライブレター、相対パス、空パス。
  cfg(windows) を必要としない形にすること。
- **抑止の遷移テスト**: 同じパスなら出ない / 別のパスなら出る / 一度も抑止していなければ出る。
- 設定の既定値と保存・復元の往復。
- ダイアログを追加するなら `cargo test --test ui_snapshot` (`docs/ui-snapshot-policy.md`)。
- `cargo test -p mimageviewer --lib`、`cargo fmt --all`、`python scripts/check_ui_glyphs.py`。

## 5. マニュアル — 切り分け手順を書く

`htdocs/mimageviewer/manual/troubleshooting.html` に
**「NAS・ネットワークドライブに置いて使う」** の節を新設し、ダイアログからここへ誘導する。

利用者は**ログを送れない**。ログを読ませずに自力で切り分けられる手順を書くこと。

原因の候補は 2 つだけで、片方だけを切り替えられる:

```
A (現状)   本体 = NAS、データ = NAS、画像 = NAS
B (比較用) 本体 = NAS、データ = ローカル、画像 = NAS   ← 変えるのはここだけ
```

画像はどちらも NAS のままなので、差が出ればデータ側が原因と分かる。

**必ず書くこと:**

- B の起動方法 (`--data-dir` を付けたショートカットの作り方を、実例で)
- **B は初回だけサムネイルを作り直すので必ず遅くなる。同じフォルダを 2 回開いて
  2 回目を比べる。** これを書かないと誤った結論になる
- 比べる 3 点: 起動 / 同じ書庫を開いたとき (2 回目) / 終了と起動を 3 回
- 読み方の表:

| 結果 | 意味 |
| --- | --- |
| B が明らかに速い・固まらなくなる | データの保存先が原因。ローカルに置けば解決 |
| B も同じ | 画像の読み込み自体が重い。回線側の問題 |
| 起動だけ速くなる | 両方が効いている |

- とくに**「固まって強制終了もできない」が B で止まるかどうか**が決定的である旨。

文体は既存ページに合わせ、実装語・バージョン番号は書かない
(CLAUDE.md「マニュアル・製品ページの記述方針」)。

## 7. 対象外

- `journal_mode` の変更。実測してから別途決める。
- data_dir の自動移動・自動フォールバック。利用者がその場所を選んでいるので、勝手に変えない。
- ネットワーク上での動作そのものの高速化。
