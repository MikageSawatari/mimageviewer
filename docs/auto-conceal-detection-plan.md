## 0. 一行で

マスクを描く 3 つのツール (消しゴム・隠蔽加工・補正レイヤーの手動マスク) に、共通の「自動検出」を足す。
画像から領域を検出し、**そのツールで編集中のマスク** (図形またはビットマップ) へ追加する。
**顔検出 (YuNet、MIT) は同梱**し、それ以外の検出器 (例: 成人向けイラストの局部の検出) は
**利用者が自分で入手した ONNX を決まったフォルダに置く (BYO)**。結果は通常のマスクと同じなので、
そのあと既存のツールで直せる。

## 1. 目的と範囲

### 1.1 やること

- **写真の顔を隠す・ぼかす・消す・補正する**。同梱の顔検出で、ダウンロードなしに使える。
- **利用者が置いた検出器で任意の分類を選ぶ**。Ultralytics 形式で書き出された ONNX (箱の検出・輪郭の
  セグメンテーション) を読む。成人向けイラストの修正を補助する用途を含むが、mIV はそのモデルを配布しない。
- **3 つのツールで同じ操作・同じ結果**にする。マスクの道具は 3 ツールでほぼ共通の仕様なので、自動検出も
  1 つだけ持ち、ツールごとの違いは「どのマスクへ書くか」だけにする (2026-11-26 利用者決定)。
- 検出結果は **提案**。利用者が確かめ、足りない所を足し、要らない所を消してから保存する。

### 1.2 やらないこと

- **モザイク除去** (既存の方針どおり実装しない)。消しゴムに局部の検出結果を渡しても、消しゴム (MI-GAN) は
  周りから埋めるだけで、隠れた内容を作り出すことはない。そのため消しゴムを外す理由にはならない
  (2026-11-26 利用者判断。隠蔽加工だけに限る案を取り下げた)。
- **自動ダウンロード**。モデルの取得は利用者が配布元から行う。mIV のアプリは取得もしないし、配布元のページも開かない (§8)。
- **「これで投稿できる」等の判定**。基準への適合は利用者が判断する ([public-wording-policies.md](public-wording-policies.md))。
- **開いたときに自動でかけること**。毎回、利用者の操作から始める。
- **領域ごとに隠し方を変えること**。隠し方 (モザイク / ぼかし等) は今までどおり隠蔽加工の全体設定で 1 つ。
- **複数の画像への一括適用** は §11 の段 3。精度は使ってみないと分からないので、段 1・2 を使ってから決める
  (2026-11-26 利用者判断)。

### 1.3 永続データの判断 (リリース済み / 未リリース)

- マスクは既存の保存先 (消しゴム = `mask.db`、隠蔽加工 = `conceal.db`、補正レイヤー = `local_adjust` の保存先、
  サイドカー `mimageviewer.dat`。いずれもリリース済み) に、**今の形式のまま**入る。自動で作ったマスクも
  手で描いたマスクと同じ表現なので、**スキーマ変更・移行はない**。
- 新しい設定 (前回選んだ検出器・余白・形など) は `settings_kv` の新しいキーで、未リリース。移行は要らない。
- 検出器フォルダ (`<data_dir>\detectors\`) も新規。

- ある国内の AI 画像投稿サイトが 2026-11-26 に、投稿時の自動モザイクを公開した。ソース (MIT) を読むと、
  上の 01miku の nano を ブラウザの ONNX Runtime で動かしている。後処理 (重なりの除去 → 32 係数と元マスクから
  輪郭マスク → 入力 640 で約 8px 太らせる) は §5.3 の参考になる。閾値は局部の分類で 0.15〜0.22。

## 3. 全体像

```
消しゴム / 隠蔽加工 / 補正レイヤー (手動マスクを編集できる状態)
  └ パネルの [自動検出…] → 設定ダイアログ (検出器・分類・形・余白)   ← 3 ツールで同じダイアログ
        └ [検出] → モーダルの進行表示 (キャンセル可)
              │  入力: そのツールのバケツ (画像の色) と同じ画素の Arc (§5.1)
              ▼
        検出 worker (1 回ごとに 1 本、ツールを知らない)
          ├ 顔: YuNet (同梱)
          └ BYO: <data_dir>\detectors\*.onnx
              │  AiRuntime の「外部モデル」セッション (§6.2)
              ▼
          検出結果 = 画像座標の箱 (矩形 / 楕円の幾何) と輪郭パッチ
              ▼
        UI スレッド: 開始時の条件と照合 → そのツールの「1 回の編集」として追加 (§7.4)
              ▼
        そのツールの既存の経路 (Undo・キャッシュの失効・補完・再合成・保存)
```

- 検出の結果は **各ツールの既存のマスク表現**に入るだけ。保存・Undo・マスクスロット・サイドカー・書き出しは
  新しい処理なしで動く。
- 新しく足すのは、検出 (前処理・推論・出力の読み取り)、検出器の一覧、ダイアログ、待ちの状態、
  ツールごとの「結果を足す」3 つの小さな関数。

## 4. 操作の流れと UI

### 4.1 流れ

1. 消しゴム・隠蔽加工・補正レイヤーのどれかで、マスクを編集できる状態にする (既存)。
2. パネルのツールパレットの近くに **[自動検出…]** ボタンがある。押すと設定ダイアログを開く。
3. ダイアログで検出器と分類を選び、[検出] を押す。
4. **検出中はモーダル** (進行表示と [キャンセル] だけ)。ページ移動・ツール操作・モード終了は受け付けない (§7.1)。
5. 終わると、見つかった領域をマスクに足し、「N か所を追加しました」(0 件なら「見つかりませんでした」) を出す。
6. 足された図形は選択ツール (S) で動かす・消すことができる。輪郭のマスクは筆・消去で直す。
7. 1 回の検出は **Undo 1 回**で取り消せる (各ツールの既存の Undo)。

### 4.2 設定ダイアログ (3 ツール共通)

`default_pos()` の通常ダイアログ (モーダル)。1093×614 でも [検出] と [閉じる] が見えること (見出しと操作行は ScrollArea の外)。

| 項目 | 内容 | 既定 |
|---|---|---|
| 検出器 | 「顔 (内蔵)」+ フォルダにある検出器を 1 行ずつ。チェックで選ぶ (複数可) | 顔のみ |
| 分類 | 選んだ検出器の分類名をチェックで選ぶ (顔は分類 1 つなので出さない) | 検出器ごとに前回値、初回は全部 |
| 形 (箱の検出器) | 楕円 / 矩形 | 顔 = 楕円、BYO = 矩形 |
| 形 (輪郭の検出器) | 輪郭に沿う / 楕円 / 矩形 | 輪郭に沿う |
| 余白 | 箱は大きさの % で広げる。輪郭は元の画像の px で太らせる | 箱 15%、輪郭 = 長辺の 0.6% (最小 2px) |
| 閾値 (詳細を開いたときだけ) | 確からしさの下限 | 検出器の既定 (§5.4) |
| 検出器フォルダ | [フォルダを開く] [一覧を読み直す] | — |

- 設定 (選んだ検出器・分類・形・余白) は 3 ツールで共有する 1 組にする。ツールごとに別の設定は持たない
  (状態を増やさない。ツールを変えても同じ検出がかかる)。
- 各検出器の行には、ファイル名・分類の数・種類 (箱 / 輪郭)・ONNX に書かれたライセンス文字列 (あれば) を出す。
- 文言は処理内容だけを書く (例:「顔を検出して楕円のマスクを追加します」)。「投稿用」などの用途判定の語は使わない。
- 読めなかったファイルは灰色の行で理由を出す (例:「出力の形式を読めません」)。黙って隠さない。

### 4.3 置き場所とボタンを押せる条件

- 3 ツールのパネルに同じボタンを置く。押せる条件は **そのツールのバケツが使える条件と同じ**にする
  (マスクの書き先がある状態)。補正レイヤーの書き先は **既存の `effective_local_mask_edit_target` で解決する**:
  ベースのマスクが `LocalMask::Raster` か `RasterVector` なら `Base`、それ以外 (グラデーション・被写体・領域分割など)
  は手動の追加 / 削除 (`manual_override.add` / `subtract`) を編集中のときだけ。追加 / 削除がまだ作られていない
  (`None`) ときも押せる (バケツと同じ。Sol レビュー R4 P2)。
- キー割り当ては v1 では付けない (ダイアログを開くだけの操作のため)。付けるなら `KeyAction` 経由 (keymap 規則)。

## 5. 検出

### 5.1 入力

- 入力は **そのツールのバケツ (「画像の色」) が見ている画素と同じもの**にする。利用者がそのツールで見ている画像と
  一致し、マスクの解像度とも一致するため (2026-11-26 のコード):

  | ツール | 入力 | マスクの大きさ |
  |---|---|---|
  | 消しゴム | `erase_base_cache[fs_idx]` の画素 (補完前の画像) | `erase_mask_size` |
  | 隠蔽加工 | `current_conceal_source_pixels(target_idx)` | `conceal_mask_size` |
  | 補正レイヤー | `current_local_adjust_source_pixels(fs_idx)` | 入力画素の大きさ (書き先が未作成でも決まる。既にある書き先はこの大きさと一致することを確かめる) |

- 座標の変換は検出の前処理の逆変換だけで済む。着手時にマスクとソースの大きさが一致することを確かめ、
  違えば検出を始めない (エラー表示)。
- 透過画像は RGB に変換して検出する (マスクは座標だけなので透過は保たれる)。

### 5.2 出力の形式 (`DetectorFormat`)

| 形式 | 出力 | 読み方 |
|---|---|---|
| `YuNet` | stride 8/16/32 ごとの cls・obj・bbox・kps | OpenCV の `FaceDetectorYN` と同じ式。5 点は v1 では使わない |
| `UltralyticsDetect` | `[1, 4+C, N]` (xywh + 分類ごとの確からしさ) | 転置 → 閾値 → 分類ごとの重なり除去 (IoU 0.5) |
| `UltralyticsSegment` | `[1, 4+C+32, N]` と元マスク `[1, 32, H/4, W/4]` | 上と同じ + 32 係数 × 元マスク → 0 以上を内側 → 箱で切り抜く |

- **形式は上の 3 つだけにする** (段 0 の結果、§17)。YOLO26 も既定の書き出しは従来形式 (`end2end = False`、出力は
  v8 / 11 と同じ並び) で、調べた BYO の候補 5 つもすべて従来形式だった。重なり除去済みの書き出し
  (`end2end = True` や `nms = True`) は v1 では **読めない検出器**として表示する (使う例が無く、形式を増やさない)。
- 形式の決め方: メタデータの `task` (`detect` / `segment`) があればそれ。無ければ出力から決める (出力 1 つで
  `[1, 4+C, N]` → 箱、出力 2 つで 2 つ目が `[1, 32, h, w]` → 輪郭で `C = 1 つ目の 2 番目の次元 - 4 - 32`)。
  `names` があれば、その数が `C` と一致すること。`end2end` が真なら読めない。**どれにも当てはまらなければ読めない
  検出器として表示する** (推測で読まない)。deepghs はメタデータに `task` が無く `names` と `stride` だけなので、
  出力からの判定になる (段 0 で確認)。

### 5.3 前処理と後処理

- **Ultralytics 系 (段 0 で ultralytics 本体と一致を確認、§17)**: 入力の大きさ `S` はメタデータの `imgsz` →
  同じ場所の `model_artifacts.json` の `args.imgsz` → 入力の形が固定ならその大きさ → 640 の順で決める。
  ultralytics の `LetterBox` と同じ計算にする: `r = min(S/h, S/w)`、縮めた大きさ `(round(w·r), round(h·r))`、
  縮小は双線形、余白 `dw = (S - 新しい幅) / 2` を左 `round(dw - 0.1)`・右 `round(dw + 0.1)` (上下も同じ) に分け、
  灰色 (114) で埋める。RGB、0..1、NCHW。出力は転置して `(cx, cy, w, h)` + 分類ごとの確からしさ (既に 0..1)。
  確からしさ ≥ 閾値で残し、**分類ごとに** 重なりを除く (IoU 0.7、ultralytics の既定)、多くて 300 個。
  座標は余白を引いて `r` で割り、画像の範囲に切り詰める。
- **輪郭**: 32 係数 × 元マスクで元マスクの解像度の値 (ロジット) を作る。**元の画像の箱の中の各画素について、
  画素の中心を letterbox の座標 → 元マスクの座標へ写し、ロジットを双線形で読んで 0 より大きければ内側**とする
  (元マスクの解像度で 0/1 にしてから拡大すると、元の画像では約 30px の階段になるため)。そのあと §4.2 の余白
  (**元の画像の px**) ぶん太らせる。結果は **検出ごとの小さなパッチ** (画像座標の矩形 + その範囲のビット列) にする
  (§7.4 の UI スレッドの負荷のため)。この方法で ultralytics の `retina_masks` と IoU 中央値 0.999 (最小 0.97) だった。
- **YuNet (段 0 で OpenCV と一致を確認、§17)**: 入力は **BGR、0..255 のまま、縦横を 32 の倍数へ右下に 0 で埋める**。
  出力は stride 8 / 16 / 32 ごとに、`score = sqrt(clamp(cls) × clamp(obj))`、
  `cx = (列 + bbox0) × stride`、`cy = (行 + bbox1) × stride`、`w = exp(bbox2) × stride`、`h = exp(bbox3) × stride`
  (行と列は埋めた後の大きさで数える)。重なりの除去は IoU 0.3。
  **段は「長辺 640・1280・2560 のうち元より小さいもの」+「元の大きさ」**で検出し、元の座標へ戻して重なりを除く
  (IoU 0.3)。顔の大きさが 10〜300px に入る段が必ずあるようにするため。元の大きさの段は集合写真の小さな顔、
  640 の段は近くで撮った大きな顔を拾う (§17 の集計)。
- 検出の出力はツールを知らない: 箱は `DetectedBox { kind: Rect | Ellipse, center, half_w, half_h }`
  (画像座標、回転 0)、輪郭は `MaskPatch { x, y, w, h, bits }`。ツールの型 (`mask_db::Shape` /
  `local_adjust_core::MaskShape`) への変換は §7.4 の各ツールの関数で行う。

### 5.4 閾値

- 既定は検出器ごとに決める。顔 = 0.6 (段 0 の写真で、0.5 は手や物・文字の面への誤検出が増え、0.7 は横顔の
  取りこぼしが目立った)。BYO = 0.25 (ultralytics の既定)。ONNX と同じ場所に `<名前>.json` (§6.1) があれば
  その分類ごとの値を使う。deepghs 形式の `threshold.json` (`{"threshold": 0.278}` のように **全分類で 1 つの値**) も読む。
- 隠す用途では **見落としより誤検出のほうが直しやすい**ので、既定は低めに置く。

## 6. 検出器の管理

### 6.1 BYO フォルダ

- 置き場は **`<data_dir>\detectors\`** に固定する (ポータブル版・`--data-dir` でも data_dir に従う)。
  フォルダを変える設定は v1 では作らない (状態を増やさない)。
- 1 つの検出器 = `<名前>.onnx` + 任意の `<名前>.json`。json は分類名・既定の閾値・既定の形を上書きするためのもの:

  ```json
  { "names": ["anus", "penis", "vagina"], "thresholds": {"anus": 0.15}, "shape": "rect" }
  ```

- 分類名は、json → ONNX のメタデータ `names` → deepghs 形式の `labels.json` (同名フォルダ内) の順で探す。
  どこにも無ければ「分類 0」「分類 1」… と出す (使えるが、利用者には分かりにくいことを表示する)。
- フォルダの読み込み (read_dir・ONNX のメタデータの読み取り) は **worker** で行う。ダイアログを開いたときと
  [一覧を読み直す] で走らせ、結果が来るまでは「読み込み中」と出す。UI スレッドで ONNX を開かない。
- ファイルを選んで取り込むボタン (コピーで登録) は v1 では作らない。[フォルダを開く] で足りるかを使ってから決める。

### 6.2 推論セッション (`AiRuntime` の外部モデル)

- 今の `AiRuntime` は `ModelKind` (固定の列挙) ごとにセッションを持ち、`load_model` は同じ種類なら読み直さない。
  BYO の検出器は数も中身も決まらないので、`ModelKind` には入れない。
- **`AiRuntime` に「外部モデル」の表を足す**: 鍵は `(パス, ファイルの大きさ, 更新時刻)`。持ち主は今と同じ `AiRuntime`
  1 つで、別のキャッシュを作らない。TensorRT には回さない (DirectML か CPU)。同時に保持するのは 2 つまで
  (古いものから閉じる)。
- **同梱の YuNet も同じ外部モデルの経路で読む** (同梱物のパスを渡す)。`ModelKind` を足さず、TensorRT の経路・
  前回実行の診断・`as_str` の表に触れない。経路を 1 つにするため。
- 既存の `with_session` は全推論を 1 つのロックで直列にしている。外部モデルの表は **別のロック**にして、
  先読みのアップスケールが走っていても検出 (利用者が待っている操作) がその後ろに並ばないようにする。
  GPU 自体は共有するので、遅くなることはある。DirectML は別セッションの並行実行を許している (R1 で確認)。
- **段 0 の結果、調べた 10 モデルはすべて DirectML で読めて動いた** (§17)。ランタイムが DirectML / TensorRT なら
  DirectML で、CPU なら CPU で読む。**黙って CPU に切り替えない** (読めなければエラーとして表示する)。

## 7. 非同期と状態

### 7.1 検出中はモーダル (状態の組み合わせを減らす)

検出の途中にページ移動・ツール操作・Undo・モード終了・別の検出が入ると、結果を足す先が変わる。これを全部
扱う仕組みは作らず、**検出中はモーダル**にする (CLAUDE.md「設計の簡素化」)。

- 設定ダイアログと進行表示は `common_modal_dialog_open` に「今表示されているか」を返す helper で登録する。
  これで止まるのは**キー入力と、共通のモーダル判定を見ている画面だけ**。隠蔽加工のキャンバス
  (`handle_conceal_paint` は `canvas_pointer_inputs` に常に有効を渡している) とパネル (無効化は
  `book_structural_op` のときだけ) は止まらない (Sol レビュー R1 P1)。消しゴムと補正レイヤーも同じ作りである前提で扱う。
- そこで **述語を 1 つ作る**: `mask_detect_active()` = 自動検出のダイアログが開いている || 検出の待ちがある。
  3 ツールそれぞれの入力の入口が、自分の既存の止める条件にこの述語を OR する:

  | 入口 | 隠蔽加工 | 消しゴム | 補正レイヤー |
  |---|---|---|---|
  | パネルの `ui.disable()` | `book_structural_op` と合わせて 1 つの `conceal_input_blocked()` に寄せる | 同じ形の `erase_input_blocked()` | 同じ形の `local_adjust_mask_input_blocked()`。**左右 2 つの Area の両方** |
  | キャンバスの `canvas_pointer_inputs` の有効フラグ | 同上 | 同上 | 同上 |
  | そのツールのキー処理 (ツール切替・Undo・スロット・プリセット・モード終了) | 同上 | 同上 | 同上 |
  | 目のプレビューの先読み (パネルより先に生の `primary_down` を読む) | `sync_conceal_preview_before_pipeline` | 無い (目はパネルの Response 経由、R4 で確認) | 無い (R4 で確認) |
  | キャンバス処理の中で、キャンバスの有効フラグより前にキーを消費する入口 | — | (実装時に確認) | `handle_local_adjust_canvas_input` の `LaToolBucket` など (`consume_action` は Modal を一律には拒まない。R4 P2) |

  各ツールのキャンバス処理は、述語が真なら **新しい操作を始める処理 (キーの消費を含む) の前で戻る**。
  キャンセル・ボタンを離したときの後始末は止めない。
  [自動検出…] ボタン自体もこの述語で無効になり、検出の二重受付はここで起きない。止まっている間も描画は続ける
  (進行表示とプレビューは出す)。プレビューは新しく押したことによる開始だけを止め、表示の継続と離したときの
  後始末は残す (Sol レビュー R2 P2)。Tab での保持は既に `KeyboardOwner::Modal` を除いている。
- ホイール (筆の半径・拡大)、右クリック・ジェスチャー、全画面のキー・閲覧用スロットは共通モーダル判定で止まり、
  多角形の右クリック確定はキャンバス側で止まる (隠蔽加工は R2、消しゴム・補正レイヤーは R4 で確認)。
  **実装担当は、上の表の「実装時に確認」の欄と、表に無い入口が無いことをコードで確かめてから実装する**。
  表に無い入口が見つかったら設計担当へ返す。
- 止めないのは、別の viewer の操作・閉じる・非同期の対象切替の完了などの lifecycle。これは §7.2 の破棄と照合で
  扱う (各ツールのモード終了 `reset_*` と対象切替の完了でも待ちを捨てる)。
- 検出は短い (顔は数十 ms、Ultralytics の nano は数百 ms の見込み。xl の 1280 や初回のセッション作成は数秒)。
  待つ時間がモーダルで困るほど長くならない見込みだが、段 0 で測る。
- それでも外から来る変化 (フォルダの監視による一覧の読み直し、裏で終わった消しゴムの補完や補正レイヤーの
  再計算、別ウィンドウ、リモート操作) は止まらないので、結果を足す前に **開始時の条件と照合する** (§7.2)。
  合わなければ捨てて「画像が変わったため中止しました」と出す。

### 7.2 待ちの状態

```rust
/// 開始時に確定し、あとから書き換えない (表示位置の付け直しの対象にしない)。
pub(crate) struct MaskDetectRequest {
    context: ViewerContextId,
    page_key: String,
    items_generation: u64,
    target: MaskDetectTarget,
    source: Arc<egui::ColorImage>,     // 検出に渡した画素 (§5.1 の表)
    mask_size: [usize; 2],
}
/// どのツールのどのマスクへ書くか。ツールごとの「同じ編集の続きか」の印を持つ。
pub(crate) enum MaskDetectTarget {
    Erase { session: u64 },            // 消しゴムのモードに入るたびに進める番号 (新規)
    Conceal { session: u64, source_kind: &'static str },  // 隠蔽加工のモードに入るたびに進める番号 (新規)
    LocalAdjust {
        owner: PageEditOwner,            // 開始時に capture_page_edit_owner で取る (付け直しの対象にしない)
        document: LocalAdjustmentLayers, // 開始時の文書 (local_page_edit_layers_for_target)
        layer_idx: usize,
        edit_target: LocalAdjustMaskEditTarget, // 開始時に effective_local_mask_edit_target で解決した書き先
    },
}
pub(crate) struct MaskDetectPending {
    request: MaskDetectRequest,
    cancel: Arc<AtomicBool>,
    rx: mpsc::Receiver<Result<MaskDetectOutput, String>>,
}
impl Drop for MaskDetectPending { fn drop(&mut self) { self.cancel.store(true, Release); } }
```

- 待ちは **viewer context の bundle に 1 つだけ** (既存の `local_adjust_segmentation_pending` と同じ扱い)。
  3 ツールで別々の待ちを持たない。根拠は **共通の受付が、待ちがある間は新しい検出を受け付けず (置き換えない)、
  開始時に捕捉した対象 1 つだけを所有する**こと (Sol レビュー R4 P2)。「同じ context で 2 つのツールを同時に
  編集しない」ことは根拠にしない: 今のコードでは、同じ入力のまとまりに Ctrl+G と Ctrl+M があると補正レイヤーと
  隠蔽加工のモードが両方立ち得る (`ui_fullscreen.rs` の隠蔽加工の開始条件に `!local_adjust_mode` が無い。
  この設計とは別の既存の問題として扱う)。受け取り時は捕捉した対象のツールのモードだけを見るので、
  両方のモードが立っていても別のツールのマスクへは書かない。
- 先例 `local_adjust_segmentation_pending` の出現箇所を全部たどり、同じ箇所に入れる: bundle の保存・復元、
  各 lifecycle での破棄 (フォルダ切替・context を閉じる・各ツールのモード終了)、`book_append_undo` の待ち判定、
  `prepared_edit`、全 context の poll、`update_phases` の再描画要求、idle・停止の判定 (一部だけ入れると、
  閉じた context の結果が別の context に入る)。
- **ただし `page_edit_owner.rs` の付け直し (`reproject_page_edit_owners`) には入れない**。先例の付け直しは
  `owner.items_generation` を今の値へ書き換えるので、入れると開始時の条件が失われる (Sol レビュー R1 P1)。
  一覧が読み直されたら (`items_generation` が変わったら) 結果は捨てる。待つのは短いので、追いかける価値が無い。
- **補正レイヤーで始めるときは、他の AI のマスク作成の待ち (`local_adjust_segmentation_pending`・
  `local_adjust_lut_pending`) が無いことを条件にする**。どちらかがある間は [検出] を押せない。補正レイヤーの
  文書を変える非同期の完了と重ねないため (先例の「マスク生成中です」と同じ扱い)。書き込み worker の完了は
  待たない (受け取り時の文書の照合で扱う)。
- **補正レイヤーの開始・受け取り・書き込みは、被写体マスクの先例 (`start_local_adjust_subject_segmentation` /
  `poll_local_adjust_segmentation`) と同じ一続きの手順にする** (Sol レビュー R4 P1。`Editing` の `revision` は
  履歴の区切りで `Selection` に戻り、開いただけでは `Editing` にならないので照合に使えない):
  1. 開始: `prepare_page_edit_history_boundary()` → `begin_local_page_edit(fs_idx)` → `capture_page_edit_owner` →
     `local_page_edit_layers_for_target(&owner.target)` で文書を取り、`owner`・`document`・`layer_idx`・`edit_target` を
     request に入れる。
  2. 受け取り: `page_edit_owner_is_current(&owner)` かつ
     `local_page_edit_document_for_producer(&owner, &document) == document` のときだけ進む (書き込み待ちの最新文書を
     取り込んだうえで、開始時と同じ文書であること)。違えば捨てる。
  3. 書き込み: 2 で得た文書を `before` として複製し、`layer_idx` のレイヤーの書き先へ §7.4 のとおり足して `after` を作り、
     既存の `set_local_adjust_layers_for_target_with_undo` を 1 回呼ぶ (Undo 1 つ・書き込み worker へ渡る)。
- 受け取り (`poll_mask_detect`、毎フレーム `try_recv`) では、次が**全部**今と一致するときだけ結果を足す:
  - 共通: context、`items_generation`、編集対象の page_key、マスクの大きさが `mask_size` と同じ、
    **今の入力画素 (§5.1 の表) が開始時と同じ `Arc` (`Arc::ptr_eq`)**。
  - 消しゴム: 消しゴムのモード中で `session` が同じ。
  - 隠蔽加工: 隠蔽加工のモード中で `session` が同じ、`source_kind` が同じ。
  - 補正レイヤー: 補正レイヤーのモード中で、上の手順 2 の文書の照合が通ること。
  一致しなければ捨てる。
- 画素の照合を `input_generation` にしないのは、**`input_generation` だけでは消しゴムの補完や補正レイヤーの
  結果の更新を網羅できない**ため。本番で進むのは元画像の読み直し (`bump_input_generation_for_fs_cache_reload`) と
  全ページ一括の `bump_all_input_generations()` (全画面の終了・補完の設定変更) で、ページ単位の
  `bump_input_generation` は本番から呼ばれていない (2026-11-26 のコード)。`Arc` の同一性ならどれが差し替わっても
  捨てられる。中身が同じで `Arc` だけ替わった場合も捨てるが、利用者がもう一度押せば済むので、それで良い。
  隠蔽加工の入力 (fs / erase_result / local_adjust) は、変化が無ければ同じ `Arc` を返すことを R2 でコードを
  確認済み。**消しゴムの `erase_base_cache` と補正レイヤーの `current_local_adjust_source_pixels` も同じ性質かを
  実装時にコードとテストで確かめる** (毎フレーム作り直す経路があれば設計担当へ返す)。
- 消しゴム・隠蔽加工ではマスクの版の照合は持たない。検出中は §7.1 の述語で、同じ context のマスクを変える入力が
  全部止まるため。補正レイヤーだけ文書を照合するのは、補正レイヤーの文書に非同期の書き込み待ちがあり、
  先例が既にその照合の仕組み (`local_page_edit_document_for_producer`) を持っているから (新しい仕組みは作らない)。

### 7.3 worker

- `std::thread::Builder` で 1 回ごとに 1 本 (先例と同じ)。`ai_runtime_init.wait_terminal_while(!cancel)` で
  ランタイムの準備を待つ。キャンセルは検出器ごと・YuNet の段ごとの区切りで見る。
- **worker は `local_ai_activity_lease()` を取り、ランタイム待ちから終わるまで持つ** (先例と同じ。Sol レビュー R1 P2)。
  推論の途中ではキャンセルが効かないので、待ちの状態を捨てた後も worker は少し残る。リモートへの引き渡しは
  この活動数を見て停止の完了を判断しているので、lease が無いと引き渡しが推論中に進む。新しい待ち合わせの
  仕組みは作らず、既存の lease を使う。
- worker はどのツールから呼ばれたかを知らない。中で完結させるもの: セッションの用意、前処理、推論、
  出力の読み取り、座標の変換、輪郭パッチの作成。
- 結果: `MaskDetectOutput { boxes: Vec<DetectedBox>, patches: Vec<MaskPatch>, counts: Vec<(String, usize)> }`。

### 7.4 結果を足す (UI スレッド)

共通の前処理として `admit_book_append_followup_mutation()` と `remote_session_blocks_local_control()` を通す
(先例と同じ)。そのあと、**そのツールの手描きの 1 操作 (図形の確定・バケツ) と同じ経路で 1 回の編集として足す**。
ツールごとの関数は 3 つ (`apply_mask_detect_to_erase` / `_to_conceal` / `_to_local_adjust`) で、どれも
「Undo の区切り → 書き込み → そのツールの既存の後処理」の順にする。

| | 消しゴム | 隠蔽加工 | 補正レイヤー |
|---|---|---|---|
| Undo の区切り | `push_undo_snapshot()` (`ui_erase.rs`、マスク全体の snapshot) | `push_conceal_undo()` (マスク全体の snapshot) | §7.2 の手順の `before` / `after` を `set_local_adjust_layers_for_target_with_undo` に 1 回渡す |
| 箱 | `mask_db::Shape::Rect` / `Ellipse` (`ShapeOp::Add`) を `erase_shapes` の末尾へ | 同じく `conceal_shapes` の末尾へ | `MaskShape::Rect` / `Ellipse` (op は描画) を編集中の `RasterVectorMask.shapes` の末尾へ |
| 輪郭 | 各パッチの範囲だけ `erase_mask` に OR | 各パッチの範囲だけ `conceal_mask` に OR | 各パッチの範囲だけ書き先の `alpha` を 1.0 にする (`alpha_mut()` はループの外で 1 回) |
| 書き先の準備 | — | — | 書き先が `LocalMask::Raster` なら `RasterVector` へ変換、追加 / 削除が `None` なら入力画素の大きさで空のマスクを作る。どちらもバケツと同じ処理を、この 1 回の編集の中で行う |
| 後処理 | 表示用テクスチャを無効にし、`clear_erase_preview(fs_idx)` で古い補完のプレビューを捨てる。**補完はここでは始めない** (次のプレビュー押下・確定・終了の既存の操作で走る。`commit_erase_shape` と同じ。R4 P2) | `commit_conceal_shape` と同じ (`conceal_mask_texture = None`・`clear_conceal_caches(idx)`) | `set_local_adjust_layers_for_target_with_undo` が行う (書き込み worker と再計算) |
| 選択 | 選択中の図形を外す | 同左 | 同左 |

- **検出が 0 件のとき・キャンセルしたとき・照合で捨てたときは、どのツールでもマスクも文書も変えず、Undo も積まない**
  (補正レイヤーでも空の書き先を作らない、`Raster` を変換しない)。
- 「描画 / 消去」の切替 (D / F) は見ない。検出は常に **書き先へ足す** (描画)。補正レイヤーで書き先が
  `OverrideSubtract` のときは、削除の範囲が広がる (書き先の意味どおり)。
- 合成の順序 (ビットマップを下地に図形を作成順に適用) は変えない。そのため **輪郭で足した部分に、前からある
  消去 (`Subtract`) の図形が重なると、そこは抜けたまま**になる。バケツと同じ既存の規則なので、変えずに
  マニュアルに書く。箱から作る図形は末尾に足すので、前の消去の図形より後で効く。
- **UI スレッドの費用 (Sol レビュー R1 P2 で見積もりを直した)**: 結果の追加そのものは図形の push とパッチの範囲の
  書き込みだけだが、Undo の区切りはマスク全体を複製し (補正レイヤーは文書の複製)、図形を足したときの表示用
  テクスチャは全体を作り直す。どれも **既存の 1 回の筆・図形の確定と同じ費用で、1 回の検出につき 1 回**。
  手描きの操作で既に払っている費用なので、検出のために worker 側で状態を準備する仕組みは作らない。大きな画像
  (例 8000×6000) でこの 1 回が目立つかは段 1 の実装時の perf ログで測り、目立つなら既存の手描きの操作と一緒に直す
  (検出だけの別経路は作らない)。

### 7.5 まれな失敗

モデルが壊れている・読めない・推論に失敗した・GPU のメモリが足りない、はログとエラー表示で終わる
(既定の割り切り)。再試行・自動で別の検出器に切り替える・途中の結果を残すことはしない。

## 8. 配布・ライセンス・公開文書

- **mIV が配布するのは YuNet だけ**。BYO の検出器は利用者が配布元から取得する。mIV のアプリは検出器の
  ダウンロードも、配布元のページを開くこともしない (配布元のページに成人向けの見本画像が載っていることがあり、
  アプリから直接開かせない)。
- ダイアログとマニュアルに書くこと:「mIV は追加の検出器を配布していません。入手した検出器は配布元の
  ライセンスに従って使ってください」。ONNX にライセンス文字列があれば、そのまま表示する (Ultralytics 製なら
  AGPL-3.0 と出る)。HF の表記を mIV が言い換えない。
- **マニュアルには、形式を確かめた検出器の具体名と配布元を載せる** (2026-11-26 利用者決定。言葉に気をつけて書く)。
  書き方の決まり:
  - 載せるのは **段 0 と利用者の確認で読めることを確かめたものだけ**。表の列は「名前・配布元 (ページの URL)・
    種類 (箱 / 輪郭)・配布元が示すライセンス・学習の仕組み (Ultralytics 製なら AGPL-3.0 の主張がある旨)」。
  - 用途の説明は **処理内容と対象の種類だけを中立に書く** (例:「成人向けのイラストで、隠す対象になる部位の
    領域を返す検出器」)。部位の名前を本文で並べない。モデルが返す分類名は、mIV のダイアログでそのまま見える
    ので、マニュアルには書かない。
  - 投稿サイト名・基準名・「投稿に使える」「基準を満たす」などの適合の判定は書かない。「高精度」などの評価語も
    書かない (精度は利用者が確かめる)。見落としがあり得ることと、結果を確かめてから使うことを書く。
  - 見本の画像は顔 (権利のはっきりした写真) だけ。成人向けの画像は載せない。配布元へのリンクは、配布元の
    ページに年齢の確認があり成人向けの見本が載ることがある旨を添える。
  - 置く場所・json の書き方・読めないときの表示も同じページに書く。
- **製品ページ・Store の説明・スクリーンショット**では、顔を隠す・ぼかす機能として紹介する。局部の検出は書かない
  (Store Policies 11.1 の説明文の年齢基準と、11.7 を避けるため。v7.20、2026-09-15 公開)。
  Store の年齢区分 (IARC) の回答に影響しないかを、公開時に確かめる。
- 表記: 投稿サイト名・基準名・適合の判定は書かない ([public-wording-policies.md](public-wording-policies.md))。
  処理の説明は「検出した領域をマスクに追加する」「余白 N% で広げる」のように機構で書く。
- 法的な整理 (2026-11-26、法律相談ではない): モザイクを**かける**機能はわいせつ性を下げる方向なので、提供で
  責任を問われる構図は考えにくい。注意点は見落としで、mIV は「これで十分」と表示しない。モザイクで違法な
  画像が合法になるわけではないことも、UI では何も示唆しない。消しゴムは周りから埋めるだけで隠れた内容を
  作らないので、検出を消しゴムにつないでもモザイク除去にはならない (§1.2)。

## 9. 既存の仕組みとの整合

- **表示順**: raw → erase → local-adjust → conceal → edit result → final pipeline は変えない。各ツールは
  自分の段の入力 (§5.1) で検出する。
- **キャッシュ**: マスクの変更は各ツールの既存の該当ページだけの失効 (§7.4 の後処理)。全体設定の変更ではないので
  `bump_conceal_generation` などの全体の失効は呼ばない。
- **消しゴムの補完**: 検出で足したマスクも手描きと同じく、古い補完のプレビューを捨てるだけで、補完 (MI-GAN) は
  次のプレビュー押下・確定・終了の既存の操作で走る。検出の完了時に保存や補完を新しく始めない。
- **補正レイヤーの書き込み**: 検出で変えた文書も既存の書き込み worker (`local_adjust_write_worker`) で保存する。
- **ZIP・PDF・見開き**: 3 ツールとも対象ページ 1 枚で動いている。検出も同じ 1 枚に行う。分岐は足さない。
- **アップスケール後の解像度**: 3 ツールともアップスケールより前段 (元の解像度) なので、検出も元の解像度で行う。
- **リモート操作中**: 先例と同じく `remote_session_blocks_local_control()` で止める。worker は
  `local_ai_activity_lease()` を終わるまで持ち、リモートへの引き渡しは推論が終わるまで完了しない (§7.3)。
- **detached viewer**: 待ちの状態は context の bundle に置き、持ち主の context でだけ受け取る。detached の
  述語・viewport の経路には触れない予定。触れる必要が出たら、detached リワークの規則 (双方のレビューで構造的な
  修正であることに合意し、[detached-rework-plan.md](detached-rework-plan.md) に記録) に従う。

|---|---|
| 検出器フォルダの read_dir・ONNX のメタデータ | worker (ダイアログを開いたとき・読み直し) |

## 12. テスト

- **単体** (検出のモジュール):
  - 各形式の出力の読み取りを、作った小さなテンソルで確かめる (既知の入力 → 既知の箱・輪郭)。
  - letterbox の行きと戻りで、画像座標が元に戻る (縦長・横長・元より大きい入力)。
  - 重なりの除去、閾値、分類の選択。
  - 輪郭パッチ: 箱での切り抜き、太らせ、元の解像度への拡大、画像の端での切り詰め。
  - メタデータ・json・`labels.json` からの分類名の決定と優先順位。どれにも当てはまらない形を「読めない」にすること。
  - `DetectedBox` / `MaskPatch` から各ツールの型 (`mask_db::Shape`・`MaskShape`・ビットマップ・alpha) への変換。
- **App レベル** (`page_edit_owner_tests` などの先例に倣う。**3 ツールそれぞれで**):
  - 結果を足すと図形とビットマップ (補正レイヤーは alpha) が増え、Undo 1 回で戻る。そのツールのキャッシュの
    該当ページが無効になる。消しゴムでは古い補完のプレビューが捨てられ (補完は始まらない)、補正レイヤーでは
    `set_local_adjust_layers_for_target_with_undo` 経由で書き込み worker へ渡る。
  - 0 件・キャンセル・照合で捨てたときは、マスク・文書・Undo のどれも変わらない (補正レイヤーで `None` の書き先や
    `Raster` のベースが、そのまま残る)。
  - 補正レイヤー: ベースが `Raster` のときは `RasterVector` に変換されて足され、追加 / 削除が `None` のときは
    入力画素の大きさで作られて足される。どちらも Undo 1 回で元に戻る。
  - 開始時の条件 (context・page_key・items_generation・ツールの印) のどれかが違う結果は捨てる。
  - 検出中 (とダイアログ表示中) は述語が真になり、**キーだけでなく、キャンバスの生のポインター入力 (筆・バケツ・
    図形・選択の操作) とパネルの操作 (スロット・プリセット・閉じる) も効かない**。[自動検出…] を続けて押しても
    2 本目が始まらない。キャンセルで待ちが消える。
  - 述語が真の間、目のボタンの矩形を押しても、ドラッグで通過してもプレビューが始まらない。押していた保持は離すと
    後始末される。
  - 開始後に同じページの入力画素が差し替わる (消しゴムの補完の完了・補正レイヤーの再計算・元画像の読み直し) と、
    `Arc` の照合で結果を捨てる。差し替わらなければ (`Arc` が保たれ) 結果を足す。一覧の読み直し
    (`items_generation` の変化) でも捨てる。
  - 補正レイヤー: 開始後に文書が変わった (書き込み待ちの取り込み後の文書が開始時と違う) 結果は捨てる。被写体
    マスクや LUT の待ちがある間は始まらない。グラデーションなど手動で書けないマスクのベースで、追加 / 削除も
    編集していないときはボタンが押せない。
  - 述語が真の間、補正レイヤーのキャンバス処理の中で直接消費されるキー (`LaToolBucket` など) が効かず、左右の
    パネルがどちらも操作できない。
  - 補正レイヤーと隠蔽加工のモードが両方立っている状態 (既存の問題) で検出しても、捕捉した対象のツールの
    マスクだけが変わる。
  - キャンセルで待ちが消えた後も、worker が終わるまでは活動の lease が残り、リモートへの引き渡しの停止判定が
    完了しない。
  - context を閉じる・フォルダを替える・モードを出ると待ちが消え、worker のキャンセルが立つ。
    **別の context のマスクは変わらない** (複数ウィンドウ)。
  - リモート操作中・本の追加の後続待ち中は始まらない。
- **UI**: ダイアログの 1093×614 の検査 (`tests/support/scroll_layout.rs` の先例)。スナップショットは足すなら
  [ui-snapshot-policy.md](ui-snapshot-policy.md) に従う。
- **利用者の実機確認**: 人物写真での顔の検出 (3 ツール)、BYO の検出器を置いたときの一覧・検出・モザイク、
  大きな画像・ZIP・PDF・見開きのページ、検出中に別ウィンドウを操作したとき。

## 15. 判断の記録

- **顔は同梱、局部は BYO**: 同梱できる顔検出が実在し (YuNet、MIT)、局部の検出器は調べた範囲ですべて
  Ultralytics 製で AGPL の主張がある。顔を隠す機能は機微性が低く、製品として紹介しやすい。
- **結果を既存のマスクにする**: 検出は完全ではない前提なので、焼き込まずに直せる形で渡す。保存・Undo などを
  新しく作らずに済む。
- **箱は図形、輪郭はビットマップ**: 箱は図形にすると動かせる。輪郭は図形で表せないので、筆やバケツと同じ
  ビットマップに入れる。
- **3 ツール共通、検出はツールを知らない**: マスクの道具が 3 ツールで共通なので、自動検出も 1 つにする。
  ツールごとの違いは入力の画素 (§5.1) と書き先 (§7.4) だけに閉じ込め、検出・ダイアログ・待ち・設定は 1 組。
  当初の「隠蔽加工だけ」は、消しゴムがモザイク除去にならないことから利用者の判断で取り下げた。
- **検出中はモーダル**: 検出は短く、途中の操作を受け付ける利点が小さい。割り込みを扱う仕組みを作るより、
  組み合わせそのものを消すほうが単純で見落としが少ない。外からの変化だけを開始時の条件との照合で捨てる。
- **待ちは context に 1 つ**: 受付が待ちの間は新しい検出を受け付けず、捕捉した対象 1 つだけを所有するので、
  ツールごとの待ちは要らない (モードの排他は根拠にしない。R4 P2)。
- **検出器フォルダは固定、取り込みボタンなし**: 設定と状態を増やさない。使ってから要否を決める。
- **外部モデルを `AiRuntime` に置く**: セッションの持ち主を 1 つにし、`ModelKind` の固定の表 (TensorRT・診断) に
  手を入れない。同梱の YuNet も同じ経路にして、読み方を 1 つにする。

### 17.3 顔検出の段と閾値

段 (長辺 640 / 1280 / 1920 / 2560 / 元の大きさ) ごとに検出し、全段の合計 (重なりを除いた後) に対してどれだけ
拾えたかを数えた (全段の合計には誤検出も含む)。

| 組み合わせ | 閾値 0.5 | 閾値 0.7 |
|---|---|---|
| 全段 | 1,351 (100%) | 960 (100%) |
| 1280 + 2560 + 元 | 94.8% | 99.1% |
| 1920 + 元 | 90.9% | 95.4% |
| 640 + 元 | 88.4% | 91.0% |
| 元を含まない最良 (1280 + 1920 + 2560) | 87.1% | 92.8% |

- 元の大きさの段が無いと、多人数の写真の小さな顔 (顔の短辺の 10 パーセンタイルが約 30px) を大きく取りこぼす。
- 一番大きい顔は短辺 1,943px (元の大きさ) あり、YuNet の得意な 300px を超えるので、640 の段も要る。
  → §5.3 は「640・1280・2560 のうち元より小さいもの + 元」の最大 4 段にした (閾値 0.7 で全段の合計の 99% を拾う
  1280 + 2560 + 元に、大きな顔のための 640 を足したもの)。
- 重ね描きを目で見た結果、閾値 0.5 は手・物・石碑の文字の面などへの誤検出が増え、0.7 は横顔・うつむいた顔の
  取りこぼしが目立った。人形の顔は 0.9 で検出された。→ 既定 0.6、ダイアログで変えられる (§4.2)。
