# mImageViewer v1.0.0 Data-Integrity Review (Opus 4.8 multi-agent)

- **実施日**: 2026-05-29
- **手法**: 「ユーザーのファイル/設定を壊す・失う」書き込み/永続化経路に限定し 6 観点で Opus 4.8 並列レビュー
  → 各指摘を独立した敵対的検証エージェントが反証 → 通過分のみ採録。
- **規模**: 17 エージェント / tool 利用 242 回 / 約 18 分。
- **結果**: 生 10 件 → 検証通過 **7 件** (P2×4, P3×3、**P1 なし**)。
- **観点**: save-encode / xmp-tag-write / archive-convert / settings-persist / sidecar-rotation-pins / delete-safety。

**P1 が無いのは重要な良い結果**: 不可逆な「原本」を触る経路は、エクスポートが必ず新規ファイルを作る
(原本は無変更)、アーカイブ変換は原本を read only、という設計のため。最も影響が大きいのは、
明示的に「ゴミ箱に移動」と約束しているのに条件次第で完全削除に倒れる #1。

## 統合レポート (synthesis agent)

### P2 — 起きにくい経路 / 緩和策ありのデータ損失・破損

#### DI-1. ゴミ箱削除が無言で完全削除になる
**`src/delete_worker.rs:144`**（UI 約束: `src/ui_dialogs/context_menu.rs:761,763`、マニュアル: `htdocs/.../manual/grid.html:261`）

`recycle_one()` は `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI` を設定するが
`FOF_WANTNUKEWARNING` が無い。Windows の `SHFileOperationW` は `FOF_ALLOWUNDO` でも、ゴミ箱に
入れられない時 (ファイルがゴミ箱予約容量より大きい / ボリュームでゴミ箱無効 / リムーバブル・USB /
多くのネットワーク共有) は**完全削除にフォールバック**する。通常は「ゴミ箱に入らない、完全削除する?」
と確認が出るが、`FOF_NOCONFIRMATION` がまさにその確認を抑制し、`recycle_one` は `Ok(())` を返す
(グリッドからは "成功" として消える)。削除対象はユーザーの不可逆な原本 (`grid_item.rs:203-212`)、
確認ダイアログは「ゴミ箱に移動しますか?」と明示している。結果、回復可能と信じたまま原本を完全に失う。

**Fix:** `fFlags` に `FOF_WANTNUKEWARNING` を追加 (windows 0.61.3 に `FILEOPERATION_FLAGS(16384)` 存在確認済)。
`FOF_NOCONFIRMATION` 下でも nuke 警告が再表示される。最小・最安。将来的には `IFileOperation` で
per-item の結果/中断取得に移行も可。

#### DI-2. ZIP 内 JPEG エクスポートで Orientation を 1 にしつつ画素は未回転
**`src/export_dialog.rs:312`**（連鎖: `src/app.rs:15374-15381`, `src/save_with_metadata.rs:324-328,409-489`）

`run_export()` は全エクスポートで `caller_applied_orientation: true` を固定する (ZipEntry も)。だが
フルスクリーン decode は非 ZIP 画像にのみ EXIF 自動回転を適用する (`app.rs:15376`:
`if zip_entry.is_none() { apply_exif_orientation(...) } else { img }`)。よって ZIP 内 JPEG の
base 画素は未回転。flag が true だと `encode_jpeg_with_metadata` が `reset_exif_orientation_in_app1` で
元の Orientation (例 6=90度回転) を 1 に書き換える → エクスポート JPEG は傾いたまま「回転なし」タグ →
EXIF 対応ビューア (Windows フォト/ブラウザ) で誤表示。`false` 分岐と unit test
`jpeg_orientation_preserved_when_caller_did_not_apply` が用意済みなのに、呼び出し側が flag を渡し
損ねている。原本 ZIP は無変更 (新規ファイル) なので回復可、P2。

**Fix:** `caller_applied_orientation: !matches!(request.source, ExportSource::ZipEntry { .. })`
(`app.rs:15376` の `zip_entry.is_none()` 条件をミラー)。

#### DI-3. WebP のタグ/レーティングが書けるが読み戻せない (round-trip 破綻 + toggle/undo 誤り)
**`src/xmp_reader.rs:76-81, 189-205, 212-227`**

writer は WebP 完全対応 (`xmp_writer.rs:1204/1272`: RIFF 解析・VP8X 昇格・原子的 `XMP ` chunk 追記)。
だが **reader が 2 つの gate で WebP 非対応**: `extension_might_have_xmp` が `"webp"` を含まず
(`read_dc_subject`/`read_xmp_rating` が空 early-return)、`has_xmp_capable_magic` が RIFF/WEBP を
判定しない (`*_from_bytes` と `tag_prewarm` が bail)。**リリース済み機能**での影響:
WebP のタグ/レーティングがグリッドバッジ・メタパネル (`ui_metadata_panel.rs:330`)・全文索引
(`ingest_text.rs:181`) に出ない。さらに `tag_write_worker.rs:312` が `tags_before` を常に空と読むので
**Toggle が常に ADD** → WebP のタグを解除できず、Undo の「before」も常に空 (誤った逆操作)。ファイルは
壊れず (Lightroom/ExifTool は読める)、損失は「アプリ内可視性 + 誤 toggle/undo」。

**Fix:** reader を WebP 対応に: `extension_might_have_xmp` に `"webp"` 追加、`has_xmp_capable_magic` に
`bytes[..4]=="RIFF" && bytes[8..12]=="WEBP"` 追加、`extract_xmp_packet` に RIFF 走査分岐追加
(`xmp_writer::parse_webp_chunks` をミラー、奇数サイズ padding 考慮)。write→read round-trip テスト追加
(既存 `minimal_webp_roundtrip_add_tag` は raw バイトしか見ず欠陥を見逃している)。

#### DI-4. solid 7z 変換で skip エントリを drain せず後続にバイトがズレる
**`src/archive_converter.rs:295-298`**

`convert_7z` のコールバックがディレクトリ/非画像エントリを `Ok(true)` で**読まずに**skip する。コメント
(「solid 圧縮でも正しく動く」「Read から読まなくても内部で進む」) は **solid 7z (7-Zip の既定)** では誤り。
sevenz-rust2 0.20.2 では block 内の各ファイルが**同一の**逐次 `block_reader` を `BoundedReader(file.size)`
で包むため、あるエントリを消費しないと stream が進まず、次のエントリが前の残バイトを読む。ライブラリ自身の
`read_file` は全エントリを `read_to_end` で drain している。トリガー: solid 7z で非画像**ファイル**
(readme.txt/.nfo/Thumbs.db) が同 block 内の画像より前にある場合。per-file CRC があれば (一般的)
ズレが `Crc32VerifyingReader` で検知され変換失敗→tmp 削除 (壊れたキャッシュは残らないが有効な
アーカイブが閲覧不能)。CRC が無い場合 (`has_crc==false`、稀) ズレたバイトを**無言でキャッシュ登録** →
開くと画像破損。原本 `.7z` は read only。

**Fix:** skip 分岐で `std::io::copy(r, &mut std::io::sink())?` で drain (ライブラリと同じ)、または
`reader.archive().is_solid` を見て常に全エントリ read_to_end。回帰テスト: solid 7z
(`push_archive_entries`) に非画像→画像の順で入れ、画像バイトの完全一致を検証。

### P3 — 軽微 / 緩和済み / 再生成可能キャッシュのみ

#### DI-5. 正規化後の同名衝突で片方の画像が名前解決不能
**`src/archive_converter.rs:299-304` (7z) / `369-372` (lzh)** — `normalize_entry_name` が `\`→`/`・先頭
`/` 除去を dedup なしで行うため `a\b.jpg` + `a/b.jpg` が同名 2 エントリに。read 時 by_index で 2 ページ
列挙するが by_name (`zip_loader.rs:540-545`) は先頭のみ返す → 2 枚目が到達不能。出力は再生成可能
**キャッシュ**、原本無事、トリガーは病的 (1 アーカイブ内でセパレータ混在)。「case 衝突」の主張は誤り
(normalize は小文字化しない)。P3 下限。**Fix:** 書込済み正規化名を `HashSet` で追跡し衝突時に suffix/skip。

#### DI-6. 設定 JSON→SQLite 移行が checkpoint 前に旧 JSON を rename
**`src/settings_db.rs:1976-1990`** — `create_new → save_full(WAL commit) → record_migrated_from_json →
rename_legacy_json_files` の間に `wal_checkpoint` が無い。`synchronous=NORMAL`+WAL (`:866-877`) では
commit は**アプリ**crash には耐えるが **OS/電源断**では checkpoint で main DB が fsync されるまで非保証。
commit 後・WAL 永続化前の電源断で `settings.db` が Present だが空 (bootstrap_complete 喪失) になり得、
boot tree が Present 分岐を short-circuit (`:2119`) するため**移行が再試行されず** Corrupted → 初回は bak
無し → `FailedFallbackDefault` (save 抑制)。緩和: 旧 JSON は**削除でなく rename** (`:1904`) なので原本は
ディスクに残り手動回復可、真の電源断のサブ秒窓のみ、初回移行限定。**Fix:** JSON rename 前に
`db.checkpoint_truncate()` (`:543` に実装済) を呼ぶ。または next boot で Present-but-Corrupted + JSON 残存
なら移行分岐へ fall through。

#### DI-7. 現行版 sidecar の parse 失敗時に disabled を立てず次編集で上書き消去
**`src/sidecar.rs:151-174`** — newer-version は `disabled=true` (`:169`) で flush 上書きを防ぐが、JSON parse
失敗 (`:151-160`) は disabled を立てず空で返す。現行版だが破損した sidecar (外部ツール/ディスクエラー/
原子書込前リリースの crash) が空 load → import 何もせず → 次の補正/マスク/隠蔽編集で `flush()` が単一
エントリで上書き → 手動回復可能だったデータを破壊。フォルダ移設時は sidecar が**唯一のコピー**になり得る
(DB キーは絶対パス基準, `adjustment_db.rs:306`)。緩和: mIV 自身の書込は原子的 (`:340-364`) で mIV は
破損 sidecar を作らない (外部要因前提)、sidecar はバックアップ層で中央 DB が正。**Fix:** parse 失敗分岐で
`me.disabled = true` (`:169` をミラー)。任意で bad file を `mimageviewer.dat.corrupt` に rename。

## (a) 安全/原子的と確認できた書き込み経路 (カバレッジ)

- **XMP タグ/レーティング writer** (`xmp_writer.rs`): `write_atomically`(`:248-266`) = temp+rename。
  container 変更は冪等 (既存 `XMP ` chunk を読み直すので重複/肥大なし)。WebP の VP8X 昇格も正しい。
  **壊れているのは reader 側だけ (DI-3)、書かれるバイトは健全。**
- **JPEG メタ encode** (`save_with_metadata.rs`): orientation reset と `caller_applied_orientation=false`
  分岐は正しく unit test 済。バグは呼び出し側の flag 誤り (DI-2) で encoder ではない。
- **エクスポート** (`export_dialog.rs`): `create_new` で**新規**ファイルに書く。encode 失敗でも原本は
  無変更・無切り詰め。
- **アーカイブ変換** (`archive_converter.rs`): 原本 `.7z`/`.lzh` は read only、出力は再生成可能キャッシュ、
  CRC 経路ではエラー時に登録前 tmp 削除 (`:222-225`)。
- **設定 DB** (`settings_db.rs`): WAL + bak1..bak10 世代 + quarantine + 移行は JSON を rename。アプリ
  crash には耐え、電源断のサブ秒窓 (DI-6) のみギャップ、その場合も旧 JSON は残る。
- **sidecar** (`sidecar.rs`): mIV の書込は temp+rename 原子的。mIV は破損 sidecar を作らない。
  newer-version は保護済 (DI-7 は parse 失敗の非対称のみ)。

原本を in-place で truncate→stream する経路は検出されなかった。

## (b) 追加すべき回帰テスト

1. **delete fallback**: `recycle_one` の flags に `FOF_WANTNUKEWARNING` が含まれること。
2. **ZIP エクスポート orientation**: EXIF Orientation=6 の ZIP 内 JPEG をエクスポート → 出力の
   Orientation タグが画素の向きと一致 (flag が false で渡る) こと。
3. **WebP XMP round-trip**: 最小 WebP にタグ+レーティングを書き、`read_dc_subject_from_bytes` /
   `read_xmp_rating_from_bytes` で読み戻して一致。tagged WebP の toggle で REMOVE が効くこと。
4. **solid 7z 変換**: solid アーカイブ (`push_archive_entries`) に非画像→画像で入れ、各画像バイトの
   完全一致を検証。
5. **同名衝突**: `a\b.jpg` + `a/b.jpg` を含むアーカイブを変換 → 両画像が名前で個別解決可能。
6. **設定移行の電源断**: `migrate_from_settings_json` 後、main `settings.db` が自己完結 (WAL 無しで
   bootstrap marker が耐久) = JSON rename 前に checkpoint されていること。
7. **破損 sidecar 非上書き**: 破損した現行版 sidecar を load → 編集 → 原本が上書きされない (disabled
   のまま) こと。
