### §1.198

Sol の実装前提検証と親の source inspection により、旧「セル幅で頭打ち」説は不成立。
`resize_to_display_color_image` はセル比率を取らず `display_px × display_px` へ fit する。
`should_save=false` でも Source の `ThumbMsg` は保存判定前に送信する。
`thumb/ready` は初回表示だけを記録し、Loaded→Loaded の結果更新では出ない。
したがって ready 件数だけから「生成結果を破棄している」とは言えない。

親は共通整数寸法選択 `fast_resize::aspect_accurate_fit_dimensions` の0.05%比率誤差条件と、
idle側の80%解像度条件の不一致を候補として提示。884:444=221:111 のような比率で、
比率精度を満たす最大整数候補が要求長辺より小さくなる可能性を、実装担当が再現検証する。
この選択処理は `e7191ad20` (2026-08-12、v3.0.0以降) で導入されている。
根因確定前にセル上限のパッチは入れない。

**根因確定と設計判断**: 実ログの要求は374px。現寸法選択は884×444から247×124を生成し、
idle判定は `247 * 5 < 374 * 4` で再成立する。400px要求なら400×201になり、
要求サイズによって非連続に発生する。親の初期予測「400pxなら221×111」は誤りとして撤回した。

Sol案の「候補を最大長辺の99%以上に制限」は独立Astraレビューで採用しない判断となった。
374pxの近傍には0.05%以下の候補がなく、最良374×188でも誤差約0.081833%になる。
既存の比率精度契約を緩和し、PDFiumのraster選択・Remote JPEGにも影響する。
代表比率テストの99%条件だけで、全比率にその優先順位を拡張できるとは判断しない。

採用設計は、生成workerが実際に評価した要求サイズを画像の生成元と一緒に保持する。
現在のLoaded画像に対応するSource生成要求が完了していれば、同じ要求サイズで再生成しない。
実画像サイズは従来どおり保持し、要求サイズで偽装しない。Sourceの再投入は
「実寸が従来の80%基準未満」かつ「現在要求がその画像の生成時要求より大きい」場合。
cacheは従来の高画質化を維持する。要求完了の判定へ80%をもう一度掛けてはならない。
374→400pxでは不足を再評価して400×201へ更新できる必要がある。

coverageは現在の画像に従属し、過去要求の最大値として合成しない。画像なしのfinalized/
cancel/errorでは更新せず、texture backlog・items世代・viewer contextと共に移動・失効する。
既存の生成元分類をtyped ownerとして結果からLoadedへ保持し、独立のpending/完了boolを足さない。
UIで寸法探索・I/Oを行わず、既存の生成画像・比率精度・保存形式を維持する。
親の判断と独立Astraの条件付き承認が一致し、具体型とproducer網羅をSolが実装前確認する。

**別の品質判断として残すもの**: 比率精度優先で374px要求から247pxへ縮むこと自体は変わらない。
大きなcacheから小さなSource画像へ置き換わる場合も既存挙動であり、今回新たに導入する劣化ではない。
これも解消するなら、比率精度と解像度の優先仕様を別に決める必要がある。
