# X 予約投稿 (X Scheduled Post) 設計 — 正本

mIV から X (Twitter) へ、指定時刻に自動で投稿する機能の設計。

- 状態: **設計合意済み・未実装**。§14 の未決が埋まるまで実装に入らない。
- 作業場所: 別 worktree (branch `x-scheduled-post`)。master と並行させる。
- 参考実装: `C:\home\xupload` (利用者の自作 Python ツール)。X 側の仕様・課金・
  失敗モードはここで実運用済みなので、**推測ではなくこの実証を出発点にする**。
- 関連: [sns-split-export-plan.md](sns-split-export-plan.md) (X の表示実測。§2.1 が
  カルーセル表示と継ぎ目比の正本)。

**この機能は利用者の金を使う。**設計の優先順位は
**「投稿されないこと」より「二重に投稿・課金されないこと」が上**。§6 がこの文書の中心。

---

## 1. 何を作るのか

1. **予約投稿**: 本文 + メディア (画像 1〜4 / 動画 1 / GIF 1) と投稿時刻を登録すると、
   その時刻に X へ投稿される。
2. **投稿プレビュー**: X のタイムラインでの見え方に近い形で、本文・改行・リンク色・
   文字数・メディアの並びを確認できる。
3. **費用の管理**: 本文に URL を含むと 1 投稿あたりの単価が跳ねる (§2.3)。予約前に
   見せ、実際に発生した課金は台帳に残し、1 日あたりの上限で暴走を止める (§6.6)。
4. **投函フォルダ**: 決められた形式の JSON を所定のフォルダへ置くだけで予約が入る
   (§8)。既存の xupload を「mIV へ予約を投げるだけ」に作り替えられる。
5. **不在時でも投稿する**: 実行は Windows タスクスケジューラに登録した 1 タスクが
   担う。**mIV を一度も起動しなくても予約時刻に投稿される** (§4.1)。

**やらないこと**は §11。**pixiv は対象外** (規約を読んだうえでの見送り。§11.1)。

## 2. 前提 — X 側の仕様 (xupload の実運用で確定している事実)

以下は `C:\home\xupload\CLAUDE.md` (2026-08-30) と `post_worker.py` に記録された
**実運用で確認済み**の事実。実装時には最新を再確認するが、設計の土台はこれ。

### 2.1 X には「予約投稿 API」が無い

- Ads API の `scheduled_tweets` は 2026-08 に `nullcast=false` (= タイムラインに出る
  通常投稿) の作成が **X 側で禁止**された。`nullcast=true` は Promoted-Only で
  タイムラインに出ないので用途を満たさない。
- X API v2 に `scheduled_at` 相当は **無い**。

→ **「時刻が来たらローカルから投稿する」以外の方法が無い。**時刻に何かが起きている
必要があるのは、この制約が理由であって設計の都合ではない。

### 2.2 認証と API

- **OAuth 1.0a のユーザーコンテキスト**。利用者が X Developer Portal で作った App の
  API Key / Secret + Access Token / Secret の 4 つを mIV に貼る。ブラウザ認可フローは
  要らない。
- Bearer Token (アプリ単位認証) では **投稿できない**。
- App が **v2 Project 配下**に無いと `POST /2/tweets` が 403。Portal の作り方次第で
  詰まるので、設定画面のヘルプに書く。
- App permissions を Read and Write に変えたら **Access Token の再生成が必須**
  (古いトークンは Read のまま)。実際に踏まれている落とし穴なので、接続確認が 403 の
  ときの案内文に入れる。
- 投稿は v2 `POST /2/tweets`、メディアは v1.1 `media/upload` (xupload が使っている
  経路)。**v2 のメディアアップロードへ移っているかは実装時に確認する**。

### 2.3 課金 (pay-per-use, 2026-02 以降)

公式の料金表 ([docs.x.com](https://docs.x.com/x-api/getting-started/pricing)、
2026-09-06 に確認) と、xupload の実運用記録から:

| 項目 | 単価 | 数え方 |
| --- | --- | --- |
| Post: Create | $0.015 | リクエスト |
| Post: Create (**本文に URL を含む**) | **$0.200** (13 倍) | リクエスト |
| Media Metadata (alt text) | $0.005 | リクエスト |
| Posts の読み取り | $0.005 | **リソース** (= 取得した投稿 1 件ごと) |
| Users の読み取り | $0.010 | リソース |
| メディアアップロード | **料金表に項目が無い** | — |

- **読み取りは「リクエスト」ではなく「リソース」単位。**取得した件数だけ課金される。
  §6.4 の照合は `since_id` + `max_results` を最小にして、必要な件数だけ取る。
  照合 1 回の実費はおよそ $0.005 x 取得件数 + 初回だけ $0.010 (`users/me`)。
- **メディアアップロードは「無料と書かれている」のではなく「項目が無い」。**
  §6 の「アップロードは自由に再試行してよい」はこの読みに依存しているので、
  **P1 で実測して裏を取る** (§2.5)。
- **URL 入りが 13 倍**なのが「リンク付きだと料金が大きく変わる」の中身。単価は X の
  公表値に依存し変わり得るので、mIV は**単価を設定値として持ち**、文言は
  「URL を含むと単価が上がる」+ 現在の設定値、という書き方にする。
  mIV が「$0.20 かかります」と断定して外したら信用問題になる。
- **高い呼び出しは `POST /2/tweets` 1 つだけ。**アップロードが無課金なら、
  「重い処理は何度でもやり直せて、危ないのは最後の 1 回だけ」という構造になる。
  §6 はこの非対称性の上に立っている。
- 空振り (投稿対象なし) では API を 1 回も叩かないので課金ゼロ。タスクの間隔を
  短くしても費用は増えない。

### 2.4 メディアの制約 (実装時に再確認する)

- 画像 4 枚 **または** GIF 1 **または** 動画 1。**混在不可**。
- 画像 5MB (PNG)、GIF 15MB、動画は容量・尺の上限あり。xupload は 5MB 超を JPEG へ
  再圧縮している (mIV は書き出し時に長辺と品質を持っているので同じ判断を設定で持つ)。
- 動画は chunked upload (INIT / APPEND / FINALIZE) + 変換処理の完了待ちが要る。
  **画像より一段重い**。v1 に含める (§14 決定 8)。
- `media_id` は発行から 24 時間で失効する。**予約時に先行アップロードはしない**
  (数日先の予約で失効するため)。投稿の直前にアップロードする。

### 2.5 費用の確認方法 — 内訳は当てにしない

公式ドキュメントには「Developer Console で使用量と課金をリアルタイムに監視できる」と
あるだけで、**エンドポイント別の内訳が見られるとは書かれていない**。合計しか出ない
前提で確かめ方を決める。

- **切り分けて測る。**「メディアアップロードが無課金か」は、投稿を 1 件も作らずに
  **アップロードだけを N 回**行い、残高が動くかを見れば分かる。通常の投稿と混ぜない。
  照合の読み取りも同様に、投稿せず読み取りだけを行って測る。
- **mIV 側の台帳と突き合わせる** (§6.6)。mIV は課金対象の呼び出しを毎回記録するので、
  「mIV の予測合計」と「Console の合計」を比べれば、想定外の課金が起きていないか
  分かる。内訳が無くても合計同士なら比較できる。
- **X 側の支出上限を必ず設定してもらう。**Developer Portal に
  「請求サイクルあたりの上限額。到達すると次のサイクルまで API リクエストが
  ブロックされる」設定がある。**mIV の 1 日上限 (§6.6) より外側で、サーバ側で
  効く最後の砦**なので、設定画面のヘルプから案内する。

## 4. アーキテクチャ

### 4.1 所有権

```
Windows タスクスケジューラ (5 分間隔・ログオン中のみ・1 タスク・多重起動しない)
└─ mimageviewer.exe --x-post-worker
    └─ mimageviewer-core.exe --x-post-worker   ← ★ 投稿するのはここだけ
        1. 投函フォルダを取り込んで DB 行にする (§8)
        2. due を claim して投稿する (§6)
        3. 終了

mimageviewer-core.exe (通常の GUI)
└─ UI スレッド (App)
    └─ 作成ダイアログ / 予約一覧 / 課金台帳 / 設定
       …… 予約を DB へ書くだけ。投稿はしない
```

- **投稿する主体は 1 つだけ** — `--x-post-worker` の一発プロセス。GUI は投稿経路を
  持たない。「今すぐ投稿」も `scheduled_at = now` の予約を作って worker を spawn する
  ので、経路は 1 本に保たれる (CLAUDE.md「1 つの意味を 2 か所に書かない」)。
  例外は**接続確認**だけで、これは投稿ではないので GUI が直接叩く。
- **唯一の真実は `x_posts.db`**。GUI・worker・投函フォルダの取り込みは、すべて DB を
  介してだけ会話する。投函フォルダは**入り口であってキューではない** (§8.3)。
- GUI と worker は**別プロセスから同じ DB を触る**。`journal_mode=WAL` +
  **`synchronous=FULL`** + `busy_timeout` を明示的に設定する。
  - `synchronous=FULL` は性能のためではなく **§6.2 の「送信中」マークを電源断で
    失わない**ため。WAL の既定 (`NORMAL`) は直近のコミットを落とし得るので、
    「送ったのに送っていないことになっている」= 二重投稿の原因になる。DB は小さく
    書き込みも稀なので、常に FULL で困らない。
  - rusqlite の既定 `busy_timeout` は 5 秒だが、`journal_mode` の変更自体が競合で
    即 `locked` になり得るので、設定する順序に注意する。
- **投稿の粒度はタスクの間隔 (既定 5 分)**。予約時刻ちょうどではなく最大 5 分遅れる。
  xupload が 5 分間隔で運用して実害が無かった値をそのまま採る。設定で 1〜15 分。

### 4.2 投稿は UI・GPU に一切依存しない

予約時にメディアを**ファイルとして凍結**する (§5.3) ため、投稿の瞬間に必要なのは
「ファイルを読んで HTTP を叩く」だけ。画像は補正・AI・注釈を合成して書き出し、動画と
GIF は元ファイルをそのまま複製する。合成パイプライン (GPU / UI スレッド) は投稿時には
走らない。これは

- 元ファイルが移動・削除・再編集されても予約内容が変わらない
- mIV を一度も起動していなくても投稿できる
- worker が何回起動し直しても同じ結果になる

の 3 つを同時に満たすための中心的な判断。

### 4.3 worker プロセスは「早期分岐」で軽く始める

タスクが 5 分ごとに core を起動するので、**投稿対象が無いときの起動が軽くなければ
ならない**。`--x-post-worker` は [src/lib.rs](../src/lib.rs) の `--pdf-worker` /
`--tensorrt-build` と同じく **GUI 初期化より前**で分岐し、次の 4 つだけを触る:

1. data_dir の解決
2. worker mutex の取得 (取れなければ即終了。§6.5)
3. 投函フォルダの走査と `x_posts.db` への取り込み
4. due があれば `x_credentials.json` を DPAPI で復号して投稿

**`settings.db` は開かない。** 設定 DB には boot decision tree / bak1..bak10 ローテーション /
quarantine があり、5 分ごとに別プロセスから触ると事故の面が増える (2026-07-19 に
実際に main と bak を順に quarantine した前例がある)。worker が必要とする設定
(投函フォルダの場所・猶予時間・連投間隔・単価・上限) は、**GUI が設定を保存するたびに
`x_post_config.json` へ写す**。書き手は GUI だけ、読み手は worker だけにする。

### 4.4 アイドル時に UI を起こさない

GUI 側は**投稿のためのタイマーを持たない**ので、常駐中に定期的に起きる理由が無い。
予約一覧ダイアログを開いている間だけ DB を見る。ここに「念のため 30 秒ごとに DB や
投函フォルダを確認する」を足さないこと。足すと `check-idle-health.ps1` の
static-background / tray-residency シナリオが落ちる (CLAUDE.md リリース手順 Phase 2)。

## 5. データモデル

### 5.1 資格情報 — `x_credentials.json` (DPAPI)

- 保存先は data_dir 直下。`pdf_passwords.json` と同じ DPAPI `Scope::User` 暗号化。
- **`settings.db` には入れない。**設定 DB は bak1..bak10 の世代バックアップを取り、
  診断 zip や設定の書き出しにも乗り得るため、秘密を置く場所として不適切。
- ログ・診断・perf ログ・エラー文言に **key / token / signature を出さない**。

### 5.2 予約キュー — `x_posts.db` (SQLite)

```sql
posts(
  id            TEXT PRIMARY KEY,   -- uuid v4
  created_at    INTEGER,            -- unix ms (UTC)
  scheduled_at  INTEGER,            -- unix ms (UTC)。判定はすべてこれ
  scheduled_local TEXT,             -- 'YYYY-MM-DDTHH:MM' 表示・再編集用の見た目の値
  status        TEXT,               -- §6.2 の状態機械
  claim_owner   TEXT, claim_at INTEGER,
  send_started_at INTEGER,          -- 送信を開始した時刻 (これが入っていたら結果は不明)
  body          TEXT,
  reply_settings TEXT,              -- everyone / following / mentioned
  in_reply_to   TEXT,               -- v1 では常に NULL (連投は非対象)
  attempts      INTEGER, last_error TEXT, last_attempt_at INTEGER,
  posted_at     INTEGER, tweet_id TEXT,
  cost_class    TEXT,               -- plain / with_url (予約時に凍結した判定)
  client_ref    TEXT UNIQUE,        -- 投函フォルダの冪等キー
  source        TEXT                -- ui / inbox
)
media(
  post_id TEXT, ord INTEGER, kind TEXT,  -- image / gif / video
  path TEXT,                             -- staging 配下の凍結済みファイル
  alt_text TEXT, bytes INTEGER, width INTEGER, height INTEGER, duration_ms INTEGER,
  media_id TEXT, media_id_at INTEGER     -- アップロード済み ID と取得時刻 (24h で失効)
)
charges(                                 -- §6.6 の課金台帳
  id INTEGER PRIMARY KEY, at INTEGER, post_id TEXT,
  kind TEXT,                             -- post_create / post_create_url / media_metadata / lookup
  unit_price_micros INTEGER,             -- そのとき設定されていた単価
  note TEXT
)
```

### 5.3 staging — メディアの凍結

- `<data_dir>/x_posts/<id>/1.jpg` …。予約作成時に書き出す。
- 投稿成功 / 取り消し / 期限切れ確定で削除する。孤児の掃除は worker 起動時に 1 回
  (DB に無いディレクトリを消す)。

### 5.4 時刻

判定は UTC epoch。入力・表示はローカル壁時計。変換は Win32 の
`TzSpecificLocalTimeToSystemTime` / `SystemTimeToTzSpecificLocalTime` を使う
(mIV は chrono を持たず、既に Win32 変換で日付を出している)。夏時間のある地域でも
「壁時計で 21:00」が正しく解決される。

**リリース済みではない**ので、実装中のスキーマ変更にマイグレーションは要らない
(CLAUDE.md「永続データ・スキーマ変更時の判断」)。出荷後は必要。

## 6. 投稿の実行 — 二重投稿・二重課金を出さないための設計

**満たす保証は at-most-once。**「必ず 1 回投稿される」は保証しない。ネットワークの
向こうで何が起きたか分からない状況は必ず存在し、そこで**投稿を優先すると二重課金が
起きる**。mIV は迷ったら止まり、人に判断させる。

二重課金の入り口は 4 つある。それぞれに対応する防御を置く。

| # | 二重課金の入り口 | 防御 |
| --- | --- | --- |
| (a) | 投稿は成功したが応答が届かない (タイムアウト / 接続断) | §6.2 の `sending` 状態 + §6.3 の判定表。**自動再送しない** |
| (b) | 投稿後・DB 更新前にプロセスが落ちる / 電源断 | §6.2 の write-ahead + `synchronous=FULL`。起動時に `sending` を見つけたら結果不明として扱う |
| (c) | worker が 2 つ同時に走る | §6.5 の三重の排他 (タスク設定 / mutex / 行 claim) |
| (d) | 何らかのバグで投稿ループに入る | §6.6 の 1 日あたり上限。超えたら止めて通知する |

### 6.1 1 回の worker 起動でやること

1. worker mutex を取る。取れなければ**何もせず終了** (§6.5)。
2. 投函フォルダを取り込む (§8)。
3. `sending` のまま残っている行があれば、**まずそれを解決する** (§6.4)。
   解決するまで、その行に対しては絶対に投稿しない。
4. `status='pending' AND scheduled_at <= now` を古い順に取得。
5. 1 行ずつ `UPDATE ... SET status='claimed' ... WHERE id=? AND status='pending'` で
   claim する。更新行数が 0 なら他が取ったので飛ばす。
6. 期限切れ判定: `now - scheduled_at > 猶予 (既定 6 時間、設定可)` なら投稿せず
   `expired`。**PC が寝ていた後に何日分もまとめて投下しないための安全弁**
   (xupload の `GRACE_HOURS` と同じ理由・同じ既定)。
7. 投稿する (§6.2)。**1 回の起動につき、1 つの予約に対する create 呼び出しは 1 回だけ。**
   同一 run 内での再試行はしない。
8. 溜まっていた場合は次の投稿まで既定 45 秒あける (xupload と同じ)。

### 6.2 1 件を投稿する手順 (write-ahead)

```
claimed
  ├─ メディアを staging から読み、media/upload する      ← 無課金。失敗したら再試行可
  │    成功した media_id は DB に記録する (24h 有効)
  │
  ├─ ★ status='sending', send_started_at=now を DB へ書いて commit する
  │    (synchronous=FULL なので、ここが返ったら電源が落ちても残る)
  │
  ├─ POST /2/tweets を 1 回だけ呼ぶ
  │
  ├─ 明確な成功  → posted (tweet_id を記録) + charges へ 1 行
  ├─ 明確な失敗  → failed または pending (再試行可)。§6.3 の表で決める
  └─ 結果が不明  → needs_review。§6.4 へ
```

**`sending` は「X に届いたかもしれない」という意味**であって、進行中という意味では
ない。worker が起動して `sending` の行を見つけたら、それは
**前回の起動が結果を確認できずに終わった**ということ。無条件に §6.4 へ回す。

### 6.3 応答の分類 — 「明確」と「不明」を分ける

`ureq` の戻り値を、**X が投稿を作った可能性があるか**で分類する。
分類を誤ると二重課金になるので、**迷うものはすべて「不明」に倒す**。

| 応答 | 分類 | 扱い |
| --- | --- | --- |
| 2xx (本文に id) | 成功 | `posted`。課金 1 件を台帳へ |
| 400 / 401 / 403 (duplicate 以外) / 404 / 422 | **明確に未作成** | `failed`。再試行しない (原因が消えるまで叩き続けない) |
| 403 duplicate content | **既に作成済み** | 直前の試行が成功していたということ。§6.4 の照合で tweet_id を拾って `posted` にする。**再送しない** |
| 429 | 明確に未作成 | `x-rate-limit-reset` まで待って `pending` に戻す |
| **5xx** | **不明** | サーバが受け取った後で落ちた可能性がある。`needs_review` → §6.4 |
| タイムアウト / 接続断 / 応答の途中切断 | **不明** | `needs_review` → §6.4 |
| リクエストを送る前のエラー (署名失敗・ファイル読み込み失敗・名前解決失敗) | 明確に未作成 | 再試行可。1 / 5 / 15 / 60 分のバックオフ。猶予窓を超えたら `expired` |

> 5xx を「未作成」に倒したくなるが、倒さない。X が 500 を返す前に投稿を作っていた
> ケースを mIV から区別する方法が無い。**区別できないものを区別したことにしない。**

### 6.4 結果不明の解決 — 推測ではなく照合する

`sending` / `needs_review` の行は、**投稿せずにまず X へ問い合わせて事実を確かめる**。

1. `GET /2/users/me` で自分の user id を取る (初回だけ。以降はキャッシュ)。
2. `GET /2/users/:id/tweets` で直近の投稿を取り、送信開始時刻の前後に
   **本文一致 (空本文ならメディア枚数と時刻)** で該当があるか探す。
   最後に成功した `tweet_id` を `since_id` に使えば取得は少なくて済む。
3. 見つかった → `posted` にして tweet_id を記録する。**再送しない。課金は 1 回のまま。**
4. 見つからない → **それでも自動では再送しない。**`needs_review` のまま残し、
   一覧に「X 側に見つかりませんでした / 最後に確認した時刻」を出して人に選ばせる。
   - 「未投稿として再送する」(押した人が二重投稿のリスクを引き受ける)
   - 「投稿済みにする」(tweet_id を貼る / 貼らない)
   - 「破棄する」

**読み取りにも単価がある**ので、この照合は**結果不明が起きたときだけ**走る。
通常運用では 1 回も呼ばれない。呼んだら台帳 (§6.6) に `lookup` として記録する。

> **なぜ「見つからない」で自動再送しないのか。** X 側の一覧に反映が遅れている可能性を
> 排除できないため。投稿が 1 回飛ぶのは翌日に人が投稿し直せば済むが、二重投稿は
> タイムラインに出てしまい、課金も戻らない。**取り返しがつかない側に倒さない。**

### 6.5 排他 — worker を 2 つ走らせない

三重にする。どれか 1 つでも効けば二重投稿は起きない。

1. **タスク側**: タスクスケジューラのタスクを「**既に実行中なら新しいインスタンスを
   開始しない**」(`MultipleInstances = IgnoreNew`) で作る。
2. **プロセス側**: `Local\mimageviewer-xpost-<data_dir のハッシュ>` の名前付き mutex。
   取れなければ即終了する。GUI の「今すぐ投稿」が同時に走っても衝突しない。
3. **行側**: §6.1-5 の `WHERE status='pending'` 付き 1 行 UPDATE。
   前回の worker がクラッシュして `claimed` のまま残った行は、`claim_at` が
   既定 30 分より古ければ引き継ぐ (`sending` は引き継がず §6.4 へ)。

### 6.6 課金台帳と上限

- **台帳**: 課金対象の API を呼ぶたびに `charges` へ 1 行残す (種別・時刻・post_id・
  そのときの単価)。予約一覧と設定画面から「今日 / 今月の件数と見込み額」を出す。
  見込みではなく**実際に呼んだ回数**なので、万一二重に呼ばれていれば台帳に出る。
- **1 日あたりの投稿上限**: 既定 20 件 / 日 (設定可)。超えたら**投稿せずに止め**、
  理由を残す。解除は人が押す。想定外のループが起きても被害は上限で頭打ちになる。
- 上限に当たった予約は `expired` ではなく `blocked` として残し、解除後に猶予窓の中で
  あれば投稿できるようにする。

### 6.7 気付かせる — 定期実行時のポップアップ

**mIV を起動しない運用が前提**なので、一覧に印を付けるだけでは誰も気付かない。
利用者判断 (2026-09-06) により、**worker が問題を見つけたらその場でポップアップを出す**。
xupload の `alert_tray.py` が pixiv 予約漏れでやっているのと同じ強さの通知にする。

出す条件は `needs_review` / `failed` / `expired` / `blocked` (上限) / 認証エラー。
**成功では出さない。**

**worker 自身がダイアログを出してはいけない。**モーダルが返るまでプロセスが生き、
タスクは「実行中」のままになる。タスクは `IgnoreNew` (§6.5) なので、
**次以降の 5 分ごとの実行が全部スキップされ、投稿が黙って止まる**。

そこで:

1. worker は投稿処理を終え、**mutex を解放してから**、
   `mimageviewer.exe --x-post-notify` を **detached で spawn して自分は終了する**。
   タスクのインスタンスはここで終わるので、次の実行は普通に来る。
2. 通知プロセスは `MessageBoxW` を 1 つ出すだけ (`MB_ICONWARNING | MB_TOPMOST |
   MB_SETFOREGROUND`)。egui も wgpu も使わないので軽く、GUI が動いていなくても出せる。
3. **1 通ずつ出さない。**「投稿できなかった予約が N 件あります」と件数でまとめる。
   通知プロセスも専用 mutex を持ち、同時に 2 つ出ない。
4. ボタンは「mIV を開いて対処」/「あとで」。前者は `--x-post-review` で mIV を起動し、
   予約一覧を該当行で開く。
5. **再通知**: 新しく発生したときは即時。未解決のまま残っている間は既定 60 分ごとに
   出し直す。「あとで」はその間隔ぶん黙る。`notified_at` / `snooze_until` を DB に持つ。
   **未解決を永久に黙らせる出口は作らない** (解決するか破棄するかしかない)。
6. 併せて `<inbox>/needs_review/<id>.txt` にも書き出す。外部ツール
   (xupload の `alert_tray.py` 等) から機械的に拾えるようにするため。ポップアップが
   主で、こちらは記録。

> **実機で確かめること**: Windows のフォアグラウンド奪取制限により、背面プロセスからの
> `MB_SETFOREGROUND` はタスクバーの点滅止まりになることがある。`MB_TOPMOST` で
> 最前面には出るはずだが、**全画面のゲームや動画の上でどう見えるかは実測する**。

### 6.8 テスト

P1〜P2 は UI を持たないので、**偽トランスポートを差した単体テストで全経路を固める**。
最低限、次を落とせるテストを書く (CLAUDE.md「状態バグには状態遷移テスト」)。

- 応答不明 → `needs_review` になり、**次の run で create が呼ばれない**
- `sending` のまま起動 → create ではなく照合が走る
- 照合で見つかる → `posted` になり、create が **1 回も呼ばれない**
- 照合で見つからない → 自動再送しない
- 403 duplicate → 再送せず照合へ行く
- 5xx → 「未作成」ではなく「不明」になる
- claim 競合 → 2 つ目の worker が同じ行を投稿しない
- 1 日上限 → 超えた分が投稿されない
- 電源断相当 (commit 後にプロセスを殺す) → 起動後に `sending` が残っている
- 通知が要る状態になっても、**worker プロセスはブロックせずに終了する** (§6.7)
- 未解決のまま 60 分経つと再通知される / 「あとで」の間は出ない

## 7. 作成 UI

### 7.1 導線

- フルスクリーンの現在ページ、またはグリッドの選択 (1〜4 件) から
  「**X に投稿 / 予約**」。
- **SNS 分割書き出しからの連携**: 分割した N 枚をそのまま添付して開く
  ([sns-split-export-plan.md](sns-split-export-plan.md) の出口)。分割はもともと X の
  カルーセルのために作った機能なので、ここが最も自然な入口になる。
- `KeyAction` を足す (既定割り当てなし。ボタン / メニューが入口)。
  `ini_name()` / `context()` / `trigger()` / `default_chords()` / `ALL_ACTIONS` /
  [keymap.ini.default](keymap.ini.default) を揃える。

### 7.2 ダイアログの中身

- 本文 (複数行。**IME 対応必須** — `dialog_enter_pressed` / `dialog_escape_pressed` と
  `ime_focus` helper 経由の TextEdit。生 TextEdit は unit test で禁止されている)
- 添付 (並べ替え・削除・alt text)
- 投稿時刻 (日付 + 時刻。「今すぐ」「30 分後」「明日 9:00」などのクイック指定)
- 返信可能範囲 (everyone / following / mentioned)
- **文字数**: X の重み付き文字数 (ASCII = 1、日本語 = 2、URL は長さに関係なく 23)。
  上限を超えたら予約ボタンを無効化し、理由を出す。上限は既定 280 で、設定で伸ばせる
  (X Premium の長文投稿用)。**既定を伸ばさない** — Premium 未契約の利用者が投稿時に
  弾かれるほうが害が大きい。
- **費用**: URL を含むかどうかで単価表示を変える。alt text を付けた枚数分の
  Media Metadata も足す。今日の残り枠 (§6.6) も併記する。

### 7.3 プレビュー

- アバター / 表示名 / @handle / 時刻 / 本文 / メディア / 反応アイコン (灰色) の
  カードを描く。プロフィールは設定画面の「アカウント情報を取得」ボタンを押した
  ときだけ API から取得してキャッシュする (勝手に課金対象の API を叩かない)。
- メディアの並びは [sns-split-export-plan.md](sns-split-export-plan.md) §2.1 の実測に
  従う。**2 枚以上はカルーセル** (1 枚目の全体 + 2 枚目の 3/4 が見える)。旧来の
  2x2 グリッドで描かない。継ぎ目比は 1.7 % を既定にする。
- 本文の折り返し・リンク色・ハッシュタグ色を再現する。
- **「これで必ずこう見える」と書かない。**環境ごとに隙間も幅も違う (同 §2.1)。
  プレビューは構図と文字数の確認用であって校正用ではない、と UI に明記する。

## 8. 投函フォルダ — 外部ツールからの予約

HTTP のローカル API は**やめた** (2026-09-06、利用者判断)。フォルダに置くだけなら
listener もポートも token も要らず、**mIV が起動していなくても予約を積める**。
xupload は既に「フォルダにファイルを置く」ことで予約している (`images/` へ
`YYYYMMDD_HHMM.png` を置く) ので、移行の形も自然になる。

### 8.1 置き場所と形式

```
<data_dir>/x_inbox/            ← 既定。設定で変更できる
    2026-09-10-morning.json    ← ★ mIV が読むのは直下の *.json だけ
    2026-09-10-morning.png     ← manifest から相対で参照できる
  accepted/                    ← 取り込んだ manifest + <name>.result.json
  rejected/                    ← 受け付けられなかった manifest + <name>.error.json
```

manifest (`*.json`, UTF-8):

```json
{
  "client_ref": "xupload:20260910_0930",
  "scheduled_at": "2026-09-10T09:30:00+09:00",
  "body": "本文",
  "media": [
    { "path": "2026-09-10-morning.png", "alt_text": null }
  ],
  "reply_settings": "everyone"
}
```

- `scheduled_at` は**オフセット付きの ISO 8601**。オフセット無しはローカル時刻と
  みなす。`"now"` を許す。
- `media[].path` は manifest からの相対 / 絶対のどちらでもよい。
- `client_ref` は**冪等キー**。同じ値の manifest を再度置いても予約は増えず、
  既存の予約の id が結果に返る。省略時は manifest の内容ハッシュを使う。

### 8.2 書き込みの約束 (これを守らないと壊れる)

1. **メディアを先に、完全に書き終える。**
2. **manifest は別名で書いてから `*.json` へ rename する** (`os.replace` / NTFS の
   rename は原子的)。mIV は `*.json` しか読まないので、書きかけを拾わない。
3. rename 後は manifest を触らない。

> **なぜファイル名に時刻を埋める方式 (`20260910_0930.png`) にしないのか。**
> 4 枚添付・alt text・動画・返信範囲・冪等キーを表現できないため。形式を 2 つ
> 持つと「予約とは何か」の綴りが 2 つになる。manifest 1 本に統一する。

### 8.3 取り込み — 投函フォルダは入り口であってキューではない

- 取り込むのは **worker だけ** (§4.1)。GUI は投函フォルダを監視しない
  (§4.4 のとおり、アイドル時に起きる理由を作らない)。予約一覧には
  「取り込み待ち N 件」を出し、「いま取り込む」ボタンで worker を spawn する。
- 取り込みは `<inbox>/processing/<uuid>/` への **rename で claim** する。
  rename に失敗したら他が取ったということなので飛ばす。
- 取り込みが終わったら DB に行ができ、メディアは staging へ凍結される (§5.3)。
  以降その予約の真実は DB だけにあり、投函フォルダ側を書き換えても影響しない。
- 結果は `accepted/<name>.result.json` に書く:
  `{ "id": "...", "status": "pending", "warnings": ["url_detected"], "estimated_cost_usd": 0.2 }`。
  受け付けられなかったものは `rejected/` へ理由付きで移す (時刻が過去すぎる /
  メディアが見つからない / 枚数が多い / 文字数超過 / 混在添付)。
- `accepted/` / `rejected/` は既定 30 日で自動削除する。

### 8.4 権限の境界

**この投函フォルダに書ける人は、利用者の X アカウントで投稿できる。**
既定の場所は data_dir 配下 (利用者スコープ) なので通常は問題ないが、
**共有フォルダやネットワークドライブを指定してはいけない**ことを設定画面と
マニュアルに明記する。ポータブル版で data_dir が USB 上にある場合も同じ注意が要る。

### 8.5 xupload の移行

現在の xupload editor は「`images/YYYYMMDD_HHMM.png` へリネームして `.txt` を書く」
ことが予約。移行後は **manifest を 1 つ書くだけ**にし、`post_worker.py` は撤去できる。
`client_ref` を `xupload:<stem>` にしておけば、再実行しても二重登録されない。

## 9. タスクスケジューラ・常駐・OS 自動起動

### 9.1 タスクスケジューラへの登録 (投稿の実行主体)

- タスクは **1 件だけ**。名前は `mImageViewer X 予約投稿` のように、一覧で見て
  何か分かる名前にする。**予約ごとにタスクを作らない。**
- トリガ: ログオン時 + **5 分間隔で無期限に繰り返す**。「ログオンしているときのみ実行」。
  最上位の特権は不要。**多重起動しない** (`IgnoreNew`、§6.5)。
- 実行するコマンドは **launcher (`mimageviewer.exe`) + `--x-post-worker`**。
  `%APPDATA%\mimageviewer\runtime\<version>\mimageviewer-core.exe` を直接登録すると
  **更新のたびにパスが変わって壊れる**。launcher のパスはインストール先で安定している。
  - launcher 側に 1 点だけ手を入れる: `--x-post-worker` が付いているときは
    `try_activate_existing` (= 既存インスタンスを前面に出す) を**しない**。
    ここを直さないと、mIV が起動中はタスクがウィンドウを前面に出すだけで終わる。
  - ポータブル版は launcher を使わず core が `mimageviewer.exe` なので、そのまま登録できる。
- 登録・解除は **利用者の明示操作 (設定のチェックボックス)** でだけ行う。
  GUI 起動時に「登録済みタスクの実行パスが現在の exe と違う」場合だけ黙って直す
  (インストール先変更・ポータブルの移動への自己修復)。
- 実装は Task Scheduler の COM API (`ITaskService`、windows crate の
  `Win32_System_TaskScheduler`)。`schtasks.exe` を叩くとコンソールが一瞬出る。

> **注意**: 「自分自身を定期起動するタスクを作るプログラム」は AV のヒューリスティクスと
> 相性が悪い。mIV は既にポータブル版で AV 誤検知を踏んでいる。緩和は
> ①配布 PE は全て Authenticode 署名済み ②利用者の明示操作でしか作らない
> ③名前と実行コマンドを一覧で読める形にする、の 3 点。**無言で作らないこと**が一番効く。

### 9.2 常駐は不要になった

投稿はタスク、予約の受け口は投函フォルダなので、**この機能のために mIV を常駐させる
必要は無い**。当初の要望にあった「予約機能を使うなら常駐させる」は、投函フォルダに
した時点で前提ごと消えている。設定画面で常駐を促さない。

### 9.3 OS 起動時の自動起動 (最小化)

**この機能の前提ではなくなったが、独立した要望として実装する。**

- `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` に値を作る。管理者権限不要。
  設定 ON/OFF がそのまま値の作成 / 削除。
- **登録するパスは launcher (`mimageviewer.exe`)**。理由は §9.1 と同じ。
- ポータブル版はフォルダごと移動され得るので、登録時のパスが消えていたら設定画面に
  「登録先が見つかりません」と出して再登録を促す。
- 起動引数 `--start-minimized`: ウィンドウを表示せずトレイへ入る。

**実装上の risk**: 「最初から非表示で起動する」は、この codebase で過去に実害が出た
**サーフェス無しフレーム**の状態そのもの
([tray-residency-cpu-spin-investigation.md](tray-residency-cpu-spin-investigation.md)、
および FS 終了直後の no-surface フレームでテクスチャアップロードを捨てて黒く固着した
v1.8.0 の回帰)。`ViewportBuilder::with_visible(false)` で起動したときに

- テクスチャアップロードが捨てられて黒くならないか
- repaint が来ず初期化が進まないまま止まらないか
- 逆に repaint を回し続けて CPU を食わないか

を `check-idle-health.ps1 -Scenario static-background` / `tray-residency` で確認する。
**ここは設計より実測が先**で、成立しないなら「一瞬表示してから畳む」に落とす。

## 10. 設定項目 (案)

環境設定に新ページ `XPost` を足す。`Startup` ページには自動起動を足す。

| 設定 | 既定 | 備考 |
| --- | --- | --- |
| X 予約投稿を使う | OFF | これが OFF なら UI もタスクも投函フォルダも動かない |

## 11. 非対象

| やらないこと | 理由 |
| --- | --- |
| **pixiv 対応** | §11.1。**X 専用として作る** |
| ローカル HTTP API | 投函フォルダで足りる (§8)。listener / port / token を増やさない |
| OAuth 2.0 のブラウザ認可フロー | 利用者が Portal でキーを取る前提。リダイレクト受けの口を増やさない |
| 予約を X 側へ登録する | §2.1 のとおり不可能 |
| 連投 (スレッド) | v1 では作らない。DB は `in_reply_to` の列だけ空けておく |
| 投稿の閲覧・返信・DM・分析 | ビューアの範囲を超える。読み取りは §6.4 の照合だけ |
| 複数アカウントの切り替え | v1 は 1 アカウント |
| リモート (mIV Remote) からの予約 | 認証境界が違う。要望が出たら別途設計 |
| 「必ず 1 回投稿される」保証 | §6 のとおり原理的に不可能。at-most-once を選ぶ |

### 11.1 pixiv — 検討して見送った記録 (2026-09-06)

「投稿画面を開いて画像をアップロードするところまでで、実際の投稿操作は利用者に
委ねる形なら成立するか」を検討し、**見送りに決めた** (利用者判断)。次に誰かが
同じことを思い付いたときのために理由を残す。

- pixiv 利用規約 (policies.pixiv.net) を読んだ範囲では、**自動化されたプログラムに
  よるアクセスを名指しで一律に禁じる条項は見つからなかった。**近いのは
  「サーバーに負担をかける行為」「不正な操作」「その他不適切と判断する行為」と、
  登録商標ガイドラインの「クローラーで**作品を収集する**行為の禁止」。
- それでも載せない理由は、規約の解釈ではなく**コードが実際に何をするか**:
  1. pixiv の投稿画面は**ファイルを選んだ時点でサーバーへ送る**。最後の 1 クリックが
     人でも、その前の通信はプログラムが起こしている。「フォームを埋めるだけ」ではない。
  2. ファイル input は JS から設定できないので、CDP か WebView2 で**ブラウザを駆動**
     することになる。後者は **mIV が pixiv のログイン Cookie を抱える**ことを意味し、
     privacy.html に「mIV は閲覧サイトのセッションを持たない」と書ける状態を捨てる。
  3. 投稿画面の DOM は pixiv 側の都合で変わる。配布物だと壊れるたびに mIV の不具合に
     なる。
  4. 個人スクリプトなら自分のアカウントの自己責任だが、配布物だと mIV の名前で
     不特定多数が同じ挙動をする。
- **画像を書き出してブラウザで投稿ページを開くだけ**の「下ごしらえ」案も出たが、
  X 専用として作ることに決めたので入れない。必要になれば独立した機能として起こす。

## 12. 段階分け

実装順序は利用者から「お任せ」(2026-09-06)。**投稿経路を先に実運用へ載せる**順にする。
xupload が既に毎日投稿しているので、早い段階で本物の運用に晒したほうがバグが出る。

| Phase | 内容 | 規模 |
| --- | --- | --- |
| **P1** | OAuth 1.0a 署名 + `ureq` クライアント + DPAPI 資格情報 + 設定ページ + 接続確認 | M |
| **P2** | `x_posts.db` + `--x-post-worker` + **§6 の全部** (状態機械 / 分類 / 照合 / 排他 / 台帳 / 上限 / ポップアップ通知) + 画像投稿 | L |
| **P3** | タスクスケジューラ登録 / 解除 / 自己修復 (§9.1) | S |
| **P4** | 投函フォルダの取り込み + 結果ファイル + **xupload の実運用切り替え** | M |
| **P5** | 作成ダイアログ + 文字数 + 費用警告 + staging 焼き込み | L |
| **P6** | プレビュー (カード / カルーセル / リンク色) | M |
| **P7** | 予約一覧・履歴・課金台帳ダイアログ + `needs_review` の解決 UI | M |
| **P8** | 動画 / GIF 添付 (chunked upload + 変換待ち) + 長文投稿 | M〜L |
| **P9** | OS 自動起動 + `--start-minimized` + idle health 実測 | M |
| **P10** | 文書 (§15) | S |

**P2 が本体。**ここを偽トランスポートで固めきってから先へ進む (§6.8)。
通知 (§6.7) も P2 に入れるので、P4 で実運用へ載せた時点で「失敗に気付けない」状態には
ならない。ただし P7 の解決 UI が入るまで、`needs_review` の解決手段は
DB を直接直すか破棄するかしかない。

## 13. 守る不変条件

1. **at-most-once。**結果が不明な送信を自動で再送しない (§6.3 / §6.4)。
2. **区別できないものを区別したことにしない。**5xx もタイムアウトも「不明」に倒す。
3. **投稿する主体は 1 つ** (`--x-post-worker`)。GUI に 2 本目の投稿経路を作らない。
4. **送信の意図は送信前に永続化する** (`sending` + `synchronous=FULL`)。
5. **投稿は UI / GPU に依存しない** (§4.2)。
6. **課金対象の呼び出しは必ず台帳に残す** (§6.6)。上限を超えたら止まる。
7. **失敗は黙らせない。**未解決の状態を永久に消せる出口を作らない (§6.7)。
   通知のためにタスクの実行を止めない (worker はブロックしない)。
8. **秘密は出さない**。ログ・診断 zip・perf ログ・エラー文言のどこにも
   key / token / signature を出さない (§5.1)。
9. **アイドル時に UI を起こさない** (§4.4)。リリース前に idle health で確認する。
10. **既定はすべて OFF**。有効化は明示操作。
11. **単価を断定しない**。設定値として持ち、変わり得ることを明記する。

## 14. 決定済み / 未決

### 決定済み

1. 実装は **core 内**。新しい exe を作らない (§3)。
2. メディアは **予約時に焼き込んで凍結**する (§4.2)。
3. 資格情報は **DPAPI**。`settings.db` に入れない (§5.1)。
4. 真実は **`x_posts.db` 1 つ**。投函フォルダは入り口であってキューではない (§8.3)。
5. **投稿するのは `--x-post-worker` の一発プロセスだけ**。GUI は投稿経路を持たない。
6. **配布範囲 = 既定 OFF の上級者向けとして配布する** (2026-09-06)。
   マニュアル・privacy.html・製品ページの更新が必須 (§15)。X Developer Portal での
   取得手順と「**課金は利用者の X アカウントに発生する**」を明記する。
7. **不在時の保証 = タスクスケジューラ主体**。常駐は前提にしない (§9.1 / §9.2)。
8. **v1 の投稿形式 = 画像 1〜4 枚 / 動画 1 / アニメ GIF 1 / 長文投稿 (X Premium)**。
   長文は上限を設定で伸ばせるようにし、既定は 280 のまま。連投 (スレッド) は作らない。
9. **pixiv は対象外。X 専用として作る** (2026-09-06、§11.1)。
10. **予約の受け口は投函フォルダ。ローカル HTTP API は作らない** (2026-09-06、§8)。
11. **at-most-once を選ぶ。**「必ず投稿される」より「二重に課金されない」を優先する
    (2026-09-06、§6)。
12. **失敗は定期実行時のポップアップで知らせる** (2026-09-06、§6.7)。一覧の印だけに
    しない。ただし **worker はブロックしない** — 別プロセスへ出す。

### 未決

1. **プロフィール取得**: 表示名 / @handle / アバターを API から取ってプレビューに
   使うか、設定に手入力させるか。取得は課金対象の API を 1 回叩く。
   → 現案は「設定画面のボタンを押したときだけ取得してキャッシュ」。
2. **P1 で実費を測る** (§2.5)。①メディアアップロードが本当に無課金か
   ②照合の読み取りが見込みどおりか。**通常の投稿と混ぜず、切り分けて測る。**
   結果が違ったら §6 の再試行方針を見直す。
3. 動画の**先行アップロード**をするか。`media_id` は 24 時間有効なので、24 時間以内の
   予約なら変換を先に済ませておける。v1 は投稿直前アップロードで始める。
