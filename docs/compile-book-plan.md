# 製本機能 (ページ収集 → 順序つき複製) 実装計画

ステータス: **v1.7.0 初期実装済み / 操作感調整前** — 起案 2026-06-15、実装 2026-06-15
(`src/books.rs`、`src/ui_main.rs`、`src/ui_fullscreen.rs`、`src/app.rs`、索引 walker/supervisor、
`docs/keymap.ini.default`)

## 実装メモ (v1.7.0)

- 製本ルートは設定可能で、既定は `Pictures\mimageviewer\books`。`Settings.book_root` が
  `None` のときは既定を使い、追加先は `Settings.active_book_name` で保持する。
- 本は製本ルート直下の通常フォルダとして扱い、ページは `0001_元名.ext` の 4 桁連番で保存する。
  1 冊 9999 ページを上限とし、グリッド追加では通常画像は byte コピー、ZIP 内画像は格納 bytes
  抽出を最優先する。焼き込むべき補正や非破壊回転がある場合だけ worker で decode + encode し、
  PDF/動画/フルスクリーン表示結果の焼き込みは既存のキャプチャ/エクスポート系の画素経路で保存する。
- UI は上部メニュー「製本」に追加した。本棚フォルダを開く、アクティブ本を開く、追加先の切替、
  本の作成/改名/削除、現在の本の並べ替えを提供する。追加ショートカットはグリッド/画像/
  動画コンテキストで `Ctrl+B` (`GridAddToActiveBook` / `FsAddToActiveBook` /
  `VideoAddToActiveBook`)。
- 並べ替えは専用ダイアログで、小サムネイル敷き詰め + ホバー拡大プレビュー + 専用サーフェス内
  drag 並べ替えを提供する。ドラッグ中は挿入位置に I 字型インジケータを描画し、左右移動ボタンと
  サムネイルサイズ調整も備える。保存して閉じる時だけ 2 パス temp rename でファイル名へフラッシュし、
  編集を破棄する場合は確認してからメモリ上の順序だけを捨てる。
- 製本ルートは Ctrl+G アイテム索引と Ctrl+S コンテナ索引の自動スキャン対象外。初期スキャンは
  既存の残留行を削除候補に落とし、watcher 差分は本棚配下の投入をスキップする。
- 本ページは確定スナップショットとして扱い、タグ/★/回転/補正/消しゴム/隠蔽/テキスト/切り取り
  などの編集入口を抑制する。絞り込みは通常の現在地フィルタ/ツールバー絞り込みで行う。
- 本フォルダ閲覧中はソート UI を無効化し、ページ順は常に番号順に固定する。手動で混入した
  ZIP/PDF/フォルダ/動画など、画像以外の項目は本ページとして表示しない。

## 0. 背景と目的

2026-06 の競合分析 (NeeView パリティ監査) で確定した「mIV に無い本物のギャップ」の一つ。
NeeView の**プレイリスト (ブック横断でページを集めて 1 冊として読める)** に相当する機能が
mIV には無い。mIV のお気に入り / タグ / ★ は **コンテナ / ファイル単位**であり、「複数の本・
フォルダから**ページだけ**を**任意順**で集めた束」を作る手段が存在しない。

本機能は NeeView 型の**参照型プレイリストではなく**、**「その時点で画像を複製して任意順に
並べ、1 冊にまとめる "製本"」= コピー型スナップショット**として作る (理由 §1)。

### 想定ユースケース
- **作画資料・ポーズ集**: 複数の本から「この構図」というページだけ抜いて参照束に
- **名シーン集**: 複数巻からページだけ集めて通し読み
- **AI 生成画像のキュレーション**: 大量生成から採用候補をプロジェクト別の束で管理
  (mIV の AI 整理ニッチと特に相性が良い)
- **選別作業**: 似た画像を束にして並べ替えながら取捨選択

## 1. 参照型を採らずコピー型にする理由

| | 参照型 (NeeView 方式) | **コピー型 (本計画)** |
| --- | --- | --- |
| 元ファイル削除/移動 | リンク切れ | **無傷** (独立) |
| ディスク | 消費しない | 複製分を消費 |
| 元の内容更新の反映 | 追従 | しない (= スナップショットなので正しい) |
| ZIP/PDF ページ | 「書庫パス+ページ番号」参照は壊れやすい | **複製済みなので一律に扱える** |
| 他ツール (Explorer/zip) での持ち出し | 参照は持ち出せない | **フォルダごとコピー/圧縮で完結** |

AI 採用候補で**残りを捨てる**、資料集として**長く残す**といった主要用途では、元を消しても
束が生き残るコピー型が決定的に優位。

## 2. 中核の設計判断: 束 = ただのフォルダ、ページ順 = ファイル名の番号 (正本)

ユーザー要件「**Explorer で見たり、フォルダを圧縮して移動してもページ順が保たれること。
そのために専用機能を呼ぶのは使い勝手が悪い**」を最優先する。したがって:

- **本の実体は、設定したルート下の「ただのフォルダ」**。中に複製された画像ファイルがあるだけ。
  mIV をアンインストールしても画像は普通に残り、Explorer / 他ビューア / zip でそのまま扱える。
- **ページ順は「ゼロ埋め番号プレフィックス付きファイル名」が正本**
  (例 `0010_元名.jpg`)。番号順 = ファイル名順 = ページ順。**専用機能なしで Explorer も
  圧縮後も順序が自明**。元のファイル名は番号の後ろに残して来歴の手がかりにする
  (ユーザー要望「元名をある程度保持」)。
- **並べ替え = ファイルのリネーム**。サイドカーに順序を持つ案 (旧案) は、Explorer/zip で
  順序が失われるため**不採用**。

### 2.1 リネーム方式の妥当性 (実測済み 2026-06-15)
「並べ替えのたびに大量リネームでは遅いのでは」という懸念を実測で否定した
(NTFS / Defender 有効 / SSD):

| ケース | リネーム回数 | 時間 |
| --- | --- | --- |
| 先頭挿入 (全体を 1 つシフト) | 1000 | **315 ms** |
| 任意並べ替えの最悪ケース (全反転・衝突回避 2 パス) | 2000 | **569 ms** |

= 1 リネーム約 0.3ms。**1000 ページの最悪ケースでも 0.6 秒未満**で、意図的な並べ替え操作
としては許容範囲。HDD では数倍になり得る。

**1 冊の上限 = 9999 ページ (4 桁連番、2026-06-15 確定)**。ファイル名は **4 桁ゼロ埋め連番 + 元名**
(`0001_元名.jpg`)。10000 ページ目を追加しようとすると**エラーで拒否**する。根拠: 4 桁の素直さ +
10000 ページ規模では並べ替え時のリネーム/ドラッグ負荷が実用域を超える (1000≈0.6秒 → 10000≈
数〜10 秒)。漫画/資料/キュレーション用途では 9999 で十分。

### 2.2 編集中はメモリ上の順序、ディスクのリネームは遅延フラッシュ (2026-06-15 確定)
実利用は「挿入は稀、並べ替えは複数ファイルを何度もドラッグ」。よって**ドラッグ中は
ディスクをリネームしない**:
- **編集中はメモリ上の順序モデルだけ更新** (= ファイル名順を一時的に上書きする「未保存
  バッファ」的状態)。インタラクティブな並べ替えは**ディスク操作ゼロ**で軽快。
- **フラッシュ (実ファイル名への一括リネーム) のトリガは、並べ替え専用モード (§7.1) の
  「保存して閉じる」を押したときだけ**。並べ替えは専用モード内でしか起きないので、通常ビューでの
  idle デバウンス監視は不要 = 単純化 (2026-06-15)。フラッシュは §2.1 実測どおり 1000 ページでも
  0.6 秒未満をバックグラウンドで 1 回 (HDD/大型本は進捗表示)。
- 未保存の並べ替えは「編集を破棄」で確認後に捨てる。アプリ終了時に黙って保存する保険フラッシュは
  行わず、終了時も未保存のメモリ順序は破棄される (明示保存モデルを優先)。
- ファイル名は **4 桁ゼロ埋め連番 + 元名** (`0001_元名.jpg`)。フラッシュ時に `0001..` へ
  連番で振り直す。
- **gap 番号 (間隔番号) はこの方式では必須ではない** (毎ドラッグでディスクを触らないため)。
  必要なら将来の最適化として残す。

**フラッシュの安全策** (要実装):
- **2 パス (全 temp 名 → 全 final 名) で中断耐性**を持たせる。フラッシュ前にクラッシュ/
  強制終了した場合、並べ替えは失われるがファイル名は前回コミット状態で無傷 (低リスク・許容)。
- フラッシュ中は対象フォルダの**監視を一時停止** ([§5](#5-リネーム時の自フォルダ監視の扱い-miv-固有の注意))。
- フラッシュ完了まではメモリ順序を正として表示し、完了後に 1 回だけ再読込。

### 2.3 本の置き場所と仮想表示 (2026-06-15 確定)
- **既定は全ビルド共通で `ピクチャ\mimageviewer\books`** (installer / 単体exe / portable すべて)。
  ユーザー設定で変更可。
  - **portable も exe 配下にせず Pictures にする** (2026-06-15 ユーザー判断)。理由: (1) mIV の
    既存のキャプチャ/エクスポート既定が**全ビルドで `Pictures\mimageviewer`** であり、ここを
    portable だけ別扱いにすると**リリース済み動作を変える**ことになり、既存 portable ユーザーの
    出力先が途中で変わって不便。(2) Pictures は配布形態に依存しない per-user の既知フォルダで
    非 APPDATA = 当初懸念 (隠れ場所/Roaming 同期/C 圧迫) を満たす。(3) 全ビルド同一でルール最小。
  - **キャプチャ/エクスポートの既定は現状維持** (= ビルド非依存 `Pictures\mimageviewer`)。
    [src/capture.rs](../src/capture.rs) `default_output_dir()` を変更しない。本ルートはその
    サブフォルダ `…\mimageviewer\books` とし、既存出力と同じ場所に綺麗に収まる。
  - **トレードオフ (許容済み)**: portable のフォルダを USB 等で持ち運んでも、本は Pictures に
    残り**一緒には移動しない**。これはルート設定可能で吸収する (持ち運びたい portable ユーザーは
    ルートを `<exe_dir>\books` に手動設定すればよい)。既定の単純さを優先。
- **`%APPDATA%` (Roaming) 直下を既定にしない**: 再生成不能なユーザーコンテンツを (a) 隠し場所で
  バックアップ漏れ、(b) Roaming 同期で大容量画像が同期対象、(c) C 圧迫、になる場所に置かない。
- **mIV 内の表示は「本棚 > 本名」の仮想ネームスペース** (検索結果の集約ビューやドライブ一覧と
  同じ流儀)。右クリック「フォルダの場所を開く」で実体 (既定 Pictures 配下) を Explorer 表示。
- 束は実フォルダなので、**仮想レイヤーとは別に通常のフォルダ閲覧でも到達できる** (仮想表示は
  便利ショートカットであって唯一の入口ではない = 堅牢)。

### 2.4 本の識別と索引スコープ: サイドカーなし・場所ベース・索引対象外 (2026-06-15 確定)
**マーカー / サイドカーファイルは置かない。本 = 番号付き画像ファイルだけの純粋なフォルダ**。
- **本の識別は「場所ベース」**: 製本ルート (既定 `Pictures\mimageviewer\books`) の**直下の各
  フォルダを本とみなす**。`.mivbook` 等のマーカーファイルは使わない。
  - マーカー方式を**不採用**にした理由 (ユーザー判断): (a) マーカーが付いた本を移動すると別の
    場所でも本として振る舞い、ユーザーが戸惑う、(b) **ZIP 化したときマーカーがゴミになる**。
  - 場所ベースの帰結: 本をルート外へ移動すると mIV 上は**通常フォルダ扱い**になる (= 本 UI の
    アフォーダンスは外れるが、ファイル名が順序を持つので**通常の画像フォルダとして無傷**)。
    再び本として扱いたければルート配下に戻す。これは許容する。
- **追加順ビューは設けない** (2026-06-15、要望の優先度を再評価): 通常は末尾追加なので
  **ページ順 ≒ 追加順**であり (並べ替えるまで一致)、わざわざサイドカーで追加順を別管理する価値が
  低い。サイドカーは ZIP/移動でゴミ化する難点もあるため持たない。**来歴 (どの ZIP の何ページ目
  から来たか) も持たない** (サイドカー前提だったため)。将来どうしても来歴が欲しくなったら、
  サイドカーではなく複製画像の XMP に源泉を書く案がある (ただし無加工 byte コピーとは両立しない
  ので、その時に再検討)。
- **本フォルダは検索インデックス対象外** (§下記):

#### 索引・メタデータのスコープ (2026-06-15 確定)
- **本フォルダは自動インデックス (Ctrl+G グローバル全文検索) の対象にしない**。
  - 理由 (性能): **遅延フラッシュで大量リネームが走るため、索引対象だと 1 リネームごとに
    「旧パス削除 + 新パス追加」の索引チャーンが数千件発生**して重い。索引から外せばこの問題が
    そもそも起きない (ユーザー指摘どおり)。コピー済みページの二重索引も避けられる。
- 本の中での絞り込みは **Ctrl+F (現在地フィルタ) / 絞り込みツールバー**で行う (現在グリッドの
  in-memory 判定なので**索引不要**。ファイル名・日付・サイズ等で絞れる)。
- 本ページには**タグ / ★ / 非破壊回転も付けない** (§2.5 の「本は確定スナップショット」と一貫。
  閲覧・並べ替え・削除・フィルタのみ)。これらが要るなら本にする前の元データ側で行う。

### 2.5 本は「確定済み」: 本棚内では編集不可、補正は複製時に焼き込む (2026-06-15 確定)
本 = **確定したピクセルのスナップショット**とする設計原則:
- **本棚フォルダ内では補正・補正レイヤー・隠蔽・テキスト注釈・AI 等の編集機能を一切出さない**
  (閲覧・並べ替え・削除のみ)。
- **追加時に編集を焼き込む**: ページ追加の瞬間に、その元ページで補正等がアクティブなら
  **結果ピクセルを焼き込んで複製**する。本に入った後から編集し直す必要をなくす
  (= 非破壊レイヤーを本側で持たない)。
- メリット: (1) **ホバー時のサムネ/プレビューが必ず短時間で表示できる** (補正パイプラインを
  通さず、焼き込み済みピクセルを読むだけ)。(2) 「本 = 完成物」という単純な心的モデル。
  (3) 並べ替え専用モード (§7.1) のプレビューも常に高速。

## 3. 既存資産との接続 (実装は薄く済む見込み)

| 必要な処理 | 流用元 |
| --- | --- |
| ページ画素の取得 (通常画像 / ZIP 内 / PDF) | 既存の `export_page_pixels_for_idx` 系 (Ctrl+E export と同じ経路) |
| 動画の現在フレーム取得 | 既存のフレームキャプチャ ([src/capture.rs](../src/capture.rs)、Ctrl+S 相当) |
| エンコード + 保存 (JPEG/PNG/WebP、メタ保持) | `save_with_metadata::save_image_with_metadata` / [src/export_dialog.rs](../src/export_dialog.rs) |
| ファイルコピー (通常画像を無加工複製する場合) | シェルファイル操作 ([src/shell_file_ops.rs](../src/shell_file_ops.rs)) / worker パターン |
| フォルダ=グリッド表示・見開き・通し読み | 既存グリッド (束は**ただの実フォルダ**なので追加実装ほぼ不要) |
| 重い I/O を UI スレッドから外す | 既存の worker + mpsc + cancel ([docs/ui-responsiveness.md](ui-responsiveness.md)) |

**複製方法の分岐 (2026-06-15 確定: 無加工コピー最優先、エンコードは最小限)**。
**判定順**: まず「元ページに焼き込むべきアクティブな編集 (補正/回転/補正レイヤー/隠蔽/注釈/AI) が
あるか」を見る。**あれば §2.5 に従い (3) のエンコード経路で焼き込む** (byte コピーより優先)。
ただしグリッドからの単純追加では、実効カラー補正が恒等かつ非破壊回転も無ければ「焼き込むものなし」とみなし、
通常画像は元ファイルを byte コピー、ZIP 内画像は格納 bytes 抽出を維持する。グローバル/標準/
ページ個別のカラー補正が非恒等、または非破壊回転があるときだけ worker で decode + 補正/回転適用 + encode する。
無ければ:
1. **ディスク上の標準画像ファイル** (jpg/png/webp/gif/bmp + heic/avif/jxl/tiff/raw 等) →
   **ファイルを bytes ごとコピー** (再エンコードなし、最速・無劣化)。exotic 形式もそのまま束に入る
   (mIV が読める)。
2. **アーカイブ (ZIP/CBZ 等) 内に格納された画像** → **格納 bytes をそのまま抽出** (再エンコード
   しない)。中身は既に JPEG/PNG 等のファイルなので無劣化・高速。
3. **PDF ページ / 動画フレーム / 編集焼き込みが要る場合** → ここだけ画素を decode →
   エンコード保存 (WebP 既定。export 経路 = Ctrl+E と同じ)。
   - 線画 (PDF) はロスレス WebP / PNG、写真・動画フレームはロッシー WebP、のように
     内容で品質を分けるか設定で選ぶ (§10)。

= 「エンコードが要るのは PDF ページ・動画フレーム・編集焼き込みの 3 ケースだけ」。それ以外は
すべて無加工コピー / 格納 bytes 抽出で無劣化。

## 4. 機能設計

### 4.1 追加トリガ (ショートカット 1 つで「アクティブな本」へ追加)
**現在のアクティブな本**に、文脈に応じた画像を複製追加する `KeyAction` を 1 つ用意する:
- **サムネイルグリッド**: カーソル位置のアイテム。**選択 (チェック) がある場合は選択画像すべて**を一括追加。
- **フルスクリーン / ウィンドウ内画像表示**: 表示中のその画像。
- **動画再生中**: 現在の再生フレームを画像として追加。
- ZIP 内ページ / PDF ページもそのまま追加対象 (§3 の decode→encode 経路)。

追加は worker で複製 (UI を止めない)。追加直後はトースト等で「○○ に追加」を提示。

### 4.2 アクティブな本 / 既定の名前なし本
- 初期状態は**デフォルトの名前なし本**が 1 冊あり、それがアクティブ。設定不要ですぐ追加できる。
- アクティブな本 = 追加先。製本画面で切り替える。

### 4.3 製本画面 (本の管理)
- **本のリネーム** (= フォルダ名変更)。
- **本の追加 / 削除** (= ルート下のフォルダ作成 / 削除。削除時に実体画像も消すか確認)。
- **コピー先 (アクティブ) の本を 1 つ選ぶ**。
- 各本のサムネ + ページ数 + 追加日などの一覧。

### 4.4 本を開く・並べ替え
- 本のフォルダを開くと既存グリッドで表示。**ページ順 = ファイル名の自然順**。本棚ルート直下の
  本フォルダでは、ユーザーが別のソート種を選んでいても番号順を強制し、`0001_...` の順序を崩さない。
  メニュー/ツールバー/詳細ヘッダのソート操作は disabled とし、「日付順を押せるが効かない」
  状態を作らない。
- 本フォルダ内に手動で ZIP/PDF/フォルダ/動画等が混入しても、ページではないため一覧表示から
  除外する。正本は「番号付き画像ファイルだけ」の純フォルダである。
- mIV 内の並べ替え (ドラッグ / コマンド) → §2.2 のリネームを worker で実行 → グリッド再読込。
- v1.7.0 初期実装では追加順表示は持たない。通常は末尾追加なのでページ順と一致し、並べ替え後は
  ファイル名のページ順を正本とする。

### 4.5 メンテナンス操作
- v1.7.0 初期実装では未実装。必要になった段階で操作感確認後に追加する。
- **番号の整理 (リナンバー)**: gap 番号が詰まった/見栄えを整えたいときに `0010,0020,…` へ振り直し
  (全体リネーム、§2.1 の実測内)。
- 重複ページの除去、欠番の詰め直し等。

## 5. リネーム時の自フォルダ監視の扱い (mIV 固有の注意)
mIV はフォルダ監視 (notify-rs) と自動インデックスを持つ。製本フォルダで数百〜千のリネームを
行うと FS イベントが大量発生し、監視/索引の reconciliation が無駄に走り得る。
- **製本フォルダは自動インデックス対象にしない** (§2.4 確定)。これで遅延フラッシュの大量
  リネーム時に索引チャーンが発生しない。
- 並べ替え/リナンバーのバッチ中は対象フォルダの監視を一時停止 → 完了後に 1 回だけ再読込。
- これは [docs/async-architecture.md](async-architecture.md) の監視・キャンセル規約に沿って実装。

## 6. 永続データへの影響 (リリース済み/未リリース判断)
| ストア | 状況 | 対応 |
| --- | --- | --- |
| 本フォルダ内のサイドカー | **置かない** (§2.4 確定) | マーカー/順序サイドカーなし。本は番号付き画像のみの純フォルダ |
| アクティブな本 / 製本ルートパス (settings.db) | 新規フィールド | settings_db 既存 migration 経路で後方互換に追加。ルートは設定可能・既定 `ピクチャ\mimageviewer\books` (§2.3)。Roaming APPDATA 直下は使わない |
| ページ順 | **ファイル名が正本** (DB に持たない) | スキーマ非依存。最も壊れにくい |
| 検索インデックス | **本フォルダは対象外** (§2.4) | 大量リネーム時の索引チャーン回避 |

本フォルダ自体は**番号付き画像だけの通常フォルダ** (サイドカーゼロ)。アンインストールやキャッシュ
削除と無関係に画像が残り、ZIP 化・移動してもゴミファイルが付かない = 設計上の利点。

### 7.1 並べ替えは「専用の並べ替えモード」に分離する (2026-06-15 確定)
通常グリッドにインライン drag-reorder を載せる案は**採らない**。理由 (ユーザー指摘): 通常
グリッドの drag は (a) 範囲外ドラッグでの auto-scroll、(b) **ウィンドウ外でドロップして意図せず
shell ドラッグアウト (コピー) が走る**、等の事故が起きやすく、既存の `SHDoDragDrop`
(モーダル) との切り分けも厄介。

代わりに**本棚フォルダ表示時に「並べ替え」ボタン**で、**専用の並べ替えページ**に入る:
- **小さめサムネイルを敷き詰めた専用ビュー** (一度に多数を見ながら並べ替えられる)。
- **サムネイルホバーで少し大きめのプレビュー** (ページの識別用)。§2.5 で本は編集不可・焼き込み済み
  なので、**プレビューは補正パイプラインを通さず常に高速**に出せる。
- **ドラッグはこの専用ページ内でのみ並べ替えを意味する** = shell ドラッグアウトと曖昧にならない
  (このビューには通常グリッドの drag-out 経路を持ち込まない)。auto-scroll はページ内に閉じた
  挙動として実装すればよく、ウィンドウ外ドロップによる誤コピーは原理的に起きない。
- ドロップ確定で §2.2 のメモリ順序を更新 (ディスクは触らず、保存して閉じるときに遅延フラッシュ)。
  編集を破棄する場合は確認を挟み、ディスク上の前回コミット順を維持する。
- 実装は**通常グリッドの drag 拡張より素直** (切り分け不要・専用サーフェス)。仮想スクロールでの
  挿入位置ヒットテストと挿入インジケータ描画が主作業。
- 補助手段としてキーボード/ゲームパッドでの「前へ/後ろへ移動」コマンドも用意する。画面上では
  サムネイルが横に並ぶため、ボタン表記は左右移動に合わせる。

## 10. 論点の仕分け

### A. 確定済み (2026-06-15、実装前に固定すべきものは決定済み)
1. **ファイル名スキーム**: `NNNN_元名.ext` の **4 桁ゼロ埋め連番 + 元名**。**1 冊上限 9999 ページ**、
   10000 ページ目はエラーで拒否 (§2.1)。衝突サフィックス規則・元名サニタイズの細部は実装時に詰める
   (= §B、形式の骨子は固定済みなので後でズレない)。
2. **本の識別 = 場所ベース** (製本ルート直下のフォルダ)。**マーカー/サイドカーは置かない** (§2.4)。
3. **メタデータ/索引スコープ**: 本フォルダは**検索インデックス対象外**、本ページに**タグ/★/回転も
   付けない**。本の中は Ctrl+F / ツールバーで in-memory 絞り込みのみ (§2.4)。
4. **サイドカー無し**: 追加順ビュー・来歴も**持たない** (§2.4)。→ 旧 "A4 来歴キー" は不要化。
5. 置き場所 = 全ビルド `Pictures\mimageviewer\books` 既定・設定可 (§2.3)。コピー型スナップショット /
   ページ順=番号ファイル名が正本 / 編集中メモリ順序+専用モード退出時フラッシュ (§2.1〜2.2) /
   本棚内は編集不可・複製時焼き込み (§2.5) / 並べ替えは専用モード (§7.1)。

### B. 実装後に試しながら詰める (cheap・derived。既存破壊なし)
- 衝突サフィックス規則 (`(2)` 等) と元名サニタイズ・元名が長い/重複時の扱い。
- エンコード形式の既定 (PDF/動画/焼き込み。既存の本は各自の形式を保持するので後変更で壊れない。
  既定: 焼き込み/PDF=ロスレス、動画フレーム=ロッシー WebP で開始)。
- 並べ替え専用モードの実装段階 (drag を最初から / キーボード「前へ後ろへ」先行)。
- アクティブ本のクイック切替 UX、本削除時に実体も消すか、同一ページ重複追加の可否、各種細かい挙動。
