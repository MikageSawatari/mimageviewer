# 実装 brief: H3b プレビューと書き出しの画素一致の検証（音楽ビデオ）

担当: Codex GPT-6.1 Sol / high（実装・テスト）。設計・検収: ClaudeCode Opus 5.5。独立レビューは別担当。
作業場所: `C:\home\mimageviewer-musicvideo`（ブランチ `musicvideo`）。報告は日本語。

## 1. 正本

`docs/music-video-export-plan.md` の §7 の **H3b** 行（「プレビューで表示したフレームが、同じ時刻の書き出しフレームと一致する:
表示フレームの欠落、前後への seek、直接 seek、音源より短い / 長い出力尺。これが通るまで H3 を完了扱いにしない」）と、
D3 の改訂（H3a の契約）、D1（プレビューと書き出しは単一のラスタライザ、縮小以外の差を作らない）。
H3b は**検証の段**で、契約や製品の挙動は変えない。検証で不一致が見つかったら、直す前に止めて原因と案を報告する。

## 2. 作業範囲

1. 書き出しの各フレームの RGBA を比べられるようにする。既存の `compute_frame_hash`（フレーム列全体の SHA-256）に加え、
   検証時だけフレームごとのハッシュ（または指定したフレーム番号の RGBA）を取り出せる仕組みを mvexport に足す
   （通常の書き出しでは計算しない。既存の `compute_frame_hash` と同じく要求の旗で有効にする）。
2. エディタの**実際のプレビュー経路**（`start_preview_if_needed` → worker → 結果の採用。解析タイムライン・`index_at`・
   `time(n)` を含む）を headless で駆動し、各要求で worker が描いた RGBA（egui の `ColorImage` へ変換する前）を取り出せる
   テスト用の口を用意する。製品の経路と別の描き手を作らない。
3. 同じスナップショット（Project・Assets・PCM と識別）から、エディタの書き出し経路（P4b-3 の GUI と同じ lib 関数）で
   書き出し、フレームごとのハッシュを得る。
4. 次の要求列で、プレビューの各フレームのハッシュが、書き出しの同じ番号のフレームのハッシュと一致することを確かめる:
   - 順方向（毎フレーム）
   - 表示フレームの欠落（例: 2〜5 フレームおきの不規則な前進、再生位置がフレーム境界の直前・直後）
   - 後退の seek、前方への遠い直接 seek、チェックポイントちょうどの番号、同じ番号の反復
   - 途中の設定変更（モジュレータ・表示ゲイン）の後に元へ戻す
   - 出力尺が音源より短い・長い（無音延長）・同じ
   プロジェクトはスペクトラム・鍵盤・モジュレータ（Envelope と Average、Onset を含む）・文字・時刻表示・画像を含める。
   解像度は小さくてよい（テスト時間を抑える）。音声は合成でよい。
5. エディタの表示（egui テクスチャ）は RGBA を premultiplied へ変換して縮小表示するだけで、画素の内容は変えないこと
   （D1）を、変換前後の関係として確認する（プレビュー画像の作成箇所が worker の RGBA だけを入力にしていること）。
6. 設計書に「H3b 検証記録」を追記し、§7 の H3b 行と H3（H3a + H3b）の状態を更新する。

## 3. テスト

- 上の要求列それぞれを独立したテストにする（失敗したときに、どの場面か分かるように）。
- 各テストが、意図的に壊した実装で落ちることを確かめて記録する。例: プレビューで `time(n)` ではなく再生位置で
  シーンを評価する、解析タイムラインを使わず時刻ベースの解析に戻す、較正入力を全尺にする、PCM の view を外す。
- 既存のテストがすべて通る。
- 確認コマンド（`MSBUILDDISABLENODEREUSE=1`）:
  ```

  cargo check -p musicvideo-editor --features dev-tools --bins
  cargo test -p musicvideo-core -p musicvideo-ui
  cargo test -p mimageviewer --lib mvexport

  python scripts/check_ui_glyphs.py
  ```
