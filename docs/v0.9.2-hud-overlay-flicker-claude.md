# v0.9.2 Task — HUD overlay flicker: Claude Code's analysis

Companion to [`v0.9.2-hud-overlay-flicker-task.md`](v0.9.2-hud-overlay-flicker-task.md),
which is the primary task doc (reproduction steps, validation checklist, risk
assessment). This file records the **Claude Code** investigation. It **agrees on the
affected area but proposes a different precise mechanism for the visible artifact**.
Read both before implementing a fix.

## Status

- Target: v0.9.2. Deferred from v0.9.1 intentionally (1-frame cosmetic glitch, no
  functional/data impact, fix touches the delicate native presenter subsystem).
- Code changes so far: none.

## Agreement with the primary task doc

- The flicker is in the **independent HUD overlay HWND path**, not the `Ctrl+S` capture
  worker (`video::screenshot::capture_frame` — pure software FFmpeg decode in a worker
  thread, touches no window / D3D11 / swap chain) and not the video decode path.
- The **click inside the right metadata panel** is load-bearing.
- The **`Ctrl+S` capture toast** is the trigger — it makes the overlay visible again.
- `MIV_HUD_OVERLAY=0` makes the flicker stop, which confirms the HUD overlay HWND path.

## Where Claude Code's analysis differs / adds

The primary doc describes the bad frame as "a transient stale/incorrect **composition
frame** of the HUD overlay HWND." Claude Code's static-analysis reconstruction instead
points at a **z-order gap that exposes the windows *below* the presenter**, and
identifies the visible artifact concretely.

### The visible artifact is most likely the un-cloaked main window (grid)

During native-video fullscreen the window stack is, bottom to top:

1. the egui **main window** — still painting the thumbnail grid every frame
   (`render_grid`, `src/app.rs` ~17691) and **not cloaked / not hidden**
   (`sync_native_video_main_cloak(false)`, `src/app/native_video.rs` ~901);
2. an opaque egui **black-backdrop** fullscreen viewport HWND;
3. the **native presenter HWND** (video) plus the **HUD overlay HWND** on top.

The user's description — "another window / a different size / a different image in the
**left half**" — matches the **main window painting the grid**: it is a separate HWND at
the normal (non-maximized) window rect, so it has a different size/position from the
fullscreen video and can occupy roughly the left part of the monitor. A purely
intra-HUD-HWND stale frame would not read as "another window of a different size."

### Mechanism (z-order angle)

1. Right panel visible → its rect becomes part of the HUD overlay HWND region.
2. **Click** inside the panel → the HUD HWND wndproc runs the foreground handoff
   `claim_foreground(presenter_hwnd)` (`src/video/native_presenter/hud_window.rs` ~855).
   Hovering alone never does this — this is why the click is load-bearing.
3. Foreground is now already on the presenter, so the presenter z-order recovery
   `ensure_native_video_front` / `request_presenter_raise`
   (`src/app/native_video.rs` ~918-953) sees "foreground is correct" and **does not arm**
   its periodic re-raise. That recovery is also **throttled (~250 ms) and reactive** — it
   only fires *after* it observes a bad z-order.
4. Cursor moves away → right panel + HUD hide → the egui overlay DComp visual is
   **detached** (`set_visual_attached(false)`, `overlay_visible` gate,
   `src/video/native_presenter/mod.rs` ~4900).
5. `Ctrl+S` → capture toast → `overlay_visible` flips false→true → the DComp visual is
   **re-attached** (`set_visual_attached(true)`, ~6246) via `AddVisual` + `Commit`.
6. Nothing actively re-raises the presenter HWND on that same frame, and the reactive
   recovery is un-armed / throttled, so for one composited frame the presenter/backdrop
   ordering slips and the main-window grid shows through.

This fits both the earlier intermittency (a race whose timing window is normally missed)
and the determinism of the discovered repro (the click reliably un-arms the recovery; the
toast reliably triggers the re-attach).

## Open question to resolve first in v0.9.2

The two docs agree on the area but not the exact bad-frame mechanism, and the two
mechanisms need **different fixes** — confirm which one before implementing:

- **Codex theory** — the bad frame is *inside* the HUD overlay HWND (region published
  after the visual is attached → HUD HWND shows a stale / oversized region).
- **Claude theory** — the bad frame is the **presenter HWND losing top z-order**,
  exposing the main window (grid) below.

How to disambiguate empirically (cheap):

- Reproduce with `--perf-log` + `MIV_HUD_DEBUG=1` and inspect, around `Ctrl+S`:
  `egui_overlay_visual attached=false/true`, `egui_overlay_present`,
  `[HUD-DEBUG] regions changed ...`, and the native foreground-handoff logs.
- On the frame the toast is shown, log the actual top-level Z order (walk
  `GetWindow(.., GW_HWNDNEXT)`, or compare the presenter HWND vs the main-window HWND).
  Presenter HWND **not** topmost on that frame → Claude theory; presenter topmost but
  HUD HWND region wrong → Codex theory.
- A single screenshot of the flicker frame disambiguates immediately: grid content =
  Claude theory; garbled HUD overlay = Codex theory.

## Fix implications

- If **Claude theory**: actively re-raise the presenter HWND z-order whenever the HUD
  overlay visual is re-attached (and/or when the capture toast is shown) — i.e. fire
  `request_presenter_raise` on the hidden→visible transition instead of relying on the
  throttled reactive recovery. Do not depend on `claim_foreground` having armed it.
- If **Codex theory**: publish/apply the new HUD HWND region *before* attaching the egui
  overlay DComp visual, as the primary doc proposes.
- The two fixes are not mutually exclusive; applying both is reasonable defense-in-depth
  and they are low-risk relative to each other.
- Per the primary doc: do **not** make the egui overlay visual permanently attached
  (historical opaque-black-overlay failure mode).

## Confidence

This is a **static-analysis reconstruction** (whole-file reads of the native presenter,
the HUD window, and the native-video glue; no live compositor capture). The
`MIV_HUD_OVERLAY=0` result confirms the *area* (HUD overlay HWND path) with high
confidence. The *exact* mechanism (z-order exposure vs intra-HWND stale region) is the
open question above and should be confirmed empirically before implementing the fix.
