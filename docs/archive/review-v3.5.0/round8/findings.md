## U01 の再判定

通常の、各ページキーが一意である一覧では **解消を確認**。

- 記録は `PageKey` のまま。`resolve_restore_scopes` が現在の一覧を 1 回走査し、各キーを `At` / `Absent` にする。以後の復元は全件検索に戻らない。
- `apply_meta_undo` / `apply_meta_redo` の両方が **毎回** resolver を呼ぶ。前の `At` / `Absent` で解決を省略しないため、Undo 後の並べ替え、別窓への切り替え、元の窓へ戻る操作をまたげる。
- `At` は使用直前にもキーを照合し、不一致の別ページへ runtime を書かない。正本の DB / sidecar 宛先は `PageAdjustmentTarget` に保持したキー・座標を使う。
- Global / Favorite のカスケード復元は順序を維持。これらの writer はこの同期呼び出し中に `items` を差し替えないため、適用前に解決した場所が途中で変わらない。
- 新しい状態は既存の `idx_hint` を置き換えており、別の pending フラグや競合する所有者は増えていない。解決・適用が同じ Undo / Redo 呼び出しで完結する構造は妥当。

## 適用範囲と残る制限

- 同じページキーを複数の index が持つ合成一覧では、意図的に `Unresolved` へ戻して全対象へ反映する。値の適用は維持されるが、この条件まで O(N+M) になったわけではない。通常一覧についての U01 解消と区別し、重複キーを許す新しい一覧を追加する際の確認点として残す。今回、新たにその一覧を生成する変更はない。
- 別窓からの Undo 後に元の viewer の表示が古いままになる残件は、既に承認された R11 / backlog §1.173 の延期範囲。新規指摘に数えない。
- 原実装にあった DB / sidecar の同期保存を含む、一括 Undo 全体の高速化を新たに保証するレビューではない。今回の対象は U01 で増えた反復検索とその修正の退行。

アプリコードの修正、配布ビルド、アプリ起動、通常プロファイルへの操作、commit / push は実施していない。
