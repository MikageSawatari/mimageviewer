# v0.9.2: native video one-frame flicker — RESOLVED

> Filename note: this file was created when the leading theory was HUD overlay
> flicker. The confirmed root cause turned out to be a Multiplane Overlay (MPO)
> plane transition. The filename is kept so existing references do not break.

## Status

- **Resolved in v0.9.2.** Fix commit `894ba08e`
  ("Fix v0.9.2 fullscreen video flicker (MPO plane transition)").
- Verified on RTX 4090 / Windows 11: with the fix, `Ctrl+S` during fullscreen
  video no longer flickers and the video looks normal.

## Symptom

While a video played in fullscreen, a toast/HUD appearing over it (notably the
`Ctrl+S` capture-save toast) caused a momentary one-frame flicker: the video
image appeared shifted/scaled in the wrong position for a single frame. It was
intermittent.

## Root cause — MPO plane transition

DirectComposition/DWM had promoted the video swap-chain visual to a hardware
overlay plane (Multiplane Overlay): the video scanned out directly, bypassing
DWM composition. When overlay content (a toast/HUD) needed to be composited on
top, DWM **demoted** the video off the overlay plane onto the composed plane,
and that plane-demotion transition showed one mis-positioned video frame.

**Decisive clue:** running an OBS screen capture made the flicker disappear. An
active display capture disables hardware overlay planes (overlay planes scan out
separately and would not be captured, so DWM composes everything). "Screen
recording makes the flicker disappear" is a classic MPO signature.

It is not an application logic bug: mIV's DComp transforms were correct. The
glitch happened inside DWM/driver plane-transition handling.

## Fix — Route A: persistent transparent cover visual

In the presenter HWND's DComp tree, a fully-transparent full-window cover visual
is kept permanently above the video visual. The presenter HWND's content is then
never a simple single swap chain, so DWM cannot promote the video to a hardware
overlay plane — and with no promotion there is no demotion transition to glitch.

- Code: `src/video/native_presenter/mod.rs`. The existing `NativeTestOverlay`
  (a premultiplied-alpha full-window swap chain) is reused with a `transparent`
  flag: it skips the test pattern and presents a `(0,0,0,0)` buffer. It is added
  with `AddVisual` directly above the video visual.
- Placed inside the presenter HWND, so it works in both `MIV_HUD_OVERLAY` modes
  and does not interfere with the HUD HWND click-through (empty `SetWindowRgn`).
- The cover is premultiplied-alpha `(0,0,0,0)` — visually invisible.
- `MIV_DISABLE_MPO_COVER` disables it (per-GPU/driver escape hatch).

The same commit also delays showing the presenter HWND until the first real
frame is presented, closing a separate ~27-30 ms open-time window where the
presenter was visible before `video_surface_swap` applied the correct geometry.

## Approaches tried and rejected (so a future investigation does not repeat them)

The early fixes all assumed an application-side logic bug and failed because the
real cause was the DWM/driver MPO transition:

- **Band-aid — suppress the `Ctrl+S` native overlay toast.** Avoided showing the
  toast so the demotion was not triggered. Rejected: only covers `Ctrl+S` (not
  the HUD bar or other overlays) and it removed the save-feedback toast.
  Reverted.
- **Suppress overlay-visual attach / re-assert the video transform.** Assumed
  the video visual transform went stale across a DComp commit. The
  `video_transform_reassert` instrumentation fired as expected but the flicker
  persisted — the transform was already correct. Reverted.
- The capture worker (`video-frame-save` FFmpeg software decode) was ruled out:
  with `MIV_DEBUG_SKIP_VIDEO_FRAME_SAVE_WORKER=1` (a temporary diagnostic flag,
  since removed) the `Ctrl+S` flicker still reproduced.

## Remaining manual verification

- `MIV_DISABLE_MPO_COVER=1`: confirm the cover is not created (log line
  `MPO-defeat transparent cover enabled` absent) — i.e. the escape hatch works.
- `MIV_HUD_OVERLAY=0` (presenter-root fallback): confirm no flicker.
- VST3 plugin GUI shown during video playback.
- Window resize and 720p<->1080p / cross-resolution video transitions: the
  cover resizes with the presenter (`NativeTestOverlay::resize`).

## Known cost

The cover is one extra full-window swap chain (~60 MB VRAM at 4K). Negligible on
capable GPUs. A future optimization could use a 1x1 surface stretched by the
visual transform; the full-size cover was kept because it is the
hardware-verified configuration.
