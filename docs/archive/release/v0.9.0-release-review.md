# v0.9.0 リリース前レビュー — 指摘事項一覧

`v0.8.2..HEAD`（645 コミット / 276 ファイル / +113k 行）を 15 機能領域に分けて精読した結果。
リリース前の一括修正用 punch list。各項目のチェックボックスは修正完了でチェックする。

- **検証状況**: `[検証済]` = レビュー後にグレップ/精読で失敗経路を確認済み。`[要検証]` = 失敗経路の存在に追加確認が必要。
- **重要度**: `P1級` = データ破損/設定消失/ソウンドネス違反、リリース前に対応方針の決定が必要。`P2` = 直したい。`P3` = 望ましい。

## 最優先: P1 級 — 対応方針の決定が必要

### A. オフライン動画アップスケールのクラッシュ復旧層が未完成（領域 6）

データ層（manifest/queue/sidecar の atomic write）は設計通りだが、安全機構が `job.rs` の実行パスから一度も呼ばれていない。

- [ ] **R6-1 [検証済]** レジューム前にソース同一性検証が行われない。`JobManifest` に `is_valid_for_source` メソッドが存在しない（`sidecar.rs:91` にはあるが自テストのみ）。ジョブ中断中にソースを同名別内容に差し替えると、古い `Done` セグメント（旧動画）+ 残り（新動画）を連結 → **2 つの異なる動画が無言で繋がった出力**。`FailureReason::StaleSource` は定義済みだがこの経路から生成されない。→ `job.rs:607` 付近、`JobManifest::load` 直後に検証追加。
- [ ] **R6-2 [検証済]** オプション変更時に古い work dir / セグメントを無言再利用。`job.rs:620` 付近、ロードした manifest の `options` が一致検証されない。2x/Q3 でセグメント 0 完了 → キャンセル → 4x/Q1 で再登録すると、解像度バラバラの破損 concat になる。→ `manifest.options` を job options と比較、不一致なら clean work dir で restart。
- [ ] **R6-6 [P2]** サイドカー書き込みが非アトミック + 順序が設計と逆。`job.rs:378` 付近、最終出力の atomic rename **後**に素の `fs::write` でサイドカー JSON を書く。crash で `.miv.mkv` だけ存在し `.miv.json` 欠落 → ペアリングが orphan 扱い。→ `save_json_atomic`（`manifest.rs:227` に既存）を使い、rename **前**に書く。

**対応方針の選択肢**: (a) R6-1/R6-2/R6-6 を修正してから出す / (b) v0.9.0 では beta・隠し扱い / (c) そのまま出す。

### B. 設定 SQLite 移行 — orphan DB が family チェックを永久汚染（領域 10）

元の JSON 消失バグクラスは構造的に解消済み（transient vs Corrupted 分類は airtight、検証済み）。だが新しい穴がある。

- [ ] **R10-1 [P1級]** transient な `save_full` 失敗（ディスク満杯・AV ロック）が clean-install / migration 中に起きると、`bootstrap_complete` マーカーなしの orphan `settings.db` が残る。次回以降のブートで毎回 `Corrupted` 判定 → quarantine ループ → **永久にデフォルト設定固定**。migration 経路では legacy `settings.json` が無傷でも `family_exists` が永久 true になり**ユーザーの実設定が二度と読めなくなる**。→ `settings_db.rs:1824`(clean-install) / `1602`(migration) の `save_full` 失敗時に、未コミットの orphan `settings.db` を削除してから `Err` を返す。あわせて cross-process boot lock があれば並行ブートの構造的隙間も塞げる。

### C. VST3 — bridge wedge にエスカレーションがない / shm 検証欠如（領域 7）

- [ ] **R7-1 [P1級]** bridge が wedge すると audio-pump が無制限に stall。`bridge.rs:883-991` の `process_audio_blocking` が chunk ごとに 100ms timeout を再アーム（最悪 300ms/block）、`audio.rs:1004` は失敗を毎ブロックログするだけで auto-disable がない → wedge した bridge は永久にスタッタリング（`../../vst3-integration.md` の「動画再生が激重」既知症状そのもの、再起動以外回復不能）。→ per-call deadline 化 + 連続 N 回失敗で `disable_with_reason`。
- [ ] **R7-3 [P1級]** shm ring が `header_->capacity` を検証なしで信頼。`audio_pipe.cpp:43,56,104,131` の `attach()` が `capacity != 0` / `% channels == 0` / マッピングサイズ内かを検証しない。`capacity == 0` で `% capacity` の**ゼロ除算クラッシュ**、capacity 過大ならマップ範囲外読み書き → AV / ヒープ破損。→ `attach()` でサイズ検証。
- [ ] **R7-2 [検証済]** プロトコルバージョンハンドシェイクが両端で no-op。C++ `handle_message("hello")`（`main.cpp:720`）が受信した `version` を読まずに `PROTOCOL_VERSION` を返すだけ。Rust も `Ready { version }`（`bridge.rs:165`）を比較しない。docs が「stale な bridge exe はプロトコル不一致で即クラッシュ」と警告しているのに、それを捕まえる唯一のハンドシェイクが機能していない。→ 両端で `version` を比較し不一致は拒否。
- [ ] **R7-5 [検証済]** `HostApplication::ref_count_` が非 atomic な `int32`（`host_app.h:44`）。コメントは「単純 atomic ref count」と書くが実体は plain int32 で `++`/`--` も非 atomic。VST3 プラグインは host を任意スレッドから addRef/release しうる → torn read → 早期 `delete`（host UAF）または leak。`ComponentHandler`/`PlugFrame` は SDK の atomic 実装を使う。→ `std::atomic<int32>` 化。

### D. GpuVideoDevice のスレッド安全性違反（領域 4）

- [ ] **R4-1 [検証済]** `gpu_video_device: Option<Arc<GpuVideoDevice>>`（`app.rs:2115`）が `Mutex` なしで各動画のデコーダスレッドに `.clone()` 配布される。fast-swap 中は `LIVE_VIDEO_DECODE_THREADS` で最大 3 スレッドが同時生存。`blit_nv12_to_rgba` が `processor_cache: RefCell<>` の `borrow()`/`borrow_mut()` と `ID3D11DeviceContext` を無同期で触る — **コード自身のコメント（`d3d11_device.rs:197-199,1132`）が「利用側で Mutex 化」と書くのに配線が守っていない**。`ffmpeg_d3d11.rs:111-113` が FFmpeg の `lock`/`unlock` callback も `None` にしているため FFmpeg の D3D11VA デコード自体も同じ ImmediateContext を無同期で使う。**`../../video-architecture.md` が記述する「fast-swap で `avcodec_send_packet` が hard-stuck する」既知症状の根本原因の有力候補**。→ FFmpeg の `AVD3D11VADeviceContext.lock`/`unlock` callback に `Mutex` を渡し、同じ `Mutex` を `blit_nv12_to_rgba` のコンテキスト操作区間でも取る（FFmpeg 公式のマルチスレッド D3D11 共有方式）。`processor_cache` も `RefCell` → `Mutex` に。

## P2 — リリース前に直したい

### 領域 1: 動画再生エンジン中核

- [ ] **R1-1 [検証済]** `info_rx` の Err 経路で worker 停止漏れ。`video/mod.rs:3962` でデコーダ panic 時に `self.error = Some(e); return None;` だけで `shutdown_workers_for_error()` を呼ばない（直下の native init error 経路や `open()` spawn 失敗経路は呼んでいる）。audio cpal stream / native presenter thread / thumbnail worker が `Drop` まで残る。→ `return None` 前に 1 行追加。
- [ ] **R1-2 [検証済]** `DecoderEvent::EofReached` が production で一度も送られない。`decoder.rs` から `EngineEvent::Decoder` を送るのは `Failed`(1529) と `SeekCompleted`(2514) のみ。actor 側にハンドラ・テストが揃っているのに死にコード。EOF は `clock.notify_eof_reached()` + `VideoPlayer::tick` が駆動。現状ユーザー実害はほぼないが、perf ログが EOF 時に状態を `Playing` と誤表示 + `../../video-architecture.md` の「EngineActor が source of truth」記述と乖離。→ decoder から `EofReached` を発火するか、doc を実装に合わせて修正。
- [ ] **R1-3 [P2]** loop seek が `duration−0.1` を target にして busy-spin。`video/mod.rs:4117` 付近。`set_loop_target_secs` は上限クランプしない仕様。Chapter/Bookmark ループの区間開始が duration 付近だと、即 EOF → ループ再発火が ~48ms ごとに繰り返しスタッターループ。→ `set_loop_target_secs` で end guard 内 target を弾くか、loop 分岐で 0.0 フォールバック。

### 領域 2: 動画音声パス

- [ ] **R2-1 [検証済]** RT コールバック `fill_output` が `std::sync::Mutex` を 2 種類ロック。`audio.rs:1446` の `AudioBuffer` mutex に加え、`audio.rs:1616-1672` で `clock.set_audio_pts()` / `now_secs()` 経由で `MasterClock` の `Mutex<ClockAnchor>` も 2〜3 回ロック。この mutex は EngineActor・UI・decoder・pump スレッドが奪い合う。**`engine/clock.rs:25-28` の MasterClock doc コメントは「cpal RT callback も `now_secs()` を呼ばない…RT 経路に Mutex は触れない」と明記しており実装と矛盾**。→ 最低でも doc コメント修正、理想は MasterClock anchor の seqlock / double-buffer atomic 化。
- [ ] **R2-2 [P2]** `clear_buffer` が UI スレッドで `raw_pending`（最大 ~5秒分・数百 `AudioFrame`）を mutex 保持中に `.iter().map().sum()` 集計（`audio.rs:69-90`、perf 有効時のみ）。その間 RT コールバックがブロック。→ guard drop 後に集計へ移す。
- [ ] **R2-3 [P2]** VST `process_block` 失敗時に毎ブロック無制限ログ + pump 停滞（`audio.rs:1004-1018`）。bridge が死ぬ/詰まると pump の毎イテレーションが最大 100ms 待ち + ログ出力。→ failure ログの rate-limit + 連続失敗 N 回でチェーン自動 bypass（C の R7-1 と統合修正可）。
- [ ] **R2-4 [検証済]** cpal stream の channels が 2 固定（`audio.rs:480`）。`default_output_config` の channel 数を無視。5.1/7.1 レシーバや mono デバイスが既定出力だと `build_output_stream` が失敗 → 動画の音声が一切出ない。→ 既知制限として明記するか、`supported.channels()` を見て明確なエラーメッセージ。
- [ ] **R2-5 [P2]** `AudioOutput::drop` の pump join が最大 ~2 秒ブロック（`audio.rs:162-178`）。pump スレッドが `reset_plugins_sync`（bridge ごとに 2 秒 timeout）や `process_block` の最中だと、fast video switch 時に UI フリーズ。→ VST 処理ループ / `reset_plugins_sync` 前に `cancel` チェック。

### 領域 3: ネイティブプレゼンター & HUD

- [ ] **R3-1 [検証済]** wndproc 内 `&'static mut WindowState` のエイリアシング・ソウンドネス懸念。`hud_window.rs:637` の `window_state()` が arm ごとに `&mut *ptr` を生成。`SetCapture` / `claim_foreground` が同期的にメッセージを再入させると外側の `&mut` が生きたまま二つ目の `&mut` が作られ Rust の aliasing 規則違反。`native_window.rs:841` の IME arm も同様（他 arm は `&` で安全寄り）。現に発火する再入経路は未確認だがパターン自体が UB-prone。→ `*mut` + 最小スコープ reborrow、または interior mutability。
- [ ] **R3-2 [P2]** `present()` が D3D11 device-lost を握り潰す（`native_presenter/mod.rs:1531` 付近）。`DXGI_ERROR_DEVICE_REMOVED`/`DEVICE_RESET` を汎用 `Err(String)` に潰し、呼び出し側は log + 16ms sleep + ループ → device-lost 時に presenter が永久に黒画面でスピン。→ device-lost を区別してエラートースト/フルスクリーン終了へ。
- [ ] **R3-3 [P2]** `recreate_backbuffer` 失敗で presenter 半死状態固着（`native_presenter/mod.rs:2249` 付近）。`ResizeBuffers` 成功後 `recreate_backbuffer` が失敗すると `surface_width/height` 更新済みだが `backbuffer = None`、以降 size guard が early-return して再作成を二度と試みない。→ 失敗時に `surface_width/height` をロールバック。
- [ ] **R3-4 [P2]** `hud_hwnd_out` が正常 presenter スレッド終了時にリセットされない（`video/mod.rs:2581`）。cancel 経路は `store(0)` するが通常の WM_QUIT 抜けでは未リセット → destroy 済み stale HUD HWND が raise allowlist に数フレーム残る。→ 1 行追加。

### 領域 6: オフライン動画アップスケール（A 以外の P2）

- [ ] **R6-3 [検証済]** クラッシュで `Running` のまま残ったセグメントがレジューム時にリセットされない。`manifest.rs:191` の `reset_stale_running_segments` は実装・テスト済みだが実行パスから未呼び出し（呼び出しはテスト 2 箇所のみ）。ハードクラッシュ後、セグメントは `Running` のまま + `.part.<worker_id>` ファイルがレジュームのたびに蓄積。→ load 後に `reset_stale_running_segments` を呼ぶ、serial 経路も `cleanup_segment_parts` を呼ぶ。
- [ ] **R6-4 [P2/要検証]** 0 フレームのセグメントが `Done` として公開され、レジューム後にフレーム欠落。`job.rs:705` 付近、FFmpeg seek がセグメント範囲を超えた等で `frame_count == 0` のセグメントがヘッダだけの空 MKV として `validate_segment_file`（`len() > 0` チェックのみ）を通過 → `Done` 記録 → 永久に reuse。→ `frame_count == 0` を hard error 扱い、`validate_segment_file` でパケット数チェック。
- [ ] **R6-5 [検証済]** ディスク容量 preflight が完全に未配線。`disk.rs` の `has_enough_space` / `free_bytes_available` / `estimate_required_bytes` は実装・テスト済みだが非テスト呼び出しゼロ。4x アップスケールは数十 GB。ディスク満杯時、数時間走った末に `ENOSPC` で失敗するが汎用 `FailureReason::Io` に誤分類。→ 登録時に `has_enough_space` で警告、disk-full の `io::ErrorKind` を `NoSpace` にマップ。
- [ ] **R6-7 [P2/要検証]** VFR ソースが無言で CFR 変換され duration / AV ずれの可能性（`job.rs:2009` 付近、全出力フレームを定 fps で再スタンプ）。→ `output_total_pts_ticks` を実 packet timing から導出、または VFR→CFR 変換を明記。

### 領域 11: TensorRT 対応（opt-in、blast radius 限定）

- [ ] **R11-1 [検証済]** `is_pack_installed()` が pack バージョンを検証しない（`tensorrt_pack.rs:63`）。`sentinel.exists() && ort_dll.exists()` だけ（doc コメント自身が「Phase 2: pack version 検証を追加」と書くが未実装）。pack v2 を入れた後 mIV を更新すると古い `onnxruntime.dll` をロード → 原因不明の「spawn failed」バナー。→ `INSTALL_OK` の version を読んで比較。
- [ ] **R11-2 [検証済/security]** `MIV_TRT_PACK_BASE_URL` 環境変数が release ビルドで `http://` をスキーム検証なしで受け入れる（`tensorrt_installer.rs:69`）。DL された DLL は `LoadLibrary` される → 任意コード実行ベクタ。manifest 自体の発行者認証もない（per-asset SHA-256 は manifest 内なので転送破損しか防げない）。→ manifest の pinned 公開鍵署名検証を追加、または `MIV_TRT_PACK_BASE_URL` を `#[cfg(debug_assertions)]` に閉じる / `https://` 必須化。
- [ ] **R11-3 [検証済]** `send_cmd` の timeout が worker を `mark_dead` しない → IPC desync + cross-process SHM race。`trt_worker_pool.rs:389` の `classify_io_error` は `"stdin write"` / `"stdout read"` / `"worker stdout が EOF"` のみマッチ、timeout 文字列はマッチしない。10s timeout（cold engine deserialize は超えうる）で worker は生存したまま後で `out_shm` に書き込む間に親が次の `infer()` を発行 → shared memory の cross-process data race + 以降の IPC レスポンスが全て 1 つズレる desync。→ timeout を fatal 扱い（`mark_dead` + kill）、`LoadModel` timeout を handshake と揃える。
