**現状では出荷を止める判断です。通常動画ズームに、別ウィンドウへ状態が漏れる P1 が1件あります。** 以下はコードから確認した指摘です。修正・ファイル更新・アプリ起動は行っていません。

**出荷前に対応すべき問題**

1. **[P1／C／BA-7] 通常動画のズーム状態が別ウィンドウへ漏れる**

   `video_zoom_state` は App にありますが、`ViewerContextBundle` の保存・交換対象に入っていません。一方、別窓の定期更新は、その context を一時的に mount して `poll_video` を呼び、そこから現在のズーム状態を presenter へ同期します。

   通常動画 A・B を別窓で開き、A を拡大すると、B の更新時にも A の倍率・中心が渡ります。また、B の項目変更によるリセットが A の状態を消す経路も成立します。設定の共有ではなく、項目固有の状態の所有漏れです。

   根拠：[状態の配置](/C:/home/mimageviewer/src/app.rs:11705)、[bundle の交換対象](/C:/home/mimageviewer/src/app/viewer_context_registry.rs:1997)、[別窓の定期更新](/C:/home/mimageviewer/src/app.rs:40919)、[presenter への同期](/C:/home/mimageviewer/src/app/native_video.rs:7034)。修正方向は、ズーム状態を viewer context の所有物にすることです。

**次版対応でもよい問題**

2. **[P2／E] お気に入り表示状態のリセット／OFF で、設定と実際の一覧順が食い違う**

   リセットは共通設定を戻しますが、現在の items を並べ替え直しません。OFF 時の frame 終端処理も同様です。

   共通設定を名前順、お気に入りを更新日時順にして一覧を開き、そのお気に入りの表示状態をリセットすると、ソート表示は名前順へ戻っても、一覧は更新日時順のまま残ります。再読み込みまで不一致が続きます。

   根拠：[設定だけを再適用する処理](/C:/home/mimageviewer/src/app.rs:64058)、[リセット経路](/C:/home/mimageviewer/src/app.rs:64212)、[OFF 経路](/C:/home/mimageviewer/src/app.rs:64077)。通常のソート変更が呼ぶ `apply_sort_change_reload` 相当の反映が必要です。

3. **[P2／B] JPEG の後続マーカーの異常で、先頭の正常な EXIF まで失う**

   新しい reader は SOS／EOI まで走査を成功させてから rexif に渡します。そのため、有効な EXIF APP1 の後でマーカー破損・切り詰め・16 MiB 上限に遭遇すると、既に読める EXIF も全て `None` になります。

   旧 rexif は最初の EXIF APP1 を見つけた時点で解析へ進むので、その後の異常に影響されません。EXIF 表示・UserComment のプロンプト検索で退行します。サムネイルの向きについては WIC fallback が残るため、必ず向きが変わるとは断定しません。

   根拠：[後続マーカー検証](/C:/home/mimageviewer/src/exif_reader.rs:94)、[上限時の全破棄](/C:/home/mimageviewer/src/exif_reader.rs:143)、[向きの fallback](/C:/home/mimageviewer/src/thumb_loader.rs:520)。必要な APP1 を取得した時点で解析できる構造が適切です。

4. **[P2／B] 検索を再実行すると、取消済みの8並列処理が積み上がる**

   cancel の確認は各項目の入口だけで、PNG チャンク走査・EXIF 読み・XMP 読みへ渡されません。古い検索は最大8件の読取を終えるまで残りますが、新しい検索は別の8スレッド pool を直ちに作ります。

   遅い共有フォルダ、大量チャンクの PNG、大きな TIFF／XMP 読取中に検索を繰り返すと、並列数が検索世代数に比例して増えます。UI で直接 join する問題ではありませんが、今回 A で解消した種類の資源競合を検索側で再発させます。

   根拠：[cancel 確認位置](/C:/home/mimageviewer/src/app/metadata_ops.rs:1663)、[検索ごとの pool 作成](/C:/home/mimageviewer/src/app/metadata_ops.rs:1953)、[旧検索の取消と再投入](/C:/home/mimageviewer/src/app.rs:49222)。

5. **[P2／A] 無関係なウィンドウのフォルダ移動で、使用中 ZIP の目次キャッシュも消える**

   新しい中央目次キャッシュはプロセス共有ですが、既存の `clear_nested_cache()` に全消去を追加しています。この関数は通常のフォルダ移動でも呼ばれます。

   別窓で大きな ZIP を読んでいる間にメイン側でフォルダを移動すると、その ZIP の目次も失効し、次の読み込みで再解析します。読取専用の別 context の操作が、変更されていない兄弟 context のキャッシュを壊す構造です。

   根拠：[共有キャッシュの全消去](/C:/home/mimageviewer/src/zip_loader.rs:621)、[通常フォルダ移動からの呼出し](/C:/home/mimageviewer/src/app.rs:20288)。mtime・サイズ検証と既存の8書庫上限を生かし、無関係な移動では消さない方向が自然です。

6. **[P2／C] 拡大して端までパンした後、表示領域を変えると映像が完全に消える**

   パンの制限は入力時だけで、表示領域変更後の `source_rect()` では再計算されません。

   数式上の例では、1920×1080 の動画を3840×1080の領域で16倍にし、右端までパンすると中心 X は2039です。その後、領域を1920×1080にすると表示範囲の左端は1979となり、映像全体が範囲外へ出ます。shader は範囲外を黒にするため、再生中でも全面黒になります。

   根拠：[領域変更時の矩形計算](/C:/home/mimageviewer/src/video/zoom_view.rs:114)、[範囲外の黒描画](/C:/home/mimageviewer/src/video/native_presenter/shaders/video_resample.hlsl:94)。実機確認ではなく、実装の数式からの確認です。

7. **[P2／D] スタック内の切り抜き設定は「切」バッジに集約されない**

   親への判定は Folder／ZIP／PDF／ZipDir を扱いますが、Stack は `_ => false` です。非代表メンバーを切り抜いてスタックへ畳むと、その状態がバッジから分からなくなります。

   根拠：[バッジの判定](/C:/home/mimageviewer/src/app.rs:47988)、[集約対象の分岐](/C:/home/mimageviewer/src/app.rs:48208)。フォルダ・アーカイブへの集約はありますが、スタックまで対応済みとは判断できません。

8. **[P2／A・既存問題] 入れ子 ZIP のキャッシュヒットは、外側 ZIP の更新を検証しない**

   入れ子データのキーは外側パスと内部パスだけです。キャッシュヒット時は新しい中央目次キャッシュにも到達しないため、外側 ZIP を同じパスで更新しても、全消去が起きるまでは旧内部 ZIP を返します。

   根拠：[キー比較](/C:/home/mimageviewer/src/zip_loader.rs:510)、[metadata 検証を経由しないヒット経路](/C:/home/mimageviewer/src/zip_loader.rs:1113)。**これは v3.5.0 にも存在し、今回の退行ではありません。** 通常 ZIP の失効改善だけでは解消されていない点として挙げます。
