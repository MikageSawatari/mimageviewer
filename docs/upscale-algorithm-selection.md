## 1. なぜ比較から始めたか

v2.11.0 で縮小に GPU Lanczos を入れたとき、**Lanczos4 を 0 度トーンだけ見て「Lanczos3 の
上位互換」と誤判定した**。角度を変えたら破綻し、撤回した。同じ轍を踏まないために、
拡大では「どのアルゴリズムにするか」を決める前に比較シートを作ることにした。

具体的に禁じたこと:

- 1 つの指標で順位を決める
- 1 種類の画像で判断する
- 1 つの倍率で判断する
- 劣化モデル (縮小フィルタ) を 1 つだけ使う — Lanczos で縮小すると Lanczos 系が有利になる

## 2. 測り方

### 2.1 候補は再実装しない

**リファレンス実装をそのまま通した。** 自前移植のバグが比較結果に混ざると、
「アルゴリズムが悪いのか移植が悪いのか」が切り分けられなくなるため。

| 系統 | 実行手段 |
| --- | --- |
| 固定カーネル | libplacebo 内蔵 upscaler (ffmpeg の `libplacebo` フィルタ経由) |
| FSR1 / NIS / Anime4K | 配布されている mpv user shader を `custom_shader_path` で適用 |

ここで測るのは「移植する価値があるか」であって「移植の実装」ではない。
mIV は wgpu (WGSL) なので、採用が決まった時点で別途移植が要る (§5)。

### 2.2 落とし穴: LUMA hook は RGB では無言で発火しない

FSR / NIS の mpv shader は `//!HOOK LUMA` を持つ。RGB で入力すると LUMA プレーンが
存在せず、**shader が適用されないまま「測れた」ように見える**。

対策として全候補を **YUV444 16bit** の同じ経路へ通し、さらに毎回
「出力が他候補と完全一致していないか」を検査した。一致したら shader 不発とみなす。
今回の全 672 組で一致は 0 件だった。

輝度だけ shader、色差は Lanczos になる (mpv での実運用と同じ)。

### 2.3 2 つのプロトコル

| | 内容 | 使いどころ |
| --- | --- | --- |
| **ground truth あり** | 原画 → 1/N に縮小 → 各手法で N 倍に復元 → 原画と比較 | 数値で順位を付ける。ただし入力が合成的に綺麗 |
| **ground truth なし** | 実寸の画像をそのまま N 倍 | **mIV が実際にやること。最終判断はこちら** |

劣化モデルは **bicubic と box の 2 種類**。順位が劣化モデルの副産物でないかを見る。

## 4. 結果

### 4.1 指標の平均順位 (7 画像 × 3 倍率 × 2 劣化モデル = 42 組)

数字は平均順位 (1 が最良、14 が最下位)。

| 候補 | SSIM | PSNR | ハロ (小さいほど良) | エッジ (立ちの強さ) |
| --- | ---: | ---: | ---: | ---: |
| Anime4K x2 VL | **2.79** | 4.48 | 11.24 | 3.95 |
| Anime4K x2 M | **3.19** | 4.93 | 10.33 | 4.57 |
| NVIDIA Image Scaling | **3.74** | 6.67 | 13.00 | 2.83 |
| FSR 1.0 | 4.45 | 5.98 | 8.38 | 5.33 |
| Lanczos3 (分離) | 5.26 | 5.12 | 8.05 | 7.07 |
| Spline36 | 6.05 | 5.43 | 5.86 | 8.50 |
| Catmull-Rom | 7.50 | 6.69 | 3.26 | 8.67 |
| EWA Lanczos sharp | 7.79 | 6.26 | 7.43 | 9.62 |
| EWA Lanczos3 | 9.02 | 6.90 | 6.38 | 10.93 |
| nearest | 9.52 | 10.90 | 2.69 | 1.62 |
| Anime4K Restore+x2 VL | 10.00 | 11.14 | 13.67 | 3.00 |
| Mitchell | 11.12 | 8.69 | 2.90 | 12.45 |
| **bilinear (比較時の旧実装)** | **12.02** | 10.07 | 1.26 | 13.10 |
| EWA Jinc3 | 12.55 | 11.74 | 10.55 | 13.36 |

読み方の注意:

- **「ハロ」と「エッジ」は単独では良し悪しにならない。** bilinear はハロが最小 (1.26) だが
  単にぼけているだけ。nearest はエッジ順位 1.62 だが階段状になっているだけ。
  指標が想定どおり動いていることの確認として見る。
- **PSNR は網点・細密ハッチングでは「ぼかした方が高く出る」**ので、拡大品質の指標に
  単独では使えない。

### 4.2 系統別の勝者 (SSIM, 劣化モデル bicubic)

| 素材 | x2 上位 | x4 上位 |
| --- | --- | --- |
| AI イラスト | Anime4K VL (0.825) | Anime4K VL (0.583) |
| 線画 (北斎) | Anime4K VL (0.772) | Anime4K VL (0.557) |
| 漫画スキャン | Anime4K VL (0.733) | Anime4K VL (0.408) |
| 細密エッチング | Anime4K VL (0.606) | NIS (0.138) |
| 網点 | Anime4K VL (0.684) | nearest (0.022) |
| 写真 (森・岩) | NIS (0.798) | NIS (0.545) |
| 写真 (人物) | NIS (0.951) | NIS (0.872) |

**題材で勝者が割れる。** 線画・漫画・イラストは Anime4K、写真は NIS。
「どれか 1 つが全部で最良」ではないという、まさに Lanczos4 で見落とした構造が出ている。

網点の x4 は全手法が崩壊 (最良でも SSIM 0.022)。4 倍縮小で網点が消えた後は
どの手法でも復元できない。指標の限界として記録しておく。

### 4.3 EWA Jinc は拡大の答えではなかった

§1.46 は縮小の測定 (§4.3.4) を根拠に EWA Jinc3 を有力候補に挙げていたが、
**拡大では最下位** (SSIM 12.55 / PSNR 11.74)、しかもハロは大きい (10.55)。
bilinear より悪い。

用語の区別が要る:

- `ewa_jinc` = 窓なしの jinc 3 ローブ。リンギングが大きい。**これが最下位のもの**
- `ewa_lanczos` = jinc を jinc で窓掛けしたもの。MPC-VR の「Jinc2m」に相当。順位 9.02 で中位

つまり MPC-VR が拡大に推奨している `Jinc2m` は `ewa_lanczos` の方であり、
それでも**分離 Lanczos3 (5.26) に負けている**。円形通過域の利点は縮小のモアレ抑制では
効いたが、拡大では対角の情報を落とす欠点の方が出る。

### 4.4 目視で見えて指標に出なかったこと

**FSR 1.0 と NIS は紙の粒状ノイズを増幅する。** どちらもシャープ化を内蔵しているため、
スキャン原稿の紙目・グレインがはっきり浮く (線画・漫画スキャンで顕著)。
ground truth 比較では「原画に近づく方向」に働くので**指標では加点され**、
実際の閲覧では「ざらつきが増えた」と見える。指標だけで決めるとここを見落とす。

Anime4K は線を再構成する方向に働くので、同じ条件で紙目は持ち上げない。
写真では逆に FSR / NIS のシャープ化が有利に見える。

これは §4.2 の「題材で勝者が割れる」と同じ話の別の側面で、
**シャープ化系は原稿ノイズのある素材と相性が悪い**という構造がある。

### 4.5 網点の「うねり」は Anime4K が作っていない — 元画像にある (2026-08-05 訂正)

**この節は 2026-08-04 に「Anime4K が網点に低周波のうねりを作る」と書いていたが、
2026-08-05 の実装後検証で原因が違うことが分かったので書き直した。**
訂正前の記述は「応答が網点格子の局所位相に依存するので、位相が回るのに合わせて
平滑化される所と網目が残る所が周期的に交替する」= **CNN 本体が作っている**としていた。

#### 実際に起きていること

利用者が実装後に元画像を拡大して観察し、**「元画像の段階で、周期的に網点とボケている
部分がある」**ことを見つけた。ニアレストでも判別できる。つまり:

- **周期的な交替は元画像に既にある。** スキャン / 縮小の過程で網点 (周期 1.67px、45°) が
  画素格子とビートを起こした moiré で、局所コントラストが約 10px 周期で変調している
- **Anime4K はそれを忠実に保つ。** 忠実なので目立つ
- **Lanczos3 はボケている部分を若干くっきりさせ、網点部との差を縮める。**
  つまり元画像の欠陥を**均して見えなくしている**

測定 (原寸座標 `(4,704)-(92,880)`、局所標準偏差マップの変動係数):

| | 変動係数 |
| --- | ---: |
| **元画像** | **0.269** |
| Anime4K x2 VL の出力 | 0.274 (ほぼ元のまま) |
| Lanczos3 の出力 | 0.218 (約 19% 圧縮) |

元画像のコントラストマップ自体に周期 9.8px / 10.4px の明確なピークがある。
**Anime4K は何も足していない。**

#### 合成網点で再現できなかった理由もこれで説明が付く

周期 1.67px の 45° スクリーンを合成して同じ reference harness に通しても
再現しなかった (`v212-verify/probe_ripple.py`)。**合成網点には「元からある
ボケと網点の周期的な交替」が無い**ので当然だった。合成で出ないことは
実装の問題ではない。

#### 結論はどう変わるか

**変わらない部分**: 網点のあるスキャン漫画では、Anime4K より Lanczos3 の方が
見栄えが良い。したがって**既定は Lanczos3 のまま**でよい。

**変わる部分**: 理由が「アルゴリズムのアーティファクト」から
**「元画像の欠陥に忠実かどうか」**になる。Anime4K の欠陥ではなく、
Lanczos3 が元画像の粗を隠しているという方が正確。素性の良い原稿では
この差は出ない。

**「決定的な欠点」という評価は取り下げる。** 実装後の実機確認では、
**文字と斜線は Lanczos3 より Anime4K が明らかに綺麗**であることが確認されている
(2026-08-05、利用者)。AI 生成イラスト・デジタル線画では従来どおり最良。

#### この節が 2 回間違えた教訓

1. **1 回目**: 「Anime4K は網点で必ず崩れる」と一般化し、現象が出ていない箇所
   (線画で分断された小さなトーン面) の説明文にまで書いて、利用者に指摘された
2. **2 回目**: 現象の**原因**を CNN に帰属させた。実際は元画像にあり、
   Lanczos3 が隠していただけだった

どちらも「拡大結果を 2 つ並べて違いを見て、違いの原因を決めつけた」ことによる。
**入力を見ずに出力の差だけから原因を推定しない。**
[§1](#1-なぜ比較から始めたか) の Lanczos4 と同じ型の誤りである。

再現: `C:\home\mimageviewer_testdata_upscale\gen_manga2_sheet.py` と `sheet_manga2\`、
測定は同ディレクトリ `v212-verify\probe_ripple.py`。
対象は `src_user\user_manga2.png` の原寸座標 `(4,704)-(92,880)`。

### 4.6 実行コスト

512x512 → 2048x2048 (x4、出力 4MP) を 240 フレーム連続で流したときの、
**bilinear からの増分** (RTX 4090)。

| 候補 | bilinear からの増分 |
| --- | ---: |
| nearest / Mitchell / Catmull-Rom / Lanczos3 / Spline36 | +0.02 〜 +0.22 ms |
| FSR 1.0 | +0.42 ms |
| NIS | +0.45 ms |
| EWA 系 | +0.43 〜 +0.49 ms |
| Anime4K x2 M | +0.77 ms |
| Anime4K x2 VL | **+1.72 ms** |
| Anime4K Restore + x2 VL | +3.08 ms |

**絶対値ではなく増分で読むこと。** 測定系には PNG デコードと 16bit フレームの
読み戻しが乗っており、bilinear ですら 3.3ms/frame と出る。mIV はテクスチャを GPU 上に
置いたままなので読み戻しは発生しない。候補間の差だけが移植後にも残る量。

§1.46 が最大リスクに挙げた「ズーム中の毎フレーム再生成」は、**思ったほど厳しくない**。
最重量の Anime4K VL でも 4MP 出力で +1.7ms、しかも結果は `GpuLanczosCache` に乗るので
静止時は倍率変更時の 1 回だけ。ただしこれは RTX 4090 での libplacebo 実装であり、
ミドルレンジ GPU と WGSL 移植後の実測は採用候補を絞ってから別途取る。

### 4.7 比較に使った NIS はリンギング抑制が実質無効だった (§4.4 への注記)

実装時に公式 SDK と突き合わせて分かったこと。**比較に使った agyild の mpv 移植は
`kEps` を `1.0` にしている。公式の値は `1/255`。**

`kEps` は `CalcLTI` の `contrast_ratio = max(a, b) / (min(a, b) + kEps)` だけに現れる。
輝度が 0〜1 に正規化されている以上、`kEps = 1.0` では比が常に 1 前後に留まり、
`saturate((ratio - 2) * 0.125)` が 0 に張り付く。つまり **LTI が常に 1.0 になり、
NVIDIA が入れたリンギング抑制が丸ごと効かなくなる**。

したがって §4.4 の「NIS は紙の粒状ノイズを増幅する」は、
**抑制を切った状態の NIS を見た観察**である。mIV の実装は公式の `1/255` を使うので、
同じ素材でもシート版よりグレインの持ち上がりは弱いはずである。
シート版と実装で見え方が違っても不具合ではない。

これは「移植元を公式 SDK にする」判断が結果的に効いた例でもある。
mpv 移植をそのまま持ってきていたら、この差に気付かないまま出荷していた。

## 5. mIV へ入れるときの移植コスト

mIV の描画は **wgpu (WGSL)**。ここで通した GLSL / mpv shader は**そのままでは使えない**。

| 候補 | 規模 | 中身 |
| --- | --- | --- |
| Catmull-Rom / Mitchell / Lanczos3 / Spline36 | 小 | 既存の分離 Lanczos シェーダの係数差し替えで済む |
| EWA 系 | 中 | 非分離 1 パス + J1 の CPU LUT (§1.46 の見積もりどおり) |
| FSR 1.0 | 中 | AMD 公式から WGSL へ。EASU 1 パス + RCAS 1 パス、約 200 行 |
| NIS | 中〜大 | 公式 SDK の 64 位相係数表と 6×6 support を WGSL fragment shader へ移植 |
| Anime4K | 大 | 多段 CNN。中間レンダーターゲット (4ch × 数枚) と 7 パス以上の描画グラフが要る |

Anime4K 固有の構造的な制約:

- **x2 固定**。任意倍率にはならないので、x2 を掛けた後に残りを通常フィルタで詰める。
  1.5 倍ズームでは 2 倍にしてから縮小する形になる
- 中間バッファの VRAM が要る。§1.46 が挙げた「拡大は出力が元より大きく VRAM 会計の
  前提が反転する」問題が、中間バッファぶん更に効く

## 6. 実装判断と後続候補

初回実装は、設定・シェーダ・キャッシュを増やさず既存の縮小経路を再利用できる
**separable Lanczos3** とした。

- `PostFilter::None`（標準）の拡大は、整数倍・非整数倍とも Lanczos3 で表示寸法へリサンプルする
- 物理 1.0 倍は元テクスチャを直接描画し、ドットバイドットを維持する
- `PostFilter::Nearest` の拡大は従来どおり NEAREST。縮小は従来どおり Lanczos3
- CRT / レトロ / セピア等の効果フィルタの拡大は従来どおり LINEAR とする。拡大方式と効果を
  独立設定にはしないため、「高品質拡大 + セピア」のような組み合わせは現時点ではできない
- 拡大では `filter_stretch = 1.0`、blur も 1.00 固定とし、支持半径 3.0 を維持する。
  「縮小時のなめらかさ」は拡大へ適用しない
- 2026-08-05 の初回実装は目標を `source × scale` としたため、大判写真では画面外まで生成しようと
  して上限フォールバックになった。修正版では **表示 trim ∩ 画面の可視範囲**だけを source
  座標で切り出し、その表示解像度へ Lanczos3 を掛ける。パン先読みは持たず、パンごとに再生成する
- 出力は一辺 8192px、総画素 4096×4096 相当を上限とする。超える場合はエラーにせず
  従来の LINEAR 表示へ戻し、性能ログへフォールバックを記録する
- 拡大 cache は context ごとに合計 4096×4096 相当の 2 枚分までを追加上限とし、既存の
  source / branch ごと 2 entry / 全体 64 entry LRU と併用する。拡大だけ可視 source UV を
  cache key に含め、縮小 cache の目標計算と保持規則は変えない

追加実装では `PostFilter::UpscaleSharp`（シャープ拡大）を選んだ物理 1.0 倍超の表示に
NVIDIA Image Scaling を使う。`PostFilter::None` の Lanczos3 は既定のまま変更しない。

- 移植元は NVIDIA Image Scaling SDK の公式 `NIS_Scaler.h` と `NIS_Config.h`。比較に使った
  agyild の mpv shader は LUMA plane だけを処理するため、実装の移植元にはしていない。
  mIV の実装は公式版と同じく RGB texture を bilinear 取得し、輝度で求めた補正を RGB 3
  channel へ反映する
- 公式 compute shader の共有メモリ tile は性能最適化なので省き、出力 1 pixel ごとに 6×6
  support を `textureLoad` する 1 pass fragment shader とした。64 位相の scale / USM 係数と
  方向判定の数式は公式 SDK から移植し、倍率上限は設けない
- alpha は bilinear のまま USM を適用せず、premultiplied RGB も alpha 以下へ保つ。
  透過境界でシャープ化由来の halo を作らないためである
- 可視 source 領域、目標寸法、出力上限、LINEAR fallback、context 別 cache / LRU は
  `UpscaleLanczos` と共通。cache key の branch で両者を分離する。perf event 名は
  `gpu/lanczos_regenerate` / `gpu/lanczos_upscale_limit_fallback` を共用し、
  `scale_branch` フィールド (`upscale_nis`) で区別する。branch ごとに event 名を分けると、
  片方の名前で書いた集計が他方を 0 件と報告し「生成されていない」と読めてしまう。
  拡大経路が 1 度も発火していなかったのを見つけたのがまさにこの集計なので、
  名前を分けると同じ発見ができなくなる
- 物理 1.0 倍は元 texture、1.0 未満は既存 `DownscaleLanczos` のまま。`UpscaleSharp` を選んでも
  縮小シェーダ・なめらかさ・cache identity は変更しない

さらに `PostFilter::UpscaleAnime`（アニメ塗り拡大）を選んだ物理 1.0 倍超の表示には、
Anime4K x2 VL を WGSL へ生成変換した多段処理を使う。

- 17 個の畳み込み出力を元 source 領域解像度の `RGBA16Float` に保持し、最後の
  Depth-to-Space 相当を任意の表示目標寸法へ直接解決する。CReLU の正負特徴と最終 14 枚の
  同時入力を維持するため、中間 texture の使い回しはしない
- alpha はネットワークへ入れず bilinear のまま保ち、補正後の premultiplied RGB を alpha
  以下へ clamp する
- 可視 source 領域、目標寸法、出力上限、context 別 cache / LRU、perf event 名は標準拡大・
  シャープ拡大と共通にし、cache / perf の `scale_branch=upscale_anime` で結果を分離する
- 中間 texture の負荷を制限するため、可視 source 領域の長辺上限を 2048px / 4096px /
  制限なしから選べる（既定 4096px）。境界値は処理し、超過時は同じ可視領域・目標寸法の
  `UpscaleLanczos` へ、専用 texture を確保する前にフォールバックする
- 網点のあるスキャン漫画では Lanczos3 の方が見栄えが良いため (§4.5 — Anime4K の欠陥では
  なく、元画像の moiré に忠実なだけで、Lanczos3 がそれを均している)、線画・ベタ塗り向けの
  選択肢に留め、**既定にはしない**。多段処理の負荷も既定にしない理由になる。
  既定の `PostFilter::None` は Lanczos3 のまま変更しない

### ドット絵拡大 (pixel-AA)

`PostFilter::UpscalePixelArt`（ドット絵拡大）は、物理 1.0 倍超の表示に、出力 1px の箱が
隣接 source テクセルを覆う面積を軸ごとの重みにした分離可能 2 タップ補間を使う。整数倍に
限定せず、非整数倍率でもドットの大きさを揃え、テクセル境界だけを常に出力 1px 幅でつなぐ。
物理 1.0 倍は元 texture、1.0 未満は既存 Lanczos3 のままである。

- 単純な smoothstep は source テクセル内の遷移幅が倍率に依存せず、高倍率ほど遷移が複数の
  出力ピクセルへ広がってぼける。pixel-AA は `tx_per_px = 1 / scale` を遷移幅に使うため、
  倍率が上がっても境界のにじみ幅が出力 1px のままになる
- hqx・xBR・MMPX などのパターン認識系は整数倍固定で、本来のドット絵に特化している。
  レトロ画面キャプチャや硬い線の低解像度画像を含む今回の任意倍率用途には採用しない
- シャープネスは 1.0 固定とする。この値は出力ピクセルの箱による厳密な面積平均に一致し、
  テクセル内部を平坦に保ちながら境界の被覆だけを混合する。設定項目は追加しない
- egui texture の sRGB encoded・premultiplied alpha を各タップで一度 un-premultiply し、
  sRGB の区分関数でリニアへ移してから混合する。既存拡大経路は見え方を変えないため
  gamma 空間のまま据え置く
