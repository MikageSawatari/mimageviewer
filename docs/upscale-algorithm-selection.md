## 1. なぜ比較から始めたか

v2.11.0 で縮小に GPU Lanczos を入れたとき、**Lanczos4 を 0 度トーンだけ見て「Lanczos3 の
上位互換」と誤判定した**。角度を変えたら破綻し、撤回した。同じ轍を踏まないために、
拡大では「どのアルゴリズムにするか」を決める前に比較シートを作ることにした。

具体的に禁じたこと:

- 1 つの指標で順位を決める
- 1 種類の画像で判断する
- 1 つの倍率で判断する
- 劣化モデル (縮小フィルタ) を 1 つだけ使う — Lanczos で縮小すると Lanczos 系が有利になる

## 2. 測り方

### 2.1 候補は再実装しない

**リファレンス実装をそのまま通した。** 自前移植のバグが比較結果に混ざると、
「アルゴリズムが悪いのか移植が悪いのか」が切り分けられなくなるため。

| 系統 | 実行手段 |
| --- | --- |
| 固定カーネル | libplacebo 内蔵 upscaler (ffmpeg の `libplacebo` フィルタ経由) |
| FSR1 / NIS / Anime4K | 配布されている mpv user shader を `custom_shader_path` で適用 |

ここで測るのは「移植する価値があるか」であって「移植の実装」ではない。
mIV は wgpu (WGSL) なので、採用が決まった時点で別途移植が要る (§5)。

### 2.2 落とし穴: LUMA hook は RGB では無言で発火しない

FSR / NIS の mpv shader は `//!HOOK LUMA` を持つ。RGB で入力すると LUMA プレーンが
存在せず、**shader が適用されないまま「測れた」ように見える**。

対策として全候補を **YUV444 16bit** の同じ経路へ通し、さらに毎回
「出力が他候補と完全一致していないか」を検査した。一致したら shader 不発とみなす。
今回の全 672 組で一致は 0 件だった。

輝度だけ shader、色差は Lanczos になる (mpv での実運用と同じ)。

### 2.3 2 つのプロトコル

| | 内容 | 使いどころ |
| --- | --- | --- |
| **ground truth あり** | 原画 → 1/N に縮小 → 各手法で N 倍に復元 → 原画と比較 | 数値で順位を付ける。ただし入力が合成的に綺麗 |
| **ground truth なし** | 実寸の画像をそのまま N 倍 | **mIV が実際にやること。最終判断はこちら** |

劣化モデルは **bicubic と box の 2 種類**。順位が劣化モデルの副産物でないかを見る。

### 2.4 素材

系統違いの 7 枚。それぞれ 512x512 (漫画スキャンのみ 279x396 の全体) を切り出した。
切り出し位置は**手で選ばず**、画像全体の 95 パーセンタイルを超える勾配画素が最も多い窓を
自動選択している (恣意的な「良さそうな所」選びを避けるため)。

## 4. 結果

### 4.1 指標の平均順位 (7 画像 × 3 倍率 × 2 劣化モデル = 42 組)

数字は平均順位 (1 が最良、14 が最下位)。

| 候補 | SSIM | PSNR | ハロ (小さいほど良) | エッジ (立ちの強さ) |
| --- | ---: | ---: | ---: | ---: |
| Anime4K x2 VL | **2.79** | 4.48 | 11.24 | 3.95 |
| Anime4K x2 M | **3.19** | 4.93 | 10.33 | 4.57 |
| NVIDIA Image Scaling | **3.74** | 6.67 | 13.00 | 2.83 |
| FSR 1.0 | 4.45 | 5.98 | 8.38 | 5.33 |
| Lanczos3 (分離) | 5.26 | 5.12 | 8.05 | 7.07 |
| Spline36 | 6.05 | 5.43 | 5.86 | 8.50 |
| Catmull-Rom | 7.50 | 6.69 | 3.26 | 8.67 |
| EWA Lanczos sharp | 7.79 | 6.26 | 7.43 | 9.62 |
| EWA Lanczos3 | 9.02 | 6.90 | 6.38 | 10.93 |
| nearest | 9.52 | 10.90 | 2.69 | 1.62 |
| Anime4K Restore+x2 VL | 10.00 | 11.14 | 13.67 | 3.00 |
| Mitchell | 11.12 | 8.69 | 2.90 | 12.45 |
| **bilinear (現行)** | **12.02** | 10.07 | 1.26 | 13.10 |
| EWA Jinc3 | 12.55 | 11.74 | 10.55 | 13.36 |

読み方の注意:

- **「ハロ」と「エッジ」は単独では良し悪しにならない。** bilinear はハロが最小 (1.26) だが
  単にぼけているだけ。nearest はエッジ順位 1.62 だが階段状になっているだけ。
  指標が想定どおり動いていることの確認として見る。
- **PSNR は網点・細密ハッチングでは「ぼかした方が高く出る」**ので、拡大品質の指標に
  単独では使えない。

### 4.2 系統別の勝者 (SSIM, 劣化モデル bicubic)

| 素材 | x2 上位 | x4 上位 |
| --- | --- | --- |
| AI イラスト | Anime4K VL (0.825) | Anime4K VL (0.583) |
| 線画 (北斎) | Anime4K VL (0.772) | Anime4K VL (0.557) |
| 漫画スキャン | Anime4K VL (0.733) | Anime4K VL (0.408) |
| 細密エッチング | Anime4K VL (0.606) | NIS (0.138) |
| 網点 | Anime4K VL (0.684) | nearest (0.022) |
| 写真 (森・岩) | NIS (0.798) | NIS (0.545) |
| 写真 (人物) | NIS (0.951) | NIS (0.872) |

**題材で勝者が割れる。** 線画・漫画・イラストは Anime4K、写真は NIS。
「どれか 1 つが全部で最良」ではないという、まさに Lanczos4 で見落とした構造が出ている。

網点の x4 は全手法が崩壊 (最良でも SSIM 0.022)。4 倍縮小で網点が消えた後は
どの手法でも復元できない。指標の限界として記録しておく。

### 4.3 EWA Jinc は拡大の答えではなかった

§1.46 は縮小の測定 (§4.3.4) を根拠に EWA Jinc3 を有力候補に挙げていたが、
**拡大では最下位** (SSIM 12.55 / PSNR 11.74)、しかもハロは大きい (10.55)。
bilinear より悪い。

用語の区別が要る:

- `ewa_jinc` = 窓なしの jinc 3 ローブ。リンギングが大きい。**これが最下位のもの**
- `ewa_lanczos` = jinc を jinc で窓掛けしたもの。MPC-VR の「Jinc2m」に相当。順位 9.02 で中位

つまり MPC-VR が拡大に推奨している `Jinc2m` は `ewa_lanczos` の方であり、
それでも**分離 Lanczos3 (5.26) に負けている**。円形通過域の利点は縮小のモアレ抑制では
効いたが、拡大では対角の情報を落とす欠点の方が出る。

### 4.4 目視で見えて指標に出なかったこと

**FSR 1.0 と NIS は紙の粒状ノイズを増幅する。** どちらもシャープ化を内蔵しているため、
スキャン原稿の紙目・グレインがはっきり浮く (線画・漫画スキャンで顕著)。
ground truth 比較では「原画に近づく方向」に働くので**指標では加点され**、
実際の閲覧では「ざらつきが増えた」と見える。指標だけで決めるとここを見落とす。

Anime4K は線を再構成する方向に働くので、同じ条件で紙目は持ち上げない。
写真では逆に FSR / NIS のシャープ化が有利に見える。

これは §4.2 の「題材で勝者が割れる」と同じ話の別の側面で、
**シャープ化系は原稿ノイズのある素材と相性が悪い**という構造がある。

### 4.5 実行コスト

512x512 → 2048x2048 (x4、出力 4MP) を 240 フレーム連続で流したときの、
**bilinear からの増分** (RTX 4090)。

| 候補 | bilinear からの増分 |
| --- | ---: |
| nearest / Mitchell / Catmull-Rom / Lanczos3 / Spline36 | +0.02 〜 +0.22 ms |
| FSR 1.0 | +0.42 ms |
| NIS | +0.45 ms |
| EWA 系 | +0.43 〜 +0.49 ms |
| Anime4K x2 M | +0.77 ms |
| Anime4K x2 VL | **+1.72 ms** |
| Anime4K Restore + x2 VL | +3.08 ms |

**絶対値ではなく増分で読むこと。** 測定系には PNG デコードと 16bit フレームの
読み戻しが乗っており、bilinear ですら 3.3ms/frame と出る。mIV はテクスチャを GPU 上に
置いたままなので読み戻しは発生しない。候補間の差だけが移植後にも残る量。

§1.46 が最大リスクに挙げた「ズーム中の毎フレーム再生成」は、**思ったほど厳しくない**。
最重量の Anime4K VL でも 4MP 出力で +1.7ms、しかも結果は `GpuLanczosCache` に乗るので
静止時は倍率変更時の 1 回だけ。ただしこれは RTX 4090 での libplacebo 実装であり、
ミドルレンジ GPU と WGSL 移植後の実測は採用候補を絞ってから別途取る。

## 5. mIV へ入れるときの移植コスト

mIV の描画は **wgpu (WGSL)**。ここで通した GLSL / mpv shader は**そのままでは使えない**。

| 候補 | 規模 | 中身 |
| --- | --- | --- |
| Catmull-Rom / Mitchell / Lanczos3 / Spline36 | 小 | 既存の分離 Lanczos シェーダの係数差し替えで済む |
| EWA 系 | 中 | 非分離 1 パス + J1 の CPU LUT (§1.46 の見積もりどおり) |
| FSR 1.0 | 中 | AMD 公式から WGSL へ。EASU 1 パス + RCAS 1 パス、約 200 行 |
| NIS | 中〜大 | 係数 LUT テクスチャ 2 枚 + スキャンライン単位の処理。GLSL 544 行 |
| Anime4K | 大 | 多段 CNN。中間レンダーターゲット (4ch × 数枚) と 7 パス以上の描画グラフが要る |

Anime4K 固有の構造的な制約:

- **x2 固定**。任意倍率にはならないので、x2 を掛けた後に残りを通常フィルタで詰める。
  1.5 倍ズームでは 2 倍にしてから縮小する形になる
- 中間バッファの VRAM が要る。§1.46 が挙げた「拡大は出力が元より大きく VRAM 会計の
  前提が反転する」問題が、中間バッファぶん更に効く

## 6. 未確定事項

1. **どのアルゴリズムを採用するか** — 目視シートを見て利用者が判断する。
   指標は Anime4K (線画系) と NIS (写真) を上位に置いているが、指標だけでは決めない
2. **題材で切り替えるか、1 本にするか** — 4.2 のとおり勝者が割れる。
   mIV には既に画像タイプ自動判別 (`ai/classify.rs`) があるので切り替えは技術的に可能だが、
   §1.46 の「設定を増やさず固定で置き換える」方針と、判定ミス時の挙動をどうするかが未整理
3. **ズーム中の実測** — §1.46 が挙げた最大のリスク。採用候補が絞れてから測る
4. **ドットバイドットを壊さないこと** — `OriginalOneToOne` は素通しのまま維持する
5. **上限クランプ** — 拡大の出力サイズは上に開いている (8 倍 × 4000px = 32000px)
