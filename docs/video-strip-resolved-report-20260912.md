#### コードから確認できたこと (原因ではなく、除外できた説明)

- **セル幅は必ず帯の全幅を割る。**`cell_width: rect.width() / count as f32`
  ([seek_strip_layout.rs:470](../src/video/seek_strip_layout.rs:470))。
  **枚数がいくつでもレイアウト上は端まで埋まる**ので、(b) が起きるとしたら
  「軸の枚数 < レイアウトの枚数」の食い違いしかない (軸の枚数ぶんしか描かず、中心は
  `cell_count/2` に固定されるので中央に寄る)
- **枚数は帯の「高さ」由来。**`ideal_width = cell_height * aspect`
  ([:505](../src/video/seek_strip_layout.rs:505))。`cell_height` は `rect.height()` から来る。
  **高さが小さいと枚数は増える**ので、「出入り途中の小さい値で枚数が減る」という説明は
  方向が逆で成り立たない
- **0 領域には既にガードがある。**幅か高さが 0 以下のフレームでは要求キーを捨てて作り直す
  ([render_core.rs:978](../src/video/native_presenter/render_core.rs:978))。
  素直な経路は塞がれている

### 1.190 ストリップのサムネイルに hw 復号を使わない — 報告環境では 13.5 GB とカクつきになる

#### 2026-09-11 追加報告（同一原因かは未確定）

2026-09-12更新: HUD一時非表示によるworker/decoder再生成ループの構造修正は `78dde1fd0` で
実装・独立承認・全体gate・確認buildまで完了し、利用者は短時間の試用で問題なさそうと報告した。
ただし、長時間のWS推移、過去21.3GiBピーク全量との因果は未確認。旧報告のHW復号
負荷全般まで解決済みとは扱わない。S4自動テストは9/12実機成功・独立承認済みだが、短いHUD寿命回帰であり長時間メモリ計測ではない。検証記録は
`target/next-version-work/video-seek-strip-lifetime-20260911/verification-manifest.json`。

利用者が動画open時の10 GB超と再生の重さを報告。その後の操作では再現しなかった。
稼働中dupe確認版PID 71256（10:39:42起動）をread-onlyで確認したところ、Windowsの
起動累積PeakWorkingSetは22,900,649,984 bytes（約21.3 GiB）、確認時WSは約2.2 GiB。
ピーク発生時刻・割当元はこの値だけでは分からず、旧報告と同一原因とは断定しない。
直近perfログにはGPU計測があるが、通常RAMの連続値はなく、PDH dedicatedとDXGI値も
大きく不一致のためPDH値をそのまま実VRAM消費と解釈しない。
11:07頃にはclose_fullscreen全体16.9秒のUI停止があり、実fs_cache.clearは63.5 msのみ。
広い区間名`fs_cache`をVideoPlayer Dropの所要時間と誤読しない。bounded音声queueの
待機も同時に記録されたが、無制限なメモリ蓄積の証拠ではない。
採取元は通常profileのログの読み取りコピーのみ、アプリ操作・停止なし。
証拠: `target/video-memory-20260911-1112/`。原因分析は継続し、機能制限やSW復号への
変更を今回の記録だけで決めない。
同セッションの追加分析ではHudHidden close 24,053回、サムネイルdecoder ready 1,054回を確認。
10:59:43〜11:00:01のAV1 1920×1080では17.7秒に593回のdecoder生成があり、
HUD hide/showに伴うworker/decoder再生成が第一調査候補。メモリpeakとの直接因果は未確定。
詳細は同証拠directoryの `analysis-report.md`。一時非表示とセッション終了の資源寿命境界を
コード・回帰で確認してから修正し、表示機能の無断制限では対処しない。

#### ⚠️ 2026-09-05 追記: 下の「software にする」案は速度の根拠を失った

下表は `ffmpeg -ss` の計測で、**シークのたびにデコーダーを作り直す**。ハードウェアは
D3D11 デバイス生成を毎回払うので不利になる。ストリップはセッション中デコーダーを
保持するので前提が違う。

`bench_seek_decode` (実 `decode_run` を、デコーダーを開いたまま呼ぶ) で測り直すと
**順序が逆転した** (KeyframesOnly、12 セル、1 セル 1 run):

| 素材 | hw 中央値 | sw 中央値 | hw 合計 | sw 合計 |
| --- | --- | --- | --- | --- |
| HEVC 5760x2880 | **56.7 ms** | 166.5 ms | 721 ms | 1,988 ms |
| HEVC 1920x1080 (2h) | **9.2 ms** | 22.9 ms | 176 ms | 280 ms |
| VP9 1920x1080 (1h44m) | **4.7 ms** | 13.7 ms | 94 ms | 150 ms |

**3 素材とも hw が 2.5〜2.9 倍速い。** 利用者の記憶 (ホバーのサムネイルを sw から hw へ
変えて速くなった) とも一致する。したがって「既定を software」は**速度では正当化できない**。
VRAM の議論だけが残る。

同時に、§1.189 の対処が効くことも確認できた。**1 セル 1 run にすれば 12 セルが
94 ms〜2.0 秒で埋まる** (実測の grouped run は 1 セル約 5 秒)。

さらに `FullFrames` へ落ちた場合の破壊力も測れた。TimeGrid の許容は**格子 1 間隔**なので、
全体表示では 8.7 分前から前方復号する。12 セルで **157,232 フレーム** (VP9)、
hw で 1 セル約 10 秒、sw は 30 秒の予算切れ。**escalation そのものを全体表示で禁じる**か、
許容幅を間隔から切り離す必要がある。

→ 現時点の方針は「**まず §1.189 を直して復号量を桁で減らし、その後に backend を再評価**」。
Codex Sol も「run 分割を直せば backend の重要度は大幅に下がるが、pool の存在は消えない」と
同じ順序を勧めている。

#### 対応案: ストリップの抽出は software 復号にする

§1.189 の実測 (同じ実ファイル、同じセル時刻) では、**software のほうが速い**。

| セル時刻 | software | d3d11va | software + `-skip_frame nokey` |
| --- | --- | --- | --- |
| 1,043.35s | 235 ms | 371 ms | **112 ms** |
| 1,565.02s | 253 ms | 586 ms | — |
| 5,216.73s | 158 ms | 384 ms | **151 ms** |

数分に 1 枚を取り出す用途では、**hw 復号の初期化コストがシークごとに乗る**ぶん不利になる。
連続再生とは前提が違う。

- ストリップの `hw_preferred` は `settings.video_hw_decode` をそのまま渡している
  ([native_video.rs:7561](../src/app/native_video.rs:7561))。これは**再生用の設定**であって、
  1 枚取り出しの設定ではない
- software にすれば **速くなり、VRAM も使わない**。§1.189 の run 分割と合わせると、
  復号量そのものが桁で減る
- 判断材料が必要なのは「常に software にするか、フレームが大きいときだけか」。
  小さい動画では hw のほうが速い可能性があるので、**閾値を決めるなら実測から**
- グリッドのサムネイル (`video-thumb`) も同じ経路を通るので、変えるなら影響範囲を確認する

#### 回帰確認

- 5760x2880 の全体表示で、ピークのコミットが波形表示と同程度に収まる
- カクつきが出ない (報告者環境での確認が要る)
- 1080p / 4K の通常動画でストリップの充填時間が悪化していない

- 規模 / 優先度: Small / **P1**。§1.189 と同時に測り、どちらがどれだけ効いたかを分けて記録する。
