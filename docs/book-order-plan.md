# 本棚の本の並び順 — §1.683 設計案

作成: 2026-11-02。対象: v5。調査基点: `c728cd613`、worktree / branch: `mimageviewer-booksort-1683` / `booksort-1683`。
**設計案であり、利用者の採択・ClaudeCode の設計受入は未実施。製品コードは未変更、製品は起動していない。**

## 1. 範囲と推奨案

「製本の管理」の本一覧を本棚ごとに並べ替え、その順を保存する。本の**ページ順**を変更する既存の「本の並べ替え」とは別の機能とする。

推奨は、本棚直下の専用 JSON ファイル、初期状態は従来の名前順、手動順は「上へ / 下へ」で編集して「保存」で一括確定する方式。手動順では既存本の相対順を保ち、未知の本は末尾へまとめて従来の名前順で並べる。新しい番号・固定ボタン・追加先候補・前/次の本は、同じ確定済み一覧から導く。利用者が選ぶ仕様は末尾の §12 に分けた。以下はその推奨を採用した場合の設計で、決定済みという意味ではない。

本内のファイル名、ページ番号、しおり、タグ、補正、読書位置、閲覧中の本を並べ替えだけで変えない。通常のフォルダ一覧として開いた本棚ルートのグリッドは既存のソート設定に従う。今回の「管理順」を通常グリッドの `SortOrder` や Ctrl+↑/↓ のツリー順へ混ぜない。

### 2.3 キャッシュの更新経路と現行の不足

- 作成・本の改名・削除・ページの並べ替え・別本への移動/コピーの成功で `book_list_cache = None`。次の描画等で通常の一覧 worker を開始する。ページの並べ替え結果の `BookOpResult::Reordered` は**本内**の操作なので、本棚順保存用には別の名前を使う。
- 追加完了は `src/app/book_append_refresh.rs::finish_book_append_terminal` から `apply_append_to_cached_list` へマージする。固定ボタンが消えてツールバーが縮むのを防ぐ、リリース済みの経路である。追加 Undo は `src/app/book_append_undo.rs` で対象行の件数を減らし、順を変えない。
- 管理画面を開く、管理の「更新」、ページ並べ替え画面を開く、メニュー/ツールバー等でキャッシュがない場合にも一覧読込がある。外部のフォルダ変更を本棚キャッシュへ常時購読する専用 watcher は今回確認した経路にはなく、**管理を開き直す/更新する時に反映**する仕様を保つ。
- `src/ui_dialogs/preferences.rs::apply_preferences_settings` の `books_root_changed` は共有索引の同期だけを行う。本棚キャッシュの無効化や旧 List 結果の root 照合はない。旧本棚の rows が新しい本棚に見える候補経路であり、新しい順のキャッシュではこの所有不足を解消する。
- 一覧と製本操作は App 共通であり、`ViewerContextBundle` ごとに本棚一覧を複製する設計ではない。閲覧 context の items / thumbnail / channel / generation は別の所有物として維持する。
- 汎用改名は `ui_dialogs/rename_item.rs` の `rename_pending` → `shell_file_ops::rename_item_async`、汎用削除は `delete_pending`、整理 copy/move は `FileOrganizeRequest::Running` という別の owner。`admit_book_append_followup_mutation` は追加 Undo 中を拒否するだけで、これらと通常 Append の相互排他にはならない。全経路を順序 writer にする案は §6 で退け、推奨範囲を既存の製本操作へ限定する。

### 2.4 スクリーンショットの「mIV」が末尾だった件

報告された表示順は `genshin / LVM比較 / mychara / R18 / 他 / mIV`。実名がこの文字列そのものなら、現行比較の結果は **`genshin / LVM比較 / mIV / mychara / R18 / 他`** になる。二つの比較関数は同じであり、通常の List 採用・未登録行への Append マージだけから、報告順になる理由は見つからない。

`list_books` は実フォルダ名を読み、全角/半角、Unicode 正規化、trim、別名表示への変換をしない。一方、作成/改名/追加先から path を作る `normalize_book_name` → `sanitize_filename` は禁則文字を `_` に替え、**先頭/末尾の ASCII 空白と `.` を除去**する。全角英字や全角空白は半角化しない。この入口差はあるが、ASCII の先頭空白なら通常は前へ寄るため、それだけで末尾表示の説明にはならない。全角等は別の比較値になり得るものの、今回実名・文字コード・当該時点のキャッシュは取得していない。**原因は未確定**であり「全角だった」と診断しない。新機能と無関係な照合順変更はしない。

必要になった場合だけ、本棚一覧 worker の出力名と比較キーを escaped 表記で採取して実名と照合する。本設計を作るための追加操作を利用者へ求めない。

## 3. 保存先の比較と移行

| 候補 | 利点 | 費用・互換性 | 判断 |
| --- | --- | --- | --- |
| 本棚直下の専用ファイル | 本棚ごとの保存、ルートを丸ごと移動/複製しても追従。通常版/portable/異なる profile で同じ本棚順を読める。v4 の直下フォルダ列挙から除外される | 本棚への書込権限が必要。ファイルも一緒にバックアップする。複数の独立したアプリが同時に書く用途の共有編集は別仕様 | **推奨** |
| `settings.db` の Settings field / 専用 table | 設定バックアップに入る。本棚が読取専用でも保存可能 | root のキー管理と移動追従が必要。本棚をコピーしても付かない。未知 field と全体保存・版 gate の影響を受ける | 不採用 |
| data-dir の別 DB / JSON | Settings 全体保存と分離できる。本棚にファイルを置かない | root→順の対応、別 profile・別 PC・ルート移動時の扱いが増える。順だけ別バックアップが必要 | 不採用 |
| フォルダ名へ番号 prefix / 各本へ ID ファイル | 名前順で読む旧版にも順を反映できる / 外部改名を ID で追える | 本名・参照pathを変える、または全本への追加書込と ID 重複/コピー規則が必要。今回の順序保存には大きい | 不採用 |

### 3.1 保存形式（提案）

保存先は `<本棚ルート>/mimageviewer.book-order.json`。名前は実装時に既存予約名との衝突も確認する。サブフォルダを作らず、temp も同じルートの通常ファイルにする。v4 に temp フォルダを「本」と認識させないためである。

```json
{"version":1,"mode":"manual","books":["mychara","mIV","genshin"]}
```

- `mode` は `name` または `manual` の排他的な enum。`name` の `books` は空。ファイル欠落を `Name` に読み替え、最初の手動順の保存まで新規ファイルを作らない。空配列の `Manual` は空の本棚を手動順で運用する意味を持つ。
- エントリは本棚**直下のフォルダ名**。絶対 path・番号・ページ情報・固定状態は保存しない。実際の I/O に使う path は列挙済み `BookInfo.path` から取り、ファイル由来文字列を無検証で `root.join` して操作しない。
- 順序ファイルの名前を `normalize_book_name` に通さない。実名との完全一致を先に使い、大小文字だけ違う名前は既存 Windows path 比較規則で一意に照合できた場合だけ同一とする。空名、`.`、`..`、区切り文字、絶対 path、同一フォルダを二度指定する列を拒否する。曖昧な衝突・現在の lossy 名で区別不能なケースを勝手に統合しない。
- `version` 不明・不正 JSON・不正な列・読取失敗と、**ファイルが存在しないこと**を別に返す。読めない保存済みファイルを「保存なし」に変換しない。予約 path が directory/reparse point 等であれば安全に拒否し、外側への上書きを避ける。読み取りサイズにも上限を設け、超過時はエラーにする（本数を黙って切らない）。
- 利用者が明示的に「名前順に戻す」を保存した場合は `mode:name` を置換保存する。失敗時に旧ファイルを消す入口と区別できる。設定 DB と既存本の形式・schema は変えない。

### 3.2 移行と旧版との往復

1. v4 の本棚（順序ファイルなし）を v5 で読むと、従来の ASCII 小文字比較 + 元名の tie-break による `Name` として表示する。追加/改名時も初回手動確定までは従来どおり名前順。読み込むだけの移行で本/設定へ書かない。
2. v5 で手動順を保存 → v4 で同じ本棚を開くと、v4 は順序ファイルを無視して従来の名前順で読む。v4 は直下の通常ファイルを本にしない。本内の画像保存・ページ並べ替えもこのルート直下ファイルを変更しない。
3. v5 に戻ると残っている順を再使用する。v4 で本の追加/削除/改名をした差は §4 の「外部変更」と同じ規則で解決する。旧版の追加・設定保存が順序ファイルを落とさないことを fixture で検証する。旧版にも手動順が見えるという保証はしない。
4. 本棚を丸ごと移すなら順序ファイルもコピーする。本フォルダだけをコピーした場合は未知の本として扱う。本棚フォルダの設定変更自体は本も順序も移さず、元へ戻せば元の順を読む。

**設定プロファイルの制約:** `settings_db::reject_newer_app_version` は新しい版で正常保存した DB を旧版の schema 更新前に拒否する。これは v4.11.0 にもある既存のデータ保護であり、専用ファイル案でも、v5 保存後の同一 settings DB を v4 が通常利用できる保証はない。今回保証するのは**本棚データの往復互換性**。実機で v4/v5 を使い分ける場合は各版に対応した別 data-dir から同じ本棚を指定する。既存 gate の解除や実設定の巻戻しを本件に含めない。同一 profile の通常起動まで必要なら、別の互換設計が必要（§12）。

## 4. 本の増減・改名と不一致の規則

純粋 resolver に、保存ポリシーと今回正常に列挙できた実フォルダ列を渡す。`Manual` は「保存列で現存する本」→「列にない現存本を従来の名前順」の連結とする。番号はこの解決後の全件列に付け、欠落本の番号を空席として残さない。

| 出来事 | `Name` | `Manual` |
| --- | --- | --- |
| 管理から新しい本を作成 | 従来の名前順 | 既存の相対順を保って末尾に追加、同じ作成 worker の終端で順も保存 |
| 未作成の追加先へページを追加 / 別本へ移動・コピーして本ができる | 従来の名前順 | 作成と同じ。既存本へのページ追加では位置を変えない |
| 外部/v4 でフォルダ追加 | 次回の通常一覧読込で名前順 | 次回読込で末尾の未知グループへ。複数の未知本は名前順。読込だけではファイルを書かない |
| v5 の管理から改名 | 名前順で位置が変わる | 旧名の位置を新名に置換し保存。改名前に未知本だった場合も、その時点の解決列での位置を保つ。大小文字だけの変更も同じ |
| 管理から削除 | 残る本を名前順 | 成功した削除対象だけ列から除き保存。残る本の相対順は維持、以後の番号は詰まる |
| 外部/v4/汎用「名前の変更」で改名 | 新名で名前順 | 原則「旧名の削除 + 未知の新名の追加」。改名を推定して旧位置を自動移送しない。大小文字だけで一意に照合できる改名は同一本。位置を保つには「製本の管理」で改名する |
| 外部/v4/汎用操作で削除・追加・本を移動/コピー | 次回読込で名前順 | 削除された行は出さず、追加された本は未知末尾。読込だけでは保存列から削らない |
| 保存列だけにある本が再出現 | 名前順 | 次の成功した明示書込までは元の保存位置へ戻る。同名再作成と同じ本の復帰は区別できない |

未知グループは、書込せずに複数回読込すると、その時点の未知本の集合で名前順になる。例: 保存 `[C,A]`、外部追加 `D` → `[C,A,D]`、続いて外部追加 `B` → `[C,A,B,D]`。一度現れた未知本も必ず追加時系列で固定する、という仕様にはしない（§12 の選択肢）。次の手動保存、または製本の管理/製本 worker による本増減・改名の成功時に、その時点の現存全件列を保存して既知にする。その時点で欠落している古いエントリは落ち、以後の同名出現は新規末尾となる。

外部変更に対して UUID・内容一致・NTFS file ID を導入しない。フォルダ単位で別の本棚へコピー/移動した本は移動先では未知本、コピー元では通常の削除規則とする。共有フォルダ上の複数プロセスによる同時編集・手動 JSON 編集の自動マージは保証しない。

ルートや本の読取不能を削除とみなさない。列挙/ページ数取得失敗では一覧全体を成功扱いせず、前回の確定済み一覧を維持して通知する。とくに `exists()==false` に I/O エラーを畳む現行実装を新しい移行判定へ流用しない。未作成本棚と、読めなくなった既存本棚も区別し、エラー時の空一覧を保存しない。

## 5. 操作と UI

### 5.1 推奨: 上へ / 下へ、保存で一括確定

「製本の管理」の本一覧ヘッダへ「本の順序…」を置き、短い専用編集画面を開く。行は番号・本名・ページ数・選択を表示し、「上へ」「下へ」で選択中の1冊を移動する。先頭/末尾では対応ボタンを無効にし、移動後も同じ本を選択して可視範囲に保つ。管理の名前編集欄・固定・追加先変更・開く等を行全体の drag target にしない。

現在の方式を「名前順 / 手動順」と表示し、「今の順を固定」で見た目を変えずに `Manual` の draft を選べるようにする。0冊/1冊でも利用でき、以後の新規本を末尾にする運用を始められる。下部の固定操作行を「名前順に戻す」「保存」「キャンセル」とする。「名前順に戻す」は draft を `Name` にするだけで、保存前は製品の確定順を変えない。上/下への移動も `Manual` の draft を作る。`Name` と同じ見た目になっても `Manual` は区別し、**mode の変更だけでも保存可能**とする。列と mode の両方が未変更なら保存を無効化する。キャンセル/編集中の×/IME を通した Esc は draft だけを破棄する。通常の管理操作に「保存」の手間を加えない。

保存中は編集・二重保存・キャンセルによる保存結果の破棄を受け付けず、非同期完了後に一度だけ新 snapshot を公開して管理画面へ戻る。編集中も保存中も、他の本を開く/追加/改名/削除/ルート変更/別管理 editor を開始する経路は共通受付で止める。既存 manager 自体も `common_modal_dialog_open` の対象であり、新しい編集 phase も同じ main/fullscreen 共通の判定へ統合する。

### 5.2 ドラッグ案との比較

| 方式 | 利点 | 費用・推奨 |
| --- | --- | --- |
| 上へ/下へだけ | 操作対象と確定点が明白。テキスト編集・スクロールドラッグ・Window 移動との競合なし | 離れた位置への移動は複数クリック。**初版の推奨** |
| 上へ/下へ + 任意のドラッグ | 遠距離を一度で移動できる。ボタン操作も残せる | 専用 handle、挿入マーカー、画面外 release、取消、auto-scroll の試験が必要。利用者が必要と判断すれば採用 |

ドラッグ採用時は「ドラッグで並べ替えを許可」を**既定 OFF のオプトイン**とし、OFF では drag sense と Grab/Grabbing のカーソル変更を一切付けない。ON 時も専用 handle に限定し、通常行や名前欄の hover でカーソルを変えない。これは `handle_toolbar_section_drag` の「頻繁なカーソル変更は煩わしい」という既存の利用者指示に合わせる。選択だけでは drag を始めず、drop は draft への変更、永続確定は同じ「保存」一か所。初版で独立した永続設定を増やさず、編集画面ごとに OFF から始める案を推奨し、必要な場合は §12 で選ぶ。

### 5.3 レイアウト・入力規約

- [coding-conventions.md](coding-conventions.md) に合わせ、`egui::Window` なら `default_pos` / `.open`、移動可、`anchor` 固定なし。中央の一覧だけを `ScrollArea` に入れ、操作行・見出し・閉じる操作は外へ固定する。既存 `drag_area(Anywhere)` と子 drag の競合は、ドラッグを採る場合に明示検査する。
- 縦バーは右端に置き `.auto_shrink([false, ...])`。本文高さは content rect と操作行の実寸から算出し、画面より大きい固定最小幅/高さを追加しない。長名、0冊、21冊以上、小画面、高倍率でも保存/取消まで届くことを確認する。
- `Area + Frame::popup` の固定パネルへ転用する場合は親領域を明示確保し、header と×を ScrollArea 外へ置く。今回は既存管理に従う Window を推奨し、固定パネルの新設は不要。
- 背面 wheel/key/chrome と既存 popup の扱いは共通 modal / `gate_main_chrome` の規則に乗せる。表示していない state の存在だけで入力を永久に止めない。
- 新しいグローバルな並べ替えキーは設けない。ボタンの通常 keyboard 操作と一覧内の選択はフォーカスローカル。独自ショートカットを足す場合は [keymap-spec.md](keymap-spec.md) / [key-customization-impl-plan.md](key-customization-impl-plan.md) に従って `KeyAction` 化の要否を再判断する。名前変更の TextEdit / IME と既存 Enter/Esc helper を維持する。

## 6. 状態の組み合わせを減らす設計

先に [CLAUDE.md「設計の簡素化」](../CLAUDE.md)を適用する。

| 検討した手 | 採否と理由 |
| --- | --- |
| 管理画面内の即時入替え・クリックごとに保存 | 不採用。連打/保存中の改名/取消/番号入力が異なる順を見る組み合わせを増やす |
| 専用の短いモーダル編集 + 一回の保存 | 採用。draft と確定列を分離し、編集中は既存の本変更・open と同時に始めない。新機能使用中だけの排他で、通常閲覧や追加を常時遅らせない |
| 全 consumer ごとの並べ替え、別ウィンドウごとの独立一覧 | 不採用。App 共通の解決済み snapshot 一つから番号・候補・固定ボタンを射影する |
| 全更新を `cache=None` → 再読込へ統一 | **一律適用は不採用**。Append の固定ボタンちらつきを再導入する。ページ数だけの更新は既存の差分マージを残す |
| 本増減/改名/手動保存は既存の一覧作成経路へ統一 | 採用。同じ worker-side reader/resolver と UI の一回の採用 helper を使う。保存 worker は完成した snapshot も返し、保存後に再度読み直す待機を作らない |
| 外部 watcher による順序ファイルの常時更新 | 不採用。管理を開く/更新する既存タイミングで読む。Remote の読取にも書込権限を持たせない |
| 汎用 Shell 操作もすべて順序 writer にする | 初版では不採用。製本と別 owner の通常操作同士の直列化、転送の成功先ごとの捕捉などへ範囲が広がる。汎用操作は外部変更と同じ照合に揃え、位置保持が必要な改名は既存の製本管理を使う。この制約の選択は §12 に明記する |
| 既存 viewer を閉じる/再ロードして順序へ追従 | 不要。本棚の順だけなので、表示中の画像や window を作り直す理由がない |

### 6.1 所有と確定の契約

- 現在の `Option<Vec<BookInfo>>` を、**root identity・メモリ上の revision・保存ポリシー・解決済み rows を一体にした snapshot**へ置き換える。これは本棚の owner で、viewer items の generation と共用しない。最後の正常 snapshot を読込中/保存中も保持し、失敗時の `None` 化を避ける。
- **List だけでなく作成/Append/Undo/改名/削除/transfer/順保存の全要求・全結果**へ、受理時に捕捉した root と root選択epoch を付ける。List にはさらに一覧要求の revision を付ける。root選択epoch は有効な本棚設定の変更ごとに進め、同じ path の `A→B→A` でも以前の操作を新しい選択へ再所属させない。root は I/O なしの既存 path 比較で照合し、UI で canonicalize / exists を呼ばない。
- worker の FS/metadata/順保守は捕捉済み root/target で完了させる。一方、**現在の本棚 snapshot・追加先・pin への UI 投影**は root/epoch が一致するときだけ行う。たとえば A で作成/Append を開始→設定を B に変更→A が完了しても、A の保存・元 viewer への正当な完了処理・成功/警告通知は行い、B の rows/active/pin を変更しない。`Created` の active 更新と `finish_book_append_terminal` の cache マージもこの採用境界を通す。元 viewer context の完了と App 共通本棚の採用資格を混同しない。
- 通常の作成/Append中の本棚設定変更は現行で可能なので、順序保存を理由に新しく禁止しない。設定変更時は旧 snapshot を外して新 root の通常読込を要求し、先行製本 job 中ならその終端後に開始する。`A→B→A` で A の旧結果が戻っても rows を直接マージせず、現在選択の A を通常読込で取得する。source/rootの不一致を理由に既に成功した FS 操作を取り消したり、別の本棚へ保存し直したりしない。
- 編集要求は本棚操作 owner の `Preparing → Editing → Saving → 終端` の**一つの型付き phase**で表す。既存 `book_op_pending` の receiver/intent と編集用の独立 pending/bool を重複させず、本棚の read/edit/save の受付・結果配送を同じ owner に整理する。既存 `BookStructuralOp` の FS/metadata 静止契約を別の bool で置き換えない。
- 編集開始前に進行中の Append/Undo/List/構造操作/本の open に加え、`rename_pending`、`delete_pending`、`FileOrganizeRequest::Running` 等の受理済みファイル操作も終えるか、編集開始を理由付きで拒否する。実行中の job を破棄して空きを作らない。受理済み worker とその完了採用の終端後だけ編集 snapshot を取る。編集中の通常変更を後から rollback/resume する仕組みは作らない。`SessionHandle::try_local_modal_lease` を開始時に取り、編集から保存結果採用まで保持して Remote の新規操作も混在させない。
- 順序 writer は既存製本 worker と手動保存だけに限定する。通常の製本操作同士も `book_op_pending` / `BookStructuralOp` の共通受付で、順保守の完了採用まで次を始めない。汎用ファイル操作は順序ファイルを書かず、reader は §4 の照合だけをする。製本の FS 実行中に起きた外部/汎用の変更を取り込む場合も、正しく列挙できた現存本へ同じ resolver を使い、既知本の相対順を変えない。
- 編集開始時に順序ファイルの版/内容 token と直下フォルダ集合を worker で捕捉する。保存前に同じ worker で再照合する。外部で構成またはファイルが変わっていたら保存せず「本棚が変更されました。更新して並べ替え直してください」と通知して editor を終了し、通常の一覧再読込へ戻す。編集中の外部変更と draft を自動マージしない。各変更後の再試行ループはない。
- 保存成功後は確定した `BookShelfOrderSaved` 相当の結果から snapshot を一度だけ swap する。その後で番号を解決する。古い List が新順を上書きする、未保存 draft をキー操作が参照する、という経路をなくす。
- 本棚フォルダの設定変更は、editor/保存中には受付を止める。通常の変更成功時は旧 snapshot の所属を外し、旧 root の List を失効させ、新 root の通常一覧読込へ戻す。`A → B → A` でも request revision で旧応答を拒否する。本の移動や profile の固定/追加先の設定変更を勝手に行わない。
- 並べ替えだけでは Append Undo の対象画像・receipt・revision を無効化する必要がない。汎用の「本の変異」intent へ雑に分類して Undo を落とさず、順序保存専用の意味を持たせる。

## 7. 更新処理の接続と退行防止

順の読込・解決・書込は `books` の本棚層（分割するなら `book_order` module）に集約する。UI 側へ JSON の解釈を散らさない。

| 既存の動き | 必要な接続と維持すること |
| --- | --- |
| `list_books` | worker でフォルダを列挙 → ポリシーを読む → 共通 resolver → snapshot。PC / Remote に同じ順を返す。互換用の生の名前順関数が必要なら命名で区別する |
| 既存本への製本追加 | `apply_append_to_cached_list` の件数差分と path 更新を残す。手動順の全件再ソート、cache の一時削除、ボタン消失を禁止する |
| Append による暗黙の新規本・作成 | FS 成功後、**同じ worker** で `Manual` の順保守まで行う。結果に順/新しい所属を載せ、UI は I/O なしで既存 snapshot へ採用。UI から保存 worker を後追い発行して、間に次の本操作を挟まない。`Name` は既存比較で新行を差し込む |
| Append Undo | 件数だけ減らす既存の経路を維持。空になっても本フォルダが残る現行動作を、順序項目の自動削除へ変えない |
| 追加先の本 | `active_book_name` と捕捉済み target path を維持。順が変わったから先頭本や同番号の別本へ切り替えない。作成で新本を追加先にする、削除時に既定名へ戻す現行動作は維持 |
| 固定 | `pinned_books` は固定集合として使い、描画順は確定 rows を絞る。ON/OFF で本棚全体の順を変えない。左クリック=開く、右クリック=その本へ追加、展開/折りたたみを維持。設定内の既存 vector を並べ直して保存する必要はない |
| 管理からの改名 | 既存の `BookStructuralOp` / key migration / bookmark journal を維持し、FS 成功後、同じ worker で旧名→新名の順保守を追加する。UI の追加先・pin 追従を残す |
| 管理からの削除・本内の transfer | 管理削除の成功対象だけ順から除き、失敗/取消で順を消さない。ページ移動/コピーでは本棚順を動かさず、移動先が新規にできた場合だけ末尾登録 |
| 汎用 Shell 改名/削除/copy/move | 順序 writer を追加しない。次回の管理 open/更新で外部変更と同じ照合をする。管理以外からの改名では位置保持を保証しないが、残る既知本の順は維持する。元来、追加先/pin の追従も製本管理の改名/削除の完了処理であり、汎用経路の意味を本件で拡張しない |
| 本内の並べ替え | `BookOpResult::Reordered` の metadata 移行・再読込を維持。本棚順序ファイルと本のページ順を混同しない |
| 更新、管理を開き直す | 最後の snapshot を保持し、成功した新 snapshot だけ採用。再走査中の rows は busy として見せる。順が確定しない間に番号を旧 rows で先行解決しない |
| 本棚フォルダの変更 | §6.1 の root 所有・失効を `apply_preferences_settings` と設定復元の共通適用境界へ接続。通常表示中に本を勝手に移動/close/reload しない |

固定ボタンは従来の固定順から管理順へ変わる。これは依頼された「新しい並び順に従う」ための意図した仕様差であり、保存なしの `Name` でも固定本の部分列を名前順にする。固定した本の集合は移行・並べ替えのために削除しない。

## 8. 非同期 I/O とまれな失敗

[ui-responsiveness.md §4](ui-responsiveness.md#4-新機能追加時のチェックリスト)に従い、順序ファイルの open/read/parse、存在/種別/mtime 確認、フォルダ走査、ページ数取得、保存前照合、serialize、temp 書込/flush/置換を worker に置く。UI は小さい draft の入替え・snapshot の射影・非blocking receive だけを行う。大きい本棚は可視行描画とし、毎 frame の全件 clone/ソート/ファイル確認を増やさない。新しい decode・GPU upload は不要。worker 区間は perf 有効時だけ計装し、idle の周期 I/O/repaint を追加しない。

保存は同じルート内の temp 通常ファイルを完成させてから atomic replace する。先に旧ファイルを削除しない。既存 `data_dir` / `archive_converter` 等の置換方式を参照し、Windows の既存宛先・ロック時の原本保持を検査する。通常の「保存後すぐ閉じる/再編集する」は成功応答の採用まで modal を維持して直列化し、終了時だけ慌てて同期保存する方式にしない。

**まれな失敗は既定の割り切り（ログ + 通知、保存済み原本を保持）で閉じる。** 自動再試行、別保存先への黙った退避、独自 journal、未保存順の永続 pending、回復処理のための完了待ちを足さない。

- 並べ替えの書込失敗: 新順を公開せず、以前の確定順を使う。初回保存失敗なら従来どおり `Name` のままであり、「保存済み Manual から名前順へ戻した」ことにはしない。「本の順序を保存できませんでした」と通知して editor を終える。保存済みを削除/空で上書きしない。
- 保存済みファイルの読取/parse/未知 version エラー: **warm/cold とも原本を保持して順序書込を止め、名前順へ自動 fallback しない**。同一 root の最後の正常 snapshot があれば表示だけ維持し、それを元に壊れた/未知版ファイルを上書きしない。cold 時は管理順を取得できなかったことを示す。番号/前次/固定ボタンを別順へ割り当てない。通常の実フォルダから本を直接開く入口は維持する。単純な回復入口は既存「更新」または再起動での再読込だけとする。
- 本の作成/改名/削除は成功したが順の保存だけ失敗: 本の FS/metadata 処理を巻き戻さず、成功と順保存の警告を分ける。旧の正常な手動順に実フォルダを §4 で照合した列を使い、全体を `Name` にしない。改名した本などが未知末尾になる場合はその限界を通知する。旧ファイルはそのまま残し、次の読込でも同じ照合をする。これは既存の FS 後 metadata 警告と同じ終端方針であり、失敗した新順を保存成功と表示しない。
- 途中の強制終了: 公開済みの完全なファイルだけを次回読む。未公開 temp を正本へ昇格しない。未確定の draft は保存されない。再構築できる cache と利用者作成の順序原本を区別し、順を勝手に再作成しない。

## 9. 番号、マニュアル、複数ウィンドウ

- 管理の先頭20件を「本1〜20を開く」へ割り当てる。21件目以降の「—」は現行どおり。固定本だけの通し番号へ変えない。未登録番号は現在の未登録通知を保つ。
- `GridBookPrev/Next` も管理順の全件で循環。追加先を開く操作は順と独立し、押下時の target を維持する。既存 Action ID、保存済み keymap、既定キーなしを変更しない。キー/リング等から同じ resolver を使う。
- 操作の有効な画面/context は既存仕様を維持する。Grid用の本番号操作を独立viewerへ新たに広げることはせず、複数窓の検証は共有本棚の整合と各閲覧contextの非干渉を確認する。
- 番号列 tooltip 案: 「操作カスタマイズの『本1〜20を開く』で使う番号です。本一覧の上から順に対応します。本の並べ替えや削除で番号が変わります。名前順では追加・名前変更でも変わります。」手動順でも削除で後ろの番号が詰まることを隠さない。固定ボタンも本一覧の順になる旨を近くに短く添える。
- 実装時に `htdocs/mimageviewer/manual/books.html`、`tut-books.html`、`shortcuts.html` の「本は名前順」を更新し、順序編集/保存・初期名前順・未知末尾・番号変化を説明する。`settings.html` の本棚保存先説明とボタン説明、`index.html`、`privacy.html` の端末内保存の説明も照合する。本棚バックアップには専用ファイルも含むことを記す。今回は未実装機能を公開マニュアルへ先行記載しない。
- 実装時に `docs/keymap-spec.md` の「本は名前順」を「本棚の確定管理順（保存なしは名前順）」へ変更し、`spec.md`、`architecture-overview.md` の保存先表、`async-architecture.md`、`ui-responsiveness.md` に owner/worker の契約を反映する。
- 複数ウィンドウでは App 共通の一つの本棚順を参照する。保存結果を root で採用し、表示を持つ consumer は同一 snapshot を射影する。開いている本の index/ページ順、parked/linked/independent の items、thumbnail cache、要求 channel、取消 token は変更しない。単なる本棚管理の open/close が兄弟 viewer の再読込や mutation invalidation を発行してはいけない。
- [detached-rework-plan.md §2](detached-rework-plan.md)を確認した。本棚順のための detached 専用フラグ/viewport 再生成/遅延は不要。共通受付の接続で detached 述語/viewport 自体の修正が必要と判明した場合は、実装前に ClaudeCode と独立 reviewer の構造合意を取り同計画 §11 へ記録する。

## 12. 利用者に聞くべき点（推奨つき、未決定）

1. **操作方法**: A **「上へ/下へ」＋保存（推奨）** / B 同じボタンにドラッグも併設。A は単純だが遠くへ移すとクリックが増える。B は長距離移動が速く、handle/auto-scroll等の実装・検証が増える。B を選ぶ場合もドラッグ/カーソル変更は既定 OFF。許可を「その編集画面だけ（推奨）」にするか「次回も記憶」にするかを選ぶ。
2. **確定方法**: A **順序専用画面で編集し「保存」でまとめて確定（推奨）** / B 管理画面内で一操作ごとに即保存。A は取消ができ、保存中との組み合わせを減らせるが1回の保存操作が増える。B は直接的だが連打/保存中の受付規則と失敗表示の設計を変更する必要がある。
3. **保存先**: A **本棚直下の専用ファイル（推奨）** / B profile内の別ストア。A は本棚と一緒に移せるが本棚への書込権限が必要。B は読取専用本棚でも使えるが順はそのprofileにだけ属し、別PC/portable/ルート移動時の引継ぎが別作業になる。
4. **既存環境と追加本の規則**: A **初回は名前順のまま、最初の手動保存後は新規本を末尾、外部未知本は末尾グループ内の名前順（推奨）** / B 未保存でも初回読込時に固定順を作り、以後は常に末尾へ追加。A は保存なしの旧環境の従来動作を保ち、読取だけでファイルを書かない。外部未知本も発見時系列で固定したい場合は B 相当の自動書込が必要で、Remote/読取専用との契約も変わる。最初の旧データ読込の表示自体は両案とも現在の名前順とする。
