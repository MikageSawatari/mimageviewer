## N01 [P1 / R12修正による退行] パッド切断時、別窓のフォルダ評価がメインのフォルダへ確定される

- 主な場所: `src/app/gamepad_input.rs:3515` (`end_gamepad_input_session` の `commit_ring_picker` 呼び出し)。
- 通常のパッド操作は `app.rs:68080–68114` で sample → 配送先決定 → active contextのmount → dispatch の順。しかし設定OFF (`gamepad_input.rs:2293`) / 切断 (`2334`) だけはsample内で終了し、今回追加された確定処理を**rootのまま**実行する。
- `ring_picker` はApp-global。別窓のpickerを取り出せる一方、`finalize_live_picker_ratings` のContainerRating分岐 (`4590–4603`) はpickerのanchorでなく `preview_current_folder_rating` を呼ぶ。保存先は現在mount中の `current_container_rating_target()` (`app.rs:49416`) なので、別窓の所有者へは戻らない。
- 条件: メインでフォルダA (★2)、F12の独立viewerでB (★1) を開く。Bのリングでコンテナ評価を★4へプレビューしたままパッドを切断する。Bの★4に加えて、操作していないAまで★4へ書き換わる。UndoもA宛てにBの変更前値1を記録するので、Undo後もAの元の★2へ戻らない。
- 証拠: `routing_probe.py` は現ソースの終了・確定・評価finalize・Undo構築の4メソッドを変更せず抽出して実行。DB/Undo/UIの境界のみ代用し、Bで終了するcontrolは `A=2 B=4 undo=(B,1,4)`、実際のsample配置と同じAでの終了は `A=4 B=4 undo=(A,1,4)`。呼び出し順と本番の保存先解決もソースで照合した。HWND/実ゲームパッドでの検証ではない。
- 修正境界: 物理入力の保持解除と、所有contextの編集確定を分ける。終了イベントにもpickerの所有者を持たせ、通常の配送と同じ所有contextで確定する。単にpickerを捨てるとR12のUndo欠落へ戻る。別ページ/別フォルダの2窓と、切断/設定OFFの両方を回帰対象にする。

## N02 [P2 / R01残件] 見開きの可視高さが半画素になり、連結境界が1px重なる

- 主な場所: `src/ui_fullscreen.rs:4385–4392` (ページの相対Yを丸める部分)、`4430–4439` (丸め前のYからunit spanを算出)。
- `continuous_unit_drawn_span` は各ページの `-page.height/2 + drawn_band` のunionを取る。この高さは、上下端を違うページが決める見開きでは**整数物理pxにならない**。一方、描画配置は各ページの相対Yを丸めるため、spanと実際のunionが違う。unit間のoffsetは依然として丸め前spanの高さを使う (`27438–27440`)。
- 最小例: Original、100%表示、DPI100%、縦連結、見開き、間隔0。左501×1001の可視Yを `[0,0.6]`、右401×1000を `[0.5,1]` とする (左右で異なる余白トリム。トリム後も両ページは縦長)。計算上のspanは1000.5pxだが、ページ配置後の高さは1001px。繰り返し並べると隣接gapが `[-1,0,-1,0]` pxになり、一つおきに1px重なる。
- 証拠: `geometry_probe.py` / `geometry_cases.rs` / `geometry-probe.log`。現ソースのページサイズ型、paint band、量子化、unit配置、連結offsetをそのままコンパイルした算術検証。DPI100/125/150/200%、倍率1/.73/1.125、4回転、gap0/1/20、正負を含む5原点を検査。単枚奇偶混在は2,880境界すべて正常。見開きは2,880中480、左右異なるトリムの見開きは2,880中960でgap誤差が0.01pxを超える。最小例は上記の整数倍率で再現するので、浮動小数誤差のepsilon追加では解消しない。
- 修正境界: unit内部の各ページを実際に置いた整数物理pixelの帯からunion/spanを一度求め、その同じ配置・高さを連結offsetと描画が共有する。中心配置の中間値を長さとして使わない。単枚の奇偶テストだけでなく、見開き・左右非対称trim・Originalズームを含める。

## N03 [P2 / R14修正による退行] AIサイズ対象外の出力もruntime初期化失敗で止まる

- 主な場所: `src/ui_fullscreen.rs:34903–34908` と `src/materializer.rs:760–763`。
- `stage_requests_ai` は段・モデル・機能モードのみで判定し、サイズ上限を見ない。この判定直後にruntime必須とし、なければエラーを返すため、後段 `select_final_ai_models` の「サイズ対象外なら正常な無処理」へ到達できない。
- 条件: AI段 (または表示用補正段)、auto upscale選択、AI上限2048×2048未満、画像4096×2160、AI runtime初期化失敗。サイズ規則上はAIをスキップして通常の編集済み画像を書き出せるべきだが、一括/製本/外部個別実体化が失敗する。AI対象の画像で初期化失敗をエラーにするR14の修正と、AI不要の画像まで止めることは区別が必要。
- 根拠: `books.rs:327–350` は「上限外は正常な無処理」「段はここまで焼く意味で、必ずAIを通す意味ではない」と明記。実選択も `ai/final_pipeline.rs:78–90` で対象外ならNoneを返す。`ai_request_probe.rs` は本番公開関数で、2048×2048 / 4096×2160がサイズ対象外なのにruntime要求はtrueになることを確認した。実ORTの故障注入はしておらず、失敗分岐はソース照合。
- 修正境界: 合成時の実寸法で適用モデルが決まった後、AIを実行する場合だけruntimeを必須にする。AIが本当に必要な場合の失敗は返し、対象外を無条件失敗にも無条件AI適用にもしない。

## N04 [P2 / 再走査workerの追加確認] 走査完了がアイドル中の画面を起こさない

- 主な場所: `src/app.rs:18005–18009` (worker完了時の `tx.send(scan)`)、`18028–18035` (UI側poll)。
- watcherイベントはUIを起こすが、`poll_current_folder_watch` がdebounce期限を消費してscanを起動すると次の起床予約はなくなる (`17753–17771`)。workerは結果をchannelへ送るだけで再描画を要求しない。`external_rescan_pending` もフレーム末尾の再描画条件 (`69234–69315`) に入っていない。
- 条件: サムネイル読込済みの静止グリッドで、動画・アニメーション・パッド保持などの継続描画がなく、外部ソフトが画像を追加/変更する。走査が最後のUIフレームのpollに間に合わないと、完了済みの結果が次のマウス/キー入力・フォーカス変更・別の通知まで取り込まれない。新しい再走査予約もそのpollに依存する。
- 証拠は完了通知→受信→フレーム起床の全経路のソース照合。watchdog (`lib.rs:474`付近) は正常なidleを許し、定期的に再描画を起こす代用品にはならない。新しい通知予約のテストは明示ループで `poll_external_rescan` を繰り返すため、この欠落を検出しない。ネイティブidle実機再現は未実施。
- 修正境界: worker完了時に所有UIのwakerを通知する (再実行・失敗・キャンセルの終端も含む)。フォルダ走査をUIへ戻したり、常時高頻度描画にする必要はない。次の入力がなくても完了が取り込まれる検証を加える。

## N05 [P3 / R13残件] 9種類目以降の関連付けcacheは開き直しても更新されない

- 主な場所: `src/app.rs:53097–53100` (extensionを8件で打ち切る部分)。
- 修正は既存cacheを持つ拡張子も再列挙するようにしたが、世代ごとに常に先頭8種類で止まる。cache全体の失効や残りの要求キューはない。9種類目を右クリックして得た候補は保持され、その後のフォルダ再読込でも更新対象にならない。
- 条件: jpg/png/gif/bmp/tif/avif/heic/jxl/webpなど9種類以上があるフォルダで、9種類目の候補を一度cacheへ入れる。その種類のアプリを追加/削除してフォルダを開き直す。先頭8種類の順序が同じなら9種類目は古い候補のまま。空候補を覚えた場合も同じ。
- 証拠: `routing_probe.py` は本番 `poll_association_handler_prewarm` のメソッドをそのまま使用し、Shell列挙のみ `new-handler` を返す代用品へ置換。3世代の再読込後も選ばれる8種類は固定で、9種類目は `old-handler` のまま。実際のWindows関連付けの変更操作は行っていない。
- 修正境界: 8件を1バッチの上限にするなら残りも後続で処理するか、未更新cacheに明示的な鮮度を持たせる。承認済みR10の「cache missがUI同期」という応答性課題とは別で、これは既存cacheの鮮度が回復しない問題。
