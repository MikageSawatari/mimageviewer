## 1. 症状 — 連結読み + タッチは何もできない

実機報告 (2026-08-09) と `MIV_TOUCH_DEBUG=1` ログで確定した:

> 初回ヘルプで誤解したのと、連結読み中にスクロールできなかったため、たまたま画面全体に
> 見開き 2 ページのみが表示され、**連結モードであると認識することもできませんでした**。

連結読み (`continuous_reading_active_for_idx`) 中のタッチは:

- **左右タップでページが進まない** — `PageSide` は `if !continuous_active` で捨てられる
  ([ui_fullscreen.rs:17098](../src/ui_fullscreen.rs))
- **1 本指ドラッグでスクロールもできない** — 下記 §3
- したがって**画面が動かず、モードを見分ける手がかりも無い**

ログの裏取り: `PageSide` は **83 件**生成され、`surface_match=true` /
`owner=ViewerTapZone` / `drive=commands` / `pass_index=0` で正常に配送されている。
認識器と相関層に問題は無く、失敗は `ui_fullscreen.rs` の dispatch にある。

**⚠ これは初回ヘルプが防ぐはずだった「詰み」を、ヘルプ自身の誤った案内が作っていた**
(「左のページへ」と書いておいて何も起きない)。plan §5 の目的に照らして最優先で直す。

## 2. 左右タップで 1 ユニット進める (連結読みでも)

**タップは連結読みでもページを進める** (利用者判断 2026-08-09)。進む量は
**単ページなら 1 ページ、見開きなら 2 ページ** = **ページ表示のときとまったく同じ**。

### 2.1 新しいナビゲーション意味を発明しないこと

**キーボードが連結読み中に `KeyAction::FsPageNext` / `FsPagePrev` で行っているのと
同じ移動をさせること。** キー側はこの 2 つを**連結読みでもガードしていない**
([ui_fullscreen.rs:14034-14035](../src/ui_fullscreen.rs))。つまり
**連結読みでページ送りできないのはタップだけ**という状態である。

- 移動量は既存の `spread_page_nav(base)` をそのまま使う
- **移動の着地も既存経路に揃えること**。連結読みでは位置移動が
  `seek_to_continuous_page` ([ui_fullscreen.rs:8958](../src/ui_fullscreen.rs)) 経由に
  なるなら、タップも同じ経路に乗せる。**離散的なファイル切り替えとして着地させない**
- 左右の物理側と移動方向の対応は `fullscreen_click_nav_delta_for_side(left, rtl)` のまま

### 2.2 マウスは変えない

マウスのクリックページ送りは連結読み中は抑制されたまま
([ui_fullscreen.rs:17567](../src/ui_fullscreen.rs)) にする。**理由をコメントに残すこと**:

- マウスにはホイールという連続スクロールの自然な手段があり、離散移動を足す必要が薄い
- 既存コメントが挙げている抑制理由 (ズーム遷移の隙の誤クリック) は、
  **認識済みの tap には当てはまらない**。タップは偶発的な入力ではない
- plan §5.14-11 で既に「タッチとマウスで意図的に挙動を変える」前例がある

マウスにも入れるかは**別の判断**として残す。今回は触らない。

## 3. 1 本指ドラッグでスクロールできるようにする

### 3.1 なぜ効かないか

連結読みのドラッグ経路 ([ui_fullscreen.rs:17449](../src/ui_fullscreen.rs)) は

```rust
} else if continuous_active && primary_down && !cursor_in_panel {
    let pointer_delta = ctx.input(|i| i.pointer.delta());
```

と、**フレームごとの `pointer.delta()`** を使っている。これは
**ズーム中の 1 本指パンで既に踏んだのと同じ形**である
(plan §5.5「拡大中の 1 本指パン修正」2026-08-08)。あのときの修正は
**ページ表示側の分岐 (`!continuous_active` の枝) にしか入れておらず**、
連結読みの枝は当時のままになっている。

なお所有権は正しい。Viewer 面の 1 本指ドラッグは閾値超えで必ず
`ViewerPointerPassthrough` になる ([touch_input.rs:497](../src/touch_input.rs)) ので、
primary は抑止されない。**問題は移動量の取り方だけ**である。

### 3.2 直し方

**ズームパンで採った方式に揃えること。** egui の drag response から移動量を得る。

- 連結スクロールは**増分**を必要とする (`scroll_vertical_reading_by(delta.scroll)`) ので、
  ズームパンのように総量から一発で決められない。
  **直前に適用した総量を保持し、その差分を適用する**形にする
  (ズームパンが `fs_pan_drag_start` を持っているのと同じ考え方)
- ドラッグ開始フレームの移動量を捨てないこと。**タッチは 1 フレームに press〜move〜release が
  まとまって届く**ので、開始フレームを捨てると全移動量を失う
- `continuous_reading_drag_delta` の主軸 / 直交の分解と `mods.ctrl` の扱いは**変えない**

### 3.3 マウス無影響

**マウスのドラッグによる連結スクロールの挙動を変えないこと。** 現在マウスで動いている
以上、移動量の取り方を変えると体感が変わり得る。マウス経路で 1:1 追従が維持されることを
確認し、変わるなら報告すること。

## 4. 初回ヘルプは変更しない

**§2 と §3 の両方が入れば、ヘルプの文言は連結読みでもそのまま正しい。**

- タップ = 「左のページへ」/「右のページへ」 → 連結読みでも成立する (§2)
- ドラッグ = スクロール → タップとは別ジェスチャなので**競合しない**
- 連結読み中は**ズームモードが使えない** (`fs_zoom_mode_context_ok` が
  `reading_flow.is_paged()` を要求) ので、1 本指ドラッグの意味は「スクロール」に一意に決まる

したがって「単ページの場合はこう / 連結の場合はこう」の**併記は不要**
(利用者が懸念していた点。Step 2d で方向不変にした文言が、モード不変にもなる)。

**ヘルプの描画・文言・スナップショットに手を入れないこと。**
