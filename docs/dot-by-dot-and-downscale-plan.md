# 100%原寸のドットバイドット化と縮小リサンプルの改善 (v2.11.0)

**ステータス: 段階1〜4 は実装・レビュー・実機検収済み。段階5 は実装と自動テストを完了し、最終レビュー・実機検収待ち。実装 = Codex Sol / レビュー・検収 = ClaudeCode。**

利用者報告 (2026-08-03) を起点に、フルスクリーン表示の「原寸なのにぼやける」問題と、
「縮小するとモアレかぼやけの二択になる」問題をまとめて解決する。

---

## 1. 報告内容

v2.9.1 に対する報告 (原文要約):

- **条件1**: Windows のスケーリング 125% / 150% で、「拡大しない」を有効にし、画面解像度より
  小さい画像をフルスクリーンで原寸表示すると、画像がぼやける。
- **条件2**: Windows のスケーリング 100% で、「拡大しない」を有効にし、見開きのページ間隔に
  **奇数** (例: 1px) を設定して 2 枚を原寸・見開き表示すると、画像がぼやける。
- 左パネルのポストフィルタ「標準 (補間あり)」と「ニアレスト (補間なし)」を切り替えると、
  **原寸表示なのに画質が変わる**。
- Ctrl+S でキャプチャ保存すると保存画像はぼやけていないので、画面表示だけの現象。
- 「原寸表示の時は元画像に手を加えずそのまま表示してほしい」
- 別途: 縮小表示は v2.6.0 以前はモアレが目立ち、v2.7.0 以降はぼやけが目立つ。モアレ抑制を
  OFF にできてもモアレかぼやけの二択で根本解決にならない。他ビューアは Lanczos を選べる。

## 2. 原因

### 2.1 条件1・条件2・ポストフィルタ差は同一原因

**「原寸」を論理ポイント基準で定義しており、物理ピクセル基準になっていない。**

倍率を決めている箇所:

| 場所 | 内容 |
| --- | --- |
| [src/displayed_image_transform.rs](../src/displayed_image_transform.rs) `resolve()` | `FullscreenFitMode::Original => (1.0, ...)` |
| [src/ui_fullscreen.rs](../src/ui_fullscreen.rs) 見開き本体 | `FullscreenFitMode::Original => 1.0` |
| 同 detached frozen 見開き | `FullscreenFitMode::Original => 1.0` |
| 同 連結読み `continuous_unit_display_size` | `FullscreenFitMode::Original => 1.0` (加えて `Original => zoom` の別扱いあり) |
| `FullscreenFitScaleLimits::apply()` | `scale.min(1.0)` / `scale.max(1.0)` |

この `1.0` は「テクスチャ 1 texel = 1 **論理ポイント**」を意味する。egui の描画座標は論理
ポイントなので、実際の物理ピクセル数は `× pixels_per_point` になる。`pixels_per_point` は
OS の表示スケール × UI 表示倍率 (設定 → スケーリング)。

| Windows スケール | 1 texel が占める物理 px | 結果 |
| --- | --- | --- |
| 100% | 1.00 | 一致 (シャープ) |
| 125% | 1.25 | 4px 周期で補間が入る |
| 150% | 1.50 | 2px 周期で 50:50 ブレンド |

「拡大しない」も `scale.min(1.0)` が論理ポイント基準なので、高 DPI では実際には 1.25 倍に
拡大されている。これが条件1。

### 2.2 描画矩形が物理ピクセル境界に整列していない

表示経路にピクセルスナップが**一切ない**。`round_to_pixels` はグリッド一覧側にしかない。

- 単ページ: `egui::Rect::from_center_size(center, display_size * total_scale)` なので
  `min.x = (表示領域幅 - 画像幅) / 2`。差が奇数だと 0.5px ずれる。
- 見開き: `layout_spread_page_rects` が
  `visible_start_x = center.x - (left_w + spread_gap + right_w) * 0.5` で位置を決める。
  `spread_page_gap_px` を論理ポイントとしてそのまま使うため、**奇数だと合計が奇数になり
  0.5px ずれる**。これが条件2。
- 連結読み: ページ位置を `visible_x += page.visible_width() + page_gap` で累積するため
  同様。

0.5px ずれると LINEAR サンプラーが隣接 texel と 50:50 でブレンドし、**倍率 1.0 のまま
画像全体が最大にぼける**。

条件2 は間隔設定で顕在化しただけで、**画像サイズと表示領域サイズの偶奇が食い違えば
単ページでも同じことが起きる**。

### 2.3 ポストフィルタで見え方が変わる理由

`PostFilter::None` と `PostFilter::Nearest` は **CPU 処理が完全に同一** (`src.clone()`)。
違いは GPU サンプラーだけで、`needs_nearest_sampler()` が true のとき
`TextureOptions::NEAREST` (mipmap なし)、false のとき `DISPLAY_IMAGE_TEXTURE_OPTIONS`
(LINEAR + 完全 mip chain) を使う。

原寸表示でも倍率が 1.0 でない / 位置が半 px ずれているため、必ず GPU サンプリングが介在し、
サンプラーの差がそのまま見える。**利用者の観測は正しい。**

物理 1:1 かつ整数位置になれば、どのサンプラーでも結果は同一になる。

### 2.4 Ctrl+S 保存がシャープな理由

キャプチャはソース解像度のピクセル空間で処理される。GPU サンプラーを通らない。

### 2.5 縮小のぼやけ (モアレ抑制 ON 時)

原因は独立に 2 つある。

**(a) 各 mip レベルの中身** — `vendor/egui-wgpu/src/mipmap.wgsl` は面積加重の box 平均。
正しい box フィルタだが、通過域が垂れて阻止域が漏れる。段階的に重ねるほど劣化が積もる。

**(b) 2 レベルの線形補間 (trilinear)** — **こちらが主因で、mip を Lanczos で作っても直らない。**

例: 1600×2300 の漫画ページを 1440p にページ全体フィット → 倍率 0.62。

```
1 画面 px が 1.61 texel を覆う  ->  LOD = log2(1.61) = 0.69
出力 = 0.31 x level0 + 0.69 x level1
```

level1 は 1/2 縮小済みで 0.5×ナイキスト以上を捨てている。倍率 0.62 なら本来 0.62×ナイキスト
まで残せるのに、捨てた画像を 69% の重みで混ぜている。最悪は LOD ≈ 0.5 (倍率 0.707 付近)。

倍率がちょうど 1/2、1/4 のときだけレベルが純粋に使われるので、そこは Lanczos mip 化が効く。
しかし実使用でちょうど 2 のべき乗になることはまずない。

**したがって「mip 生成を box → Lanczos に変えるだけ」は採らない。**
`trilinear blend をやめ、表示サイズちょうどへ 1 回でリサンプルする`ことが必須。

## 3. 決定事項

### 3.1 「100%原寸」の意味を物理ピクセル 1:1 に変更する (既存動作の変更)

利用者判断 (2026-08-03) により、新モードを追加するのではなく**既存の意味を変える**。

- 画像ビューアの慣習として「原寸」「等倍」「100%」「ドットバイドット」「Actual Pixels」は
  画像 1 ピクセル = 画面 1 ピクセルを指す。論理ポイント基準では、この機能を選んだ瞬間に
  高 DPI では必ず補間が入り、機能の目的が達成できない。
- 「拡大しない」「縮小しない」も同じく物理基準になる。
- **副作用**: 125% 環境では画像が従来より 20% 小さく表示される。150% では 33% 小さくなる。
  これは意図した変更であり、`src/version_highlights.rs` の「重要な変更点」で告知する。
- UI 表示倍率 (設定 → スケーリング) を変えても原寸表示の物理サイズは変わらない (正しい挙動)。

### 3.2 縮小は案C (GPU リサンプル + 表示サイズのテクスチャ) を採用

案A (CPU Lanczos + 新キャッシュ層 + worker) は品質は出るが、リサイズ / ズームで
「暫定表示 → 差し替え」の二段構えが避けられず、ソフト → シャープの切り替わりが見える。
また 20〜50ms / 回をクリティカルパスに足す。

案C は表示サイズちょうどの自前 wgpu テクスチャを GPU 上で作る。所要 0.3〜5ms 級 (計算値、
spike で実測すること) なので worker もキャッシュ無効化も二段構えも不要。描画側は現状の
`paint_texture` (Mesh 4 頂点) のままなので、自由回転・表示トリムの UV crop・見開き・
連結読み・tint・クリップとの整合を取り直す必要がない。

### 3.3 フィルタは Lanczos3。縮小経路は 1 本化する

**フィルタ選定 (2026-08-03、実測により決定)**

CPU 参照実装で nearest / bilinear / mip+trilinear / Mitchell-Netravali / Catmull-Rom /
Lanczos2 / Lanczos3 を比較した。素材と結果は `C:\tmp\miv-downscale-compare\`
(バックアップ: `C:\home\mimageviewer_testdata_downscale\`)。

懸念だった Lanczos3 のリンギングを数値で確認した。**純黒白のエッジではオーバーシュートが
0/255 でクリップされて見えない**ため、網点トーン (中間調) と接する黒帯の縁で測定した。

| フィルタ | 縮小率 0.25 のハロー | 縮小率 0.41 のハロー |
| --- | --- | --- |
| bilinear / mip+trilinear (現行) | 0.0 | 24.1 / 24.6 |
| Mitchell | 2.7 | 17.9 |
| Catmull-Rom | 5.5 | 24.4 |
| Lanczos2 | 5.9 | 23.5 |
| **Lanczos3** | **9.0** (255 階調中 = 3.5%) | **14.3** (最小) |

- Lanczos3 のハローは最悪でも 3.5%。1px 幅なので実機では見えない (利用者確認済み)
- 現行の bilinear / trilinear が 0.0 なのはリンギングが無いのではなく、情報ごと潰しているため
- 0.41 のような中間的な縮小率では **Lanczos3 が最も余計な模様が出ない**
- 網点トーンでは現行 (mip+trilinear) と bilinear に残留格子 = モアレがはっきり見える。
  Mitchell / Lanczos2 / Lanczos3 は平坦になり正しい
- 細線 1px は現行では白飛びしてコントラストが落ちる。Lanczos 系は残る

**採用: Lanczos3。** サムネイル生成で既に Lanczos3 を使っているため、一覧とフルスクリーンの
見た目も揃う。Mitchell はリンギングが最小だがそのぶん軟らかく、元の「ぼやける」苦情へ戻る
方向。Lanczos2 は Lanczos3 に対する明確な利点が測定から出なかった。

**経路の一本化 (利用者判断 2026-08-03)**

保守とバグのリスクを下げるため、縮小の表示経路は 1 本だけにする。3 層に分けて扱う。

| 層 | 判断 |
| --- | --- |
| mip chain の生成 | **残す。** 比較表示 (wipe/diff) と 360 度パノラマが使い続ける |
| trilinear で表示する経路 | **削除。** ぼやけの主因なので残す理由がない |
| 設定 | 旧チェックと強度は削除。同一 Lanczos3 経路の支持幅だけを変える「縮小時のなめらかさ」を持つ |

つまり「mipmap をやめる」のではなく「**trilinear で通常静止画を最終表示するのをやめる**」。
mip 生成のコードとテストは比較表示と 360 度パノラマのために生きる。通常静止画の縮小は
Lanczos3 の 1 経路とし、「縮小時のなめらかさ」はその支持幅だけを変える。

**削除の順序 (利用者判断 2026-08-03、A案)**: ①Lanczos を実装 → ②spike で開発機 (RTX 4090) の
実測とタップ数上限の設計確認 → ③**同じリリース内で** trilinear 表示経路と設定を削除する。

低スペック GPU の実測は**行わない**。開発機が RTX 4090 のみで内蔵 GPU を実測できないため。
判断根拠:

- mIV は AI アップスケールを売りにしており、想定利用者のマシンは比較的高スペック
- ミップ前縮小でタップ数を有界にする設計 (§4.3) により、ソース解像度によらず
  30〜120M フェッチに収まる。理論上の最悪ケースは見積もりで押さえられる
- リリース間隔が短い運用なので、「重すぎる」という報告が来てから対応しても間に合う。
  経路を 2 本抱える期間を作るより素直

したがって旧経路を保険として残すことはしない。利用者から見れば経路は最初から 1 本。

## 4. 設計

### 4.1 物理ピクセル 1:1

- `DisplayedImageTransformInput` と `FullscreenFitScaleLimits` に実効 `pixels_per_point` を
  持たせ、上記 4 サイトへ配る。`Original` の倍率は `1.0 / ppp`、`apply()` のクランプも
  `1.0 / ppp` を基準にする。
- ppp は各サイトの近く (`ctx.pixels_per_point()`) から取れる。**detached / frozen viewport は
  ppp が異なる**ので、必ずその viewport の値を使うこと。main の値を流用しない。
- `fs_image_draw_rect_for_size` など自由関数は引数を追加して伝搬する。

### 4.2 ピクセルスナップ

**位置だけを丸め、サイズは丸めない。** サイズまで丸めると倍率が変わりアスペクトが狂う。

**実効の物理スケールが整数に十分近いときだけ適用する。** 非整数倍率ではスナップしても
意味がなく、ズーム中のカクつきの原因になるだけなので、この条件で自然に無効化される。

- 単ページ系: `DisplayedImageTransform::resolve` / `from_resolved_rect` の末尾 1 箇所に
  入れる (全経路がここを通る)。
- 見開き: `layout_spread_page_rects` を物理 px 単位で組み直す。
  **ページ間隔も `round(gap * ppp) / ppp` に量子化する** (条件2 の直接原因)。
- 連結読み: ページ位置の累積を都度丸める (累積誤差を持ち越さない)。
- クリップ矩形・hit rect・detached frozen の正規化矩形との整合を確認すること。

### 4.2.1 見開きの高さ合わせは 1:1 のとき行わない (2026-08-04 追加)

**背景**: 段階1・2 実装後の実機確認で、高さが 1px 違う 2 ページを原寸・見開き表示すると
**低い方のページだけがぼやける**ことが判明した。

見開きレイアウトは 2 ページの高さを揃えるため、低い方を拡大している。

```rust
let combined_h = ls.y.max(rs.y);
let left_w  = ls.x * (combined_h / ls.y);
let right_w = rs.x * (combined_h / rs.y);
```

800×1121 と 801×1120 を並べると、右ページの係数が `1121/1120 = 1.000893` になり、
**倍率そのものが非整数**になる。位置スナップでは救えない (倍率が 1:1 でないため)。
ポストフィルタの標準 ⇔ ニアレスト切り替えで右半分だけ見た目が変わることも確認済み。

同寸ページ (800×1120 × 2) では係数が両方 1.0 になり、奇数間隔でもシャープに表示される
ことを確認済み。したがって §4.2 のページ間隔量子化は正しく効いている。

**決定 (利用者判断 2026-08-04)**: **ユニットの実効物理倍率が整数近傍のときは高さ合わせを
行わない。** 各ページを自分の寸法のまま同じ倍率で描き、**縦は中央揃え**にする。

- 判定はスナップと同じ `physical_scale_is_near_integer` を使う。`Original` だけでなく、
  「拡大しない / 縮小しない」で 1:1 へクランプされた場合や整数倍ズームも同じ扱いになる
- 高さの違うページではノド部分に段差が出るが、これは 1:1 表示の正しい帰結として受け入れる
- 高さ合わせは「見開きを 1 枚の連続したページに見せる」ための機能であり、1:1 を約束する
  モードとは本質的に両立しない。スキャン漫画では数 px の寸法差が普通にあるため、
  そのたびに片ページがぼやける現状の方が実害が大きい

**あわせて直すこと**: スナップ判定がユニット全体の倍率で行われているが、各ページの実効倍率は
`total_scale × (combined_h / page_h)` である。高さ合わせを残す経路では**ページごとの実効倍率**で
判定すること。

**実装 (2026-08-04)**: 通常見開き、detached frozen snapshot、連結読みの見開きペアを、
ページ別サイズ・高さ合わせ係数・content bbox から同じ geometry を作る経路へ統一した。
フィット倍率は従来の高さ合わせ geometry から求め、その最終 `total_scale` が物理整数近傍なら
固有寸法 geometry へ切り替える。hit rect、clip、正規化座標、Zoom composite は選択後の geometry
から導出し、スナップ述語は各ページの実効倍率へ適用する。

### 4.3 GPU Lanczos リサンプル (案C)

**方式**: ページごとに表示サイズちょうどの自前 wgpu テクスチャを持ち、egui のテクスチャとして
登録する。中身は separable Lanczos3 の 2 パスで GPU 生成する。表示矩形が変わったら再生成する。

> **実装上の必須事項 その1 — 論理サイズと貼るテクスチャの分離**:
> 2026-07-08 の調査メモ (`git show 2b68c27f:docs/downscale-moire-lod-plan.md` §4.3) が
> 明示的に警告している罠がある。**当時 mipmap を選んだ最大の理由がこれ**だった。
>
> > `draw_fs_image` は `handle.size_vec2()` を画像の論理サイズとして使っており、この用法は
> > `ui_fullscreen.rs` 内に 10 箇所以上ある。縮小段のテクスチャをそのまま渡すと
> > 「画像そのものが 1/4 サイズ」と誤解し、**原寸表示・ズーム・ルーペ・pixel grid がずれる**。
>
> mipmap は mip level が 1 個の `wgpu::Texture` 内にあるため `size_vec2()` が level 0 の
> 寸法を返し続け、この問題を完全に回避できた。**案C は表示サイズのテクスチャを貼るので、
> この罠を正面から踏む。** `size_vec2()` は現在も 29 箇所 (`ui_fullscreen.rs` だけで) 使われている。
>
> 守るべき不変条件:
> - **レイアウト計算は元の画像サイズ (`source_size`) で行う**
> - **描画に使う texture handle だけ差し替える**
> - **UV は 0..1 のまま使う**
> - **ルーペは原寸固定** (拡大鏡なので縮小テクスチャではボケる)
> - **pixel grid は論理サイズ必須**なので縮小テクスチャの対象から外す
>
> 幸い当時より条件は良い。`src/displayed_image_transform.rs` が導入され、
> `source_size` と `texture_size` が別フィールドとして分離済み (54-55 / 68-69 行) なので、
> 分離点は構造として既に存在する。**段階3 の spike で、まずこの分離が成立するかを確認すること。
> 成立しないなら案C 自体を見直す。**
>
> **実装上の必須事項 その2**: 縮小時は **Lanczos カーネルを 1/scale 倍に引き伸ばす**こと
> (正しいローパス)。固定幅 6 タップで実装するとローパスが効かずエイリアシング (モアレ) が
> 残り、§3.3 の測定結果が再現しない。**これが最もよくある実装ミス**。CPU 参照実装
> `C:\tmp\miv-downscale-compare\gen_downscale_compare.py` の `resample_1d()` の
> `filt_scale` が該当箇所。

**ズーム中の挙動**

- Lanczos を「表示サイズちょうど」へ掛ける処理は倍率 s に対して連続。タップ数 `6/s` は整数へ
  丸めるが、増減する瞬間の端のタップは重みがほぼゼロなので、正規化していれば段差は出ない。
- trilinear は構造上なめらかだが常にボケている。Lanczos は各フレームでその倍率の最適解を
  出すので、**ズーム途中のどの倍率でも現行よりシャープ**になる。案A のような
  「暫定表示 → 差し替え」の二段構えも発生しない。
- **唯一の不連続点はミップ前縮小のレベル切り替え。** 通常の閲覧倍率 (0.25〜1.0) では
  level 0 から直接リサンプルするのでレベル切り替えが起きない。1/4 未満まで縮小したときだけ
  発生し得るので、**前縮小を使う閾値を下げる + 境界にヒステリシスを入れる**こと。
- シャープなフィルタは高周波を残すため、ズーム中にトーンがわずかに「サラサラ」動いて
  見える可能性がある (over-blur していた trilinear には無かった挙動)。面積を正しく積分するので
  level 0 bilinear ほどではないが、spike で実際に見て確認すること。

**タップ数を有界にする前縮小**: Lanczos3 は縮小倍率 s に対して 6/s タップ/軸が必要。
極端な縮小でタップ数が発散するので、

1. `L = floor(log2(1/s))` の mip レベルまで前縮小し、残り比率を 0.5〜1.0 に収める
2. そこから表示サイズちょうどへ Lanczos3 リサンプル (6〜12 タップ/軸)
3. **trilinear blend はしない**

とする。通常の閲覧倍率 (0.25〜1.0) では level 0 から直接で足りる。mip chain は極端縮小用の
前縮小として残す。

### 4.3.1 旧経路と設定の撤去

§3.3 の順序 (実装 → 実測 → 削除) に従い、**同一リリース内で**次を削除する。

- `vendor/egui-wgpu` の `image_mipmap_sampling_enabled` / `image_lod_bias` による

**mip chain の生成そのもの (`vendor/egui-wgpu/src/mipmap.rs` / `mipmap.wgsl`) は残す。**

### 4.3.2 段階3 spike の結論 (2026-08-04)

**結論: 問いAは go、統合方式は C-1 を推奨する。** この spike 完了時点では
段階4の製品統合には未着手だったが、2026-08-04 に後述の構成で実装した。

#### 問いA — size_vec2() の分離

commit b38610d5 時点で size_vec2() はリポジトリ全体に 43 呼び出し、そのうち
ui_fullscreen.rs に 29 呼び出しある。全件を次のように分類した。

| 分類 | 呼び出し数 | 場所と用途 |
| --- | ---: | --- |
| 静止画の論理レイアウト。縮小 TextureHandle へ単純置換すると壊れる | 12 | ui_fullscreen.rs:5245/5246, 7780, 9074, 15686, 16501, 16516, 19240/19241, 19543, 19598、および app.rs:37916。単ページ、見開き、連結読み、detached frozen snapshot の寸法 |
| 静止画の論理情報または原寸参照。単純置換すると壊れる | 6 | ui_fullscreen.rs:4253, 10265, 10303, 10356, 10465, 19041。縦横判定、原寸/GPU clamp 表示、AI 出力寸法、ルーペ |
| 縮小テクスチャの対象外 | 25 | animated frame、thumbnail、動画、detached 診断ログ、UI preview、grid、Text UI、設定画面、thumb quality、comic lab |

したがって、**既存 TextureHandle を表示サイズの TextureHandle で置き換える素朴な案は no-go**。
一方、C-1 は次の ownership 境界にすれば分離できる。

1. 元の TextureHandle と各 cache は一切置き換えず、size_vec2() の owner として残す。
2. DisplayedImageTransform は元ハンドルの論理寸法から従来どおり解決する。
3. Lanczos 出力は wgpu texture と登録済み TextureId の typed resource として別に持つ。
4. DisplayedImageTransform::paint_texture に渡す TextureId だけを出力側へ差し替える。
   同メソッドは実テクスチャ寸法を読まず、0..1 の UV と任意の TextureId だけを Mesh に載せる。

egui-wgpu の公開 Renderer::texture から managed level 0 の wgpu texture を参照でき、
Renderer::register_native_texture で Rgba8Unorm の出力を登録できることも spike の型検査で確認した。
新規 vendoring は不要。

ルーペは現在の resolve_fs_processed_texture → 元 TextureHandle の経路をそのまま使い、
Lanczos TextureId を渡さない。pixel grid はユーザー拡大が 1 倍超のときだけ描かれるため、
§4.4 の縮小分岐と排他的であり、同様に元ハンドルの論理寸法を使い続けられる。

分離そのものの段階4工数は 1〜2 日程度。単ページだけでなく見開き・連結・holdover・detached
snapshot を同じ typed paint resource に通し、別の bool / Option を増やさないことが条件。

#### 問いB — C-1 を推奨

**C-1 (register_native_texture + paint TextureId の差し替え) を採る。**
既存 DisplayedImageTransform が自由回転、表示トリム UV、見開き、連結読み、tint、clip、
source↔screen 写像を既に所有しており、その最後の TextureId だけを交換できるため。

C-2 は size_vec2() から独立できるが、CallbackTrait 側で同じ geometry、clip、tint、trim、
自由回転、ページごとの paint order を再実装することになる。表示 transform の owner が二重化し、
段階4の回帰面と detached rework への波及が C-1 より大きい。

#### 問いC — RTX 4090 実測

開発専用 gpu_lanczos_spike を追加し、mImageViewer 本体を起動せず DX12 で測定した。
実装は vertical → horizontal の separable 2 pass。縮小時の support は各軸で 3/scale、
すなわち最大タップ数を約 6/scale へ引き伸ばす。中間 texture は Rgba16Float とし、
負のローブを pass 間の Rgba8 clamp で失わない。最終出力だけ register_native_texture が要求する
Rgba8Unorm とした。

素材は src_2480x3508.png。各測定は 5 回 warmup 後に 50 回を 1 timestamp query 区間で測り、
独立 4 run の中央値を採った。mip 有効時は brief 指定どおり
L = floor(log2(1/s)) を適用した。

| 縮小率 | 経路 | mip level | 残り比率 | 最大タップ (縦/横) | 実 texture fetch | GPU 時間中央値 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 0.63 | level 0 直接 | 0 | 0.630 | 10 / 10 | 85.0M | 0.164 ms |
| 0.63 | mip 前縮小 | 0 | 0.630 | 10 / 10 | 85.0M | 0.168 ms |
| 0.41 | level 0 直接 | 0 | 0.410 | 15 / 15 | 73.5M | 0.193 ms |
| 0.41 | mip 前縮小 | 1 | 0.820 | 8 / 8 | 23.7M | 0.047 ms |
| 0.25 | level 0 直接 | 0 | 0.250 | 24 / 24 | 65.1M | 0.136 ms |
| 0.25 | mip 前縮小 | 2 | 1.000 | 5 / 5 | 5.4M | 0.027 ms |

ミップ前縮小を使えば残り比率は 0.5〜1.0、実ループの最大タップは 5〜10、
fetch は 5.4〜85.0M に収まり、§4.3 の 30〜120M 目安と同じくソース解像度に対して有界になる。
0.25 の 5 tap は倍率がちょうど 1.0 で support 端のゼロ重みを fetch しない実装上の値。

#### CPU 参照との品質差

GPU 出力を full/r<率>_lanczos3.png と全画素比較した。

| 縮小率 | 経路 | MAE | RMSE | 最大差 | 2 階調超の画素 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 0.63 | level 0 直接 | 0.0194 | 0.1393 | 1 | 0% |
| 0.41 | level 0 直接 | 0.0258 | 0.1608 | 1 | 0% |
| 0.25 | level 0 直接 | 0.0304 | 0.1744 | 1 | 0% |
| 0.41 | box mip level 1 → Lanczos | 4.3752 | 10.1723 | 111 | 29.48% |
| 0.25 | box mip level 2 → Lanczos | 3.8615 | 10.1112 | 97 | 24.33% |

level 0 直接経路は float64 の CPU 参照と最大 1 階調差であり、カーネル引き伸ばしを含めて
参照実装を再現した。したがって網点の平坦化と 1px 細線の保持は CPU 参照と数値上同等。

一方、現行 box mip を 0.41 / 0.25 で先に使うと、後段が Lanczos でも full-resolution
Lanczos 参照とは一致しない。これは固定 6 tap の問題ではなく、box 前縮小で情報を先に失うため。
§4.3 の「通常の閲覧倍率 0.25〜1.0 は level 0 から直接」と整合する結果なので、
**段階4では少なくとも 0.25〜1.0 を直接 Lanczos とし、mip 前縮小は 0.25 未満の極端縮小だけに
限定する**。切替閾値とヒステリシスは段階4で決める。brief の L 式は mip 前縮小を有効にした
ケースの計測としては確認済みだが、0.41 / 0.25 の通常経路へ無条件適用しない。

#### ClaudeCode 検収時の追加結論 — mip 前縮小は全面的に不要 (2026-08-04)

spike の実測値は、**separable Lanczos の縮小コストがソース画素数で有界**であることを示している。
測定値と次の式が完全に一致する (ソース 2480×3508 = 8.70M px)。

```
fetch 数 ≈ 6 × W_src × H_src × (1 + s)        s = 縮小率
  s=0.63 → 52.2M × 1.63 = 85.1M   (実測 85.0M)
  s=0.41 → 52.2M × 1.41 = 73.6M   (実測 73.5M)
  s=0.25 → 52.2M × 1.25 = 65.3M   (実測 65.1M)
```

pass1 (縦) の出力は `W_src × H_dst`、タップは `6/s` なので、両者の s が打ち消し合って
**s に依存しない**。pass2 は `s` に比例する。つまり **縮小率が小さくなるほどコストは減る**。
タップ数が発散する、という §4.3 当初の前提は誤りだった。

mIV は表示テクスチャを長辺 8192 へ clamp している (`clamp_dynamic_for_gpu`) ため、
直接経路の最悪ケースも有界になる。

```
最大ソース = 8192 × 8192 = 67.1M px
最大 fetch = 6 × 67.1M × 2 = 805M
RTX 4090 の実測スループット (85.0M / 0.164ms = 518M fetch/ms) → 約 1.6 ms
```

したがって **mip 前縮小は不要**。加えて box mip 経路は品質が明確に劣る
(MAE 3.86〜4.38、最大差 97〜111、2 階調超が 24〜29%)。

**決定: 段階4 では mip 前縮小を実装しない。全縮小率で level 0 から直接 Lanczos する。**

これにより次が同時に消える。

- 品質の崖 (切替点で box mip の劣化が入る)
- **ズーム中の唯一の不連続点** — §4.3 で懸念していた mip level 切替の pop
- 切替閾値とヒステリシスの設計・実装 (段階4 見積もりの「mip 閾値/ヒステリシス」項目)
- mip chain の品質に対する依存

残る考慮点:

- 低スペック GPU では最悪ケース (8192² のソースを小さく表示) が 20〜40ms 級になり得る。
  ただし再生成は**表示矩形が変わったときだけ**で、静止した閲覧中は発生しない。
  §3.3 の A案 (高スペック機を想定し、報告が来たら対応) の範囲内として受容する。
- 通常静止画の Lanczos 経路自体は mip chain を参照しないが、比較表示 (wipe/diff) と
  360 度パノラマは従来の mip chain を使い続ける。旧 trilinear 経路と設定を含む削除判断は
  **段階5**へまとめ、段階4では既存 `DISPLAY_IMAGE_TEXTURE_OPTIONS` を変更しない。

### 4.3.3 縮小のなめらかさ設定 (blur factor) — 2026-08-04 決定

**背景**: 段階4 の実機確認で網点トーンに若干の残留モアレが見えるとの報告。
Lanczos3 は理想ローパスではなく阻止域に漏れがあるため原理的に残る。

#### 一度出した lanczos4 推奨を撤回する

当初「lanczos4 はローブ数が多く理想 sinc に近いのでモアレもシャープさも改善する上位互換」と
判断したが、**軸に平行 (0°) のトーンだけで測った誤りだった。**

超サンプリング (8x) の正解画像との MAE で測り直した結果 (縮小率 0.41):

| ケース | l3 b1.00 | l3 b1.10 | l3 b1.20 | l4 b1.00 | l4 b1.10 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 規則 4px 0° | 54.72 | 55.70 | 56.36 | 55.31 | 56.34 |
| 規則 4px **45°** | 59.16 | 49.80 | **44.65** | **64.60** | 51.23 |
| 規則 4px 15° | 43.46 | 41.88 | 42.09 | 42.41 | 42.21 |
| 規則 3.3px 30° | 35.35 | 33.52 | **32.85** | 34.42 | 33.47 |
| スキャン風 45° | 59.09 | 51.86 | **47.95** | **63.37** | 53.13 |
| 位置ジッタ 0° | 49.49 | 48.09 | **47.33** | 50.43 | 48.90 |
| **合計** | **301.28** | 280.85 | **271.22** | **310.53** | 285.28 |

**同じ blur なら lanczos4 は lanczos3 より一貫して悪い。** 45° 回転トーンで特に悪化する。

理由: リサンプルが **separable (縦横の 1D パス)** なので 2D の通過域はひし形になり、対角方向の
周波数を軸方向より通しやすい。ローブ数を増やして 1D の遮断を鋭くすると **対角成分をより多く
通してエイリアスする**。**したがって lanczos4 は採用しない。ローブ数は 3 のまま。**

#### 軸平行トーンは最悪ケース

検証素材 `src_2480x3508.png` のトーンは軸平行で、**フィルタ差が最も大きく出る最悪ケース**。
実際の漫画スキャンは 45° 前後の回転スクリーンが標準で位置・径のばらつきもあるため、
差はこれより小さい。この点は `C:	mp\miv-downscale-compareull\README.txt` にも明記した。

#### blur factor が唯一有効なつまみ

カーネル支持幅を `1/scale` より広げて遮断周波数を下げる (ImageMagick の `filter:blur` と同じ)。
**回転・不規則を含む全ケースで一貫して効く。**

```
filt_scale = (1.0 / scale) * blur
```

**上限は 1.30。** 縮小率で最適点が異なり、上げすぎると悪化する。

| blur | 0.41 誤差合計 | 0.63 誤差合計 | 0.41 の 0°線コントラスト |
| ---: | ---: | ---: | ---: |
| 1.00 | 246.56 | 265.86 | 135.5 |
| 1.10 | 225.15 | 248.08 | 125.8 |
| 1.20 | 214.86 | 236.01 | 112.9 |
| **1.30** | 210.92 | **233.17** (最小) | 97.0 |
| 1.40 | 209.43 | 239.21 (悪化) | 79.3 |
| 1.50 | 208.77 | 251.16 | 61.5 |
| 1.60 | 208.49 | 266.82 (b1.00 より悪い) | 44.2 |

縮小率 0.63 では 1.30 を超えると**表現できるはずの周波数まで削り始め**誤差が増加へ転じる。
1.60 では何もしないより悪い。したがって 1.30 より上を選ばせない。

#### 設定として公開する (§3.3 の「設定を持たせない」を一部改める)

§3.3 で「Lanczos ならトレードオフ自体が消えるので設定不要」としたが、**残余のトレードオフは
実在した**のでその前提は誤りだった。ただし旧設定とは性質が違う。

| | 旧設定 (削除) | blur 設定 |
| --- | --- | --- |
| 実体 | **2 つの描画経路**の切り替え | 同一経路の**スカラー 1 個** |
| 検証マトリクス | 倍化する | 増えない |
| 保守コスト | 高い | ほぼゼロ |

経路は 1 本のままなので、§3.3 で設定を消した論拠 (保守とバグのリスク) は blur には当てはまらない。

**決定 (利用者判断 2026-08-04)**:

| 項目 | 内容 |
| --- | --- |
| 場所 | 左パネル (旧「縮小表示のモアレを抑制する」の位置) |
| 表示名 | **縮小時のなめらかさ** |
| 範囲 | 0% 〜 100% を blur **1.00 〜 1.30** にマップ、10% 刻み |
| 既定 | **0% (blur 1.00)** |
| フィルタ | Lanczos3 固定 |

既定 0% の理由: ①「勝手にぼかすな」という報告への対応なので既定で意図的にぼかさない
②旧既定はモアレ抑制 ON (ぼやけ側) だったので 0% が最も大きな改善を体感できる
③左パネルにあるので気になる内容に当たったその場で上げられる。

UI 文言は処理内容ベースにする (「モアレ抑制」のような評価語を避ける)。

#### 段階5の実装結果 (2026-08-04)

- Settings は 0〜100 の整数値を所有し、読込時に 0〜100・10刻みへ正規化する。
- blur は 1.0 + percent × 0.003 で一意に求め、0 / 50 / 100% は 1.00 / 1.15 / 1.30 になる。
- シェーダーは filter_stretch = max(1, 1 / scale) × blur とし、支持幅と重みの距離を同じ
  filter_stretch から導出する。CPU 側のフェッチ数見積りも同じ式を使う。
- 正規化済み percent を出力 resource と cache key に含める。値が変わったときは viewer
  context が所有する Lanczos 出力 cache を消去し、保持中の旧出力を同じ目標寸法として
  再利用しない。
- 旧 2 フィールドは Settings に残さず、serde の未知フィールドとして読み飛ばす。旧値を含む
  JSON の読込と、再保存時に旧キーが出ないことを回帰テストで固定した。
- Lanczos4 は採用せず、支持幅上限は実測どおり blur 1.30 に固定した。

#### 段階4の製品統合結果 (2026-08-04)

製品経路へ次の構成で統合した。

- `FullscreenPaintResource::{Direct, Resampleable, Lanczos}` を表示用の単一 typed resource とした。
  全 variant が元の `TextureHandle` を保持し、論理寸法は常にそこから取る。Lanczos variant
  だけが別所有の native `TextureId` を `paint_texture` へ渡す。
- 単ページ、見開きの左右、縦 / 横連結読み、page transition、nav / colorize holdover、
  detached single / spread / continuous frozen snapshot と keep-alive backstop を同じ resource
  へ接続した。比較表示、360 度パノラマ、ルーペ、pixel grid、thumbnail、animated、動画は
  対象外のまま。
- cache key は page idx、元 `TextureId`、`items_generation`、ページ別
  `input_generation`、目標寸法。回転とトリムは full source のリサンプル結果を変えず、
  `DisplayedImageTransform` が geometry / UV を所有するため key に含めない。
- 目標寸法は CPU 参照と同じ `floor(source × physical_scale)` を基準にし、量子幅は 1 px とした。
  同一 source / generation の直近 2 寸法と context 全体 64 entry の LRU を保持し、往復リサイズ
  の再生成を抑える。mip 前縮小、切替閾値、ヒステリシスは持たない。
- 出力は `Arc` 所有とし、cache / holdover / detached snapshot の最後の owner が消えた時点で
  `Renderer::free_texture` を 1 回だけ行う。cache は `ViewerContextBundle` に属し、
  fullscreen close、source 一括 invalidation、context swap / park、連結読み keep-set と同じ
  lifecycle で clear / retain する。
- 出力は実寸・mip なしの `LanczosOutputs` として共有 VRAM 会計へ加え、`TextureId` で
  重複排除する。perf log は生成ごとの source / target、推定 texture fetch 数、
  encode + submit の CPU 時間、context 内の累積再生成回数を記録する。

量子化候補は、量子化寸法で Lanczos3 を生成後、参照寸法へ線形補間する条件で
`full/r*_lanczos3.png` と比較した。

| 量子幅 | 0.63 | 0.41 | 0.25 |
| ---: | --- | --- | --- |
| 1 px (採用) | GPU spike MAE 0.0194 / 最大差 1 | MAE 0.0258 / 最大差 1 | MAE 0.0304 / 最大差 1 |
| 2 px | 参照寸法と同じ | 参照寸法と同じ | MAE 2.4367 / 最大差 77 |
| 4 px | MAE 7.8907 / 最大差 120 | MAE 3.3641 / 最大差 98 | MAE 2.2496 / 最大差 73 |

2 px でも参照寸法が奇数のケースでは品質基準を大きく外れるため、再確保削減より
最大 1 階調差の維持を優先した。残リスクは、低速 GPU と連続リサイズで exact target の
再生成頻度が高くなり得ること。実機計測は perf log の再生成回数・CPU submission 時間と
段階3の GPU throughput を併用して評価する。旧 trilinear と設定の削除は段階5で行う。

### 4.3.4 EWA (Jinc) の再測定 — 過去の測定を撤回 (2026-08-04)

利用者経由で「MPC-BE / MPC Video Renderer の Jinc2m が良い」という意見が来たため、
分離型 Lanczos3 と EWA (Jinc) を測り直した。**その結果、本セッション前半で記録した
「EWA は市松で分離型より悪い (218.99 vs 89.78)」は誤りだったと判断する。**
当時のスクリプトは残っておらず再現できないが、今回の測定では同じ市松で EWA の方が
1 桁良い (0.14 vs 3.10)。当時の実装は縮小時にカーネル半径を `1/scale` へ広げていなかった
可能性が高い。以後 EWA の評価は本節の数値を基準にする。

再生成: `C:\tmp\miv-downscale-compare\gen_jinc_compare.py` /
`gen_jinc_angles.py` (バックアップ: `C:\home\mimageviewer_testdata_downscale\`)。

**Jinc とは**: `jinc(x) = 2·J1(πx)/(πx)` (J1 = 第1種ベッセル関数)。sinc が 1 次元の
理想ローパスなら、jinc は**円形の通過域**を持つ 2 次元の理想ローパス。EWA
(Elliptical Weighted Average) は 2 次元の半径 `r = hypot(dx,dy)` へ直接カーネルを
評価する非分離リサンプルで、通過域が円になる。分離型は `h(u)·h(v)` なので通過域は
**正方形**になり、対角方向はナイキストの角まで通す。この差が斜めのトーンで出る。

網点 (周期 4px) を 0.41 へ縮小したときの残留ばらつき (小さいほどモアレが少ない):

| 方式 | 0度 | 15度 | 30度 | 45度 | 不規則 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 分離 L3 blur1.00 (v2.11.0 既定) | 13.48 | 18.95 | 35.74 | 48.82 | 53.68 |
| 分離 L3 blur1.30 (なめらかさ100%) | 0.91 | 2.84 | 3.49 | 7.72 | 30.23 |
| EWA Jinc3 | 11.01 | 11.54 | 11.69 | 11.59 | 36.38 |

1px 斜線束のコントラスト (大きいほどディテールが残る):

| 方式 | 0度 | 30度 | 45度 | 60度 |
| --- | ---: | ---: | ---: | ---: |
| 分離 L3 blur1.00 | 123.5 | 140.5 | 162.6 | 140.5 |
| 分離 L3 blur1.30 | 87.6 | 118.3 | 146.2 | 118.3 |
| EWA Jinc3 | 123.4 | 129.7 | 145.1 | 129.7 |

**EWA Jinc3 は角度にほぼ依存しない** (11.01〜11.69)。円形通過域から予測されるとおりで、
分離型が 13→49 と角度で 3.6 倍悪化するのと対照的。しかも 0 度の細線コントラストは
分離 blur1.00 と同等 (123.4 vs 123.5) を保つ。**分離 blur1.00 に対しては全角度で優位。**

ただし万能ではない:

- **不規則トーン (実スキャン相当) では分離 blur1.30 に負ける** (36.38 vs 30.23)。
  Jinc を入れても「なめらかさ」設定は要る
- 斜めディテールは分離 blur1.00 より 8〜10% 落ちる (円形通過域が対角の角を落とすため)。
  トーンには有利、斜めの線画には不利という**選択的なバイアス**であって無条件の改善ではない
- **コストが約 6.5 倍**。0.41 縮小で分離が約 30 タップ、EWA は約 196 タップ。
  結果はキャッシュされるので静止時は一度きりだが、リサイズ中は毎フレーム走る

**用途による向き不向き**: MPC Video Renderer 自身の FAQ が「拡大は Jinc2m、
**縮小は Lanczos**」を推奨している。上の幾何と一致する。拡大では出力グリッドが
十分広いので円形通過域でも情報を失わず、斜めエッジの階段が出ない利点だけが残る。
縮小では出力グリッドが表現できるのは正方形の領域なので、円は表現可能な対角成分まで
捨てる。**掲示板の評価は動画の拡大についてのもので、mIV の主戦場 (縮小) とは逆方向。**

なお `Jinc2` の `2` はローブ数 (jinc の零点 2 本 = 支持半径 2.233)。`m` が何を指すかは
MPC-VR の FAQ に記載がなく未確認。アルゴリズムの分類は変わらない。

**v2.11.0 では採用しない。** 非分離シェーダは新規の GPU 経路で、タップ数が 6.5 倍に
なるためリサイズ中の実測が要る。現行経路は実機検証済みで、Jinc は「現行が壊れている」
ではなく「より良い候補がある」という位置づけ。v2.12.0 の検討項目とする
(`next-release-backlog.md`)。

### 4.4 拡大 / 等倍 / 縮小の境界

**ここを曖昧にすると両機能が干渉する。** 実効の物理スケールで 3 分岐する。

| 実効の物理スケール | 処理 |
| --- | --- |
| < 1.0 (縮小) | Lanczos リサンプル → 表示サイズのテクスチャを貼る |
| = 1.0 (ドットバイドット) | **リサンプルなし。テクスチャを直接貼る** |
| > 1.0 (拡大) | リサンプルなし。従来どおり bilinear / nearest (ポストフィルタ設定に従う) |

ちょうど 1.0 かつ整数位置に着地していれば、**どのサンプラーでも結果が同一**になる。
これは検証条件としても使える (後述)。

### 4.5 PDF の扱い

`PdfDisplayFitMode::Original` は「1 texel = 1 ピクセル」ではなく**ラスタライズ密度**の指定
(`viewport_w.max(viewport_h)`、最低 4096px)。PDF には native ピクセルが無いので「原寸」の
定義自体が別物である。

**本計画では PDF のラスタライズ密度の意味は変更しない。** ただし描画矩形のスナップと
Lanczos リサンプルは PDF ページにも同様に適用する (表示テクスチャとしては同じ扱い)。

### 4.6 連結読みの `Original` 別扱い

連結読みには `Original => zoom` という別の意味論の分岐がある。ここは個別に整理し、
物理 1:1 の定義と矛盾しないようにすること。

- `displayed_image_transform.rs` の既存 9 テストのうち、`scale_limits_are_part_of_the_resolved_geometry`

- 新規: 単ページで画像幅と表示領域幅の偶奇が食い違っても、原点が物理 px 整数へ着地すること。
- 新規: 連結読みで N ページ積み上げても累積誤差で原点が非整数にならないこと。
- 新規: 高さが 1px 異なる見開きを原寸表示しても両ページが物理 1:1 を保ち、各原点が物理 px

- Lanczos シェーダーの WGSL が parse / validate できること

- 「縮小時のなめらかさ」0 / 50 / 100% が blur 1.00 / 1.15 / 1.30 に対応すること。

## 9. 注意点・リスク

- **VRAM**: 元テクスチャ + 表示サイズテクスチャの二重持ちになる。表示サイズ側は小さい
  (2560×1440 RGBA = 14MB) が、連結読みの texel 予算
  ([final-composite-budget-thrash-plan.md](final-composite-budget-thrash-plan.md)) への計上を
  最初から設計に入れること。過去にここで thrash の実害が出ている。
- **リサイズ中の再確保**: 2 px 以上の切り上げ量子化は CPU 参照に対して最大差 73 以上となったため
  採用せず、1 px exact target と source ごとの直近 2 寸法 LRU を採用した。連続的に新しい寸法へ
  変わる間は毎フレーム再生成し得るので、低速 GPU では perf log で再生成回数と submission
  コストを確認する。
- **detached viewer**: [detached-rework-plan.md](detached-rework-plan.md) の凍結ルールが有効。
  detached の述語 / viewport 経路に触れる場合は、実装前にプラン §2 を読み、症状パッチでは
  なく構造的修正であることを ClaudeCode と合意し、触れた範囲を同プランに記録すること。
  段階4は既存 snapshot geometry を変えず typed paint resource と出力 lifetime を
  viewer context ownership に接続した。変更範囲は同プラン §11 に記録済み。
- **スナップとズームの相互作用**: 4.2 の「物理スケールが整数のときだけ」条件を守ること。
  無条件にスナップすると連続的なパン / ズーム中に 1px 単位でカクつく。
- **拡大側は本計画の対象外**: 100% 超の拡大は従来どおり。Lanczos 拡大は行わない。
