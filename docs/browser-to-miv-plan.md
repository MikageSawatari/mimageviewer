## 1. 要望

利用者 (2026-11-19):

> 「Chromeブラウザで、画像をｍIVに転送するなどして、３Dやアップスケールなどで閲覧したり、画像を保存できる機能。どのような方法がとれるのかの検討からだとおもいますが、ブラウザ観ているXポストの画像や、pixiv画像などを、ｍIVの機能を使って手軽に閲覧するような機能が欲しいです」

## 2. 結論 (推奨)

1. **段 1: 既存の「クリップボード取り込み」に「見る」を足す。** **利用者の決定 (2026-11-20)**: **段 1 単独では出荷しない。最初から段 2 (ブラウザに重ねる形) を作る** (§13 Q1)。利用者の言葉:「右下の小窓経由ではクリップボード自動保存とあまりかわらず不便なので、その状態ではリリースすることはないと考えてます。」以下の段 1 の記述は、検討の記録として残す。
   - Chrome で右クリック →「画像をコピー」→ 右下の小窓の **[見る]** → mIV の全画面に出る → D / U。
   - 画像はブラウザがすでに持っているものを使う。mIV は通信しない。拡張機能・ストア公開・レジストリ登録が要らない。
   - mIV へ開く経路は、2 重起動と同じ既存の activation チャネル 1 本に乗せる。要求はクリックの時点で作り、受付・保留・最新 1 件の選別・表示先の扱いは既存のものに従う (§7、§8)。
2. **段 2 (利用者の判断): Chrome 拡張「mIV で見る」。ブラウザの表示領域に mIV の窓を重ねて開く** (利用者の要望 2026-11-20、§9)。
   - 右クリック 1 回で、mIV の閲覧の窓がブラウザのページの部分に重なって開き、そこで D / U / 補正が使える。窓はビューワモードで決まる (フル機能なら一覧と連動する別ウィンドウで編集もできる、複数ウィンドウならそのモードの表示専用の窓、§9.1)。
   - 画像は mIV の新しい「ブラウザ閲覧」フォルダに自動で保存される。補正パネルで「このページ」を選んで付けた補正はその画像に残り、後でフォルダを開くと一覧の「補」の印で分かる。U のショートカットや、標準を選んだままの補正は既存どおり標準を変え、画像には残らない (§9.1)。
   - 拡張が画像の URL を自分で取得し (Cookie を付け、参照元にはページの origin を付ける。どのサイトにも同じ規則、§9.2)、中身を native messaging で中継 exe へ渡す。中継 exe が「ブラウザ閲覧」フォルダへ保存してから mIV へ渡す。mIV 本体は通信しない。当初の「downloads API で保存させる」案は、参照元を付けられず pixiv で失敗したので改めた (§9.11)。
   - 新しく発生するもの: Chrome ウェブストアへの公開と審査、拡張と中継 exe の保守、サイトごとの許可 (初回に Chrome の確認が出る、§9.6)、表示領域の位置の決め方 (標準の API が無いので右クリックの座標から求める、§9.3)、凍結中の別ウィンドウの経路への変更 (§9.5)。
3. **mIV が URL から自分で画像を取りに行く方式 (案 C・G) は推奨しない。** X の規約の「公開されたインターフェース以外の手段によるアクセス」の禁止に最も近い (§4.1)。
4. **送る画像は「ブラウザが表示している画像」に限る。** サイトごとに原寸の URL へ書き換える処理は作らない (§6)。
5. **画像は常に保存してから開く。** 「見るだけで保存しない」一時表示は作らない (状態を増やさないため、§7)。

### 3.2 クリップボード取り込みの今の動き (段 1 の土台)

- Chrome / Edge の「画像をコピー」は、`PNG` と `HTML Format`、`UniformResourceLocatorW` (画像の URL)、`Chromium internal source URL` (ページの URL) を入れる (2026-10-02 の S0 の記録、コピー操作は利用者、[clipboard-capture-plan.md](clipboard-capture-plan.md) §5.8)。
- mIV は `PNG` を保存し、出どころ (画像 URL・ページ URL) を Mark of the Web (`Zone.Identifier`) に書く (同 §10.2)。ファイル名は `<日時>-<ドメイン>_<連番>` (同 §2.6)。
- 保存したら小窓に「クリップボードの画像を保存しました [開く] [×]」を出す。**[開く] は保存先フォルダを一覧に開いてファイルを選ぶだけ**で、全画面にはしない。しかも一覧表示中にしか受け付けず、全画面・detached 中は小窓の文面を差し替えて何もしない ([app.rs:19934](../src/app.rs) `clipboard_capture_reveal_admitted`、同 §6.4)。
- 小窓の段階では通信しない。HTML から画像を取りに行くのは、利用者が選択ダイアログを開いたときだけ (同 §4-2)。

### 3.3 開いた後に 3D 写真・アップスケールが使えるか

- **3D 写真** (`FsDepthParallax`、既定キー D) は画像の閲覧画面 (全画面・ウィンドウ・F12 の別ウィンドウ) で使える。表示中のテクスチャから奥行きを推定するので、ファイルの置き場所や索引への登録は条件にならない。
  - 既存の機能条件はそのまま掛かる: 動画・アニメーション画像・見開き・連結読み・GPU 描画なし・編集中・ページめくり中は使えない。**別のウィンドウが 3D 写真を使っている間**も始められない ([depth_parallax.rs:174](../src/depth_parallax.rs)〜:225、[app/depth_view.rs:961](../src/app/depth_view.rs)、[depth-parallax-plan.md](depth-parallax-plan.md) §6.1)。
  - 初回はモデル (約 0.67 GB) の追加ダウンロードが要る。
- **AI アップスケール** は全画面で U / Shift+U / Alt+U。補正プリセット全体ではなく、実効の範囲 (ページ・お気に入り・全体) のアップスケールのモデルを次・前・なしに切り替える ([ui_fullscreen.rs:37224](../src/ui_fullscreen.rs))。`ai_feature_mode` と大きさの上限に従い、アニメーション画像には掛からない ([spec.md:3584](spec.md))。
- したがって、**受け取った画像を普通のフォルダに保存して既存の経路で開けば、保存場所・索引に関する追加の条件は無く、3D 写真とアップスケールのための専用のつなぎは作らなくてよい**。既存の機能条件は通常の画像と同じく掛かる。

- インストーラは Inno Setup で、レジストリを書かない (`[Registry]` 節が無い、[installer/mimageviewer.iss](../installer/mimageviewer.iss))。アプリもレジストリへは書かない (読み取りだけ)。

## 4. 規約・配布の一次情報

2026-11-19 に取得して確認した。引用は短い抜粋で、法的な判断ではない。**どの方式なら規約上問題ないと断定はできない**ので、ここでは「方式ごとにどの条項が論点になるか」だけを整理する。

### 4.1 X 利用規約 (Effective: October 9, 2026、https://x.com/en/tos)

- 公開されたインターフェース以外の手段によるアクセスを禁じる: "access or search … by any means (automated or otherwise) other than through our currently available, published interfaces"
- 注記: "crawling or scraping the Services in any form, for any purpose without our prior written consent is expressly prohibited"
- 複製・再利用は X の提供する手段で: "If you want to reproduce, modify, … distribute, … or otherwise use the Services or Content on the Services, you must use the interfaces and instructions we provide"
- 利用者へのライセンスは、X が提供するソフトウェアを X 上で使うためのもので、他人の投稿の保存を明示的に許す文言は見当たらない。保存を明示的に禁じる文言も見当たらない。
- 違反を "induce or knowingly facilitate others" した者も責任を負う条項がある (大量取得の損害賠償の節)。ツールの配布者に関係し得る。
- X API を利用者ごとのキーで使う方式は規約上取れない (X Restricted use cases「Multiple applications」、メモ `reference_x_api_byok_not_allowed`)。API を使わないなら Developer Agreement の当事者にはならないが、上の ToS の条項が直接の論点になる。

方式への当てはめ (解釈であり、X の公式見解ではない):

- **ブラウザが表示し終えた画像を、ブラウザの「画像をコピー」で取り出す** (案 A): 新しい取得は起きない。どの条項も名指ししていない。
- **拡張がブラウザの downloads API で画像の URL を改めて保存させる** (案 B): 取得はブラウザが行うが、表示とは別の取得になる。「ブラウザを使う」ことだけから「X が提供するインターフェースによる取得」とは言えず、上の条項がどう当てはまるかは未確定。A と同じ扱いには置かない。
  - 2026-11-22 に、B の取得は「ブラウザの中の拡張が、利用者の右クリック 1 回につき、表示中の画像の URL を 1 回取得する」形に改めた (§9.2-3)。ブラウザの外からの取得 (C・G) ではない点は同じで、表示とは別の取得である点も同じ。条項の当てはまりは引き続き未確定。
- **mIV がブラウザの外から画像 URL を直接取りに行く** (案 C・G): "other than through our currently available, published interfaces" に当たると読める余地が最も大きい。

### 4.2 pixiv (サービス共通利用規約 最終改訂 2026-06-22、https://policies.pixiv.net/)

- 第 14 条の禁止行為: 「投稿情報を、当該著作者（創作者）の同意なくして転載する行為」、「通常の範囲を超えて本サービスのサーバーに負担をかける行為」、「機械的にまたは短時間で大量に…操作を行う行為」。
- pixiv ガイドライン (最終改定 2026-03-18、https://www.pixiv.net/terms/?page=guideline): 「クローラーなどのプログラムを使って作品を収集する行為」を禁止。
- 登録商標のガイドライン (アプリ開発者向け): pixiv 製でない旨の併記を求め、「作品投稿者本人の承諾なしに作品を印刷/転載することは禁止します」。
- 閲覧者の私的な保存を明示的に許す文言も、禁じる文言も見当たらない。
- 画像サーバーが参照元 (Referer) を見ることは、ヘルプに「一部のページではサイトを表示するためにリファラを使う仕組みを導入しています」とあるだけで、画像配信の条件としての公式な明記は見つからなかった (https://www.pixiv.help/hc/ja/articles/235584528)。

設計への帰結 (案に依らない):

- **1 回の利用者の操作で 1 枚だけ**。一覧の一括取得・巡回・自動取得は作らない (クローラーとみなされる形を最初から持たない)。
- **mIV から外へ送らない・共有しない**。保存先は利用者の PC だけ。
- 拡張機能をストアに出すなら、説明文に「X・pixiv 製ではない」旨と、サイト名を宣伝に使わないことを守る (§11)。

### 4.3 Chrome ウェブストアと拡張機能の配布

- 禁止される製品: "Do not encourage, facilitate, or enable the unauthorized access, download, or streaming of copyrighted content or media." (https://developer.chrome.com/docs/webstore/program-policies/policies)
  - YouTube の動画ダウンロードを助ける拡張は、典型的な違反例として挙がっている (https://developer.chrome.com/docs/webstore/troubleshooting/)。
  - 動画ダウンローダの類は、違反ではなくても掲載推奨の対象から外され得る。
  - 段 2 の拡張は「ブラウザの『名前を付けて画像を保存』を 1 枚ずつ mIV へつなぐもの」として説明する。審査がどう判断するかは出してみないと分からない (未確認)。
- 単一目的: "An extension must have a single purpose that is narrow and easy to understand."
- 権限は最小に: "Request access to the narrowest permissions necessary"。広い host 権限を求めると審査が長くなる: "Reviews may take longer for extensions that request broad host permissions" (https://developer.chrome.com/docs/webstore/review-process)。
- `activeTab` は右クリックメニューの実行で付与され、インストール時の警告が無い。ただし付与されるのはそのタブの origin だけで、`pbs.twimg.com` のような別 host の画像の取得には host 権限が要る (https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)。
- `nativeMessaging` のインストール時の警告は "Communicate with cooperating native applications" (https://developer.chrome.com/docs/extensions/reference/permissions-list)。
- 登録は 1 回の登録料が要る (金額は公式ページに記載が無く未確認)。Trader / Non-Trader の申告が要り、個人は Non-Trader で登録できる。
- **ストア外の配布は事実上できない**。Windows ではローカルの CRX からのインストールは Chrome 33 から不可で、外部インストールの update_URL はウェブストアを指す必要がある (https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions)。ストア外のホストは Linux だけ。企業ポリシーでの強制インストールは Active Directory 参加が前提。「パッケージ化されていない拡張機能を読み込む」(デベロッパーモード) は開発用で、一般の利用者に頼む手順にはできない。
- Edge は Edge Add-ons に別途出す (無料)。Edge は Chrome の native messaging のキーも読む (https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging)。

### 4.4 Native messaging (https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

- 登録: `HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>` の既定値に manifest の完全パス。manifest は `name` / `description` / `path` / `type: "stdio"` / `allowed_origins` (拡張の ID、ワイルドカード不可)。
- 形式: UTF-8 の JSON の前に 32 bit の長さ。上限は host → 拡張 1 MB、拡張 → host 64 MiB。Windows では stdin/stdout を `O_BINARY` にする。
- `sendNativeMessage` は**1 メッセージごとに host のプロセスを新しく起動**する。第 1 引数は呼び出し元の origin。
- content script からは呼べない (拡張の service worker / ページから)。

### 4.5 PC 内の HTTP サーバーへ送る方式の制約

- Chrome 142 から、Web ページから 127.0.0.1 などへの通信には「ローカル ネットワーク アクセス」の許可が要る (https://developer.chrome.com/blog/local-network-access)。
- 拡張の service worker は、host 権限があれば対象外とされている (Google の LNA adoption guide、2026-05-18 版)。content script はページの origin として扱われる。

## 7. 状態の組み合わせを減らすための決定

CLAUDE.md「設計の簡素化」に従い、扱う組み合わせを先に減らす。

1. **開く経路は既存の 2 重起動 1 本だけ**。段 1 の [見る] は、同じプロセスの中から 2 重起動と同じ 2 つの呼び出し (open-path パイプへのパスの送信と activation event) を行う (§8.2)。段 2 は launcher を通し、同じ activation チャネルへ「表示先の指定 (重ねる位置) を型として持つ要求」を入れる (§9.2)。どちらも、小窓専用・拡張専用の受付を作らない。
   - このチャネルの受信側 ([startup_ops.rs:302](../src/app/startup_ops.rs)〜) はすでに、受付の判定 (`activation_open_precheck`: Remote の操作中は拒否、本の構成エディタ中は拒否、文書モーダル中はチャネルに残して閉じた後に開く、[startup_ops.rs:227](../src/app/startup_ops.rs))、受理できる要求の最新 1 件の選別、解決後の制限 (★固定の範囲外は拒否、[startup_ops.rs:918](../src/app/startup_ops.rs)) と表示先の採用 (既存の detached 設定・退避) を持っている。
   - 受信後の関数を直接呼ぶ形は採らない。保留と最新 1 件の選別はチャネルの受信処理が担っているので、別の入口から呼ぶとそれを通らない。MCP の `open_in_viewer` はモーダル中に保留せず拒否を返す別の受付で ([startup_ops.rs:203](../src/app/startup_ops.rs))、共有するのは解決・表示の下流だけ。
   - 新しい受付規則・画面ごとの分岐を作らない。
2. **保存してから開く**。開く時点でファイルはディスク上にある。「一時ファイルを表示中に消す」「保存ボタンを押す前に閉じた」などの組み合わせが生まれない。要らない画像は通常の削除で消す。
3. **1 回の操作で 1 枚**。まとめて送る・待ち行列は持たない。続けて送ったら、開く経路の「最新 1 件」に従う。段 2 では、保存の完了順が押した順と食い違わないよう、拡張は 1 件ずつ処理し、処理中に押されたものは断る (§9.1)。並行して保存して完了順で送る形は、通常の連続操作で古い画像が開くので採らない。古いものを取り消して置き換える形も、取り消しの途中の組み合わせが増えるので採らない。
4. **3D 写真・アップスケールは自動で始めない**。開いたら D / U を押す。自動で始めると、モデル未取得・GPU なし・アニメーション画像・大きさの上限などの組み合わせを開く処理が全部引き受けることになる (§13 Q3 で利用者が望めば、既存の D の入口判定をそのまま呼ぶ形で後から足す)。
5. **段 2 の中継 exe は 1 メッセージ 1 プロセス** (`sendNativeMessage`)。常駐しない・接続を保たない。
6. **mIV が起動していないとき**は、段 1 は何もしない (小窓は mIV の中のもの)。段 2 は launcher が `--browser-view` を付けたまま core を起動する (§9.2-7)。
7. **まれな失敗は割り切る** (CLAUDE.md の既定)。保存の失敗・パイプの失敗はログと通知だけで、再試行・回復の状態を持たない。

## 8. 段 1 の設計: 小窓の [見る]

> **利用者の決定 (2026-11-20)**: 段 1 単独では出荷しない (§2-1、§13 Q1)。この節は検討と独立レビューの記録として残す。段 2 と一緒に [見る] も入れるかは、段 2 の実装の範囲を決めるときに改めて判断する。

### 8.1 利用者向けの仕様

- 対象: 「画像がコピーされたら自動で保存する」が ON のとき (既存の設定、既定 OFF)。
- 保存完了の小窓を「クリップボードの画像を保存しました [見る] [開く] [×]」にする。
  - **[見る]**: 保存した画像を、2 重起動でファイルを渡したとき (Explorer の「送る」と同じ) とまったく同じく開く (取り込みフォルダの一覧 + その画像の全画面)。一覧表示中に限らず、全画面・detached の表示中からも押せる。前面化・受付の制限 (Remote の操作中・★固定の範囲外など)・表示先の設定 (detached 等) は既存の 2 重起動のもの。押すと小窓は閉じる。全画面では同じ月のフォルダの前後の取り込み画像へも移れる。
  - **[開く]**: 今までどおり (取り込みフォルダを一覧で開いて選ぶ)。リリース済みの動作なので変えない。
- 一覧の Ctrl+V (今のフォルダへ保存) には [見る] を足さない (Ctrl+V は mIV の中の操作で、保存先も一覧に見えているため)。
- HTML のコピー (画像を選んで保存) にも足さない。複数枚の選択の後に「どれを開くか」という新しい選択が生まれるため。

### 8.2 実装の要点 (案)

**[見る] は「そのファイルで mIV を 2 重起動した」のと同じことを、小窓の thread から行う** (独立レビュー第 2 回を受けた単純化、§7-1)。

- 2 重起動の core は、`single_instance::send_open_path_to_existing(path)` で open-path パイプへパスを送り、`single_instance::signal_activate_existing()` で activation event を立てて終わる ([lib.rs:1440](../src/lib.rs))。launcher も同じ 2 つを行う ([crates/launcher/src/main.rs:665](../crates/launcher/src/main.rs))。
- [見る] が押されたら、popup thread は次の順で処理する。App への新しい event・新しい要求の型・出どころの印は作らない。
  1. 表示中の保存完了の通知からパスを取り出し、通知を消費して小窓を閉じる。
  2. `send_open_path_to_existing(path)` でパスを送る。
  3. `signal_activate_existing()` で activation event を立てる。
- **保証は既存の 2 重起動と同じ「パイプの受信時点」のもの** (第 3 回 P2 で訂正)。
  - 要求は、パイプの listener thread がメッセージを受け取った直後に作られ、その時点の Remote の所有・取得世代・受信時刻が閉じ込められる ([single_instance.rs:557](../src/single_instance.rs))。クリックの時点ではない。クリックの後、受信の前に Remote が終われば、通常の要求として扱われ得る。これは 2 重起動で同じ操作をしたときと同じで、既存の Remote 所有の約束は保たれる。
  - App が後で event を処理する時点で要求を作る形 (第 1 回 P1) にはならない。
  - 受付 (Remote の操作中・本の構成エディタ中の拒否、文書モーダル中の保留、最新 1 件、★固定の範囲外の拒否) と、拒否されたときの知らせは、既存の 2 重起動のもの。
  - 前面化は既存の activation event の処理 (`window_activation::activate_main_window`、[single_instance.rs:754](../src/single_instance.rs)) が、App の受付とは別の thread で行う。受付の成否とは独立に前面化を要求するので、受付の前にも前面化し得る。
- パイプの名前は送信側・受信側とも同じ `process_names()` から作られ、`--data-dir`・ポータブル版でも一致する ([single_instance.rs:215](../src/single_instance.rs)、:391)。同じプロセスからの送信を拒む条件は無く、既存の終了処理にも自己送信がある (:482、独立レビュー第 3 回の確認)。
- popup thread は egui のメインの thread ではないので、送信がメインの描画を止めることはない。ただし popup thread は小窓のメッセージ処理 (`GetMessageW` / `DispatchMessageW`、[clipboard_capture/popup.rs:624](../src/clipboard_capture/popup.rs)) も担うので、同期の送信 (接続の待ちと書き込み、[single_instance.rs:442](../src/single_instance.rs)〜:466) の間は小窓の処理が止まる。手順 1 で先に小窓を閉じておくので、利用者に見える影響は無い見込み (未確認)。

**小窓は押したら閉じる**:

- [見る] を押したら小窓を閉じる。受付の結果を小窓へ返す経路は作らない (パイプは一方向で、結果は App の中で後から決まるため)。
- これで、[見る] と [開く] を続けて押す・古い応答が新しい通知を書き換える、といった組み合わせが生まれない。

**この形を選んだ理由と、失うもの** (CLAUDE.md「設計の簡素化」):

- 第 1 回の反映では、小窓専用の出どころの印・受付結果ごとの前面化・小窓への応答を足した。第 2 回のレビューで、それぞれに「受理をどの時点で確定するか」「応答の所有と終端」「保留の原因のモーダルが別の窓にある場合」の穴が出た。小窓専用の受付を作るほど組み合わせが増えるので、既存の 2 重起動と同じものにして、新しい受付の組み合わせを無くした。
- **失うもの**: 既存の [開く] は「受付できないときは前面化せず、小窓の文面で知らせる」が、[見る] は 2 重起動と同じく**受付の成否とは独立に前面化を要求する** (受付の前にも前面化し得る)。Remote の操作中などに押すと mIV が前に出て、既存の 2 重起動の知らせが出るだけになる。また、全画面を表示していた場合に、前面化で既存の「別のウィンドウへ切り替えたらフルスクリーンを閉じる」動作 (`fullscreen_keep_on_app_switch`、既定 OFF) が働くかは追跡していない (未確認)。どちらも、利用者が今 Explorer の「送る」で同じ操作をしたときと同じ振る舞い。
- 前面化は、利用者が小窓をクリックした直後なので許可される条件を満たす見込み (成功は保証されない、未確認)。失敗はログだけ。

**作らないもの**:

- 「保存したら自動で全画面に開く」設定。コピーのたびに mIV が前に出ると作業を邪魔するうえ、クリックの無いところからの前面化は Windows の制限で失敗しやすい (Windows の前面化の規則からの推定、未確認)。

### 8.3 detached viewer との関係

- この段は既存の 2 重起動を同じプロセスの中から起こすだけで、detached の述語や viewport の経路、受付の処理を変えない。表示先は既存の `MainNew` の採用と detached 設定・退避の処理に従う ([app.rs:4608](../src/app.rs)、[app.rs:72904](../src/app.rs))。
- 通常の全画面・一覧と連動する別ウィンドウ (F12)・一覧と連動しない画像の窓・複数ウィンドウモードのそれぞれで、2 重起動のパスがどの context に開くかは、この段では追跡していない。[見る] は 2 重起動と同じ結果になるので、この段で新しい表示先の判断は生まれない。マニュアルに [見る] の開き方を書くときに確かめ、2 重起動と違う説明は書かない。
- 実装で detached の述語・経路に変更が及ぶことが分かったら、CLAUDE.md の凍結ルール (構造的修正であることの双方合意と [detached-rework-plan.md](detached-rework-plan.md) への記録) に従う。

### 8.4 テスト (案)

- [見る] の処理が、通知を消費して小窓を閉じた後で、保存したファイルのパスで `send_open_path_to_existing` と `signal_activate_existing` を、この順で 1 回ずつ呼ぶこと (呼び出しを差し替えられる形にした handler-level test)。
- [開く] の今の動作 (一覧表示中だけ・選択するだけ・受付できないときは前面化せず文面を差し替える) が変わらないこと。
- 受付や表示先は既存の 2 重起動のテストが持っているので、[見る] 専用の受付のテストは作らない。

## 9. 段 2 の設計の骨子: 拡張「mIV で見る」— ブラウザの表示領域に重ねて開く (案 B)

利用者は 2026-11-20 に、段 1 を挟まず最初から段 2 を作り、拡張をストアで正式に公開する方向を決めた (§13 Q1・Q7)。この節は実装前の設計の骨子で、スパイク (§9.9) と凍結の決まりの手順 (§9.5) を経て詳しく設計する。

利用者の要望 (2026-11-20、この節の形を決めたもの):

> 「ブラウザの拡張で、画像をｍIVで見る、とすると、ブラウザの描画ウィンドウの範囲にｍIVのウィンドウを重ねて、その場所で見れるようにしたいです。この際は、ｍIV側に自動保存され、画像に編集などを加えた場合、後でｍIV側のフォルダを見れば分かる形にしたいです（クリップボードと同じ用に、ブラウザ閲覧用の保存フォルダを追加する）」

### 9.1 利用者向けの仕様

- 画像を右クリック →「mIV で見る」。
- 画像は mIV の**「ブラウザ閲覧」フォルダ**に保存される。既定は `ピクチャ\mimageviewer\browser\YYYY-MM` (クリップボード取り込みの `clipboard` と並ぶ。保存先は変更できる)。ファイル名と出どころ (Mark of the Web) は取り込みと同じ規則 (`<日時>-<ドメイン>_<連番>.<拡張子>`、[clipboard-capture-plan.md](clipboard-capture-plan.md) §2.6・§10.2)。
- mIV の閲覧の窓が、**ブラウザの表示領域 (タブ・アドレスバーの下のページの部分) に重なって**開く。そこで D (3D 写真)・U (アップスケール)・補正が使える。閉じる (Esc・×) と、mIV はメインウィンドウへフォーカスを送らない。その後ブラウザに戻るかは Windows の既定の動きによる見込みで、未確認 (§9.3)。複数ウィンドウモードの前の窓や、未起動から起動したときのメインウィンドウ (§13 Q16) は残る。
- **使う窓はビューワモードの設定で決まる** (§13 Q10・Q11):
  - **フル機能ウィンドウ (既定)**: 「一覧と連動する別ウィンドウ」(F12 の別ウィンドウと同じ種類) で開く。F12 の別ウィンドウを使わない設定でも、この 1 回だけ別ウィンドウで開く。編集できるのはこの種類だけ ([app.rs:71030](../src/app.rs)〜:71043 は設定とウィンドウの種類の両方を見て、独立した窓・複数ウィンドウモードの窓で編集の道具を止める)。一覧と連動するので、**メインウィンドウの一覧は「ブラウザ閲覧」フォルダへ移る**。
  - **ブラウザ閲覧の窓では F12 (別ウィンドウ表示の切り替え) を使えない** (§9.3、§13 Q17)。押すと「ブラウザから開いた窓では F12 は使えません」と知らせるだけにする。F11 (窓の中での枠なし全画面) は既存どおり使える。
  - **複数ウィンドウ**: そのモードの決まりどおり、開くたびに新しい窓を作る。窓は表示専用で、色調補正・ポストフィルタ・AI の表示設定は使えるが、編集の道具は使えない ([spec.md](spec.md) の複数ウィンドウの節)。前の窓は既存どおり残る (同じ位置に重なる)。
- **編集の跡が後で分かる範囲** (独立レビュー第 5 回 P1 で訂正):
  - mIV の補正は元の画像を書き換えない。**その画像だけに付けた補正 (ページ個別)** は、`adjustment.db` の `page_params` に画像の絶対パスをキーとして残る ([adjustment_db.rs:1](../src/adjustment_db.rs)〜、:610 `normalize_path`)。後で「ブラウザ閲覧」フォルダを開くと、その画像には一覧で「補」の印が付く ([app.rs:75946](../src/app.rs) `grid_edit_badges`)。ページ個別にするには、補正パネルで書き込む先に「このページ」を選んで補正する。パネルは、その画像にページ個別の設定が無ければ標準を最初に選んでいて ([ui_adjustment_panel.rs:255](../src/ui_adjustment_panel.rs))、選んでいる先へ書く (:14572)。標準を選んだままスライダーを動かすと、標準が変わる (独立レビュー第 6 回 P1 で訂正)。
  - **U / N / P のショートカットは、ページ個別とは限らない**。書き込む先は、その画像にページ個別の設定があればそれ、無ければ最も近いお気に入りの標準、それも無ければ共通の標準になる ([app.rs:94427](../src/app.rs) `resolve_adjust_scope`)。新しく保存した画像にはページ個別の設定が無いので、U は通常、標準を変える。そのため、ほかの画像にも効き、その画像に「補」の印は付かない。これは既存の動作で、段 2 では変えない (§13 Q15)。
  - サムネイルに反映されるのは色の補正だけで、アップスケールやポストフィルタは反映されない (同「サムネイル」の節)。別のファイルとして残したいときは、既存の書き出し (Ctrl+E) を使う。
  - 「ブラウザ閲覧」フォルダの中で mIV が名前を変えた場合は、補正の記録も付いて移る (既存の `rename_key_migration.rs`)。mIV の外で移動・改名した場合は、既存のフォルダの控え (`mimageviewer.dat`) と内容の一致による復元の範囲で戻る (既存の仕組み、[edit-content-identity-plan.md](edit-content-identity-plan.md))。
- 場所▼に「ブラウザ閲覧」を出す。表示条件と位置はクリップボード取り込みの項目と同じ規則 (連携が有効なときだけ、メインウィンドウの場所▼だけ)。
- 対象は静止画だけ (`contexts: ["image"]`)。アニメーション画像も開けるが、3D 写真は既存の条件どおり使えない (§3.3)。

### 9.2 流れ

1. 右クリック →「mIV で見る」。拡張の service worker は、何かを始める**前**に処理中にする (`chrome.storage.session`、§9.4-6)。
   - **サイトの許可を求める**: 同じクリックの処理の中で (ユーザー操作の扱いが切れる `await` より前に)、`permissions.request` で画像の origin とページの origin の host 権限を一度に求める (https://developer.chrome.com/docs/extensions/reference/api/permissions)。許可済みなら確認は出ない。画像の origin を断られたら、取得できないので理由をバッジで示して終える。ページの origin だけを断られたら、取得は続け、位置は推定にする (§9.3)。
2. **位置を読む**: `scripting.executeScript` でそのタブの上位フレームに小さな関数を入れ、`window.screenX` / `screenY` / `outerWidth` / `outerHeight` / `innerWidth` / `innerHeight` / `devicePixelRatio` と、記録しておいた直前の右クリックの座標 (§9.3) だけを読む。**ページの内容は読まない**。ページの拡大率は `tabs.getZoom`、窓の状態 (通常・最大化) は `windows.get` で読む。
3. **取得する** (2026-11-22 に改めた。改める前は `downloads.download` でブラウザに保存させる案、§9.11):
   - 右クリック情報の `srcUrl` (§13 Q4 によっては `linkUrl`) を、拡張の service worker が `fetch` で取得する (`credentials: "include"`、`cache: "no-store"`)。Cookie の扱いは、許可したサイトへの拡張の取得として Chrome に従う。
   - **参照元は、どのサイトでも常にページの origin (`https://<ページのホスト>/`) にする**。取得の直前に、その画像の URL と完全に一致し、タブに属さない要求 (`tabIds: [TAB_ID_NONE]`) だけに効く 1 回限りの規則 (`declarativeNetRequest` のセッションの規則、`modifyHeaders` で `Referer` を設定) を足し、取得が終わったら成否にかかわらず消す。ページの origin は、ブラウザ自身がそのページで画像を表示するときに既定の参照元の方針 (`strict-origin-when-cross-origin`) で送る値と同じで、パスや検索語は送らない。
   - **サイトごとの分岐は持たない** (利用者の決定 2026-11-22、§13 Q18)。コードにサイト名・ホスト名は書かない。
   - 上限: 中継 exe への 1 回のメッセージは 64 MiB まで (§4.4) で、中身は base64 で約 4/3 倍になる。宣言された大きさ (`Content-Length`) が上限を超えるものは読み始める前に、読んでいる途中で超えたものはその時点で止めて失敗にする。
4. `sendNativeMessage` で中継 exe へ `{ "v": 1, "kind": "open_bytes", "data_b64", "content_type", "page_url", "image_url", "view": { 2 で読んだ値 }, "zoom", "window": { 状態 } }` を送る。
5. **中継 exe** は検査 (§9.8) の後:
   1. 中身を復号し、形式を**中身の先頭のバイトから**決める (`content_type` は記録に残すだけで、拡張子の決定には使わない)。画像でなければ失敗を返す。
   2. 「ブラウザ閲覧」フォルダへ、取り込みと同じ名前の規則で書く。設定ファイルに書いてあるのは保存先の**基底のフォルダ**で (§9.7)、基底と月のフォルダ (`YYYY-MM`) は、無ければ中継 exe がこの時点で作る (取り込みが保存のときに作るのと同じ、[clipboard_capture/data.rs:487](../src/clipboard_capture/data.rs)〜:497)。まだ無いことは通常の状態で、失敗として扱わない。
   3. 書いたファイルに Mark of the Web (`ZoneId=3`・`ReferrerUrl`・`HostUrl`、userinfo と fragment を除く) を書く。名前の規則と記録の形式は取り込みと共有の部品にし、2 か所に書かない。
   4. 登録された launcher を `mimageviewer.exe --browser-view <位置> -- <書いたファイルのパス>` で起動する。
   5. 拡張へ「受け渡しまで成功」と、書いたファイルのパスを返す。
6. **要求の終端**: 拡張は、次のどれで終わっても処理中を解く。
   - 成功 (中継 exe が「受け渡しまで成功」を返した)。
   - 許可を断られた、位置の読み取り (2) の失敗、取得の失敗 (HTTP の失敗・上限超過・通信の失敗)、参照元の規則の追加・削除の失敗、中継 exe のエラーの応答、`sendNativeMessage` の失敗: バッジで理由を示して解く。再試行はしない。
   - 取得や受け渡しの途中で service worker が止まった場合 (まれ): 次に起きた worker が、残った参照元の規則を消し、その要求を失敗として 1 回だけ示す。受け渡しが済んでいたかは分からないので、やり直さない。
7. **launcher** (既存の「起動中なら渡す・未起動なら起動する」の分岐、[crates/launcher/src/main.rs:206](../crates/launcher/src/main.rs)):
   - 起動中なら、新しいパイプ `mImageViewerBrowserView_v1` (版の欄を持つ型付きの要求。既存の open-path パイプは版の欄が無くパスしか運べないので使わない) で core へ送る。**activation event は立てない** (立てるとメインウィンドウが前に出て、ブラウザを隠すため)。前面化の許可は `AllowSetForegroundWindow` で core へ渡す (MCP の中継と同じ、[crates/mcp-server/src/pipe.rs:244](../crates/mcp-server/src/pipe.rs))。
   - **起動中の core は launcher と別の版のことがある** (独立レビュー第 5 回 P8)。launcher は同梱の core を展開する前に既存のインスタンスへ渡すので ([crates/launcher/src/main.rs:206](../crates/launcher/src/main.rs))、更新した launcher と、更新前から動いている core の組み合わせが起こり得る。新しいパイプが無い・版が合わないときは、launcher はログに残し、「mIV を再起動してください」とメッセージを出して終わる。既存の open-path パイプへ黙って切り替えること、別の core を起動することはしない。再試行もしない。
   - 起動していなければ、`--browser-view` を付けたまま core を起動する。
8. **core**: パイプの listener が受け取った直後に、既存と同じ `ActivationOpenPath::received` で要求を作る。違いは、要求が表示先の指定 (`BrowserOverlay { 位置 }`) を型として持つことだけ。要求は既存の activation チャネルへ入り、**受付は 2 重起動と同じ** (Remote の操作中の拒否・本の構成エディタ中の拒否・文書モーダル中の保留・最新 1 件・★固定の範囲外の拒否、§7-1)。
   - **表示の意図は要求と一緒に、表示が決まるまで運ぶ** (独立レビュー第 5 回 P5)。今の受付は、選んだ要求からパスだけを取り出して下流へ渡し ([startup_ops.rs:348](../src/app/startup_ops.rs))、下流の持ち主 (`StartupOpenPathOwner::Activation`、[app.rs:4601](../src/app.rs)) は追加の情報を持たない。そこで `BrowserOverlay` を下流の持ち主の型に入れ、解決・一覧の復元待ち ([startup_ops.rs:1842](../src/app/startup_ops.rs))・表示の確定まで運ぶ。新しい要求に置き換えられた・拒否された・取り消された要求の意図は、その要求と一緒に捨てる。App に「次の 1 回だけ」の印を置く形は取らない。
   - **未起動のとき**は、`--browser-view` の引数から、初回の起動の持ち主 (`InitialStartup`、[startup_ops.rs:296](../src/app/startup_ops.rs)) に同じ意図を持たせる。メインウィンドウは通常の起動どおり表示され、その上に重ねる窓が開く (メインがブラウザの一部を隠し得る。§13 Q16)。
   - 受理されたら、2 重起動と同じく親フォルダ (「ブラウザ閲覧」の月のフォルダ) をメインの一覧に読み、そのファイルを開く。表示先は §9.1 のとおりモードで決まり、窓を新しく作るときに位置を種 (seed) として渡す (§9.3)。
   - **一覧の選択も、要求の画像に合わせたまま保つ** (試作で見つかった、§9.11)。試作では、要求の画像を選んだ後で、フォルダの履歴の復元 (`resume_loading_items_after_sidecar` の `move_grid_cursor`) が選択を前回見ていた画像へ戻し、一覧と連動する窓 (`sync_detached_viewer_to_selected`) がそれに追従して前回の画像を開き直した (試作のログのバックトレース、2 回)。開く要求がある間は、要求の持ち主が選択も持ち、履歴の復元は選択を動かさない形にする。どの関数で持たせるかは実装前に追跡して確定する。製品の通常の 2 重起動 (F12 の窓が開いているとき) で同じことが起きるかは未確認で、実装前に確かめる。
9. **受付の結果ごとの前面化** (本文と §13 Q14 をそろえた、独立レビュー第 5 回 P7):

   | 結果 | 前面化 |
   | --- | --- |
   | 受理 | 開いた窓 (重ねた窓) を前に出す。メインウィンドウは前に出さない |
   | 保留 (文書モーダル中) | 何もしない。モーダルが閉じた後に受付をやり直し、受理なら上と同じ |
   | 拒否 (知らせのあるもの): Remote (いま Remote が操作中の拒否と、受信したときの Remote の所有による拒否の 2 経路、[startup_ops.rs:302](../src/app/startup_ops.rs)〜:330)・本の構成エディタ中・解決後の★固定の範囲外 ([startup_ops.rs:918](../src/app/startup_ops.rs)) | メインウィンドウを前に出し、既存の 2 重起動の知らせを見せる。どの経路でも、要求の持ち主が `BrowserOverlay` を持つときだけ前に出す (持ち主が意図を運ぶので後段の拒否でも分かる) |

### 9.3 重ねる位置

- **表示領域の画面上の位置を直接返す標準の API は見つかっていない**。MDN の `screenX` などのページに該当するものは無く、`mozInnerScreenX` は非標準 (https://developer.mozilla.org/en-US/docs/Web/API/Window/mozInnerScreenX)。
- **右クリックの座標から求める** (2026-11-22 に改めた、§9.11)。マウスのイベントは、画面上の座標 (`screenX` / `screenY`) と表示領域の中の座標 (`clientX` / `clientY`) を両方持つので、その差が表示領域の左上になる。
  - 許可したページの origin に、拡張が小さなスクリプトを登録する (`scripting.registerContentScripts`、上位フレームだけ、`document_start`、拡張専用の分離された環境 `ISOLATED`、ブラウザを再起動しても残す)。スクリプトは `contextmenu` を捕捉段階・受動で聞き、直前の 1 回の座標と、そのときの `window.screenX` / `screenY` / `innerWidth` / `innerHeight` / `devicePixelRatio` だけをページの中の変数に置く。どこへも送らない。読むのは「mIV で見る」を選んだときの 2 だけ。
  - 登録した後に開いたページだけでなく、すでに開いているタブにも入れる: 拡張の起動時 (`runtime.onInstalled` / `onStartup`) と許可が増えたとき (`permissions.onAdded`) に、許可済みの origin のタブへ同じスクリプトを `executeScript` で入れる。拡張を読み込み直すと、前から開いていたタブのスクリプトは新しい拡張から見えなくなるため (試作で、利用者の 1 回目の確認が 2 回とも記録なしだった、§9.11)。
  - 記録を使うのは、記録したときと今とで、窓の位置・表示領域の大きさ・`devicePixelRatio` が同じときだけ。違えば推定 (下) にする。右クリックした要素が送る画像と違っても (画像の上に別の要素が重なるサイト)、表示領域の左上は同じなので使う。
  - 換算: 表示領域の左上 (DIP) = `screenX − clientX × ページの拡大率`。物理ピクセル = DIP × (`devicePixelRatio` ÷ ページの拡大率)。拡大率 100% の通常の窓で、縦タブの有無にかかわらず合った (利用者が X・pixiv で 4 回、§9.11)。**拡大率が 100% 以外のときの単位の解釈は未確認** (試作は別の解釈 `(screenX − clientX) × 拡大率` もログに残している)。
- **記録が無いときの推定**: ページの origin を断られた、記録が古い、などのとき。窓の外側 (`screenX` / `outerWidth` ほか) と表示領域の大きさ (`innerWidth` ほか) の差を、右と下に枠 8 DIP、残りの幅を左 (縦タブの側)、残りの高さを上 (タブ・アドレスバー) とみなす。最初の版は左右に半分ずつ配っていたため、縦タブで約 150 DIP 左上へずれた (利用者のスクリーンショット、§9.11)。右側のサイドパネル・ドッキングした開発者ツールではずれる。推定は位置合わせの見た目の便利さのためで、正確さは保証しない。
  - 単位: `screenX` / `screenY` は CSS ピクセル ("in CSS pixels"、https://developer.mozilla.org/en-US/docs/Web/API/Window/screenX) とされるが、試作では拡大率 100% で DIP として扱って合った。`devicePixelRatio` はページのズームでも変わる (https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)。
  - 未確認の場面: ページのズーム、最大化した窓、倍率の違う複数のモニター、右側のサイドパネル、Edge。
  - Chrome の内部の子ウィンドウを Windows の機能で探して矩形を取る方法は、非公開の作りに頼るので採らない。
  - 代わりに `chrome.windows.get` の窓全体の位置と大きさを使えば、推定は要らない (タブ・アドレスバーも隠れる)。単位が画面のピクセルか論理ピクセルかは公式の記述が無く未確認 (https://developer.chrome.com/docs/extensions/reference/api/windows)。どちらにするかは §13 Q9。
- **mIV の窓の位置**: 別ウィンドウの位置は物理ピクセルで持ち、モニターの倍率に合わせて置く既存の仕組みがある ([app/detached_placement.rs:709](../src/app/detached_placement.rs) `apply_detached_host_rect`、[detached-dpi-placement-plan.md](detached-dpi-placement-plan.md))。拡張からの位置は、新しく作る窓の位置の種として渡す。渡す場所は窓の種類で違う (独立レビュー第 5 回 P2):
  - **一覧と連動する別ウィンドウ** (フル機能): 作る境界は `prepare_viewer_presentation_open` → `commit_viewer_session(DetachedWindow, independent=false)` ([app.rs:72318](../src/app.rs)、:72358)。今の種は、既定 (メインウィンドウ + 48 px、960×720) か保存済みの位置 ([app/detached_placement.rs:49](../src/app/detached_placement.rs)〜:92)。この種の代わりに要求の位置を渡す。どの関数で差し込むかは、実装前に追跡して確定する。
  - **複数ウィンドウモードの窓**: 独立した context を作る入口は種の引数を既に持ち ([app.rs:67978](../src/app.rs) `start_active_detached_loading_context(ctx, placement_seed, …)`)、今は前の窓からずらす位置に使われている。この種として渡す。
  - 検査は既存の保存済み位置と同じ (大きさが妥当で、タイトルバーがどこかのモニターの上にあること、[app.rs:2620](../src/app.rs))。検査に通らないときの扱いも既存の保存済み位置と同じにする (実装時に確かめる)。
- **枠**: 既存の別ウィンドウは枠付き (タイトルバーあり、[ui_fullscreen.rs:33478](../src/ui_fullscreen.rs))。窓の外側を表示領域に合わせるので、タイトルバーがページの上端に重なる。枠なしの表示は今はモニター全体を覆う形しかなく ([app.rs:71669](../src/app.rs))、任意の位置の枠なしは新しい表示形式になるので作らない (§13 Q12)。
- **位置を合わせるのは窓を作るときの 1 回だけ**。ブラウザを後から動かしても追従しない。
- **窓の用途を、作るときに決めて窓に持たせる** (独立レビュー第 5 回 P3)。窓ごとの持ち物 (`DetachedWindowRuntime`) に「作った用途」(`Normal` / `BrowserView`) を置き、`BrowserOverlay` の要求で作った窓だけが `BrowserView` になる。ほかの作り方 (F12・通常の開く) はすべて `Normal`。作った後で用途は変えない。
- **すでに一覧と連動する別ウィンドウが開いていたら、閉じて作り直す** (CLAUDE.md「設計の簡素化」の「閉じて作り直す」)。既存の窓 (利用者が F12 で開いた `Normal` の窓を含む) を閉じ、その窓の用途どおりに位置を保存してから、要求の位置で `BrowserView` の窓を作る。このときの閉じる理由は「重ねる窓への置き換え」で、メインへフォーカスを送らない (下の表)。既存の窓を動かす・中身だけ差し替える形は採らない (動かすと `Normal` の窓の保存位置がブラウザの位置で上書きされ、動かさないと重ならない)。閉じると 3D 写真は既存どおり終わる。
  - 複数ウィンドウモードは、そのモードの決まりどおり新しい窓を足す (前の窓は閉じない)。
- **閉じるときの後始末は、窓の用途と閉じる理由の 2 つだけで決める** (独立レビュー第 6 回 P2)。
  - 今の終了処理は、窓ごとの持ち物 (runtime) を取り除いた**後で**メインへのフォーカスを決めている ([app.rs:67777](../src/app.rs)、:67742)。Esc の経路では、さらに早く閲覧を終えている ([app.rs:82940](../src/app.rs))。そこで、閉じる処理を始めるところで用途 (`Normal` / `BrowserView`) と閉じる理由を値として取り出し、閉じる処理の持ち主がその値を最後まで持つ。runtime を取り除いた後でも、この値で判断する。App に印は足さない。
  - 閉じる理由: 利用者が閉じた (Esc・×) / 重ねる窓への置き換え / F12 による表示の切り替え (`Normal` の窓だけ) / **その他の既存の終わり方** (設定の変更で窓を閉じる [ui_dialogs/preferences.rs:3187](../src/ui_dialogs/preferences.rs)、Remote が操作を握るときの一括の終了 [remote_ipc/ui.rs:1211](../src/remote_ipc/ui.rs)、アプリの終了など)。既存の終了の原因 (`RemoteAcquire`・`AppExit` など、[app/close_return.rs:5](../src/app/close_return.rs)) はそのまま持ち、新しい理由はそれに足すだけにする。

  | 用途 | 閉じる理由 | 位置の保存 ([app.rs:3525](../src/app.rs)) | メインへのフォーカス ([app.rs:67789](../src/app.rs)) |
  | --- | --- | --- | --- |
  | `Normal` | 利用者が閉じた・F12 | 既存どおり保存する | 既存どおり |
  | `Normal` | 重ねる窓への置き換え | 保存する | 送らない (ブラウザの上に新しい窓を出すので) |
  | `BrowserView` | 利用者が閉じた・重ねる窓への置き換え | 保存しない (利用者が覚えさせた F12 の位置をブラウザの位置で上書きしない) | 送らない (送るとメインが前に出てブラウザを隠す) |
  | `Normal` | その他の既存の終わり方 | 既存どおり | 既存どおり |
  | `BrowserView` | その他の既存の終わり方 | **保存しない** (終わり方によらない) | 既存の終わり方の持ち主の方針どおり (設定の変更・Remote・アプリの終了は、利用者が mIV を操作している場面なので変えない) |

- **`BrowserView` の窓では F12 を使えなくする** (独立レビュー第 6 回 P3、§13 Q17)。今の F12 は、表示中の窓ではなく保存された設定 (別ウィンドウを使うか) を反転する ([app.rs:93939](../src/app.rs))。F12 の別ウィンドウを使わない設定のまま `BrowserView` で開いた窓で F12 を押すと、設定が OFF → ON になって窓は別ウィンドウのまま残り、「切り替え」にならない。また F11 → F12 の往復で枠なしの状態と戻る位置を保つ既存の約束 ([app/tests.rs:6826](../src/app/tests.rs)) があり、`BrowserView` の窓から `Normal` の窓へ戻る位置が引き継がれると、ブラウザの位置が F12 の位置として残る。F12 を使えなくすれば、この組み合わせ自体が無くなる。`Normal` の窓同士の F12・F11 の既存の約束は変えない。
  - **判定は入力の出どころではなく、切り替える対象の窓で行う** (独立レビュー第 7 回 P1)。F12 の切り替えは、重ねた窓の中のキーだけでなく、メインの一覧のキー ([app/update_phases.rs:931](../src/app/update_phases.rs)) やゲームパッドのリング ([app/gamepad_input.rs:8510](../src/app/gamepad_input.rs)) からも同じ切り替えの関数 (`toggle_detached_viewer_mode`) に入る。そこで、この共通の関数の入口で「切り替える対象の窓の用途が `BrowserView` なら断って知らせる」とする。キーの割り当てを変えた同じ操作 (`KeyAction`) やリングも、これで同じく断られる。

### 9.4 状態の組み合わせを減らす決定 (段 2)

1. **受付は 2 重起動の activation チャネル 1 本のまま**。違いは要求が持つ表示先の型 (`BrowserOverlay`) だけで、拡張専用の受付・保留・応答を作らない (§7-1)。
2. **位置は作るときの 1 回だけ**。追従しない。既存の連動窓は動かさず、閉じて作り直す。窓の扱いは作ったときの用途だけで決まる (§9.3)。
3. **ブラウザとはつながったままにしない**。受け渡しが済めば、mIV の窓とブラウザは無関係。ブラウザのタブを閉じても、mIV の窓はそのまま。
4. **mIV の外の状態を待たない**。取得は 3 で拡張が済ませ、保存と記録は 5 で中継 exe が済ませてから core へ渡す。core が受け取るのは保存済みの普通のファイル (§7-2 と同じ)。
   - 取得を拡張に移したことで、当初の案にあったダウンロードフォルダの中継・ダウンロードの完了待ち・履歴の消去・保存場所の確認ダイアログ・`downloads` 権限がなくなった (組み合わせが減る)。
5. **窓の種類はビューワモードで決まる 2 通りだけ** (フル機能 → 連動する別ウィンドウ、複数ウィンドウ → そのモードの窓、§9.1)。段 2 のために、モードの決まりを変えない。
6. **拡張は 1 件ずつ処理し、処理中に押されたものは断る**。処理中の範囲は 1 の直前から、6 のどれかの終端まで (成功・失敗・中断のどれでも解く)。処理中に押されたら何もせず、バッジで「処理中」を示す (§7-3)。
   - 保証の範囲: 拡張の中では押した順に 1 件ずつ送る。launcher に渡した後の順序は、既存の 2 重起動の受信順に従う。
   - **service worker の停止は通常の動作** (30 秒の無操作で止まり、グローバル変数は失われる、https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)。処理中の要求は `chrome.storage.session` に置き、各イベントの前に読む。`storage.session` は拡張が読み込まれている間メモリに保たれ、ブラウザの再起動などで消える (https://developer.chrome.com/docs/extensions/reference/api/storage)。取得は数秒で終わる 1 回の処理なので、途中で止まったときは §9.2-6 のとおり失敗として示し、やり直さない。
   - 異常終了などで処理中のまま取り残された場合は、ブラウザの再起動で解ける (まれな失敗の割り切り)。
7. **まれな失敗は割り切る**。保存・記録・パイプの失敗は、ログと拡張のバッジだけ。ファイルは消さない: 保存した後の失敗 (記録・launcher の起動) なら「ブラウザ閲覧」フォルダに残る。保存する前の失敗では、どこにも残らない (もう一度押せば取り直す)。

### 9.6 権限

(2026-11-22 に改めた。改める前は `downloads` を使い host 権限を求めない案だった、§9.11)

- 宣言する権限: `contextMenus`、`nativeMessaging`、`storage` (処理中の要求)、`activeTab` と `scripting` (位置を読む・右クリックの記録を入れる)、`declarativeNetRequestWithHostAccess` (取得 1 回だけの参照元の規則)。`downloads` は使わない。
  - 試作は規則が効いたかを確かめるため `declarativeNetRequestFeedback` も宣言していた。製品では使わない。

### 9.7 中継 exe と登録

- 中継 exe は小さな別 exe (`mimageviewer-browser-host.exe`、仮称) にする。core や launcher を host にしない (host は stdin/stdout の決まった形式で 1 メッセージごとに起動されるので、本体の起動処理と混ぜない)。
- 登録は mIV の環境設定から行う (「ブラウザ連携を使う」)。インストーラは今レジストリを書かないので、インストーラでは登録しない。
  - 登録時に、中継 exe と manifest を `%APPDATA%\mimageviewer\browser-host\` に置き、`HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>` と Edge のキーに manifest のパスを書く。
  - **登録時に launcher の絶対パスと「ブラウザ閲覧」の保存先の基底のフォルダを確定し、中継 exe の隣の設定ファイルに書く** (月のフォルダは中継 exe が保存のときに作る、§9.2-5)。core は自分を起動した launcher のパスを環境変数で受け取っているが ([crates/launcher/src/main.rs:284](../crates/launcher/src/main.rs))、ブラウザが起動する中継 exe にはその引き継ぎが無いため。保存先の正本は mIV の設定で、利用者が変えたら core が設定ファイルを作り直す。
  - **公開の順序**: 中継 exe とその隣の設定ファイルは、変更のたびに新しいフォルダ (`browser-host\<世代>\`) に完成させる。そのあと manifest を一時ファイルに書いて置き換え (rename) で差し替え、`path` を新しいフォルダへ向ける。レジストリのキーは常に同じ manifest のパスを指すので、書き換えない。
    - ブラウザが読むのは manifest だけなので、「設定が置かれる前の中継 exe」「書き換え途中の設定」を読むことはない。版が同じで launcher の場所や保存先だけ変わる場合も、同じく新しいフォルダを作る。
    - 実行中の中継 exe は上書きしない。古いフォルダは次の更新で消す (消せなければ残し、次の機会に消す)。
  - 更新するのは core (登録が有効なとき、起動時と保存先の変更時に確かめる)。単体 exe 版の本体は版ごとに `%APPDATA%\mimageviewer\runtime\<ver>` へ展開されるが、記録するのは launcher (利用者が置いた `mimageviewer.exe`) のパスなので、版が変わっても記録は変わらない。
  - **launcher のパスが分からない起動** (core を直接起動した場合など、launcher からの環境変数が無いとき) では、既存の登録を変えず、新しい登録もしない。環境設定の「ブラウザ連携を使う」は、理由を示して押せなくする。
  - launcher を移動・削除した後は、中継 exe が「launcher が見つからない」を返し、拡張が「mIV の環境設定で連携を登録し直してください」を示す。自動で探し直す処理は持たない。
  - core の起動時の更新と、中継 exe からの launcher の起動が重なっても、中継 exe は manifest が指していたフォルダのものが最後まで動き、launcher の起動は launcher の既存の処理に任せる。新しい待ち・排他は足さない。
  - 解除は同じ画面から (キーとファイルを消す)。登録・解除は既定のデータフォルダの mIV だけが行い、別のデータフォルダの mIV からは共有の登録を変えない。
  - **保留 (段 2 の詳細設計で決める)**: アンインストール後に残るレジストリのキー・中継 exe・拡張・「ブラウザ閲覧」フォルダの画像の扱い。インストーラは今レジストリを触らないので、消すにはインストーラの変更が要る。画像は利用者のデータなので消さない。
- **既定のデータフォルダの mIV だけ**を対象にする案を推す。技術的には、中継 exe 側の設定に送り先 (`--data-dir`) を 1 つ持たせれば他のデータフォルダにも送れる (launcher は `--data-dir` 付きなら core に任せる、[crates/launcher/src/main.rs:206](../crates/launcher/src/main.rs))。それでも限るのは、登録の持ち主を 1 つにして、「どのデータフォルダの mIV が登録を変えたか」の組み合わせを作らないため (保守と状態削減の判断、§13 Q5)。
- launcher と core は同じ版で配る (launcher が core を内包する) が、**起動中の core は別の版のことがある** (§9.2-7)。新しいパイプは版の欄を持ち、合わなければ launcher が再起動を促して終わる。`v` は拡張と中継 exe の間の版で、知らない版なら「mIV を更新してください」を返す。

### 9.8 中継 exe の検査

- 第 1 引数の origin が、登録した拡張の ID であること (Chrome も `allowed_origins` で絞るが、中継側でも見る)。
- `v` が知っている版であること。
- メッセージの長さ (先頭の 4 バイト) が上限以下であること。上限を超えるものは、本文を読む前に断る。
- `data_b64` が正しい base64 で、復号した中身の先頭のバイトが対応する画像の形式であること (拡張子はここから決める)。
- `page_url` と `image_url` が HTTP(S) であること (Mark of the Web に書くため)。
- `view` の値がすべて有限の数で、大きさが正であること。右クリックの記録があれば、その値も同じ (画面上の妥当性は mIV 側の既存の検査に任せる、§9.3)。
- 拡張から受け取ったパスはもう無い (中継 exe が保存先とファイル名を決める) ので、パスの検査は要らない。
- 設定ファイルに記録した launcher が存在し、保存先の基底のフォルダが設定されていること (フォルダがまだ無いことは失敗にしない。作れなければ失敗)。

### 9.9 着手前に確かめること (スパイク、利用者の操作が要る)

### 9.10 拡張の公開の手順と費用 (Q7)

2026-11-20 に ClaudeCode の調査役が公式のページを取得して確かめた。登録・支払い・同意・提出は利用者が自分のアカウントで行う (エージェントは行わない)。

**Chrome ウェブストア**

- **費用**: 開発者登録のときに 1 回だけ登録料を払う ("pay a one-time registration fee"、https://developer.chrome.com/docs/webstore/register)。継続の課金の記載は無い。**金額は公式のページに記載が無く未確認** (一般には 5 米ドルと言われている)。登録の画面で確かめる。無料の拡張なら、住所は求められない (購入・追加機能・定期購入を提供するときだけ要る、https://developer.chrome.com/docs/webstore/set-up-account)。
- **登録**: 日本は登録できる国に入っている。開発者のメールアドレスは登録後に変えられない ("After an account is created, you cannot change its email address.")。公開専用のアドレスを使うことが勧められている。メールの確認と、ストアの「提供元」に出る公開者名が必須。Trader / Non-Trader の自己申告がある (https://developer.chrome.com/docs/webstore/trader-disclosure/)。Google アカウントの 2 段階認証が要るかは、読んだページでは未確認。
  - **メールアドレスの選び方** (2026-11-20 に利用者から質問、公式のページで確かめた範囲):
    - Google Workspace のエイリアスは Google アカウントではないので、エイリアスでサインインはできない ("you can't sign in with an email alias address"、https://support.google.com/a/answer/33327)。エイリアス宛のメールは主アカウントの受信箱に届く。管理コンソールの「メニュー > ディレクトリ > ユーザー」でユーザーを開き「Add Alternate Emails」から追加する (1 ユーザー 30 個まで追加費用なし、反映は最大 24 時間)。エイリアスから送るには、利用者が Gmail で別の差出人を設定する。
    - Chrome ウェブストアには、変えられない「開発者のメール」(ストアからの通知の宛先) と、ダッシュボードの Account ページで「Add email」から入力し確認のリンクで検証する**連絡先のメール** ("enter an email address and then request verification"、https://developer.chrome.com/docs/webstore/set-up-account) がある。連絡先のメールは**拡張の連絡先として公開される** ("Only displayed under your extensions' contact information.")。連絡先のメールに使えるアドレスの制限は記載が無い (Google アカウントである必要も書かれていない) ので、確認のリンクを受け取れるエイリアスは使える見込みだが未確認。開発者のメールがサインインする Google アカウントそのものか、Workspace のアカウントで登録できるかも記載が無く未確認。登録の画面で確かめる。
    - メールを変えたくなったら、新しいアカウントを作って拡張を移す申請をする ("create a new account and transfer your Chrome Web Store items to it"、https://developer.chrome.com/docs/webstore/register)。
    - Edge は個人の Microsoft アカウントが必須で、職場・学校のアカウントでは登録できない ("doesn't support registering with a work or school account"、https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/create-dev-account)。
- **進め方** (2026-11-20 利用者と確認): 連絡先のメールは、利用者がドメインのエイリアスを用意済み。まずスパイク (§9.9) と実装を開発者モード (パッケージ化されていない拡張の読み込み) で確かめ、公開できる内容で動いてからストアの準備を進める。開発者モードの拡張は利用者自身の確認にだけ使い、配布には使わない (§4.3)。
  - **拡張の ID**: native messaging の manifest の `allowed_origins` には、拡張の ID を `chrome-extension://<ID>/` の形で並べる。ワイルドカードは使えない ("allowed_origins values can't contain wildcards"、https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)。開発中とストアで同じ ID にするには、ZIP を公開せずにダッシュボードへアップロードし、「Package」タブの「View public key」で出る公開鍵を manifest の `key` に入れる (https://developer.chrome.com/docs/extensions/reference/manifest/key)。そのため、ストアのアカウントは提出の直前ではなく、開発者モードの確認の途中 (ID を固定したくなった時点) で作るとよい。ID を固定しない間は、開発用の ID を `allowed_origins` に足して確かめる。Edge のストアの ID は Chrome と別になる。
- **提出**: ダッシュボードで「Add new item」→ ZIP をアップロード → Store Listing・Privacy・Distribution (必要なら Test instructions) を埋める → 「Submit for Review」 (https://developer.chrome.com/docs/webstore/publish)。審査に通ってから 30 日以内に公開する (過ぎると下書きに戻る)。新しい公開者は、公開できる拡張が 2 つまで。
- **Privacy タブ** (https://developer.chrome.com/docs/webstore/cws-dashboard-privacy): 単一の目的の説明、権限ごとの理由 (§9.6 の宣言する権限と任意の host 権限のすべて)、リモートのコードを使わないこと、データの扱いの開示と認証、プライバシーポリシーの URL。ローカルだけで扱うデータでも開示が要る ("even when data is processed or stored locally"、https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)。プライバシーポリシーは mIV の `privacy.html` に拡張の節を設けて指す (§11)。
- **掲載の素材** (https://developer.chrome.com/docs/webstore/images): 128×128 の PNG のアイコン (ZIP の中にも)、スクリーンショット 1〜5 枚 (1280×800 か 640×400)、詳しい説明文。小さいプロモ画像 (440×280) は任意だが、無いと表示順が後ろになる。
- **審査の期間**: 多くは数日、長いと数週間 ("within a few days, but it can take up to a few weeks"、https://developer.chrome.com/docs/webstore/review-process)。新しい開発者・新しい拡張・強い権限は長くなりやすく、`downloads` は強い権限の例として挙がっている (2026-11-22 に `downloads` は使わない形に改めた。代わりに任意の広い host 権限の宣言がある、§9.6)。**更新も毎回同じ審査を通る**。

**Microsoft Edge アドオン** (Edge の利用者向け。Edge は Chrome ウェブストアからも入れられるが、Edge の場合も考えて両方に出すかは公開の準備で決める)

- **費用**: 無料 ("There is no registration fee"、https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/create-dev-account)。Microsoft アカウントを主な所有者とする Partner Center の開発者アカウントが要る。個人のアカウントを選ぶ (会社から個人へは変えられない)。
- **提出**: Partner Center で新しい拡張を作り、ZIP・公開範囲 (公開 / 非表示)・プロパティ・プライバシー・掲載情報を埋めて提出 (https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension)。説明文は 250〜10,000 字、ロゴ (最小 128×128) が必須。審査は最大 7 営業日。
- 両方のストアに出す場合、native messaging の manifest の `allowed_origins` に両方の拡張の ID を並べる (§4.4)。

**mIV の公開作業への影響** (実装の段で [release-checklist.md](release-checklist.md) に足す):

## 11. 公開文書への影響

- 段 1:

- 段 2 (日本語と英語の両方。`privacy.html` は 1 ファイルに両方の言語がある):
  - mIV 本体は通信しないが、**ブラウザの中の拡張が画像を取得する**ので「ネットワーク通信」に書く。既存の「撮影地点を地図で開く」もブラウザ経由の通信として説明しているのと同じ扱い ([privacy.html:288](../htdocs/mimageviewer/privacy.html))。書くこと: 右クリックで「mIV で見る」を選んだときだけ、その画像の URL を拡張が 1 回取得する。そのサイトの Cookie が付き、参照元としてページの origin (ホスト名まで) が付く。取得の前に、そのサイトの許可を Chrome の確認で求める。mIV からも拡張からも開発者へは送らない。
  - 「端末内に保存されるデータ」に足すこと: 画像は「ブラウザ閲覧」フォルダに保存される (保存する前に失敗したときはどこにも残らず、保存した後に失敗したときは「ブラウザ閲覧」フォルダに残る)。出どころの記録 (Mark of the Web) として、画像の URL とページの URL がファイルに書かれる。中継 exe・manifest・launcher のパスと保存先の記録の置き場所と、レジストリのキー。解除のしかたと、解除・アンインストールの後に残るもの (§9.7 の保留が決まってから)。
  - 拡張がタブから読むのは、窓の位置と大きさ、直前の右クリックの座標だけで、ページの内容は読まないこと (§9.2-2、§9.3)。許可したサイトのページでは、右クリックの座標を記録する小さなスクリプトが動くこと (記録はそのページの中に置くだけで、どこへも送らない)。拡張は、画像の中身と、右クリックした画像の URL・ページの URL を、PC の中だけで中継 exe へ渡すこと (開発者へは送らない)。
  - 製品ページの「安心して使えます」の本文 (ネットワークは更新確認と「ご自分で選んだ機能」、[index.html:1252](../htdocs/mimageviewer/index.html)) は一般的な表現のままで偽にならない。リンク先の通信の一覧 (`privacy.html`) は上のとおり更新する。
  - マニュアル: 拡張の入れ方、mIV 側の登録・解除、使えるのは既定のデータフォルダの mIV だけであること (Q5)、「ブラウザ閲覧」フォルダと場所▼、重ねて開く窓の動き (位置はずれ得る・追従しない・メインの一覧が移る・開いている F12 の窓は閉じて作り直す・閉じるときに mIV はメインへフォーカスを送らない (閉じた後にどの窓が前に来るかは Windows の動作による)・この窓が開いている間は F12 の切り替えを使えない)、編集が画像ごとに残る範囲 (補正パネルで「このページ」を選んだ補正は「補」の印で分かる、U や標準を選んだままの補正は標準を変える)、★固定の範囲の注意、拡張がバッジで示す失敗 (処理中・未登録・版のずれ・launcher が見つからない・サイトの許可を断った) とその直し方。初めてのサイトでは Chrome の許可の確認が出ること。サイトによっては Shift+右クリックでブラウザのメニューを出すこと (§9.9)。
  - 拡張のストア掲載ページのプライバシーの開示は「開発者へ収集・送信しない」と範囲を明示する。X・pixiv 製ではない旨を書き、サイト名やロゴを宣伝・アイコンに使わない。
- どちらの段も、外部ダウンローダの名前・URL・使用例を公開文書とコミットメッセージに書かない ([public-wording-policies.md](public-wording-policies.md))。機能の説明は「ブラウザで見ている画像を mIV で開く」とし、「サイトから画像を集める」「一括で保存する」とは書かない。
