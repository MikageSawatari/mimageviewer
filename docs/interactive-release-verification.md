# 実アプリ検証の実行確認

2026-09-08の利用者指定。実アプリを起動・操作する検証は、通常の開発反復から分離し、
原則リリース前の検証枠でまとめて実施する。必要な検証を省く変更ではなく、実施時期と
PC使用の了承を明確にする運用である。

## 通常の開発中

実装、source調査、unit/integration・snapshot・fakeテスト、ログ解析、buildと隔離成果物の
準備を進める。実アプリの起動、前面切替、マウス・キー操作は自動的に続けて実行しない。
`test-full.ps1`や`build-dist.ps1`へ実アプリ操作テストを無条件で連結しない。
実行を見送った項目は「実装済み・実アプリ未検証」等として検証待ちに残す。

## リリース前の検証枠

1. 変更対象と既存の必須検証から、今回実行するシナリオを確定する。
   成果物、非対話テスト、隔離条件、実行コマンドを先に準備する。
2. 利用者へシナリオ一覧、見込み時間、前面ウィンドウ・マウス・キーボードの使用、
   保存先を示し、「今この検証を実行してよいか」を確認する。
   時間枠を設ける場合は開始・終了時刻と、その枠内で許可する再試行範囲も決める。
   実装・非対話テスト・buildは先に済ませ、時間枠を実アプリ確認へ充てる。
3. **明示的な了承が届いてから**、その実行または合意した一連の検証だけを実施する。
   会話中の予告、沈黙、過去の一般的なマウス方式の選択、開発の続行指示は了承とみなさない。
   予定した範囲を超える再実行や後日の検証には改めて確認する。
   時間枠の終了後に操作を続けないよう、入力解放と後始末の時間も見込む。
4. 対象プロセスの後始末と証跡保存を終え、PC操作を再開できること、成功・失敗・
   環境不成立・未実施を報告する。未実施や環境不成立をPASSへ読み替えない。

`ui-smoke.ps1`は`-InteractiveApproved`を実行側の明示指定として要求する。
このflagは同意を取得する機能ではなく、上記確認を済ませた後にのみ指定する。
未指定時はprepare/build・run directory作成・アプリ起動より前に終了する。

対象シナリオと実装状況は[実アプリsmoke設計](ui-smoke-automation-plan.md)を参照。
複数窓PDF、静止画列drag、動画入力・zoom、横長画像idle収束を必要な検証枠へ組み込む。
従来のpage-turn、perf smoke、idle-healthなども、実アプリの起動・操作を伴えば同じ確認が必要。
既存logの解析だけでPCを操作しない処理は通常の開発中に実行してよい。

`NativeTopPanoramaHover`は単独で約90秒を見込み、使い捨て640x360動画を別窓で開く間に
前面ウィンドウとマウスを使用する。native側が送る入力は上端36ptへのMouseMove 1件だけで、
実`native_top_panorama` Responseのenabled/位置/owner/source/hostを観測して終了する。
click、wheel、key、panは送らない。この具体scenarioの実行了承が届くまでは
`-InteractiveApproved`を付けず、portable artifactの準備と非対話検証までに留める。

## データ保護と記録

実行了承は、通常profileの起動許可を兼ねない。エージェントは引き続き
`prepare-portable-smoke.ps1`が用意する`target/portable-smoke/mimageviewer.exe`と
使い捨て`data`だけを使う。通常設定を必要とする確認は、利用者自身が確認用buildを起動する。
通常profileを使う旧scriptへ、このflagを付けてエージェント実行を解禁することはしない。

リリース記録には、了承した検証範囲・実行日時・成果物とscenarioの証跡・各結果・
未実施理由を残す。既存の必須テスト、実機確認、通常データ保護の条件は維持する。

## Windowsの入力デスクトップを開始前に確認する

同じWindows sessionでも、テストプロセスのdesktopと実入力desktopが異なる場合がある。
2026-09-10のCodex実行では、通常のsandbox経路で起動したrunnerが
`CodexSandboxDesktop-...`、実入力先が`Default`だった。ウィンドウ描画は進むが
foregroundを得られず、複数窓の操作待ちやnative入力の環境失敗になった。
これは製品機能の不合格とは分けて記録する。

実機suiteの開始前に、読み取り専用でsession、thread desktop、input desktop、
foregroundの取得を確認する。不一致ならアプリを起動して再試行を重ねず、
正規の承認付き実行経路が利用可能かを確認する。同日の`exec_command`では
`require_escalated`の承認付き読み取りが`Default`上で実行されることを確認した。
この確認は個別実行の環境証拠であり、将来の実行先を無条件に保証しない。

sandbox内からdesktopを切り替えたり、入力先の検証を外したりして成立させない。
通常デスクトップで実行できる場合も、具体suiteの利用者了承、隔離データ、exact PID/HWND、
再試行上限はそのまま適用する。環境不成立だったrunの証拠と回数も残す。
