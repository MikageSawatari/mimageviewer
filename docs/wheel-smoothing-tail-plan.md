# ホイール平滑化の残量による空描画を止める (§1.827 候補 F)

2026-11-20 設計メモ。ブランチ `wheel-smoothing-827` (master 03e1cb024 から)。
計測と原因は、統括の共有ノート `cpu-827-interim.md` と調査ブランチ `cpu-827-investigation` にある。

## 1. 症状と原因

- 観測 (portable-smoke、OS 入力 SendInput、メインPC 165Hz、2026-11-20 18:25〜18:29、承認済み):
  - 全画面のページ内スクロールでホイールを 1 秒に 15 ノッチ回すと、描画が 165 fps に張り付く。
  - 端でパンが 0 回の区間でも同じ。ホイールを止めた後も約 0.3 秒続く。
  - UI スレッドは 1 コアの 43〜48%。
- 原因 (コード):
  - egui は Line/Page 単位 (と 8 pt 以上の Point) のホイールを `WheelState::unprocessed_wheel_delta` に積む (`vendor/egui/src/input_state/wheel_state.rs:178`)。
  - 積んだ分は 0.1 秒で 90% のペースで `smooth_scroll_delta` へ吐き出す (`wheel_state.rs:190-201`)。
  - 残量が 0.2 を超えている間、`wants_repaint_after` は即時の再描画を返す (`input_state/mod.rs:688`)。この判定は `begin_pass` の直後に行われる (`context.rs:517`)。
- mIV の多くの持ち主は、生の `Event::MouseWheel` から動きを決める。消費時には、その pass のイベントと `smooth_scroll_delta` だけを消す (`src/wheel_input.rs:141-211`)。
  - egui 内部の残量は残るので、後続の pass で誰も使わない吐き出しが続き、ノッチごとに約 0.25 秒、リフレッシュレートで描き続ける。
  - 入力 1 回で 3 フレームなら、15 ノッチ/秒は 45 fps のはず。

## 2. 方針

**生のイベントから動きを決める持ち主が、ホイールを消費し、その pass にほかのホイールが残っていないときに、既存の `InputState::discard_pending_scroll()` を呼ぶ。** egui 側の変更はしない。

`discard_pending_scroll()` (`vendor/egui/src/input_state/mod.rs:517-525`) は、残量 `unprocessed_wheel_delta` だけを捨てる。現在の delta・イベント・gesture 状態・modifier は保つ。既存の vendor テスト (`mod.rs:1983`) が、この契約を固定している。すでにポップアップを閉じる境界と、ページ一覧のホバー境界で使われている (`ui_fullscreen.rs:28662`, `30395`, `ui_page_overview.rs:642-649`)。

捨てる処理は viewport の残量全体に効く (特定のイベントの寄与だけを捨てるのではない)。InputState は viewport ごとなので、別の窓には効かない。同じ viewport の中の別の持ち主には効きうるので、§2.2 の条件で限定する。

### 2.1 検討した案と採否 (CLAUDE.md「状態の組み合わせを減らす」)

| 案 | 内容 | 採否 |
| --- | --- | --- |
| a. 3 つの消費関数の中で一律に捨てる | `consume_wheel_segment` / `consume_remaining_wheel_inputs` / `consume_wheel_input` の中で `discard_pending_scroll()` | **不採用**。`consume_wheel_input` はポップアップの持ち主が、ポップアップ内の egui `ScrollArea` が読んだ後に、開いている間は毎 pass 呼ぶ (下表の「保つ」側)。ポップアップの滑らかなスクロールは残量の吐き出しで成り立っているので、一律に捨てると最初の pass の分しか動かなくなる。全画面 HUD のポップアップは「開いている間は残量を保ち、閉じるときだけ捨てる」と明示的に作ってある (`ui_fullscreen.rs:30388-30396`) |
| b. egui にイベントごとの帳簿を足す | 消費したイベントの寄与分だけを残量から差し引く | **不採用**。同じ pass で生イベントの持ち主とスクロール領域の両方にホイールが届く場合は、§2.2 の条件 (残りがあれば捨てない) で今の挙動のまま残せる。pass をまたぐ受け渡しでは、egui の ScrollArea は残量をホバー中の領域にしか当てない (`scroll_area.rs:1926`) ので、帳簿で守るものがほとんどない。帳簿は vendor egui の変更と、線形でない吐き出し (`abs < 1.0` で全量を移す) の扱いを要し、得るものに対して大きい |
| c. **生イベントの持ち主だけが、消費後に残りが無ければ既存の `discard_pending_scroll()` を呼ぶ** | 持ち主ごとに「この pass のホイールを全部受け取ったので、残量も終える」と宣言する | **採用**。egui は無変更。ポップアップの持ち主は今の「閉じる境界で捨てる」規則のまま |

### 2.2 捨てる条件と、混ざる経路

捨てる条件は 2 つで、両方を満たすときだけ捨てる。

1. その持ち主が、この pass で少なくとも 1 件のホイールイベントを実際に取り除いた。述語が外れた、対象の区間が古かった、などで 1 件も取り除かなかったときは捨てない。
2. 取り除いた後、この pass の `input.events` に `Event::MouseWheel` が 1 件も残っていない。残っていれば、後で別の持ち主 (ScrollArea を含む) が使う可能性があるので捨てない。その pass は今の挙動のまま。
   - 例: 全画面のパネルの上で、同じ pass に Ctrl+ホイールと通常ホイールが入る。Ctrl はズーム、通常はパネルの ScrollArea。条件 2 で捨てない。

確認した経路:

- **別の窓 (viewport)**: InputState は viewport ごとなので混ざらない。全画面・detached・root はそれぞれ自分の残量だけを捨てる。既存テスト `wheel_frame_tests.rs:1043-1145` は、子 viewport の消費が root のその pass の値を変えないことを固定している。次の pass の吐き出しも変えないことを、新しいテストで足す。
- **全画面の HUD ポップアップ**: 前面の対象のとき、`FsHudPopupWheelInput::take` がイベントと `smooth_scroll_delta` を先に退避する (`ui_fullscreen.rs:28645`, `38534-38563`)。全画面のホイール処理はイベントを見ないので、捨てる処理も走らない。overflow の所有はポップアップの矩形の中だけ (`38554`)。ポップアップの外の画像上で回したときは、画像の持ち主が受け取って捨てる。そのときポップアップ内はホバーされていないので、残量は元々ポップアップに当たらない。
- **全画面の左右パネル**: パネル上の通常ホイールは、全画面のホイール処理が受け取らない (`ui_fullscreen.rs:8421` の `!cursor_in_panel`)。イベントが残るので条件 1 で捨てない。
- **pass をまたぐ受け渡し** (フォルダツリー→一覧、パネル→画像、ポップアップ→画像、root の UI→埋め込みの閲覧):
  - egui の ScrollArea は、残量の吐き出しをホバー中の領域にしか当てない (`scroll_area.rs:1926`)。ポインタが元の領域を離れた時点で、元の領域は今でも残量を受け取らない。
  - そのため、新しい持ち主が捨てても、元の領域の動きは変わらない。
  - 例外はポインタがパネルの上のまま、通常ホイールの直後に Ctrl+ホイールでズームする場合。egui は残量全体を最後のイベントの修飾キーで分類する (`input_state/mod.rs:460-470`、`wheel_state.rs:129-141`) ので、今でもパネルの残量はズーム側へ回り、誰も読まない。変化しない。
  - 利用者の判断 (2026-11-20、統括経由): フォルダツリー→一覧の境界で残りが失われうる件は割り切る。上の理由で、実際には今と変わらない見込み。
- **一覧の popup / menu**: popup が開いていると `process_scroll` は早期 return する (`app.rs:63596-63606`)。ポインタがフォルダペイン内なら `process_scroll` 自体が呼ばれない (`app.rs:102573-102588`)。
- **タッチ・トラックパッド** (`InTouch`、8 pt 未満の Point): 残量を通らず直接その pass の delta に入る (`wheel_state.rs:169-176`)。古い残量が無ければ、捨てても影響はない。Shift/Alt による軸の付け替えと、イベントごとの修飾キーでの振り分けは変えない。

### 2.4 API の形

Sol の提案に従い、名前で役割を分ける。

- `consume_wheel_segment` と `consume_remaining_wheel_inputs`: 本番の呼び出し元はすべて生イベントの持ち主なので、生イベントの持ち主の操作として定義し直す。§2.2 の条件で残量を終える処理を中に入れる。
- `consume_wheel_input` (全部消費): 2 つに分ける。
  - 生イベントの持ち主用 (一覧 `process_scroll`): 全部消費し、§2.2 の条件で残量を終える。
  - ポップアップ・素通し防止用: 今の挙動のまま (イベントと今の pass の delta だけを消す。何も無い pass でも delta を消す既存の挙動を保つ)。
- 直接イベントを取り除いている持ち主 (ナビゲーター・シーク列など) は、取り除いた後に、残量を終える共有の関数を呼ぶ。
  - 共有の関数は条件 2 (残りが無いこと) を自分で確かめる。条件 1 は呼び出し側が「取り除いた」ときだけ呼ぶことで守る。
- 名前は実装担当が既存の命名に合わせて決める。条件を書いた場所が 1 か所になるようにする (同じ判定を各所に書き写さない)。

## 3. 挙動の変化

- **全画面の画像と一覧のホイール**:
  - ノッチごとの空描画がなくなる。描画は入力 1 回あたり 3 pass (入力の pass、egui の 2 回目、遅延付きに戻る pass) に戻る。
  - 動き (パン・ページ送り・ズーム・列数) は生のイベントから決まるので変わらない。
  - 3 pass は、他に再描画の理由が無い場合の値。ページ送りのアニメーション・読み込み・編集・再生などは、今までどおり別に描画を続ける。
- **一覧**: egui の一覧 ScrollArea が残量で毎 pass わずかに動き、App の値で戻されていた (`ui_main.rs:21727`、`app/grid_scroll.rs:281-285`、`scroll_area.rs:1390-1396`、`ui_main.rs:1884-1893`)。この見えない揺れもなくなる。
- **ナビゲーター・シーク列・そのメニュー**: 同じく空描画がなくなる。大きさ・時間範囲・メニューの行は生のイベントで決まるので変わらない。
- **全画面のカーソル自動非表示**: 今は残量の吐き出しも操作として数えている (`ui_fullscreen.rs:28543-28547`, `34159`)。変更後は、ホイールを止めた直後から非表示までの待ち時間が数え始められる。ホイールを止めてからカーソルが消えるまでが、最大で約 0.25 秒早くなる。
- **音楽ビューのタイムライン (利用者の判断済み)**:
  - 動画・音声の通常ホイールは、既定が前後のファイルへの移動 (`ring_shortcut.rs:2446-2448`、`#[default] NavigateItems`)。環境設定で音量の上げ下げに変えられる。どちらでも、全画面のホイール処理が消費する。
  - 中央のタイムラインの egui ScrollArea (`ui_fullscreen.rs:60569`、ホイール有効) はその後に描かれ、今は消費済みのホイールの残量で少し動く。量は 1 ノッチの大半で、165Hz では最初の pass の後に約 87% が残る。動くと手動の操作とみなされ、自動追従が 1 秒止まる (`ui_music_timeline.rs:805-822`、`ui_fullscreen.rs:60629-60653`)。
  - 既定 (項目移動) のとき: 新しい曲を開くと、自動追従の停止と前回のスクロール位置をリセットする (`app.rs:80583-80594`)。タイムラインは曲ごとに別の ScrollArea (`ui_fullscreen.rs:60575` の id に曲の番号)。残量は回してから約 0.25 秒で尽きるので、新しい曲の波形はほとんどの場合、尽きた後に描かれる。解析がすぐ終わる場合 (直近の曲の再利用など) だけ、新しい曲の先頭でタイムラインがわずかに動き、自動追従が 1 秒止まり得る (コードからの推論、実機は未確認)。見た目の変化はほぼない。
  - 音量のとき: 音量を変えるたびに波形が少し流れて自動追従が 1 秒止まる動きがなくなり、音量だけが変わる。
  - 変更後に中央のタイムラインを動かす方法: 中ボタンのドラッグ、スクロールバー、▲▼ ボタン。Ctrl+ホイールはタイムラインの尺 (1 行あたりの秒数) を変える (`ui_fullscreen.rs:60048`, `60099`)。スクロールではない。
  - 利用者の判断 (2026-11-20、統括経由): 受け入れる。判断の前に利用者が受けた説明は「既定 (前後のファイルへ移動) では見た目はほぼ変わらない。音量に設定しているときだけ、波形が少し流れて追従が 1 秒止まる動きがなくなる」。この説明のうち「Ctrl+ホイールの行送りは今のまま使える」は誤りで、正しくは上の 3 つの方法と尺の変更。統括に訂正を伝える。

## 4. 不変条件とテスト

- **生イベントの持ち主が、この pass のホイールを全部消費した場合**: 次の pass からは残量の吐き出しが無い。
  - `smooth_scroll_delta` が 0、`zoom_delta()` が 1.0。
  - 入力の pass から数えて 3 pass 目に、即時でない再描画の遅延へ戻る。
- **1 件も消費しなかった場合、または消費後にホイールが残っている場合**: 残量を捨てない。今の挙動のまま。
- **捨てた後に来た新しいホイール**: 普通に処理される。
- **ポップアップの持ち主**: 次の pass にも吐き出しが届き、ポップアップ内の ScrollArea が動き続ける (今の挙動の固定)。
- **別 viewport**: 子 viewport で捨てても、root の次の pass の吐き出しは、捨てない場合の基準と同じ。

テストの作り方 (Sol の提案):

- 再描画の数え方:
  - `app/tests.rs:37255` 付近の `root_repaint_delay` / `settle_repaint_state` の形を使い、`FullOutput` の `viewport_output[id].repaint_delay` を見る。
  - `Duration::ZERO` でなくなるまでを数える。カーソル・ツールチップの遅延付きの起床は許す。
  - 時刻は固定の刻みで進める。kittest の既定 (0.25 秒) では 1 ノッチの大半が最初の pass で吐き出されるので、`.with_step_dt(1.0 / 165.0)` か `1.0 / 60.0` にする。
- 何も起きない入力の pass には、本当に空の入力を使う。`wheel_frame_tests::frame` は毎回 `PointerMoved` を入れ、それ自体が再描画を続けさせる (`wheel_frame_tests.rs:15`) ので、そのまま繰り返さない。
- 全画面: `in_page_scroll::handler_tests::{app, seed, paint, run_in_viewport}` と、本番の合流 helper `collect_actual_merge` / `actual_merge` を使う。パンが動く場合と、端でパンが変わらない場合の両方を見る。
- 一覧: `background_click_scroll_regression_tests::harness_with_size` (`app/tests.rs:113096`) は、grid を描く前に `process_scroll` を呼ぶ。
- ポップアップ: フィットのポップアップのオフセットの検査と、整理先サブメニューの harness を使う。端から離れた位置で、pass ごとにオフセットが増え続けることを見る。
- 混ざる pass: 2 つの区間を同じ pass に入れるには `harness.input_mut().events` へ直接入れる。kittest の `event()` は別々の step になる。
- 追加の場合分け:
  - 生/生の混在 (音楽ビューの通常と Ctrl)。
  - 生/ScrollArea の混在 (パネル上の Ctrl+通常)。
  - 1 件も消費しなかった場合。
  - 捨てた後の新しいホイール。
  - 次の pass の `zoom_delta() == 1.0`。
- ナビゲーターとシーク列: `HeadlessNativeBatchTarget::draw_regions` (`render_core.rs:23717`) は、本番のシーク列の消費と実際の ScrollArea を組み合わせている。
- native の両メニュー: 1 Line ノッチでちょうど 1 行動き、空の idle 入力・1/165 秒刻みで 3 pass 以内に即時再描画を終える。矩形外と、シーク列メニューの `max_scroll == 0` ではイベントと当該 delta・残量を保持する。
- 計測: portable-smoke で承認済みの 3 種 (OS 入力 16%・2%・合成キー) を再計測し、ホイール区間の fps と UI スレッドの CPU を比べる。

## 5. detached viewer リワーク中のルールとの関係

- 全画面のホイール処理と detached の動画の消費は、detached の host viewport でも走る。
- 変更は既存の消費点に「残量も終える」を足すだけで、detached の述語・viewport の経路・入力の routing は変えない。
- 捨てる処理は viewport の残量全体に効く。InputState は viewport ごとなので、別の viewer context には効かない。同じ viewport の中の別の持ち主へは、§2.2 の条件 2 で効かないようにする。
- Sol (実装前レビュー、2026-11-20) は、「消費した持ち主の境界で、使われない平滑化を終えるのは構造的な修正で、症状パッチではない」に合意した。条件は、viewport 全体の取り消しと特定イベントの所有を区別して書くこと (上の 3 点目)。
- 実装後のレビューでも同じ主張への合意を取り、`docs/detached-rework-plan.md` の §11 に、触れた範囲と理由を記録する。

## 6. 範囲外

- egui の「request_repaint 1 回で 2 回描く」(候補 B)、root viewport の occluded 描画 (候補 A)、キーの 3 フレーム (候補 C)、拡大の作り直し (候補 D)。
- 永続データの変更はない。
