## 1. 何が起きているか (実測で確定)

利用者報告は「ZIP / RAR でホイールを高速に回すと『読み込み中』のまま進まなくなる」。
2026-09-03 の実測 (`bench_zip_seek` + 実機 perf log の再集計、数値は §1.174 に記載) で
因果が閉じた。

1. `App::start_fs_load_with_purpose` はページごとに `std::thread::spawn` する。**上限がない。**
2. `update_prefetch_window` は不要になった要求に cancel を立てるが、
   **worker 側の cancel 確認はデコード後にしかない**。不要と分かった処理も最後まで
   CPU と I/O を使い切る。
3. 結果、意図した先読み窓 17 (`prefetch_back` 4 + `prefetch_forward` 12 + 現在ページ) に対し、
   **実際の同時実行が最大 51 (3 倍)** になる。35.1 秒の区間の 29% で 17 を超えていた。
4. 10,000 エントリの書庫では、1 ページのうち **56ms が中央目次の再解析**で、
   これが同時数にほぼ比例して伸びる。51 本同時では 1 本あたり 998ms。
5. **現在ページの worker も 51 本のうちの 1 本**なので、利用者が見ているページ自身が
   約 1 秒待たされる。その間に来た入力がさらに worker を足すため窓が空かない。

438 件のロードのうち **349 件 (80%) が、全額を払い切ってから捨てられていた**。

**「先読み窓の件数」と「実際に動いている処理数」が一致していないことが本体**であり、
目次の再解析はその上に乗る定数倍 (大きい書庫でのみ効く) である。

## 2. 何を直し、何を直さないか

直す:

- 実行数の上限を持ち、**取消済みでも worker が終了するまで枠を占有させる**。
- 現在ページと見開きの相方を、先読みの後ろに並ばせない。
- 開始前の待ち行列を有限にし、窓から外れた未開始の先読みは開始せずに捨てる。
- 大きい書庫で目次を再解析しない。

直さない (今回の範囲外):

- 固定待ち時間を足してページ送り自体を遅くすること。**契約は §5 のまま維持する。**
- サムネイル代替、カラー化・補正、停止ページの最終画質への切り替え。現状の挙動を保つ。
- 寸法キャッシュの永続化・背景スキャン (採用仕様が未決定。§7.3 参照)。

## 3. 設計 — `FsPageLoadScheduler`

### 3.1 所有境界 (ここを間違えると別窓で壊れる)

**予算はプロセス全体で 1 つ、要求の所有は viewer context ごと。**
別窓を増やしても全体の実行数は増えない。これは
[detached-rework-plan.md](detached-rework-plan.md) の BA-7 (bundle と App-global の境界) に
沿った分割である。

| 対象 | 所有者 | 理由 |
| --- | --- | --- |
| 実行枠 (permit) の総数 | App-global に 1 インスタンス | CPU / I/O / 展開メモリは機械に 1 つしかない |
| 要求 (idx / purpose / 世代 / cancel) | `ViewerContextBundle::fs_pending` (現状のまま) | cancel と result が別 context へ漏れない |

`App` に detached 用の新しい `bool` / `Option` フラグは足さない (憲法 3)。
スケジューラは `Arc<FsPageLoadScheduler>` を 1 つ持つだけで、状態は型の内側に閉じる。

`fs_pending` は既に `ItemsGenerationMap<FsPendingValue>` で、破棄フックに
`cancel_fs_pending_value` が付いている。**チケットは `FsPendingValue` が RAII で持つ**ので、
context の破棄・世代切り替え・窓を閉じる操作は、既存の破棄経路をそのまま通るだけで
チケットの取消になる。新しい撤収経路を増やさない。

### 3.2 状態遷移 — 枠は「実際に終わる」まで返らない

```
受付 ──▶ 待機 ──▶ 実行 ──▶ 終了 (結果 / エラー)
          │         │
          │         └─▶ 取消中 ──▶ 終了 (枠はここで初めて返る)
          │
          └─▶ 取消 (未開始なので枠を取らずに消える)
```

**不変条件 (テストで縛る)**:

- 実行中 + 取消中の合計が、いかなる時点でも上限を超えない。
- `cancel` を立てただけでは枠は空かない。**実終了 / エラーで必ず返却される。**
- 待機中に cancel された要求は、**1 バイトも読まずに**消える
  (現在は読んでデコードしてから捨てている)。
- 枠の返却漏れが起きないこと。permit は RAII (`Drop`) で返す。`GlobalIoSemaphore`
  ([io_semaphore.rs](../src/io_semaphore.rs)) と同じ形にする。

実装は `Mutex + Condvar`。`try_lock + sleep` は禁止 (CLAUDE.md 並行処理節、
[async-architecture.md](async-architecture.md) §5.5)。

### 3.3 上限値 — PDF プールと同じ形にする

既存の `PdfWorkerPool` は「既定 5、うち 1 つを Critical 予約」という形を持つ。
**同じ形を採る** (新しい語彙を増やさないため)。

- 総枠: 既定 **6**。
- うち **2 枠を High 予約** (現在ページ + 見開きの相方)。先読みは残り 4 まで。

実測では、この書庫で 4 本同時なら 1 ページ 118ms、51 本なら 1,033ms。
**上限値は実測後に再調整する** (§8)。設定として露出するかは実測後に判断し、
本計画では固定値で入れる。

> 空きメモリなどの実行時状態で上限を変えない (CLAUDE.md「決定性優先」)。
> CPU 数のような静的な機械特性を使う場合も、設定だけで挙動が決まる形を崩さない。

### 3.4 優先度と昇格

| 優先度 | 対象 |
| --- | --- |
| `High` | `fullscreen_idx` のページ、および表示中の見開きの相方 |
| `Normal` | 先読み |

- 先読みで待機中 / 実行中のページが現在ページになったら、**取り消して投げ直さず昇格する**。
  取消と再投入を繰り返すと、既に払った読み出しを捨てることになる。
- 昇格は待機列の順序にのみ効く。**実行中のものは実行のまま**で、割り込み手段は持たない。
- `page_is_displayed` (App の既存述語) を判定の唯一の出所にする。同じ問いに 2 つ目の
  述語を作らない。

### 3.5 合流 (同じページの重複要求)

`fs_pending` は idx キーなので、**同一 context 内の重複は既に起きない**。
本計画で足すのは次の 2 点:

- 別 context が同じ書庫の同じエントリを要求した場合も、**結果は合流させない**。
  合流させると result の宛先が 2 つになり、世代の対応付けが壊れる。
  同じ問いに 2 つの所有者を作らない。**共有するのは実行枠の上限だけ**にする。
- 先読み → 現在ページの昇格は、上記のとおり同一チケットの優先度変更として扱う。

### 3.6 取り消せる境目を作る

現在、`decode_canonical_image` は書庫読み出しとデコードを行い、
**呼び出し元がその後にはじめて cancel を確認する**。以下の境目で確認を入れる:

1. 枠の取得直後 (`acquire_cancellable` 相当で、待機中の cancel は即座に抜ける)。
2. 書庫からの読み出し完了直後、デコード開始前。
3. アニメーションの全フレーム展開のフレーム境界。

中断できない処理 (PDFium レンダ、Susie ワーカーの IPC など) は**終了まで枠内で待たせる**。
UI スレッドでは待たない。

> 段階を増やすときは、**取り消せない処理を取り消せるように見せかけない**。
> 早期 return には型付きの理由を残し、無言で抜けない。

## 4. ZIP 目次の再利用

`zip` 2.4.2 の `ZipArchive<R>` は `Clone` で、解析結果を `shared: Arc<Shared>` として持つ。
**reader が `Clone` なら、目次を再解析せずに読み出しハンドルを増やせる。**

採る形 (どちらかを実測で選ぶ):

- **(a) 位置指定読みの reader**: 1 つの `File` を `Arc` で共有し、`seek` 位置を
  clone ごとに独立に持つ reader を書く。`ZipArchive` を clone すれば目次は共有され、
  メモリは 1 冊分で済む。並列読み出しとシーク位置の独立性を型で保証できる。
- **(b) 有界ハンドルプール**: `ZipArchive<BufReader<File>>` を上限つきで使い回す。
  実装は単純だが、目次のメモリを枠数ぶん持つ (10,000 エントリ × 6 枠)。

いずれの場合も保つもの:

- **失効**: ファイルの更新 (`mtime` + サイズ) が変わったら捨てる。
- **名前解決の段は複製しない**。`resolve_entry_index` (正確名 → `\` 区切り → 復号名) が
  唯一の出所である ([zip_loader.rs](../src/zip_loader.rs) の doc コメント参照。
  過去に別経路で書いて日本語書庫の寸法が 1 件も取れなくなった)。
- 入れ子 ZIP (`NESTED_CACHE`)、CRC、エラー処理、RAR 経路の挙動。
- **全処理を 1 本のロックで直列化しない**。表示待ちが増える。

キャッシュの上限は書庫数で有界にし、フォルダ移動・書庫切り替えで捨てる。

> 効果はエントリ数に比例する。27〜669 エントリの通常の書庫では 0.15〜4ms しかないので、
> **これは大きい書庫のための改善であり、詰まりの主因ではない** (主因は §3)。

## 5. 順送りと直接シークの契約 (混ぜない)

- **順送り** (ホイール / キー): 「途中ページを飛ばさず表示する」既存方針を保つ。
  能力を超えた入力を無制限に後追いしない。**受付の段階で有界にする**のであって、
  固定待ち時間を足してページ送りを遅くするのではない。
- **直接シーク** (シークバー / ページ指定): **最新の指定位置を優先する**。
  途中位置は表示対象ではないので、待機中の中間要求は開始せずに捨てる。

この 2 つを 1 つの述語で表現しない。どちらの契約で来た要求かを型に持たせる。

## 6. 派生 — 静止 PNG の誤った「アニメーションを読み込み中…」

**確認済みの欠陥。** `FsLoadPurpose::animation_expansion_started_at_for`
([app.rs](../src/app.rs)) は `Self::Display { started_at } => Some(started_at)` と、
**通常のページ表示要求を無条件にアニメーション展開扱いにしている**。
`item_may_expand_animation` は拡張子 (`gif` / `png` / `webp`) だけで候補にするので、
静止 PNG のページ読み込みが 150ms を超えると
`draw_animation_expansion_progress` が「アニメーションを読み込み中…」を出す。

**直し方**: 「一般の画像読み込み」と「形式を確認した後のアニメーション展開」を分ける。
拡張子は候補の絞り込みにしか使えないので、**worker が実際に複数フレームだと判定してから**
通知する。既存の `fs_early_dims` と同じ形で、worker から早期に「これはアニメーションで
N フレーム」を伝える経路を足す。判定材料が来るまでは通常の読み込み表示にする。

§3 で詰まり自体が解消すると 150ms を超える頻度は下がるが、**誤りは残る**ので別に直す。

## 7. 派生 — 目盛りが読み込みにつれて細かくなる

### 7.1 機構 (コード上は成立する)

見開き・非連結読みでは `build_spread_display_units_for_nav` の表示単位数から目盛りを作る。
**未知寸法は縦長扱い**なので 2 ページで 1 単位に組まれる。表示 / 先読み / サムネイル読込で
横長と判明すると単独の単位になり、**後続のペアの切れ目がずれて総単位数が変わる**。
横長 1 枚につき必ず 1 本増えるわけではなく、目盛りの間引きもある。

### 7.2 再現条件 (2026-09-03 に切り分け)

前回の調査で使われた `text2img_flat_10000_stored.zip` は、**200 枚を抽出した限り
すべて縦長** (1792×2304 が 196、他も縦長)。**この書庫では上の機構は発火し得ない**ため、
「未再現」だったこと自体が条件と整合する。

再現には横長混在の書庫が要る。手元では
`testimage/zip/36e09bc4_ものけもの四夜_ふるからー版_特典用.zip` が 27 枚中 1 枚が横長
(見開きを 1 枚で取り込んだ体裁) で、最小の再現候補になる。まず
**`build_spread_display_units_for_nav` の純ロジックに対する単体テスト**で、
寸法が判明するにつれて単位数が変わることを固定する。実機の再現はその後でよい。

### 7.3 採用仕様は未決定

寸法キャッシュの先行取り込み・永続化・ヘッダスキャンは候補だが決めていない。
Remote の `collect_zip_entry_dims` は外側 ZIP を一度開いて各エントリの先頭最大 64KiB を
読む既存部品で、RAR / 入れ子には別の対応が要る。背景スキャンだけでは完了前の組み替えが残る。
全件確定待ちや元ページ番号基準のシークへ変える場合は UX 判断が別途要る。
Remote 側 §1.0i で「近傍だけ + 非同期補完」を不採用とした判断も参照する。

**本計画では 7.2 の単体テストまでを範囲とし、仕様選定は別途行う。**

### 8.1 S1 の再計測と、そこで決めたこと (2026-09-04)

利用者の実機セッション (10,000 エントリ書庫、`--perf-log`) を解析した結果。

**上限は守られている**: `running + cancelling` の最大は **6 で違反 0**。worker スレッドの
同時数は 51 → **18** (大半は permit 待ちで park)。現在ページの完成は
p50 762ms → **148ms**。取消の 60% (317/529) が **1 バイトも読まずに** 終わるようになった
(`cancel_before_acquire`、p50 22ms)。

**残っていた待ちの正体**: 表示中ページの permit 待ちは p50 1ms だが、**129 回中 16 回で
20ms 超 (最大 201ms)** 待っていた。その 16 回は**すべて、6 枠全部が取消済み worker で
埋まっていた** (`running=0` / `cancelling=6`)。セッション全体でも取消中が **p50 5 枠 / p95 6 枠**。

**原因は旧規則との重複だった**。`update_prefetch_window` の「現在ページがロード中なら他の
pending を全部キャンセルする」が毎フレーム走り、取消済み worker は実終了まで枠を返さない
(cancel → 実終了は p50 591ms、最大 2,836ms) ので、**予算が丸ごと不要な仕事で埋まる**。
旧規則は「cancel すれば即座に空く」という、いまは成り立たない前提の上に立っていた。

→ **旧規則を撤去した。** 現在ページの保護は High 予約枠が担う (実測 p50 1ms)。
先読みの新規開始を現在ページ完成まで見送る early return は残す。
[async-architecture.md](async-architecture.md) §3.3 を更新済み。

### 8.2 まだ残っている判断

**worker はページごとの使い捨てスレッドのまま。** スケジューラは実行数を縛るが、待機中の
要求もスレッドを 1 本占める (実測の待機数は p95 8 / 最大 16)。park 中は CPU を使わないので
S1 の目的は満たすが、「受付・待機・実行を所有する」構造の理想形はワーカープールである。
プール化するかは、旧規則撤去後の待機数を測ってから判断する。

**取消済み worker が枠を返すまでが長い** (p50 591ms)。書庫読み出しの内側に取消の境目が
無く、目次の再解析を最後まで払ってからでないと cancel に気付けないため。
**S2 (§4) がこの区間そのものを削るので、S2 後に再測する。**

## 9. 回帰確認

### 9.1 状態テスト (スケジューラ)

遅い読み出し / デコーダを注入し、要求を連打しても:

- **取消中を含む実行数と待機数が上限内**である。
- cancel を出しただけでは枠が空かず、**実終了 / エラーで必ず返却される**。
- 待機中に取り消された要求は読み出しを開始しない。
- 昇格が、既に払った読み出しを捨てないこと。

### 9.2 経路の網羅

同一ページの再要求、見開き両側、ホイール / キー押しっぱなし / シーク、逆方向へ戻す操作、
別書庫への移動、閉じる操作、**別窓 2 つ**。

- 古い結果が新しい context へ入らない。
- 片方の cancel が他方の有効な要求を消さない。
- 通常画像 / ZIP / RAR / PDF の同等経路を監査する (同じ形の入口を数えてから直す)。

### 9.3 実機 smoke

`.\scripts\build-dev.ps1` の成果物で、10,000 エントリ書庫と通常サイズの書庫の両方。
アイドル健全性 (`check-idle-health.ps1`) も回す (新しい待機ループを足すため)。

## 10. 記録 (detached リワーク中の手続き)

本計画は viewer context の所有境界に触れるため、CLAUDE.md「Detached viewer リワーク中の
ルール」に従う。着手前に [detached-rework-plan.md](detached-rework-plan.md) §2 を読み、
**症状パッチではなく構造的修正であることに ClaudeCode と Codex の双方が合意**したうえで、
触れた範囲と判断理由を同書 §11 へ記録する。
